## 1. 消息队列基础

**本节问题**

- [1. 点对点队列与发布订阅在消息分发上有什么区别？](#1-点对点队列与发布订阅在消息分发上有什么区别)
- [2. 为什么选择 MQ，而不是同步接口调用或线程池异步执行？](#2-为什么选择-mq而不是同步接口调用或线程池异步执行)
- [3. MQ 与数据库都要落盘，为什么它们的高并发写入能力和访问模式可能不同？](#3-mq-与数据库都要落盘为什么它们的高并发写入能力和访问模式可能不同)

### 1. 点对点队列与发布订阅在消息分发上有什么区别？

点对点队列通常让同一组消费者竞争处理任务，一条交付由其中一个消费者承担；发布订阅让多个独立订阅分别收到同一事件。

实际产品常通过“主题加消费组或独立队列”组合两种语义，因此不能只按产品名字判断它属于哪一种。

**追问 1：订单创建事件要分别触发库存、通知与统计时，应怎样组织消费关系？**

库存、通知、统计各使用独立消费组或独立绑定队列，每组内部多实例分担任务。

若把三个业务放在同一竞争队列里，它们可能各拿到一部分事件，而不是每个业务都处理所有订单。

### 2. 为什么选择 MQ，而不是同步接口调用或线程池异步执行？

MQ 适合把请求受理与后续处理解耦，让独立进程通过可保留的消息传递工作，并在可控范围内削峰和重试。

- 线程池只解决进程内异步，进程退出可能丢掉内存任务；同步调用能立即取得业务结果，但上游更容易受下游延迟影响。
- 引入 MQ 是把问题重新分配，不是消除一致性和容量限制。

**追问 1：同步调用、进程内线程池与独立 MQ，在响应时机和失败影响范围上有什么区别？**

同步调用等待远端结果；线程池可让当前线程先返回，但任务仍依附本进程；MQ 可跨进程保存并投递任务。

返回“已受理”不能冒充“业务已完成”，接口应提供结果查询或通知。

**追问 2：削峰之后，积压、延迟和一致性问题由谁负责处理？**

生产端限制接受速率和可靠发送，Broker 控制存储容量与保留策略，消费者处理积压和幂等，业务负责超时与补偿。

持续输入超过输出时，任何有限队列最终都会耗尽，必须限流、扩容或拒绝。

**追问 3：比较 Kafka、RocketMQ、RabbitMQ 时，哪些业务需求应优先于单一吞吐指标？**

先比较顺序范围、延迟消息、事务消息、路由、回放、消息规模和运维能力。

Kafka 偏分区日志与高吞吐回放，RocketMQ 提供丰富业务消息能力，RabbitMQ 强调队列与路由；不能脱离版本和负载给出绝对优劣。

### 3. MQ 与数据库都要落盘，为什么它们的高并发写入能力和访问模式可能不同？

MQ 往往把数据顺序追加到日志，索引较少，并通过批量写入、页缓存和顺序消费摊薄成本；关系数据库除了保存数据，还可能维护多个索引、唯一约束、MVCC 和事务锁，并支持随机更新与复杂查询。

两者承担的工作不同，不能以同样“落盘”推导吞吐必然相同。

**追问 1：从顺序追加、索引维护、事务语义、批处理与读取方式比较，而不是只回答“MQ 更快”。**

比较时固定消息大小、批次、复制数、刷盘和确认级别。

- 数据库批量追加也可能很快，MQ 开启更强持久化或大量小消息也会变慢。
- Kafka 的某些零拷贝主要优化文件到网络读取，不应笼统说“MQ 写入完全不复制”。

## 2. 消息可靠性

**本节问题**

- [1. 如何沿生产、存储和消费三段链路设计消息防丢方案？](#1-如何沿生产存储和消费三段链路设计消息防丢方案)
- [2. 消息已处理但 `ACK` 丢失时，系统为什么无法仅凭超时判断真实结果？](#2-消息已处理但-ack-丢失时系统为什么无法仅凭超时判断真实结果)
- [3. 生产者在发送超时后重试，如何避免同一业务事件被重复写入消息系统？](#3-生产者在发送超时后重试如何避免同一业务事件被重复写入消息系统)

### 1. 如何沿生产、存储和消费三段链路设计消息防丢方案？

防丢要覆盖业务事件产生、生产发送、Broker 持久化复制以及消费落地四个环节。

1. **业务事件：** 业务提交与发送之间用 outbox 或事务消息衔接。
2. **生产发送：** 发送检查确认并有限重试。
3. **消息存储：** Broker 配置可靠存储。
4. **消费落地：** 消费者先可靠完成业务再确认，同时以事件 ID 幂等。

还要有监控、对账和补发能力。

**追问 1：生产端发送、`Broker` 保存和消费端处理，分别在哪些位置可能出现结果未知或数据丢失？**

业务提交后进程未发送就退出，事件可能根本没进 MQ；发送超时可能已写入但确认丢失；Broker 未达持久化要求便故障可能丢数据；消费者先 ACK 后业务失败可能永久漏处理。

**追问 2：确认、持久化与副本机制各自覆盖什么故障，为什么启用其中一项还不够？**

生产确认说明到达特定服务端边界，不代表消费者成功；持久化防部分进程或机器故障，副本防特定节点故障；消费 ACK 表示处理责任交还 Broker。任何一项都不能自动覆盖另一系统的事务。

**追问 3：故障后需要核对和补发时，怎样凭业务事件标识还原一条完整链路？**

从唯一事件 ID 关联业务事务、发送记录、Broker 位点与消费结果，确定缺失区间而不是盲目全量补发。

补发复用同一业务事件 ID，消费者按相同幂等规则处理，并记录补偿结果和异常。

### 2. 消息已处理但 `ACK` 丢失时，系统为什么无法仅凭超时判断真实结果？

超时只能说明在等待期限内没收到确认，不能区分“对方没执行”和“执行成功但响应丢失”。

可靠系统通常接受消息可能重投，再通过业务幂等把重复交付转换为单次有效结果。恰好一次必须说明限定的系统边界与故障假设。

**追问 1：“至多一次”“至少一次”和“恰好一次”分别约束哪一层的消息交付或处理？**

至多一次允许丢失但不重试同一交付；至少一次通过重试降低丢失风险但可能重复；恰好一次描述某个受控范围内每条输入产生一次有效结果。交付次数与外部业务副作用次数是两个层次。

**追问 2：消费者完成业务写入后确认丢失，发送方能否仅凭超时判断业务是否执行？**

不能。确认丢失和执行前退出对发送方可能表现相同。

应查询业务事件状态或安全重投，让消费者利用幂等记录识别已经完成的操作，而不是根据超时反向推断未执行。

**追问 3：消息系统内部的恰好一次保证，能否自动覆盖外部数据库或支付接口的副作用？怎样说明保证范围？**

不能自动覆盖。Kafka 内部事务可协调 Kafka 输出与消费位点，但 MySQL、支付调用另有事务边界。

外部系统需同事务去重、幂等接口或可靠补偿，不得仅在简历或答案里写“开了 EOS 所以全链路一次”。

### 3. 生产者在发送超时后重试，如何避免同一业务事件被重复写入消息系统？

优先使用消息系统提供的幂等生产机制，并为同一业务事件保存稳定事件 ID。

- 重试同一发送与业务重新创建一个新发送是不同情况，客户端内部幂等通常不能识别应用重启后人为产生的另一条等价事件。
- 业务端仍要约束重复事件产生，消费端也要防重复副作用。

**追问 1：生产端幂等与消费端幂等各覆盖哪一段链路，为什么不能相互替代？**

生产端幂等减少网络重试造成的重复写入；消费端幂等处理重投、消费重启、人工回放以及上游业务重复。

即使 Broker 只存一份，消费者业务提交后 ACK 丢失仍会重复处理，所以两者不能互替。

## 3. 消息消费机制

**本节问题**

- [1. 消费者如何把消息去重与业务更新组合起来，避免重复扣款或重复扣库存？](#1-消费者如何把消息去重与业务更新组合起来避免重复扣款或重复扣库存)
- [2. 消费失败后如何设计重试、退避和死信处理？](#2-消费失败后如何设计重试退避和死信处理)
- [3. 全局有序、分区有序与同一业务 key 有序有什么区别？](#3-全局有序分区有序与同一业务-key-有序有什么区别)
- [4. 订单超时等需求应如何选择延迟消息或定时扫描方案？](#4-订单超时等需求应如何选择延迟消息或定时扫描方案)

### 1. 消费者如何把消息去重与业务更新组合起来，避免重复扣款或重复扣库存？

将事件 ID 的唯一记录与业务更新放进同一个数据库事务。

- 首次事件插入成功后执行业务，再一起提交；重复事件触发唯一冲突时读取已有处理结果，不再次修改。
- 关键是去重记录和业务效果共同成功或共同回滚，而不是在另一个缓存中独立写“已消费”。

**追问 1：先写已消费标记再执行业务，与先执行业务再写标记，各有什么故障窗口？**

先标记后业务：进程中途退出会导致重投被跳过但业务未完成；先业务后标记：中途退出后重投会再次执行。

只有同一个原子提交边界，或另有严谨状态协议，才能关闭这个窗口。

**追问 2：事件 ID、唯一约束与业务更新怎样放在同一个本地事务中？**

可使用以下事务结构，事件表以 `(consumer_name,event_id)` 为唯一键：
```sql
START TRANSACTION;
INSERT INTO consumed_event(consumer_name, event_id) VALUES ('inventory', ?);
UPDATE inventory SET available = available - ?
WHERE sku_id = ? AND available >= ?;
-- 应用检查受影响行数；不符合业务条件则按业务协议记录失败或回滚。
COMMIT;
```
实际参数通过预编译绑定。业务需要保存“失败但已处理”的终态时，应明确写入结果，而不是一律无限重试。

**追问 3：消费者重复、并发收到同一事件时，怎样返回或继续处理，而不把唯一键冲突当成未知系统故障？**

并发插入由唯一约束裁决；重复者只在确认原事务已提交且内容匹配后返回已处理结果。

若同事件 ID 携带不同业务参数，应作为数据冲突告警，不能直接忽略。其他数据库错误也不能统统当作重复。

### 2. 消费失败后如何设计重试、退避和死信处理？

暂时故障采用有上限的指数退避与随机抖动，避免瞬间重试风暴；格式错误、永久业务拒绝等进入明确失败或死信流程。

- 死信需要责任人、诊断信息、修复与受控重放，不是把错误藏起来。
- 严格顺序业务还要明确失败时是否阻塞同 key 后续事件。

**追问 1：可恢复的暂时失败与永远无法处理的坏消息，是否应该使用同一种重试策略？**

短时网络或限流可稍后重试；非法格式、缺必需字段或不支持的版本反复重试通常无用。

不可仅按异常类粗分，还需结合下游错误码和操作幂等性，资金结果未知先查询。

**追问 2：重试次数、退避和死信处理怎样防止无限循环与资源耗尽？**

记录尝试次数、最初发生时间、下次执行时间和错误原因，设置最大次数与总期限，超限进入死信并告警。

重放沿用事件 ID，限制速率，避免修复后把全部历史失败同时压到下游。

**追问 3：严格顺序业务中，一条失败消息长期阻塞后续消息时，应怎样权衡顺序与可用性？**

跳过坏消息可能破坏状态依赖；一直阻塞会降低可用性。

可按业务 key 隔离暂停，人工或自动修复后续跑，或设计允许跳跃的版本状态机。不得对要求严格顺序的链路静默跳过。

### 3. 全局有序、分区有序与同一业务 key 有序有什么区别？

全局有序要求所有消息共享一个总顺序，通常明显限制并行度；分区有序只在一个分区内有顺序；同业务 key 有序允许不同 key 并行，只要求一个实体的事件按其业务次序完成。

Broker 记录顺序不自动等于消费者副作用完成顺序。

**追问 1：严格顺序消费遇到一条失败消息时，继续消费与阻塞等待分别会牺牲什么？**

继续处理可能使取消先于创建、支付先于订单准备；阻塞等待保住顺序但会拖延后续消息。

常见做法是按 key 隔离、限次重试、状态校验和人工修复，而不是在一个全局队列上让所有业务陪同等待。

### 4. 订单超时等需求应如何选择延迟消息或定时扫描方案？

延迟消息适合大量到期触发，减少频繁扫描，但实际交付会受积压、故障和时间精度影响；定时扫描以数据库到期时间为依据，易于补偿，但需要合适索引、分批与调度控制。

订单关单通常以延迟触发为主、扫描兜底，最终通过状态条件更新确认是否仍可关闭。

**追问 1：触发精度、执行可靠性和补偿成本如何权衡？**

把“计划到期”“触发到达”“业务完成”分开。允许秒级误差可采用相应延迟机制；严格时限还需容量预留和监控。

任何触发都可能重复或迟到，必须复核支付状态，关闭与支付冲突由业务事务协调。

### 1. Kafka 的 `Topic`、`Partition`、`Broker` 与消费组如何组织一条消息的完整生命周期？

Topic 是逻辑消息类别，Partition 是有序追加日志与并行单位，Broker 保存分区副本并提供生产和消费请求，消费组维护独立的分区分配与读取进度。

生产者选择分区并写入其 Leader，消费者按分配从分区读取，完成业务后提交下一次读取的 offset。

**追问 1：生产者怎样选择 `Topic` 与 `Partition`，`Broker` 怎样保存并提供读取？**

可显式指定分区，或按 key 和分区器定位；无 key 的批量分发策略还依客户端版本。

Broker 将记录追加到分区日志并复制给副本，按 acks 等条件确认，消费侧按 offset 拉取保留范围内的记录。

**追问 2：消费组、分区分配与 `offset` 分别在消息读取过程中承担什么职责？**

组内协调谁负责哪些分区，offset 表示每个分区进度，不是整个 Topic 的统一序号。

提交值通常是最后连续处理完成记录的下一位；独立消费组各自保存进度，互不因对方消费而删除消息。

### 2. Kafka 如何通过日志组织、顺序写、批处理与零拷贝获得高吞吐？

Kafka 用分区日志顺序追加、分段文件、批量发送和压缩降低每条记录的固定成本，并利用操作系统页缓存。

- 文件向网络发送时可采用减少用户态复制的路径；TLS 等条件可能改变实际路径。
- 高吞吐来自整体访问模式，不是单靠“消息在磁盘上所以快”。

**追问 1：日志分段及索引如何支持按 `offset` 或时间定位消息？**

每段以起始 offset 标识，offset 稀疏索引将逻辑位置映射到文件近似物理位置，再顺序扫描到目标记录；时间索引先定位相关 offset。

稀疏索引节省空间，但不是每条消息都有一个完整索引项。

### 3. Kafka 的副本、`ISR`、`acks` 与 `min.insync.replicas` 怎样共同约束写入确认？

副本数决定冗余，ISR 表示当前跟得上的同步副本集合；acks 决定生产确认条件，min.insync.replicas 在 acks=all 时约束允许写入所需的最小同步副本数。

典型配置是副本 3、min ISR2、acks all，并关闭不安全选主，但这仍不能代替业务 outbox 和消费幂等。

**追问 1：`acks`=0、`acks`=1 与 `acks`=all 分别等待什么，`ISR` 为什么可能变化？**

acks=0 不等待 Broker 确认；1 等 Leader 本地追加确认，不等全部副本；all 等当前 ISR 满足相应复制确认条件。

ISR 会因副本落后、恢复或故障变化，所以 all 不是固定等待三个节点。

**追问 2：`ISR` 副本数低于写入所需条件时，怎样在写入失败与继续可用之间取舍？**

当 ISR 低于最小要求，拒绝相关写入可保护可靠性但牺牲可用性；降低门槛能继续写，却增加单副本故障丢失风险。不能把重试错误简单吞掉再向用户报告可靠完成。

**追问 3：为什么 `acks`=all 不应简单解释成“任意多数派确认”，这些配置又不能自动覆盖哪些业务故障？**

ISR 不是随便选取的多数节点，而是特定同步集合。

确认也不自动表示每副本逐条 fsync，更不表示数据库已提交或消费者成功。应用重发、业务未发送和外部副作用仍需独立保障。

### 4. Kafka 怎样在同一消费组内分配分区，并让不同消费组独立消费？

普通订阅消费者在同一组内共享分区，每个分区在稳定分配下由一个成员负责，一个成员可负责多个分区；不同组独立读取同一日志，各自维护位点。

该模型适用于普通消费组，不要与其他新型共享消费语义混为一谈。

**追问 1：一个 `Topic` 有 4 个分区，同一消费组运行 6 个普通订阅消费者时，并行消费能力受什么限制？**

只有 4 个分区，最多 4 个普通消费者同时获得分区，另外 2 个可能空闲。

单个消费者内部线程池能并发业务处理，但不自动突破分区顺序和位点提交的约束。

**追问 2：再创建一个独立消费组后，它的进度与原组有何关系？**

新组有独立 group.id 与提交位点，可从其起始策略读取。

原组已经消费并不意味着记录被删除，新组是否还能读取取决于日志保留范围。

**追问 3：消费者离开或重新加入时，哪些分区与进度状态需要重新协调？**

协调器重新分配受影响分区，旧成员需停止相关处理并提交安全进度，新成员从有效位点恢复。

尚未提交的工作可能重做，已经失去分区所有权的任务不能继续盲目提交后续位点。

### 5. 根据给定故障时序，分析 Kafka 消费位点与数据库更新之间的重复消费风险。

题设：消费者手工提交 offset；数据库更新不是 Kafka 事务的一部分。

```text
1. 消费者收到订单事件 E。
2. 消费者在数据库中扣减库存并提交事务。
3. 进程在提交该消息对应消费进度前退出。
4. 消费者重新启动并恢复消费。
```

先假定当前没有业务去重机制，再设计改进方案。

重启后从已提交的旧 offset 恢复，事件 E 可能再次被读取；没有幂等时库存会再次扣减。

- 先提交数据库再提交位点提供的是可能重复的处理；把顺序反过来又可能漏处理。
- 正确改进是在数据库本地事务中同时记录 E 的已处理状态和库存变化，位点随后提交。

**追问 1：消费者重新启动后，哪些消息可能再次被读取，数据库会出现什么重复效果？**

从旧提交位点到崩溃前已处理但未提交进度的记录都可能重放，不只有最后一条。

若每次都直接执行扣减，重复事件会产生额外业务副作用。

**追问 2：把提交 `offset` 移到数据库更新之前，会产生哪一种相反风险？**

先提交 offset，再更新数据库，中间退出会让消费者恢复时跳过尚未落地的事件，造成漏扣或业务遗漏。

交换两次操作顺序无法让两个独立系统自动原子提交。

**追问 3：事件唯一 ID 与数据库本地事务怎样共同避免重复生效，为什么只调整提交先后顺序不够？**

用稳定事件 ID 建唯一约束，与库存更新同事务提交；重投时唯一冲突表明已完成或需核对既有结果，不能再扣。

提交消费进度只覆盖每个分区连续完成的范围，不能越过尚未处理的较小 offset。

### 6. Kafka 的幂等生产者和事务机制各解决什么问题？

幂等生产者通过生产者身份、分区序号等机制识别客户端重试，减少同一发送被重复追加；事务把多个 Kafka 写入以及相应消费位点纳入共同提交或中止的边界。

消费者需使用 read_committed 才按提交结果过滤事务记录。两者都不是任意业务请求的永久去重系统。

**追问 1：发送重试中的幂等，与一批 Kafka 写入共同提交，分别解决什么问题？**

网络重试去重主要针对同一生产会话的发送序列；事务可跨多个分区组织一批输出的可见性。

应用重新生成一个新事件再发送，不一定被视为同一重试，需要业务 ID 控制。

**追问 2：读取 Kafka、处理、再写回 Kafka 的流程，哪些读写可以处于同一事务边界？**

在事务中写出处理结果，并通过 sendOffsetsToTransaction 提交输入消费进度；事务提交后输出和进度共同生效，失败则中止并重读。

需要正确的 transactional.id、生产者隔离和消费组元数据处理。

**追问 3：处理过程中还更新 MySQL 时，为什么不能直接把 Kafka 的保证当成数据库也恰好执行一次？**

MySQL 不参与普通 Kafka 事务，数据库提交与 Kafka 提交之间仍有故障窗口。

- 可让数据库去重与业务更新同事务，或使用 outbox/CDC。
- 不要把 Kafka Streams 内部语义扩展成所有第三方系统的恰好一次。

### 7. Kafka 的 `Controller` 与 `GroupCoordinator` 分别管理什么状态？

Controller 管理集群元数据、Broker 状态、分区副本和 Leader 等；GroupCoordinator 管理消费组成员、分配协调及位点相关状态。

前者回答数据由谁承载，后者回答某组消费者由谁处理分区。两种协调发生在不同层次，故障影响也不同。

**追问 1：分区 `Leader` 变更与消费组 Rebalance 有什么区别？**

分区 Leader 变化是副本服务角色切换；Rebalance 是消费组分区所有权调整。

Broker 故障可能同时触发二者，但消费者加入只需组重新分配，不意味着业务分区重新选主。

**追问 2：元数据仲裁为什么不等于业务分区复制？**

KRaft 管理元数据日志的一致性；普通 Topic 数据仍按 Kafka 分区复制、ISR 和确认机制处理。

不能因为元数据使用 Raft，就把每个业务分区的 acks all 解释成 Raft 多数派提交。

### 8. Kafka Rebalance 由哪些事件触发，会怎样影响正在执行的消费？

成员加入、退出、心跳超时、处理超时、订阅或分区变化，都可能使组重新分配。影响包括分区暂停、所有权转移和未提交记录重放。

应按经典 eager、cooperative 或新消费协议分别分析，不能一概说每次都让所有消费者全停。

**追问 1：哪些成员变化、订阅变化或超时可能触发重新分配？**

显式关闭、进程崩溃、超过 session timeout 或 max.poll.interval，以及新增订阅分区都可能触发。

静态成员和不同协议会改变时机与范围，需看客户端与 Broker 配置。

**追问 2：正在处理的数据与尚未提交的 `offset`，遇到分区转移后需要怎样交接？**

撤销分区前停止接收该分区新任务，等待可控范围内任务完成，只提交连续完成的进度；未完成部分交给新成员重做。

外部已完成但未提交位点的操作依幂等记录避免再次生效。

**追问 3：怎样结合所用消费协议与分配策略分析停顿和重复处理，而不把不同版本行为混在一起？**

eager 通常先撤销全部再分配；cooperative 倾向增量迁移；新协议由服务端承担更多协调职责。

调优成员稳定性、批量处理时间和分配策略，同时用实际 rebalance 日志验证，而不混用各版本默认值。

### 9. Kafka 消费者处理单批消息过久时，心跳与 poll 间隔会如何影响组成员资格？

心跳表示进程仍可通信，poll 间隔约束消费者是否持续推进处理；后台心跳正常也不意味着可以无限久不 poll。处理一批过久可能失去组资格并引发分区重分配。

应限制每批记录、单条处理耗时和外部依赖超时，再合理配置处理间隔。

**追问 1：如何在提高批量吞吐的同时避免反复 Rebalance？**

根据最坏合理处理时间设置 max.poll.records 和 max.poll.interval.ms，优化慢 SQL/RPC，必要时 pause 分区并持续协调，而不是只把超时调到极大。静态成员和新组协议还需分别确认行为。

**追问 2：消费任务转到线程池后应如何提交位点？**

KafkaConsumer 通常不能被多个线程任意并发调用；由消费线程管理 poll、pause 和提交，工作线程回报完成。

每个分区只提交连续已完成区间的下一 offset，例如 10 未完成、11 已完成，不能提交 12 跳过 10。

### 10. Kafka 如何保证同一业务实体的消息顺序？

同一业务实体使用稳定 key，并确保所有生产路径采用一致分区规则，使记录进入同一分区；消费侧按该 key 串行推进实际副作用。

Kafka 提供分区日志顺序，但多个独立生产者的业务因果顺序、重试以及消费内部并发仍需应用约束。

**追问 1：生产者怎样把同一业务实体路由到同一分区，消费者读取顺序能保证什么？**

如订单 ID 作为 key，同一分区读取按 offset 递增。

这个顺序是日志追加顺序，不必然等于不同主机的创建时间；需要因果关系时增加实体版本或序列号。

**追问 2：生产端重试或消费端把同分区消息并行执行，可能在哪一步破坏业务完成顺序？**

关闭幂等且允许多个在途批次时，前批失败重试可能落到后批之后；消费者将同分区消息全部扔进线程池，则后消息可能先提交业务。

应使用满足幂等顺序要求的生产配置，并按 key 串行或版本条件处理。

**追问 3：增加分区数量后 key 路由可能变化，顺序业务扩容前应怎样规划？**

哈希取模的分区数变化会改变路由，旧分区尚有未消费记录时新记录可能先处理。

可预留分区、稳定业务分片映射，或暂停写入并迁移排空后切换；不能直接扩分区就承诺旧新全链路顺序不变。

### 11. Kafka 的日志删除与日志压实（Log Compaction）有什么区别？

日志删除按时间或空间回收旧 segment，适合有限历史保留；日志压实按 key 淘汰旧版本，保留恢复最新状态需要的信息。

- 压实不是 gzip 等字节压缩，也不是即时只剩一条记录。
- 消费进度与保留策略独立，已消费消息不会因此立即删除。

**追问 1：按时间或空间删除日志，与按消息 key 保留状态，分别适合哪些回放需求？日志压实与消息压缩编码是同一件事吗？**

需要完整事件历史用删除策略并设足保留期限；恢复某个 key 最新状态可用 compaction。

字节压缩降低存储和传输体积，不改变逻辑历史；压实则会丢弃被新值替代的旧记录。

**追问 2：消费完成后消息是否立即删除？消费者长期离线、位点超出保留范围时会发生什么？**

消费者离线太久，位点可能早于 log start，产生越界并按重置策略处理。

若旧日志已删除，仅改 offset 不能恢复内容，需要外部归档或权威数据重建。

**追问 3：使用压实日志恢复状态时，如何理解删除标记、尚未完成压实的重复 key 和最终可恢复的状态？**

同 key 旧值在清理完成前仍可能出现，恢复按日志次序覆盖；tombstone 表达删除，也受保留时限影响。

消费者必须在设计窗口内完成全量恢复，不能假设任意久以前的删除标记永久存在。

### 12. Kafka 的高水位、日志末端位点与 Leader Epoch 各自用于什么判断？

LEO 表示本地日志的下一写入位置；HW 是复制已提交的可读边界，通常 offset 小于 HW 的记录才可按普通消费读取；LSO 在存在未完成事务时限制 read_committed 的可见范围。

Leader Epoch 标识领导任期及相关日志历史，用来协助判断分歧和安全截断。

**追问 1：日志末端位点（LEO）、高水位（HW）和最后稳定位点（LSO）分别约束什么？**

统一使用“边界为下一位置”的口径：LEO 是本地末端，HW 是复制提交边界，LSO 通常为 HW 与最早未完成事务起点中的较小值。

不要把这些边界与最后一条实际记录的 offset 混淆，压实还可能造成 offset 空洞。

**追问 2：存在未完成事务时，`read_committed` 消费者是否能够读到高水位之前的所有消息？**

不能。未完成事务可能挡住后面的记录，即使它们已在 HW 之前，read_committed 也要等待相应事务解决，并过滤已中止事务记录。

read_uncommitted 与 read_committed 的区别不只是一句“能不能读取最新”。

**追问 3：Leader Epoch 如何帮助副本在领导者切换后校验日志？为什么仅比较日志长度不能确认内容一致？**

两个副本日志长度相同，某个位置之后内容仍可能来自不同 Leader 历史。

Epoch 与对应起点帮助确认共同前缀并截断分歧，单看最大 offset 无法证明内容一致。

### 13. Kafka 的 `KRaft` 元数据管理与历史 ZooKeeper 模式有什么区别？

历史 Kafka 通过 ZooKeeper 保存和协调部分集群元数据；KRaft 使用 Kafka 自身的 Controller 仲裁组和元数据日志。

- Kafka 4.0 已不支持 ZooKeeper 模式，升级要先规划受支持的迁移路径。
- KRaft 改的是元数据控制平面，不是把普通分区复制改成任意多数派 Raft。

**追问 1：以 Kafka 4.0 为版本边界，说明元数据仲裁与业务数据副本的职责，升级规划中需要检查哪些兼容性问题。**

核对 Broker、Controller、客户端协议和元数据版本，先备份并演练迁移与回滚；旧 ZooKeeper 集群不能不经支持路径直接启动成 4.0。

业务数据仍按分区副本、ISR 和生产确认规则分析，独立检查事务与消费协议兼容性。

### 14. Kafka 的分区数、消息 key、批次大小和压缩如何影响吞吐、延迟与数据倾斜？

分区增加潜在并行度，也增加文件、元数据和恢复成本；key 分布决定是否出现热点分区；批次和压缩提高吞吐但增加等待与 CPU 开销。

应在相同可靠性配置下，围绕消息大小、P99、吞吐和消费者容量调优，而不是把每个参数都调大。

**追问 1：扩容分区是否可能改变同一个 key 的路由，顺序业务应如何处理？**

常见哈希分区器会因分区数变化改变映射。顺序业务需使用稳定分片映射、排空切换或版本序列机制，确认旧新路由交接；只增加消费者而不处理热点 key，也无法均匀拆开单实体顺序流。

### 15. Kafka 的 `auto.offset.reset` 在什么情况下生效？

auto.offset.reset 在没有可用初始提交位点，或当前位点已不在服务器保留范围内时决定起点；已有有效提交位点时通常按该位点继续，并不会因为改成 earliest 就自动重放全部历史。

主动重放需要显式 seek、重置组位点或使用新组。

**追问 1：新消费组没有已提交位点，与已有位点超出日志保留范围，分别怎样决定起始位置？**

新组没有历史进度，按配置选择当前可读起点；旧组位点越界也触发对应策略。

earliest 指当前最早保留位置，不是 Topic 从创建以来第一条已被删除的消息。

**追问 2：`earliest`、`latest` 与 `none` 有什么行为差异？已有有效提交位点时，修改此参数是否自动重新消费？**

earliest 从最早可用位置开始，latest 从当时末端开始，none 在缺少可用进度时抛出异常要求人工处理。

有效位点优先，不应把这个参数当作永久覆盖消费者进度的开关。

**追问 3：需要历史重放时，如何安排位点重置、消费组状态与业务幂等，避免漏处理或重复产生副作用？**

先停止或协调原组，保存旧位点，确定重放分区和时间范围，使用管理命令或受控 seek，预演结果。

重放可能再次触发支付、通知等副作用，需隔离输出或复用幂等规则，确认后再恢复正常消费。

### 1. RocketMQ 同步发送、异步发送与单向发送应如何按业务可靠性选择？

经典 RocketMQ 客户端同步发送等待发送结果，异步发送通过回调接收结果，单向发送不等待 Broker 确认。

需要可靠业务事件时应处理同步返回或异步回调及失败重试；单向方式适合能容忍丢失的辅助数据，不能用“调用没报错”证明消息可靠保存。

**追问 1：“发送方法返回”与“业务最终处理成功”为什么不是同一件事？**

发送成功只到达所配置的 Broker 确认边界，不代表消费者已经执行，更不代表数据库业务事务提交。

接口要区分事件已受理和业务最终完成，消费者结果通过状态表或事件反馈，避免前端误认为异步下单已成功。

### 2. RocketMQ 的 `NameServer` 与 `Broker` 如何支撑路由、消息存储和消费读取？

NameServer 提供路由元数据，Broker 注册 Topic 队列等信息并保存消息，生产者和消费者获取路由后直接与相应 Broker 通信。

- 经典架构中 NameServer 不转发每条业务消息，也不是业务数据的持久化节点。
- 不同 5.x 部署还可能引入 Proxy，应按实际客户端协议说明。

**追问 1：一条消息从生产到消费经过哪些主要环节？**

生产者查询路由、选择队列、发送到 Broker；Broker 按存储和确认配置处理；消费者取得队列或消息分配后读取、执行业务并确认进度。

路由缓存、重试和故障切换都有窗口，不能说注册中心短暂异常就必然所有已有调用立即中断。

### 3. RocketMQ 的 `CommitLog`、`ConsumeQueue` 与索引文件分别承担什么角色？

经典存储中，CommitLog 顺序保存完整消息；ConsumeQueue 为 Topic 的逻辑队列保存指向 CommitLog 的位置等索引；IndexFile 支持按消息 key 等定位候选。

把完整消息统一追加，再通过较轻的逻辑索引读取，有助于兼顾写入吞吐和队列消费。

**追问 1：完整消息、逻辑队列位置与按业务键查找，分别由什么结构支撑？**

CommitLog 是消息主体；ConsumeQueue 将逻辑消费位置映射到物理位置和大小等；业务 key 索引是辅助检索，不是唯一约束，也不应直接用于证明消息只发送一次。

**追问 2：一次写入与一次消费怎样关联这些结构，实现顺序追加与队列读取？**

消息先追加到存储日志，再由分发过程构建逻辑队列索引；消费者按队列进度查索引，再取完整消息。

索引可见性与可靠性边界需结合版本和实现，不应把每一层都假定在同一同步步骤完成。

**追问 3：磁盘、页缓存和刷盘策略分别可能在哪一段成为瓶颈？**

顺序追加仍受磁盘和刷盘延迟限制；缓存命中有利于读取，积压很久后的冷数据可能需要真实磁盘读取。

大量小批次、同步刷盘或副本慢都可能降低吞吐，必须看端到端指标。

### 4. RocketMQ 的负载均衡粒度如何限制消费者扩容效果？

消费者扩容受实际负载均衡粒度限制。RocketMQ 4.x 经典 PushConsumer 主要按队列分配，一个队列在同组内由某个消费者负责；部分 5.x 客户端使用消息级负载均衡，不能套用“消费者永远不能超过队列数”的统一结论。

顺序消息与下游容量还会继续限制实际并发。

**追问 1：以 RocketMQ 4.x 的经典 PushConsumer 为例，队列与消费者如何分配？消费者数量超过队列数时会怎样？**

稳定分配下，一个消费者可处理多个队列，一个队列通常只分给组内一个消费者；消费者比队列多时会有实例无队列可处理。

增加消费线程只影响实例内能力，还需考虑顺序约束。

**追问 2：使用 RocketMQ 5.x 的其他客户端或消费方式时，如何确认采用的是队列级还是消息级负载均衡？**

查明 SDK、Push/Simple/Pull 等模式及服务端协议；消息级分配以单条或消息组的交付约束为依据，队列级则迁移整个队列责任。

应以对应版本文档与实际分配指标验证，不能只看服务端升级成 5.x。

**追问 3：顺序约束、单条消息耗时与下游容量分别可能在什么位置限制并发，为什么不能只增加消费者数量？**

同订单串行链、单条慢调用和数据库并发上限都可能成为瓶颈。

先看消费处理耗时、积压位置和热点分布，再选择优化业务、分组隔离、增加队列或实例；盲目扩容可能只把下游压得更慢。

### 5. RocketMQ 经典客户端中的集群消费与广播消费有什么区别？

在 4.x 经典客户端中，集群消费让同组实例分担消息，广播消费让各实例各处理一份。

- 二者适合不同业务语义，不仅是配置名称不同：位点保存、失败重试和实例离线补读等也需要分别理解。
- 现代客户端未必提供同样模式，不能用旧示例推断全部版本。

**追问 1：多个实例分担同一组业务任务，与每个实例都处理一份消息，分别如何选择消费模式？**

库存任务需要一组实例分担，选集群模式并保证重复处理幂等；每台实例都需要更新本地状态，可考虑广播，但配置同步不能只依赖可能丢失的在线通知，还要有版本回读。

**追问 2：两种模式的消费位点、失败重试与实例上下线行为是否完全相同？请说明客户端及服务端版本。**

经典广播消费通常由客户端本地维护进度，失败重试能力与集群模式不同，不应假设 Broker 会替每个离线实例可靠补齐全部历史。

集群消费进度与重试由相应消费组机制管理，具体看所用 SDK。

**追问 3：新版本客户端未提供同名模式时，如何根据实际消息分发语义设计等价业务方案？**

可为独立业务订阅建立不同消费组，或用配置中心 Watch/版本同步解决本地配置分发。

每个实例独立消费组可能产生大量组状态和生命周期负担，需要评估，而不是机械地用随机 group.id 模拟广播。

### 6. RocketMQ 如何根据 `Topic`、`Tag` 或属性过滤消息？

Topic 是较粗的业务分类，Tag 用于同一 Topic 下的轻量分类，属性过滤可表达更细条件，具体语法与支持需要匹配版本。

Broker 侧过滤可在传输前减少无关消息，客户端过滤则实现灵活但已支付网络和拉取成本。同组订阅条件通常应保持一致，避免消费语义混乱。

**追问 1：消费端过滤与 `Broker` 侧过滤分别节省什么资源，需要付出什么成本？**

Broker 过滤节省网络与消费者 CPU，但增加服务端判断成本，并非任意复杂表达式都高效；客户端过滤简单可控，但无关消息也要送达。

过滤不是鉴权边界，敏感消息还需 Topic 权限与数据隔离。

### 7. RocketMQ 延迟消息如何组织投递与到期触发？

延迟消息先被可靠保存，到达计划时间后才进入可供业务消费的阶段，而不是由生产者线程 sleep 后发送。

4.x 经典方案以预设延迟等级为主；5.x 提供基于指定投递时间的能力，具体精度、范围与 Topic 类型需按版本配置确认。到期表示可以投递，不保证业务在那一刻完成。

**追问 1：结合使用版本说明时间精度和使用约束。**

以 Apache RocketMQ 4.9.8 的默认配置为例，延迟消息使用从 1 开始的等级，对应 `1s、5s、10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h`。

例如 `setDelayTimeLevel(3)` 表示约 10 秒后具备投递条件，不是任意指定一个毫秒时间点；Broker 的 `messageDelayLevel` 配置会改变等级映射。

- RocketMQ 5.x 的定时消息能力可以按投递时间设置，但不能直接沿用 4.x 等级表解释；应同时核对服务端、SDK 和 Topic 消息类型。
- 无论哪种，到期时间都不是业务完成时间：存储负载、投递扫描和消费积压可能继续增加延迟，超时关单仍需检查订单当前状态并保留补偿扫描。

### 8. RocketMQ 事务消息如何衔接本地事务，事务回查为什么必要？

事务消息先向 Broker 发送不可被正常消费的半消息，再执行生产者本地事务，之后提交或回滚消息；二次确认丢失时 Broker 回查本地事务结果。

它主要衔接“本地事务成功”与“事件最终可投递”，不自动让消费者数据库与生产者数据库处于一个强一致事务。

**追问 1：半消息、本地事务执行与二次确认怎样衔接？**

半消息保存成功后才执行本地事务；本地成功则提交消息使其可投递，失败则回滚。

提交结果未知时保持可回查状态，不能仅凭线程没有返回就断言事务失败。

**追问 2：本地事务成功但确认丢失时，`Broker` 为什么需要回查？**

本地提交后进程退出或网络中断，Broker 不知道该投递还是丢弃。

回查让生产者依据持久化记录回答，而不是永远依赖丢失的那一次确认。

**追问 3：回查应依据什么持久化业务状态判断，如何避免错误提交、错误回滚或长期悬而未决？**

以事务 ID 对应的业务状态或事务记录为准，记录与业务修改同本地事务提交。

暂时查不到且可能仍在执行时返回未知并有限重查，超出业务期限需告警处理；不能把数据库瞬时不可用当成本地事务必定回滚。

### 9. RocketMQ 的刷盘方式与副本复制方式如何共同影响可靠性？

同步刷盘强调本节点日志落到持久化存储后再满足相应确认条件，同步复制强调达到所需副本进度；两者保护的故障范围不同。

异步刷盘或异步复制提升吞吐，但在进程、断电或主节点丢失时可能留下不同丢失窗口。必须结合 Broker 模式和客户端发送状态判断。

**追问 1：同步刷盘与同步复制分别覆盖什么故障？**

刷盘降低单节点断电丢内存日志的风险，复制降低单节点不可恢复故障的风险；复制到别人的内存不等于所有副本已 fsync，单节点刷盘也不等于有新主可继续服务。

**追问 2：消息发送成功应基于哪一种确认边界理解？**

检查实际发送状态、超时错误、刷盘方式与复制模式，而不是只看方法无异常。

即便 MQ 侧可靠保存，业务 outbox、消费幂等和人工补偿仍需存在，不能把发送确认扩大成整个业务已完成。

### 1. RabbitMQ 的 `Exchange`、`Queue`、`Binding` 与 Routing Key 如何配合路由消息？

Exchange 接收生产消息，根据类型与 Binding 将消息路由到一个或多个 Queue；消费者从队列获取消息。

- Routing Key 是消息携带的路由信息，Binding 是交换机到队列的规则。
- 没有匹配队列时消息不会凭空等待未来队列，因此生产端要检测无法路由。

**追问 1：消息从 `Exchange` 到 `Queue` 怎样匹配 Routing Key 和 `Binding`？**

生产者指定交换机和 Routing Key，交换机按绑定规则匹配目标队列。

多个队列可各获得一份，同一队列内多个消费者则通常竞争交付；不能把一条队列的多个消费者当作每人一份广播。

**追问 2：direct、topic 与 fanout 分别适合什么匹配或广播需求？**

direct 按键精确匹配；topic 按分段模式匹配，`*` 匹配一个词段、`#` 匹配零个或多个；fanout 忽略 Routing Key 向绑定队列广播。具体权限和队列生命周期需独立配置。

**追问 3：没有任何队列接收时，生产者应怎样发现，而不把发送调用返回当成已经交付？**

发布时设置 mandatory 并处理 return，结合 publisher confirm 跟踪 Broker 处理结果。

仅 TCP 写入成功或收到 confirm ACK，都不能单独证明进入了预期业务队列。

### 2. RabbitMQ 的生产者确认、消费者 `ACK` 与持久化分别保障什么？

生产者确认说明 Broker 已按相应队列和存储要求承担消息责任；消费者 ACK 说明消费者完成处理并允许移除该次未确认交付；持久化和副本决定 Broker 故障后消息能否保留。

三者针对不同阶段，不存在开启某一个就全链路绝不丢的捷径。

**追问 1：生产者确认与消费者 `ACK` 分别确认哪一段，不确认哪一段？**

publisher confirm 不确认消费者业务完成，consumer ACK 不确认生产者本地事务成功。

消息可靠进入队列后，若消费者先 ACK 再更新数据库失败，业务仍可能丢失。

**追问 2：只有确认但未满足持久化或复制要求时，节点故障可能造成什么后果？**

经典队列需要同时检查 durable 队列与持久消息，临时或自动删除队列还会因生命周期丢弃内容；复制队列有自己的多数派确认规则。

没有满足存储条件的消息不能仅因网络确认就宣称断电安全。

**追问 3：确认丢失后重发或重投，业务怎样避免重复生效？**

确认丢失会导致生产重发或消费重投。以稳定业务事件 ID 去重，数据库业务和去重记录同事务提交后再 ACK。

Broker 消息 ID 本身通常不自动提供任意业务副作用去重。

### 3. RabbitMQ 的 `publisher confirm` 与无法路由时的 `return` 机制有什么区别？

publisher confirm 表示 Broker 对发布的处理结果，basic.return 表示在 mandatory 发布下消息无法路由到队列。

- 无法路由的消息也可能收到 confirm ACK，因为交换机已经完成了“没有目标队列”的处理。
- 生产者需要同时跟踪两类事件，不能只监听 confirm。

**追问 1：`Broker` 接收消息与成功路由进目标队列，分别意味着什么？**

Broker 接收并处理发布请求，未必找到目标 Queue；消费者只能从实际队列取得消息。

队列声明、绑定错误或 Routing Key 不匹配都可能产生“成功发布但业务没收到”的表象。

**追问 2：没有可匹配队列时，生产者应怎样收集 `return` 与 confirm 信息并决定补偿？**

用消息业务 ID 或发布序号关联 return 与 confirm，无法路由时保留失败事件并修正配置后重发。

不能把每次 return 都立即无限重试，错误绑定不修复只会持续失败。

**追问 3：发布消息时 `mandatory` 标志与 return 回调怎样配合？为什么收到 confirm ACK 后仍要判断是否发生无法路由？**

mandatory=true 让无法路由消息返回给生产者；未启用时可能被丢弃或按其他路由配置处理。

对相应发布，Broker 会先发送 return 再确认，但客户端异步处理仍要正确关联，不应看到 ACK 就提前清除失败信息。

### 4. RabbitMQ 如何利用 `TTL` 与死信机制实现延迟处理？

常见方案把消息放入没有业务消费者的延迟队列，为消息或队列设置 TTL，过期后通过死信交换机路由到真正的业务队列。

它利用过期与死信转发实现延后可消费，不等于专门的高精度定时器，死信转发可靠性还要按队列类型和配置核对。

**追问 1：消息到期进入死信链路后，实际在哪个队列被消费？**

到期消息成为死信，被 DLX 按指定路由送到业务队列，再由消费者处理。

要检查死信交换机、目标队列和权限都存在，并避免循环死信路由。

**追问 2：同一队列中不同到期时间、消费者暂停等因素，会怎样影响触发时刻？**

经典实现中，不同消息 TTL 混在同一队列可能受队头到期处理影响，短 TTL 消息不一定立刻越过前面长 TTL 消息。

到达业务队列后若消费者暂停或积压，实际执行继续延迟。

**追问 3：业务必须按时关单时，为什么还需要检查状态并设计补偿，而不是把到期通知当成唯一事实？**

关闭订单时仍应读取权威状态并做条件转换，已经支付就不能关单。

持久保存截止时间，使用扫描兜底和幂等补偿处理漏投、迟到与重复；不把 TTL 通知当作支付状态的最终裁决。

### 5. RabbitMQ 的 Quorum Queue 如何通过复制维持队列可用性？

以 RabbitMQ 4.x 为例，Quorum Queue 使用基于 Raft 的复制状态机保存队列数据，通过 Leader 和多数副本维持提交与故障恢复。

- 少数派无法独立维持正常写入可用性，3 副本通常容忍 1 个故障，前提是剩余多数可通信且数据有效。
- 可靠性仍需 publisher confirm 和正确 ACK。

**追问 1：请说明使用版本；不要把历史经典镜像队列的配置与当前 Quorum Queue 混为一谈。**

经典镜像队列已在 4.0 移除，不能继续以旧 `ha-mode` 配置解释 4.x 的高可用。

Quorum Queue 有独立的成员、磁盘和故障恢复要求，网络分区时不能把任意存活节点当作可写主队列。

### 6. RabbitMQ 的 `prefetch` 如何影响消费并发、内存占用与消息分配？

prefetch 限制消费者或通道按配置允许的未确认交付数量，控制提前压给客户端的工作量。它不是自动创建业务线程，也不等于并发数。

适当预取可隐藏网络等待，过大则增加内存、分配不均和失败重投量，过小可能让处理资源等待消息。

**追问 1：未确认消息上限怎样影响消费者预取量与负载分配？**

手工 ACK 场景中，达到未确认上限后 Broker 暂停继续交付，直到有确认释放额度。

RabbitMQ 的按消费者与通道范围有特定语义，应检查 basic.qos 的配置，不能只看数字。

**追问 2：`prefetch` 很大但处理很慢时，内存、分配均衡与故障后的重投量可能怎样变化？**

慢消费者会囤积大量任务，其他消费者即使空闲也未必拿到这些已交付消息；进程失败时囤积部分一起重投。大消息还会占满堆和缓冲区，导致 GC 或 OOM。

**追问 3：怎样结合实际并发数和处理耗时调优，而不是只提高预取值？**

以实际工作并发和平均/长尾处理时间为基准，逐步调到能维持忙碌而不过量堆积，观察吞吐、unacked、内存和公平性。

下游容量不足时提高预取只增加排队，不提高完成速度。

### 7. 消费者手工 `ACK`、`NACK` 与重新入队分别会如何改变 RabbitMQ 消息状态？

ACK 表示该交付已处理；NACK 或 reject 可选择重新入队，或不重入队并进入死信/丢弃流程。未确认消息在连接失效后可能重新交付。

delivery tag 的作用域是通道，必须在正确通道确认，批量确认也不能越过未完成业务。

**追问 1：如何区分暂时故障与无法处理的坏消息，避免无限重投循环？**

短时故障使用延迟退避后重试，不宜立刻 requeue 形成忙循环；格式错误或永久拒绝记录原因并进入死信或终态。

重试计数应可靠保留，不能假设所有队列类型自动提供统一重试上限，重新交付仍要幂等。

### 8. RabbitMQ 中消息进入同一队列，是否足以保证业务按发送顺序完成？

不足。同一队列的入队与交付顺序，不等于多个消费者或多个工作线程的完成顺序；重新入队、优先级和故障重投也会影响观察结果。

严格同订单顺序需要从生产路由到业务提交都保持同 key 的串行约束，并定义失败时是否暂停。

**追问 1：多个消费者、预取以及消费端内部并行，会怎样影响处理完成顺序？**

消费者 A 取到创建但处理慢，B 取到取消先完成，就破坏业务顺序。

prefetch 大时客户端缓存任务更多；即使只有一个消费者，内部线程池并行也可能乱序。

**追问 2：拒绝后重新入队或连接断开重投时，应如何分析顺序变化？**

失败消息重入队不应被假定永远回到严格原位置，其他消息可能已经被交付或完成。

需要版本/状态校验，或暂停同 key 后续事件并修复前序，而不是仅依赖队列的 FIFO 名称。

**追问 3：需要同一订单严格顺序处理时，怎样结合分发、消费并发和失败策略设计，同时评估吞吐代价？**

按订单 ID 路由到固定分片队列，每个分片采用受控单活或串行消费，同订单内部不并发完成；失败进行有界重试和隔离。

不同订单可并行，提高分片数分担压力，但全局严格顺序会显著限制吞吐。

## 要点回顾

- 防丢需要覆盖完整业务链路：业务事件产生、发送、存储与消费落地都要有可恢复的记录和确认边界。
- 幂等与顺序必须落到业务提交：消息读取顺序不必然等于事务完成顺序，消费确认也不能替代业务结果校验。
- 组件能力需要带条件比较：副本、事务消息、延迟消息及重试机制应限定产品版本、消费模型和故障范围。
