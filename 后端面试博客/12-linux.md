## 1. Linux 基础

**本节问题**

- [1. 排查 Linux 服务时，如何从服务名称找到工作目录、配置文件、日志位置和启动参数？](#1-排查-linux-服务时如何从服务名称找到工作目录配置文件日志位置和启动参数)
- [2. 通过终端直接启动、后台运行和交给服务管理器运行，有哪些生命周期差异？](#2-通过终端直接启动后台运行和交给服务管理器运行有哪些生命周期差异)

### 1. 排查 Linux 服务时，如何从服务名称找到工作目录、配置文件、日志位置和启动参数？

先找到真实运行的 PID，再沿进程信息确认启动命令、可执行文件和工作目录；若由 systemd 管理，同时检查服务单元。

配置和日志路径优先从启动参数与实际配置文件追踪，不假定所有服务都安装在固定目录。
```bash
pgrep -af '服务的特征字符串'
ps -p "$pid" -o pid,ppid,user,lstart,args
readlink -f "/proc/$pid/exe"
readlink -f "/proc/$pid/cwd"
tr '\0' ' ' < "/proc/$pid/cmdline"
systemctl cat example.service
```
其中`pid`应先明确赋值，服务名按实际替换；输出可能包含敏感参数，不应直接公开。

**追问 1：从进程启动参数和工作目录，可以确认哪些路径，哪些路径仍需检查配置？**

参数可能给出配置文件、profile、日志目录或工作目录；相对路径要按进程工作目录和框架规则解析。

日志也可能进入 stdout、journald 或远端采集系统，不一定存在本地日志文件。还需检查配置覆盖优先级和实际打开的文件。

**追问 2：服务名相同但运行多个实例时，怎样避免读取错误进程或错误日志？**

核对 PID、启动时间、监听端口、用户、容器或命名空间，以及命令行中的实例标识。

- 服务名相同并不能证明是同一个实例；PID 还可能被复用。
- 先确定请求实际命中的实例，再读取相应日志和配置，避免拿健康副本的数据解释故障副本。

**追问 3：没有标准安装目录时，应怎样沿实际进程信息查找，而不假设固定路径？**

通过`/proc/$pid`、`lsof -p "$pid"`和服务管理配置反向追踪文件，而不是全盘猜测`/etc`下某个名称。容器中路径还要在对应挂载命名空间内解释。

没有权限时先申请最小必要权限，不应通过修改文件权限来获取排查便利。

### 2. 通过终端直接启动、后台运行和交给服务管理器运行，有哪些生命周期差异？

前台进程与终端会话紧密关联；命令后加`&`只是放到后台作业，不自动获得可靠托管；nohup 可降低终端退出的影响，但不提供完整重启、资源和日志管理。

生产服务通常交给 systemd、容器编排或其他监督器，明确启动、健康检查、退出和重启策略。

**追问 1：终端退出、进程异常结束以及机器重启后，如何保证服务按预期停止或重新启动？**

终端退出是否影响进程取决于会话和信号处理；可靠服务应定义停止信号、收尾超时和退出码，异常退出后由监督器按策略重启，开机是否启动也显式配置。

重启要有退避和频率上限，避免配置错误引起无限快速重启；管理器显示 running 也要配合业务就绪检查。

## 2. 文件与权限

**本节问题**

- [1. 文件权限 rw-r----- 与目录的读、写、执行权限分别意味着什么？](#1-文件权限-rw-r------与目录的读写执行权限分别意味着什么)
- [2. 软链接与硬链接有什么区别？](#2-软链接与硬链接有什么区别)
- [3. 如何查找指定名称或包含指定内容的文件？](#3-如何查找指定名称或包含指定内容的文件)

### 1. 文件权限 rw-r----- 与目录的读、写、执行权限分别意味着什么？

`rw-r-----`表示普通文件所有者可读写、所属组可读、其他用户无权限，即常见的 640。

- 目录的读权限允许列出名称，执行权限允许搜索和穿过目录，写权限配合执行权限可创建或删除目录项。
- 文件能否删除主要还取决于父目录权限，而不只是文件自身是否可写。

**追问 1：文件的读写权限与目录的读、写、执行权限，分别控制什么？**

文件 r/w 控制读取和修改内容，x 控制作为程序执行；目录 r/w/x 分别侧重列目录、修改目录项和按路径访问。

目录的 sticky bit、ACL 和安全模块可能再施加约束，因此不能只看一行传统权限位就解释所有访问失败。

**追问 2：文件本身可读但上级目录不可遍历时，会出现什么现象？**

路径中任一上级目录缺少必要的执行权限，即使目标文件自身可读，也可能无法打开。

- 应逐级检查路径，而不是仅对目标文件执行 chmod。
- 目录可遍历但不可列出时，知道准确名称仍可能访问对应文件，这与目录读权限不同。

**追问 3：怎样确认实际运行用户、所属组和整条路径的权限，而不直接扩大到所有用户可写？**

使用`ps -p "$pid" -o user,group,args`确认运行身份，用`id 用户名`查看组，用`namei -l /实际/路径`检查每级权限，必要时看`getfacl`及 SELinux/AppArmor 策略。

只补充需要的用户或组权限，避免用 `chmod 777` 掩盖错误归属或部署路径问题。

### 2. 软链接与硬链接有什么区别？

硬链接是同一文件 inode 的另一个名称，内容和元数据属于同一文件；软链接是保存目标路径的独立文件。

硬链接通常不能跨文件系统，也通常不能链接目录；软链接可以指向目录、跨文件系统，甚至指向暂时不存在的目标。

**追问 1：删除源文件后两者分别会怎样？**

删除一个硬链接名称后，只要还有其他链接或打开引用，文件仍可访问；删除软链接指向的目标路径后，软链接通常变为悬空。

- 所谓“源文件”对硬链接不是特殊地位，各名称都是同一文件的入口。
- 用`ls -li`、`stat`和`readlink`可核对 inode 与目标路径。

### 3. 如何查找指定名称或包含指定内容的文件？

按名称、类型或时间找文件用 find；按内容找匹配行用 grep。例如：
```bash
find /srv/app -type f -name '*.log'
grep -RInF -- 'request_id=abc123' /srv/app/logs
```
名称模式应引用，避免先被当前 Shell 展开。目录很大时先缩小路径和时间范围，避免在高负载机器全盘扫描。

**追问 1：`find` 与 `grep` 分别解决什么问题？**

find 遍历目录并检查文件元数据，grep 读取内容匹配文字或表达式。

- 可以组合`find ... -exec grep -nF -- '关键字' {} +`，安全处理含空格的文件名。
- 固定文本优先`-F`，正则需求才用相应模式；权限错误和压缩日志要单独处理，不能把“没有输出”直接当成内容不存在。

## 3. 进程管理

**本节问题**

- [1. 如何从服务名定位进程，再下钻到线程数量、线程状态与资源占用？](#1-如何从服务名定位进程再下钻到线程数量线程状态与资源占用)
- [2. 正常结束服务与强制杀死进程，在信号处理和资源清理上有什么区别？](#2-正常结束服务与强制杀死进程在信号处理和资源清理上有什么区别)
- [3. `kill` 命令执行后进程仍然存在，应该如何区分信号未处理、不可中断等待和僵尸状态？](#3-kill-命令执行后进程仍然存在应该如何区分信号未处理不可中断等待和僵尸状态)

### 1. 如何从服务名定位进程，再下钻到线程数量、线程状态与资源占用？

先用 pgrep 或 ps 确认目标进程，再看线程级状态和资源变化。常用命令为：
```bash
ps -p "$pid" -o pid,ppid,user,stat,%cpu,%mem,nlwp,etime,args
ps -L -p "$pid" -o pid,tid,stat,pcpu,comm
top -H -p "$pid"
```
进程级指标定位对象，线程级指标帮助找热点；还应记录时间窗口，避免只看一瞬间。

**追问 1：`ps` 与 `top` 等工具应如何组合，而不是只查看进程是否存在？**

ps 适合生成可保存的快照，top 适合连续观察趋势；结合 pidstat 可看线程 CPU 和上下文切换速率。

- Linux 线程 ID 与 Java 线程栈中的 native ID 需按进制对应，不能直接拿 Java 逻辑线程编号查系统线程。
- 高 CPU 或大量 WAITING 都只是线索，需要与业务栈和请求量关联。

### 2. 正常结束服务与强制杀死进程，在信号处理和资源清理上有什么区别？

正常停止通常先发送 SIGTERM，应用有机会停止接收新请求、等待存量任务、提交必要状态并关闭资源；SIGKILL 无法被捕获或忽略，应用不能执行正常清理。

内核会回收进程资源，但不会替应用完成业务事务、消息确认或日志刷新。

**追问 1：终止服务时，应如何选择信号并确认退出结果？**

优先通过服务管理器停止，让其执行既定流程；直接操作时先核对 PID 与启动时间，再 TERM 并等待限定时间，仍无法退出才评估 KILL。

用进程状态、端口和服务管理器确认退出，`kill -0`只用于存在性或权限检查，不代表业务健康。停止前保留诊断证据，避免一开始就强杀。

### 3. `kill` 命令执行后进程仍然存在，应该如何区分信号未处理、不可中断等待和僵尸状态？

kill 发送信号不等于进程立即消失。应核对目标 PID、权限、命令退出码和进程状态：信号可能未成功发送，可能被阻塞或处理较慢，也可能进程处于不可中断等待，或已经退出成为僵尸。还要排除服务管理器立刻重启了新进程。

**追问 1：进程未收到信号、收到但尚未处理、处于不可中断等待与僵尸状态，应怎样区分？**

查看`ps -p "$pid" -o pid,ppid,stat,wchan:32,args`，并检查`/proc/$pid/status`中的 SigPnd、ShdPnd、SigBlk、SigIgn 和 SigCgt。

Z 表示僵尸，D 常表示不可中断等待；R 或 S 则继续检查信号处理及业务收尾。PID 相同与不同启动时间也要注意复用问题。

**追问 2：不同状态分别需要检查信号、父进程还是底层 I/O？**

信号发送失败看权限和 PID；信号被屏蔽或捕获看信号状态及应用栈；Z 看父进程是否 wait 回收；D 看等待通道、内核栈和磁盘/NFS 等底层 I/O。不能对所有情况统一增加强杀次数。

**追问 3：为什么再次发送 `SIGKILL` 不一定立刻解决，处理前应保留什么证据？**

SIGKILL 无法被应用忽略，但处于某些不可中断内核等待的任务仍需等到可终止位置；僵尸已经没有可杀的执行体。

先保存进程、线程和内核等待信息、相关设备日志及启动时间，再决定修复父进程或底层资源，防止强制重启丢失根因证据。

**本节问题**

- [2. `grep`、`awk` 与 `sed` 分别适合哪些文本处理任务？](#2-grepawk-与-sed-分别适合哪些文本处理任务)
- [3. 针对下面的访问日志，写出统计接口访问量的命令或管道。](#3-针对下面的访问日志写出统计接口访问量的命令或管道)
- [4. 日志每行包含司机 ID、订单 ID 和订单状态，如何统计接单数最多的 10 位司机？](#4-日志每行包含司机-id订单-id-和订单状态如何统计接单数最多的-10-位司机)
- [5. Shell 中变量展开、引用和退出状态会怎样影响自动化脚本的正确性？](#5-shell-中变量展开引用和退出状态会怎样影响自动化脚本的正确性)

### 1. 管道、标准输出、标准错误与重定向如何配合？

标准输入、输出、错误分别是描述符 0、1、2；管道默认把前一个命令的标准输出接到后一个命令的标准输入，标准错误不会自动进入管道。

重定向按从左到右处理，先改变哪个描述符会影响后续复制关系。

**追问 1：把服务输出保存到日志并同时保留错误信息时，应如何组织命令？**

将输出和错误追加到同一个日志可用：
```bash
./app >>app.log 2>&1
```
同时显示并记录可用：
```bash
./app 2>&1 | tee -a app.log
```
- `2>&1 >app.log`与`>app.log 2>&1`不同，前者先让错误指向当时的标准输出。
- 管道中的失败状态需另行检查，不能只看 tee 成功。

### 2. `grep`、`awk` 与 `sed` 分别适合哪些文本处理任务？

grep 适合按匹配条件选行，awk 适合按字段计算和聚合，sed 适合按行范围或模式做文本替换。

三者可以组合，但先明确分隔符、转义和记录格式；结构化 JSON 日志优先用合适的解析器，不宜用简单空格分割冒充可靠解析。

**追问 1：如何查看文件第 10 至 20 行、提取指定列并按条件筛选？**

例如：
```bash
sed -n '10,20p' app.log
awk '{print $2}' access.log
awk '$3 == 500 {print $2, $4}' access.log
```
- 第一条打印 10 至 20 行，第二条取第二列，第三条按状态码筛选并输出路径与耗时。
- 样例以空白分隔为前提，字段内含空格或引号时必须调整解析方式。

### 3. 针对下面的访问日志，写出统计接口访问量的命令或管道。

题设：字段按空格分隔，依次为时间、接口路径、状态码、耗时毫秒；样例记录如下：

```text
12:00:01 /orders 200 18
12:00:02 /orders 500 300
12:00:03 /users 200 10
12:00:04 /orders 500 280
12:00:05 /users 500 90
```

要求按访问次数降序输出“次数 接口路径”。先完成全部访问统计，再处理追问中的过滤条件。

假设日志保存在`access.log`，可流式提取路径、排序并计数：
```bash
awk '{print $2}' access.log |
  LC_ALL=C sort |
  uniq -c |
  LC_ALL=C sort -k1,1nr -k2,2 |
  awk '{print $1, $2}'
```
题设输出为：
```text
3 /orders
2 /users
```
第二次排序按次数降序，并以路径作为并列时的稳定顺序。

**追问 1：如何只保留状态码为 500 的记录，并按接口路径统计次数？**

把第一步改为`awk '$3 == 500 {print $2}' access.log`，后续管道不变，得到：
```text
2 /orders
1 /users
```
应按第三字段匹配状态码，而不是 grep 整行中的 500，后者可能误匹配耗时、路径或其他内容。

**追问 2：如果路径带查询参数，应在哪一步统一路径口径，避免同一接口被拆成多组？**

在计数前统一口径，例如`awk '{p=$2; sub(/\?.*$/, "", p); print p}'`去掉查询串，再排序统计。

路径参数也可能需要按路由模板归一化，如`/orders/:id`；是否区分大小写、尾斜杠和编码应按应用路由规则，不宜擅自合并不同资源。

**追问 3：日志很大或持续写入时，怎样避免一次性把全部数据读入交互编辑器？**

awk 和 grep 可逐行处理，sort 可使用外部排序和临时文件，不必打开到编辑器。

给 sort 指定合理的`-S`和`-T`控制内存及临时目录，并检查磁盘余量；持续写入日志则明确统计截止点或轮转文件，避免把一个仍在变化的文件误当成固定样本。

### 4. 日志每行包含司机 ID、订单 ID 和订单状态，如何统计接单数最多的 10 位司机？

文件 `driver.log` 的每行格式为“司机 ID 订单 ID 状态”，以一个或多个空白字符分隔，不含表头；`ACCEPTED` 表示接单成功，同一事件可能重复记录。只统计出现过 `ACCEPTED` 的司机—订单组合，按接单数降序、司机 ID 数值升序输出前 10 位司机。

```text
101 9001 ACCEPTED
101 9001 ACCEPTED
101 9001 COMPLETED
102 9002 ACCEPTED
```

先筛选 ACCEPTED，再对“司机 ID、订单 ID”去重，最后按司机聚合。

以下命令输出“接单数 司机 ID”，按接单数降序、司机 ID 数值升序取前 10：
```bash
awk '$3 == "ACCEPTED" {print $1, $2}' driver.log |
  LC_ALL=C sort -k1,1n -k2,2n -u |
  awk '{count[$1]++} END {for (id in count) print count[id], id}' |
  LC_ALL=C sort -k1,1nr -k2,2n |
  head -n 10
```
样例结果为`1 101`和`1 102`。ID 按题设当作普通十进制数；超大 ID 若超出工具精确数值范围，应改用稳定的字符串规范和相应比较方式。

**追问 1：只统计 `ACCEPTED` 行时，如何确保同一司机对同一订单的重复日志只计一次？**

必须先过滤 ACCEPTED，再对司机和订单组合去重。

不能只按订单去重，否则可能把不同司机的记录合并；也不能先把所有状态计数，否则 COMPLETED 会额外增加接单数。同一组合重复出现多少次，最终都只保留一次。

**追问 2：去重键与最终分组键分别是什么？给出可执行的命令，并说明排序依据。**

去重键是二元组(driver_id,order_id)，分组键只有 driver_id。

- 上述命令的第一轮 sort 按两个数值字段去重，awk 累加每名司机的唯一组合数，最后 sort 按第一列降序、第二列数值升序保证并列稳定。
- 输出格式应在脚本和使用方之间明确，而不是依赖 awk 哈希遍历顺序。

**追问 3：日志不能全部放入内存时，如何控制排序资源与临时文件空间？并列计数需要怎样规定稳定顺序？**

第一轮 sort 可设置`-S 128M -T /已准备的临时目录`并保证空间。

- 若司机种类也极多，awk 聚合仍可能占用大量内存，可在去重结果中提取司机 ID，再外部排序、uniq 计数。
- 并列顺序仍按题设司机 ID 数值升序，不以文件先后或随机哈希顺序决定。

### 5. Shell 中变量展开、引用和退出状态会怎样影响自动化脚本的正确性？

Shell 变量展开可能引起分词和通配符展开，退出状态决定异常路径是否继续。

- 可靠脚本应引用路径变量、显式检查关键命令和输入，避免把外部输入拼成可执行语法。
- 自动化部署尤其不能把“某个最后命令成功”当成整个流程成功。

**追问 1：路径含空格或通配符时，未引用变量与使用双引号会产生什么不同结果？**

`cat $path`在路径含空格时可能变成多个参数，含`*`时还可能展开成其他文件；`cat -- "$path"`把它作为单个参数，并用`--`结束选项解析。

双引号仍允许变量展开，但阻止这些不期望的分词和通配符处理；命令替换也应按使用场景引用。

**追问 2：管道前一条命令失败、最后一条命令成功时，默认管道退出状态如何确定？Bash 的 `pipefail` 有什么作用？**

默认管道退出状态通常取最后一条命令，即前面的读取失败也可能被最后的 sort 成功掩盖。

- Bash 的`set -o pipefail`使管道返回最右边非零状态，无失败时才返回 0；还可立即读取 PIPESTATUS 逐项诊断。
- `set -e`有条件和上下文例外，不能代替显式错误处理。

**追问 3：执行部署或清理操作前，怎样检查空变量、命令失败和实际目标，避免脚本在异常路径继续运行？**

用`${var:?必须设置}`或条件检查拒绝空值，校验路径位于预期根目录，先打印或 dry-run 确认目标，再执行；关键步骤用`if ! command; then ...; exit 1; fi`等明确失败分支。

- 临时文件用安全方式创建并 trap 清理，拒绝直接 eval 不可信输入。
- 清理脚本尤其要限制目标，而不是只依赖一个未检查变量。

## 5. 日志分析

**本节问题**

- [1. 如何从持续写入的日志中筛选指定时间段和关键字的记录？](#1-如何从持续写入的日志中筛选指定时间段和关键字的记录)
- [2. 日志被轮转、重命名或重新创建后，`tail -f` 与 `tail -F` 的跟踪行为有什么区别？](#2-日志被轮转重命名或重新创建后tail--f-与-tail--f-的跟踪行为有什么区别)

### 1. 如何从持续写入的日志中筛选指定时间段和关键字的记录？

先明确时间戳格式、时区和日志轮转范围，再按时间和关键字组合筛选。

- 固定宽度且按时间可字典比较的日志可用 awk 按范围过滤；关键字匹配可用 grep -F。
- 若是 JSON 或跨行堆栈，应使用能保持记录边界的解析方式，不能只按一行文字过滤。

**追问 1：实时跟踪与历史定位应如何配合使用？**

历史定位先根据报警时间与请求 ID 找完整上下文，再用`tail -F app.log | grep --line-buffered -F -- '关键字'`观察后续变化。

- 只实时追尾可能错过故障起点，只看历史单条也可能漏掉持续重试。
- 应关联实例、时间偏差和 Trace ID，并控制日志中的敏感信息暴露。

### 2. 日志被轮转、重命名或重新创建后，`tail -f` 与 `tail -F` 的跟踪行为有什么区别？

以 GNU tail 为例，`tail -f`默认跟随已打开的文件描述符，文件重命名后仍可能继续跟随旧文件；`tail -F`相当于按文件名跟随并重试，会尝试在路径被替换或重建后重新打开。它们适合不同轮转方式，不是单纯“一个更实时”。

**追问 1：如何确认自己看到的是当前文件，而不是仍被进程持有的旧文件？**

用`ls -li`或`stat`查看当前路径的 inode，用`lsof -p "$pid"`或`/proc/$pid/fd`确认应用实际打开的对象。

若应用仍写旧 inode，`tail -F` 看到的新文件可能没有日志；这时要按应用约定重新打开日志，而不是只更换查看命令。

## 6. 网络工具

**本节问题**

- [1. 如何确认端口监听状态、占用进程以及连接所处的 TCP 状态？](#1-如何确认端口监听状态占用进程以及连接所处的-tcp-状态)
- [2. 如何组合 `curl`、`ss`、`lsof` 与 `tcpdump` 判断请求停在域名解析、建连还是应用响应阶段？](#2-如何组合-curlsslsof-与-tcpdump-判断请求停在域名解析建连还是应用响应阶段)
- [3. ping 与 `traceroute` 分别帮助观察什么网络现象？](#3-ping-与-traceroute-分别帮助观察什么网络现象)

### 1. 如何确认端口监听状态、占用进程以及连接所处的 TCP 状态？

先用`ss -lntp`检查 TCP 监听地址、端口及进程，再用`ss -antp`观察连接状态；具体文件和连接归属可用`lsof -nP -iTCP:8080`。

查看进程信息可能需要相应权限，也要在正确网络命名空间中执行。

**追问 1：`netstat`、`lsof` 等工具提供的信息如何相互印证？**

netstat 或 ss 显示网络端点和状态，lsof 从进程打开的文件视角展示 Socket 归属。通过 PID、端口、四元组和采样时刻交叉确认。

监听在 127.0.0.1 与 0.0.0.0 的可达范围不同，主机端口映射也可能转到容器，不能只看到端口号就认定目标服务正确。

### 2. 如何组合 `curl`、`ss`、`lsof` 与 `tcpdump` 判断请求停在域名解析、建连还是应用响应阶段？

按请求阶段逐层验证：DNS 取得什么地址，TCP 是否建立，TLS 是否完成，HTTP 何时收到首字节及完整响应。

curl 提供端到端计时，ss 提供连接状态，lsof 关联进程，tcpdump 用于证实报文交互。它们应围绕同一请求和时间窗口使用。

**追问 1：怎样分别验证解析结果、目标端口、连接建立与 HTTP 响应？**

可用`dig 域名`查解析，`ss -lntp`查监听，再用：
```bash
curl -sS -o /dev/null --connect-timeout 3 --max-time 10 \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  'https://实际域名/health'
```
- 这些 time 值主要是从请求开始累计的时点，分析阶段耗时需作适当差分。
- 诊断指定 IP 时可用`--resolve`保留正确 Host 和 TLS 主机名，避免改成 IP 后测到不同虚拟主机。

**追问 2：端口处于监听状态或 ping 能返回时，为什么还不能证明业务接口可用？**

监听只证明内核有接收入口，应用可能未 accept、线程池耗尽或依赖不可用；ping 只验证特定 ICMP 路径，不验证 TCP 端口、TLS 或业务响应。

健康接口也要说明是存活检查还是核心依赖就绪，不能用一个静态 200 替代完整业务验证。

**追问 3：需要抓包时，应怎样限定范围并把时间点关联到应用日志，而不只收集大量无关数据？**

按目标 IP、端口、协议、网络接口和短时间范围限制抓包，控制数量、截断长度和文件权限。

例如，在已经获准采集的诊断环境中，可以将目标地址替换后执行：

```bash
timeout 10s tcpdump -i any -nn -s 128 -c 2000 \
  'host 192.0.2.10 and tcp port 443' -w trace.pcap
```

- `192.0.2.10` 是示例地址，不是要实际访问的服务器；`timeout` 限制运行时间，`-c` 限制包数，`-s` 限制每包捕获长度。
- 截断过短可能无法保留完整的协议头，因此要按诊断目标调整。
- 记录请求 ID 与采集时间，并同代理和应用日志对齐。
- TLS 抓包通常不能直接看到明文业务，但能观察握手、重传和关闭；文件仍可能包含敏感信息，应限制访问并在诊断完成后清理。

### 3. ping 与 `traceroute` 分别帮助观察什么网络现象？

| 比较项 | 特点与用途 |
|---|---|
| ping | ping 利用 ICMP 回显观察可达性、往返延迟和丢包 |
| traceroute | traceroute 通过逐步增加 TTL 或 Hop Limit 观察路径上响应的节点 |

它们提供网络诊断线索，但中间设备可能限速或不回应，路径也可能与实际业务流不同。

**追问 1：路由中某一跳不回复是否必然表示业务流量被阻断？**

不必然。某一跳不回控制报文，可能只是防火墙策略或 ICMP 限速；若后续节点和终点仍可达，不能据此断言该跳丢弃业务数据。

中间节点的响应慢也不一定表示它转发业务慢，需要结合终点延迟和真实连接判断。

**追问 2：如何结合实际 TCP 请求验证？**

对实际域名和端口执行 curl 或相应客户端请求，必要时采用 TCP 模式的 traceroute 并结合 ss 和抓包。

分别比较解析地址、建连、TLS 和首字节时延；ping 失败但 HTTPS 正常、ping 正常但 TCP 端口被阻断都可能发生。

## 7. 资源监控

**本节问题**

- [1. 如何结合 CPU、平均负载、内存与磁盘 I/O 指标判断服务的资源压力？](#1-如何结合-cpu平均负载内存与磁盘-io-指标判断服务的资源压力)
- [2. `free` 中的 `free`、available、buffer 与 cache 应如何解读？](#2-free-中的-freeavailablebuffer-与-cache-应如何解读)
- [3. `df` 与 `du` 的统计口径为什么可能不同？](#3-df-与-du-的统计口径为什么可能不同)
- [4. 磁盘显示还有空间却无法创建文件时，为什么还需要检查 inode、挂载状态与用户配额？](#4-磁盘显示还有空间却无法创建文件时为什么还需要检查-inode挂载状态与用户配额)
- [5. 服务报告“Too many open files”时，如何检查文件描述符限制与实际占用？](#5-服务报告too-many-open-files时如何检查文件描述符限制与实际占用)

### 1. 如何结合 CPU、平均负载、内存与磁盘 I/O 指标判断服务的资源压力？

CPU 指标反映计算、系统调用及部分等待情况；平均负载反映一段时间的可运行和某些不可中断任务压力；内存看可用量、回收和交换；磁盘看吞吐、延迟、队列和利用情况。

可组合 top、vmstat、iostat 和 pidstat，按相同时间窗口观察，而不是只取一张截图。

**追问 1：单个指标正常时，为什么不能直接排除资源瓶颈？**

CPU 低仍可能被锁、磁盘或网络阻塞；内存总量正常仍可能触及容器限制；磁盘吞吐不高也可能是小随机 I/O 延迟很大。

还要检查每核、每盘、每实例的不均衡和业务 P99，系统平均值可能掩盖局部瓶颈。

### 2. `free` 中的 `free`、available、buffer 与 cache 应如何解读？

free 表示当前未使用内存，available 估计无需严重影响系统即可供新应用使用的内存，包含部分可回收缓存；buffer 和 cache 反映内核用于块设备、文件页及相关缓存的数据，具体列组合依工具版本而异。

Linux 会利用空闲内存缓存文件，所以 free 小不必然是坏事。

**追问 1：空闲内存很少但 available 仍充足，与持续交换或 `OOM` 风险有什么区别？**

available 充足且没有持续交换、直接回收或分配失败，通常不需为了提高 free 而手工清缓存；available 持续下降、swap in/out 和 major faults 上升、内存压力或 OOM 事件出现则需处理。

容器还要单独检查 cgroup 限额，主机有空闲不代表容器可继续分配。

### 3. `df` 与 `du` 的统计口径为什么可能不同？

df 询问文件系统已用和可用空间，du 遍历可见目录树并统计文件占用。

- 已删除但仍打开的文件、挂载覆盖、稀疏文件、硬链接、保留空间和统计范围差异，都可能使二者不同。
- 比较前先确保路径属于同一个文件系统且权限足以遍历。

**追问 1：`df` 与 `du` 分别统计哪一层的信息，结果为何不一定相同？**

df 包含文件系统层面的已分配块等，du 通常只统计遍历到的文件实际分配空间。

- du 的 apparent-size 选项又会改变口径。
- 不能把 df 减 du 的差值直接解释成“隐藏垃圾”，应先核对挂载点、链接和打开文件。

**追问 2：文件已经删除，但进程仍持有打开引用时，怎样定位占用？**

可用`lsof +L1`查找链接计数小于 1 但仍打开的文件，再按 PID 和 FD 确认；结合`/proc/$pid/fd`及文件大小判断占用。

- 让应用按正常流程关闭或重新打开日志，空间才能回收。
- 直接再次删除路径已经没有作用，强制截断打开文件还可能破坏业务。

**追问 3：释放磁盘前怎样确认影响范围，避免误删当前业务仍需要的数据？**

先确认文件所属进程、用途、备份和保留策略，区分可清理日志、临时文件与数据库/WAL 等不可随意删除内容。

评估清理 I/O 与恢复需求，优先通过应用提供的轮转、过期或归档机制处理，并在清理后核对 df、进程错误和业务状态。

### 4. 磁盘显示还有空间却无法创建文件时，为什么还需要检查 inode、挂载状态与用户配额？

文件创建不仅需要数据块，还需要 inode、可写挂载、目录权限和配额额度。

可查看`df -h`、`df -i`、`findmnt`及相应配额信息，并结合具体错误码区分 ENOSPC、只读文件系统和权限失败。数据库或容器还可能有自身存储限额。

**追问 1：大量小文件和已删除但仍打开的文件，会分别造成什么现象？**

大量小文件可能耗尽 inode 而字节空间仍充足；已删除但仍打开的大文件可能让 df 显示占用，而 du 找不到对应路径。

前者要按业务策略清理或调整文件组织，后者要定位持有描述符的进程并正常释放。两者都不能只用“再删几个最大的可见文件”解决。

### 5. 服务报告“Too many open files”时，如何检查文件描述符限制与实际占用？

先确认是进程级描述符上限还是系统级文件表压力，再看实际打开对象及增长趋势。

- `/proc/$pid/limits`反映目标进程限制，`/proc/$pid/fd`可查看描述符，lsof 用于识别 Socket、文件和管道。
- 定位增长来源后再调整上限，避免把泄漏推迟成更严重故障。

**追问 1：进程的软限制、硬限制与系统级限制有什么区别，`ulimit` 和 `/proc/<pid>/limits` 分别反映什么？**

软限制是当前生效上限，硬限制限制普通进程可把软限制提高到多少；系统级还有总文件句柄等约束。

`ulimit -Sn/-Hn`通常查看当前 Shell 及其后续子进程环境，不自动代表已经运行的服务；systemd 的 LimitNOFILE 和容器配置也要核对，最终以目标进程 limits 为准。

**追问 2：怎样区分连接数真实增长、文件未关闭与连接泄漏？**

连续记录 FD 数量，按 Socket、普通文件、管道等分类，并关联请求量和连接池指标。

- 流量回落后正常连接会逐步释放或稳定在池容量，泄漏则持续增长。
- 大量 CLOSE_WAIT 提示关闭路径问题，重复打开同一文件不关闭则看异常和早返回路径；单次 lsof 只能提供线索，需观察趋势。

**追问 3：提高限制前应评估哪些内存和下游容量问题，为什么单纯调大参数不能修复泄漏？**

更多连接和文件会消耗内核内存、应用缓冲、线程及下游额度。

- 上限提高前估算每连接成本、连接池和数据库容量，保留拒绝与告警。
- 泄漏的根因是生命周期管理错误，调大限制不会让 close 自动发生，只会延后资源耗尽时间。

## 要点回顾

- 先确定目标再执行命令：PID、启动时间、运行用户、容器和命名空间应一致，避免拿错实例的信息解释故障。
- 统计前先统一口径：日志格式、时间范围、去重键和排序规则会直接影响结果，脚本还要处理引用与退出状态。
- 资源指标需要交叉验证：free、RSS、df、du 和连接状态各有统计边界，调整限制之前先区分正常增长与生命周期错误。
