## 1. 进程与线程

### 1. 进程有哪些主要状态？

教材通常把进程描述为新建、就绪、运行、阻塞和终止状态：就绪表示具备运行条件但尚未获得 CPU；运行表示正在 CPU 上执行；阻塞表示等待 I/O、同步条件等事件，暂时不能继续。

实际 Linux 状态码还区分可中断睡眠、不可中断等待、停止、僵尸等，不能与教材五态逐字对应。

**追问 1：哪些事件会使其状态发生变化？**

调度器分配 CPU 使就绪转运行，时间片用尽或被抢占使运行转就绪；等待 I/O 或锁条件可使运行转阻塞，事件完成后阻塞转就绪，再等待调度；退出或被终止进入结束流程。

I/O 完成不代表立即占用 CPU，唤醒与真正运行之间仍可能排队。

### 2. 进程与线程在地址空间、资源共享和故障隔离上的差异，会怎样影响并发设计？

进程提供独立地址空间和较强资源隔离，线程是进程内共享资源的执行单元。

多线程共享数据方便、通信开销较低，但错误写内存或进程级故障可能影响全部线程；多进程需要 IPC 和数据序列化，却更容易隔离崩溃、权限和资源使用。

**追问 1：同一进程内线程共享什么，哪些寄存器、栈和调度状态必须各自维护？**

线程通常共享代码、堆、全局变量、打开文件表等进程资源；各自维护寄存器、程序计数器、栈、线程局部存储和调度状态。

线程栈虽然逻辑上独享，但仍位于同一地址空间，其他线程若持有指针也可能访问，不能将其当成硬件隔离的私有内存。

**追问 2：一个执行单元异常时，故障隔离边界会怎样影响其他任务？**

线程中的错误若导致进程崩溃，其他线程也会终止；语言运行时可能捕获部分异常，但不能保证隔离所有内存、资源和运行时故障。

独立进程通常不会因另一个进程普通崩溃而直接丢失地址空间，但共享服务、机器和内核仍是共同故障域。

**追问 3：需要并发与隔离时，如何在多线程与多进程之间选择，而不只比较创建开销？**

可信的高频共享计算可用线程；不可信插件、需要独立权限或容易崩溃的任务可用进程、容器等隔离。

- 还要比较数据规模、IPC 成本、资源限制、启动恢复、调试和运维复杂度。
- 并发与隔离并非二选一，可以每个进程内部再使用多线程。

### 3. fork、exec 与 `wait` 分别在进程生命周期中完成什么工作？

`fork` 创建子进程，父子从调用返回处继续执行，返回值不同；`exec` 系列用新程序替换当前进程的程序映像，成功后不返回原程序；`wait` 或 `waitpid` 等回收子进程退出状态，释放剩余管理资源。

exec 不是再创建一个新 PID 的同义词。

**追问 1：fork 后父子进程的地址空间、文件描述符与执行位置如何变化？**

父子拥有各自虚拟地址空间，常用写时复制共享物理页，后续写入再分离；文件描述符表被复制，但相应描述符可引用同一打开文件描述，共享文件偏移等状态。fork 在子进程返回 0，在父进程返回子 PID。

多线程进程 fork 后，子进程只保留调用线程，继承的锁状态需特别谨慎。

**追问 2：exec 成功后哪些程序内容被替换？**

原代码、堆、栈和大部分用户态映射被新程序替换，PID 通常保留。

- 没有设置 close-on-exec 的文件描述符可继续保留，信号处理和其他属性按接口规则重置或继承。
- 执行成功后不会再走 exec 后面的原代码；失败才返回错误，调用方必须处理。

### 4. 僵尸进程与孤儿进程有什么区别？

僵尸进程是子进程已退出，但父进程尚未读取退出状态；孤儿进程是父进程先退出，子进程仍由系统指定的接管者管理。

两者描述不同关系，一个关心退出回收，一个关心父子生命周期，不是同一种“异常运行状态”。

**追问 1：子进程已退出但父进程尚未回收，与父进程先退出，分别形成哪一种情况？**

子进程已终止而父进程没调用 wait 类接口回收，形成僵尸；父进程先终止、子进程尚存活，则子进程成为孤儿，并被相应 subreaper 或 PID 命名空间中的 init 等接管。孤儿可以正常继续工作，之后也需要被接管者回收。

**追问 2：它们占用或依赖哪些资源与回收机制，排查时为什么不能一概当作仍在运行的进程处理？**

僵尸已经不执行代码，主要保留 PID、退出状态和少量内核管理信息，反复 kill 它没有意义，应修复父进程回收逻辑。

- 孤儿可能仍正常占用 CPU、内存和文件，是否需要停止取决于业务。
- 应结合 PPID、状态码和服务管理关系处理，不能只按名称清理。

## 2. 进程调度

**本节问题**

- [1. 不同进程调度策略如何在响应时间、吞吐与公平性之间取舍？](#1-不同进程调度策略如何在响应时间吞吐与公平性之间取舍)
- [2. 进程与线程上下文切换需要保存和恢复哪些状态？](#2-进程与线程上下文切换需要保存和恢复哪些状态)

### 1. 不同进程调度策略如何在响应时间、吞吐与公平性之间取舍？

先来先服务实现简单但长任务会拖慢短任务；短作业优先有利于平均等待但可能饿死长任务；时间片轮转改善交互响应但增加切换；优先级调度体现任务重要性但需防饥饿。

实际系统还区分普通、实时等调度类别，公平性与延迟策略依内核版本而不同。

**追问 1：任务类型和负载变化时，哪些调度成本需要关注？**

关注可运行队列长度、抢占频率、上下文切换、缓存失效、NUMA 迁移和任务唤醒延迟。

- CPU 密集任务主要争取计算份额，I/O 密集任务经常睡眠并要求唤醒响应。
- 不能把某一种旧 Linux 调度器名称当成所有版本的永久实现，应先固定内核和调度策略。

### 2. 进程与线程上下文切换需要保存和恢复哪些状态？

上下文切换要保存当前执行单元的寄存器、栈指针、执行位置和必要调度状态，再恢复下一个执行单元。

跨进程还可能切换地址空间和相关内存管理上下文；同进程线程通常不需要更换整个地址空间，但仍有调度和缓存成本。

**追问 1：保存和恢复寄存器、执行位置与调度状态分别需要做什么？**

内核保存足以让任务日后继续执行的 CPU 状态，更新任务运行、等待或就绪信息，再加载目标任务的内核栈和寄存器上下文。

切换不是把整个进程内存复制一遍，进程的堆和代码通常仍留在原来的映射中。

**追问 2：跨进程切换时，地址空间与缓存行为可能带来哪些额外影响？**

切换页表上下文可能影响 TLB，缓存工作集也可能因新任务运行而被替换；地址空间标识等硬件机制可以减轻部分开销，所以不能简单说每次切换都清空全部缓存。

跨核迁移还可能增加缓存重新填充和 NUMA 远端访问。

**追问 3：并发执行单元增加后，为什么吞吐可能不升反降？怎样结合等待与切换开销判断？**

过多可运行线程会增加切换、锁竞争和工作集压力；大量等待下游的线程则可能只增加排队和内存。

- 应同时观察 CPU 利用率、run queue、切换次数、任务等待与吞吐。
- 若 CPU 已饱和，继续加线程通常不能创造更多计算能力。

## 3. 进程通信

**本节问题**

- [1. 跨进程通信应如何在管道、消息队列、共享内存和 Socket 之间选择？](#1-跨进程通信应如何在管道消息队列共享内存和-socket-之间选择)
- [2. 匿名管道、命名管道与 Unix Domain Socket 的使用条件有什么区别？](#2-匿名管道命名管道与-unix-domain-socket-的使用条件有什么区别)

### 1. 跨进程通信应如何在管道、消息队列、共享内存和 Socket 之间选择？

单向字节流可用管道，明确消息边界可用消息队列或相应 Socket 类型，双向请求响应可用 Socket，同机大块数据交换可用共享内存。

选择时还要考虑是否跨主机、权限、阻塞与背压、生命周期和故障恢复，不能只按单次传输速度排序。

**追问 1：需要单向流、消息边界、双向通信或共享大块数据时，分别如何选择？**

父子进程串联标准输入输出适合匿名管道；无亲缘关系的本机进程可用命名管道或 Unix Domain Socket；跨机器通常用网络 Socket。

POSIX/System V 消息队列保留消息边界，共享内存则要自己定义记录格式与索引。字节流也能传消息，但必须自行分帧。

**追问 2：共享内存减少了什么数据交换成本，为什么仍需另外设计同步？**

共享内存让进程访问同一批物理页，减少重复拷贝与系统调用，但多个进程仍可能同时修改数据。

需要进程共享的锁、信号量或正确的原子协议，定义写入完成标志和内存顺序；把普通线程锁随便放进去不代表已经满足跨进程语义。

**追问 3：进程意外退出时，通信对象与已写入部分数据怎样收尾？**

管道或 Socket 可以通过 EOF、错误和连接关闭感知对端退出；共享内存及命名 IPC 对象可能需要显式清理和恢复。

对部分写入的数据使用长度、校验、提交标记或事务式记录，避免把半条消息当成完整内容。还要防止锁持有者退出后其他进程永久等待。

### 2. 匿名管道、命名管道与 Unix Domain Socket 的使用条件有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| 匿名管道 | 匿名管道通常通过继承描述符连接相关进程 |
| 命名管道 | 命名管道以文件系统路径暴露端点，便于无亲缘进程打开 |
| Unix Domain Socket | Unix Domain Socket 适合同机双向通信，并可使用流式、数据报或序列包类型 |

它还可支持传递文件描述符和获取对端凭据等能力。

**追问 1：同机进程传输数据时，需要从消息边界、双向通信、权限和开销哪些方面比较？**

管道通常是单向字节流，没有通用业务消息边界，小于 PIPE_BUF 的写原子性也不等于任意读取自动按消息返回。

- Unix 流 Socket 仍需分帧，数据报或序列包可保留边界。
- 路径权限、对端身份和缓冲限制都要检查；同机 Socket 避免部分网络协议开销，但并非天然零拷贝。

## 4. 同步与死锁

**本节问题**

- [1. 互斥锁与信号量有什么区别？](#1-互斥锁与信号量有什么区别)
- [2. 死锁形成需要满足哪些条件？如何从资源申请顺序和超时策略降低风险？](#2-死锁形成需要满足哪些条件如何从资源申请顺序和超时策略降低风险)
- [3. 条件变量与互斥锁为什么通常配合使用？](#3-条件变量与互斥锁为什么通常配合使用)
- [4. 死锁、活锁与饥饿有什么区别？](#4-死锁活锁与饥饿有什么区别)

### 1. 互斥锁与信号量有什么区别？

互斥锁表达临界区的独占所有权，通常由获得锁的执行单元释放；信号量表达可用资源或事件计数，通过获取减少额度、释放增加额度。

信号量允许多个持有者，也可由不同执行单元释放，具体规则依 API 而定。用途相近但语义不同。

**追问 1：二元信号量与互斥锁能否在所有场景互换？**

不能完全互换。二元信号量只有 0 或 1 的额度，但通常没有同样的所有者、递归或优先级继承语义；错误的额外释放还可能破坏互斥约束。

锁的释放责任和异常处理更适合直接用互斥锁表达，而信号量更适合资源额度和跨任务通知。

**追问 2：限制并发访问数和保护一个临界区时，分别应怎样选择？**

保护共享对象的一组不变量，用互斥锁将检查和修改包在同一临界区；限制同时访问外部服务最多 N 个任务，用初值 N 的信号量，并确保只在成功获取后释放。

获得一个额度不自动保护任务内部所有共享数据，必要时仍需其他同步。

### 2. 死锁形成需要满足哪些条件？如何从资源申请顺序和超时策略降低风险？

经典死锁需要互斥、占有且等待、不可抢占和循环等待同时成立。

- 两个线程各持一把锁，再等待对方释放，就可能无法继续。
- 实践中优先统一锁顺序、缩短持锁范围、避免持锁调用慢外部服务，并为失败路径设计释放和重试，而不是只加超时参数。

**追问 1：用两个线程各持一把锁再请求对方锁的例子，说明四个必要条件怎样同时成立。**

线程 A 持锁 L1 并等 L2，线程 B 持 L2 并等 L1：L1 和 L2 互斥；双方等待时保留已持有锁；锁不能被外部强行安全夺走；A→B→A 形成循环。

只有满足这一完整依赖关系，才可据此判定对象锁死锁。

**追问 2：统一资源顺序、限时获取与失败释放，分别试图破坏哪个条件？**

统一全局资源顺序破坏循环等待；尝试获取失败后释放已占资源，可以破坏占有且等待；限时获取只是提供退出机会，必须配合实际释放才能解除循环。

释放后重试还要退避和限制次数，否则双方反复冲突可能变成活锁。

**追问 3：预防、避免与检测死锁的处理时机有什么不同，超时本身是否能证明一定发生了死锁？**

预防在设计上让必要条件不同时成立；避免在分配时评估是否仍处于安全状态，例如银行家思路；检测允许等待发生后分析等待图，再终止或回滚受害者。

超时只说明等待过久，也可能由慢任务或高负载引起，不是死锁的充分证据。

### 3. 条件变量与互斥锁为什么通常配合使用？

条件变量负责等待某个条件变化，互斥锁负责保护该条件对应的共享状态。

- 正确模式是持锁检查条件，不满足则原子地释放锁并等待，唤醒后重新获得锁并再次检查。
- 通知本身不是业务条件，也不会替代共享状态的修改。

**追问 1：等待前检查条件与被唤醒后重新检查条件分别避免什么问题？**

等待前持锁检查，防止条件检查与进入等待之间丢失通知；唤醒后重查，防止条件被其他线程抢先消耗，或 API 允许虚假唤醒。

即便某种语言实现不提供虚假唤醒，也可能因多个等待者竞争而需要重新检查，不能直接把通知等同于条件仍成立。

**追问 2：通知早于等待时应如何设计状态？**

把“是否有任务”“是否已经结束”等事实保存在锁保护的变量中。

- 通知先到但任务仍存在时，后来的线程读到条件已满足，就无需等待。
- 不能只发送一次通知而不保存状态，因为条件变量一般不会像消息队列一样为未来等待者保存每次事件。

### 4. 死锁、活锁与饥饿有什么区别？

| 机制 | 特点与边界 |
|---|---|
| 死锁 | 死锁是参与者互相等待且无法推进 |
| 活锁 | 活锁是线程仍在运行或反复让步，却持续碰撞而没有完成有效工作 |
| 饥饿 | 饥饿是某个任务长期得不到资源，其他任务可能仍正常推进 |

三者都影响进度，但线程状态和修复方向不同。

**追问 1：为什么持续执行也可能无法取得有效进展？**

两个任务都发现冲突、主动退让、马上重试，又总在同一时刻冲突，就可能活锁；高优先级任务不断到来可能让低优先级任务饥饿。

应根据等待图、执行轨迹和完成率判断，分别采用锁顺序、随机退避、公平排队或优先级老化，而不是只看 CPU 是否在运行。

### 1. 虚拟地址如何通过页表映射到物理内存，分页解决了什么管理问题？

虚拟地址拆成虚拟页号和页内偏移，页表把页号映射到物理页框并记录权限等属性，偏移在转换中保持。

分页使进程看到连续的虚拟空间，而物理页可以分散分配，便于隔离、共享、按需分配和回收。

**追问 1：页表怎样把虚拟页映射到物理页，同一虚拟地址在不同进程中是否指向同一内存？**

不同进程通常有各自页表，所以相同虚拟地址可以对应不同物理页；共享映射也可让不同虚拟地址指向同一物理页。

地址值相同不代表跨进程指针可以直接使用，必须通过共享内存映射等明确建立关系。

**追问 2：分页与分段分别按什么方式组织地址空间，解决什么管理问题？**

分段按代码、数据、栈等逻辑区域管理，可有不同长度和权限；分页按固定大小块管理，降低物理连续分配要求。

- 分页通常消除物理分配的外部碎片，但仍有页内碎片与页表成本。
- 现代通用系统常以分页为主要内存管理机制，逻辑区域仍可由虚拟内存区域描述。

**追问 3：虚拟地址已经分配但物理页尚未就绪时，后续访问怎样衔接缺页处理？**

内核可以先登记合法虚拟区域，不立即分配物理页。

- 首次访问遇到不在场页触发缺页异常，内核检查合法性后分配零页、读取文件或恢复换出页，更新页表，再让指令重试。
- 若地址不合法或权限不允许，则可能向进程发送异常信号，而不是自动分配任何地址。

### 2. TLB 与多级页表分别怎样降低地址转换的成本和存储开销？

TLB 是地址转换缓存，命中时不用再逐级读取页表；多级页表把虚拟地址索引分层，只为实际使用的区域分配下级页表，减少稀疏地址空间的页表内存。

前者主要减少转换时间，后者主要减少页表空间，两者协同工作。

**追问 1：进程切换或工作集增大时，TLB 命中率为什么可能变化？**

切换到不同地址空间或访问更多页，会改变 TLB 中的有效工作集，导致更多未命中和页表遍历；地址空间标识等硬件可减少不必要的刷新。

大页可能提高 TLB 覆盖范围，但也增加分配、碎片和回收复杂度，不能只因 TLB miss 高就无条件启用所有大页方案。

### 3. 一次内存访问发生缺页异常后，操作系统如何决定后续处理？

缺页处理先检查地址是否属于合法虚拟区域及访问权限，再判断为何没有可用映射。

合法访问可能通过分配匿名页、从页缓存或磁盘读取文件、换入交换页或执行写时复制来满足；非法访问通常转为进程可见的异常，如 SIGSEGV。

**追问 1：内核首先如何区分地址非法、权限不允许与合法但页尚未就绪？**

地址没有对应 VMA，或写入不允许写的区域，不能按普通按需分配处理；合法区域中页尚未建立映射才继续查具体原因。

文件映射还可能遇到越过有效文件内容等情况并产生 SIGBUS，不能把所有缺页错误都统一当作内存不足。

**追问 2：匿名页、文件映射页和写时复制页，分别可能需要什么处理？**

匿名页首次访问可映射共享零页或分配清零页；文件映射页先查页缓存，未命中才需要读取；写时复制页在写入时分配私有页并复制原内容，再改为可写。

权限页错误不都代表恶意越界，也可能正是内核用来实现写时复制的正常机制。

**追问 3：发生缺页是否必然需要磁盘读取，怎样区分不同缺页带来的成本？**

不必然。页已在内存、只缺页表映射，或只需分配零页、执行 COW，都可能不读磁盘；需要文件或交换设备 I/O 的缺页成本高得多。

Linux 常用 minor/major fault 区分是否需要相应 I/O，但应结合实际内存和磁盘指标解释，而不是只统计总缺页次数。

### 4. 进程中的堆、栈、静态数据区和内存映射区域各适合保存什么？

栈保存调用帧、局部自动变量等，堆用于动态生命周期对象，静态数据区保存全局或静态存储期数据，内存映射区可承载共享库、文件映射和较大动态分配。

具体布局受语言运行时、编译器和操作系统影响，不能把某语言的“堆”直接等同于所有进程映射。

**追问 1：申请虚拟地址空间是否意味着物理内存已经全部分配？**

不一定。虚拟区域可以按需分配，首次访问才建立物理页；操作系统还可能采用过量承诺等策略。

- 申请接口成功不意味着未来所有页面访问都绝不会失败。
- 评估内存要区分虚拟大小、实际驻留、共享页和资源限制。

**追问 2：释放内存后进程的 RSS 为什么未必立即下降？**

内存分配器可能把释放块留在进程内供后续复用，页内还有其他存活对象也无法整页返还；共享页、缓存和碎片也会影响 RSS。

- 语言 GC 释放对象同样不保证立即向操作系统归还页。
- 应比较活对象、分配器保留空间和映射，而不是只凭 RSS 不降判断泄漏。

### 5. 页面置换用于解决什么问题？

物理内存有限时，需要从已有页中选择回收对象，为新访问腾出空间。

- 理想目标是回收近期不再使用且回收成本较低的页，同时避免把热点页反复换出。
- 页面置换与应用层缓存淘汰思路相似，但还要处理脏页、映射和交换设备等约束。

**追问 1：常见策略如何选择要换出的页面？**

FIFO 按进入顺序淘汰，简单但可能表现不佳；LRU 近似利用最近访问推测未来；Clock 通过访问位近似选择较冷页面；最优算法淘汰未来最晚使用的页，只能作理论对照。

真实 Linux 采用更复杂且随版本变化的回收机制，不能直接说内核逐次精确维护教材 LRU 链表。

### 6. 页缓存、交换空间与匿名内存有什么区别？

页缓存保存文件内容，匿名内存保存不直接对应普通文件的堆栈等数据，交换空间可作为部分匿名页等的后备存储。它们在可回收性和落盘方式上不同。

内存紧张时“回收缓存”和“把程序数据换出”不是同一操作。

**追问 1：内存紧张时，回收文件缓存页与换出匿名页分别需要什么处理？**

干净文件缓存可丢弃，之后从文件重读；脏文件页需先写回才能安全回收。

- 匿名页若仍需保留，通常要有交换等后备空间才能换出；没有相应空间时不能随意丢弃。
- 被锁定、正在使用或受其他限制的页也不一定可立即回收。

**追问 2：大量反复换入换出怎样影响业务进展，什么时候需要进一步检查 `OOM` 风险而不只看 `free` 数值？**

工作集大于可用内存时，页频繁换出又马上换入会造成抖动，CPU 可能不高但业务延迟很大。

应看 available、swap in/out、major faults、内存压力和 cgroup 限制，而非只看 free；若回收仍无法满足分配，就要检查 OOM 事件、增长来源并减少工作集或扩容。

### 7. CPU 缓存行与缓存一致性协议解决什么问题，伪共享为什么会降低并发性能？

CPU 缓存以缓存行（cache line）为单位存储和维护数据，一致性协议协调多个核心对同一缓存行的读取和写入。

- 两个线程修改不同变量，但变量恰好落在同一缓存行时，也可能反复使对方缓存失效，这就是伪共享。
- 逻辑上无共享字段，不代表硬件缓存粒度上没有冲突。

**追问 1：两个线程只修改各自的变量，为何仍可能相互影响？**

核心 A 写变量 a 需要获得所在行的写权限，核心 B 写同一行中的 b 又使 A 的副本失效，缓存行在核心间反复转移。

可通过分离热点字段、合理填充或分片计数降低竞争，但填充增加内存并依赖布局，需用性能测试确认，不应随意给所有字段加大间隔。

**追问 2：缓存一致性是否等于业务复合操作具有原子性？**

不是。缓存一致性协调缓存行副本，并不把“读取、加一、写回”变成一个原子业务操作，也不替代语言内存模型要求。

多个字段的不变量仍需锁或正确原子协议保护；volatile 可见性也不自动消除伪共享。

- [2. 在信号处理函数中执行日志输出、申请内存或加锁，为什么可能不安全？](#2-在信号处理函数中执行日志输出申请内存或加锁为什么可能不安全)

### 1. 系统调用、中断与异常如何触发内核处理？

系统调用是程序主动请求内核服务，如 read、write；中断通常来自设备等异步事件；异常由当前指令执行触发，如缺页或非法操作。

CPU 根据相应入口转入内核处理，内核完成工作后恢复用户程序，或进行调度、发送信号等后续动作。

**追问 1：用户态与内核态切换为什么存在开销，应用行为如何影响切换次数？**

切换涉及特权级、寄存器和内核入口处理，可能伴随安全检查、数据复制和调度，但一次系统调用不一定切换到另一个进程。

大量小 I/O 会增加固定开销，可用缓冲、批处理或适当零拷贝降低次数；不能为了少一次系统调用就忽略错误处理和内存占用。

### 2. 在信号处理函数中执行日志输出、申请内存或加锁，为什么可能不安全？

以 POSIX 信号处理为前提，处理函数可能打断正在持有库内部锁的代码。

- 此时再调用非异步信号安全的日志、malloc 或加锁操作，可能重入不一致状态或等待自己已经持有的锁。
- 线程安全不等于异步信号安全，普通互斥锁不能解决这种重入问题。

**追问 1：如何把复杂处理转交正常执行流程，而不是直接在信号处理函数中完成？**

处理函数只做最小操作，例如设置合适的 sig_atomic_t 标志，或用异步信号安全的 write 向非阻塞 self-pipe 通知；主事件循环再执行清理和日志。

- 也可在受控线程中通过 sigwait 类机制同步接收信号。
- 通知通道满、errno 保存和退出顺序都应考虑，不能把复杂业务放进信号回调。

### 1. 阻塞、非阻塞、同步与异步 I/O 描述的分别是什么行为？

阻塞与非阻塞描述一次调用在条件不满足时是否等待；同步与异步描述 I/O 完成过程及结果由谁推进和通知。

非阻塞 read 可以立即返回 EAGAIN，但真正读取仍由调用方随后执行；完整异步 I/O 则提交操作后，由系统完成并通过事件或回调通知结果。

**追问 1：调用是否立即返回，与数据准备和复制由谁完成，分别属于哪个维度？**

“立即返回”只说明没有在这次调用中等待，不说明数据已准备好或已复制完成。

- 同步 read 返回成功时数据通常已进入调用方缓冲；异步提交返回后缓冲的使用和释放需要等完成通知。
- 线程池把阻塞 read 包成 Future 是应用层异步接口，不等于底层内核 I/O 模型也变了。

**追问 2：使用非阻塞套接字不断重试，与等待就绪通知后再读取，有什么资源差异？**

不断空转重试会消耗 CPU；等待就绪通知可让线程在没有工作时睡眠，一次管理多个连接。

- 得到通知后再读仍要处理部分数据、EOF 和 EAGAIN。
- 为追求低延迟采用忙轮询需要明确专用资源和负载，不能作为通用服务器默认方案。

**追问 3：为什么不能把“用了多路复用”直接等同于完整异步 I/O？**

多路复用主要通知“某个描述符现在可能可读或可写”，并没有替应用完成所有读写、分帧和业务处理。epoll_wait 本身也可以阻塞。

真正的完成式异步接口通知的是已提交操作的完成结果，二者的缓冲生命周期和调用责任不同。

### 2. `select`、poll 与 epoll 如何管理待观察的文件描述符和就绪事件？

select 通过描述符集合，poll 通过数组表达本次关注对象，调用时检查并返回就绪情况；epoll 在内核维护长期关注集合和就绪队列，用 epoll_ctl 更新、epoll_wait 获取事件。

epoll 减少了大量空闲连接反复提交和扫描的成本，但仍需维护内核状态并处理实际活跃事件。

**追问 1：三者怎样登记关注的文件描述符并返回就绪事件？**

select 常用位图且有 FD_SETSIZE 等接口限制；poll 用 pollfd 数组，返回各项 revents；epoll 先创建实例、登记事件，再等待返回就绪项。

不能把 epoll 解释为用户态与内核态完全共享所有数据而没有任何复制，也不能把所有操作都说成固定 O(1)。

**追问 2：连接总数很多但活跃连接很少时，重复扫描和事件通知的成本怎样变化？**

select/poll 每次通常需要处理整个关注集合，连接总数大而活跃少时浪费更多工作；epoll 可主要返回就绪项，并摊销登记成本。

若几乎所有连接持续活跃，实际读写和事件处理仍随活跃量增长，优势也需结合负载验证。

**追问 3：得到可读通知后，为什么业务仍要正确处理实际读取结果与连接状态变化？**

通知后状态可能被其他线程消费或改变，可读也可能表示 EOF 或错误，不一定是有完整业务消息。

应使用非阻塞描述符，检查实际返回值、错误码和连接生命周期，避免拿着一次过时通知执行永久阻塞读取。

### 3. epoll 的 LT 与 ET 触发方式有什么区别？

LT 是水平触发，只要描述符仍满足关注的就绪条件，后续等待仍可返回；ET 是边沿触发，主要在相关就绪变化或新事件到来时通知，不能依赖剩余数据持续产生重复提醒。

ET 常与非阻塞 I/O 和完整的读写状态机配合使用。

**追问 1：LT 与 ET 对“仍然有数据可读”和“状态刚发生变化”的通知方式有什么区别？**

LT 下缓冲还有可读数据，下一次 epoll_wait 通常仍报告可读；ET 下消费了一个事件却只读一部分，不能保证下一次仅因旧数据仍在就再次通知。

实际事件合并与到达方式由内核管理，因此不是精确“每个包通知一次”的模型。

**追问 2：ET 下只读取部分数据就返回，后续可能怎样遗漏处理机会？**

若对端不再发新数据，应用可能回到 epoll_wait 等待，而内核缓冲中还留着未读内容，双方因此卡住。

解决方式是持续读取到 EAGAIN；需要公平地限制单连接处理量时，可把未读完连接放入应用就绪队列继续处理，而不是直接忘记它。

**追问 3：怎样使用非阻塞读取并处理 `EAGAIN`，为什么读取就绪仍不等于完整应用消息已经到达？**

read 返回正数就处理并继续，返回 0 处理对端有序关闭，EINTR 按策略重试，EAGAIN/EWOULDBLOCK 表示当前已读尽可立即取得的数据，再等待后续事件；其他错误按连接策略关闭。

读尽内核缓冲后仍可能只有半帧，应用解析状态必须保留，不能把 EAGAIN 当成消息结束。

### 4. mmap 与 sendfile 等零拷贝路径分别减少了哪些拷贝或切换？

普通文件读取后再发送通常经历磁盘到页缓存、页缓存到用户缓冲、用户缓冲到套接字缓冲、再由设备发送。

- mmap 让用户地址映射页缓存，减少一次显式读取复制；sendfile 可在内核内把文件数据送往套接字，避免经过用户缓冲。
- 零拷贝是减少特定 CPU 复制，不是数据完全不移动。

**追问 1：普通文件读取再发送的路径，通常在哪些地址空间之间复制？**

典型 read+write 路径有内核到用户、用户到内核两次 CPU 复制，另有设备到内存、内存到网卡等 DMA 传输和系统调用开销。

缓存命中、网卡卸载及内核实现会改变实际路径，因此“四次复制”只能作为带前提的解释模型。

**追问 2：mmap 与 sendfile 分别省去了什么拷贝或切换，哪些设备传输仍然存在？**

mmap 省去页缓存到独立用户缓冲的 read 复制，但映射页仍可能缺页，后续普通 socket write 仍可能复制；sendfile 避免用户态往返，在支持的硬件路径上还可减少内核缓冲间 CPU 复制。

磁盘读取、网络发送和必要协议处理仍存在，不能把减少拷贝等同于没有 I/O 成本。

**追问 3：需要加工数据、加密或跨平台时，怎样判断这些路径是否仍然适用？**

若需逐字节加工数据，往往仍要访问或生成用户态缓冲；TLS 加密可能改变 sendfile 路径，内核 TLS 或硬件卸载有版本和设备条件。不同操作系统和文件类型支持也不同。

应测量 CPU、吞吐和延迟，并保留正确的部分写入、错误与回退处理。

### 5. 文件描述符、打开文件描述（open file description）与文件本身是什么关系？

文件描述符是进程表中的整数索引；打开文件描述是内核记录一次打开状态的对象，包含文件偏移和部分状态标志；底层文件由 inode 等表示。

多个描述符可以引用同一打开文件描述，也可以通过不同打开文件描述访问同一个文件。

**追问 1：同一个文件被多次 open，以及通过 dup 复制文件描述符，在文件偏移量和状态标志的共享上有什么区别？**

对同一路径分别 open 通常创建不同打开文件描述，文件偏移相互独立；dup 复制描述符引用，二者共享偏移和文件状态标志。

- 描述符自身的 close-on-exec 等标志则属于另一层。
- 需要并发按固定位置读写时，可用 pread/pwrite 避免共享偏移竞争。

**追问 2：fork 后父子进程继承的文件描述符可能共享哪些状态？**

fork 复制父进程描述符表，但对应条目仍引用同一打开文件描述，因此父子读写可能共同推进文件偏移，并共享相应状态。

用户态 stdio 缓冲却被复制，若父子都刷新已有缓冲可能产生重复输出，这与内核偏移共享是两个问题。

**追问 3：关闭其中一个文件描述符，是否必然使其他引用同一打开文件描述的描述符失效？**

不会。关闭一个描述符只是移除该引用，其他有效引用仍可使用，直到相关打开文件描述不再被引用。

数字描述符很快可能被复用，所以异步任务不能仅凭旧整数判断它仍指向原文件；应明确所有权和关闭时机。

### 6. Linux 文件名、目录项与 inode 之间是什么关系？

目录项把文件名映射到 inode，inode 保存文件元数据及数据块关联等信息，文件名本身不存成 inode 中的唯一名称。

一个 inode 可以有多个硬链接名称，打开文件又可以在名称被移除后继续存活。路径、目录项和已打开文件对象不能混为一谈。

**追问 1：重命名文件、建立硬链接和创建软链接时，哪些关系发生变化？**

同文件系统内重命名主要改变目录中的名称关系；硬链接增加指向同一 inode 的目录项；软链接是独立文件，内容是另一个路径。

软链接路径目标不存在时会悬空，硬链接则仍是同一文件的有效名称，通常不能跨文件系统建立硬链接。

**追问 2：文件被删除但进程仍持有打开的文件描述符时，为什么仍能继续访问数据，磁盘空间何时才能回收？**

unlink 删除名称并减少链接计数，不会让已打开描述符立即失效。

- 文件在没有链接且相关打开引用、映射等都释放后，数据空间才可最终回收。
- 因此日志被删除后进程继续写旧文件，会出现 du 看不到、df 仍占用的现象。

**追问 3：日志轮转时怎样协调路径替换与进程重新打开文件，避免继续写入不可见的旧文件？**

常见做法是重命名旧日志、创建新文件，再通知应用按约定重新打开日志；确保原描述符关闭后旧文件可回收。

copytruncate 可以避免重开需求，但复制与截断之间存在丢失或重复的竞争窗口，应明确接受程度。不能仅换路径就假定进程已自动写入新 inode。

## 要点回顾

- 共享与隔离是并发设计的起点：线程共享地址空间，多进程有不同的隔离边界，创建成本不是唯一的选择依据。
- 可运行、等待与真正执行分开观察：上下文切换、缺页、锁等待和资源回收都可能影响请求进度。
- 区分就绪通知与操作完成：多路复用不自动完成业务读写，零拷贝也只是减少特定的数据复制与用户态往返。
