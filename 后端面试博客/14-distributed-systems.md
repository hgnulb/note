# 十四、分布式：一致性、锁、事务、ID 与任务调度

从多实例带来的部分失败问题出发，本文将一致性理论与锁、事务、发号、数据分布和任务调度联系起来。讨论重点不是给组件贴 CP 或 AP 标签，而是在明确操作、网络与故障条件后，解释哪些结果能够被保证。

## 1. 分布式基础

**本节问题**

- [1. 从单机扩展到多实例后，会新增哪些通信、状态共享和部分失败问题？](#1-从单机扩展到多实例后会新增哪些通信状态共享和部分失败问题)
- [2. 服务调用超时为何只能说明结果未知，而不能直接说明对方执行失败？](#2-服务调用超时为何只能说明结果未知而不能直接说明对方执行失败)
- [3. 多机房部署如何在可用性、访问延迟与数据一致性之间选择方案？](#3-多机房部署如何在可用性访问延迟与数据一致性之间选择方案)

### 1. 从单机扩展到多实例后，会新增哪些通信、状态共享和部分失败问题？

多实例不是把同一个单机程序复制几份就完成了。每个进程有独立内存和本地锁，远程通信可能延迟、丢失或返回未知结果；某个节点成功时，另一个节点可能已经失败。

因此需要重新划分状态的权威位置、跨节点一致性边界、幂等规则，以及故障发现和恢复流程。

**追问 1：本地内存、锁与事务的边界在多实例后有哪些变化？**

本地缓存可能出现不同版本，本地锁只能保护当前进程，本地数据库事务也不会自动覆盖其他数据库或 RPC。

共享状态应移到明确的存储与协调机制，或设计可合并的分片状态；不能把静态变量、ThreadLocal 或进程内单例当成全局唯一状态。

**追问 2：只有一部分节点或网络链路失效时，怎样区分可用节点与可推进的业务？**

节点活着不等于业务可用，它可能连不上数据库或缺少必要副本。

- 故障检测只能基于超时和心跳作出判断，无法在任意网络延迟下完美区分慢节点与宕机。
- 应按操作检查依赖、仲裁和资源条件，区分可降级读取与必须停止的写入。

**追问 3：状态复制、故障检测和恢复需要怎样配合，而不只是把进程部署多份？**

状态复制决定故障后还能恢复什么，故障检测决定何时尝试切换，恢复协议决定谁有权继续写。

- 切换需要避免两个节点同时作为权威，并通过日志、版本、幂等与对账修复部分完成操作。
- 还要演练节点暂停、网络分区和旧节点恢复，而不仅测试正常负载均衡。

### 2. 服务调用超时为何只能说明结果未知，而不能直接说明对方执行失败？

超时只说明调用方在规定时间内没有收到可用结果，不能推断服务端没有执行。请求可能未送达，也可能已经成功提交但响应丢失。

对有副作用的操作，应使用稳定业务请求 ID、可查询的执行状态和幂等重试，保留结果未知状态，直到获得足够证据再决定继续或补偿。

**追问 1：请求未到达、执行中途失败与已成功但响应丢失，从调用方视角有什么相同现象？**

这几种情况对调用方都可能表现为超时、连接中断或网关错误。

- TCP 层确认也只能反映字节传输，不等于业务事务提交。
- 仅根据一次网络错误直接重发扣款，或直接回补库存，都可能与远端已经完成的操作冲突。

**追问 2：怎样通过业务流水号、结果查询和幂等重试逐步确认？**

第一次调用前生成业务流水号，后续查询与重试都使用同一标识。

- 服务端把标识、请求摘要、执行状态和结果持久化，并将关键业务效果与幂等登记置于同一原子边界。
- 查询不到还要区分请求尚未登记与真正确定未执行，必要时等待或沿原幂等键重试。

**追问 3：订单或资金流程如何保存“处理中”与“结果未知”，避免盲目补偿已经成功的操作？**

本地状态机应区分已发起、处理中、结果未知、成功和确定失败，并记录远端流水与尝试信息。

- 后台对未知状态主动查单、有限重试，超过处理窗口后告警或转人工。
- 补偿本身也是独立业务操作，必须检查原操作结果、满足前置状态并具有幂等标识。

### 3. 多机房部署如何在可用性、访问延迟与数据一致性之间选择方案？

先定义 RTO，即可接受的恢复时间，以及 RPO，即可接受的数据损失范围，再选择同城多副本、跨区域主备或多活方案。

- 跨机房同步复制通常增加写入延迟并影响分区时可用性；异步复制降低正常链路成本，但切换可能丢失未复制的数据。
- 多活还必须解决写入归属和冲突，不能只部署两个入口。

**追问 1：先明确可接受的恢复时间和数据损失，再怎样选择主备、读路由与复制策略？**

RPO 接近零要求提交确认覆盖足够的异地持久副本，代价是跨地域往返和故障时等待或拒绝。允许有限损失则可以异步复制并监控复制滞后。

RTO 由故障确认、选主、连接切换、缓存预热及业务恢复共同决定，不只是 DNS 修改耗时。

**追问 2：主机房失效、网络分区与用户跨机房访问，分别会挑战哪些保证？**

主机房失效考验副本完整性与容量；网络分区考验是否会产生两个可写主；跨机房访问考验读后写一致性与尾延迟。

可以按用户或业务实体固定写入归属，但跨分区事务与迁移仍需明确协议。读副本不能不加条件地承诺最新状态。

**追问 3：故障切换后怎样隔离旧写入并核对数据，恢复演练应验证什么？**

通过仲裁、租约及资源侧 fencing 隔离旧写入，更新路由并处理存量连接。

- 核对日志位点、未完成事务和业务流水，再让恢复节点以正确角色加入。
- 演练要测实际 RTO/RPO、切换后的容量、旧主恢复、重复请求及回切流程，而不是只确认备用机能启动。

## 2. 一致性理论与协议

**本节问题**

- [1. 发生网络分区时，如何结合 CAP 与业务需求确定一致性和可用性的取舍？](#1-发生网络分区时如何结合-cap-与业务需求确定一致性和可用性的取舍)
- [2. CAP 中的一致性与数据库 ACID 中的一致性是一回事吗？](#2-cap-中的一致性与数据库-acid-中的一致性是一回事吗)
- [3. Paxos、Raft 与 ZAB 分别围绕什么问题设计？](#3-paxosraft-与-zab-分别围绕什么问题设计)
- [4. 多数派相交为什么有助于维护一致性，却不能单独构成完整的共识协议？](#4-多数派相交为什么有助于维护一致性却不能单独构成完整的共识协议)

### 1. 发生网络分区时，如何结合 CAP 与业务需求确定一致性和可用性的取舍？

CAP 讨论的是出现网络分区时，系统不能同时保证线性一致性和所有非故障节点对请求的可用响应。

业务需要先确定哪些操作不能接受冲突，例如余额扣减通常宁可拒绝一部分写入；允许冲突后合并的展示或统计，可以接受暂时不同状态。它不是正常网络下随意“任选两个”的产品标签。

**追问 1：网络分区发生后，哪些操作必须选择等待、拒绝或接受可能不同的状态？**

孤立分区无法确认其他分区最新状态时，若仍接受读写，就可能返回旧值或形成冲突；要维持线性一致性，则部分节点需等待、转发或拒绝。

不同操作可以采取不同策略，例如允许读取带时效说明的缓存，但停止不可安全完成的余额更新。

**追问 2：强一致与最终一致分别适合什么业务约束，BASE 怎样表达取舍？**

强一致适合不能并发突破约束的关键状态；最终一致适合能容忍传播延迟并有收敛规则的视图。

- 最终一致必须说明更新怎样传播、冲突怎样解决，以及在停止更新后能否收敛。
- BASE 强调基本可用、软状态和最终一致，是设计思路，不是替代事务约束的完整协议。

**追问 3：讨论具体组件时，为什么还需要限定读写操作、部署方式和保证范围？**

同一个组件可能支持不同读一致性、复制确认和故障切换配置，其保证也可能只针对单 key 或单事务。

- 必须指出是哪个操作、哪些节点故障、是否发生分区以及是否允许旧数据。
- 不能因为产品用了 Raft，就直接推断所有外部业务流程都强一致。

### 2. CAP 中的一致性与数据库 ACID 中的一致性是一回事吗？

不是。CAP 中的 C 通常指线性一致性：操作看起来在调用与返回之间某个时刻原子生效，并尊重真实时间顺序。

- ACID 中的 C 指事务前后满足数据与业务不变量，例如约束合法、转账金额守恒。
- 数据库提供事务机制，应用仍要正确表达业务约束；两种“一致性”不能直接互相替代。

**追问 1：讨论某个系统是 CP 还是 AP 时，为什么必须明确网络分区、操作类型和保证范围？**

CP/AP 是对故障假设下行为的概括，不是脱离配置的永久属性。

- 一个系统可能对写入要求多数派，对读取允许访问旧副本；也可能保证单行一致但不保证跨服务事务。
- 描述时应明确分区中的请求是否成功、返回多新数据以及约束作用范围。

### 3. Paxos、Raft 与 ZAB 分别围绕什么问题设计？

Paxos、Raft 与 ZAB 都与故障条件下的共同决定和状态复制有关，但抽象层次不同。

- 基础 Paxos 解决一个值的共识，Multi-Paxos 将其用于连续决定；
- Raft 围绕复制日志组织选主、日志复制和安全规则；
- ZAB 是 ZooKeeper 使用的原子广播协议，重点保证事务顺序及主节点恢复后的历史一致性。具体产品还有协议之外的存储和客户端语义。

**追问 1：这些协议试图解决共同决定与复制顺序中的哪些问题？**

核心问题是多个副本不能各自选择互相矛盾的已提交历史，同时在满足可用节点条件时继续推进。

- 共识通常决定一个值或日志位置的值，状态机复制再按一致顺序执行确定性操作。
- 日志达成共识不等于业务外部副作用自动只执行一次。

**追问 2：`Leader`、任期或轮次，以及提交顺序分别怎样帮助处理故障？**

轮次、任期或 epoch 用来区分新旧领导者和提案，多数派交集与持久化承诺帮助新领导者继承已确定结果。提交顺序约束防止副本跳过必要前缀。

不能只凭 Leader 名称认为不会分裂，旧 Leader 必须被协议拒绝或在失去仲裁后停止有效提交。

**追问 3：比较 Paxos、Raft 与 ZAB 时，应区分协议目标、实现方式和具体产品，而不只背一个分类结论。**

比较时可说明 Paxos 的提案与接受规则、Raft 的领导者驱动日志及选举限制、ZAB 的恢复和广播阶段。

不要把“Paxos 无 Leader、Raft 有 Leader”当成普遍结论，实际 Multi-Paxos 常使用稳定领导者。协议安全性、活性条件和产品读写语义应分别讨论。

### 4. 多数派相交为什么有助于维护一致性，却不能单独构成完整的共识协议？

多数派相交只保证两组多数派至少共享一个节点，提供传递历史信息的机会；如果共享节点可以随意接受冲突值，交集本身并不能阻止错误。

共识还要求持久化任期与投票、拒绝过期请求、继承已提交历史，以及规定哪些日志可以提交。

**追问 1：任期、日志顺序和提交规则分别还需要约束什么？**

任期或轮次限制旧领导者继续被认可，日志匹配规则检查前缀一致，选举规则约束候选者是否足够新，提交规则定义何时对外确认。

节点重启后还必须保留必要状态，否则曾经作出的投票或承诺会被忘掉，破坏安全性。

**追问 2：复制副本数达到多数是否就等于已经提交？**

不一定。例如 Raft 的 Leader 不能仅靠“某条旧任期日志当前已复制到多数节点”就直接据此提交该旧条目；通常需要当前任期条目达成多数派复制，再连带提交其前缀。

不同系统还可能把复制确认与持久化确认分开，必须按协议定义判断。

## 3. 分布式锁

**本节问题**

- [1. 本地 `synchronized` 或 Mutex 为什么不能保护多个服务实例之间的互斥操作？](#1-本地-synchronized-或-mutex-为什么不能保护多个服务实例之间的互斥操作)
- [2. 多实例业务需要互斥时，如何选择数据库、Redis、ZooKeeper 或 etcd 锁方案？](#2-多实例业务需要互斥时如何选择数据库rediszookeeper-或-etcd-锁方案)
- [3. 分布式锁持有者暂停、锁过期或网络分区后，如何判断互斥是否仍然有效？](#3-分布式锁持有者暂停锁过期或网络分区后如何判断互斥是否仍然有效)

### 1. 本地 `synchronized` 或 Mutex 为什么不能保护多个服务实例之间的互斥操作？

`synchronized` 和普通 Mutex 协调的是当前进程内的执行单元。

- 两个服务实例即使使用相同变量名或相同业务 ID，也持有不同的本地锁，无法互相排斥。
- 跨实例互斥需要共享的原子协调点，或者直接利用数据库约束、状态条件更新来保证业务正确，不是所有场景都必须引入独立锁服务。

**追问 1：分布式锁至少应检查哪些安全性、活性与故障恢复要求？**

安全性要求同一资源不能被两个有效持有者同时破坏；活性要求故障后其他请求最终有机会继续。

还需检查锁所有权、误删、租期、续期、可重入需求、等待超时、主从切换，以及旧持有者恢复后的写入限制。锁服务可用并不自动等于业务操作安全。

### 2. 多实例业务需要互斥时，如何选择数据库、Redis、ZooKeeper 或 etcd 锁方案？

先看资源和业务约束：如果保护的就是单库记录，数据库事务、唯一约束或条件更新通常更直接；

- Redis 锁延迟低、使用方便，但要评估异步复制和租期失效；
- ZooKeeper、etcd 提供基于一致性协议的协调状态，但仍有会话或租约到期、客户端暂停等问题。
- 选择的是明确故障模型下的保证，不是简单比较加锁速度。

**追问 1：业务需要怎样的互斥粒度、延迟、故障容忍和使用复杂度？**

明确锁保护的业务实体、持有时间、可接受等待和故障停顿，以及是否需要公平、可重入或锁外资源保护。

- 过大粒度会串行化无关操作，过小粒度可能不能保护完整不变量。
- 若唯一约束就能完成防重复，不必额外增加一条分布式锁故障链路。

**追问 2：数据库、Redis、ZooKeeper 与 etcd 在锁状态、过期和故障恢复方面应比较哪些行为？**

数据库锁通常跟随事务或连接释放，但长事务占用连接和锁；Redis 租期需原子设置并校验持有者释放，切主存在复制窗口。

ZooKeeper 临时节点依赖会话，etcd Lease 依赖续约；两者失去多数派时部分操作不能继续。所有方案都需处理获取结果未知和旧客户端恢复。

**追问 3：选定方案后，锁持有者停顿或网络分区时，受保护操作怎样继续得到正确约束？**

锁失效通知不是瞬间可靠的，旧执行者可能恢复后继续写。

- 关键资源应支持单调 fencing token、版本条件或幂等状态转换，拒绝过期持有者的请求。
- 若资源不支持这些校验，就要承认租约锁的业务安全边界，不能声称任何暂停下都严格互斥。

### 3. 分布式锁持有者暂停、锁过期或网络分区后，如何判断互斥是否仍然有效？

不能只检查客户端是否曾经拿到锁。客户端暂停、网络断开或续租失败时，锁可能已经到期并被其他客户端取得，但旧客户端并不知道。

正确性要落到受保护资源上的版本或 fencing 校验，让旧请求即使恢复执行也不能覆盖新持有者的有效结果。

**追问 1：旧持有者暂停期间锁已失效，新持有者开始工作后，旧请求恢复会有什么风险？**

例如 A 获锁后长时间暂停，租期到期，B 获锁并写入新状态；A 恢复后仍执行旧写入，可能覆盖 B。

即使 A 释放锁时会校验随机 token，也只能防止误删 B 的锁，不能防止 A 已经发往数据库或文件系统的旧业务写入。

**追问 2：fencing token 怎样让资源侧区分新旧持有者，检查必须放在哪里才有效？**

每次有效授锁返回递增的 fencing token，资源端在执行写入时原子检查 token 不落后于已经接受的有效任期，并保存比较状态。

- 检查必须与业务修改在同一保护边界内，不能只在客户端先查锁后写。
- token 只区分新旧持有者，同一持有者的重复操作仍需业务幂等。

**追问 3：只有锁服务端的过期时间，没有资源侧校验时，为什么不能直接推出业务写入永远互斥？**

服务端到期只是允许别人重新获锁，不会自动撤销旧线程的 CPU 执行权，也不能收回已在网络中的请求。

- 只有资源侧拒绝旧任期、事务版本校验或等价约束，才能把锁状态变化落实到真实业务效果。
- 对不支持校验的外部系统，只能依赖额外协议和明确风险假设。

### 1. 订单、库存分别由两个服务和两个数据库管理时，为什么本地事务不足以保证整条链路一致？

本地事务只能原子提交同一个事务资源管理器覆盖的操作。

- 订单库提交成功后库存服务可能超时或失败，两个独立数据库不会因为方法上加了一个事务注解就共同回滚。
- 需要选择资源预留、分布式事务协议，或可靠事件加补偿，让每个中间状态和失败路径都有定义。

**追问 1：应先明确哪些业务不变量，再决定强一致、最终一致或补偿方案？**

先确定不能超卖、不能重复扣款、已付款订单不能无记录消失等不变量，以及哪些状态允许暂时不一致。

- 若库存预留失败可以撤销订单，可采用状态机和最终一致；若必须同时成功且资源支持，则评估 XA 等方案。
- 技术方案应服务于约束，不应先选一个中间件再假设业务自然正确。

### 2. 分布式事务两阶段提交如何组织协调者和参与者？

两阶段提交由协调者统一决定事务结果。第一阶段询问参与者能否提交，参与者完成本地准备并持久化必要状态，返回同意或拒绝；所有参与者同意后，协调者持久化提交决定并通知提交，否则决定回滚。

它能协调多个资源，但准备状态可能长期占锁，协调者故障还可能导致阻塞。

**追问 1：准备与提交阶段分别要求参与者保存什么状态并持有什么资源？**

准备阶段的参与者必须能够在重启后恢复承诺，通常保存 redo/undo 或等价事务日志，并保留阻止冲突修改的资源。第二阶段收到最终决定后提交或回滚，再释放资源。

协调者的最终决定也需要可靠记录，不能仅存在内存中。

**追问 2：协调者或某个参与者在不同阶段故障时，哪些结果无法立即确认？**

参与者尚未同意准备时通常可以拒绝或回滚；一旦进入已准备状态，若不知道协调者决定，就不能随意自行提交或回滚。

协调者可能已记录提交但只通知了部分节点，因此其余节点看到超时并不代表全局失败。恢复时需查询可靠决定或执行协议规定的终止流程。

**追问 3：恢复与超时处理为什么需要遵守协议，而不能简单把未知状态当成回滚？**

把未知状态直接回滚，可能与已经提交的其他参与者形成不一致。

- 超时用于触发恢复与调查，不自动赋予任意改变最终结果的权利。
- 生产上要评估协调者持久化、高可用、锁超时和人工恢复；复制协调者能改善可用性，但不能消除所有分区下的等待。

### 3. 三阶段提交相比两阶段提交试图缓解什么问题？

三阶段提交在准备和最终提交之间引入预提交阶段，试图让参与者拥有更多共同状态，并在特定同步与故障假设下减少两阶段提交的阻塞。

它不是“增加一次交互就同时获得任何网络条件下的强一致和高可用”。

**追问 1：在网络分区和超时假设下，是否可以不加条件地认为它同时消除了阻塞并保证一致性？**

不能。经典三阶段提交的非阻塞结论依赖有界延迟等假设；发生网络分区或超时判断与真实状态不一致时，不同分区可能依据各自状态作出冲突决定。

面试中应说明它缓解的是特定故障模型下的阻塞问题，而不是绕过 CAP 或代替实际产品的完整一致性协议。

### 4. TCC 如何把跨服务事务拆成 Try、Confirm 与 Cancel？

TCC 把业务拆成预留资源的 Try、确认预留的 Confirm，以及释放预留的 Cancel。

- 它是业务层协议：例如 Try 冻结库存而不是立即把交易视为完成，Confirm 将预留转为已消费，Cancel 解除冻结。
- 协调者驱动各分支终态，每个分支要有持久化记录、合法状态转换和幂等能力。

**追问 1：Try 阶段预留的业务资源，与直接完成业务修改有什么区别？**

预留让资源暂时不能被其他交易使用，但仍保持可以确认或释放的业务状态。

- 若 Try 已经发送不可撤销的通知或完成无法退款的扣费，就失去了容易取消的前提。
- 预留也有成本，需要控制有效期、冻结规模和长期未决事务。

**追问 2：Confirm 和 Cancel 怎样根据持久化状态决定执行动作？**

分支记录事务 ID、业务资源、预留量和状态，Confirm 只允许从已预留转为已确认，Cancel 只允许释放仍处于预留态的资源。

状态转换和真实库存或余额变化放在本地事务中，避免只改状态未改资源。已完成的重复请求返回已有结果。

**追问 3：重复调用和部分失败时，怎样让提交或补偿可以安全重试？**

用唯一事务或分支 ID 去重，确保重复 Confirm 不重复扣减、重复 Cancel 不重复回补。

- 网络错误后协调者重试同一分支而不是生成新业务请求；长期失败进入重试队列和告警。
- 需要处理空回滚和悬挂，不能仅靠“执行前查一次状态”而没有原子约束。

### 5. TCC 中的空回滚、悬挂与重复提交分别如何发生？

空回滚是 Cancel 到达时 Try 尚未成功预留；悬挂是 Cancel 已完成后迟到的 Try 又预留资源；重复提交是 Confirm 被重试并可能多次产生业务效果。

解决办法是持久化分支状态机，用唯一 ID 和条件转换把处理次序与资源操作绑定，而不是假设网络按发送顺序交付。

**追问 1：Cancel 先于 Try、Try 迟到以及 Confirm 重复到达，分别会形成什么问题？**

Cancel 先到时不能盲目增加库存，否则会凭空回补；需要记下已取消状态。随后到达的 Try 应看到终态并拒绝预留。

- Confirm 重复到达应返回已确认结果，不能再次扣减。
- Confirm 与 Cancel 的竞争要由协调结果和本地状态条件共同约束。

**追问 2：事务记录和状态机应怎样限制合法转换，阻止迟到的 Try 重新占用资源？**

可维护不存在、已预留、已确认、已取消等状态。空回滚时创建取消墓碑；Try 只有在不存在且未被取消时才能登记和预留，状态插入与资源冻结同事务完成。

Confirm、Cancel 使用条件更新并检查影响行数，禁止从取消态恢复为预留态或从确认态盲目释放。

**追问 3：补偿失败后怎样继续恢复，避免虽然阻止了重复执行，资源却一直未释放？**

幂等记录不能在资源尚未释放时先标成补偿成功。释放资源与取消状态应共同提交；失败则保留可重试状态、错误原因和重试进度。

后台扫描长时间未决分支，按协调者最终决定重试，超出自动恢复能力时告警并进入有审计的人工处置。

### 6. 本地消息表与可靠消息方案如何衔接数据库更新和消息发送？

在业务数据库同一本地事务中写业务数据和 Outbox 消息记录，提交后由发送器投递 MQ，确认后标记发送完成。

- 这样避免业务已提交却没有任何待发送记录，但发送与更新发送状态仍不是跨系统原子操作，因此消息可能重复。
- 配合消费端幂等、重试和对账，才能形成可靠的最终一致链路。

**追问 1：业务更新与待发送消息怎样保存在同一个数据库本地事务中？**

业务更新和消息插入必须使用同一数据库事务、同一有效连接边界，消息包含唯一事件 ID、业务 ID、版本及必要载荷。

- 事务回滚时两者一起回滚；提交后发送器通过轮询或 CDC 发现待发送事件。
- 不要在事务提交前先发消息，再把“未来一定会提交”当成事实。

**追问 2：后台发送成功但更新发送状态前退出，重新投递会带来什么重复？**

MQ 已确认但发送器在标记完成前退出，恢复后会再次发送同一事件 ID。

- 不能为了避免重复，先把消息标记已发送再投递，否则宕机会永久漏发。
- 正确选择是允许至少一次投递，再由幂等消费控制重复业务效果。

**追问 3：消费端幂等、发送重试和长期失败告警怎样共同完成最终一致性，而不是假设消息仅会发送一次？**

发送器有限退避重试并监控积压和最老未发送时间；消费者把去重登记和业务更新放在同一本地事务中。

- 坏消息进入可查询的失败状态或死信处理，不静默丢弃。
- 最终一致还依赖服务最终恢复、持续重试与人工修复，不能把 MQ 已接收等同于所有下游已完成。

### 7. 跨服务业务应如何选择强一致事务方案或最终一致方案？

先判断业务是否允许可见的中间状态，以及操作能否预留或补偿。

- 跨少量支持 XA 的资源且事务很短，可以评估强协调事务；库存预留等适合 TCC；长流程和跨异构系统常采用 Saga 或可靠事件。
- 不能因为“最终一致性能好”就允许关键资金或库存不变量在中间状态被突破。

**追问 1：如何比较业务容忍度、补偿复杂度和系统可用性成本？**

比较的不只是正常延迟，还包括持锁时间、协调者故障、资源支持范围、补偿是否可逆、运营对账成本和允许的恢复窗口。

- 最终一致需要明确 Pending 等中间状态及查询体验；强协调方案需要接受分区时等待或拒绝。
- 优先缩小事务边界，避免为了技术上的统一把整条长业务链锁在一起。

### 8. Seata AT 模式如何记录回滚信息并协调全局事务？

Seata AT 通过数据源代理执行受支持的 SQL，记录修改前后镜像和回滚日志。

- 第一阶段在本地提交前完成分支注册并取得相应全局锁，然后把业务修改与回滚日志一起提交本地事务，释放本地数据库锁；不能把顺序理解成“先随意提交，再申请全局锁”。
- 第二阶段全局提交主要清理回滚信息，全局回滚则依据镜像执行补偿。
- 全局锁约束参与这一机制的写入，普通读取及绕过代理的操作仍需要另行分析隔离边界。

**追问 1：它与手工 TCC 的业务侵入性、锁持有和数据库支持条件有什么区别？**

AT 对业务代码侵入较低，但依赖受支持的数据库、JDBC 访问、SQL 和数据源代理；TCC 由业务显式实现预留、确认与取消，开发成本更高但可适配非数据库资源。

AT 第一阶段提交后释放本地锁，仍以全局锁协调参与该机制的写入；绕过代理的写入不能假设受全局锁保护。

**追问 2：全局回滚遇到数据已被修改时应关注什么？**

回滚前要比较当前数据与记录的后镜像，发现外部修改时不能直接用前镜像覆盖，否则可能抹掉合法更新。

- 应识别脏写、保留未决状态并按策略重试或人工修复。
- 普通 SELECT 也不能自动视为全局事务级的已提交读，应明确代理方式和所需隔离边界。

### 9. Saga 如何将长业务流程拆为本地事务与补偿操作？

Saga 把长流程分成多个已经独立提交的本地事务，并为可补偿步骤定义相应补偿。

- 某一步失败后，由编排器或事件协作驱动重试、回退或补偿。
- 它没有把所有步骤锁成一个数据库事务，因此需要业务状态机、幂等以及对中间状态的隔离策略。

**追问 1：每一步本地事务与相应补偿分别表达什么业务含义？**

例如创建订单、扣减或预留库存、发起支付是不同本地事务；取消订单、释放库存、退款是业务补偿。

补偿不是数据库 undo，它可能产生新的业务流水，也未必把世界恢复到完全相同的历史状态，例如已发短信无法收回。

**追问 2：与 TCC 的预留资源相比，Saga 的隔离性和补偿成本有什么差异？**

TCC 通常先预留再确认，资源在确认前有明确冻结状态；Saga 常允许步骤先提交，其他业务可能看到中间结果，因此隔离较弱。可用业务锁、状态检查或语义约束限制冲突。

补偿需要处理外部世界和并发变化，不能仅把每条正向 SQL 反过来执行。

**追问 3：补偿本身再次失败或业务操作无法完全逆转时，怎样保存状态并继续处置？**

保存每步执行与补偿状态、幂等键和错误原因，失败后继续重试同一动作。

- 不可逆操作应尽量放在流程后段，或设计替代补偿、人工审核与对账流程。
- 不要把整个 Saga 标记已回滚后丢掉仍失败的补偿；终态必须反映实际业务结果。

## 5. 分布式 ID

**本节问题**

- [1. 分布式 ID 应如何在 UUID、自增、号段和雪花方案之间选型？](#1-分布式-id-应如何在-uuid自增号段和雪花方案之间选型)
- [2. 基于 Redis `INCR` 生成全局 ID 时，怎样组织前缀、时间段与序列号？](#2-基于-redis-incr-生成全局-id-时怎样组织前缀时间段与序列号)
- [3. 号段模式如何降低 ID 生成对数据库的访问压力？](#3-号段模式如何降低-id-生成对数据库的访问压力)

### 1. 分布式 ID 应如何在 UUID、自增、号段和雪花方案之间选型？

UUID 便于分散生成，但应选定版本并评估长度、排序和碰撞模型；数据库自增简单却依赖中心写入；号段把数据库协调摊薄到批次；雪花类方案组合时间、节点和序列，通常趋势有序、吞吐高，但依赖节点身份和时钟管理。

先明确唯一范围、排序要求和故障恢复，再选方案。

**追问 1：唯一、严格递增与趋势有序是不是同一要求，业务真正需要哪些？**

唯一只要求不重复；严格递增要求后生成或后完成的 ID 大于先前 ID，还要明确“先后”的观察边界；趋势有序只是在时间上大致增长。

雪花 ID 不自动保证多节点调用完成顺序上的严格递增，号段并行消费也可能返回较小的旧号段 ID。

**追问 2：UUID、自增、号段和雪花方案在协调成本、数据库索引与生成容量上怎样比较？**

随机 UUID 通常不依赖在线协调，但较长键和随机写入会影响索引；自增依赖数据库服务；号段用一次事务领取一批 ID，允许本地快速发号；雪花主要本地计算，但需管理节点号、每时间单位序列容量与时钟。

不同 UUID 版本有不同时间排序特征，不能把所有 UUID 都概括为完全随机。

**追问 3：雪花方案遇到时钟回拨或节点标识冲突时，应怎样处理而不是继续无条件发号？**

节点号必须唯一且有安全的租用或分配规则，旧实例恢复不能复用正在使用的身份。

- 小幅回拨可等待时钟追平或采用经设计的逻辑时间；大幅回拨应拒绝发号、切换安全节点或使用其他保证唯一的方案。
- 序列用尽也要等待或扩展协议，不能回绕继续发重复 ID。

### 2. 基于 Redis `INCR` 生成全局 ID 时，怎样组织前缀、时间段与序列号？

可以将业务前缀、时间分桶和 Redis 原子递增序列组合为 ID，例如固定格式日期加定宽序号，但必须定义每桶最大容量、时区及计数器保留周期。

`INCR` 只保证一个有效实例上的原子加一，不自动保证异步复制切换、备份恢复或计数器重建后的全局不重复。

**追问 1：主从切换、计数器重建和位数溢出可能影响什么保证？**

主从切换可能丢失最后一段计数，恢复旧备份或错误删除计数器可能重新发出历史序号；位宽用尽后截断或取模也会重复。

需要持久化策略、不可复用的世代标识、数据库唯一约束或改用更强的发号方案。格式补零只改变展示，不解决容量与故障安全。

**追问 2：唯一、递增和趋势有序是否相同？**

唯一不代表有序；同一 Redis 计数器可按操作顺序增长，但跨时间桶、跨实例和故障恢复后的顺序需要额外定义。

- 多个请求获得序号后，响应可能逆序到达，所以调用完成顺序不一定严格递增。
- 业务若只需要可索引的趋势有序，不应额外承诺全局时序。

### 3. 号段模式如何降低 ID 生成对数据库的访问压力？

号段模式在数据库中原子增加某业务的最大已分配值，一次领取不重叠区间，例如 `[10001,11000]`，实例在内存中逐个发放。数据库访问从每个 ID 一次降低为每个号段一次。

实例崩溃时未用完的 ID 可以作废，通常允许空洞，但绝不能把已分配区间重新发给其他实例。

**追问 1：号段领取、耗尽与数据库暂时不可用时，应考虑哪些连续服务问题？**

领取号段应使用事务或条件更新保证互不重叠；接近耗尽时可以异步预取下一段并采用双缓冲。

- 数据库暂时不可用时只能继续使用已经可靠领取的剩余号段，用尽后应失败或等待，不能自行猜测新范围。
- 号段大小在数据库压力、可持续时长与空洞浪费之间取舍。

## 6. 一致性哈希

**本节问题**

- [1. 一致性哈希如何减少节点增减引起的数据迁移，虚拟节点又解决什么问题？](#1-一致性哈希如何减少节点增减引起的数据迁移虚拟节点又解决什么问题)

### 1. 一致性哈希如何减少节点增减引起的数据迁移，虚拟节点又解决什么问题？

普通取模使用 `hash(key) % N`，N 改变会影响大量映射。

- 一致性哈希把节点和 key 放在同一哈希环上，key 分配给顺时针遇到的节点；节点增减主要影响相邻区间。
- 虚拟节点让一个物理节点拥有多个分散区间，缓解节点少时的分布不均，也便于按权重分配容量。

**追问 1：直接取模分片在节点数变化时，为什么可能影响大量已有映射？**

例如从 3 个节点变为 4 个节点，同一个哈希值的余数通常发生变化，许多不属于新增节点的数据也会换位置。因此扩缩容可能造成大规模迁移和缓存失效。

固定逻辑槽再迁移槽，是另一种降低物理节点变化影响的方案，不必都叫一致性哈希。

**追问 2：一致性哈希与虚拟节点分别怎样减少迁移和缓解分布不均？**

加入节点只接管其负责的新区间，删除节点把相应区间转交后继节点；虚拟节点把迁移打散到多个物理节点，降低某个邻居独自承受全部压力。

它改善的是哈希空间分配，真实容量仍取决于 key 大小、访问频率和节点性能，需要监控及再平衡。

**追问 3：一个 key 特别热时，仅增加虚拟节点能否分散这个 key 的全部压力？**

不能。一个 key 通常仍映射到一个负责位置，增加虚拟节点不会自动把这个 key 的读写分散。

读热点可用副本、本地缓存或请求合并；写热点需要业务拆分、分片计数或专门的串行处理，并明确合并与一致性语义。

## 7. 幂等与重试

**本节问题**

- [1. 接口幂等应如何通过业务唯一键、去重记录或状态控制实现？](#1-接口幂等应如何通过业务唯一键去重记录或状态控制实现)
- [2. 同一幂等键被并发提交或携带不同请求参数时，服务应如何处理？](#2-同一幂等键被并发提交或携带不同请求参数时服务应如何处理)
- [3. 调用结果不确定时，如何设计有限重试与可重复执行的补偿？](#3-调用结果不确定时如何设计有限重试与可重复执行的补偿)
- [4. 多层服务都自动重试时，为什么一次故障可能放大为请求风暴？](#4-多层服务都自动重试时为什么一次故障可能放大为请求风暴)

### 1. 接口幂等应如何通过业务唯一键、去重记录或状态控制实现？

幂等是同一个业务操作执行多次，与执行一次具有相同的业务效果。

- 可以使用业务唯一键、持久化幂等记录或状态条件更新实现，但识别重复与实际写入必须处在同一可靠原子边界。
- 仅在 Redis 中先设置“已处理”，再独立写数据库，可能产生标记成功而业务失败的问题。

**追问 1：业务唯一键、幂等记录和状态条件分别怎样识别同一次业务操作？**

订单请求可使用请求 ID，领取优惠券可用用户与券批次唯一键，支付确认可依赖支付流水与订单状态。

- 幂等键要代表一次业务意图，不是每次网络尝试都重新生成。
- 状态条件例如只允许 `PENDING→PAID`，能阻止重复转换，但还需保存必要的原执行结果。

**追问 2：先判断再执行时，怎样避免并发请求都通过检查？**

利用数据库唯一约束、原子条件更新或可靠的事务串行化，不能只做普通查询后再插入。

- 并发请求中一个取得执行资格，其余读取已有结果或返回处理中。
- 锁可以降低竞争，但最终业务约束仍应由写入条件保证，不能把锁超时当成不可能发生。

**追问 3：去重记录与实际业务更新应怎样保持一致，避免成功标记和真实结果分离？**

在同一数据库事务内写入幂等记录、业务效果和返回结果，失败共同回滚。

- 跨外部系统时使用对方的幂等键及结果查询，再以状态机推进本地状态。
- 幂等记录的生命周期要覆盖业务可能的重试或重放窗口，不能随意短期过期后再次放行旧事件。

### 2. 同一幂等键被并发提交或携带不同请求参数时，服务应如何处理？

服务端应把幂等键与请求摘要绑定，并保存执行状态和可复用结果。

- 相同键、相同参数的重试返回原结果或明确的处理中状态；相同键、不同参数通常应拒绝，不能误用旧响应。
- 并发取得执行资格要靠唯一约束或条件状态转换，不能依赖两次普通读写。

**追问 1：幂等记录要区分哪些处理中、成功和失败状态，并保存什么结果？**

至少区分处理中、成功、确定失败以及必要的结果未知，保存请求摘要、业务 ID、结果、更新时间和执行世代。

处理中记录长期未更新时，需要查业务真实状态后决定接管，不能直接视为失败。响应丢失后成功记录可用于重放原结果。

**追问 2：相同 key 携带不同参数时，应如何拒绝或校验，而不错误复用原结果？**

对影响业务效果的参数做规范化摘要，并在同一幂等记录中校验。

- 不同参数复用键应返回明确冲突，防止原本支付 100 元的键被拿来请求 200 元。
- 摘要规范化要固定金额、字段缺失与顺序语义，不能把不等价请求错误归为相同。

**追问 3：记录过早过期或原事务回滚后，再次请求应该怎样推进？**

过早删除记录可能让旧请求再次产生效果，因此保留期限应覆盖客户端重试、MQ 回放和业务追溯要求，关键唯一约束可长期保留。

原事务确定回滚后可按规则重试；若提交结果未知，应先查询，不应直接清除标记重做。新执行者接管还要防止旧执行者迟到提交。

### 3. 调用结果不确定时，如何设计有限重试与可重复执行的补偿？

先分类错误：明确不可重试的参数或业务拒绝直接返回；暂时故障且操作幂等时，使用同一业务键、有限次数和退避重试；提交结果未知时，优先查结果或沿对方支持的幂等协议继续。

补偿是新的业务动作，应有独立状态、幂等键和可重试的执行记录。

**追问 1：如何避免重试产生额外副作用，并在补偿失败后继续恢复？**

重试不生成新的业务意图，也不绕过原唯一约束；每次尝试受同一个总时限和重试预算限制。

- 补偿前确认原操作及前置状态，避免退款与原扣款尚未确定时相互冲突。
- 补偿失败保留待处理记录并告警，恢复后继续同一补偿，而不是先标记“已回滚”再丢掉失败动作。

### 4. 多层服务都自动重试时，为什么一次故障可能放大为请求风暴？

多层独立重试会乘法放大请求量。例如三层每层最多尝试 3 次，一次入口请求最多可能触发底层 27 次调用。下游越慢，上游越重试，形成排队和超时反馈。

应选择明确的重试责任层，统一 deadline、次数和并发预算，并用退避、抖动及熔断避免同步冲击。

**追问 1：一条链路每层都重试时，实际请求次数怎样被放大？**

若每层包含首次调用的最大尝试次数为 `a1、a2、…`，最坏底层尝试次数可达到它们的乘积，而不是相加。

重试还会占用线程、连接和队列，原超时任务未取消时，新旧请求可能同时执行，实际资源压力更大。

**追问 2：总 deadline、重试层级、退避与抖动应该怎样共同配置？**

从入口分配总 deadline，子调用使用剩余预算，重试与等待都算在内。

- 选择少量有语义信息的层负责重试，采用有上限的指数退避和随机抖动，配合全局重试预算或令牌额度。
- 剩余时间不足、已熔断或容量不足时应停止，而不是机械完成全部次数。

**追问 3：哪些操作不能直接重试，怎样先确认业务结果并保护已经过载的下游？**

无幂等保障的扣款、发券或发送通知不能盲目重试；先按业务流水查询或使用幂等请求。参数错误、权限拒绝等通常重试无益。

已过载的下游应限流、减少重试和及时失败，必要时降级非核心能力；不能把“重试成功率”建立在压垮整个系统之上。

## 8. 分布式任务调度

**本节问题**

- [1. 分布式调度与单机定时任务有什么区别？](#1-分布式调度与单机定时任务有什么区别)
- [2. XXL-JOB 等分布式调度方案如何组织调度中心、执行器和任务分片？](#2-xxl-job-等分布式调度方案如何组织调度中心执行器和任务分片)
- [3. 任务被调度成功与任务业务执行成功为什么需要分别记录？](#3-任务被调度成功与任务业务执行成功为什么需要分别记录)

### 1. 分布式调度与单机定时任务有什么区别？

单机定时任务由一个进程按时间触发；分布式调度还需要决定哪个实例执行、怎样分片、失联后是否重派，以及怎样汇总结果。

多实例上的同一个定时注解通常会各自触发，并不自动保证全局只执行一次。需要调度协调与业务幂等共同保证正确性。

**追问 1：如何避免多个实例重复执行同一任务？**

可以通过集中调度、数据库条件领取、带租约的任务分片或领导者选举分配执行权。

- 但租约到期重派时旧任务可能仍在运行，因此业务效果仍需任务 ID、分片 ID、版本或唯一约束去重。
- 应区分“只安排一个执行者”和“故障重试后业务只生效一次”。

### 2. XXL-JOB 等分布式调度方案如何组织调度中心、执行器和任务分片？

调度中心保存任务配置、时间规则和调度记录，执行器注册可用地址并执行具体处理逻辑；路由策略决定本次触发目标，分片任务把分片序号和总数交给业务拆分数据。

框架解决触发与路由，但任务结果一致性、部分完成恢复和外部副作用幂等仍需业务实现。

**追问 1：调度中心、执行器和任务分片分别负责什么，怎样决定任务到哪台机器运行？**

中心负责触发、路由、失败重试和记录，执行器负责接收、运行及回调。

- 分片可以按主键哈希、范围或预先划分的工作单元处理，不能只启动 N 个执行器却让它们都扫同一全集。
- 节点数变化时还要明确分片任务的稳定标识和重分配方式。

**追问 2：执行器失联后重新派发时，旧实例可能仍在执行，怎样避免重复业务效果？**

失联不等于停止执行，重派与旧执行者可能重叠。以任务业务批次和记录 ID 建唯一约束，或通过条件状态领取及 fencing 版本限制旧实例继续提交。

对于已完成的一部分结果，接管任务从持久进度恢复，而不是每次都无条件从头制造副作用。

**追问 3：调度成功、执行开始与业务完成分别怎样记录并用于重试和告警？**

记录调度请求是否被接收、实际开始时间、分片进度、业务终态和回调结果。

- 调度接口成功只说明触发被接受，不等于业务完成；回调丢失也不一定说明业务失败。
- 重试前结合业务状态确认，监控长时间运行、迟到回调和连续失败，避免无限自动重跑。

### 3. 任务被调度成功与任务业务执行成功为什么需要分别记录？

调度成功表示任务被安排或被执行器接收，业务成功表示预期数据效果已经完成，两者之间可能发生进程故障、部分提交或回调丢失。

需要分别保存调度尝试记录和稳定的业务任务状态，重试只增加执行尝试，不改变同一业务任务的身份。

**追问 1：执行器失联后重新派发任务时，如何处理原任务仍在运行、部分结果已写入与迟到回调？**

每次执行可有递增的 attempt 或租约版本，更新进度与终态时检查当前有效执行权，拒绝旧回调覆盖新结果。业务明细按唯一键幂等提交并保存断点。

执行器失联后先查任务结果，必要时接管未完成部分；不能仅凭调度日志标记失败，就把已经完成的扣款或发券再次执行。

## 要点回顾

- 超时是观察结果，不是远端失败证明：有副作用的操作要保留业务标识、查询能力和结果未知状态。
- 协调状态与真实业务效果需要衔接：锁过期、任务重派或事务补偿，不会自动阻止旧执行者继续写入。
- 方案的代价应与保证一起说明：强协调、最终一致、号段和哈希分片都需要明确适用范围、故障行为与恢复成本。
