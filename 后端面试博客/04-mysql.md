### 1. `CHAR`、`VARCHAR` 与 TEXT 有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| CHAR | `CHAR` 适合长度较固定的短字符串 |
| VARCHAR | `VARCHAR` 保存实际长度及长度信息，适合长度变化较大的值 |
| TEXT | TEXT 系列适合较长文本，但行内、行外存储取决于 InnoDB 行格式和记录大小，不能简单认为 TEXT 永远在表外 |

选择时同时考虑查询字段、索引和行宽，而不是只比较最大容量。

**追问 1：固定长度、变长与大文本的保存方式怎样影响空间和读取？**

CHAR 有定长及填充语义，尾部空格的保存、返回和比较还受类型与排序规则影响；VARCHAR 按实际字节长度变长存储；大字段可能使用溢出页。

热点查询不读取正文时，窄字段表或拆分正文表可以减少不必要的页和传输开销。

**追问 2：字段声明长度、字符集以及是否需要索引，应怎样共同影响类型选择？**

声明长度通常以字符计，但字符集决定最坏字节数；索引长度限制按相应字节规则计算。

固定编码可考虑 CHAR 或二进制类型，姓名等选合理 VARCHAR，正文选 TEXT 并单独规划搜索方式。不要为“以后够用”把所有短字段都声明极大长度。

### 2. `VARCHAR` 声明长度、实际字符数与实际字节数有什么区别？

`VARCHAR(n)` 的 n 表示最多字符数，不是每行固定占用 n 字节。

- 实际字符数可用 CHAR_LENGTH 观察，字节数可用 LENGTH 观察；多字节字符集下两者可能不同。
- 实际存储还包含长度、NULL 位图、记录头、事务字段及可能的行外指针等开销。

**追问 1：为什么不能用声明长度直接估算每行占用？**

同样 VARCHAR(100)，保存两个 ASCII 字符与一百个多字节字符占用不同。

声明上限影响合法输入、最坏行宽以及部分执行内存估算，但不能直接当成平均行长。容量估算应采样真实数据并包含索引及页填充率。

**追问 2：长文本放在同一表中会怎样影响热点查询？**

长文本可能降低每页容纳记录数，增加溢出页、回表和网络成本；SELECT * 更容易把不需要的正文读出来。

可以只投影必要字段，或把低频大字段放到关联表/对象存储；拆分也增加关联和维护成本，需要按访问频率验证。

### 3. `utf8mb3`、`utf8mb4` 与排序规则分别影响什么？

| 比较项 | 特点与用途 |
|---|---|
| utf8mb3 | utf8mb3 最多用三个字节表示一个字符，不能覆盖全部 Unicode 码点 |
| utf8mb4 | utf8mb4 支持包括常见补充平面表情在内的完整 Unicode 范围 |
| 字符集 | 字符集解决可表示内容和编码 |
| 排序规则 | collation 解决比较、排序及大小写/重音等规则 |

两者都会影响索引比较语义。

**追问 1：存储表情、多语言文本以及按大小写比较字符串时，应怎样设计字符集和 collation？**

新业务通常选择 utf8mb4，并按需求明确大小写敏感性和重音规则，例如用户名唯一性是否区分大小写。二进制标识和用户可见自然语言不一定用同一规则。

连接、数据库、表和列的字符集要协调，迁移前检查已有唯一键是否因新比较规则产生冲突。

### 4. 金额字段使用 `DECIMAL`、整数最小货币单位或浮点类型，各有什么取舍？

金额需要可控的十进制精度，通常使用 DECIMAL 或整数最小货币单位，避免二进制浮点的表示与累计误差。

DECIMAL 直观支持小数位，整数便于精确加减但要明确币种和缩放因子；浮点更适合允许误差的测量或统计，不能直接套到记账。

**追问 1：`DECIMAL` 的精度与小数位如何根据业务约束设计？**

`DECIMAL(p,s)` 的 p 是总有效位数，s 是小数位数，整数部分最多 p-s 位。

- 根据单笔最大金额、累计上限、税率及汇率中间精度设计，并规定舍入时点和模式。
- 数据库字段精度与 Java BigDecimal 等应用类型应一致，不能先用 double 算完再存 DECIMAL。

### 5. `DATETIME` 与 `TIMESTAMP` 有什么区别？

DATETIME 表达日历日期时间值，不自动按会话时区做 UTC 转换；TIMESTAMP 通常按会话时区写入时转换、读取时再转换，适合表达一个时间点但可表示范围更小。

以 MySQL 8.4 为例，DATETIME 的日期范围约为 1000 年至 9999 年，TIMESTAMP 的秒级范围约为 1970 年至 2038 年，两者均可配置小数秒精度。

**追问 1：时区转换、可表示范围与存储语义分别有哪些差异？**

TIMESTAMP 的会话时区会改变显示值，DATETIME 保存的日历字段不因此自动变化；DATETIME 基础存储通常 5 字节，TIMESTAMP 为 4 字节，小数秒另占空间。

存储字节不是首要选型依据，必须首先保证时间语义和未来范围正确。

**追问 2：记录订单发生时刻与记录某地固定营业时间，应该怎样选择并约定应用时区？**

订单发生时刻可用 UTC 约定的 DATETIME，或在范围允许时用 TIMESTAMP，应用和连接时区必须统一。

某地每天 9 点营业是当地时间规则，应额外保存时区标识，不能只存一个 UTC 时刻。夏令时及跨地区展示由明确的时区规则处理。

### 6. `NULL`、空字符串和 0 在查询中有什么区别？

NULL 表示缺失或未知，空字符串是长度为零的字符串，0 是确定数值，三者不应混用。

- SQL 使用三值逻辑，表达式可能为 TRUE、FALSE 或 UNKNOWN；WHERE 只保留 TRUE。
- 字段设计应准确表达业务含义，而不是为了少写判空把所有缺失值都改成 0。

**追问 1：为什么 `NULL` 不能按普通值直接用 = 判断，三值逻辑怎样影响过滤条件？**

`x = NULL` 的结果不是普通相等判断，应使用 `IS NULL`；MySQL 的 `<=>` 提供 NULL 安全比较。

`x <> 1` 也不会选出 NULL 行，需要时应显式加上 `OR x IS NULL`。NOT UNKNOWN 仍然是 UNKNOWN。

**追问 2：`COUNT`、SUM、比较运算和唯一约束中，`NULL` 可能带来什么不同结果？**

COUNT(*) 统计行，COUNT(col) 忽略 NULL；SUM 忽略 NULL，无可聚合值时通常返回 NULL 而非 0；普通比较遇到 NULL 产生 UNKNOWN。

MySQL 唯一索引允许多个 NULL，因此可空唯一字段不一定实现业务想要的“缺失值也只能一次”。

**追问 3：“未知”“未填写”与业务数值零应如何区分，哪些字段适合设置 `NOT NULL`？**

必需身份、状态和金额等可设 NOT NULL，并提供有业务意义的约束；确实可选且未知的值保留 NULL。

不要用 0 表示“未填年龄”又把真实 0 岁混入，也不要无条件把 NULL 聚合转换为 0 而掩盖无数据与数值为零的区别。

### 7. 数据库三大范式分别解决什么问题？

| 比较项 | 特点与用途 |
|---|---|
| 第一范式 | 第一范式要求每个字段值符合关系模型中的原子表达 |
| 第二范式 | 第二范式要求非主属性完全依赖候选键，避免只依赖组合键的一部分 |
| 第三范式 | 第三范式进一步避免非主属性对候选键的传递依赖 |

范式用于减少冗余和更新异常，不是要求所有查询必须通过尽可能多张表关联。

**追问 1：第一、第二、第三范式分别约束哪些依赖关系？违反后可能出现什么更新问题？**

例如订单明细以订单号和商品号为键，却把只依赖商品号的商品分类反复存储，就容易更新不一致；用户表重复保存由地区编码决定的地区名称，也有传递依赖。

拆出独立实体后，新增、修改和删除可以围绕唯一事实维护。

**追问 2：高频读取场景引入冗余字段时，怎样维护数据一致性，并判断收益是否超过维护成本？**

高频展示可冗余商品名或统计值，但必须区分历史快照与需同步的当前值。

- 前者有意保持下单时内容，后者需要事务、事件或定期校验维护。
- 比较读性能收益、写放大和一致性容忍度，不把反范式当成取消全部约束。

### 8. 物理外键与由应用维护的关联关系各有什么优缺点？

物理外键由数据库在写入时检查引用完整性，能覆盖不同应用写入路径，但增加约束检查、锁及迁移成本，跨库场景能力有限。

应用维护关联更灵活，却必须保证所有写入路径都遵守规则，并处理并发和补偿。不能把“不用外键”解释成“不需要引用完整性”。

**追问 1：删除父记录、并发写入以及分库分表时，如何保证引用完整性？**

同库关键关联可以在事务内校验和写入，并利用外键或必要的锁防止校验后父记录被删除；级联删除应评估规模和业务语义。

跨分片关联可使用状态机、逻辑删除、事件同步和孤儿数据巡检，避免只做一次无锁存在性查询。

### 9. 自增 ID 与 UUID 作为 InnoDB 主键时，会怎样影响数据组织、插入和索引成本？

InnoDB 聚簇索引按主键组织数据，自增整数短且大体顺序插入，通常有较好的页局部性；随机 UUID 较长且分散写入，可能增加页分裂与缓存压力。UUID 的优势是跨节点独立生成。

不能把所有 UUID 都当成随机布局，也不能只凭主键类型断言实际性能。

**追问 1：主键顺序、长度与更新频率怎样影响聚簇索引插入和页分裂？**

顺序键通常更多写到右侧页，随机键可能修改大量页并造成分裂，分裂还涉及迁移记录和更新父节点。

高并发顺序写也可能有末端页热点；频繁更新主键意味着移动聚簇记录并维护相关索引，应尽量保持稳定。

**追问 2：二级索引为什么也会受到主键长度影响？**

二级索引叶子保存主键作为行定位信息，因此主键越长，每个二级索引越宽，缓存命中、树高和维护成本都可能受影响。

字符串 UUID 与 BINARY(16)的成本也不同，应按实际编码比较。

**追问 3：业务需要跨库唯一标识时，怎样比较自增键、UUID 与其他 ID 方案，而不是只比较生成速度？**

可比较数据库自增、号段、雪花及有序 UUID 等方案的唯一性、时间依赖、排序、长度和可用性。

业务外部标识与内部聚簇主键也可以分开，但新增唯一索引会有成本。全局唯一不等于严格连续或绝对时间有序。

### 10. 表没有显式主键时，InnoDB 如何选择聚簇索引？

InnoDB 优先使用显式主键作为聚簇索引；没有主键时，选择合适的、所有键列均为 NOT NULL 的唯一索引；仍没有时创建隐藏的行 ID 聚簇索引。

实际表设计最好显式给出稳定主键，避免把内部隐藏标识当成可供业务使用的 ID。

**追问 1：主键过长或频繁更新主键，会怎样影响二级索引和写入成本？**

主键长会被带入二级索引，放大空间和访问成本；更新主键可能改变记录在聚簇树中的位置，并修改二级索引定位信息。

应选择稳定、尽量紧凑且满足业务访问的键，而不是把频繁变动的业务属性直接作为主键。

### 11. `AUTO_INCREMENT` 为什么可能出现不连续的 ID？达到类型上限后又会怎样？

AUTO_INCREMENT 保证按其分配规则生成值，不保证已提交记录连续编号。

- 事务回滚、预分配未用完、失败插入和并发执行都可能留下空洞。
- 达到字段可表示上限后，新自动编号无法继续合法生成，插入会失败，必须在接近上限前扩展类型或迁移 ID 方案。

**追问 1：事务回滚、批量申请和并发插入为什么可能留下编号间隙？**

编号申请与最终业务提交不是同一个可回退计数过程，回滚不会把已申请的号码安全地发给任意后续事务。

批量预留和并发交错进一步增加不连续，因此不能通过补齐空号判断是否丢单。

**追问 2：达到字段类型上限时，怎样判断失败风险并规划扩容？**

监控当前自增值、增长速率、字段有符号性和业务高峰，估算剩余时间；改 BIGINT 等应评估 DDL、应用类型和上下游序列化兼容。

不要等插入报错后再临时重置计数器，重复 ID 可能破坏业务。

**追问 3：为什么不宜用最大 ID 推算有效记录数，或者要求普通自增主键严格连续？**

删除、回滚、批次空洞都会使最大 ID 不同于行数。

严格连续的财务凭证号需要专门串行化分配或业务登记机制，且考虑作废与审计，不能要求普通主键同时保持高并发、无空洞和事务回滚复用。

### 12. DELETE、TRUNCATE 与 DROP 在删除范围、表结构和事务行为上有什么区别？

DELETE 是按条件删除行的 DML，InnoDB 事务内可回滚；TRUNCATE 清空整张表并重置相应自增状态，属于 DDL，通常通过重建等方式实现；DROP 删除表定义和数据。

以 MySQL 8.4 为例，后两者不能按普通用户事务中的 DELETE 方式回滚，且涉及隐式提交和元数据锁。

**追问 1：以 MySQL 8.4 的 InnoDB 为例，说明清空业务表前需要检查哪些风险。**

确认目标库表、外键、权限、备份与恢复点、复制影响和当前长事务。

- TRUNCATE 不逐行触发 DELETE 触发器；DELETE 全表可能产生大量 undo 和锁。
- 先保护数据再选择方式，不把“执行更快”作为唯一标准，也不在业务事务中夹入会隐式提交的 DDL。

### 13. 逻辑删除与物理删除在查询、唯一约束和数据恢复方面有什么区别？

逻辑删除保留行并用状态标记不可见，便于审计和特定恢复；物理删除解除数据记录，查询规则更直接，但恢复通常依赖备份或历史记录。

逻辑删除把复杂度转移到所有查询、唯一约束、容量和最终清理流程，不是无成本撤销。

**追问 1：所有查询如何保证过滤掉已删除记录，关联查询是否也需要相同规则？**

列表、详情、聚合、JOIN 和子查询都应遵守可见性规则，手写 SQL、后台任务和缓存也不能漏掉。

框架自动加过滤只覆盖其支持路径，需测试关联查询和绕过框架的写入。

**追问 2：唯一键曾被已删除数据占用时，怎样满足重新创建的业务要求？**

不能简单把 `(business_key, deleted)` 当成万能方案，因为多次删除可能都占用 deleted=1。

可按业务用唯一删除标识、归档表，或生成列配合可空唯一索引只约束活跃记录。恢复旧记录时也要重新检查现有活跃数据冲突。

**追问 3：长期保留逻辑删除数据，会怎样影响索引、容量与恢复流程？**

已删除行仍占索引和存储，过滤字段选择性可能改变计划；恢复需要验证关联对象、状态和权限，不只是把标志改回 0。

制定保留期限、归档及物理清理策略，并满足数据删除义务和备份政策。

### 14. 视图、普通查询与物化结果表有什么区别？

普通查询直接执行 SQL；视图保存查询定义，对外提供可复用的逻辑关系，通常并不预先保存全部查询结果；物化结果表保存计算结果，需要另外维护刷新。

MySQL 普通视图不应当成自动维护的原生物化视图使用。

**追问 1：报表查询需要复用逻辑时，应怎样权衡实时性、查询开销和数据维护成本？**

实时性高且查询代价可接受时用普通查询或视图；复杂报表可预聚合到结果表，换取读性能，但需规定刷新延迟、增量处理、失败重试与全量校验。视图简化权限或 SQL 复用，不保证查询一定更快。

### 15. 一条 `SELECT` 从进入 MySQL 到返回结果，会经过哪些执行阶段？

连接建立和认证后，服务器解析 SQL 并检查语义，优化器选择访问路径与连接顺序，执行器按计划调用存储引擎读取数据，完成过滤、聚合、排序等操作并返回结果。

MySQL 8.4 没有旧版的查询缓存阶段，不能把历史查询缓存流程直接套到当前版本。

**追问 1：连接处理、解析、优化与执行分别完成什么工作？**

连接处理管理会话和权限；解析确认语法及对象；优化估算不同计划成本；执行器组织算子和结果。

连接复用减少握手，不会跳过每次查询的全部执行工作。

**追问 2：优化器根据什么信息选择访问路径，存储引擎负责哪些实际读取？**

优化器参考索引、统计信息、条件选择性和成本模型；InnoDB 负责索引页访问、Buffer Pool、MVCC 及必要锁。

SQL 书写顺序不等于实际访问顺序，最终需要通过 EXPLAIN 和执行指标确认。

**追问 3：命中 Buffer Pool 与需要磁盘 I/O 时，完整请求中哪些开销会变化？**

Buffer Pool 命中可避免对应数据页的物理读取，但 CPU 过滤、回表查页、锁等待和网络传输仍存在。

未命中会增加磁盘 I/O 及等待；不能看到命中率高就排除慢 SQL，更不能把所有延迟都归咎于磁盘。

### 16. 数据库连接池的最大连接数、空闲连接数、获取超时与连接最大存活时间应如何配置？

连接池配置应以数据库可承受的并发工作量和请求预算为基础，而非直接设成 max_connections。

最大连接数限制在途 SQL 并发，空闲设置减少频繁建连，获取超时把排队控制在接口预算内，最大存活时间帮助更新旧连接并适配基础设施回收策略。应结合实例总数规划。

**追问 1：最大连接数、空闲连接数、获取超时和最大存活时间分别约束什么？**

最大连接数控制池上限；空闲数控制保留连接，具体最小或最大空闲参数因池而异；获取超时限制等连接时间；最大存活时间限制连接寿命，通常在归还或合适时机回收，不能依赖它强制终止任意业务事务。

**追问 2：应用从 5 个实例扩为 20 个实例，而单实例池大小不变，数据库连接需求会怎样变化？**

理论连接上限会扩大为原来的 4 倍，还要计入后台任务、管理连接和其他应用。

扩应用实例前应同步分配数据库连接预算，避免应用扩容反而让数据库过载。

**追问 3：连接增加但吞吐没有提高时，怎样区分数据库容量、慢事务和连接等待，而不是继续扩大池子？**

看池等待时间、活跃连接、SQL 耗时、锁等待和数据库 CPU/I/O。

- 大量活跃连接都卡在同一锁上，扩大池只增加等待者；池等待高但数据库仍有余量才可能适度扩池。
- 缩短事务、修正泄漏与慢 SQL 通常比无限加连接有效。

### 1. InnoDB 如何利用数据页和 B+ 树组织表数据？

InnoDB 以页作为主要管理和 I/O 单位，聚簇索引的 B+树叶子保存整行记录，二级索引叶子保存索引键和主键。

- 查询通过树定位叶页，范围扫描利用叶页间顺序关系。
- 页缓存、日志和锁机制共同支撑事务访问，不能只画一棵树就解释完整存储引擎。

**追问 1：与 MyISAM 相比，索引组织、事务和锁机制有哪些关键差异？**

MyISAM 的数据文件和索引文件分离，索引指向数据位置，通常使用表级锁，不支持 InnoDB 式事务和崩溃恢复；InnoDB 使用聚簇组织、行级及间隙等锁并支持 MVCC。

二者的常见索引都可使用 B+树，不应误说 MyISAM 必然是 B 树。

### 2. InnoDB 的记录、数据页、区和表空间分别是什么层次？

记录保存在数据页中，页构成 B+树节点；页再由区、段及表空间等层次组织。

- 常见 InnoDB 默认页大小为 16KiB，但可以在初始化时按支持范围配置，区大小也不能脱离页大小永久说死。
- 表空间是页的逻辑管理容器，不等于每表必然只有一种文件布局。

**追问 1：一条记录所在页与 B+ 树节点之间是什么关系，区和表空间如何组织这些页？**

叶页保存记录，非叶页保存用于导航的键和子页引用；页是树节点与物理管理之间的连接点。

多个页按区等单位分配，索引段及表空间负责更大范围管理，避免每条记录都单独进行操作系统分配。

**追问 2：页内查找与跨页范围扫描分别怎样进行？**

页内通过页目录等结构缩小范围，再在记录间查找；范围扫描先定位起点，随后沿有序叶页遍历。

叶页有序并不保证在磁盘上绝对连续，相邻逻辑记录仍可能需要不同物理 I/O。

**追问 3：随机主键插入导致页分裂时，为什么不能只计算增加一条记录的大小？**

页满插入可能拆分页、移动现有记录、分配新页并修改父节点，伴随日志和缓存更新。

随机写还可能访问更多冷页，所以新增一行带来的写放大远大于该行业务字段字节数。

### 3. 一行数据超过单个数据页可容纳范围时，InnoDB 如何保存长字段？

InnoDB 并不要求所有长字段完整放在同一叶页内。

- 根据行格式、页大小和行宽，可把部分变长字段存入溢出页，页内保留必要信息或指针。
- 例如 DYNAMIC 行格式在满足条件时可把较长字段主要存到页外。
- 不能把“超过 16KiB”当成唯一触发条件，页内还有其他记录和开销。

**追问 1：行格式、页内数据与溢出页之间是什么关系？**

COMPACT 与 DYNAMIC 等行格式的行内前缀及页外处理不同，记录的可用页内上限也小于整页。

TEXT、BLOB 或较长 VARCHAR 是否行外取决于实际记录，不能只看字段类型名称。

**追问 2：读取 TEXT 等字段为什么可能产生额外 I/O？**

查询需要长字段时，定位聚簇记录后可能还需读取溢出页，再传输较大数据；只查询索引内短字段则可能避免这些访问。

选择性投影、正文分表或对象存储可减少热点接口成本，但要维护关联及一致性。

### 4. Buffer Pool 如何参与数据页读取、修改与脏页刷盘？

Buffer Pool 缓存数据页和索引页，读请求优先查缓存，未命中再读取存储；更新在缓存页上修改，使页变脏，随后由后台或压力驱动刷回数据文件。

持久化不是靠每次更新立刻写整页，而是由 WAL 和日志刷盘与脏页管理配合。

**追问 1：查询怎样定位缓存页，缓存未命中时后续发生什么？**

根据页标识查找缓存页，命中后进行锁存、可见性等处理；未命中需取得可用缓存页并发起读取。

若缺少可回收干净页，可能需要等待脏页写回，单纯扩大查询并发可能加重等待。

**追问 2：更新页后，为什么不必立即把整个数据页写回表文件？**

先确保相关 redo 满足写前日志约束，崩溃时可重放尚未进入数据文件的修改。

把多次对同一页的修改合并到一次刷页，能够减少随机写；但日志进入内存缓冲不等于已经获得断电持久性。

**追问 3：脏页刷盘跟不上更新速度时，会怎样影响前台请求和可用缓存？**

刷盘滞后会推迟 checkpoint、占用缓存和 redo 空间，引发前台等待或延迟抖动。

应观察脏页比例、刷盘速率、checkpoint 进度、存储延迟与写入峰值，调整 I/O 能力及业务批量规模，而不是只改一个 Buffer Pool 参数。

### 5. Buffer Pool 的 LRU 管理如何应对全表扫描造成的缓存污染？

InnoDB 使用带新老区域的改进 LRU 管理，新读入的页通常先进入较冷区域，不会立即全部提升为热点；再次访问和时间条件等影响提升。

- 这样一次性扫描大量页时，更不容易把长期热点全部挤出。
- 它是针对访问模式的近似策略，不保证任何扫描都无污染。

**追问 1：热点读取和一次性全表扫描的访问特征有什么不同？**

热点页被持续重复访问，一次性全表扫描则把大量短期只访问一次的页带入缓存。

两者若都直接放到最热端，扫描结束后真正高价值页可能已经被淘汰。

**追问 2：为什么简单地把每个新读入页都视为热点，可能挤出真正有价值的数据？**

新页只证明“这次需要”，不证明未来高复用。把新页暂放冷区、对短期访问提升做限制，给真实热点更长保留机会。

相关比例和时间参数应结合负载调整，不能用“LRU 只看最后一次访问”解释全部行为。

**追问 3：怎样区分缓存污染、预读与脏页管理问题，并观察命中率和磁盘 I/O 变化？**

比较扫描前后 Buffer Pool 读请求、物理读、热点接口延迟和缓存页分布；预读是提前加载预测会用的页，脏页管理是把修改安全写回，与淘汰冷热不同。

命中率下降伴随磁盘读取上升才更支持污染假设，不能只看一个瞬时指标。

### 6. Buffer Pool、Log Buffer 与操作系统页缓存分别缓存什么？

Buffer Pool 缓存 InnoDB 的数据和索引页；Log Buffer 暂存 redo 记录，减少频繁写日志文件的开销；操作系统页缓存管理文件 I/O 缓存，是否经过它还受直接 I/O 等配置影响。三者处于不同层次，不是同一块内存的三个名字。

**追问 1：增大 Log Buffer 与增大数据页缓存，对长事务和查询命中率的影响为什么不同？**

增大 Log Buffer 可能减少大量生成 redo 的事务在提交前被迫写日志的频率，但不会直接提高数据页查询命中率；增大 Buffer Pool 能保留更多数据页，却不替代日志持久化策略。

长事务的问题还包括 undo 与锁，不能只靠增大日志缓冲解决。

### 7. Change Buffer 缓存的是什么修改，适合怎样的二级索引写入？

Change Buffer 缓存符合条件且尚未进入 Buffer Pool 的二级索引页修改，等相关页读入或后台合并时再应用，从而减少随机读取。

- 它不是整条业务更新的缓存，也不替代 redo log。
- MySQL 8.4 的 `innodb_change_buffering` 默认值是 `none`，即默认不缓冲新的此类修改；讨论收益时应明确是否显式启用。
- 修改该配置不等于丢弃已经存在的缓冲条目，这些条目仍需合并。

**追问 1：哪些二级索引修改适合先缓冲，缓冲结果什么时候需要合并到真实页？**

适用于受支持的普通二级索引修改且目标页未缓存等条件，随后在访问该页或后台合并时应用。主键页、特定索引类型及配置不满足时不能使用。合并成本只是被推迟和集中，不是消失。

**追问 2：唯一性校验为何限制唯一索引的适用范围？**

唯一索引更新需要检查是否违反唯一性，往往必须读取相关页，便失去“暂不访问目标页”的主要收益。普通索引无需同样的唯一性检查，因此更适合缓冲。

不能为了使用 Change Buffer 去删除业务必需的唯一约束。

**追问 3：随机写入多与读后立即访问的场景，收益可能怎样不同？回答时说明版本及是否启用的配置。**

大量随机写、目标页分散且不会马上读取时，可能有较大收益；写后立即读会很快触发合并，节省有限，还增加管理开销。

固定版本与配置后比较随机 I/O、合并积压和延迟，不把它列为所有写多业务的必选优化。

### 8. Doublewrite Buffer 解决什么页写入故障？有 redo log 后为什么仍需要关注页的完整性？

Doublewrite 主要处理数据页写入过程中只写了一部分的“撕裂页”风险。

- 相关页在写到最终位置前，先经过可用于恢复完整页的双写路径；崩溃后可用完整副本恢复，再应用 redo。
- redo 描述页修改，但若基页本身损坏，仅靠增量记录未必能可靠重建。

**追问 1：部分页写入与事务尚未提交，是哪两类不同的故障？**

部分页写入是物理页完整性问题，可能包含同一页新旧片段；未提交事务是逻辑事务状态问题，可通过 undo 回滚。

它们可同时发生，但需要不同恢复机制，不能说“双写就是给事务备份一份”。

**追问 2：`redo` 可以描述修改，为什么还需要有可恢复的完整页作为基础？**

redo 通常以预期页状态为基础重放修改，不一定包含每页完整镜像。双写提供可靠完整页基础，redo 恢复其后修改。

支持原子页写等特定存储环境可有不同配置，但关闭双写前必须确认实际硬件和文件系统保证。

### 9. 删除大量记录后，为什么表文件可能不会立即缩小？

删除先改变记录和页中的使用状态，空间可在 InnoDB 内部复用，不等于操作系统文件立刻缩小。

历史版本还可能需要保留到没有 Read View 引用，之后 purge 才能清理。表大小、有效数据量和文件占用是三个不同指标。

**追问 1：页内空洞、可复用空间和操作系统看到的文件大小应如何区分？**

页内空洞可以被后续写入利用，空闲页也可能留在表空间中；操作系统只看到文件已分配空间，不知道其中哪些记录已删除。

不能仅用 df 判断 DELETE 是否成功，应结合行数、索引和表空间统计。

**追问 2：重建表需要评估什么影响？**

重建表或合适的 OPTIMIZE 操作可能回收空间，但需额外磁盘、I/O、redo/binlog 及元数据锁，还可能增加复制延迟。

先确认确有收益、支持的在线方式和回滚方案；不能对高峰大表直接执行再等待结果。

### 1. 主键索引、唯一索引与普通索引在约束和查询用途上有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| 主键索引 | 主键索引唯一且不允许 NULL，一张表只有一个主键 |
| 唯一索引 | 唯一索引约束键值唯一，但 MySQL 对 NULL 有特殊处理 |
| 普通索引 | 普通索引主要提供访问路径，不要求唯一 |

InnoDB 中主键通常决定聚簇组织，其他索引通常是二级索引。

约束正确性与查询效率应分别设计，再利用同一索引兼顾二者。

**追问 1：约束数据唯一性与提高查找速度，是哪两个不同目标？**

索引能加速定位，但普通索引不会阻止重复；唯一约束能在并发写入时保证数据库内的唯一事实，却不一定覆盖最合适的查询排序。

不能为了加速而删除业务约束，也不能认为有唯一键就无需其他查询索引。

**追问 2：“同一用户只能领取一次同一张券”应怎样建立唯一键？**

对领取表的 `(user_id, coupon_id)` 建立联合唯一键，并将两列设为 NOT NULL；如果券允许按活动轮次重复领取，应把轮次纳入业务唯一键。

索引字段必须对应真正的业务去重范围，而不是使用每次都变化的请求时间。

**追问 3：仅由应用先查询再插入，两个并发请求可能怎样绕过判断？数据库约束失败后业务应如何响应？**

两个请求都先查到不存在，随后都尝试插入；唯一约束让最多一条成功。

应用应识别指定唯一约束冲突，查询已存在结果并返回“已领取”或幂等结果，不应把所有数据库错误都当作重复成功。

### 2. 为什么 InnoDB 选择 B+ 树作为索引结构，而不是 B 树或其他结构？

B+树把大量键和子页引用集中在非叶页，叶页按序保存数据，通常具有高扇出和较低树高，适合页式存储的点查与范围扫描。

- 二叉树高度更大，哈希结构不擅长范围与排序；B 树可在内部节点存数据，而 B+树更便于统一叶层扫描。
- 选择来自访问模式，不是某种结构在所有环境都最快。

**追问 1：数据库索引需要怎样兼顾点查、范围查询、页读取与更新？**

点查需要快速定位，范围查询需要顺序遍历，更新需要控制重组成本。

B+树可在有限高度内定位叶页，再沿叶页读取范围；索引更新仍需维护顺序、分裂合并和日志，因此索引并非无代价。

**追问 2：为什么较大的扇出和较低的树高能够改变磁盘访问次数？**

一次页读取可获得很多导航键，树每下一层能排除大量候选范围；根和中间页还常驻缓存，所以树高不等于每次一定发生同样次数磁盘 I/O。应区分逻辑页访问与实际物理读取。

**追问 3：索引长度与单条记录大小变化后，怎样估算树高与空间，而不是固定背一个可存储条数？**

非叶扇出约由可用页空间除以键长、子页引用及记录开销估算；叶页容量约由可用页空间除以叶记录长度估算，再考虑填充率。

聚簇叶保存整行，二级叶保存索引键和主键，因此两类树容量不同。

**追问 4：在简化模型中，设每个非叶节点最多指向 1000 个子页、每个叶页保存 100 条记录。根到叶共 3 层时最多容纳多少条记录？现实中的页头、填充率和记录长度为什么会改变这个估算？**

简化模型中有 `1000×1000` 个叶页，每页 100 条，总计 `1000²×100=100000000` 条。

现实中页头、目录、变长字段、主键长度及未填满页面都会降低或改变容量，所以“三层必然两千万”不是固定定律。

### 3. 聚簇索引与二级索引的访问路径有什么区别，回表开销如何产生？

聚簇索引叶页直接保存整行；二级索引先定位索引记录，若所需字段不全，则用其中主键再查聚簇索引，这一步叫回表。

覆盖索引意味着查询所需字段能够由所选索引提供，通常能减少回表；还应考虑 MVCC 可见性判断等特殊路径。

**追问 1：二级索引叶子记录包含什么，为什么有些查询还需要访问聚簇索引？**

InnoDB 二级索引叶子包含索引列和主键。查询只取这些字段时通常可直接返回；需要 amount 等索引外字段，就要沿主键访问整行。大量离散主键回表可能增加随机页访问。

**追问 2：哪些查询字段组合可以由索引直接提供，覆盖索引减少的是哪一段访问？**

例如索引 `(user_id, status)`，查询 user_id、status 及主键 id 通常可以覆盖；查询额外正文则不行。

覆盖主要省去二级索引到聚簇索引的访问，不代表不用读取任何索引页或执行过滤。

**追问 3：为了覆盖查询不断增加索引列，会怎样影响写入、存储和维护成本？**

覆盖列过多会使索引变宽、降低页容量并放大更新成本，字段频繁变化还会增加写入维护。

优先覆盖高频关键查询的少量字段，对低频大字段不宜为了少一次回表无限扩宽索引。

### 4. 联合索引的字段顺序如何影响等值查询、范围查询和排序？

联合索引按字段从左到右的字典序排列。左侧字段确定后，右侧字段才在该子范围内有序，因此等值前缀、范围边界和 ORDER BY 共同决定它能承担定位、过滤还是排序。

SQL 中 AND 条件的书写顺序不是索引列顺序，优化器可以重排等价条件。

**追问 1：从联合键的排序方式解释，为什么字段顺序会影响定位能力？**

索引 `(a,b,c)` 先按 a，再在同 a 中按 b，再按 c。

a 未限定时，所有 b 相同的记录不一定连续；a、b 都等值时，c 形成连续有序范围。这个排序关系是最左前缀规则的依据。

**追问 2：等值、范围和排序条件组合变化后，怎样区分用于定位、过滤和排序的索引部分？**

等值前缀后的范围列可缩小扫描边界，后续列仍可能参与索引内过滤，但未必继续精确定位或满足全局排序。

不能用“范围后全部失效”概括；还要区分开闭范围、多区间及优化器使用的具体方式。

**追问 3：没有首列条件时，为什么还应看执行计划，而不是简单认定任何索引访问都不存在？**

可能进行覆盖索引全扫描，或在适用条件下采用跳跃扫描等访问方式。

- 它们与使用首列连续定位的成本不同，所以“没首列”不等于“完全不读索引”。
- 最终看 type、使用键部分、扫描量和是否额外排序。

### 5. 给定以下订单表与联合索引，逐条分析查询可能怎样使用索引。

采用 MySQL 8.4、InnoDB。表结构如下：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    status INT NOT NULL,
    created_at DATETIME NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    KEY idx_tenant_status_time (tenant_id, status, created_at)
);
```

需要分析的查询：

```sql
SELECT id FROM orders WHERE status = 1;

SELECT id FROM orders
WHERE tenant_id = 10 AND status = 1
ORDER BY created_at DESC LIMIT 20;

SELECT id, amount FROM orders
WHERE tenant_id = 10 AND status = 1
  AND created_at >= '2026-01-01 00:00:00';
```

题目未给出行数与数据分布，应区分索引的适用能力和优化器最终选用的访问路径。

第一条缺少 tenant_id，不能直接利用常规左前缀按 status 连续定位，但可因只取 id 而采用覆盖索引扫描，特定条件下也可能有其他优化。

- 第二条固定 tenant_id 与 status，可在对应范围按 created_at 逆向扫描并取 20 条，id 已在二级索引中。
- 第三条三列构成等值加时间范围定位，但 amount 不在该索引，需要回表。

**追问 1：分别判断用于定位、索引内过滤和排序的字段，并指出哪些查询需要取得索引外字段。**

第一条 status 可在索引记录内过滤，id 可直接提供；第二条前两列定位、第三列排序，通常不需额外 filesort；第三条前两列等值、第三列范围，amount 需访问聚簇记录。

这里描述的是可用能力，不代表缺少数据规模时已确定最终计划。

**追问 2：把 status 从等值改为范围条件，后续 `created_at` 的作用可能怎样变化？**

status 变成范围后，created_at 仅在每个 status 内部有序，不再天然构成所有结果的全局时间顺序。

- 它可能继续用于过滤或部分范围边界，但 ORDER BY created_at 往往需要额外处理。
- 应看具体谓词及执行计划，不能一概说时间列完全无用。

**追问 3：为什么还不能仅凭这些语句断言最终计划？应查看哪些估算与实际执行信息？**

优化器会比较行数、选择性、LIMIT 收益、回表与排序成本，表很小或返回比例很高时可能选全表扫描。

需要 SHOW CREATE TABLE、索引统计、参数分布、EXPLAIN 及受控 EXPLAIN ANALYZE，比较估算和实际扫描、loops、耗时，而不仅是 key 字段。

### 6. 两条常用查询的过滤列顺序不同，应该创建一个联合索引还是多个索引？

不按 WHERE 里字段出现顺序机械建索引，而是先归纳查询的等值前缀、范围、排序和返回列。

- 一个合理联合索引可能覆盖多条等价查询；若访问前缀根本不同，可能需要不同索引。
- 要比较整体工作负载的读收益与写入维护成本，避免每条 SQL 都新增一条索引。

**追问 1：如何结合等值条件、范围条件、排序、区分度与写入成本，而不是只按 SQL 中字段出现顺序设计？**

例如 a、b 都等值的两条查询只是书写顺序不同，通常无需两套索引；一条主要按 a 范围查、一条只按 b 查，需求就不同。

用真实参数、调用频率和扫描量验证，对高频排序或覆盖需求给予权重，同时检查冗余前缀索引是否仍承担唯一约束等职责。

### 7. 索引下推把哪些条件判断移到了更接近数据的位置？

索引条件下推把可仅依据索引列判断的部分条件交给存储引擎，在回表取得整行前先过滤不满足的索引记录。

它减少无用回表及上层传递，不是把任意 WHERE 逻辑都执行在索引里，也不等于覆盖索引。

**追问 1：哪些条件可以在读取二级索引记录后、回表之前判断？**

例如联合索引定位 a 的范围后，b 上的条件若能由索引值判断，可先过滤，再只对通过的记录读取索引外字段。

条件是否支持下推受索引和表达式等限制，不能把 SQL 函数全部视为可下推。

**追问 2：减少回表次数与完全避免回表有什么区别？**

ICP 让部分候选不再回表，但最终返回仍需索引外字段时，合格记录仍要回表；覆盖查询则通常连合格记录的字段都由索引提供。两者优化不同阶段，可以存在联系但不能混称。

**追问 3：怎样从执行计划和访问行数验证索引下推的收益，而不是只看是否存在索引？**

观察 `Using index condition`、扫描与返回行数、回表相关成本和实际耗时，对比关闭/开启或等价改写的受控测试。

仅出现索引名说明选了访问路径，不能说明过滤有效，也不能排除大量候选。

### 8. 函数计算、隐式类型转换、`LIKE` 和 `OR` 等写法，会怎样影响索引使用？

索引利用依赖表达式能否转成有序键范围。对列做函数或类型转换可能破坏普通索引定位，前缀 LIKE 通常比前导通配符更容易形成范围；OR 可能使用索引合并，也可能全表扫描。

最终应分析具体表达式与成本，避免背“某关键字一定失效”。

**追问 1：比较对索引列做函数处理，与对右侧常量做计算，对定位条件的影响是否相同？**

`DATE(created_at)=...` 对列变换，普通时间索引可能无法直接定位；`created_at >= 常量表达式` 若右侧可先算成常量，通常仍能形成范围。

可把按日查询改为半开时间区间，或使用合适的函数索引/生成列索引，需固定版本与表达式。

**追问 2：字符串和数值比较中的隐式转换，为什么需要看具体转换发生在哪一侧？**

字符串列与数值参数比较时，列可能按数值转换，多种字符串映射同一数值，普通字符串有序定位可能不再适用；若只是把常量转成列的类型，影响不同。

统一应用绑定类型与字段类型，并通过 EXPLAIN 检查，而不是只问“有没有加引号”。

**追问 3：能够使用索引但优化器没有选用时，应怎样进一步验证原因？**

统计信息过时、命中比例高、索引太宽或回表成本大，都可能使全表扫描更便宜。

采集实际参数和数据分布，更新统计后比较；强制索引只能作为受控验证或明确约束，不应替代根因分析。

### 9. `IS NULL`、`IS NOT NULL`、`OR` 和不等条件是否一定导致索引失效？

不一定。MySQL 可以为 NULL 建立索引，也能把某些不等或 OR 条件转成范围或索引合并。是否选择索引取决于可定位能力、返回比例和成本。

将这些语法全部列为“索引失效口诀”容易得出错误结论。

**追问 1：如何区分“不能用于定位”“使用索引扫描”和“优化器主动选择全表扫描”？**

不能定位但可扫描整个较窄覆盖索引，是一种索引访问；能形成范围但选择性太低，优化器可能主动全表扫描；确实对列施加不可利用变换，则是访问能力受限。

应分别看 type、key、使用键部分、Extra 和实际扫描量。

### 10. 优化器为什么会在多个可用索引之间作出不同选择，甚至选择看起来不合理的计划？

优化器按成本估算选择计划，不知道未来真实耗时。

- 索引基数、直方图、相关字段分布、LIMIT 和回表代价等都会影响选择；统计信息不准确或参数分布倾斜时，估算可能偏离实际。
- 看起来不合理的计划需要用实际数据验证，而不是仅凭“应该走某索引”。

**追问 1：统计信息怎样影响候选计划的行数和成本估算？**

估算返回行数越多，回表、连接和排序成本越高；多列相关性可能使独立估算失真，热点值与冷门值也不同。

一个索引对大多数值有效，不代表对所有参数都有效。

**追问 2：数据分布变化或估算与实际行数差异很大时，应怎样验证和更新统计信息？**

比较 EXPLAIN 估算与 EXPLAIN ANALYZE 实际行数及 loops，检查数据增长和 ANALYZE TABLE 时间，必要时更新统计或配置适合的直方图。

更新统计本身有资源成本，线上应控制窗口，并观察其他关键查询是否受影响。

**追问 3：使用提示强制选择索引前，怎样比较不同参数值下的计划，避免只修好一条样例查询？**

用高频、热点、冷门和边界参数测试候选计划，比较吞吐、I/O 与尾延迟。

- 提示会限制优化器未来适应数据变化的空间，应有监控和撤销机制。
- 不能只用一条开发样例就永久 FORCE INDEX。

### 11. 唯一索引包含 `NULL` 时，唯一性判断有什么边界？

MySQL 唯一索引通常允许多个 NULL，因为 NULL 不是普通相等值。

- 联合唯一键中只要包含可空部分，就可能允许业务看来重复的记录。
- 数据库约束的语义必须与业务“相同”定义一致，不能只看到 UNIQUE 就认为所有组合都被严格去重。

**追问 1：多个可空列组成联合唯一索引时，如何确认约束符合业务去重规则？**

先明确缺失值是否也算同一种状态；需要严格唯一时可设相关列 NOT NULL，或用经过论证的生成列/规范化表示。

不能随意把 NULL 替换成一个可能与合法数据冲突的常量。对全空、部分空和正常值分别编写并发插入测试。

### 12. 字符串前缀索引如何在空间、区分度与查询能力之间取舍？

前缀索引只保存字符串前若干字符，可减少索引宽度，但前缀相同的不同完整值会落入同一候选范围，需要进一步核验。

选择长度要看实际区分度、查询方式和索引字节限制，不能只选最短前缀。

**追问 1：为什么不能只考虑索引长度，还要分析排序与覆盖查询？**

前缀未保存完整字段，查询完整值通常不能仅靠该前缀索引覆盖；完整字符串排序也不能简单由短前缀顺序代替。

可比较不同前缀的 DISTINCT 比例和扫描候选数；若主要是精确长标识查询，可另评估固定摘要索引加原值校验，但摘要冲突不能忽略。

### 13. 索引已经很多时，怎样识别冗余索引和低收益索引？

结合索引定义、查询统计和实际执行计划识别重复、前缀包含及长期低收益索引。

`(a,b)`有时可以覆盖普通索引 a 的访问，但不能因此直接删除承担唯一约束或其他特殊功能的索引。未使用统计也受观测窗口和业务周期影响。

**追问 1：如何比较查询收益与插入、更新、存储维护成本，并验证删除索引不会伤害关键请求？**

评估索引大小、写频率、关键查询频次及维护成本；可在 MySQL 支持的情况下先设为不可见索引观察计划，但不可见仍有写维护成本。

覆盖业务高峰和月结等周期，准备恢复 DDL 并监控回归，再决定真正删除。

### 14. 一次覆盖索引查询是否在所有 MVCC 场景下都完全不访问聚簇索引？

不是绝对。覆盖描述所需列是否由索引提供，但 InnoDB 还必须确认记录对当前 Read View 可见。

二级索引没有与聚簇记录相同的完整版本链信息，遇到删除标记或无法直接确认版本可见性等情况，仍可能访问聚簇索引并借助 undo 构造可见版本。

**追问 1：二级索引记录的删除标记或版本可见性需要进一步判断时，应如何分析回表原因？**

应区分“取索引外字段导致回表”和“MVCC 可见性验证导致访问聚簇记录”。

- 高并发更新、长快照和删除状态可能改变实际访问成本。
- 不能凭 EXPLAIN 中的覆盖标记就证明运行期间完全没有聚簇页访问。

### 1. 事务的 ACID 分别约束什么？用转账例子说明事务失败时应保持哪些业务事实。

| 比较项 | 特点与用途 |
|---|---|
| 原子性（A） | 原子性要求事务要么整体生效要么撤销 |
| 一致性（C） | 一致性要求约束和业务不变量被保持 |
| 隔离性（I） | 隔离性约束并发事务相互影响 |
| 持久性（D） | 持久性要求已提交结果在约定故障模型下可恢复 |

转账中不能只扣 A 不加 B，余额和流水也要符合业务规则；数据库不会自动知道所有业务不变量，代码与约束仍需正确。

**追问 1：单个数据库事务的边界为什么不能自动覆盖外部 RPC 调用？**

本地事务管理的是该数据库参与的资源，远程 RPC 有独立状态和提交时点。即使本地回滚，远程已经扣费也不会自动撤销。

跨系统需要幂等、结果查询、可靠消息或适当分布式事务方案。

### 2. 脏读、不可重复读和幻读有什么区别？四种隔离级别如何影响并发可见性？

| 比较项 | 特点与用途 |
|---|---|
| 脏读 | 脏读是看到别的事务未提交修改 |
| 不可重复读 | 不可重复读是同一行多次读取看到其他事务已提交的新值 |
| 幻读 | 幻读关注相同查询条件对应的记录集合变化 |

隔离级别规定并发现象的允许范围，具体数据库可提供比最低标准更强的实现保证。

**追问 1：分别给出脏读、不可重复读和幻读的事务执行时序。**

脏读：A 改余额未提交，B 读到新值，A 随后回滚；不可重复读：B 第一次读 100，A 改 120 并提交，B 再次读 120；幻读：B 按金额范围读出若干行，A 插入匹配行并提交，B 再次按同条件得到更多行。分析时要明确普通快照读还是加锁读。

**追问 2：四种隔离级别对上述现象的要求有什么不同？InnoDB 默认采用哪一种？**

READ UNCOMMITTED 可发生脏读；READ COMMITTED 排除脏读；REPEATABLE READ 进一步要求可重复读取，其标准最低要求不一定排除幻读；SERIALIZABLE 提供可串行化效果。

InnoDB 默认 RR，通过一致性快照和必要的范围锁在相应场景避免幻读，但不应把所有混合读写都解释成同一快照。

**追问 3：业务选择读已提交或可重复读时，还应比较哪些并发、可见性与锁竞争成本？**

RC 通常每次一致性读取建立新视图，较新数据更容易被后续语句看到，且部分范围锁开销较少；RR 复用快照便于多次读取保持一致，但长快照和范围锁可能增大版本保留及竞争。业务应选所需语义，不能单纯追求级别越高越好。

### 3. `autocommit`、`START TRANSACTION` 与连接池复用之间有什么关系？

autocommit 开启时，未显式开启事务的语句通常各自构成事务；START TRANSACTION 开启显式事务，直到 commit 或 rollback 结束。

连接池复用的是带会话状态的连接，因此状态泄漏会把上个请求的事务设置带到下个请求，造成意外未提交或隔离差异。

**追问 1：一个连接执行完事务后遗留了隔离级别或自动提交状态，会怎样影响后续请求？**

例如上个请求关闭自动提交后未恢复，下个请求执行更新可能长时间不提交并持锁。

- 隔离级别、只读和自定义 session 变量也可能残留。
- 应由框架统一管理事务，并确认池会重置哪些属性，异常路径确保回滚和归还连接。

### 4. InnoDB 如何通过日志、锁与多版本机制实现事务特性？

undo 保存回滚及历史版本所需信息，redo 配合 WAL 支持崩溃后重放，锁与 MVCC 控制并发访问；约束和业务逻辑共同保持一致性。

- binlog 承担复制和时间点恢复等服务器层职责，并与引擎提交协调。
- ACID 不是一个“事务开关”内部完全相同的四件事。

**追问 1：不同机制分别侧重原子性、持久性还是隔离性？**

原子性主要依赖 undo 及事务回滚流程，持久性依赖 redo 和正确刷盘；隔离性依赖锁、Read View 及版本链。

业务一致性还依赖唯一、外键等约束以及正确代码，数据库不能自动修复一段把钱转错账户的事务。

**追问 2：为什么不能只靠其中一种机制解释完整事务？**

只有锁不能恢复断电数据，只有 redo 不能决定哪些并发版本可见，只有 MVCC 不能让多步写入自动共同回滚。

机制必须按执行、提交和恢复流程协作，回答时最好用同一笔更新串起来，而不是给 ACID 随意各配一个词。

### 5. MVCC 的版本链、undo log 与 Read View 如何协同决定可见版本？

聚簇记录包含最近修改事务 ID 和指向 undo 的回滚指针，历史版本由 undo 信息重建。

Read View 记录创建时活跃事务集合和事务 ID 边界；读取时从当前版本向历史版本查找第一个可见版本。它是逻辑版本选择，不是把全库所有行复制一份。

**追问 1：一条记录的历史版本怎样串联，Read View 根据哪些信息决定可见性？**

通常先判断是否为本事务修改；比视图中最小活跃事务 ID 更早的已提交版本可见，大于或等于视图建立时下一可分配事务 ID 的版本不可见；中间范围再看是否在活跃集合。

不可见就沿 undo 回退，直到找到可见版本或确认记录当时不存在。

**追问 2：读已提交与可重复读在创建或复用 Read View 时有什么区别？**

RC 通常每次一致性读创建新 Read View，因此后续语句可看到其间提交；RR 通常首次一致性读建立后在事务内复用。

加锁当前读不简单套用同一规则，DML 也不是永久基于最早快照执行。

**追问 3：事务自己的修改怎样参与可见性判断，为什么不能把读取结果简单理解成“开始时所有行的副本”？**

事务可以读取自己的修改，因此结果可能同时包含旧快照中别人的版本和自己刚写的新版本。

- 新插入、删除和更新通过版本规则判断，不是物理快照复制。
- 需要解释具体语句类型和发生顺序，不能只说“事务开始时拍了张照片”。

### 6. 执行 `START TRANSACTION` 的时刻是否必然等于建立一致性快照的时刻？

不必然。普通 START TRANSACTION 开始事务边界，但在 RR 下，一致性快照通常到首次一致性读取时才建立。

- 因此开始事务与首次 SELECT 之间其他事务的提交，可能被首次读取看见。
- `WITH CONSISTENT SNAPSHOT` 可在相应支持的隔离语义下提前建立快照。

**追问 1：普通 `START TRANSACTION` 与第一次一致性读取之间，可能存在怎样的时间差？**

A 先 BEGIN 但暂不读，B 修改并提交，A 再首次普通 SELECT，通常能把 B 已提交版本纳入视图。

把 BEGIN 时间当成所有情况下的快照时间，会得出错误结果。

**追问 2：`WITH CONSISTENT SNAPSHOT` 会改变哪个时间点，结论依赖什么隔离级别？**

在 InnoDB 的 RR 语境中，`START TRANSACTION WITH CONSISTENT SNAPSHOT`建立事务一致性读取所需快照；对不提供同样快照语义的隔离级别不能照搬结论，MySQL 会有相应处理或警告。

它也不把后续所有加锁读变成旧版本读。

**追问 3：两个事务在不同时间点建立快照时，怎样解释它们读取相同行得到不同版本？**

两个视图创建时的活跃事务与提交边界不同，选择到的版本自然可能不同。这是符合隔离规则的结果。

分析时列出视图建立点、更新提交点及读取类型，而不根据事务名字或开始顺序直接猜。

### 7. 快照读与当前读如何影响事务看到的数据，可重复读又如何处理幻读？

普通 SELECT 通常使用一致性快照，依据 Read View 读取可见版本；UPDATE、DELETE 及 SELECT FOR UPDATE 等使用当前读并取得必要锁。

RR 下重复快照读看到稳定集合，范围加锁读可通过 next-key/gap 锁阻止相关插入。两条路径解决问题的方式不同。

**追问 1：为什么不能只用一句“MVCC 解决幻读”概括所有读写场景？**

MVCC 保证某个视图中的读取一致，但不阻止其他事务真实插入数据；范围锁才限制相应并发写入。

- 混合当前读、快照读及本事务更新时，可能看到不同版本。
- 必须说明语句、索引范围与事务时序，不能把“RR 彻底没有任何集合变化”当作无条件结论。

### 8. 按给定的事务时序，判断可重复读事务 A 在每一步会看到什么数据。

题设：MySQL 8.4、InnoDB；`account(id PRIMARY KEY, balance INT NOT NULL)` 中只有 `(1, 100)`。事务 A 使用 `REPEATABLE READ`，按下列顺序执行，无其他并发操作：

```text
1. A：START TRANSACTION
2. A：SELECT balance FROM account WHERE id = 1
3. B：UPDATE account SET balance = 120 WHERE id = 1，并提交
4. A：SELECT balance FROM account WHERE id = 1
5. A：SELECT balance FROM account WHERE id = 1 FOR UPDATE
6. A：UPDATE account SET balance = balance + 10 WHERE id = 1
7. A：SELECT balance FROM account WHERE id = 1
8. A：COMMIT
```

B 的更新与提交均在步骤 4 之前完成；逐步分析，不假定普通查询与加锁查询总是读取同一版本。

步骤 2 读取 100 并建立 A 的一致性视图；B 提交 120 后，步骤 4 普通 SELECT 仍读 100；步骤 5 当前加锁读看到 120；步骤 6 在当前记录 120 上加 10 得到 130；步骤 7 读取自己的修改，得到 130。最后 A 提交 130。

这组结果不矛盾，来自不同读取语义。

**追问 1：步骤 2 与步骤 4 的普通 `SELECT` 有何关系，步骤 5 又采用什么读取语义？**

步骤 2 和 4 复用 RR 一致性视图；步骤 5 使用当前读并获得 id=1 的排他记录锁，因此看到 B 已提交的 120。

当前读不会把 A 原先普通 SELECT 的历史视图简单“刷新成全局最新快照”。

**追问 2：步骤 6 的更新以哪个版本为基础，步骤 7 能否读取事务自己的修改？**

`balance=balance+10`在实际当前记录上执行，而不是拿步骤 2 的 100 写回 110。事务能读到自己的更新，所以步骤 7 返回 130。

若业务先读 100 再用常量写 110，语义将不同，这也是丢失更新需要单独分析的原因。

**追问 3：混合快照读与当前读时，怎样解释结果而不笼统归结为“隔离级别失效”？**

RR 并不要求当前加锁读与历史快照读永远同值，且事务自身写入必须可见。应逐条标记“快照、当前、自己修改”三类来源。

如果业务需要基于读取结果作互斥决策，应在适当范围使用加锁读或原子条件更新。

### 9. 两个事务先读取同一计数再各自写回，为什么可能丢失一次更新？

两个事务都先读到 count=10，再各自计算 11 并写回，即使写入时行锁使它们先后执行，最终仍可能只有 11，丢失一次业务增加。

问题在于把过期读取计算出的常量覆盖当前值，不是数据库没有给 UPDATE 加锁。

**追问 1：构造两个事务读取相同旧值后分别写回的时序，指出丢失更新发生在哪里。**

A 读 10、B 读 10、A 写 11 提交、B 等待后也写 11 提交，最终 11。

第二次写回没有验证读取版本是否仍有效，所以覆盖了其他事务已完成的业务变化。

**追问 2：原子 UPDATE、版本号条件更新与 `SELECT FOR UPDATE`，分别怎样改变竞争过程？**

`UPDATE ... SET count=count+1`在行锁保护下基于当前值加一；

- 版本号条件更新只有 version 仍相同才成功，否则重读重算；
- SELECT FOR UPDATE 则在决策前锁住行，并在同一事务内完成读取与更新。选型还要看冲突率和操作范围。

**追问 3：采用失败重试时，需要重做哪部分读取和计算，怎样避免重复副作用？**

重试整个受影响事务，重新读当前状态并重新计算，不能重发旧常量或只重试最后一句。

事务外扣费、发短信等副作用需幂等键或可靠补偿，避免数据库重试导致外部操作重复。

### 10. 长事务即使主要执行查询，也会怎样影响 `undo` 保留、purge 与数据库资源？

长时间存活的 Read View 可能使旧版本仍被某个事务需要，阻碍 purge 清理相关 undo；即使事务主要读，也可能占用连接、保留元数据锁并阻塞 DDL。

持续写的长事务还会积累更多 undo、redo 和行锁。应区分“没有修改”与“没有系统成本”。

**追问 1：长期存在的 Read View 为什么可能影响历史版本清理？**

purge 必须保证没有活跃视图需要即将清理的版本，老视图会延长保留窗口。

其他事务持续更新时，历史版本和空间压力可能不断增长，查询自身很安静也不代表无影响。

**追问 2：主要执行查询的长事务，与持续修改数据的长事务，分别占用或阻碍什么资源？**

长读主要保留快照、连接及部分事务级资源；长写还会长时间持有写锁、增加回滚成本和复制应用负担。

只有开始但未建立视图、未做访问的事务与真正活跃长事务也应区分。

**追问 3：怎样从持续时间、历史版本数量和访问方式判断改进方向？**

检查 INNODB_TRX、history list length、事务开始时间、当前 SQL、连接来源和 undo 空间。

优化为短事务、稳定键分批或专用一致性导出；若业务确需长快照，应隔离资源并规划容量，而不是直接杀掉所有长查询。

### 11. 在 MySQL 事务中执行 DDL，为什么可能出现与普通 DML 不同的提交行为？

MySQL 许多 DDL 会在执行前隐式提交已有事务，并在执行后结束自身事务，因此不能与普通 DML 任意组合成可回滚大事务。

MySQL 8.4 的原子 DDL 保证一条支持的 DDL 及相关字典、引擎修改在故障下保持原子一致，不等于用户 ROLLBACK 可以撤销任意建表或改表。

**追问 1：以 MySQL 8.4 为例，执行普通 `ALTER TABLE`、`TRUNCATE TABLE` 前后，应如何判断隐式提交？**

普通 ALTER TABLE、TRUNCATE TABLE 属于会隐式提交的语句，应在调用前确认没有期待继续回滚的业务事务。

DDL 失败也不代表此前被隐式提交的 DML 会自动恢复。

**追问 2：先更新业务数据，再执行会隐式提交的 DDL，最后调用 `ROLLBACK`，哪些操作不能按最初预期撤销？**

先 UPDATE 再执行此类 DDL，UPDATE 可能已在 DDL 开始前提交；最后 ROLLBACK 无法撤销它，也不能按普通 DML 回滚已经完成的 DDL。应把模式变更与在线业务事务分开发布。

**追问 3：临时表创建的例外与原子 DDL 分别意味着什么？为什么原子 DDL 不等于任意用户事务都能回滚建表？**

MySQL 8.4 中，`CREATE TEMPORARY TABLE` 和 `DROP TEMPORARY TABLE` 不会像普通建表、删表一样隐式提交，但这两条操作本身也不能被用户 `ROLLBACK` 撤销：例如创建临时表后回滚，表仍然存在。

- 不要把这个例外推广到临时表上的全部 DDL，`ALTER TABLE`、`CREATE INDEX` 等仍有隐式提交规则。
- 原子 DDL 保证的是一条支持的 DDL 内部在崩溃后的全成或全败，不是让任意用户事务能够回滚其中的 DDL。

### 12. `SAVEPOINT`、`ROLLBACK TO SAVEPOINT` 与完整事务回滚有什么区别？

SAVEPOINT 在当前事务中设置回滚位置，ROLLBACK TO 撤销此位置之后的部分修改，但不结束整个事务；完整 ROLLBACK 结束事务并撤销全部未提交修改。

保存点不是新的独立事务，不能单独持久提交其中一段。

**追问 1：同一批操作中只撤销后一部分时，保存点如何定位回滚边界？**

例如先更新 A，设 SAVEPOINT s，再更新 B，ROLLBACK TO s 撤销 B 但保留 A 在当前事务内的修改；之后仍需 COMMIT 或 ROLLBACK 决定最终结果。

RELEASE SAVEPOINT 只是删除保存点，不提交其前的数据。

**追问 2：回滚到保存点是否意味着外层事务已经结束，或者所有已持有的锁都已释放？**

不会结束外层事务，也不能假定所有后续取得的锁都被释放。

InnoDB 对保存点回滚的锁释放有具体规则，已有记录锁可能继续保留；需要减小锁占用时应缩短事务，而不是频繁回滚保存点。

**追问 3：在同一个连接中再次执行 `START TRANSACTION`，能否直接得到可独立提交的嵌套事务？请说明 MySQL 的行为。**

不能。MySQL 在当前连接中再次执行 `START TRANSACTION` 时，会先隐式提交当前事务，再开始新事务；不是回滚原事务，也不是创建独立的嵌套子事务。

- 例如更新 A 后再次开启事务，再更新 B，最后 `ROLLBACK` 只能撤销新事务中的 B，A 已经提交。
- 需要部分回滚用保存点；需要真正独立的事务，可使用另一连接，并明确两笔事务之间的业务一致性。

### 1. 共享锁、排他锁与意向锁之间是什么关系？

| 机制 | 特点与边界 |
|---|---|
| 共享锁 S | 共享锁 S 允许多个事务读取受保护记录 |
| 排他锁 X | 排他锁 X 用于排斥其他冲突读写锁 |
| 意向锁 IS / IX | 表级意向锁 IS/IX 表示事务准备在表内某些记录上取得共享或排他锁，方便表级与行级锁协调 |

多个 IX 通常可以共存，这不妨碍它们在同一行上发生 X 锁冲突。

**追问 1：为什么加行锁时还需要表级意向信息？**

如果没有意向信息，取得整表排他锁时可能需要检查大量行锁。

- 意向锁让数据库先在表层判断兼容性，再细到记录层协调。
- 它表达后续行锁意图，不是业务层的“乐观锁版本号”。

**追问 2：意向锁是否等于把整张表的每一行都锁住？**

不是。IX 不等于每行都加 X，也不自动阻塞另一个事务操作不同记录。

需要分别看表级锁兼容矩阵与记录锁冲突；不能看到表级 IX 就说数据库已经锁死整张表。

### 2. InnoDB 如何根据索引访问路径和查询条件确定加锁范围？

InnoDB 的行锁实际围绕索引记录和扫描范围建立。

- 记录锁保护某条索引记录；间隙锁阻止在某段键区间插入；next-key 锁组合记录及其前方间隙。
- 唯一等值命中等条件可缩小为记录锁，RR 范围访问则可能保护间隙。实际范围取决于索引、隔离级别和语句执行路径。

**追问 1：记录锁、间隙锁与临键锁分别保护哪些范围？**

记录锁对应一个键；间隙锁通常只限制插入，不等同于锁住两端已有记录；next-key 常表示 `(前一键, 当前键]`。

边界优化可能拆成纯记录或纯间隙锁，因此不能对所有查询机械套用一个区间模板。

**追问 2：同一业务过滤条件选择不同索引时，为什么可能影响实际锁住的记录或间隙？**

经二级索引扫描时会锁相关二级记录，排他访问还可能锁对应聚簇记录；走全表扫描会接触更多记录和间隙。

业务 WHERE 相同但计划不同，实际并发影响就可能不同，应结合 EXPLAIN 及锁表观察。

**追问 3：`SELECT FOR UPDATE` 的锁何时释放，应怎样结合事务状态检查，而不是只看 SQL 已返回？**

显式事务中的相关锁通常保留到 COMMIT 或 ROLLBACK，SQL 返回并不代表释放。

- 自动提交下语句结束事务也结束，无法保护随后另一条语句。
- 保存点回滚、非匹配行释放等还有具体规则，诊断时要看事务是否仍活跃。

### 3. 根据给定表结构，分析不同加锁查询的锁定范围。

题设：MySQL 8.4、InnoDB、`REPEATABLE READ`；表 `t(id INT PRIMARY KEY, value INT NOT NULL)` 已提交记录为 `(10, 1)`、`(20, 1)`、`(30, 1)`。下列语句分别在独立的新事务中执行，执行后暂不提交：

```sql
SELECT * FROM t WHERE id = 20 FOR UPDATE;
SELECT * FROM t WHERE id = 25 FOR UPDATE;
SELECT * FROM t WHERE id >= 20 AND id < 30 FOR UPDATE;
```

各案例开始时恢复到相同初始数据。先根据题设推导，再说明如何观察数据库实际持有的锁。

按 MySQL 8.4 中 PRIMARY 升序定位/范围扫描的路径分析：`id=20`命中唯一记录，保护 20 本身；

- `id=25`未命中，保护间隙 `(20,30)`；
- `id>=20 AND id<30`保护记录 20 及后续间隙 `(20,30)`，排除上界 30 的记录本身。
- 第三种不能照搬旧版教程一概说 30 也加排他记录锁；应同时确认实际访问计划与锁模式。

**追问 1：唯一索引等值命中、等值未命中和范围查询，分别可能保护哪些记录与间隙？**

第一种通常表现为 20 上的 `X,REC_NOT_GAP`；第二种可表现为依附后继键 30 的 `X,GAP`，但其保护对象是 30 之前的间隙；第三种结合 20 记录锁及 30 前间隙锁。

表级 IX 还会存在，不能把它与记录区间相加误认为全表锁。

**追问 2：另一个事务分别执行 `INSERT INTO t VALUES (22, 1)` 或 `UPDATE t SET value = 2 WHERE id = 30` 时，哪些案例可能发生等待？如何观察实际锁信息？**

在上述路径下，插入 22 在第一种不受该记录锁阻止，在第二、三种会等待间隙保护解除；仅更新已有 30 的 value，在三种案例中都不因这些间隙锁而被阻止。

- 用不同会话执行，并查询 `performance_schema.data_locks`、`data_lock_waits` 的 INDEX_NAME、LOCK_MODE、LOCK_DATA 及阻塞关系，区分纯 GAP 与包含记录的 next-key；
- 若实际计划不同，应按真实扫描重新判断。

**追问 3：另建非唯一索引 `KEY idx_value(value)`，执行 `SELECT * FROM t FORCE INDEX (idx_value) WHERE value = 1 FOR UPDATE`。重复索引值、扫描范围和对聚簇索引记录的加锁如何影响结果？**

非唯一二级索引实际按 value 与主键组合区分记录，value=1 会扫描所有相同 value 的索引项及必要边界间隙，并对匹配的聚簇记录 10、20、30 加排他记录锁。

- 此时更新 30 会冲突，新插入 value=1 也受范围保护。
- 非唯一等值不能套用“唯一等值命中只锁一行”的优化。

### 4. UPDATE 的过滤字段没有可用索引时，会怎样影响扫描量和加锁范围？

没有可用索引的 UPDATE 可能扫描大量甚至全部聚簇记录；在 RR 等语义下，扫描对应记录和间隙的加锁会显著扩大影响，即使最终只修改少量行。

其表现可能接近整表不可写，但不能直接称为 InnoDB 自动把行锁升级成表锁。

**追问 1：索引访问范围扩大后，为什么扫描与持锁影响可能明显增加？**

数据库必须先找到满足条件的记录，扫描范围越大，处理和锁管理成本越高，可能阻塞无关请求。

RC 等隔离级别对非匹配记录和间隙锁的处理不同，因此还要固定隔离级别，而不是仅依据 UPDATE 结果行数推断持锁量。

**追问 2：如何查看实际持有的记录或间隙锁，为什么不能简单把现象称为“行锁自动升级成表锁”？**

查看 EXPLAIN、事务状态、data_locks 与 data_lock_waits，核对索引名及 RECORD/TABLE 类型。

- 大量记录锁和表级 IX 并存，与真正表级 X 锁不是一回事。
- 优化过滤索引和事务范围，避免以为调大锁等待超时就解决了扫描问题。

### 5. 插入意向锁与间隙锁有什么区别？

插入意向锁表示某事务准备向索引间隙插入，用于与现有范围保护协调；普通间隙锁主要阻止该区间的新插入。

插入意向不是整表的 IX 锁，也不意味着所有同一间隙的插入彼此串行。真正冲突还要看目标位置和唯一性约束。

**追问 1：多个事务向同一索引间隙插入是否一定互相阻塞？**

不一定。例如已有 10 和 20，分别插入 12 和 15 通常可以并发；若另一事务持有 `(10,20)` 的间隙锁，两者会等待。

插入相同唯一键则涉及记录与唯一性检查冲突，是另一条约束。

**追问 2：并发插入、唯一键冲突与范围锁同时出现时，应如何分析等待关系？**

先列出已有范围锁，再看各插入位置、唯一键候选及获取顺序。

- 唯一性检查可能取得共享或排他等相关锁，多个插入/删除交错也可能死锁。
- 不能只看到“INSERT”就认为它只加一种固定锁。

### 6. 数据库更新中，如何选择乐观并发控制或悲观加锁？

低冲突、读取后可重算的业务可用版本号或状态条件进行乐观并发控制，更新失败再重试；高冲突或必须先读取并保护多步决策时，可用 SELECT FOR UPDATE 等悲观方式。

两者最终都依赖数据库原子写入及锁机制，并非“乐观方案完全没有锁”。

**追问 1：高冲突与低冲突业务中，失败重试和持锁成本如何权衡？**

乐观方案避免长时间持锁，但竞争高时重复计算和重试放大；悲观方案减少反复失败，却增加等待、死锁和连接占用。

简单库存可直接条件 UPDATE，不必先读再锁；复杂多行规则应固定访问顺序、缩短事务并设置有限重试。

### 7. 阅读以下执行顺序，判断何时可能形成数据库死锁。

题设：MySQL 8.4 的 InnoDB 表 `account(id INT PRIMARY KEY, balance INT NOT NULL)` 已有记录 `(1, 100)`、`(2, 100)`，没有其他约束或触发器；A、B 各自开启事务，按以下先后顺序执行：

```text
1. A：UPDATE account SET balance = balance - 10 WHERE id = 1
2. B：UPDATE account SET balance = balance - 20 WHERE id = 2
3. A：UPDATE account SET balance = balance + 10 WHERE id = 2
4. B：UPDATE account SET balance = balance + 20 WHERE id = 1
```

步骤 3 发出后不要求先返回，随后由另一个连接发出步骤 4；两个事务在上述步骤中均未提交。

步骤 1 中 A 持有 id=1 的排他记录锁，步骤 2 中 B 持有 id=2 的排他记录锁。

- 步骤 3 中 A 请求 id=2 而等待 B；步骤 4 中 B 又请求 id=1 而等待 A，于是形成 `A等B、B等A` 的循环。
- InnoDB 启用死锁检测时会选择牺牲事务回滚，使另一方能够继续。

**追问 1：按步骤画出两个事务的持锁与等待关系，在哪一步形成循环等待？**

步骤 3 只有单向等待，还不是本题的循环死锁；步骤 4 建立反向边，循环形成。

两个事务未提交，因此不能指望前两条 UPDATE 完成后锁已经释放。牺牲者由数据库选择，不保证永远是后发起的事务。

**追问 2：本题已经使用主键等值访问，再增加索引能否解决访问顺序相反的问题？统一更新顺序和缩短事务分别改善什么？**

已经通过主键精确定位，再加索引不能修复相反获取顺序。

统一按较小账户 ID 先锁，可以破坏循环等待；缩短事务降低锁重叠机会，但不单独保证所有访问顺序都无死锁。转账金额方向与锁顺序应分开设计。

**追问 3：数据库选择一个事务作为回滚对象后，应用如何确认回滚范围，并有限重试整个业务操作？**

典型死锁错误会回滚整个牺牲事务，应用应清理事务上下文后，有限次数重新执行整个转账逻辑并加入退避。

不要只重试最后一句，否则扣减与增加可能不配对；事务外副作用必须具备幂等或延后到可靠提交之后。

### 8. MDL 元数据锁、全局读锁与 InnoDB 行锁分别保护什么？

MDL 保护表定义及使用期间的元数据一致性，全局读锁用于某些全局一致性或管理操作，InnoDB 行锁保护索引记录和范围。

它们属于不同层次：长事务即使普通 SELECT 不加行锁，也可能因持有元数据锁阻塞 DDL。

**追问 1：元数据锁、全局读锁与行锁分别保护什么对象，通常由哪些操作触发？**

DML 访问表会取得相应 MDL，ALTER TABLE 通常需要更强的元数据锁；`FLUSH TABLES WITH READ LOCK`等可取得全局读锁；UPDATE 和加锁 SELECT 取得 InnoDB 记录/间隙锁。

不要把所有“等待锁”都当成行锁冲突。

**追问 2：一个未结束的事务为什么可能阻塞 `ALTER TABLE`，后续普通请求又如何形成排队？**

一个未结束事务仍使用表，ALTER 等待其 MDL；等待中的排他元数据请求又可能影响后续普通访问的排队，形成大量请求堆积。

根因可能是最早那个空闲未提交连接，而不是当前看起来最慢的 DDL。

**追问 3：处理阻塞前，怎样找到真正的持有者，并评估终止事务或取消 DDL 的影响？**

结合 metadata_locks、threads、processlist 和事务表找到持有者、等待者及开始时间。

取消尚未执行的 DDL 可先释放排队压力；终止持有者可能触发大事务回滚，需评估耗时和业务结果。先止损并保留证据，不盲目 kill 所有连接。

### 9. 死锁检测和锁等待超时在触发原因、错误处理与回滚范围上有什么区别？

死锁检测发现等待图中的循环，通常立即回滚一个事务；锁等待超时是等待超过配置时长，未必存在循环。

以 InnoDB 常见默认行为为例，死锁回滚整个事务，锁等待超时通常仅回滚当前语句，除非配置改变。因此两种错误不能使用同一未经检查的重试逻辑。

**追问 1：业务重试前应该确认整个事务还是单条语句已被回滚，并检查哪些配置？**

核对错误码、事务状态、`innodb_deadlock_detect`、`innodb_lock_wait_timeout` 与 `innodb_rollback_on_timeout`。

为简化正确性，业务可以在可控边界主动回滚整个失败事务后重试，但要保证读取重做、次数有限和外部副作用幂等，不能继续提交一半操作。

- [4. redo log 与 `binlog` 为什么需要协调提交，日志两阶段提交如何工作？](#4-redo-log-与-binlog-为什么需要协调提交日志两阶段提交如何工作)

### 1. redo log、undo log 与 `binlog` 分别记录什么，如何参与持久化、回滚与恢复？

| 比较项 | 特点与用途 |
|---|---|
| redo log | redo 记录 InnoDB 页修改所需的重放信息 |
| undo log | undo 保存回滚与构造历史版本所需信息 |
| binlog | binlog 在服务器层记录可用于复制和时间点恢复的变更 |

它们不是彼此完整备份：redo 解决引擎崩溃恢复，undo 解决撤销和 MVCC，binlog 连接跨实例变更历史。

**追问 1：三种日志分别保存什么信息，主要由哪一层维护？**

redo 与 undo 由 InnoDB 管理；binlog 由 MySQL 服务器层组织，可采用 ROW 等格式。

redo 常被描述为物理或生理日志，不能说每条都保存完整数据页；undo 也不是简单把全表复制一份。

**追问 2：已有 `binlog` 为什么还需要 `redo`，`undo` 又怎样支持回滚和 MVCC？**

binlog 不足以直接恢复引擎内部页状态和未落盘修改，因此仍需 redo；undo 可以逆转未提交操作或恢复旧版本。

undo 页自身也需要相应持久化保护，不能说 undo 只是内存中的临时数据。

**追问 3：描述一笔更新时，怎样区分执行成功、事务提交和故障后可恢复？**

UPDATE 返回表示语句执行，可能仍处于未提交事务；COMMIT 成功表示达到配置定义的提交确认边界；断电是否可恢复还取决于日志刷盘和存储保证。

三者应分别描述，尤其不能把“写进 Log Buffer”当成断电不丢。

### 2. 一条 UPDATE 从读取旧记录到提交，会怎样串联数据页、`undo`、`redo` 与 `binlog`？

1. **定位与加锁：** 执行 UPDATE 时先定位当前记录并取得必要锁。
2. **准备回滚信息：** 准备 undo 信息。
3. **修改内存页：** 修改 Buffer Pool 中的记录和相关索引。
4. **记录重做日志：** 生成 redo 保护这些页变化。
5. **协调事务提交：** 服务器收集 binlog 事件，提交阶段协调引擎准备、binlog 持久化及引擎提交。

数据页可以稍后刷回，日志顺序与提交状态保证恢复时能判断如何处理。

**追问 1：请用同一笔事务说明各类日志的产生时机，以及崩溃后哪些信息用于恢复或回滚。**

例如余额 100 改 120，undo 保留重建旧值所需信息，redo 描述相关页修改，ROW binlog 记录行变更。

崩溃后先依 redo 恢复引擎页状态，再根据事务提交证据决定保留或回滚未提交事务；不能只看数据页上已经是 120 就断定事务一定提交。

### 3. WAL 与 Checkpoint 分别解决什么问题？

WAL 要求在脏数据页持久化前，其相关日志先达到需要的持久化边界，从而支持故障恢复；Checkpoint 标记哪些较早的修改已安全落到数据页，可推进日志回收和缩短恢复范围。

WAL 强调先后约束，Checkpoint 强调恢复起点及空间推进。

**追问 1：`redo` 日志空间接近用满时为什么可能影响前台写入？**

redo 容量有限，仍可能用于恢复的旧日志不能覆盖；当 checkpoint 落后，系统需要加快脏页刷盘，必要时限制或等待前台写入。

增大 redo 容量只能扩大缓冲窗口，不能无限抵消持续低于业务写入的存储能力。

**追问 2：已提交事务的数据页尚未刷回表文件，是否意味着数据一定丢失？**

不意味着。只要相关提交和 redo 达到所需持久化保证，重启可重放这些修改。

反过来，数据页已经写过也不证明事务已提交，恢复仍可能利用 undo 撤销未提交事务。

### 4. redo log 与 `binlog` 为什么需要协调提交，日志两阶段提交如何工作？

InnoDB 提交与 binlog 必须保持一致，否则可能出现主库有事务但副本日志没有，或 binlog 包含事务而引擎恢复却回滚。

内部两阶段提交通常先让引擎处于 prepare 状态，再记录 binlog 提交证据，最后完成引擎 commit；崩溃恢复依据这些证据裁定事务结果。

**追问 1：为什么不能任意先后独立提交 `redo` 与 `binlog`，而不协调它们的状态？**

独立提交的先后两种顺序都可能留下中间崩溃窗口。

需要一个可恢复的准备状态和协调证据，而不是把两个文件连续 write 一下就认为原子。

**追问 2：准备阶段、`binlog` 写入后和最终提交附近发生崩溃时，恢复过程需要核对什么证据？**

仅有 prepare 且无完整 binlog 提交证据的事务通常应回滚；prepare 已存在且 binlog 中有完整对应事务证据，则可完成提交；已完成引擎提交则按一致恢复状态保留。

应考虑日志完整性、XID 关联和刷盘配置，不能只看文件里出现过某条 SQL 片段。

**追问 3：日志两阶段提交与跨服务分布式事务的两阶段提交，讨论范围有何不同？**

这里是 MySQL 服务器与本地存储引擎、binlog 之间的内部协调；跨服务 2PC 涉及远程参与者、网络分区及分布式协调。

概念相似，但故障模型、参与资源和性能成本不同，不能由内部 2PC 推导出任意 RPC 也在事务里。

### 5. `binlog` 不同记录格式在复制正确性、日志体积和执行成本上有哪些取舍？

STATEMENT 记录执行语句，日志可能较小但依赖确定性与执行环境；ROW 记录行变更，便于复制正确还原但大批量修改可能产生较多日志；MIXED 按规则选择。

binlog_format 不只是存储压缩选项，还影响复制、CDC 及故障排查能力。

**追问 1：应如何结合实际 SQL 与复制需求选择？**

有非确定性函数、触发器或复杂执行差异时要注意语句复制风险；CDC 通常更适合 ROW，并需检查 row image 能否提供下游所需字段。

大事务日志体积可通过批次和业务优化控制，不能只为缩小日志而忽略复制正确性。

### 6. `innodb_flush_log_at_trx_commit` 与 `sync_binlog` 如何影响持久化保证和提交性能？

`innodb_flush_log_at_trx_commit`控制 redo 提交写出与刷盘，`sync_binlog`控制 binlog 的同步频率。

要求较强本机断电持久性时常采用两者均为 1，并依赖真实可靠的存储 fsync 语义；这仍不自动保证异步副本切换零丢失。

**追问 1：分别说明数据进入日志缓冲、写入操作系统缓存与持久化刷盘的区别。**

日志仍在数据库进程的用户态缓冲区时，进程崩溃就可能丢失；写入操作系统页缓存后，单独的 mysqld 进程退出通常不会清空这些数据，但机器断电仍可能丢失；完成可靠存储支持的 fsync 后，才获得相应的持久化保证。

- 对于 redo，`innodb_flush_log_at_trx_commit=1` 在每次提交时按要求写出并刷盘，`2` 在提交时写出并周期刷盘，`0` 通常周期写出和刷盘。
- 组提交可以让多个事务共享一次同步，不意味着每笔事务必定各做一次独立 fsync。

**追问 2：进程崩溃和机器断电时，不同配置会留下怎样的数据风险？**

redo 配置为 `2` 时，单独 mysqld 崩溃与机器断电风险不同；配置为 `0` 时，还可能丢失留在进程日志缓冲中的数据。

- 周期刷盘不等于严格的一秒丢失上限，调度和 I/O 延迟可能扩大窗口。
- `sync_binlog=0` 不要求 MySQL 主动按事务组同步 binlog，由操作系统处理；`N>0` 表示每累计 N 个 binlog 提交组后同步一次。
- N 不是固定秒数，也不必等于 N 笔事务；风险需要同时结合事务分组、redo 和真实存储语义判断。

**追问 3：组提交怎样减少刷盘开销？高吞吐与高可靠业务应怎样确定可接受的取舍？**

组提交把多个并发事务的日志组织成一组同步，摊薄 fsync 成本，而不是必须为每笔事务单独刷一次。

先用组提交、合适存储及批次优化吞吐，再根据业务可接受损失明确是否放松持久化；资金等关键数据不能用模糊“偶尔丢一点”做配置依据。

### 1. SQL 的逻辑处理顺序与数据库实际执行计划有什么区别？

SQL 是声明式语言，逻辑处理顺序用于解释结果含义，物理执行计划则由优化器安排。

通常先形成 FROM/JOIN 关系并按 ON 匹配，再 WHERE 过滤、GROUP BY 聚合、HAVING 筛组、SELECT 投影，随后去重、ORDER BY 和 LIMIT 等；实际执行可以在保持语义的前提下重排和下推。

**追问 1：说明 `FROM`、`JOIN`、`WHERE`、`GROUP BY`、`HAVING`、`SELECT`、`ORDER BY` 和 `LIMIT` 的逻辑关系。**

WHERE 筛选原始行，HAVING 筛选分组结果，SELECT 决定输出表达式，ORDER BY 决定结果次序，LIMIT 裁剪结果。

外连接还要保留未匹配行，不能把所有 ON 条件都任意挪到 WHERE 而认为结果相同。

**追问 2：为什么不能把 SQL 的书写顺序直接当成物理执行顺序？优化器可以怎样改变访问与连接顺序？**

优化器可以提前过滤、调整内连接顺序、选择索引、转换半连接或物化子查询，不必按文本从左到右机械执行。

外连接、聚合、窗口和相关子查询等语义会限制可重排范围，EXPLAIN 反映的是实际选择。

**追问 3：某些子句中能使用 `SELECT` 别名而另一些不能时，如何结合 MySQL 语法规则判断，而不是机械套用顺序？**

MySQL 允许在 GROUP BY、ORDER BY 及某些 HAVING 表达式使用 SELECT 别名，WHERE 通常不能引用同层 SELECT 别名。

别名解析属于具体语法规则，不能仅靠背逻辑顺序推导所有合法性；有歧义时用明确表达式或子查询。

### 2. `COUNT(*)`、`COUNT(1)` 与 `COUNT(字段)` 的统计结果有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| COUNT(*) | COUNT(*)统计结果行数 |
| COUNT(1) | COUNT(1)统计非 NULL 常量所在行数，因此两者通常结果相同 |
| COUNT(字段) | COUNT(col)只统计 col 不为 NULL 的行 |

选择 COUNT(*)能直接表达“数行”，不必为了传闻中的性能优势改成 COUNT(1)。

**追问 1：字段包含 `NULL` 时结果如何变化？**

三行数据中某字段有一行 NULL，COUNT(*)和 COUNT(1)为 3，COUNT(该字段)为 2。

LEFT JOIN 补出的空关联行也会被 COUNT(*)算作一行，统计子表数量时应使用非空子表主键。

**追问 2：为什么比较执行效率还要结合存储引擎和执行计划？**

引擎是否保存精确行数、事务可见性、覆盖索引和过滤条件都会影响成本。

- InnoDB 可能扫描较窄二级索引，但仍需按当前事务可见性计数。
- 不能把 COUNT(1)永久排在 COUNT(*)之前，也不能把统计函数选型与索引访问分开看。

### 3. InnoDB 对全表 `COUNT` 的处理为什么可能与 MyISAM 不同？

MyISAM 对无 WHERE 的某些全表 COUNT 可以使用维护的行数信息；InnoDB 存在 MVCC，不同事务可见行集合不同，无法用一个全局固定计数回答所有一致性视图，通常需要扫描合适索引并判断可见性。

表统计中的估算行数不能替代精确 COUNT。

**追问 1：不同事务看到的数据版本、可用索引和近似统计值，会怎样影响统计方案的正确性与代价？**

实时精确计数需要支付扫描或维护成本；允许近似的监控可使用统计值；高频业务计数可以维护汇总表或异步统计，但必须设计增删、回滚及校验。

不能把缓存计数与事务快照内精确行数当成同一保证。

### 4. `WHERE` 与 `HAVING` 分别在什么阶段过滤数据？`GROUP BY` 与 `DISTINCT` 如何选择？

WHERE 在分组前筛选行，HAVING 在分组后筛选聚合结果。

- GROUP BY 用于按键组织聚合，DISTINCT 直接表达对投影结果去重。
- 它们在某些无聚合查询中结果相近，但语义和可优化方式应分别理解，不应为了套口诀互换。

**追问 1：数据行过滤与分组后过滤，分别应写在哪个位置？**

订单是否已支付是行条件，放 WHERE；每个用户订单数是否超过 5 是聚合条件，放 HAVING。

能在分组前合法过滤的条件提前过滤，通常可减少参与聚合的数据量。

**追问 2：统计每个用户的已支付订单数，再筛选订单数超过 5 的用户，应怎样组织 SQL？**

可写为：
```sql
SELECT user_id, COUNT(*) AS paid_count
FROM orders
WHERE status = 'PAID'
GROUP BY user_id
HAVING COUNT(*) > 5;
```
- 需要排除未归属订单时再明确 `user_id IS NOT NULL`。
- 索引选择应结合 status 选择性和 user_id 分组，不能脱离数据分布断定唯一最优索引。

**追问 3：只需要去重而不计算聚合结果时，`GROUP BY` 与 `DISTINCT` 的选择依据有什么不同？**

只需要去重时 DISTINCT 通常更清楚；需要 SUM、COUNT 等分组结果时用 GROUP BY。

二者都不保证输出顺序，必须 ORDER BY；性能要看计划及索引，不能认为 DISTINCT 一定更慢或 GROUP BY 一定会排序。

### 5. 根据给定数据，写出所有用户及其已支付订单数，保留没有已支付订单的用户。

表结构：`users(id PRIMARY KEY)`；`orders(id PRIMARY KEY, user_id, status)`，`status='PAID'` 表示已支付。数据为：

```text
users
id
1
2
3

orders
id  user_id  status
11  1        PAID
12  1        CANCELLED
13  2        CANCELLED
```

要求每位用户恰好返回一行，订单数为零的用户也必须出现在结果中。

将支付状态限制放在 LEFT JOIN 的 ON 中，再统计订单主键：
```sql
SELECT u.id, COUNT(o.id) AS paid_count
FROM users AS u
LEFT JOIN orders AS o
  ON o.user_id = u.id AND o.status = 'PAID'
GROUP BY u.id
ORDER BY u.id;
```
- 结果为 `(1,1)、(2,0)、(3,0)`。
- 每个用户都保留，只有匹配到的已支付订单参与计数。

**追问 1：`INNER JOIN` 与 `LEFT JOIN` 在本题中会保留哪些用户？**

INNER JOIN 并在关联时筛 PAID，只保留用户 1；LEFT JOIN 保留 1、2、3，未匹配者的订单列补 NULL。

若 INNER JOIN 不筛状态，用户 2 会因取消订单出现，但这已不是题目要统计的关系。

**追问 2：把 `orders.status` 的条件写在 ON 或 `WHERE` 中，结果怎样变化？**

ON 中的状态条件限制匹配哪些订单，不删除左侧用户；把 `o.status='PAID'` 放 WHERE，会滤掉补 NULL 行，也排除只有取消订单的用户，效果退化为只保留有已支付订单的用户。

不能靠简单追加 `OR o.id IS NULL` 修复所有“只有非支付订单”的情况。

**追问 3：`COUNT(*)` 与 `COUNT(orders.id)` 对补出的空关联行如何计数，需要什么索引支持查询？**

COUNT(*)会把未匹配的补 NULL 行计为 1，COUNT(o.id)为 0，符合要求。

可考虑 orders 上的 `(user_id,status)` 联合索引，id 作为 InnoDB 主键已在二级索引中；最终还需比较数据量和连接计划。

### 6. 如何查询“从未下单”的用户，并避免 `NULL` 或一对多关联造成漏查、重复？

表结构：`users(id BIGINT PRIMARY KEY)`、`orders(id BIGINT PRIMARY KEY, user_id BIGINT NULL)`。

订单表可能含有多条属于同一用户的记录，也可能含有 `user_id` 为 `NULL` 的记录。查询所有从未关联任何订单的用户 ID。

可用相关 NOT EXISTS 直接表达没有订单：
```sql
SELECT u.id
FROM users AS u
WHERE NOT EXISTS (
  SELECT 1 FROM orders AS o WHERE o.user_id = u.id
);
```
或使用反连接写法：
```sql
SELECT u.id
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
WHERE o.id IS NULL;
```
两者都只返回没有匹配订单的用户，不会因同一用户有多笔订单而产生“未下单”重复行。

**追问 1：分别使用 `NOT EXISTS` 和 `LEFT JOIN` 编写查询，为什么结果中每个用户只应出现一次？**

NOT EXISTS 对每个用户判断一次存在性；LEFT JOIN 有匹配订单的行全部因 o.id 非 NULL 被过滤，只剩每个未匹配用户的一条补 NULL 行。用非空订单主键判断，比任意可空业务字段更可靠。

**追问 2：改用 `NOT IN` 时，子查询中的 `NULL` 会怎样影响结果？**

若 `NOT IN (SELECT user_id FROM orders)` 的集合含 NULL，某个本应不匹配的用户也可能得到 UNKNOWN 而被 WHERE 排除。

可过滤子查询 NULL，但本题 NOT EXISTS 语义更直观，避免把未知值当成不存在。

**追问 3：应为关联条件创建什么索引？如何判断执行计划是否避免了不必要的重复扫描？**

为 orders.user_id 建立索引，便于按用户快速验证是否存在。

通过 EXPLAIN 检查半连接/反连接转换及访问类型，受控实际执行观察 loops 与扫描量；不要假设每个用户都一定全表扫描，也不能只看到子查询就认为必慢。

### 7. `IN`、`EXISTS`、`NOT IN` 与 `NOT EXISTS` 如何按语义和执行计划选择？

IN 判断值是否属于集合，EXISTS 判断子查询是否至少返回一行；NOT IN 和 NOT EXISTS 分别是否定成员关系与否定存在性。存在 NULL 时三值逻辑使两种否定不总等价。

优化器可能把不同写法转换成相似执行方式，所以选择应先保证语义，再比较计划。

**追问 1：先从存在性与成员关系解释 `IN`、`EXISTS` 的语义，而不预设哪个执行更快。**

IN 的子查询返回的值参与比较，EXISTS 通常只关心有没有行，SELECT 列表写 1 还是其他常量不改变存在性。

相关 EXISTS 可用索引在发现首个匹配后停止，但优化器也可能采用其他转换。

**追问 2：子查询包含 `NULL` 时，`NOT IN` 为什么需要单独分析？`NOT EXISTS` 怎样表达“没有匹配行”？**

当集合中含 NULL 且没有明确相等项时，NOT IN 可能为 UNKNOWN；NOT EXISTS 则检查关联条件是否产生实际匹配行，NULL 是否匹配由该条件决定。处理可空列时要写清业务语义，而不是无条件替换。

**追问 3：相同结果的两种写法，应怎样结合优化器转换、索引与数据量比较执行成本？**

比较半连接、反连接、物化、索引查找和实际行数，使用真实参数及规模。

不要背“小表用 IN、大表用 EXISTS”作为绝对规则；现代优化器转换、相关性和 NULL 限制都会改变执行成本。

### 8. `UNION` 与 `UNION ALL`、`DISTINCT` 与 `GROUP BY` 分别在什么情况下产生相同或不同的结果？

UNION 默认对合并结果去重，UNION ALL 保留全部行；DISTINCT 对 SELECT 投影去重，GROUP BY 把记录分组并可计算聚合。

结果相同需要满足具体字段和重复条件，排序则必须单独由 ORDER BY 表达。不要把去重顺便产生的顺序当成稳定输出。

**追问 1：去重、分组聚合和结果排序应怎样区分？**

两个来源可能有相同行时，UNION ALL 会保留重复，UNION 会合并；GROUP BY 加 SUM 后输出的是聚合值，不等于 DISTINCT 原行。

明确去重键很重要：只按用户去重与对全部字段组合去重不是一回事。

**追问 2：选择哪种写法会增加临时表或排序成本？**

去重、分组和排序可能使用临时结构、排序或索引优化，UNION ALL 通常省去全局去重成本，但完整查询仍可能因 ORDER BY 等产生额外工作。

是否落盘取决于数据量、行宽和配置，不是出现 DISTINCT 就必然磁盘排序。

### 9. 用 SQL 查询每个部门最高的三个不同薪资档位，并返回这些档位的所有员工。

采用 MySQL 8.0 及以上版本，表结构为 `employee(id PRIMARY KEY, dept_id NOT NULL, salary DECIMAL(12,2) NOT NULL)`。

一个部门的薪资示例：

```text
id  dept_id  salary
1   10       20000
2   10       20000
3   10       18000
4   10       16000
5   10       16000
6   10       15000
```

要求适用于所有部门，不仅处理示例部门。

本题要前三个不同薪资档位并保留同档所有员工，应使用 DENSE_RANK：
```sql
WITH ranked AS (
  SELECT id, dept_id, salary,
         DENSE_RANK() OVER (
           PARTITION BY dept_id ORDER BY salary DESC
         ) AS salary_rank
  FROM employee
)
SELECT id, dept_id, salary
FROM ranked
WHERE salary_rank <= 3
ORDER BY dept_id, salary DESC, id;
```
示例部门返回员工 1、2、3、4、5，不返回薪资 15000 的员工 6。

**追问 1：`ROW_NUMBER`、`RANK` 与 `DENSE_RANK` 怎样处理并列记录，本题应如何选择？**

ROW_NUMBER 每行分配不同序号；RANK 并列同名次但后续跳号，例如 1、1、3、4；DENSE_RANK 并列同档且不跳号，例如 1、1、2、3。

题目明确不同薪资档位，因此不能用 ROW_NUMBER 截三行，也不应使用会跳档的 RANK。

**追问 2：如果需求变为“每个部门最多返回三位员工”，应怎样处理并列并保证结果稳定？**

改为 `ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC, id)` 后取序号<=3。

- id 作为唯一稳定次序处理同薪资，示例返回 1、2、3。
- 必须确认这种并列取舍符合业务，而不是数据库随意选三个人。

### 10. 如何根据以下简化执行计划，确定慢查询下一步应验证什么？

给定查询：

```sql
SELECT id, amount
FROM orders
WHERE tenant_id = 10 AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

为练习提供下列简化计划片段；表含上述字段，但未给出完整索引定义与数据分布：

```text
type: ALL
key: NULL
rows: 1000000
filtered: 2.00
Extra: Using where; Using filesort
```

请先提出需要补充的信息，再判断可能的改进方向。不要把计划片段当成已经证明的根因。

该片段提示估算全表扫描并进行过滤和额外排序，但尚不足以证明唯一根因。

- 先取 SHOW CREATE TABLE、完整索引、实际参数、数据分布和运行耗时；
- 候选方案是围绕 `(tenant_id,status,created_at)` 形成等值前缀加有序扫描，必要时评估是否把 amount 纳入覆盖，但不能只凭片段立即上线索引。

**追问 1：`type`、`key`、`key_len`、`rows`、`filtered` 与 `Extra` 各自表示什么？该片段缺少哪些信息，哪些数值只是估算？**

type 表示访问方式，ALL 通常全表扫描；key 为选中索引，key_len 表示使用键的估算长度；rows 是估算读取行数，filtered 是估算过滤后比例，Extra 描述额外步骤。

此处缺少 key_len、候选索引、实际行数、loops 和各阶段耗时；1000000 和 2%都不是已测量事实。

**追问 2：取得表结构、索引定义与数据分布后，应如何设计并验证候选索引？为什么 `key` 不为空或 `key_len` 变大不能单独证明查询已充分优化？**

比较候选索引是否减少扫描、回表与排序，LIMIT 能否提前停止，并评估 amount 覆盖带来的写成本。

key 非空可能只是完整索引扫描，key_len 更大也不代表扫描更少；需要在热点与冷门参数上验证实际耗时及资源。

**追问 3：`EXPLAIN ANALYZE` 与普通 `EXPLAIN` 的执行行为有什么不同？线上运行前应评估哪些扫描、锁等待和资源风险？**

普通 EXPLAIN 主要展示估算计划，EXPLAIN ANALYZE 会实际执行支持的语句并记录运行指标，可能带来真实扫描和等待。

在线上应先评估查询规模、锁语义、超时和系统负载，优先在隔离环境或合适副本验证，不能把 ANALYZE 当成零成本查看。

### 11. `Using filesort` 是否一定表示发生了磁盘排序？

不一定。filesort 表示未直接利用索引顺序完成排序，是一种额外排序处理，可能完全在内存中完成，也可能数据过多后使用磁盘临时文件。名称里的 file 不能直接当作磁盘 I/O 证据。

**追问 1：MySQL 为什么会创建内部临时表？**

内部临时表可用于保存分组、去重、派生结果或集合运算的中间数据，具体是否创建取决于执行计划。

它不同于用户显式 CREATE TEMPORARY TABLE，生命周期及管理方式也不同。

**追问 2：`ORDER BY`、`GROUP BY`、`DISTINCT` 与 `UNION` 分别可能引入哪些额外处理？**

ORDER BY 可能额外排序，GROUP BY 需要分组聚合，DISTINCT 和 UNION 需要去重；索引、流式执行和优化器转换可减少部分工作。

应看实际临时表、排序合并和磁盘指标，优化行宽、过滤和索引，而不只加大内存参数。

### 12. `LIMIT` 深分页为什么会随偏移量增大而变慢？

`LIMIT offset,size`通常仍需找到并跳过前 offset 条符合条件的结果，再返回 size 条；偏移越大，扫描、排序或回表工作可能越多。

返回 20 行并不代表只处理 20 行，因此深分页不能仅通过减少页面大小解决。

**追问 1：如何结合索引、查询改写或分页方式降低扫描成本？**

优先使用稳定排序键的游标分页，从上页末尾继续定位；必须支持跳页时可先在覆盖索引中取主键，再回表取少量结果，减少无用回表但不消除偏移扫描。

对极深历史页可限制访问或采用搜索/归档方案，明确一致性和排序要求。

### 13. 按 `created_at`、id 降序排列订单时，怎样实现稳定的游标分页？

题设：`orders(id BIGINT PRIMARY KEY, created_at DATETIME NOT NULL)`，已有联合索引 `(created_at, id)`。

当前页最后一条记录为：

```text
created_at = 2026-01-10 12:00:00
id         = 300
```

要求每页 20 条，排序为 `created_at DESC, id DESC`。写出下一页查询条件，并讨论新增订单对后续页面的影响。

下一页应严格落在复合游标之后：
```sql
SELECT id, created_at
FROM orders
WHERE created_at < '2026-01-10 12:00:00'
   OR (created_at = '2026-01-10 12:00:00' AND id < 300)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```
时间相同用唯一 id 继续排序，索引 `(created_at,id)` 可支撑相应有序访问；最终以计划验证范围与扫描成本。

**追问 1：下一页条件怎样同时处理时间早于游标，以及时间相同但 ID 更小的记录？**

第一部分选择更早时间，第二部分选择同一时间但较小 id，二者互斥且覆盖所有应在下一页的记录。使用严格小于排除上页最后一条，避免重复。

**追问 2：只按 `created_at` 作为游标，或使用非唯一排序条件，可能产生什么遗漏或重复？**

只用时间会跳过与游标同时间但尚未返回的记录；使用<=又可能重复上页记录。

非唯一排序在相同键中顺序不稳定，会让翻页结果漂移，因此需要唯一的次级排序字段。

**追问 3：翻页期间新增数据时，游标分页与固定快照的保证有何不同，业务需要哪一种？**

新插入且排在游标之前的订单不会挤动下一页的偏移，但它们不会自动出现在已经翻过的页面；对排序字段的更新、删除仍可能改变可见集合。

要得到某一时刻固定结果，需快照、固定上界及业务版本等额外机制，游标本身不是全局快照。

### 14. 多表 `JOIN` 的执行顺序、连接条件和索引如何共同影响性能？

关联性能取决于过滤后各表规模、连接顺序、连接算法和索引访问。

- 内连接常可由优化器重排，外连接受保留行语义限制；被驱动表关联键有合适索引可减少重复扫描。
- 多表 JOIN 不是天然禁止项，但缺少选择性和索引的关联可能放大中间结果。

**追问 1：优化关联查询时，应如何验证瓶颈而不是只增加索引？**

先检查实际 SQL 和返回行数，比较估算与实际 loops、各表过滤选择性、关联列类型/排序规则及索引。

- 消除意外笛卡尔积、N+1 和重复行，再考虑索引、预聚合或查询拆分。
- 拆成多次应用查询也有网络和一致性成本，不能默认更快。

### 15. 批量插入或更新大量数据时，如何控制事务规模与数据库压力？

批量操作减少往返和提交开销，但批次过大会长时间占锁、积累日志并增加失败回滚成本。

应按行大小、索引数量、执行耗时及复制压力确定批次，使用稳定键推进进度，并设置超时和重试边界。批次大小不是固定背一个 1000 即可。

**追问 1：索引维护、锁持有和批次大小应如何权衡？**

索引越多写维护越重，随机更新可能触及很多页；长事务会扩大锁冲突和副本应用延迟。

可按主键顺序批量、减少无效更新、控制事务持续时间，观察每批耗时与资源动态调整。进度记录和幂等应防止失败重跑造成重复业务效果。

### 16. 遇到唯一键冲突时，普通 `INSERT`、`INSERT ... ON DUPLICATE KEY UPDATE` 与 `REPLACE` 有什么区别？

普通 INSERT 遇到唯一冲突会报错；ON DUPLICATE KEY UPDATE 在冲突时执行指定更新；REPLACE 在冲突时具有删除旧行再插入新行的语义，不是普通原地更新。

是否允许改变旧值、保留旧 id 和触发关联动作，决定应该选择哪种写法。

**追问 1：它们分别如何处理已有记录、未指定字段和受影响行数？**

普通 `INSERT` 遇到唯一键冲突会报错，不更新旧行；

- `ON DUPLICATE KEY UPDATE` 执行指定更新表达式，未被更新的字段保留；
- `REPLACE` 按新行构造，未提供的字段按默认值规则处理，可能失去旧字段内容。
- 对单行 `ON DUPLICATE KEY UPDATE`，默认受影响行数为：新增 1、实际更新旧行 2、赋回相同值 0；连接启用 `CLIENT_FOUND_ROWS` 时，无变化的情况可返回 1。
- `REPLACE` 的计数是删除行数加插入行数，多个唯一键分别冲突不同旧行时，结果可能大于 2。因此不能把受影响行数直接当成新增业务记录数。

**追问 2：删除后插入与原记录更新，对自增 ID、外键和触发器可能产生什么不同影响？**

REPLACE 可能重新分配自增 id、触发删除与插入相关触发器或外键动作；若多个唯一键冲突，还可能涉及多条旧记录。

- ON DUPLICATE 也可能消耗自增申请但语义不同。
- 必须根据业务身份和审计要求选择，不能为了省一个异常处理用 REPLACE 覆盖订单。

**追问 3：业务只允许第一次请求生效时，哪种写法可能意外改变已存在的数据？如何结合唯一键设计幂等语义？**

“第一次请求生效”通常应使用唯一业务键加普通 INSERT，冲突后核对原请求和结果。

无条件 ON DUPLICATE 更新或 REPLACE 会改变第一次结果，破坏幂等语义；相同幂等键带不同参数应拒绝或明确报冲突。

### 17. 从千万级表导出数据时，普通一次性查询、流式读取与分批读取各有什么风险？

一次性读入全部结果容易耗尽应用内存和网络缓冲；流式读取降低峰值内存，但可能长时间占连接、快照和事务；分批读取释放资源更及时，却要处理并发变化和断点一致性。

选择取决于是否要求固定时点数据和允许多长导出时间。

**追问 1：数据库扫描、网络传输、客户端缓冲和事务持续时间分别怎样控制？**

只查必要列，使用稳定唯一键分批，限制每批与总体超时，并记录进度。

- 流式结果要及时关闭，处理方慢时施加背压；需要严格一致导出时采用明确快照或专门备份方案，并评估 undo 保留。
- 不能一边跨事务随意 OFFSET 翻页，一边宣称结果是单一快照。

### 18. 如何在持续读写的大表上新增字段或索引，尽量减少业务停顿？

先确认目标变更在 MySQL 8.4 及当前表结构上支持哪种 DDL 算法，评估表大小、磁盘、复制和长事务，选择低风险窗口并设置等待/超时策略。

在线 DDL 只是允许某些并发，不等于全过程无锁、无额外空间和无复制影响。

**追问 1：在线 DDL 不同算法、元数据锁和额外磁盘空间需要怎样评估？**

INSTANT 尽量只改元数据，INPLACE 由引擎执行且可能重建数据，COPY 通常通过复制到新表完成；即使允许并发 DML，开始或结束阶段仍可能需 MDL。

先清理或协调长事务，监控临时空间、在线日志和副本延迟。

**追问 2：操作失败或复制延迟扩大时如何止损？**

在等待阶段可取消 DDL 减少排队；已执行大量工作时取消也可能需要清理和回滚时间。

- 按阈值停止放量或延后变更，保护空间和复制，不随意 kill 正在执行重要业务的全部连接。
- 需要明确失败后旧结构是否仍有效，并验证业务恢复。

**追问 3：以 MySQL 8.4 为例，`INSTANT`、`INPLACE` 与 `COPY` 分别适用于哪些变更？它们是否都意味着完全不加锁或不重建数据？**

支持条件满足时添加/删除部分列等可使用 INSTANT；增加普通二级索引等常可 INPLACE，但有实际扫描构建；某些字段类型变更需 COPY 或其他重建路径。

具体能力受行格式、索引和变更组合限制，显式指定算法可避免意外降级，不支持就应报错后重新规划。

## 8. 主从复制与读写分离

**本节问题**

- [1. MySQL 主从复制如何传递并应用已提交事务？](#1-mysql-主从复制如何传递并应用已提交事务)
- [2. 读写分离遇到复制延迟时，如何满足业务的写后读一致性要求？](#2-读写分离遇到复制延迟时如何满足业务的写后读一致性要求)
- [3. `GTID` 与基于 `binlog` 文件位置的复制定位有什么区别？](#3-gtid-与基于-binlog-文件位置的复制定位有什么区别)
- [4. 主库故障切换时，如何选择新主库、隔离旧主库并重新路由应用连接？](#4-主库故障切换时如何选择新主库隔离旧主库并重新路由应用连接)
- [5. 全量备份与 `binlog` 如何配合恢复到指定时间点？](#5-全量备份与-binlog-如何配合恢复到指定时间点)

### 1. MySQL 主从复制如何传递并应用已提交事务？

主库将已提交事务的变更组织到 binlog，副本连接主库接收日志并写入 relay log，再由应用线程按复制规则执行到副本数据。

接收和应用是不同阶段，副本可能“日志已收到但数据尚不可见”。主从复制不是每次查询从主库拉取完整表。

**追问 1：`binlog`、relay log、日志接收与日志应用分别发生在哪一段链路？**

binlog 在主库，relay log 在副本；接收线程负责传输，应用线程或并行 worker 负责执行事务。

并行复制也要遵守依赖和提交顺序等规则，不能把更多 worker 等同于任意事务都可并发。

**追问 2：主库确认提交、从库收到日志与从库应用完成，是不是同一个时间点？**

不是。主库提交确认、远端日志保存和远端事务应用可能依次发生并相隔较长时间。

读写分离若只检查连接正常而不检查复制进度，写后读仍可能看到旧值。

**追问 3：异步复制与半同步复制的确认边界有什么不同，会怎样影响写入延迟和故障后的数据风险？**

异步复制通常不等待副本确认；半同步在配置的等待点要求一定副本确认日志接收/持久保存等边界，不等于等待副本完成 SQL 应用。

半同步增加网络等待，也可能超时退化，需检查配置、状态和故障切换策略，不能一概宣称零丢失。

### 2. 读写分离遇到复制延迟时，如何满足业务的写后读一致性要求？

按请求的一致性要求路由：刚写后的关键读取可读主库；也可携带提交位置或 GTID，等待副本追到该进度后再读；普通展示允许短暂延迟则读副本。

固定 sleep 一段时间只能降低概率，不能保证复制一定追平。

**追问 1：刚写入后立即读取，从库可能处于什么状态？**

副本可能未收到事务、收到但未应用，或应用被大事务/锁/I/O 阻塞。

因此主库返回成功后立即读副本，可能查不到新订单或读到旧状态，不能当成写入失败。

**追问 2：关键请求读主库、等待复制进度与接受延迟展示，分别需要什么业务前提？**

关键请求读主库成本较高但简单；等待位点需有超时及回退；最终一致展示应明确“处理中”或刷新语义。

必须在同一选中副本上确认进度后读取，避免检查一个节点却从另一个落后节点取数。

**追问 3：怎样避免把所有读请求永久切回主库，又怎样验证写后读要求确实得到满足？**

按会话或业务操作短期粘主，达到已知进度后恢复副本路由；对无强时效要求的查询继续分流。

监控实际写后读失败率、等待时间和主库负载，不能只用整体 Seconds_Behind 类估算当成每个事务的确定证明。

### 3. `GTID` 与基于 `binlog` 文件位置的复制定位有什么区别？

文件位置复制用 binlog 文件名和偏移表示读取进度，切主时需要映射不同服务器日志位置；GTID 为事务提供跨复制拓扑可识别的标识，副本维护已执行集合，便于自动定位缺失事务。

GTID 简化定位，不自动解决数据冲突或任意误删。

**追问 1：发生主从切换或重新接入副本时，怎样判断哪些事务已经执行，哪些还需要补齐？**

比较候选节点的 executed/retrieved 等 GTID 集合及日志可用范围，缺失事务若源仍保留可继续同步；已被清理的缺口可能需要重新备份恢复。

不要把两个节点“最大事务号相同”简单当成集合相同，更不能随意跳过失败 GTID 掩盖数据差异。

### 4. 主库故障切换时，如何选择新主库、隔离旧主库并重新路由应用连接？

故障切换要先确认故障与可达多数/控制面判断，再选择数据进度合适的副本，隔离旧主防止双写，提升新主并让其他副本跟随，最后更新应用路由和连接。

恢复可写只是其中一步，已确认事务的保留程度取决于复制及持久化保证。

**追问 1：怎样判断候选副本的复制进度，并评估尚未同步的事务？**

比较副本已接收和已执行事务、剩余日志、故障前确认边界，尽可能补齐可获取事务。

副本最容易连接不代表数据最新；无法确认的事务要形成明确风险范围与后续核对计划。

**追问 2：为什么必须隔离旧主库，怎样处理应用连接与路由缓存？**

旧主可能只是网络隔离而仍能接收写入，不隔离就会形成分叉。

通过网络、代理、只读/权限或基础设施 fencing 等可靠措施防止其继续写；应用连接池要重新建连并刷新路由，同时处理提交结果未知的请求。

**追问 3：恢复可写后，应怎样校验一致性，而不是把切换成功当成零数据丢失？**

检查复制拓扑、GTID 差异、关键业务流水、唯一约束和应用错误，必要时对账修复。

旧主恢复后不能直接当新主合并写入，应作为受控数据源核对后重建或重新加入。高可用流程不能替代备份与恢复演练。

### 5. 全量备份与 `binlog` 如何配合恢复到指定时间点？

先恢复一份一致的全量备份，再从备份对应的 binlog/GTID 位置按事务顺序重放增量，停止在目标时间或事务边界之前。

恢复准确性依赖备份一致点、日志完整性和事务边界，不能只用模糊时间截掉一段日志就保证结果正确。

**追问 1：误删发生后，如何保护现场、定位恢复边界，并在隔离环境验证结果后再切换？**

误删后保护备份和 binlog，限制进一步破坏，记录语句、时间、GTID 与影响范围；在隔离实例恢复并校验关键表及业务不变量，再决定提取数据回补或切换。

避免直接在生产全量回放产生重复事件，也不要覆盖唯一仍有证据的实例。

## 9. 分库分表

**本节问题**

- [1. 如何判断是否需要分库分表，并选择合适的拆分方式与分片键？](#1-如何判断是否需要分库分表并选择合适的拆分方式与分片键)
- [2. 按用户 ID、商家 ID、时间范围或哈希分片，各会产生什么查询与扩容特征？](#2-按用户-id商家-id时间范围或哈希分片各会产生什么查询与扩容特征)
- [3. 分库分表后，跨分片 `JOIN`、聚合、排序与分页为什么更困难？](#3-分库分表后跨分片-join聚合排序与分页为什么更困难)
- [4. 分库分表后，业务没有携带分片键时如何定位目标数据？](#4-分库分表后业务没有携带分片键时如何定位目标数据)
- [5. MySQL 分区表与应用层分库分表有什么区别？](#5-mysql-分区表与应用层分库分表有什么区别)

### 1. 如何判断是否需要分库分表，并选择合适的拆分方式与分片键？

先识别瓶颈：不合理 SQL 可先优化，读压力可用索引、缓存或副本，单点容量及写入无法满足时再考虑拆分。垂直拆分按业务或字段分离，水平拆分按记录分散。

分片键应让主要访问落在少数分片，并兼顾数据与流量分布。

**追问 1：性能瓶颈来自数据规模、单点写入还是不合理查询，怎样先区分？**

看工作集、索引大小、存储增长、CPU/I/O、锁和热点查询；数据千万行不是自动分表阈值。

一个低效查询扫全表，与单节点确实无法承受正常写入，需要不同措施。

**追问 2：水平拆分与垂直拆分分别改变什么，分片键应服务哪些主要访问路径？**

垂直拆分减少业务耦合或行宽，水平拆分分摊同类记录；用户型查询可按用户分片，商家型交易则需考虑商家热点。

分片键最好稳定，不应频繁更新，也要规划无键查询和跨实体事务。

**追问 3：拆分带来的跨片查询、事务和运维复杂度，是否值得当前业务承担？**

拆分增加全局 ID、跨片查询、事务、扩容迁移和运维成本。

只有收益确实超过复杂度，且具备路由、监控、备份和迁移能力时才值得实施；不以“架构显得高级”为理由提前分库分表。

### 2. 按用户 ID、商家 ID、时间范围或哈希分片，各会产生什么查询与扩容特征？

按用户或商家分片便于聚合其业务数据，但大用户可能形成热点；按时间范围便于归档与裁剪，却可能使最新分片承受主要写入；哈希分布较均匀，但范围查询和扩容路由更复杂。方案应匹配主要查询，而不是一味追求记录数平均。

**追问 1：主要查询是否携带分片键，时间归档和随机分布会怎样影响跨片访问？**

查询带分片键可直接路由，不带则可能散发查询。时间归档适合范围分片；哈希可以分散新写入但跨时间扫描需访问多片。

复合或二级路由可以折中，同时要控制分片数量和查询放大。

**追问 2：热点商家或大用户的数据集中时，怎样判断是容量倾斜还是流量倾斜，并选择处理方式？**

容量倾斜看数据量，流量倾斜看 QPS、热点键及耗时，两者不一定一致。

大商家可独立分片或进一步子分片，读热点可缓存和副本分担，单记录写热点则要改变业务串行化方式，不能只把整库平均分开。

### 3. 分库分表后，跨分片 `JOIN`、聚合、排序与分页为什么更困难？

跨片 JOIN 需要跨节点搬运和匹配数据，聚合需要合并局部结果，排序分页需要各片取候选再归并；网络、部分失败和一致性快照都增加复杂度。局部索引再好，也不能消除全局查询的协调成本。

**追问 1：如何在查询能力、实时性和系统复杂度之间选择方案？**

优先让高频事务和查询按分片键收敛；跨业务报表可用 CDC 到搜索或分析库；小规模跨片查询可由中间层并行与归并，但设置范围和超时。

预聚合与冗余提高读效率却引入延迟和校验成本，应明确可接受一致性。

### 4. 分库分表后，业务没有携带分片键时如何定位目标数据？

可选全分片查询、辅助路由表、从 ID 中解析路由信息，或用搜索索引定位分片。

- 全扫描简单但放大请求，辅助映射更快却需要维护一致性，搜索定位适合复杂维度但可能延迟。
- 常见做法是主业务 ID 与路由设计一起规划，而不是上线后再补猜测。

**追问 1：全分片扫描、辅助路由表与搜索索引分别怎样找到目标记录？**

全分片扫描向所有分片查询并合并；路由表把业务键映射到分片；搜索索引返回记录 ID 及分片键，再去权威存储确认。返回搜索结果并不等于已经读取最新主数据。

**追问 2：辅助映射滞后或失效时，怎样避免错路由或无法查询？**

映射写入需与主数据变化协调，可用同事务记录、可靠事件或版本校验；迁移期间保留旧新路由版本及重定向，失效时有限回查或修复。不能在映射未找到时立刻断言业务记录不存在。

**追问 3：全局唯一约束和业务幂等应放在哪一层保证，为什么不能只依赖各分片的局部唯一键？**

如果同一业务键可能落不同分片，局部唯一键无法阻止跨片重复。

可以用确定性路由让同键到同片，或使用集中唯一登记服务/表等协调；幂等键与业务写入还必须保证原子边界。全局约束会产生新的可用性和容量成本。

### 5. MySQL 分区表与应用层分库分表有什么区别？

MySQL 分区表由单个数据库实例内部把一张逻辑表分成多个分区，优化器可做分区裁剪，便于部分数据维护；应用分库分表把数据路由到多个表或实例，可分担存储和计算。

分区表并不天然把负载横向分散到多台数据库服务器。

**追问 1：两者分别在哪个层面裁剪数据、分散存储或分担计算，为什么不能混为一谈？**

分区裁剪减少访问某些分区，分库分表通过独立实例分散资源，但增加跨节点查询和事务成本。

MySQL 分区还受唯一键必须包含分区表达式所用列等约束；不能把分区功能当成无改造的全局分布式数据库。

## 要点回顾

- 字段与索引共同影响访问成本：类型、字符集、行宽、主键和联合索引应围绕实际查询设计，而不是只比较理论容量。
- 事务可见性、加锁范围与持久化是不同维度：分析并发 SQL 时，需要同时明确隔离级别、访问路径、执行顺序和事务边界。
- 优化与扩展都要验证结果：索引存在不等于扫描量小，采用主从复制不等于所有副本立即可见最新写入，分库分表也会增加查询与迁移成本。
