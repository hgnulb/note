### 1. Spring 中的控制反转与依赖注入怎样改变对象创建和依赖管理？

控制反转是把对象创建、装配和生命周期管理交给容器；依赖注入是容器把对象所需的协作者传进去，而不是业务对象自行查找或创建。

- 它让业务依赖抽象、配置负责选择实现，也便于替换测试依赖。
- IoC 不等于不再使用 new，而是把创建职责从业务调用处集中到容器及配置边界。

**追问 1：手工 `new` 的对象与交给容器管理的 Bean，在依赖注入和代理增强方面有什么区别？**

普通 new 出来的对象通常不经过 Spring 的注入、后置处理和代理创建流程，即使类上有 `@Transactional` 或 `@Autowired`，也不会因此自动生效。

容器管理的 Bean 可能被注入依赖并最终以代理形式暴露；业务应取得和调用容器提供的对象，而非绕过它另建实例。

### 2. Spring 的容器、AOP 与模板类分别体现了哪些设计模式？

Spring 用工厂及注册表思想统一管理对象，用代理模式承载 AOP，用模板与回调分离通用流程和业务步骤。

- 设计模式的价值在于把稳定基础设施与变化点分开，而不是给每个类强行贴一个模式名称。
- 框架中的单例是每容器、每 Bean 定义的共享实例，不是全 JVM 绝对只有一个对象。

**追问 1：选两个实际使用过的例子，说明它们如何减少重复代码或支持扩展。**

可以举 `JdbcTemplate`：统一取得和释放连接、执行语句、转换异常，调用方只提供 SQL、参数或结果映射；再举事务代理：调用前开启或加入事务，调用后提交或回滚，业务方法聚焦业务规则。

面试中应说明自己确实使用过的部分，不应编造阅读源码或项目经历。

### 1. 构造器注入、Setter 注入和字段注入有什么区别？

构造器注入在对象创建时满足必需依赖，可使用 final 字段，便于直接实例化测试；Setter 注入适合可选或可重新配置依赖；字段注入简洁，但隐藏构造条件，单测替换也不如显式构造方便。

依赖过多往往提示类职责过大，不能仅换注入方式掩盖设计问题。

**追问 1：服务必须依赖支付组件才能工作，并需要方便编写单元测试时，选择哪种注入方式？**

这个场景优先选择构造器注入：支付组件缺失时对象无法成功创建，依赖关系在构造签名中清晰可见，测试可以直接传入替身，不需要启动 Spring 或反射修改字段。

只有一个构造器时，现代 Spring 通常不需要显式写 `@Autowired`。

**追问 2：依赖变成可选、需要分阶段配置，或存在循环依赖时，选择依据会怎样变化？**

可选依赖可使用明确的可选参数、ObjectProvider 或 Setter，并规定缺失行为。分阶段配置要防止未完成初始化就对外暴露。

循环依赖应先拆分职责、抽取第三方协作或使用事件，不应仅把构造器改成字段注入就认为架构问题已解决。

### 2. 同一接口有多个 Bean 实现时，`@Autowired` 如何确定注入对象？

`@Autowired` 先根据类型寻找候选，再结合限定符、主候选等规则选择；单值注入无法确定唯一候选时会失败。

按名称匹配等具体兜底行为还与注入点和版本有关，不能把它简单解释成“始终先按名字找”。重要依赖应显式表达选择规则。

**追问 1：当同一接口注册了多个实现时，仅按类型注入为什么可能产生歧义？**

同一个 Payment 接口有支付宝和微信两个 Bean，仅凭 Payment 类型无法知道业务需要哪一个。

此时新增实现可能暴露原本隐含的假设；这是装配歧义，不是组件扫描“随机选错”。

**追问 2：`@Qualifier`、`@Primary` 以及注入 `List<T>` 或 `Map<String,T>` 分别适合哪些场景？**

`@Qualifier` 缩小候选范围，适合明确某个渠道；`@Primary` 标记单值注入的优先候选；注入 `List<T>` 获得全部匹配实现，`Map<String,T>` 通常以 Bean 名称作为键。

集合注入可以构造策略注册表，但对业务渠道编码应建立明确映射。

**追问 3：新增一个实现后原有注入失败，应如何检查候选 Bean、限定条件和实际选择结果？**

检查实际注册的 Bean 名称、类型、profile、条件装配、Qualifier 和 Primary，确认是否重复扫描或自动配置增加了候选。

对选择规则写容器测试；不要依赖定义顺序，更不要为了消除歧义随意删除正确实现。

### 3. `@Component` 扫描、`@Bean` 方法与 `@Import` 分别如何向容器注册对象？

`@Component` 通过扫描识别业务组件；`@Bean` 通过配置方法创建和注册对象，适合第三方类或复杂构造；`@Import` 显式导入配置、普通组件，或借助选择器和注册器扩展注册。

它们最终都形成容器能够管理的 Bean 定义，但发现方式不同。

**追问 1：第三方类没有组件注解时如何管理？**

在配置类中声明 `@Bean`，由方法调用第三方构造器或工厂完成配置，再交给容器管理。

需要多个实现、不同生命周期时明确 Bean 名称和作用域；不能指望给外部 jar 添加扫描路径就让没有相关定义的普通类自动成为 Bean。

**追问 2：`@Configuration` 与普通配置类中的 `@Bean` 调用应如何理解？**

完整 `@Configuration` 默认通过代理拦截配置类内的 Bean 方法调用，使跨方法引用取得容器对象；

- 普通组件中的 Bean 方法或 `proxyBeanMethods=false` 属于轻量方式，直接调用就是普通 Java 调用，可能创建额外实例。
- 推荐通过方法参数注入依赖，减少对配置类自调用语义的依赖。

### 4. `BeanFactory`、`ApplicationContext` 与 `FactoryBean` 的职责有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| BeanFactory | BeanFactory 是管理和取得 Bean 的核心容器接口 |
| ApplicationContext | ApplicationContext 扩展了它，提供事件、资源访问、国际化和更完整的应用生命周期能力 |
| FactoryBean | FactoryBean 则是一个受容器管理、专门生产其他对象的 Bean |

三者不是同一层次的“不同工厂实现”。

**追问 1：容器负责管理 Bean，与某个 Bean 专门负责生产对象，两者的角色为何不能混淆？**

BeanFactory 管理许多 Bean；FactoryBean 自己是其中一个生产对象的组件，其 `getObject()` 返回产品。

通过普通 Bean 名取得的通常是产品，使用 `&beanName` 可取得 FactoryBean 本身。产品是否单例也由相关契约决定。

**追问 2：应用需要生命周期事件、资源访问等容器能力时，应怎样理解 `ApplicationContext` 与 `BeanFactory` 的关系？**

ApplicationContext 在 BeanFactory 的依赖管理能力之上组织应用环境，常见应用使用它作为入口。

需要发布事件、读取资源或处理上下文关闭时，应使用其相应能力；业务代码仍应优先依赖具体协作者，而不是到处注入整个容器进行服务定位。

### 5. Spring 容器从读取配置到 Bean 可用，会经历哪些主要阶段？

容器先建立环境并读取配置，解析扫描、Bean 方法等形成 BeanDefinition；再执行定义级后置处理、注册实例级后置处理器，随后按作用域和懒加载规则创建对象、解析依赖、初始化并可能生成代理。最后完成上下文刷新并发布相关事件。

不是先把所有类 new 一遍，再统一补注解。

**追问 1：`BeanDefinition` 注册、依赖解析与 Bean 实例化之间是什么关系？**

BeanDefinition 是创建配方，包含类型、作用域、依赖等元数据；依赖解析决定某个注入点对应哪个对象；实例化才真正调用构造器或工厂。

定义已注册不等于对象已创建，对懒加载 Bean 更不能在启动完成时假定已初始化。

### 6. Bean 的实例化、属性注入、初始化与销毁如何衔接？

典型流程是实例化、依赖填充、Aware 等回调、初始化前后处理和初始化回调，最后暴露可用实例或代理；容器关闭时对受完整管理的对象执行销毁。

具体回调由不同扩展组件介入，不能把所有注解行为想象成 Bean 自己自动执行。

**追问 1：实例化、依赖注入、初始化回调与销毁回调分别处理什么？**

实例化创建对象，依赖注入设置协作者，初始化回调使对象具备可用状态。

- 若同时配置且对应不同方法，常见初始化顺序为 `@PostConstruct` → `InitializingBean.afterPropertiesSet()` → 自定义 `initMethod`；
- 销毁时为 `@PreDestroy` → `DisposableBean.destroy()` → 自定义 `destroyMethod`。
- 这些是 Spring 管理下的回调顺序，不是 Java 构造器顺序。
- 单例通常由容器在关闭时销毁；prototype Bean 创建完成后，容器不自动管理其销毁，调用方应承担资源释放责任。

**追问 2：`BeanPostProcessor` 在哪些阶段介入，返回代理对象时会怎样影响后续使用？**

BeanPostProcessor 可以在初始化前后处理实例；自动代理通常在初始化后包装，也可能为循环依赖提前提供引用。

调用方取得的可能是代理而非原始对象，因此依赖注入后的业务调用需要基于对外暴露对象理解。

**追问 3：某个初始化步骤失败时，怎样判断对象是否已经能够被业务安全使用？**

初始化失败通常使该 Bean 创建失败，甚至导致上下文启动失败，不能把早期暴露引用当成已可安全服务。

初始化期间不要把 this 泄漏给后台线程或全局注册表；资源已部分创建时，需要安排失败清理，只有完整就绪后才对外接流量。

### 7. `BeanFactoryPostProcessor` 与 `BeanPostProcessor` 分别在什么阶段工作？

BeanFactoryPostProcessor 处理 Bean 定义等容器元数据，通常在普通 Bean 实例化之前；BeanPostProcessor 处理已经创建的实例，可注入能力、执行回调或返回包装对象。

前者改变创建配方，后者改变或替换具体成品。

**追问 1：修改 `BeanDefinition` 与包装 Bean 实例有什么区别？**

修改 BeanDefinition 可以影响类、属性、作用域等后续创建规则，不应为此随意提前 getBean。

包装实例则可能加入代理、校验或初始化逻辑；它不会自动修改所有同类 Bean 的定义。

**追问 2：自动代理通常在哪个环节出现？**

代理式 AOP 由自动代理创建器等 BeanPostProcessor 在实例生命周期中介入，通常在初始化后决定并返回代理。

循环依赖需要早期代理引用时，会通过相应早期引用扩展点协调；不能简单说“AOP 在类加载时修改全部字节码”。

### 8. Spring Bean 的常见作用域有什么区别？

常见作用域包括 singleton、prototype，以及 Web 环境的 request、session、application、websocket。

单例适合无请求状态的服务组件，短生命周期状态应归属于请求或明确的数据对象。作用域决定实例共享和生命周期，不替代并发控制。

**追问 1：单例 Bean 是在什么范围内共享，为什么单例不自动等于线程安全？**

singleton 是每个容器、每个 Bean 定义共享一个实例；多个容器或多个定义仍可有多个对象。

单例被多个请求线程同时调用，可变字段仍可能产生竞态，容器不会自动给业务方法加锁。

**追问 2：在单例中保存当前用户或请求临时状态会有什么风险？怎样调整状态归属与生命周期？**

把 currentUser 或临时订单存在单例字段中，会造成跨请求覆盖甚至数据泄漏。

- 优先放在局部变量、显式参数或 request scope 中；必须共享的数据使用并发容器或同步机制。
- ThreadLocal 也需及时清理，不能作为跨异步任务的自动传递机制。

### 9. 单例 Bean 依赖 prototype Bean 时，每次调用都会得到新对象吗？

不会。单例在创建时直接注入 prototype，通常只取得并保存一次该实例，后续调用仍使用它。

prototype 的含义是每次向容器请求该 Bean 时创建，而不是任何持有它的对象每次调用方法都自动替换。

**追问 1：延迟获取对象与直接注入一次有什么不同？**

使用 `ObjectProvider<T>.getObject()`、方法注入或适当 scoped proxy，才能在需要时重新向容器获取。

要明确获取粒度：每个业务操作取一次，与每个代理方法调用取一次，可能有不同的状态保持行为。

**追问 2：如何确认实例的创建和销毁责任？**

容器负责 prototype 的创建、装配和初始化，通常不跟踪其完整销毁生命周期；持有者负责释放其外部资源。

请求作用域和容器单例有对应销毁管理，但仍应验证异常退出和手动创建路径。

### 10. Spring 如何利用三级缓存处理部分循环依赖，为什么还要考虑提前暴露的代理对象？

在允许循环引用的典型 Spring 单例创建流程中，实例构造后可以先注册早期引用工厂；另一个 Bean 注入它时，通过该工厂取得原始或早期代理引用，打破属性注入的递归等待。

通常所说三级缓存分别保存完整单例、早期引用及早期引用工厂。它是特定生命周期协调，不是所有循环都可解决。

**追问 1：两个单例通过属性注入相互依赖时，提前暴露引用怎样打破创建过程的循环？**

A 已构造但尚未填充 B 时，先暴露 A 的工厂；创建 B 需要 A，取得早期 A 后完成 B，再把 B 注入 A。

前提是已有可暴露的 A 实例，因此不能把这套流程直接用于构造器相互等待。

**追问 2：依赖对象最终需要被代理时，为什么还要保证提前取得的引用与最终暴露对象的关系？**

若 B 持有原始 A，而其他调用方持有带事务等能力的代理 A，会出现行为不一致。

- 早期引用工厂允许代理创建器按需提供同一条对外引用路径，并与最终包装协调。
- 三级结构的重要作用是延迟生成和协调早期引用，而不只是多存一个对象。

**追问 3：构造器循环、prototype 循环和 Spring Boot 禁止循环引用配置下，能否直接套用同一个结论？**

构造器循环尚无对象可暴露，prototype 循环也不能直接套用单例缓存流程。

Spring Boot 2.6 起默认禁止循环引用，具体工程配置仍需检查；允许配置只能解除部分限制，不建议当成长期设计修复。更合理的是拆分职责或打断双向依赖。

- [3. 阅读以下代码，分析通过代理调用 `entry()` 时，哪些调用会经过 AOP 增强。](#3-阅读以下代码分析通过代理调用-entry-时哪些调用会经过-aop-增强)
- [4. 多个切面同时作用于同一个方法时，如何确定执行顺序？](#4-多个切面同时作用于同一个方法时如何确定执行顺序)

### 1. 日志、权限检查、监控等逻辑为什么适合用 AOP 处理？

日志、权限和监控是跨多个业务方法重复出现的横切逻辑，AOP 能统一实现并减少遗漏。

- 但切点范围和执行顺序必须明确，不能把核心业务状态流转隐藏在难以发现的切面里。
- 分析时应说明增强在哪里发生，以及哪些调用不会进入切面。

**追问 1：切面、切点与通知之间是什么关系？**

切面组织一组横切行为，切点选择哪些方法执行连接点需要增强，通知定义增强何时及如何执行，例如前置、返回、异常、最终和环绕通知。

切点匹配到方法，不代表任意 this 自调用都会经过代理。

**追问 2：环绕通知不继续调用目标方法会发生什么？**

环绕通知如果不调用 `proceed()`，目标方法不会执行，适合缓存命中、拒绝访问等明确短路场景。

需要返回与方法契约兼容的结果或抛出正确异常；漏掉 proceed 会造成业务静默不执行，finally 中的资源清理也要由通知自己负责。

### 2. Spring AOP 如何创建代理并执行增强逻辑？

Spring 代理式 AOP 为目标对象创建代理，代理拦截调用并构造拦截器链，执行增强后再调用目标方法。JDK 动态代理基于接口，CGLIB 基于子类。

是否选类代理还受框架配置影响，不能仅凭“实现了接口”断定工程一定使用 JDK 代理。

**追问 1：JDK 动态代理与 CGLIB 分别怎样把调用引入增强逻辑？**

JDK 代理通过 InvocationHandler 接收接口方法调用；CGLIB 生成子类并覆盖可覆盖的方法，把调用引入拦截器。

两者最终都需要执行增强链和目标逻辑，不是每次业务调用重新生成一份代理类。

**追问 2：目标类的接口、方法可见性和 `final` 限制，会怎样影响可代理范围？**

JDK 代理对外暴露接口方法，目标实现方法为 final 不妨碍通过接口代理拦截；CGLIB 不能继承 final 类，不能覆盖 final 或 private 方法。还需考虑方法可见性、模块访问等条件。不要把 CGLIB 的限制错误套在所有代理方式上。

**追问 3：创建了代理后，为什么还必须检查实际调用是否经过该代理？**

代理只能拦截经过自身的调用。手工 new 目标对象、持有原始引用、同类 this 调用都可能绕过增强。

验证时检查实际 Bean 类型、调用来源、切点匹配和代理配置，而不是只看到注解就判断功能生效。

### 3. 阅读以下代码，分析通过代理调用 `entry()` 时，哪些调用会经过 AOP 增强。

题设：启用 Spring 代理式 AOP，切点只匹配 `OrderService.process`，容器中的 `OrderService` 已成功创建代理。以下为业务类片段，外部调用者从容器取得 Bean 后调用 `entry()`。

```java
@Service
public class OrderService {
    public void entry() {
        this.process();
    }

    public void process() {
        // 处理订单
    }
}
```

不使用 AspectJ 编织，也不通过额外机制获取自身代理。

题设中外部调用进入 `entry()` 的代理，但切点只匹配 process，因此 entry 本身没有该增强。

- 进入目标对象后，`this.process()` 是目标对象的普通内部调用，不重新经过代理，所以 process 也不会获得预期增强。
- 这里没有使用字节码编织或自身代理回调，不能假定 Spring 自动重定向 this。

**追问 1：同类内部的 `this.process()` 与外部持有代理调用 process()，调用路径有何区别？**

内部调用直接从目标 entry 到目标 process；外部持有代理调用 process，则先经过匹配的拦截器链再到目标方法。

方法可见性相同，区别在调用路径，不在注解“有没有写对”。

**追问 2：把 process 拆到另一个 Bean 后，增强是否就会按预期执行，还需要哪些前提？**

把 process 放进另一个容器管理的 Bean，并注入其代理，通过该依赖调用，通常可让增强生效。

仍需保证新 Bean 被扫描或注册、切点更新到正确类型、方法可代理，以及调用没有换成手工 new 的实例。

**追问 3：`private`、`final` 方法以及 AspectJ 编织方式，与这里的代理模型有何不同？**

private 方法不是对外代理接口，类代理也不能覆盖它；final 方法不能被类代理覆盖，但接口代理可以在接口调用外侧增强。

AspectJ 编织把增强织入字节码，其连接点与自调用处理能力不同，不能用代理式 AOP 的结论不加区分地解释。

### 4. 多个切面同时作用于同一个方法时，如何确定执行顺序？

通过 `@Order`、Ordered 等明确切面优先级；在可比较的不同切面之间，通常数值越小优先级越高，进入时先执行、退出时后执行。

多个通知形成嵌套链，不是把所有 before 和 after 随机拼接。没有明确顺序的同级行为不应作为业务保证。

**追问 1：环绕通知前后逻辑、异常通知以及权限与事务切面的先后顺序，可能怎样影响结果？**

权限在事务外检查可避免无权请求先开事务；重试若放在事务内，可能反复使用已回滚的事务，通常需要每次尝试有正确的新事务边界。

- 异常通知或环绕通知吞掉异常，会改变外层事务是否判断为失败。
- 应画出进入、proceed、异常和退出的完整顺序来验证。

### 1. `@Transactional` 如何通过代理完成事务开启、提交与回滚？

`@Transactional` 提供事务属性，由代理中的事务拦截器读取，交给选定事务管理器创建或加入事务，执行目标方法后按结果及回滚规则提交或回滚。

数据库真正的 ACID 由数据库机制提供，Spring 负责把调用边界与连接、事务状态协调起来。

**追问 1：调用进入代理时，怎样决定创建新事务还是加入现有事务？**

拦截器根据传播行为和当前事务状态判断，例如 REQUIRED 有事务就加入，没有就创建；REQUIRES_NEW 挂起外层再新建。

还要选择正确事务管理器，检查隔离、超时等属性在已有事务中是否能生效。

**追问 2：目标方法正常返回与抛出异常时，代理依据什么决定提交或回滚？**

正常返回通常提交，但共享事务被标记 rollback-only 时不能正常提交。

异常则按 rollbackFor/noRollbackFor 等规则处理；以未修改默认规则的 Spring 6.1 为例，RuntimeException 和 Error 默认回滚，受检异常默认不回滚。

**追问 3：数据库连接与当前线程怎样关联，为什么普通对象上的同名注解不等于已经具有事务能力？**

常见命令式事务通过 TransactionSynchronizationManager 等将连接资源绑定到当前线程，数据访问组件复用该连接。

注解只有经容器启用相应基础设施、通过代理调用且访问参与该事务的资源时才有作用；响应式事务则使用不同的上下文机制，不能一概说都是线程绑定。

### 2. 事务传播行为与事务隔离级别分别控制什么？

| 机制 | 特点与边界 |
|---|---|
| 传播行为 | 传播行为控制嵌套调用如何参与事务 |
| 隔离级别 | 隔离级别控制并发数据库事务之间的可见性与冲突语义 |

前者是调用组合，后者是数据并发，两者不能相互替代。

例如 REQUIRES_NEW 不等于更强隔离，SERIALIZABLE 也不决定是否加入外层事务。

**追问 1：外层已经有事务时，`REQUIRED`、`REQUIRES_NEW` 与 `NESTED` 分别怎样处理内层调用？**

REQUIRED 加入现有物理事务；REQUIRES_NEW 挂起外层并建立独立物理事务；NESTED 通常在同一物理事务内建立保存点，以支持内层部分回滚。是否支持 NESTED 取决于事务管理器与资源。

**追问 2：外层没有事务时，行为有哪些变化？`NESTED` 的保存点支持还需要检查哪些事务管理器条件？**

没有外层事务时，这三种行为通常都开启新事务。基于 JDBC 的事务管理器可利用保存点支持嵌套，JPA/JTA 等不能不加条件地套用相同能力。

加入已有事务时，内层声明的隔离级别通常不会自动改变外层已开始的物理事务。

### 3. 内层 `REQUIRED` 事务标记回滚后，外层捕获异常并继续提交，会发生什么？

内外层 REQUIRED 共享同一物理事务，内层失败若已将其标记 rollback-only，外层即使捕获异常也不能把该事务重新变成可提交。

外层尝试提交时可能收到 `UnexpectedRollbackException`，这是防止调用方误以为事务已成功，而不是异常捕获语句没生效。

**追问 1：内外层 `REQUIRED` 调用共享什么事务状态，`rollback-only` 表达什么？**

它们共享连接和物理事务结果，rollback-only 表示最终只能回滚。

内层逻辑边界可以独立存在，但不能独立决定同一物理事务的一部分永久提交。

**追问 2：外层已经捕获异常，为什么仍可能在提交时遇到 `UnexpectedRollbackException`？**

catch 只改变 Java 控制流，不撤销事务管理器此前设置的回滚标记。外层方法正常返回时，事务拦截器仍检查事务状态。

还要确认内层确实经过事务代理；普通内部调用抛异常被本方法吞掉，可能是另一种情况。

**追问 3：哪些业务结果应共同回滚，哪些可以独立提交？怎样据此调整事务边界而不只改异常捕获？**

订单与库存等同一数据库内的共同不变量应共同回滚，不能为“避开异常”滥用独立事务。

- 审计等允许独立保存的数据可以放到另一个 Bean 的 REQUIRES_NEW，或用可靠事件设计。
- 先明确成功/失败语义，再选择边界，不是只调整 catch。

### 4. `REQUIRES_NEW` 与 `NESTED` 在物理事务、保存点和失败回滚上有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| REQUIRES_NEW | REQUIRES_NEW 是独立物理事务，内层可以先提交并独立回滚 |
| NESTED | NESTED 通常是在同一物理事务内设置保存点，内层成功只表示越过保存点范围，不等于已经持久提交 |

NESTED 可回滚内层而继续外层，但最终仍服从外层事务结果。

**追问 1：独立物理事务与同一事务中的保存点，在提交时间和回滚范围上有什么区别？**

独立事务有自己的连接、提交时点和隔离属性；保存点只是同一事务的回滚位置。

内层 NESTED 的修改通常要等最外层提交才最终提交，不能用保存点实现真正的跨事务独立可见性。

**追问 2：外层最终回滚时，两种内层操作分别会怎样？**

外层回滚不会撤销已经成功提交的 REQUIRES_NEW；NESTED 的内层修改随整个物理事务一起回滚。

相反，内层 NESTED 回滚到保存点后，外层是否继续由业务决定，仍需正确传播或捕获异常。

**追问 3：并发请求都在外层持有连接后再进入 `REQUIRES_NEW`，连接池为什么可能成为限制？**

外层挂起时通常仍占着连接，内层还需另一条连接。

- 若每个请求都持一条外层连接并等待内层连接，可能形成池耗尽甚至互相等待。
- 应按并发与嵌套深度估算资源、缩短边界，并避免把大量独立事务隐藏在循环调用中。

### 5. 阅读以下事务代码，分别分析原代码和追问中的变体能否按预期回滚。

题设：使用 Spring 代理式声明式事务和同一个关系数据库；事务管理器配置正确。代码中的 `orders.insert()` 使用参与该事务管理器的数据库访问组件。`place()` 本身没有事务。

```java
@Service
public class PurchaseService {
    private final OrderRepository orders;

    public PurchaseService(OrderRepository orders) {
        this.orders = orders;
    }

    public void place() {
        save();
    }

    @Transactional
    public void save() {
        orders.insert();
        throw new IllegalStateException("failed");
    }
}
```

不使用 AspectJ 编织；分别独立分析各变体。讨论默认异常回滚规则时，采用未额外修改规则的 Spring Framework 6.1 配置。

原代码通过代理调用 place 后，在目标内部直接调用 save，绕过 save 的事务拦截。

- place 本身无事务，因此不能因 save 上的注解就保证插入回滚；插入可能已按自动提交完成，随后异常只影响 Java 调用。
- 必须区分“异常抛出了”和“数据库事务已覆盖它”。

**追问 1：外部通过容器取得的代理调用 place 时，save 上的事务注解是否生效？为什么？**

不生效，属于代理式事务的自调用问题。可把事务方法放到单独服务，并通过注入的代理调用，或把合适事务边界放在外部实际调用的方法上；不能依靠改变方法名字解决。

**追问 2：改为外部直接通过代理调用 save 后，`RuntimeException` 会怎样影响数据库更新？**

外部直接经代理调用 save 后，事务会按配置开始，insert 参与该事务；

抛出 IllegalStateException 属于 RuntimeException，按题设 Spring 6.1 默认规则回滚，前提是没有其他独立事务或不支持事务的写入路径。

**追问 3：若 save 内部捕获异常且正常返回，或把异常改为受检异常，回滚行为还需要检查什么规则？**

内部捕获并正常返回且未标记回滚时，通常提交。受检异常在题设默认规则下不触发回滚，需按业务配置 `rollbackFor` 或主动设置回滚状态。

不要使用过宽回滚规则掩盖错误分类，也要避免把异常转换时丢失原始原因。

### 6. 在事务方法中启动多个线程操作数据库，为什么需要重新分析事务边界？

普通命令式 Spring 事务通常绑定当前线程，新线程不会自动继承同一数据库连接和事务。

- 每个异步任务若另开事务，会有独立提交结果；父方法回滚无法撤销子线程已提交的操作。
- ThreadLocal 复制工具也不能安全地把一个 JDBC 事务复制成并行事务。

**追问 1：调用方事务通常绑定在哪个执行上下文，是否会自动传到新线程？**

事务资源绑定在调用线程的上下文，线程池切换会改变执行线程。

即使传递用户 ID、trace ID，也不意味着事务连接已正确传播；JDBC 连接通常不适合由多个线程同时执行一个复杂事务。

**追问 2：多个线程各自写入后，其中一个失败，怎样判断已经提交的范围？**

检查每个任务是否有事务、何时提交、是否使用自动提交和同一数据库。

- 某个 Future 失败只说明该任务返回失败，不表示其他任务已回滚。
- 汇总时必须区分未开始、执行中、已提交、结果未知等状态。

**追问 3：业务要求全部成功或全部失败时，应怎样重新选择执行方式和一致性方案？**

同库强原子要求可把数据库写入集中在单线程本地事务，前置独立计算可以并行；跨服务则选择可靠消息、TCC、Saga 等适合业务的协调。

不能把“等待全部 Future 完成”当作分布式事务提交协议。

### 7. 一个业务方法只有部分操作需要事务时，如何划分事务边界？

事务应覆盖需要共同维护数据库不变量的最小操作集合，纯计算、远程查询和非关键通知尽量放在事务外。

可通过另一个 Bean 的事务方法或 TransactionTemplate 精确包住这段写入；拆分后要重新检查事务外读到的数据是否可能过期，必要时在事务内再次校验。

**追问 1：为什么需要警惕长事务及事务中的耗时远程调用？**

长事务延长锁和连接占用，影响 undo 清理并增加死锁机会；远程调用的超时不可控，还不能随本地回滚自动撤销。

通知可在提交后触发，但要求可靠投递时要使用同事务的消息记录等方案，而不是只把 HTTP 调用移到后面。

### 8. 使用 JDBC 或 `TransactionTemplate` 时，应怎样显式控制事务的开始、提交和回滚？

JDBC 手工事务要关闭自动提交，在同一连接上执行相关操作，成功 commit，失败 rollback，最后恢复状态并释放连接。

TransactionTemplate 则由事务管理器处理这些基础工作，在回调中执行事务业务，异常或 setRollbackOnly 控制回滚。它更适合方法内部只有一小段需要事务的场景。

**追问 1：与 `@Transactional` 相比，编程式事务在哪些细粒度边界中更合适？**

编程式事务让边界在代码块中明确可见，避免代理自调用限制，便于控制多段独立事务；声明式方式更适合稳定的方法级边界，减少样板。

两者都必须避免捕获异常后误提交，也不自动覆盖远程服务。

**追问 2：连接复用前需要恢复什么状态？**

至少关注 autoCommit、readOnly、隔离级别及其他会话设置，连接池通常会做部分重置，但不能假定所有自定义 session 变量都会恢复。

使用框架管理连接时不要擅自 commit/close 破坏其生命周期；直接管理则在 finally 中有序恢复和关闭。

### 9. 事务的只读标记、超时设置和隔离级别分别控制什么？

只读标记用于表达读意图并可能优化驱动、数据库或 ORM 行为；超时限制事务执行预算，具体通过语句超时等机制实现；隔离级别定义并发访问语义。

它们不是三个由 Spring 在任意环境下强制实现的通用开关，实际效果必须落实到资源和事务管理器。

**追问 1：只读标记是否等于在所有数据库上禁止写入？**

不等于。有的管理器只把它当优化提示，有的配置会执行数据库只读事务命令；不同数据库与驱动行为不同。

业务禁止写入还应靠权限、访问边界或数据库约束，不能只依赖 readOnly 注解。

**追问 2：设置是否生效需要检查哪些事务管理器和驱动条件？**

检查是否创建新事务、是否仅加入已有事务、所选事务管理器、驱动超时和数据库隔离支持。

事务超时不意味着外部 RPC 自动取消；多个独立请求的超时也不能直接相加替代整体预算。

### 10. 订单事务提交后再触发通知，如何使用事务事件监听？

可以使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 在相关事务成功提交后处理事件，避免事务未提交就通知外部。

- 但它是进程内的时机协调，不是可靠消息队列；数据库提交后进程立即退出，监听动作仍可能没完成。
- 关键通知应把待发送事件与业务变更写入同一个数据库事务。

**追问 1：普通同步事件、异步事件与 `AFTER_COMMIT` 事务事件的触发时机有什么区别？**

普通事件默认同步在发布线程执行，可能发生在事务中；异步事件转到执行器，启动时机并不自动等待事务提交；AFTER_COMMIT 绑定事务完成阶段。

没有事务时默认不会执行事务监听，除非显式配置 fallbackExecution 等行为。

**追问 2：数据库已经提交，但进程在完成通知前退出，会留下什么结果？**

数据库数据已经生效，通知可能丢失；重启后若没有持久事件记录，系统甚至不知道需要补发。

AFTER_COMMIT 监听若继续写数据库，也应明确新事务边界，不能认为原事务还有一次后续提交机会。

**追问 3：哪些通知允许丢失，哪些需要可靠投递与补偿？为什么仅改变监听时机不够？**

低价值临时统计可接受丢失；订单通知、库存联动等需要持久事件、重试、幂等和告警。

Outbox 等方案让发送失败可恢复，消费者按业务事件 ID 去重。提交后触发只是减少时序错误，不能消除崩溃窗口。

### 11. 测试方法加了 `@Transactional`，是否意味着测试过程中产生的所有数据库写入都会自动回滚？

不意味着。Spring 测试事务通常作用于测试线程及参与同一事务的调用，并常在测试结束回滚；真实 HTTP 服务线程、异步任务或 REQUIRES_NEW 事务可能独立提交。

应按每条写入的执行线程和事务边界分析，不能把测试注解当成整个进程的全局回滚。

**追问 1：测试线程内直接调用服务，与向随机端口启动的服务发送真实 HTTP 请求，事务边界有什么不同？**

测试线程直接调用参与 REQUIRED 的服务，通常加入测试事务；向随机端口发 HTTP 请求时，服务端在另一线程处理，不会继承测试线程的事务，服务提交会真实保留。

MockMvc 是否共享线程也应结合实际调用方式判断。

**追问 2：异步任务或独立事务写入的数据，为什么也需要单独安排测试清理？**

异步任务和独立事务没有被测试事务统一覆盖，可能在测试已结束后继续写入。

需要等待任务结束、显式删除测试数据或重建隔离环境，避免清理后任务又写回数据。

**追问 3：如何设计隔离的数据集和清理机制，避免测试互相污染？**

使用独立数据库或 schema、唯一业务前缀、可重复初始化和清理脚本，集成测试可使用临时容器。不要在多个并发测试中依赖同一自增值或全表删除。

断言不仅检查数据存在，也应验证回滚、重复请求与失败后的状态。

### 1. 控制器如何接收路径参数、查询参数与 JSON 请求体？

路径中的资源标识用 `@PathVariable`，查询参数和常见表单参数用 `@RequestParam`，JSON 请求体用 `@RequestBody` 交给消息转换器反序列化。

- 返回对象使用 `@ResponseBody` 或 `@RestController`，再通过转换器生成 JSON 等响应。
- 绑定解决格式转换，业务约束仍需参数校验和权限检查。

**追问 1：`@PathVariable`、`@RequestParam`、`@RequestBody` 以及返回 JSON 的处理方式有什么区别？**

三者分别从路径、参数集合和请求体取值，不能因为字段同名就随意互换。

`@RequestBody` 依赖 Content-Type 与可用转换器，通常不能把同一个请求体重复读取成多个独立对象；返回 JSON 也应明确字段、状态码和错误契约，而不是把实体对象无筛选暴露。

### 2. 请求进入 Spring MVC 后，如何经过控制器定位、参数绑定、方法执行和返回值处理？

请求先经过 Servlet 过滤器链进入 DispatcherServlet，由 HandlerMapping 找到处理器及拦截器，再由 HandlerAdapter 完成参数解析、方法调用和返回值处理。

- 对象响应由 HttpMessageConverter 写出，视图响应经视图解析渲染；异常交给 HandlerExceptionResolver 等机制。
- 它是可扩展处理链，不是 DispatcherServlet 自己完成所有细节。

**追问 1：`DispatcherServlet` 怎样选择处理器，参数又怎样绑定成方法入参？**

映射根据路径、方法、媒体类型等选择控制器；参数解析器读取路径参数、请求参数或请求体，并进行类型转换和校验。

匹配不到方法、参数格式错误与业务异常发生在不同阶段，响应也应区分。

**追问 2：方法返回对象、直接输出响应或抛出异常时，分别通过什么后续环节处理？**

返回值处理器决定是写 JSON、处理异步结果还是渲染视图；直接写响应需要正确管理提交状态；异常可由 `@ExceptionHandler`、`@RestControllerAdvice` 或默认解析器处理。

已经提交部分响应后，不能再可靠地改写成另一份完整错误 JSON。

**追问 3：过滤器、拦截器与控制器处理分别处于链路什么位置？**

过滤器在 Servlet 层包围请求，可能在确定控制器前运行；拦截器在 MVC 处理器链内，可获得 HandlerMethod 等信息；控制器负责业务入口。

拦截器的 afterCompletion 与过滤器 finally 适合清理，但异步请求的线程切换要单独理解。

### 3. 传统 Spring MVC 应用中的父容器与子容器如何组织 Bean？

传统 Spring MVC 常由根 ApplicationContext 管理 service、repository 等共享组件，由每个 DispatcherServlet 的子 WebApplicationContext 管理控制器和 MVC 配置。

子容器可以查找父容器，父容器通常不能反向查找子容器；同名 Bean 在子容器可遮蔽父容器对象。

**追问 1：哪个方向能够查找对方的 Bean？**

子到父查找适合控制器依赖业务服务；父到子不可见有助于根业务层不依赖某个 Web 入口。

重复扫描同一服务到父子两个容器，可能产生两份实例或事务配置不一致，应明确扫描边界。

**追问 2：与常见 Spring Boot 应用配置有何区别？**

常见 Spring Boot Servlet 应用通常使用统一应用上下文，不必手动复制传统 XML 父子容器布局；特定管理端口、复杂配置等仍可能有上下文层次。

不能因使用 Spring MVC 就断定项目一定有固定的两个容器。

### 4. 过滤器与拦截器在请求链路中的位置和可处理对象有什么区别？

Filter 属于 Servlet 规范，处理请求和响应的底层包装、编码、认证链等；HandlerInterceptor 属于 Spring MVC，在找到处理器后介入，可读取目标方法信息。

过滤器能覆盖不进入 MVC 的资源，拦截器则更贴近控制器调用。选择时看所需信息和必须覆盖的入口。

**追问 1：鉴权、日志与请求处理等需求应如何选择实现位置？**

请求包装、通用跨域和安全过滤链适合过滤器；按控制器注解记录操作信息可用拦截器或 AOP。

- 认证授权优先使用成熟安全框架，避免仅靠 MVC 拦截器遗漏其他路径。
- 日志应包括异常和异步完成，ThreadLocal 等资源必须在正确边界清理。

### 5. 如何统一处理控制器异常并设计稳定的错误响应？

用 `@RestControllerAdvice` 和针对异常类型的 `@ExceptionHandler` 集中映射错误，返回稳定错误码、可理解消息和请求追踪标识。

- HTTP 状态表达协议层结果，业务码表达更细业务原因。
- 保留服务端原始异常链和日志，但不向客户端暴露 SQL、堆栈或凭据。

**追问 1：如何区分参数错误、业务失败和系统异常，而不是所有情况都返回同一个“成功”状态？**

参数格式或校验错误通常对应 400，未认证 401，无权限 403，状态冲突可用 409，限流用 429，系统故障用 5xx。业务拒绝也需按接口契约明确表达。

全部返回 200 会误导监控、重试和调用方；错误响应结构保持一致不等于状态码都相同。

### 6. Spring MVC 如何对请求参数与嵌套对象进行校验，并返回可定位字段的错误信息？

在请求 DTO 字段上声明约束，在控制器参数上触发 Bean Validation；嵌套对象使用 `@Valid` 级联，并对不同业务阶段使用分组。

- 统一异常处理把字段路径和规则失败映射成稳定响应。
- 格式转换错误、字段校验和业务规则失败应分层处理，不能只加一个注解就替代全部检查。

**追问 1：`@Valid`、`@Validated`、嵌套对象校验与分组校验各适合什么需求？**

`@Valid` 是标准级联校验标记；Spring 的 `@Validated` 可选择校验组，并用于某些方法校验入口。

嵌套对象需要在引用或容器元素处声明级联；新增和更新的不同必填规则可分组，但复杂业务条件宜使用明确业务校验。

**追问 2：请求体字段校验与服务方法参数校验的调用位置有什么区别？请说明 Spring 版本及代理条件。**

请求体对象校验发生在 MVC 参数解析过程中；服务方法校验通常由方法校验基础设施在调用边界处理。

- Spring 6.1 增加 MVC 内建方法校验能力，与类级 `@Validated` 代理路径不能混淆。
- 需要固定版本，确认是代理拦截还是 MVC 原生机制，避免自调用绕过。

**追问 3：校验失败时，如何返回字段路径、错误原因和稳定的错误码，同时避免泄露敏感输入？**

返回如 `code=INVALID_ARGUMENT`、`field=address.city`、`message=不能为空`，保留多个字段错误但限制数量。

- 密码、令牌和完整个人信息不应原样回显；日志也应脱敏。
- 客户端可依赖字段路径与错误码，不依赖框架异常类名或内部堆栈。

### 7. Spring MVC 与 WebFlux 的请求处理模型有什么不同？

Spring MVC 基于 Servlet，可采用阻塞请求处理，也支持异步请求；WebFlux 基于响应式处理链，通常用较少事件循环线程承载大量非阻塞 I/O，并提供背压语义。

WebFlux 不意味着所有操作自动非阻塞，MVC 也不等于永远一个请求独占一个线程直到完成。

**追问 1：业务调用链包含阻塞数据库或外部 SDK 时，为什么不能只替换 Web 框架就认为获得了非阻塞能力？**

JDBC、阻塞 SDK 或文件操作若直接放到事件循环，会阻塞该线程负责的其他请求。

- 需要使用响应式驱动，或将阻塞部分转移到受限调度器，并控制下游并发。
- 是否值得改造要看端到端调用链、团队成本和负载，不能只比较框架名字。

### 8. Spring Security 如何通过过滤器链完成认证与授权？

Spring Security 通过 Servlet 过滤器链建立 SecurityContext，执行认证、授权和异常转换。

- 认证回答“是谁”，授权回答“能做什么”；应用配置匹配的 SecurityFilterChain、认证机制和访问规则。
- 它不是单个登录接口，也不是给所有控制器加一个拦截器就完成安全设计。

**追问 1：用户身份的建立、权限判断和异常响应分别位于哪里？**

认证过滤器从凭据获得 Authentication 并保存上下文，授权组件根据身份和请求规则判断访问；未认证与无权限分别由认证入口、访问拒绝处理等机制返回。

必须避免信任客户端直接传入的身份字段，并在请求结束正确清理上下文。

**追问 2：方法级权限控制与接口过滤有什么区别？**

接口规则保护 HTTP 入口；`@PreAuthorize` 等方法级控制保护服务方法的业务权限，可覆盖多个入口调用同一服务的情况。

启用方法安全后仍有代理调用边界，并且对象级、租户级数据权限不能仅靠“拥有某角色”替代。

### 1. Spring Boot 启动流程如何衔接配置加载、容器初始化与应用启动？

SpringApplication 启动时准备监听器和环境，加载配置属性，创建合适的 ApplicationContext，注册主配置和 Bean 定义，刷新容器并启动内嵌 Web 服务，执行启动回调，最后进入就绪状态。

启动过程中的不同事件表示不同阶段，不应把“端口已监听”直接等同于所有业务初始化完成。

**追问 1：关键阶段分别完成什么工作？**

环境阶段确定 profile 和属性；定义阶段处理扫描与自动配置；刷新阶段创建单例、注册基础设施并启动容器；Runner 等处理启动任务；就绪后才应让流量进入。

慢预热可异步完成，但健康检查要准确表达服务是否真的可用。

### 2. 为什么 Spring Boot 的可执行 jar 能直接启动内嵌 Web 容器？

Spring Boot 构建插件把应用类、依赖和启动器组织成可执行归档，Manifest 指定启动器，由其建立类加载环境并调用应用入口。

- Web 依赖和自动配置再创建并启动嵌入式 Servlet 容器。
- 可执行 jar 不是“没有容器”，而是不再要求另部署一个外部容器来托管应用。

**追问 1：它与普通 jar 的目录结构、依赖加载和入口启动有什么区别？**

常见 Boot jar 中应用类位于 BOOT-INF/classes，依赖位于 BOOT-INF/lib，启动器处理嵌套依赖。

- 普通 jar 通常只保存自己的类，依赖还需外部 classpath。
- 具体启动器包名会随 Boot 版本变化，结构与启动职责比死记某个类名更重要。

**追问 2：容器线程与业务线程池应如何区分？**

Web 容器线程处理连接和 Servlet 请求，业务线程池处理应用主动提交的异步任务；二者有各自容量和队列。

异步化只是把等待移到另一资源，必须一起评估数据库连接池、超时和请求完成路径。

### 3. Spring Boot 如何发现自动配置类，并根据条件决定配置是否生效？

Spring Boot 从自动配置候选入口读取配置类，再按类路径、属性、已有 Bean 和应用类型等条件决定注册哪些定义。

- 自动配置通常使用 `@ConditionalOnMissingBean` 给应用自定义对象让位。
- Starter 主要组织依赖，自动配置模块提供条件化创建逻辑，两者职责不同。

**追问 1：配置类怎样被发现，条件装配又怎样判断某项配置是否应生效？**

候选配置先被发现，随后条件筛选；有相关 jar 不代表所有配置一定激活。

常见条件包括 OnClass、OnProperty、OnBean、OnMissingBean，应结合条件评估结果理解某个 Bean 为什么存在或缺失。

**追问 2：应用声明了自己的同类 Bean 后，自动配置怎样与它协调？**

符合回退规则的自动配置在发现用户 Bean 后不再提供默认 Bean。

- 这不是任意同名对象都能安全覆盖，名称冲突和类型选择仍受配置约束。
- 应优先通过文档支持的自定义扩展点，而非开启无差别 Bean 覆盖。

**追问 3：自定义 Starter 时，依赖、配置类、配置属性和自动配置入口应怎样组织？**

Starter 引入所需依赖，自动配置类用 `@AutoConfiguration` 等声明，配置属性用 `@ConfigurationProperties` 绑定，条件保证按需启用和允许用户接管。

补充配置元数据及容器测试，验证缺类、关闭属性和用户自定义 Bean 等分支。

**追问 4：以 Spring Boot 3.x 为例，自动配置类通过什么文件被发现？`AutoConfiguration.imports` 与历史自动配置注册方式有何区别？**

Boot 3.x 使用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 列出自动配置类。

历史上常通过 spring.factories 的 EnableAutoConfiguration 键注册；不能因此认为 spring.factories 在所有其他扩展机制中都失去用途。升级时按目标版本迁移注册入口。

### 4. 自动配置未生效或被自定义 Bean 覆盖时，如何判断是哪一个条件没有满足？

先确认自动配置是否被发现，再看条件评估报告：哪个类、属性或 Bean 条件未满足，是否被排除，是否因用户配置而回退。

- 可使用启动 debug 条件报告或受控的 Actuator conditions 端点。
- 排查重点是“为什么没有创建”，不是先手工再造一个同名 Bean。

**追问 1：条件装配、组件扫描范围和配置顺序分别可能造成什么差异？**

组件不在扫描范围内会根本没注册；OnMissingBean 看到用户对象会回退；不同配置顺序可能改变判断时可见的定义；profile 或属性可能关闭配置。

将问题缩小成最小容器测试，可以避免在整个应用里盲目调整注解。

### 5. 配置文件、环境变量与启动参数同时提供同一配置时，如何判断最终值？

Spring Boot 按外部化配置的优先级合并属性；常见情况下命令行参数可覆盖环境变量，环境变量可覆盖配置文件，但完整顺序还包含测试属性、系统属性和导入配置。

应查看最终 Environment 和属性来源，不只打开 application.yml 猜测。

**追问 1：多环境配置应如何管理，怎样避免把密钥硬编码进代码或制品？**

公共默认值与环境专属配置分离，使用 profile、配置中心或部署注入表达差异。

- 密钥放到受控秘密管理或环境注入中，限制日志及 Actuator 暴露。
- 配置变更应有版本、审核、灰度和回滚，不把生产凭据提交到 Git 或镜像层。

### 6. `@ConfigurationProperties` 与 `@Value` 分别适合什么配置读取需求？

`@ConfigurationProperties` 适合一组相关、结构化配置，提供类型绑定及校验；`@Value` 适合少量单值注入或表达式。

配置对象应表达明确领域边界，不要把全部应用参数集中成一个可随意修改的全局对象。

**追问 1：多字段配置如何进行类型绑定与校验？**

定义有类型字段的属性类，使用明确前缀并注册绑定，结合 `@Validated` 和约束检查范围、必填项。

嵌套配置也需校验；启动时尽早发现非法配置比首次请求才报错更可靠。

**追问 2：修改配置文件是否就意味着已创建对象会自动刷新？**

不会自动保证。普通文件修改不会天然重新绑定已创建 Bean；动态刷新需要配置中心、刷新基础设施或自行实现的原子配置发布。

多个字段必须一起生效时，应创建新不可变快照后整体替换，避免请求读到半更新配置。

### 7. 使用 `@Async` 时，为什么同类内部调用可能仍是同步执行？

代理式 `@Async` 将经过代理的方法调用提交给执行器；同类 this 调用绕过代理，仍在当前线程执行。

- 必须启用异步基础设施、使用可代理方法并明确执行器。
- 异步意味着执行和结果分离，不意味着失败自动重试或任务可靠保存。

**追问 1：调用是否经过代理，以及是否指定执行器，分别怎样影响实际执行线程？**

经过代理才有机会切换线程；通过注解指定执行器或配置默认执行器决定任务落到哪里。

应明确线程数、队列和拒绝策略，不能依赖某个版本的默认执行器假设它一定有界。

**追问 2：异步方法返回 `Future` 与不返回结果时，异常分别怎样被调用方感知？**

返回 Future/CompletableFuture 时，异常通过结果对象传播，需要观察完成结果；void 异步方法的未捕获异常可交给 AsyncUncaughtExceptionHandler 等处理。

只在调用处 try-catch 提交方法，通常抓不到任务稍后发生的异常。

**追问 3：调用方存在事务或请求上下文时，哪些内容不会自动随异步任务传递，怎样控制队列积压？**

命令式事务不自动跨线程，请求上下文和 ThreadLocal 也需受控传递与恢复。

传递必要不可变信息，不把整个请求对象长期保留；任务队列有界，监控排队时间和拒绝量，必须可靠的业务可使用持久队列。

### 8. `@Scheduled` 如何执行定时任务？

`@Scheduled` 由应用内调度基础设施按 cron、固定频率或固定延迟触发方法。

它适合本实例定期工作，但不是分布式调度协议，也不天然保存每次执行状态。执行器、时区、异常和停机恢复都应显式考虑。

**追问 1：多实例部署后是否自动保证只执行一次？**

不会。多个应用实例通常各自注册并执行相同任务。

需要全局单次执行时，可使用分布式调度、数据库领取任务或带失效处理的锁，并让业务幂等；锁只减少并发，不能代替执行结果记录。

**追问 2：任务耗时超过调度间隔、多个任务共享执行线程以及节点重启时，分别有哪些风险？**

慢任务会造成后续延迟或线程争用，不同触发模式及执行器的并发行为不同；节点重启可能漏过某个时间点。

关键任务用状态表记录应执行项及完成结果，支持补跑；不要只根据 cron 触发日志判断业务已完成。

### 9. Spring 的事件发布与监听默认在什么线程执行？

普通 Spring 应用事件默认由发布线程同步调用监听器，除非配置异步广播器或使用相应异步能力。

- 事件是解耦调用的一种机制，不自动提供跨进程可靠性。
- 发布者是否等待、异常如何传播和事务处于哪个阶段都要明确。

**追问 1：同步监听、异步监听与事务事件监听的时机有什么区别？**

同步监听在发布调用内执行；异步监听进入执行器，可能与发布者事务并行；事务事件监听绑定提交或回滚阶段。

三者可组合但语义不同，不能把“事件”统一理解成“提交后异步执行”。

**追问 2：慢监听器会怎样影响业务请求？**

同步慢监听会延长请求及事务时间；异步则把压力转到队列和线程池，仍可能积压。

应区分必须完成的主业务与可延迟的副作用，配置超时、失败处理和可观测性，需要可靠事件时落库或使用 MQ。

### 10. Spring Cache 的 `@Cacheable`、`@CachePut` 与 `@CacheEvict` 如何配合缓存查询、更新与失效？

`@Cacheable` 命中缓存时可跳过方法执行；`@CachePut` 仍执行方法并把结果写缓存；`@CacheEvict` 删除缓存项。

缓存注解提供统一访问抽象，但一致性依赖缓存提供者、事务时机和业务键设计，不能自动把数据库和 Redis 变成同一事务。

**追问 1：查询、强制更新缓存与删除缓存，分别应该由哪种注解表达？**

读多的查询使用 Cacheable，确需重新计算并更新缓存用 CachePut，数据变更后失效用 CacheEvict。

是否在调用前删除、异常时是否删除等由配置决定，应避免同时组合出相互冲突的语义。

**追问 2：同一个方法的不同参数怎样形成正确的 key，避免不同业务数据互相覆盖？**

key 应包含决定结果的必要参数，例如租户、用户、查询条件及必要版本。

使用明确 key 表达式或 KeyGenerator，避免只用方法名导致不同租户共用结果，也避免包含无关随机参数破坏命中率。

**追问 3：同类调用、事务回滚或失效操作失败时，缓存会处于什么状态，应怎样补偿？**

自调用可能绕过缓存代理；事务回滚前已经写缓存会留下不存在的数据；失效失败会保留旧值。

可在提交后失效、使用事务感知缓存策略，并以可靠重试或 CDC 修复；仍需考虑提交与失效之间窗口，不能宣称注解可保证强一致。

### 11. Spring Boot Actuator 能提供哪些健康检查和指标信息？

Actuator 提供健康状态、指标、环境与配置诊断等管理能力，结合 Micrometer 可输出请求、线程池、JVM 和连接池等指标。

它用于观测应用，不是启用后就自动知道所有业务故障；业务就绪和关键依赖状态仍需设计合理的检查。

**追问 1：应用存活与就绪应如何区分？**

存活检查判断进程是否应被重启，就绪检查判断是否适合接流量。

把短暂数据库故障直接作为存活失败，可能触发全实例重启风暴；就绪可更谨慎地反映无法处理业务，但需考虑所有副本同时退出流量的后果。

**追问 2：管理端点暴露范围和访问权限需要怎样控制？**

只暴露必要端点，使用独立管理网络或端口、认证授权和访问控制，敏感属性脱敏。

heapdump、env、loggers 等可能暴露数据或改变运行状态，不能因为是管理端点就公开到互联网。

### 12. 如何在 Spring Boot 中配置多个数据源，并让指定操作使用正确的事务管理器？

为每个数据源配置 DataSource、对应数据访问工厂和事务管理器，通过限定符及 `@Transactional(transactionManager="...")` 明确选择。

多数据源存在于同一 Spring 应用，不代表不同数据库操作自动参与同一个原子事务。

**追问 1：通过路由数据源做读写分离时，事务已开始后再切换目标数据源会有什么边界？**

路由数据源通常在取得连接时选择目标；事务已绑定连接后再改变路由键，通常不会让已有事务自动换库。

应在事务开始前决定读写路由，并在 finally 清理线程上下文；需要跨库一致性时另选分布式事务或补偿方案。

### 13. Spring Boot 项目出现依赖版本冲突时，如何确定运行时实际使用的依赖？

先用 Maven dependency:tree 查看解析结果，再检查最终制品及运行时类来源。

- 编译依赖树、打包内容和生产实际 classpath 可能不同，尤其容器额外库、手动覆盖版本和重复 jar 会引发问题。
- Spring Boot BOM 提供协调版本，但不应认为随意覆盖其中一项仍必然兼容。

**追问 1：Maven 的直接依赖、传递依赖、`dependencyManagement` 和 BOM 分别起什么作用？**

直接依赖由项目声明，传递依赖来自所依赖模块；dependencyManagement 管理版本等默认规则，不等于自动引入依赖；BOM 是集中管理相关版本的 POM。

Maven 冲突协调通常采用最近路径等规则，具体还受显式声明和管理配置影响。

**追问 2：使用 `dependency:tree` 后，如何定位被替换或排除的版本，并检查作用域和打包结果？**

检查 omitted for conflict、exclusions、scope 和 dependencyManagement，确认最终选中版本；查看 jar 内实际库列表，再通过类加载信息确认运行时载入哪份类。

不要只搜索 pom.xml 中出现次数，也不要将 test/provided 依赖误认为一定被打包。

**追问 3：为什么“编译通过”仍可能在运行时出现 `NoSuchMethodError`？如何在升级前验证兼容性？**

编译时方法存在，但运行时加载旧版类没有该签名，就会出现 NoSuchMethodError。

升级应做 API/二进制兼容检查、集成测试和目标制品启动测试，统一依赖版本，避免只在 IDE 编译成功就发布。

### 14. 普通单元测试、`@WebMvcTest` 与 `@SpringBootTest` 应如何选择？

普通单元测试只创建被测对象，速度快且便于隔离；`@WebMvcTest` 加载 MVC 相关切片，适合参数、校验和错误响应；`@SpringBootTest` 加载完整应用，验证自动配置及组件集成。

按验证目标选择最小足够范围，而不是每题都启动完整服务。

**追问 1：只验证业务分支、验证参数绑定与异常响应、验证完整应用集成，分别需要加载哪些组件？**

业务分支测试可用构造器注入替身，不需要容器；MVC 切片测试使用 MockMvc 等验证请求到响应；完整集成需加载配置、数据访问和必要中间件。

真实 HTTP 端口与模拟请求在事务和线程边界上不同。

**追问 2：哪些依赖适合使用测试替身，哪些行为需要连接真实数据库或中间件验证？**

外部支付服务、时钟和随机源适合替身，数据库隔离级别、真实 SQL、Redis 脚本和消息确认行为应有真实组件集成测试。

替身只能证明代码按照假定契约工作，不能证明假定与真实组件一致。

**追问 3：如何避免每个简单测试都启动完整容器，同时又不遗漏配置和事务集成问题？**

建立分层测试：大量快速单测，少量控制器切片测试，再用关键集成测试覆盖事务、映射、配置与失败恢复。

容器上下文缓存可降低启动成本，但测试不可随意共享可变数据或遗留后台任务。

### 1. MyBatis 如何根据可选查询条件生成 SQL？

MyBatis 将动态 SQL 节点根据参数计算成 BoundSql，最终交给 JDBC 执行。

- `if` 选择条件，`where` 处理 WHERE 与前导 AND/OR，`trim` 定制前后缀，`foreach` 生成集合条件。
- 框架能拼接语句，但不会判断“空条件更新全部订单”是否符合业务意图。

**追问 1：if、where、trim 与 foreach 如何配合？**

例如可选用户和状态条件分别由 if 包围，再放入 where；批量 ID 用 foreach 生成占位符列表。set 或 trim 可处理更新字段的逗号。

数据值仍用参数绑定，不能把动态 SQL 等同于全部字符串直接拼接。

**追问 2：集合为空时怎样避免生成错误 SQL 或意外扩大更新范围？**

在业务入口明确空集合含义：拒绝、返回空结果，或显式生成永假条件。

- 更新和删除要求必要范围条件，不能让空列表分支直接消失导致全表操作。
- 对生成 SQL 和边界输入编写测试，比只检查 XML 是否能解析更重要。

### 2. MyBatis 的 Mapper 接口没有手写实现类时，调用如何被转换成 SQL 执行？

Mapper 接口由 MyBatis 创建动态代理，方法调用映射到已注册的 MappedStatement，参数被转换成 SQL 绑定信息，执行器处理缓存及语句执行，StatementHandler 调用 JDBC，ResultSetHandler 将结果映射回对象。

没有手写实现类，不代表 SQL 由方法名无条件自动推导。

**追问 1：代理、参数处理与 JDBC 执行之间如何衔接？**

代理先定位命名空间和方法对应语句；动态 SQL 生成最终语句与参数映射，ParameterHandler 通过 TypeHandler 设置 PreparedStatement 参数；执行器调用数据库后处理结果及缓存。

MyBatis-Plus 等增强可能额外生成语句，不能混同为基础 MyBatis 的全部行为。

### 3. MyBatis 的 `#{}` 与 `${}` 为什么会产生不同的 SQL 执行与安全效果？

`#{}` 通常生成 PreparedStatement 的参数占位符，值由 JDBC 绑定；`${}` 是文本替换，输入会成为 SQL 语法的一部分。

普通查询值应使用绑定参数，直接替换只应用于严格受控的标识符等位置，不能接受未经校验的用户文本。

**追问 1：参数绑定和直接字符串替换发生在什么环节，对最终 SQL 有何不同影响？**

`${}` 在生成 SQL 文本时替换，可能改变语法；`#{}` 保留 SQL 结构并在执行时绑定值。

参数绑定能防止该值被当成 SQL 指令解释，但不替代数据库权限、输入约束和其他动态片段的安全检查。

**追问 2：查询值、表名和排序字段，哪些能通过普通参数占位完成？**

姓名、状态、日期等值可以绑定；表名、列名、ASC/DESC 这样的结构通常不能用普通值占位符代替。

写 `ORDER BY #{column}` 不等于安全地按该字段排序，它可能只是对一个常量表达式排序。

**追问 3：无法直接绑定的动态标识符应怎样约束来源，避免把未经校验的输入拼进 SQL？**

把前端排序选项映射到服务端固定白名单，例如 CREATED_AT 映射为受控列名，并校验方向。

- 租户分表等标识符同样从可信路由规则产生，不拼接任意原始输入。
- SQL 注入的防线是区分数据与语法，不是简单替换引号。

### 4. MyBatis 一级缓存和二级缓存分别在什么范围内生效，何时失效？

一级缓存默认属于 SqlSession，可通过 localCacheScope 等调整；二级缓存按 Mapper namespace 等配置共享，通常需显式启用相关映射。

它们保存查询结果，失效依赖 MyBatis 观察到的更新和事务生命周期，无法自动感知所有外部写入。

**追问 1：两个 `SqlSession` 与两个 Mapper 命名空间之间，分别共享或隔离哪些缓存？**

不同原始 SqlSession 的一级缓存隔离；同一命名空间启用二级缓存后，可跨会话共享已提交缓存内容，不同 namespace 默认不共享，除非显式引用。

相同 SQL 文本不意味着在任意 Mapper 间共享缓存。

**追问 2：更新、提交、回滚或关闭会话时，缓存怎样失效？**

更新通常清理本会话缓存，并按配置标记二级缓存失效；提交时处理事务性缓存发布，回滚不应把未提交结果发布给其他会话。关闭结束一级缓存生命周期。

select 的 useCache、flushCache 及事务是否发生更新都会影响细节，不能概括为每次提交无条件清空所有缓存。

**追问 3：多表关联与多实例部署后，哪些写入路径可能没有同步失效缓存，怎样判断是否适合启用？**

关联查询引用 B 表但由 A namespace 缓存，B 的更新未必失效 A；外部 SQL、其他服务和本地多实例缓存也可能不一致。

复杂动态数据通常谨慎启用二级缓存，或采用有明确失效协议的业务缓存，不能认为“缓存更少查询”就必然更正确。

### 5. MyBatis 分页插件如何介入查询执行？

分页插件通常通过拦截 Executor 或 StatementHandler 等执行路径，识别分页参数，按数据库方言改写 SQL，并可能额外执行总数查询。

它不是数据库自动理解 Java 分页对象；最终性能仍取决于生成的 SQL、索引和分页方式。

**追问 1：逻辑分页与物理分页在数据读取量、内存和性能上有什么区别？**

逻辑分页可能先查询较多结果，再在客户端跳过或截取，增加传输与内存；物理分页把范围限制下推到数据库，但大 OFFSET 仍可能扫描大量记录。

游标分页可减少偏移成本，总数查询也需单独评估，不能只看返回十条数据。

### 6. MyBatis 如何完成字段名转换及一对一、一对多结果映射？

简单字段可通过别名、驼峰映射或 resultMap 对应到属性；复杂关系用 association 表示单对象、collection 表示集合。

- 关联可以通过一条 JOIN 映射，也可通过嵌套查询获取。
- 应根据结果规模和访问模式选择，而不是所有关系都自动延迟加载。

**追问 1：字段名与 Java 属性名不同，`resultMap` 和命名约定分别怎样处理？**

SQL 别名和显式 resultMap 最直接，`mapUnderscoreToCamelCase` 可支持下划线到驼峰的约定。

相同列名出现在多个表时应使用明确别名或列前缀，避免映射覆盖。

**追问 2：`association`、`collection`、嵌套查询与连接查询分别适合什么关系？**

一对一关联用 association，一对多用 collection；JOIN 减少往返但会重复父行数据，嵌套查询便于按需获取却可能放大 SQL 数量。

正确设置 id 映射有助于聚合同一父对象，避免把重复结果误当成多个实体。

**追问 3：延迟加载与逐条加载关联数据，为什么可能造成 N+1 查询及会话生命周期问题？怎样验证实际 SQL 次数？**

查询 N 个父对象后逐个触发关联，会形成 1+N 次查询；会话已结束或序列化时触发加载，还可能出现生命周期和隐式查询问题。

通过 SQL 日志、调用计数和代表性数据验证，必要时批量加载、明确 DTO 或改用受控连接查询。

### 7. MyBatis 插件通过哪些扩展接口介入 SQL 执行？

MyBatis 插件可拦截 Executor、StatementHandler、ParameterHandler、ResultSetHandler 的受支持方法。

插件通过代理链参与执行，适合分页、审计和数据权限等横切扩展，但它不是任意修改内部对象都保证兼容的接口。插件应限定范围并覆盖 SQL 类型及异常路径。

**追问 1：分页、SQL 审计与数据权限插件同时存在时，执行顺序可能怎样改变最终 SQL？**

数据权限先后加入条件会影响 count SQL 与分页结果，审计看到改写前还是改写后 SQL 也由拦截位置决定。

- 多个插件嵌套时按实际链路验证，防止条件重复、参数索引错位或更新失去范围。
- 升级 MyBatis 后应运行集成测试，而不是仅确认插件能加载。

### 8. MyBatis-Plus 相比 MyBatis 提供哪些常用能力？

MyBatis-Plus 提供通用 CRUD、条件构造器、分页、逻辑删除、乐观锁等增强，减少常见数据访问代码。

它仍基于 MyBatis 和数据库能力；复杂查询、业务不变量及正确事务边界依然由应用设计，自动生成 SQL 也需要审核。

**追问 1：使用逻辑删除、乐观锁与分页插件时，怎样避免误以为框架已经自动解决全部并发和数据权限问题？**

逻辑删除需要在所有相关查询和唯一约束中保持一致；乐观锁要求版本字段、支持的调用路径和受影响行数检查；分页不保证深分页高效；数据权限不能仅由一个查询插件覆盖全部手写 SQL。应查看实际 SQL、失败分支和绕过增强的路径。

### 9. MyBatis 的 SIMPLE、REUSE 与 BATCH 执行器有什么区别？

SIMPLE 通常每次执行创建相应语句；REUSE 尽量复用相同 SQL 的 Statement；BATCH 将适合的更新加入 JDBC 批处理，再集中执行。

选择 BATCH 可以减少往返，但异常和受影响行数的可见时点会后移，不应把每次 mapper 返回值当成最终数据库执行结果。

**追问 1：批处理什么时候真正执行 SQL？**

BATCH 在 flushStatements、提交或某些需要先执行前序更新的查询路径触发实际批处理。具体驱动还影响批量改写和性能。

回滚前尚未发送与已经发送但未提交是不同状态，不能只看 Java 循环已执行多少次。

**追问 2：结果获取、异常发现与事务提交之间怎样衔接？**

批次执行时才能获得 BatchResult 等结果，错误可能直到 flush 或 commit 才暴露；成功执行批次不代表已经事务提交。

需控制批次大小、正确处理部分执行错误，并用事务确定回滚范围，避免只捕获单条调用异常。

### 10. MyBatis `TypeHandler` 如何完成 JDBC 类型与 Java 类型之间的转换？

TypeHandler 在设置 PreparedStatement 参数和读取 ResultSet/CallableStatement 值时，完成 Java 类型与 JDBC 类型之间的转换。

- 自定义处理器应明确数据库存储格式、空值和非法值语义，并在全局或具体字段映射中注册。
- 它处理类型转换，不负责业务校验或自动解决版本兼容。

**追问 1：枚举、JSON、时间和自定义值对象需要怎样注册转换规则，并处理 `NULL`？**

枚举建议保存稳定业务码而非 ordinal；JSON 应规定结构和兼容策略；时间类型明确时区和数据库字段；值对象需检查合法性。

NULL 既可能表示缺失，也可能是业务值，应与 primitive 默认值区分，必要时指定 jdbcType 并使用包装类型。

### 11. MyBatis 的 `SqlSession` 与 Spring 管理的事务、数据库连接之间是什么关系？

原始 SqlSession 代表一次 MyBatis 会话，包含执行器、一级缓存与关联连接；MyBatis-Spring 通过 SqlSessionTemplate 等把 Mapper 调用协调到 Spring 管理的事务资源。

相同事务内通常复用合适会话和连接，事务外则按调用生命周期获取和释放。

**追问 1：手工创建的 `SqlSession` 与通过 Spring 注入的 Mapper，在会话获取和关闭责任上有什么不同？**

手工 openSession 的调用方负责提交、回滚和关闭；通过 Spring 管理的 Mapper 调用，生命周期由集成组件与事务管理器协调，不能随意对其连接手工提交。

数据源和 SqlSessionFactory 必须与所选事务管理器正确匹配。

**追问 2：使用 MyBatis-Spring 时，同一事务与无事务调用的会话复用如何影响一级缓存？**

同一 Spring 事务中复用会话，重复查询可能命中一级缓存；事务外单次 Mapper 调用往往获取并释放会话，不能把它概括成“一个 HTTP 请求固定一个 SqlSession”。

localCacheScope=STATEMENT 等配置也会改变缓存范围。

**追问 3：为什么不应把原始 `SqlSession` 实例当成线程安全对象长期共享？**

原始 SqlSession 有可变执行状态，不应跨线程长期共享；线程安全的 SqlSessionTemplate 通过委派到当前事务会话实现使用安全，不等于底层原始实例突然变成并发对象。异步访问应建立各自正确的会话与事务边界。

## 要点回顾

- 容器管理与线程安全分开讨论：Bean 的作用域、生命周期和依赖注入不自动保证可变业务状态安全。
- 关注代理实际经过的调用边界：AOP、事务和异步增强能否生效，取决于调用路径及相应配置，不能只看注解是否存在。
- 把请求绑定、参数校验与数据库约束分别落实：格式转换成功不等于业务合法，框架事务也不能替代数据库的真实提交与回滚。
