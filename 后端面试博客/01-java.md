### 1. Java 的八种基本类型分别适合表示哪些数据？

Java 有四种整数类型 `byte`、`short`、`int`、`long`，两种浮点类型 `float`、`double`，以及 `char` 和 `boolean`。

- **整数与二进制数据：** 普通整数计算通常使用 `int`，较大计数和时间戳使用 `long`，二进制数据常用 `byte[]`。
- **浮点数与金额：** `float`、`double` 表示二进制浮点近似值，不适合直接承担要求十进制精确的金额计算。
- **字符与布尔值：** `char` 表示 UTF-16 代码单元，`boolean` 表示真假。

**追问 1：各数值类型的范围、精度和默认值有什么区别？`char` 表示的内容能否直接等同于一个完整的可见字符？**

**整数范围**

`byte`、`short`、`int`、`long` 分别是 8、16、32、64 位有符号整数，范围为 `−2^(n−1)` 到 `2^(n−1)−1`

**浮点数精度**

`float`、`double` 分别采用 32、64 位二进制浮点表示，有效十进制数字约为 6～7 位和 15～16 位

**浮点数范围**

最大有限正数约为 `3.4028235×10^38` 和 `1.7976931348623157×10^308`，最小正非零值约为 `1.4×10^-45` 和 `4.9×10^-324`，也支持负数、正负零、无穷和 NaN

**`MIN_VALUE` 的含义**

注意 `Float.MIN_VALUE`、`Double.MIN_VALUE` 指最小正非零值，不是最负值

**`char` 与可见字符**

`char` 是 16 位无符号 UTF-16 代码单元，范围为 0～65535；一个可见字符可能需要代理对甚至多个码点

**默认值与初始化**

字段和数组元素默认初始化为数值零、`'\u0000'`、`false` 或引用的 `null`；局部变量不能依赖默认值直接读取

**`boolean` 的存储**

Java 语言规范没有把 `boolean` 的存储占用固定为某个字节数

**追问 2：基本类型与包装类型在空值、比较和集合使用上有什么差异？**

- **空值语义：** 基本类型直接表示值，不能为 `null`；包装类型是对象，可以表达缺失值，也是泛型集合存储基本数值时使用的类型。
- **比较规则：** 基本类型的 `==` 比较数值，两个包装对象的 `==` 比较引用身份，内容比较通常使用 `equals` 或空值安全的 `Objects.equals`。
- **使用成本：** 包装对象还会带来对象、引用和装箱拆箱开销。

**追问 3：成员变量和局部变量的初始化要求是否相同？请求中的可选数值字段应如何选择类型？**

- **初始化规则：** 实例字段、静态字段和数组元素有默认初始化；局部变量必须在使用前被明确赋值。
- **可选参数：** 接口中的可选数值一般使用包装类型，以区分“未传”与“传了 0”。
- **校验边界：** 是否允许缺失、缺失后采用什么默认值，应在参数校验边界明确处理，而不是靠隐式拆箱决定。

### 2. 阅读以下代码，说明整数溢出发生在哪一步，并修正计算方式。

以下代码位于 Java 方法中：

```java
int a = 50_000;
int b = 50_000;
long x = a * b;
long y = (long) a * b;
long z = (long) (a * b);
```

分别判断 `x`、`y`、`z` 是否等于数学上的乘积，并解释原因。

- **数学结果：** 数学乘积是 `2_500_000_000`，超过 `int` 最大值。
- **实际结果：** `x` 和 `z` 都是 `-1_794_967_296L`，只有 `y` 为 `2_500_000_000L`。
- **溢出原因：** 原因是乘法先按操作数类型执行，结果才赋给目标变量；溢出后再转换为 `long` 无法恢复丢失的信息。
- **修正方式：** 正确写法是先将至少一个乘数提升为 `long`，例如 `long result = (long) a * b`。

**追问 1：赋值目标是 `long`，是否足以让右侧乘法按 `long` 计算？三行代码有什么区别？**

赋值目标不会倒过来改变乘法的运算类型。`x` 的右侧是 `int × int`；`y` 的一个操作数已经是 `long`，另一操作数随之提升；`z` 的括号内仍先进行 `int` 乘法。

需要检测溢出而不是容忍环绕时，可以使用 `Math.multiplyExact`，同时选择正确的 `int` 或 `long` 重载。

**追问 2：把较大范围的数值强制转换为较小类型时，可能丢失哪些信息？如何检查业务输入和运算边界？**

整数窄化可能丢失高位并改变符号；浮点转整数还涉及小数截断、范围以及 NaN 等情况，不能都概括为“保留低位”。

入口校验业务范围，中间运算使用足够宽的类型，关键加减乘使用 `Math.*Exact` 检测；超出 `long` 范围时改用 `BigInteger`，不要把异常结果当成合法业务值。

### 3. 自动装箱和拆箱在什么情况下发生？

- **转换定义：** 装箱是把基本类型转换为对应包装类型，拆箱则取出包装对象中的基本值。
- **触发位置：** 它们会出现在赋值、方法调用、泛型集合和混合运算等位置。
- **典型示例：** 例如向 `List<Integer>` 添加 `int` 会装箱，执行 `Integer n = null; int x = n;` 会在拆箱时抛出空指针异常。
- **使用前提：** 业务上应先明确空值语义，再进行运算。

**追问 1：`Integer` 与 `int` 混合运算或比较时，会发生怎样的转换？包装值为 `null` 时有什么风险？**

`Integer` 参与与 `int` 的算术运算或数值比较时通常先拆箱，如 `boxed + 1`、`boxed == 1`。

如果 `boxed` 为 `null`，就会抛出 `NullPointerException`；两个 `Integer` 之间直接使用 `==` 则不是同一套数值比较规则。

**追问 2：两个 `Integer` 使用 `==` 比较时，为什么不能只根据数值推断结果？缓存机制与对象身份有什么关系？**

两个包装对象的 `==` 比较对象身份。自动装箱和 `Integer.valueOf` 对一定范围的值进行缓存，至少覆盖 −128～127，因此部分相等数值可能共享对象，但较大数值不能据此推断。

数值比较应使用 `equals`；允许空值时用 `Objects.equals`，不要把缓存范围写成业务正确性的前提。

**追问 3：接口参数允许为空时，怎样完成校验、默认值处理和比较，避免隐式拆箱异常？**

必填字段先校验非空，可选字段按业务显式补默认值或保留缺失状态。

- 比较两个可空对象可使用 `Objects.equals`；需要大小比较时先处理空值，再比较基本值。
- 不要通过把所有缺失值都转换为 0 来掩盖“未知”与“真实为零”的差异。

### 4. 为什么金额计算通常不直接使用 `float` 或 `double`？

`float`、`double` 采用二进制浮点表示，很多十进制小数无法精确表示，误差会在累计、比较和舍入时暴露。

- 金额一般使用 `BigDecimal`，或在币种和最小单位明确时用整数保存分等最小单位。
- `BigDecimal` 也不是自动正确：构造输入、精度、舍入和金额单位必须统一。

**追问 1：用字符串与 `double` 创建 `BigDecimal` 时，得到的值可能有什么差异？**

`new BigDecimal("0.1")` 表示精确的十进制 0.1；`new BigDecimal(0.1)` 会保留该 `double` 的二进制近似值，得到较长的小数。

已有 `double` 时，`BigDecimal.valueOf` 通过其十进制字符串表示构造，通常更符合预期，但不能恢复此前运算已丢失的精度。最好从原始十进制文本或整数单位开始计算。

**追问 2：比较 1.0 与 1.00 时，`equals` 和 `compareTo` 的判断依据有什么区别？**

对 `new BigDecimal("1.0")` 和 `new BigDecimal("1.00")`，`equals` 同时比较数值与 scale，结果为 `false`；`compareTo` 只比较数值大小，结果为 0。

做金额大小判断通常用 `compareTo`。作为哈希键或集合元素时，必须事先约定是否规范化 scale，避免相等性规则与业务语义冲突。

**追问 3：除法、累计计算和最终展示分别应在哪一步确定精度与舍入规则？**

先定义业务精度和结算规则。除法可能产生无限小数，要明确 scale 或 `MathContext` 及 `RoundingMode`；中间计算保留足够精度，避免每一步都无依据地舍入。最终结算按币种规则舍入，展示格式再独立处理。

税费、分摊等需要逐项舍入的业务，应依业务规则而不是一律“最后才舍入”。

### 5. Java 的参数传递是值传递还是引用传递？

Java 只有值传递。基本类型传递其数值，对象参数传递“引用这个值”的副本。

方法内外的引用副本可以指向同一个对象，所以修改对象内容可能对外可见；但重新给形参赋值，只改变方法内部的副本，不会让调用方变量重新指向另一个对象。

**追问 1：传入基本类型、对象引用时，方法实际得到的分别是什么值？**

`int` 参数得到整数值的副本；对象参数得到引用值的副本，而不是对象的深拷贝，也不是调用方变量本身的地址。

判断调用影响时，应区分变量中的引用和引用所指向的对象。

**追问 2：修改对象属性与把形参重新指向另一个对象，对调用方有什么不同影响？**

执行 `person.setName("新名字")` 修改的是共享对象，调用方可观察到变化；执行 `person = new Person()` 只让方法内形参指向新对象。

数组同样如此：修改元素能影响原数组，重新给数组形参赋值不能替换调用方的数组变量。

**追问 3：一个方法想同时返回“修改后的对象”和处理状态，怎样设计返回值，而不是依赖在方法内重新给形参赋值？**

返回一个包含结果对象和状态的明确类型，例如 `record UpdateResult(Person person, boolean changed) {}`，由调用方接收返回值。

需要原地更新时，接口应写清变更语义；需要新对象时优先显式返回，不依赖让读者猜测的副作用。

### 6. 封装、继承和多态在业务代码中分别解决什么问题？

封装把状态和维护该状态的规则放在一起，限制外部直接破坏对象约束；继承复用或扩展父类型行为，但会形成较强耦合；多态让调用方面向统一接口，而由不同实现执行各自逻辑。

它们的目的不是减少几行代码，而是控制依赖和变化范围。

**追问 1：以“统一接口调用不同支付实现”为例说明多态；什么情况下组合比继承更合适？**

定义 `PaymentService.pay()`，由银行卡和电子钱包实现；订单服务只依赖接口，选择实现后统一调用。

- 若只是复用日志、重试等能力，而没有稳定的“是一种”关系，组合通常更合适。
- 通过注入协作者组合能力，能避免父类改动影响大量子类，也便于测试和替换。

### 7. 方法重载与重写有什么区别？调用目标分别在什么时候确定？

重载是在同一可见调用范围内，方法名相同而参数列表不同，由编译器根据实参的静态类型等规则选择方法签名。

重写是子类对可继承实例方法提供实现，调用的实例方法签名确定后，运行时再根据对象实际类型进行动态分派。不能只用返回类型不同构成重载。

**追问 1：分别从参数列表、返回类型和继承关系判断重载与重写。**

重载看参数个数、类型或顺序，返回类型不同本身不够。

重写要求兼容的方法签名，返回类型允许协变，访问权限不能缩小，受检异常不能扩大；`private` 方法不被继承重写，`static` 方法属于隐藏，构造器也不能重写。

**追问 2：父类引用指向子类对象时，如何区分编译期选中的方法签名与运行时执行的方法实现？**

例如 `Parent p = new Child()`，先按 `Parent` 的可见方法和实参静态类型完成重载选择；如果所选的是可重写实例方法，再执行 `Child` 对该签名的重写。

不能因为对象实际为 `Child`，就跳到只有 `Child` 定义的另一个重载上。

### 8. 接口与抽象类有什么区别？

接口主要定义可实现的能力和协作契约，一个类可以实现多个接口；抽象类可以保存实例状态、定义构造器并提供共同实现，但类只能直接继承一个父类。

现代 Java 接口也允许默认、静态及私有辅助方法，不能再简单回答“接口里只能写抽象方法”。

**追问 1：需要共享状态和公共实现，与仅约定一组能力时，选择依据有什么不同？**

同一类对象具有稳定的共同状态和生命周期规则时，抽象类有利于集中维护；只需约定调用能力、支持多种无继承关系的实现时，接口更合适。

是否有公共代码不是唯一依据，还要判断继承关系是否自然、扩展是否需要共享状态。

**追问 2：新需求同时包含多个可组合的能力时，怎样避免形成过深的继承层次？**

把支付、审计、缓存等能力拆成小接口，通过对象组合与依赖注入连接，而不是增加“带缓存且带审计的某某子类”。

不同能力可以独立替换和测试；必要时用小型抽象基类复用稳定流程，但避免把所有变化塞进继承树。

### 9. 接口的 `default` 方法解决什么兼容性问题？

默认方法允许接口在增加行为时提供一个可继承实现，减少已有实现类必须立即修改的压力，也便于为接口提供通用操作。

不过它并不保证任何接口演化都没有冲突；多个继承来源可能要求实现类显式消歧。

**追问 1：与抽象类提供公共实现相比，默认方法有哪些能力限制？**

默认方法不能像抽象类一样保存实例字段或定义构造器，只能利用接口公开的能力完成行为。

接口字段是常量，不是每个实现对象的可变状态；复杂状态共享仍应由实现类或组合对象负责。

**追问 2：一个类实现的两个无继承关系的接口提供了同签名默认方法时，如何解决冲突？**

实现类必须显式重写该方法，选择一个实现或组合实现。

需要调用某个直接父接口的默认实现时，可以在重写方法中使用 `InterfaceName.super.method()`。不能依赖接口书写顺序决定赢家。

**追问 3：类继承的方法与接口默认方法同时存在时，如何判断实际调用目标？**

通常遵循“类方法优先于接口默认方法”，接口之间则优先采用更具体子接口的方法。

继承链上的抽象类方法也可能要求子类实现，不能仅因接口提供默认方法就认为已经满足。多个无继承关系的默认实现冲突时由类显式解决。

### 10. 设计跨包继承的类时，`public`、`protected`、包访问权限和 `private` 如何限制成员访问？

`public` 对外可见；`private` 限制在声明类的访问上下文内；包访问权限只对同包代码开放；`protected` 对同包代码以及满足规则的子类开放。

跨包子类访问 `protected` 实例成员时，还受接收者类型限制，不能通过任意父类对象访问其受保护成员。

**追问 1：哪些实现细节应隐藏，哪些方法适合留作扩展点？**

内部可变字段、校验细节优先隐藏，通过方法维护不变量；确实允许子类定制的步骤才设置受保护扩展点。

- 跨包子类通常能通过 `this`、`super` 或符合子类型限制的引用访问，而不能拿一个任意 `Parent` 实例绕过封装。
- 开放权限应由扩展需求决定，而不是为方便调用全部设为 `public`。

### 11. `static` 成员与实例成员的归属和生命周期有什么区别？

`static` 成员属于声明它的类，通常由该类的所有实例共享；实例字段属于每个对象。

静态字段由类的生命周期管理，在准备阶段获得默认值，在初始化阶段执行相应的显式赋值；它不是“整个系统永远只有一份”：不同定义类加载器可形成不同的类及静态状态。实例对象的生命周期由引用可达性等决定。

**追问 1：把请求数据保存在静态字段中会带来什么共享状态风险？**

静态字段保存当前用户、请求参数等信息，会让并发请求覆盖或读取彼此数据，还可能长期持有大对象。

- 请求数据优先通过参数传递，必要的线程上下文使用后必须清理。
- 方法是否为 `static` 并不能单独决定线程安全，关键仍是访问了哪些共享可变状态及如何同步。

### 12. 使用枚举表示订单状态时，怎样兼顾类型安全和数据兼容？

枚举把有限的合法状态集中定义，使方法参数、分支和状态转换更有约束。

数据库与接口应保存稳定业务编码，而不是依赖枚举声明位置；状态迁移仍需独立规则验证，枚举本身不会阻止“已退款直接改成待支付”等非法转换。

**追问 1：枚举相较于散落在代码中的字符串或整数常量，有什么维护优势？**

枚举减少拼写错误和魔法值，能把名称、编码和少量稳定行为放在一起，新增状态也更容易找到相关代码。

但外部系统可能发送未来状态，持久化与反序列化层仍要设计兼容边界。

**追问 2：把 `ordinal()` 直接保存到数据库后，调整枚举顺序会产生什么问题？如何使用稳定的业务编码？**

`ordinal()` 是声明顺序，从 0 开始；插入或调整枚举常量后，历史数字可能被解释成另一个状态。

应定义不随排序变化的 `code`，例如 `PAID("PAID")`，并通过明确映射读写数据库；显示顺序另行保存。

**追问 3：接收未知状态值时，接口应该拒绝、兼容还是保留原值？依据是什么？**

涉及支付、授权等必须理解语义的操作，应拒绝未知状态并报警，不能默认为成功；只做展示、转发或兼容读取时，可使用 `UNKNOWN` 加原始值保留信息。

选择依据是未知状态是否可能破坏业务不变量，以及上下游版本是否允许渐进升级。

### 13. `final` 修饰类、方法和变量时分别有什么作用？

`final` 类不能被继承，`final` 实例方法不能被重写，`final` 变量只能被赋值一次。

- 它可以帮助表达稳定引用或限制扩展，但不自动让对象不可变，也不等同于所有访问都线程安全。
- 并发下还要考虑对象构造、安全发布和内部可变状态。

**追问 1：`final` 修饰的引用所指向的对象能否修改？**

能修改。`final List<String> names` 不允许重新绑定另一张列表，但仍可调用 `names.add()`。

- 真正不可变需要控制所有可变字段，必要时防御性复制，并且不暴露内部可变引用。
- `final` 字段的初始化安全语义也不能替代对象后续修改所需的同步。

### 14. `==`、`equals` 与 `hashCode` 分别解决什么比较问题？

对基本类型，`==` 按相应数值或布尔规则比较；对引用类型，`==` 比较是否指向同一对象。

- `equals` 表达对象的逻辑相等，默认实现仍是身份相等；`hashCode` 为哈希定位提供散列值。
- 相等对象必须有相同哈希值，但哈希相同不意味着对象相等。

**追问 1：重写 `equals` 时，为什么需要检查 `hashCode` 的约定？否则 `HashMap` 和 `HashSet` 可能出现什么现象？**

哈希容器先按哈希选择位置，再用相等性确认。如果两个对象 `equals` 为真却哈希不同，可能被放入不同位置，表现为查找失败或逻辑重复元素同时存在。

`equals` 还应满足自反、对称、传递、一致和对 `null` 为假等约定。

**追问 2：自定义对象作为 key 后，修改参与 `equals` 或 `hashCode` 的字段，再执行查找或删除会怎样？**

对象放入容器后，容器不会因为字段变化自动重新分桶。

- 用变化后的哈希去查询，可能找不到原节点；改变比较字段也会破坏逻辑去重。即便迭代还能看到它，也不代表查询删除正常。
- 应避免修改作为键的相等性字段，或先移除、修改后重新插入。

**追问 3：为这类 key 设计不可变字段或独立业务标识时，需要保留哪些相等性规则？**

使用稳定且不可变的业务 ID，或对参与相等性判断的字段进行不可变设计。

- 必要约束是“`equals` 为真时，`hashCode` 必须相同”，不是强制两个方法逐字使用完全相同的字段集合；哈希只使用相等性字段的子集，甚至固定返回一个值，也可能满足契约，但会增加冲突。
- 实际实现通常选取与逻辑身份一致且分布较好的字段。
- 数据库新对象尚未分配 ID、跨类型继承比较等情况也需约定，避免对象入集合后改变身份。

### 15. `String` 的不可变性体现在哪些方面？

`String` 创建后其字符序列不能通过正常公开 API 改变，所谓修改通常是生成新字符串。

- 不可变性使共享、作为哈希键和缓存哈希等操作更容易保持稳定。
- `StringBuilder` 和 `StringBuffer` 则是可变缓冲区，适合多次拼接后一次生成字符串。

**追问 1：频繁拼接字符串时，`String`、`StringBuilder` 与 `StringBuffer` 分别有哪些代价？**

循环反复拼接不可变字符串可能产生大量中间对象和复制；编译器会优化某些拼接表达式，但不能据此忽略循环成本。

`StringBuilder` 通过可扩容缓冲区追加，`StringBuffer` 还为相应方法提供同步。容量预估、最终结果大小也会影响开销。

**追问 2：单线程局部拼接与多个线程共享同一个缓冲对象，应如何选择？方法本身线程安全是否等于多个调用组合也安全？**

单线程局部拼接通常选择 `StringBuilder`；共享缓冲区可采用外部同步或合适的 `StringBuffer` 方法，但“先检查长度，再追加”之类复合操作仍需整体保护。

更常见的做法是每个任务独立构建结果，避免共享可变缓冲区。

### 16. 字符串字面量、`new String` 与 `intern` 的对象共享行为有什么区别？

字符串字面量与编译期常量字符串共享驻留字符串。

- `new String("abc")` 会创建新的 `String` 对象，因此与字面量的引用身份不同，但内容相等。
- `intern()` 返回该内容的驻留表示；已有相同内容时返回已有驻留对象，否则建立该内容对应的驻留关系。

**追问 1：请分别比较对象身份与字符串内容，说明字符串常量池的作用。**

`"abc" == "abc"` 为真，`new String("abc") == "abc"` 为假，而两者 `equals` 为真；`new String("abc").intern() == "abc"` 为真。

常量池用于共享内容相同的驻留字符串，不意味着所有运行时拼接自动驻留，也不意味着业务比较应使用 `==`。

### 17. 受检异常、运行时异常与 `Error` 有什么区别？

受检异常要求调用方捕获或在方法签名中声明，适合表达接口要求明确处理的失败；`RuntimeException` 及其子类不受该编译期要求约束；`Error` 通常表示较严重的运行环境或虚拟机问题。

业务设计不应只按“会不会崩溃”分类，而应说明调用方能否合理恢复、补偿或拒绝请求。

**追问 1：参数错误、业务拒绝与底层服务失败，应在什么边界捕获、转换或继续抛出？**

参数错误在入口校验，业务拒绝使用明确业务结果或异常，底层超时等在服务边界转换为稳定语义并保留原始原因。

能处理才捕获，不具备恢复能力时继续传播；不要层层重复打印相同堆栈，也不要随意捕获全部 `Throwable` 后假装恢复。

**追问 2：捕获异常后只打印日志再返回成功，会怎样影响调用方、事务和后续重试？**

调用方会误认为成功，可能继续执行后续步骤；事务代理观察不到异常时还可能提交；重试与告警也失去正确触发信号。

应返回真实失败或继续抛出，让事务按规则回滚，并通过幂等和明确的可重试分类决定后续处理。

### 18. 阅读以下代码，判断返回结果，并解释 `try` 与 `finally` 的执行关系。

```java
static int calculate() {
    int value = 1;
    try {
        return value;
    } finally {
        value = 2;
        return value;
    }
}
```

调用 `calculate()`，分别分析原代码及追问中的变体。

原代码返回 2。`try` 中先计算待返回的 1，但方法真正退出前会执行 `finally`；`finally` 自己的 `return 2` 覆盖了原返回动作。

这种写法容易掩盖结果或异常，生产代码通常只在 `finally` 中做清理，不在那里返回。

**追问 1：删除 `finally` 中的 `return` 后，结果如何变化？**

删除 `finally` 中的 `return` 后返回 1。

- `try` 中的返回表达式已求值得到基本类型值 1，随后把局部变量改为 2，不会改变已保存的返回值。
- 如果返回的是可变对象引用，而 `finally` 修改对象内容，调用方可能观察到对象内容变化，应区分这两种情形。

**追问 2：如果 `try` 中抛出异常，而 `finally` 仍然 `return`，调用方还能否观察到原异常？怎样改写更合适？**

原异常会被 `finally` 的返回动作覆盖，调用方看不到它。

应让 `finally` 只释放资源；资源支持 `AutoCloseable` 时优先使用 `try-with-resources`，以保留主异常和关闭阶段的被抑制异常。需要转换异常时，显式保留 cause。

### 19. Java 泛型提供了哪些编译期检查？

泛型让容器元素、方法参数和返回值之间的类型约束在编译期表达出来，减少强制转换和类型误用。

Java 主要通过类型擦除实现泛型：类型变量擦除为上界或 `Object`，编译器在必要位置插入转换，并可能生成桥接方法，维持重写行为。

**追问 1：类型擦除后，运行时还能够获得哪些类型信息？**

普通对象通常不携带完整的实际泛型实参，不能从任意 `ArrayList<String>` 实例直接获得元素类型。

但类、字段、方法等声明的泛型签名可保存在 class 文件中，并通过反射读取；匿名子类保留声明参数的技巧利用的是这类元数据，不是泛型完全没有擦除。

**追问 2：为什么不能通过 `Object` 引用上的 `instanceof List<String>` 验证列表元素类型？`List<?>` 与原始类型 `List` 在读写和类型检查上有何区别？**

若被测表达式的静态类型为 `Object`，不能写 `obj instanceof List<String>` 来证明所有元素都是字符串，因为运行时没有足够信息检查这个泛型实参；

- 可以用 `obj instanceof List<?>` 判断是不是列表，再逐个校验元素。
- `List<?>` 表示元素类型未知，读取通常得到 `Object`，不能随意加入非空对象；原始 `List` 绕过部分泛型检查，可能产生堆污染。
- 不要把限制扩大成“任何版本、任何上下文都不能对参数化类型使用 `instanceof`”。
- Java 16 起放宽了部分可安全检查的类型转换，例如从 `List<String>` 测试 `ArrayList<String>` 可以合法，但仍不是逐个验证元素，也不能消除之前由原始类型写入造成的堆污染。

### 20. 泛型中的 `extends`、`super` 与无界通配符分别适合什么场景？

可按 PECS 理解：只把容器当作某类值的生产者时用 `? extends T`，把它当作接收该类值的消费者时用 `? super T`。

- 无界 `?` 适合只关心容器而不依赖具体元素类型的操作。
- 通配符限制的是类型安全的读写能力，不是给容器加上运行时只读锁。

**追问 1：从一个容器读取数值，以及把整数写入另一个容器时，分别如何使用 `extends` 和 `super`？**

`List<? extends Number>` 可以按 `Number` 读取，但不知道具体是整数还是浮点列表，不能随意添加一个 `Number`。

- `List<? super Integer>` 可以写入 `Integer`，读取时只能可靠地按 `Object` 接收。
- 需要同时以同一具体类型读写时，使用类型参数 `T` 往往更清楚。

**追问 2：为什么 `List<Integer>` 不能直接赋给 `List<Number>`？若允许这样赋值，会破坏什么类型约束？**

假设允许 `List<Integer>` 赋给 `List<Number>`，随后就能通过后者加入 `Double`，破坏原列表只包含整数的约束，因此泛型默认不协变。

通配符通过限制某些写入或读取操作，在保留安全的前提下表达所需变化关系。

### 21. 自定义注解如何声明、读取并参与业务处理？

使用 `@interface` 声明注解，并通过 `@Target` 规定作用位置、`@Retention` 规定保留阶段。

- 运行时处理需要 `RUNTIME` 保留策略，再由反射、AOP 或框架处理器读取元数据并执行逻辑。
- 注解本身只是声明信息，不会独立完成校验、日志或权限检查。

**追问 1：以校验或操作日志为例，说明注解本身与读取注解并执行逻辑的代码各自负责什么。**

例如方法标注 `@OperationLog("创建订单")`，切面读取标记，在调用前后记录操作与结果；字段校验注解则由校验器执行规则。

还应规定异常路径、敏感数据脱敏和代理调用边界，不能只写上注解就认为所有调用已经被拦截。

### 22. Java 反射机制如何支持框架在运行时创建对象和调用方法？

反射通过 `Class`、`Constructor`、`Method`、`Field` 等元数据，在运行时查看类型、调用构造器、读写字段和调用方法。

- 框架可根据配置或注解选择实现，而不在编译期写死所有目标类。
- 它提供的是动态能力，不是必须使用的通用替代方案。

**追问 1：相较于直接调用，反射在类型检查、访问控制与执行开销上有哪些取舍？**

直接调用通常有更明确的编译期检查和更好的优化机会；反射错误更容易在运行时暴露，还涉及参数包装、访问检查和调用开销。

`setAccessible` 也不能无条件绕过模块封装和所有安全限制，应使用受支持的开放方式，而不是依赖私有实现细节。

**追问 2：框架缓存反射信息后，减少的是哪部分重复工作？业务代码什么时候不需要引入反射？**

缓存可以减少重复查找方法、扫描注解、解析字段等工作；它不会自动消除每次调用、参数转换及业务执行成本。

目标类型和调用关系明确的普通业务代码，直接调用或接口多态更清楚；确有插件、映射、序列化等动态需求时再使用反射。

### 23. Java SPI 如何实现接口与具体实现的解耦？

SPI 由框架定义服务接口，实现方提供实现与注册信息，调用方通过发现机制加载提供者。

- 传统 classpath 下，`ServiceLoader` 可读取 `META-INF/services/接口全限定名`；模块系统还支持 `uses`、`provides` 声明。
- 调用方依赖契约，不必把每个具体实现写入核心代码。

**追问 1：接口调用方为什么可以不直接依赖某个实现类？实现是怎样被发现和选择的？**

实现类被运行时配置和类加载器发现，调用方拿到的仍是接口类型。

发现不等于自动做完选择：多个实现如何按名称、能力或优先级匹配，需要框架制定规则，不能默认使用“碰巧第一个”。

**追问 2：存在多个实现或第三方扩展时，如何组织配置与加载，并处理实现缺失或初始化失败？**

规范实现名称、依赖、兼容版本和选择规则，必要时校验唯一性。

提供者可能延迟加载，配置错误或初始化失败可能在迭代时暴露；应明确是启动失败还是跳过非关键扩展，并记录真实错误，避免应用运行很久才发现必需实现缺失。

### 24. 对象序列化时，如何控制字段是否参与序列化以及版本兼容？

使用 Java 原生序列化时，非静态且非 `transient` 的实例字段通常参与默认序列化；需要更精细的控制可实现自定义读写逻辑。

- 版本兼容要同时考虑类型标识、字段变化和业务语义。
- 不要把不可信来源的原生序列化数据直接反序列化为任意对象。

**追问 1：`serialVersionUID` 与 `transient` 各起什么作用？**

`serialVersionUID` 用于序列化兼容性检查，流与本地类不匹配会导致 `InvalidClassException`，但编号相同并不自动保证业务兼容。

`transient` 排除默认序列化中的对应实例字段，反序列化后通常恢复为默认值，除非自定义逻辑补回；它不是加密或通用隐私保护机制。

### 25. 懒汉式单例采用双重检查锁时，为什么需要两次判空和 `volatile`？

双重检查锁先在无锁路径检查是否已初始化，减少初始化完成后的锁开销；进入锁后再次检查，防止多个竞争线程重复创建。

实例引用使用 `volatile`，保证构造完成与引用发布之间的正确可见性和顺序。示例基于 Java 5 及之后的内存模型：

```java
public final class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        Singleton value = instance;
        if (value == null) {
            synchronized (Singleton.class) {
                value = instance;
                if (value == null) {
                    value = new Singleton();
                    instance = value;
                }
            }
        }
        return value;
    }
}
```

**追问 1：第一次判空和进入锁后的第二次判空分别避免什么问题？**

第一次判空使已经初始化的调用直接返回；第二次判空负责正确性。

两个线程都可能在外层看到空，一个线程完成创建后，另一个获得锁时必须重新判断，否则仍会创建第二个对象。

**追问 2：对象创建和引用发布之间有哪些步骤？省略 `volatile` 时，另一个线程可能观察到什么状态？**

从理解上可分为分配空间、执行初始化和发布引用。

- 缺少安全发布约束时，其他线程可能观察到非空引用，却未观察到完整初始化状态。
- `volatile` 写与后续读建立发布和获取关系；只保证初始化路径内部互斥，不能自动保护外层无锁读取。

**追问 3：除了双重检查锁，能否选择更简单的单例写法？比较时应保留哪些初始化与并发要求？**

可采用静态内部类持有者，由类初始化机制实现延迟初始化与线程安全；不需要同样的延迟控制时可使用枚举单例。

还要比较序列化、反射、类加载器隔离及测试替换需求；单例初始化安全不代表它的所有可变业务字段都安全。

### 26. 静态内部类单例、枚举单例与双重检查锁单例有什么区别？

静态内部类利用持有者类首次主动使用时的初始化保证，实现简洁的懒加载；枚举提供语言和序列化层面的单例支持；双重检查锁可显式控制创建过程，但同步和发布细节更多。

三者都只在相应的类加载器范围内讨论唯一性，不是跨进程单例。

**追问 1：如何比较延迟初始化、并发安全，以及反射或序列化带来的影响？**

内部类在访问持有者时初始化，枚举在枚举类初始化时创建常量，双重检查锁在首次成功竞争时创建。

- 普通类还需考虑反射构造和反序列化产生新实例，必要时使用 `readResolve` 等；枚举的反射构造和序列化处理有专门约束。
- 能采用简单方式时，不必为了展示技巧坚持双重检查锁。

### 27. 浅拷贝与深拷贝有什么区别？

浅拷贝创建新的外层对象，但内部引用字段仍可能指向原对象；深拷贝按约定复制需要独立的可变对象图，使后续修改互不影响。

深拷贝不是必须复制所有东西：字符串等不可变对象可以安全共享，数据库连接、锁等资源也不能机械复制。

**追问 1：外层对象被复制后，内部可变集合或引用对象是否仍被共享？**

例如复制 `Order` 后，如果 `items` 仍是同一个 `List`，给副本增加明细会影响原对象。

即使列表本身被复制，列表中的可变 `Item` 仍可能共享，必须逐层判断需要独立到什么程度。

**追问 2：需要得到独立可修改的副本时，复制构造、显式递归复制与序列化复制应怎样取舍？**

复制构造和显式复制最容易表达业务边界，代价是维护代码；递归复制要处理循环引用和共享身份；序列化复制通常更重，并依赖类型、字段和格式兼容。

优先复制真正需要修改的状态，明确资源字段如何处理，不把“换个容器”误认成完整深拷贝。

### 28. 面对大量 if-else 和持续增加的业务类型，如何利用策略、工厂或模板方法组织代码？

先找出变化维度。不同业务策略遵循同一调用契约，可提取策略接口；如何创建或查找策略由工厂或注册表负责；多个实现具有稳定执行骨架而部分步骤变化，可使用模板方法。

改造目标是让新增业务只增加局部实现，不是简单地把 if-else 移到另一个超大方法。

**追问 1：如何区分算法选择、对象创建与流程骨架这几类扩展需求？**

策略解决“本次用哪种行为”，工厂解决“对象如何创建或取得”，模板方法解决“流程顺序固定、哪些步骤允许替换”。

- 例如订单结算固定校验与落单流程，优惠算法使用策略，支付实现通过注册表选择。
- 只有两三个稳定分支时，直接条件判断也可能更清晰。

### 29. 代理模式、装饰器模式与适配器模式分别在改变什么？

代理主要控制对目标对象的访问，如鉴权、远程调用和延迟加载；装饰器保持相同核心接口，按组合叠加功能；适配器把已有接口转换为调用方期望的接口。

它们结构可能相似，区分依据是设计意图与接口关系，而不是是否“包了一层”。

**追问 1：为接口适配、权限控制和功能叠加各选择一种方案，并说明为什么不是另外两种。**

对接字段和方法不匹配的外部 SDK 用适配器；在调用前验证权限用代理；为输出流叠加缓冲、压缩等能力用装饰器。

适配器不是主要用于决定是否放行，代理也不应为了控制访问顺带改变调用契约，装饰器的重点则是可组合增强。

### 30. 观察者模式与责任链模式如何组织多个处理者？

观察者描述一个事件源向多个订阅者发布变化，强调一对多通知；责任链让请求沿处理者链流转，由每个处理者决定处理、继续或终止，强调处理顺序与传递规则。

二者都需要明确同步、异步和异常策略，模式名称不会自动给出可靠性保证。

**追问 1：通知订阅者与按顺序执行校验规则有什么区别？**

订单事件通知统计、消息和积分属于观察者式解耦；参数、权限和额度依次校验属于责任链。

前者各订阅者通常相互独立，后者前一步拒绝往往意味着后续不能继续。

**追问 2：某个处理者失败时，后续处理如何决定？**

校验链失败应中止并返回明确原因；非关键事件监听失败可隔离、记录或重试；必须可靠完成的副作用应持久化事件和处理状态。

规则应在接口中明确，而不是任由异常传播顺序决定业务结果。

### 31. Lambda 与函数式接口如何配合？

Lambda 是函数式接口的一种简洁实现表达式，目标接口必须满足单个抽象方法的约束；默认和静态方法不计入该抽象方法数量。它适合传递一段行为，如比较规则和回调。

Lambda 不是完全没有类型的独立函数，类型由上下文中的目标接口确定。

**追问 1：它与匿名内部类有什么使用差异？**

匿名内部类声明一个匿名类，可定义自己的字段和方法；Lambda 更聚焦于行为，并且其中的 `this` 指向外层上下文，而不是新的匿名类对象。

Lambda 的实现与实例复用由运行时决定，不应依赖其对象身份做同步或业务判断。

**追问 2：Lambda 捕获局部变量时受到什么限制？**

捕获的局部变量必须是 `final` 或事实不可变，也就是赋值后不再重新绑定。

- 但引用所指对象仍可变，例如可以修改捕获列表的内容，这并不自动线程安全。
- 并发回调需要另外保护共享对象，不能把“引用不能重赋值”当成“对象不可变”。

### 32. 如何使用 `Stream` 对用户列表完成过滤、分组和汇总？

已定义 `User` 类，包含 `Long id`、`String name`，并提供 `getId()`、`getName()` 方法。给定用户列表：

```text
(1, "张三")
(null, "李四")
(1, "王五")
(2, "赵六")
```

写出一个 `Stream` 表达式：忽略 ID 为空的用户，将其余姓名按 ID 分组，结果类型为 `Map<Long, List<String>>`。

先过滤无效 ID，再按 ID 分组，分组内通过 `mapping` 收集姓名。

题设结果是 ID 1 对应张三、王五，ID 2 对应赵六；默认分组 Map 不保证键的遍历顺序。示例采用 Java 8 API：

```java
Map<Long, List<String>> result = users.stream()
    .filter(Objects::nonNull)
    .filter(user -> user.getId() != null)
    .collect(Collectors.groupingBy(
        User::getId,
        Collectors.mapping(User::getName, Collectors.toList())));
```

需要导入 `java.util.*` 和 `java.util.stream.Collectors`；`User` 按题设定义。

**追问 1：先过滤空 ID，再按 ID 收集多个姓名，应怎样组合中间操作与终止操作？**

`filter`、`map` 等中间操作描述流水线，通常在终止操作触发时才执行；`collect` 是这里的终止操作。

`groupingBy` 接收分组键提取函数，`mapping` 再把组内的 `User` 转换为姓名，不能用普通 `toMap` 默认逻辑直接接收重复键。

**追问 2：如果改为每个 ID 仅保留一个姓名，重复键的处理规则应如何显式表达？**

使用带合并函数的 `toMap(User::getId, User::getName, (oldValue, newValue) -> oldValue)` 可保留先遇到的值，改为返回 `newValue` 则保留后者。

还要明确姓名是否允许为空、流是否有稳定顺序；业务要求“最新记录”时应按时间比较，而不是含糊地依赖遍历次序。

### 33. 为什么 `parallelStream` 不一定更快？

并行流需要拆分数据、调度任务、合并结果，这些开销可能超过并行收益。

- 它更适合规模足够、可拆分、计算密集且操作相互独立的任务。
- 共享线程资源、阻塞调用和副作用都会使表现变差，不能仅把 `stream()` 改成 `parallelStream()` 就认定完成了优化。

**追问 1：使用它时需要检查哪些共享状态与任务特征？**

检查数据规模与可拆分性、每个元素的计算量、是否有顺序要求、合并操作是否满足结合律，以及是否修改共享集合或上下文。

使用非线程安全结果容器、依赖 `ThreadLocal` 或执行不可交换的累计逻辑，都可能造成错误。

**追问 2：阻塞调用、数据量过小或有副作用的操作，分别可能带来什么问题？**

阻塞可能占住共享 `ForkJoinPool` 的工作线程，影响其他任务；小任务容易被调度成本淹没；副作用既可能产生竞态，也可能因加锁抵消收益。

应使用无共享副作用的归约，并在接近真实负载下比较吞吐和分位延迟；阻塞业务更适合有界且显式管理的执行方案。

### 34. `Optional` 如何表达“可能没有结果”，又不能替代哪些空值处理？

`Optional<T>` 是明确表达“可能没有一个 T 结果”的返回类型，使调用方必须面对缺失情况，但它不能代替参数校验、集合空元素治理或所有字段设计。

`Optional` 自身不应为 `null`，也不宜为了形式统一而把任何字段都包一层。

**追问 1：`of`、`ofNullable`、`empty`、`map` 与 `flatMap` 分别适合什么数据处理方式？**

`of` 要求值非空，`ofNullable` 接受可空值，`empty` 表示缺失；`map` 对存在值做普通转换，`flatMap` 适合转换本身已经返回 `Optional` 的情况，避免多层嵌套。

缺失状态会沿这类转换继续传播，直到业务边界处理。

**追问 2：默认值需要执行数据库查询时，`orElse` 与 `orElseGet` 会有什么求值差异？**

`orElse(loadFromDatabase())` 的参数会先求值，即使已有结果也会执行查询；`orElseGet(this::loadFromDatabase)` 只在缺失时调用供应函数。

默认值生成昂贵或有副作用时，应特别注意这种差异。

**追问 3：返回 `Optional` 后再无条件调用 `get`，是否真正消除了空值风险？如何在业务边界明确处理缺失结果？**

无条件 `get()` 在缺失时仍会抛出 `NoSuchElementException`，只是换了一种失败。

可使用 `orElseThrow` 抛出明确业务异常、提供合理默认值，或者分支处理“未找到”。不要把需要拒绝的场景悄悄转成空对象。

### 35. `Instant`、`LocalDateTime` 与 `ZonedDateTime` 分别表达什么时间信息？

`Instant` 表示时间线上的一个真实时刻；`LocalDateTime` 只有本地日期和时分秒，不含时区，不能独立确定全球唯一时刻；`ZonedDateTime` 同时关联时区规则。

持久化、计算和显示应区分真实时刻与当地日历规则，避免把服务器默认时区作为隐含业务前提。

**追问 1：跨时区系统保存一个真实发生的时刻，与保存“每天当地时间 9 点执行”的规则，应如何选择类型？**

事件发生时间通常保存 `Instant` 或统一时间基准，显示时再转换时区；“每天当地 9 点”应保存当地时间和地区时区 `ZoneId`，逐日根据规则计算下一次触发时刻，而不是固定每 24 小时累加。

**追问 2：夏令时切换可能使某个当地时间不存在或出现两次，系统应怎样规定处理方式？**

夏令时前进可能产生不存在的本地时间，回拨可能使同一时间出现两个偏移。

- 业务要明确跳过、顺延或选择早/晚偏移，并保存足够信息防止任务重复执行。
- API 的默认解析策略可以作为实现，但必须确认与业务规则一致。

**追问 3：多线程格式化时间时，`DateTimeFormatter` 与 `SimpleDateFormat` 的使用边界有什么区别？**

`DateTimeFormatter` 不可变且线程安全，可以共享；`SimpleDateFormat` 有可变状态，不应未经同步被多线程共享。

新代码优先使用 `java.time`，并明确格式、时区和语言环境；外部输入解析还应校验严格程度，避免宽松解析接受非法日期。

### 1. 需要保留顺序、允许重复、按键查找或自动去重时，分别如何选择 `List`、`Set`、`Queue` 与 `Map`？

| 比较项 | 特点与用途 |
|---|---|
| List | `List` 表达有位置顺序、允许重复的序列 |
| Set | `Set` 表达不重复元素的集合 |
| Queue | `Queue` 表达按某种出队规则处理任务，不一定都是先进先出 |
| Map | `Map` 表达键到值的映射，键唯一 |

选型还要看是否需要排序、并发访问、容量上限以及主要操作成本，不能只按容器名称选择。

**追问 1：请为待处理任务、用户去重和 ID 查询各选一种集合，并说明理由。**

普通待处理任务可用 `ArrayDeque`，多线程生产消费可用有界 `BlockingQueue`；

- 用户去重可用以稳定用户 ID 为元素的 `HashSet`；
- 按 ID 查询对象可用 `HashMap<ID, Object>`。
- 若要保留插入顺序可用 `LinkedHashSet` 或 `LinkedHashMap`；若需按键排序再考虑树结构。

### 2. 需要栈、普通队列或双端队列时，如何选择 `Deque`、`ArrayDeque` 与 `LinkedList`？

| 比较项 | 特点与用途 |
|---|---|
| Deque 接口 | `Deque` 是双端队列接口，可在两端操作，也能作为栈使用 |
| ArrayDeque | `ArrayDeque` 基于可扩容数组，通常适合局部栈和队列 |
| LinkedList | `LinkedList` 基于双向链表，同时实现 `List` 与 `Deque`，但节点和指针开销更大 |

选择要结合操作位置，而不是认为链表一定更快。

**追问 1：头尾插入、读取和删除分别对应哪些方法？返回特殊值的方法与抛异常的方法有什么区别？**

头尾插入可用 `addFirst/addLast` 或 `offerFirst/offerLast`；

- 删除可用 `removeFirst/removeLast` 或 `pollFirst/pollLast`；
- 查看可用 `getFirst/getLast` 或 `peekFirst/peekLast`。
- `remove/get` 在空队列时抛异常，`poll/peek` 返回特殊值；栈的 `push/pop` 对应同一端的插入删除。
- `ArrayDeque` 不允许 `null` 元素。

**追问 2：为什么不能把普通 `ArrayDeque` 直接当成多线程共享队列？如何处理容量和线程安全要求？**

`ArrayDeque` 本身不提供线程安全和阻塞等待。

- 多线程需要外部同步或选择并发队列；生产消费需要容量与背压时用有界 `BlockingQueue` 或 `BlockingDeque`。
- 无界并发队列只解决并发访问，不解决过载时内存无限增长。

### 3. `PriorityQueue` 如何维护优先级，它是否保证遍历结果整体有序？

`PriorityQueue` 通常基于数组二叉堆，保证队首是比较规则下优先级最高的元素，默认是最小元素；它不保证内部数组或迭代结果整体有序。

需要完整有序输出，可以反复 `poll`，或复制后排序；不能直接把迭代器输出当排序结果。

**追问 1：插入、查看队首、删除队首和删除任意元素的主要成本分别是什么？**

插入和删除队首通常为 `O(log n)`，查看队首为 `O(1)`；按对象查找或删除任意元素通常先线性定位，整体为 `O(n)`。扩容还可能有数组复制成本。堆只维护父子之间的偏序，并没有全局排序。

**追问 2：自定义比较器时如何处理同优先级任务？元素入队后修改参与比较的字段会有什么风险？**

同优先级元素默认不保证稳定顺序，可在比较器中追加单调序号作为第二关键字。

- 比较数值应使用 `Integer.compare` 等，避免相减溢出。
- 入队后修改排序字段不会自动重建堆，应先移除再修改后重新插入，或使用不可变任务描述。

**追问 3：多线程任务调度应如何选择并发优先队列，并防止低优先级任务长期得不到执行？**

`PriorityBlockingQueue` 提供线程安全的优先级队列，但通常是无界的，仍需外部控制待处理规模。

低优先级任务防饥饿可用老化提升、多队列配额或最长等待时间策略；优先队列本身不会自动提供这些业务公平性保证。

### 4. `ArrayList` 的扩容过程和数据搬迁成本是什么？

`ArrayList` 用数组保存元素引用，容量不足时申请更大数组并复制原内容。

- 以 JDK 8 为例，常规增长基于旧容量的约 1.5 倍，同时确保满足本次最小容量要求。
- 追加平均为摊销 `O(1)`，但触发扩容的那一次包含 `O(n)` 复制，不能理解成每次追加都恒定耗时。

**追问 1：以 JDK 8 为例，第一次添加元素和容量不足时分别如何分配数组？扩容需要复制哪些内容？**

默认无参构造最初使用空数组，第一次添加通常分配容量 10；指定容量或其他构造方式的路径不同。

- 扩容复制的是数组中的引用值，不会深拷贝每个业务对象。
- 大规模写入时，短暂同时持有新旧数组也会增加峰值内存。

**追问 2：按下标访问、在中间位置插入和删除元素，各自的主要成本是什么？**

按下标访问为 `O(1)`；中间插入和删除要搬移后续引用，通常为 `O(n)`；按值删除还需先查找。

尾部追加不扩容时成本低，尾部删除通常也不需要整体搬移。

**追问 3：已知批量写入规模时，预设容量如何影响扩容次数、复制成本和闲置内存？**

根据预期元素数量指定初始容量或使用 `ensureCapacity`，可以减少重复扩容和复制；但估得过大又会长期保留空闲引用槽。

应按批次和数据规模估算，不要给每个小列表都预留巨大容量。

### 5. `ArrayList` 与 `LinkedList` 应如何根据访问方式选择？

| 比较项 | 特点与用途 |
|---|---|
| ArrayList | `ArrayList` 擅长按下标访问、连续遍历和尾部追加，内存布局更紧凑 |
| LinkedList | `LinkedList` 的随机定位要沿节点查找，只有已经定位到节点的迭代器附近插入删除才具有局部优势 |

常规业务列表通常优先考虑 `ArrayList`，再根据实际访问模式验证。

**追问 1：按下标随机访问、尾部追加、已定位节点后的插入与按值删除，各自需要完成哪些操作？**

`ArrayList` 随机访问为 `O(1)`，中间增删需要搬移；`LinkedList` 按下标访问通常为 `O(n)`，通过已定位的 `ListIterator` 插入删除可在局部完成。

按值删除两者都通常先查找；尾部追加在容量充足数组或链表尾指针可用时都很便宜。

**追问 2：“链表适合频繁增删”为什么不能脱离定位成本、内存占用与缓存局部性单独判断？**

链表节点要额外保存前后引用，节点分散还可能降低缓存局部性。

- 业务常见的“删除第 k 个”仍需先定位，不能只计算最后断开链接的两三次赋值。
- 数组批量移动通常也经过优化，最终应通过真实数据规模测试。

**追问 3：业务需要高频遍历和偶尔批量删除时，你会选择哪一种结构，如何验证选择？**

高频遍历通常选择 `ArrayList`；批量删除可使用 `removeIf` 或构建保留元素的新列表，避免逐个中间删除造成大量重复搬移。

验证时同时比较吞吐、分配量、内存和延迟，而不只在几个元素上测一次耗时。

### 6. `ArrayList` 的 subList、`Arrays.asList` 与独立复制的 `List` 有什么区别？

`subList` 是原列表的区间视图，`Arrays.asList` 是指定数组的固定大小列表视图；`new ArrayList<>(source)` 则复制容器中的元素引用，得到独立结构。

前两者与原存储存在关联，第三种只复制结构而不自动深拷贝元素。

**追问 1：逐一判断视图与原容器是否共享数据，以及是否支持增删。**

`ArrayList.subList` 的元素设置和合法结构操作会反映到原列表；`Arrays.asList` 支持 `set`，但不支持改变长度的增删，并会反映到原数组。

独立 `ArrayList` 支持增删，结构变化不影响原容器，但内部可变元素仍可能共享。

**追问 2：保留 subList 后再修改原列表结构，后续访问可能出现什么问题？需要独立修改时应该如何复制？**

通过视图之外的路径结构性修改原列表后，继续使用 `subList` 的行为不再有稳定保证，常见表现为 `ConcurrentModificationException`。

需要独立修改时用 `new ArrayList<>(source.subList(from, to))`；需要元素也独立时，再按业务复制可变对象。

### 7. 以 JDK 8 为例，`HashMap` 的 `put` 和 `get` 如何完成寻址、哈希冲突处理与键匹配？

JDK 8 `HashMap` 以数组保存桶，桶内使用链表或红黑树处理冲突。

1. **计算哈希：** 先对 key 的哈希进行扰动。
2. **定位桶：** 再利用数组长度定位桶。
3. **匹配键：** 最后结合哈希和 `equals` 判断是否为同一个键。
4. **写入结果：** 已有相等键时替换值，新的键才新增映射。

**追问 1：从 key 的 `hashCode` 到数组下标，再到键匹配，分别经过哪些处理？**

非空 key 先取 `hashCode()`，通过 `h ^ (h >>> 16)` 混合高低位；下标通常为 `(capacity - 1) & hash`。空 key 的哈希按 0 处理。

扰动和下标选择只是定位过程，不能取代相等性判断。

**追问 2：目标桶为空、存在不同 key 的冲突、已存在相等 key 时，`put` 的处理有什么区别？**

空桶直接建立节点；非空桶先检查是否已有相等键，若有则更新对应值；若没有则沿链表追加，或在树中插入，并按条件进行树化或扩容。

修改已有映射不等于新增一个元素，`size` 不应因此增加。

**追问 3：`get` 如何沿同一访问路径找到值？为什么哈希相同还需要比较 key？**

`get` 使用相同的哈希与下标定位，再检查桶首、链表或树。

不同对象可能产生相同哈希，甚至不同哈希映射到同一个桶，所以还必须比较键；否则哈希冲突就会被误判成同一条业务记录。

### 8. `HashMap` 为什么要求容量为 2 的幂，扩容时如何迁移已有元素？

容量为 2 的幂时，可以使用掩码快速定位，并让容量翻倍后的迁移只依赖一个新增的哈希位。

- 旧桶中的节点要么留在原下标，要么移动到“原下标＋旧容量”。
- 这让迁移不必重新调用每个 key 的 `hashCode()`，但仍需要遍历和搬移节点。

**追问 1：长度为 2 的幂怎样影响下标计算？负载因子控制什么？**

`(n - 1) & hash` 取哈希低位，要求 n 是 2 的幂才能按这种规则覆盖各桶。

负载因子决定容量与扩容阈值的关系，默认通常为 0.75；它是空间与冲突的折中，不是每个桶都必须填满后才扩容。

**追问 2：扩容后一个旧桶中的元素怎样分散到新桶，为什么不必完全重算所有定位信息？**

对旧容量 `oldCap`，检查 `(hash & oldCap)`。

- 为 0 的节点留在低位链，为非 0 的节点进入高位链；JDK 8 普通链表拆分保留各自相对次序。
- 迁移是重新组织桶，不是深拷贝业务 key/value。

**追问 3：预计写入 1000 个键值对时，如何考虑初始容量与负载因子，减少中途扩容？**

默认负载因子下要使阈值至少容纳 1000 个元素，可按 `ceil(1000 / 0.75)` 估算构造容量，最终数组容量会取适当的 2 的幂，通常为 2048，阈值为 1536。

直接 `new HashMap<>(1000)` 通常先得到容量 1024、阈值 768，写到 1000 时仍会扩容。

### 9. JDK 8 的 `HashMap` 为什么引入红黑树，链表树化与退化需要满足哪些条件？

树化用于改善严重哈希冲突下长链表的查找退化。JDK 8 的相关常量是树化阈值 8、扩容拆分时的退化阈值 6、最小树化容量 64。

实际转换要看代码路径：普通 `put` 向已有 8 个节点的链表再加入节点时会尝试树化；容量不足 64 时优先扩容。

**追问 1：为什么不能只看链表长度决定是否树化，还需要考虑数组容量？**

数组较小时，冲突可能主要来自桶数量不足，扩容可以把原桶拆开，比建立较重的树节点更合适。容量较大仍存在长链才更值得树化。

红黑树改善常见查找复杂度，但面对大量完全同哈希且不可比较的键，也不能无条件承诺每次查找都是严格 `O(log n)`。

**追问 2：树化与退化采用不同条件，可以避免什么反复转换？**

滞后条件可减少临界长度附近反复转换。要特别区分扩容拆分和普通删除：拆分树桶时，分支节点数不超过 6 会转链表；普通删除还根据树形结构判断，不是任何删除路径都机械执行“剩 6 个就退化”。面试中报出常量后，应说明路径边界。

**追问 3：JDK 7 与 JDK 8 的冲突处理、迁移方式和并发风险有哪些不同？**

JDK 7 主要是数组加链表，迁移中的头插及并发修改可能形成环；JDK 8 引入树桶和新的拆分迁移方式，但仍有并发覆盖、丢失更新和结构状态竞争。

修复某个旧版死循环风险，不等于 `HashMap` 已经线程安全。

### 10. 多个线程分别向 `HashMap` 写入不同的 key，为什么仍不能保证线程安全？

线程使用不同 key 也会竞争共享的桶数组、桶节点、计数和扩容状态。

- key 不同不意味着一定落入不同桶，即使落入不同桶，也可能同时触发扩容或修改公共元数据。
- 因此普通 `HashMap` 不支持未经同步的并发写入。

**追问 1：即使 key 带有不同线程 ID 前缀，哪些内部状态仍会被同时修改？**

共享状态包括 `table`、`size`、扩容阈值、桶首和链表或树链接。

线程 ID 前缀只能改变业务键，不会给内部结构增加原子性或可见性保证。

**追问 2：并发插入与并发扩容分别可能造成什么后果？只保证单次写入互斥是否足以覆盖完整业务流程？**

并发插入可能覆盖节点或使计数不准确，扩容期间还可能丢失元素或破坏访问路径。

只锁单次 `put` 不能保护“查无记录后插入”等复合操作；需要统一保护整个业务临界区，或使用 `ConcurrentHashMap` 的原子组合方法。

### 11. 集合迭代过程中直接增删元素，为什么可能触发 `ConcurrentModificationException`？

很多普通集合的迭代器会保存预期修改计数，与集合当前修改计数比较，以尽早发现迭代期间的结构变化。

这是 fail-fast 检错机制，不是同步机制，也不保证对所有错误并发访问都能抛异常。

**追问 1：fail-fast 如何发现结构性修改？没有抛异常是否就意味着并发访问安全？**

例如 `ArrayList` 的迭代器比较 `expectedModCount` 与 `modCount`。

- 并发可见性、访问路径和检查时点都会影响是否检测到，所以“没抛异常”不能证明线程安全。
- 对迭代器允许范围之外的结构修改，不应依赖偶然可运行的表现。

**追问 2：单线程遍历时删除满足条件的元素，应怎样使用迭代器或集合提供的删除方法？**

单线程可在迭代器遍历后调用该迭代器的 `remove()`，或使用 `removeIf`。不要在增强 for 中直接调用列表的结构性删除。

并发遍历则按需求使用外部同步、快照或并发容器，而不是仅捕获异常后重试。

### 12. `HashSet` 如何判断重复元素？

`HashSet` 按元素的哈希和相等性判断是否重复：先定位桶，再用 `equals` 确认。

它保证的是所定义相等性下不重复，不是自动比较对象所有字段，也不保证元素遍历顺序。

**追问 1：它与 `HashMap` 有什么关系？**

典型实现使用 `HashMap` 保存元素，集合元素作为 Map 的 key，value 使用统一占位对象。

因此哈希冲突、扩容以及键不可随意修改的约束也会影响 `HashSet`。

**追问 2：插入内容相同的自定义对象时，哪些方法会影响去重结果？**

自定义对象需要让 `equals` 和 `hashCode` 满足契约。

- 保留 `Object` 的默认身份相等时，字段相同但实例不同的对象仍可同时存在；重写 `equals` 却保留不匹配的哈希实现，可能使逻辑相等对象进入不同桶。
- 仅重写 `hashCode` 而保持身份相等不必然违反契约，只要稳定性等要求仍成立，但也不会自动实现按字段去重。用于去重的业务身份字段应保持稳定。

### 13. `HashMap` 与 `ConcurrentHashMap` 对 `null` 键和值的限制有什么区别？

`HashMap` 允许一个 `null` key 和多个 `null` value；`ConcurrentHashMap` 不允许空键或空值。

并发 Map 使用 `null` 作为“当前没有对应结果”的明确标识，避免将它同时用作一个正常存储值。

**追问 1：为什么在并发查询中需要区分“没有映射”与“映射值为空”？**

普通 Map 的 `get` 返回 `null` 可能表示不存在，也可能表示映射到空值，常需额外 `containsKey`。

- 并发情况下，两次检查之间数据可能变化，无法把这个组合当成原子判断。
- 需要表达“已查询但无结果”时，可保存明确的占位对象或包装类型，而不是向 `ConcurrentHashMap` 写 `null`。

### 14. `HashMap`、`LinkedHashMap` 与 `TreeMap` 在有序性和操作成本上有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| HashMap | `HashMap` 不保证遍历顺序，普通查找平均接近 `O(1)` |
| LinkedHashMap | `LinkedHashMap` 额外维护链接顺序，可以按插入顺序或访问顺序遍历 |
| TreeMap | `TreeMap` 基于红黑树，按自然顺序或比较器排序，基本查找和更新通常为 `O(log n)`，并支持范围访问 |

**追问 1：插入顺序、访问顺序与键的排序顺序分别适合什么场景？**

需要稳定保留录入次序可选 `LinkedHashMap`；

- 需要基于访问顺序实现有界缓存规则时，可使用它的访问顺序模式及淘汰扩展，但仍要处理线程安全；
- 需要按时间或编号做前驱、后继和区间查询时，`TreeMap` 更直接。

### 15. `Comparable` 与 `Comparator` 如何影响 `TreeMap`、`TreeSet` 和集合排序？

`Comparable` 定义类型的自然顺序，`Comparator` 则在类型外提供可替换排序规则。

`TreeMap` 和 `TreeSet` 用比较结果决定键或元素在排序意义上是否相同，而排序列表仍可保留比较结果相同的多个元素。比较规则需要稳定、传递，并避免溢出。

**追问 1：比较结果为 0 与 `equals` 返回 `true` 是否必须相同？**

语法上不强制相同，但通常建议与 `equals` 一致，以满足集合的一般使用预期。

`BigDecimal` 的自然顺序就是典型差异：1.0 与 1.00 比较结果为 0，`equals` 却为假。

**追问 2：不一致时可能出现什么去重或查找现象？**

如果比较器只按年龄比较，两个不同 ID 的同龄用户可能在 `TreeSet` 中被视为同一个元素；换成 `HashSet` 又按 `equals/hashCode` 区分。

应明确集合身份规则，必要时添加稳定 ID 作为次级排序条件，而不是把数据丢失误认为集合 Bug。

### 16. `ConcurrentHashMap` 在 JDK 7 与 JDK 8 中分别如何组织并发控制？

JDK 7 `ConcurrentHashMap` 以多个 Segment 分段，每段独立维护哈希表并加锁；JDK 8 使用一个桶数组，主要通过 CAS、桶级同步、可见性字段和协作扩容组织并发。

目标是缩小写入竞争范围，同时让读取通常不必获取互斥锁。

**追问 1：JDK 7 的分段锁与 JDK 8 的桶级并发控制，锁住的范围有何不同？**

Segment 锁保护一个分段，分段内多个桶可能一起受阻；桶级同步把常见非空桶更新限制在更小范围。

两者都不是“每个业务 key 固定一把锁”，哈希冲突仍会让不同 key 共享竞争点。

**追问 2：JDK 8 中空桶插入与已有节点更新为何采用不同处理路径？CAS 与 `synchronized` 分别承担什么职责？**

空桶插入可以 CAS 地从空替换为新节点，避免先建锁；非空链表或树更新需要保护多步结构操作，普通路径使用 `synchronized` 并验证桶首是否仍有效。

CAS 适合一次原子状态转换，不能单独把复杂链表修改自动变成原子事务。

### 17. 以 JDK 8 的实现为例，`ConcurrentHashMap` 的 `get` 为什么通常不需要加锁？

JDK 8 中，桶元素通过具有相应可见性语义的访问读取，节点的关键字段采用 `final` 或 `volatile` 等约束。

- 读线程可以在写入同时遍历可见结构，不必像写线程一样锁住整个修改过程。
- “get 不加互斥锁”仍然依赖严格设计的发布、读取和迁移协议。

**追问 1：节点、数组元素和 value 的可见性需要通过什么机制保障？**

`key/hash` 等初始化后稳定的字段、`value/next` 等可变可见字段，加上对数组元素的受控访问，共同保证读线程观察到合法节点。

不能只说“整个数组是 volatile”，因为数组引用可见和每个数组元素可见不是一回事。

**追问 2：读线程碰到正在扩容的桶时，如何找到数据？无锁读取是否意味着读取整个 `Map` 的一致快照？**

遇到扩容转发节点时，读取会按转发信息到新表查找；不同 key 的多个读取可能对应不同并发时点。

单个映射的线程安全和可见性不等于整张 Map 的一致快照，`size`、遍历和跨键约束需要另行设计。

### 18. 以 JDK 8 的实现为例，`ConcurrentHashMap` 扩容时如何继续处理并发读写？

扩容创建新数组后，线程按区间迁移旧桶；迁移完成的桶放置转发节点，指向新表。

- 读操作据此查找，写线程发现迁移状态后可以协助扩容或转向新表。
- 迁移协议保证访问方能分辨旧位置和新位置，而不是一边随意搬运一边无条件读写。

**追问 1：迁移中的桶如何标记，读写线程怎样识别迁移状态？**

JDK 8 使用 `ForwardingNode` 等特殊节点和状态标记已迁移桶。

非空桶迁移时需要协调对该桶的更新，确保迁移结果与并发写入不互相覆盖；看到转发节点后不能继续把它当普通数据节点。

**追问 2：多个线程如何分担迁移工作，避免重复搬迁并继续处理读写？**

线程通过原子更新迁移索引领取区间，避免多个线程重复处理相同区间；`sizeCtl` 等状态协调参与者和扩容完成。最后确认各区间完成后再切换主表引用。

协作提高扩容并行度，但热点写和迁移仍有成本，预估容量仍有意义。

### 19. `ConcurrentHashMap`、`Hashtable` 与 `Collections.synchronizedMap` 有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| Hashtable / synchronizedMap | `Hashtable` 与 `Collections.synchronizedMap` 的常见方法主要通过同一互斥锁串行保护 |
| ConcurrentHashMap | `ConcurrentHashMap` 针对并发读取和局部更新设计，通常能减少竞争 |

同步包装不会自动让迭代和多个方法组成的业务动作成为整体原子操作。

**追问 1：比较锁粒度、遍历时的同步要求，以及多个操作组合执行时的安全边界。**

同步包装 Map 的遍历通常需要按文档在包装对象上外部同步；`ConcurrentHashMap` 的迭代器是弱一致的，不等于冻结全表。

对后者在外面加一把普通锁，如果其他写入方不使用同一把锁，也不能获得全局互斥。跨键事务要统一锁协议或重新设计数据结构。

### 20. `ConcurrentHashMap` 的单个方法线程安全，是否意味着“先检查、再更新”也线程安全？

不意味着。`containsKey`、`get`、`put` 各自安全，但两个线程仍可同时观察到缺失并分别执行初始化或覆盖。

应优先使用容器提供的单键原子方法，把条件判断与更新放在同一个操作里；涉及多个 key 或外部副作用时再确定更大的事务边界。

**追问 1：计数或延迟初始化时，`putIfAbsent`、`compute`、`merge` 与外部加锁应如何选择？**

存在则不覆盖可用 `putIfAbsent`，按旧值更新可用 `compute`，计数合并可用 `merge`；这些回调应短小，避免慢 I/O 或递归修改相关映射。热点统计也可保存 `LongAdder`。

若业务同时修改两项关联状态，需要统一锁或更高层协调，单键原子 API 不能替代。

### 21. `CopyOnWriteArrayList` 如何实现并发访问，代价体现在哪里？

`CopyOnWriteArrayList` 写入时复制当前数组，在新数组上完成修改，再发布新数组；读者继续访问已发布的稳定数组。

这样读取不必跟写入争用同一把互斥锁，迭代器可遍历创建时的快照。代价是写入复制、额外内存和读者看到旧快照。

**追问 1：一次写入需要复制哪些数据，迭代器观察到的是哪个时点的内容？**

复制的是整个引用数组，而非深拷贝所有元素；旧迭代器仍引用旧数组，因此不会看到后续增删。迭代器通常不支持结构性修改。

若元素本身可变，元素字段修改并不自动受“数组快照”保护。

**追问 2：读多写少但集合很大时，还需要评估什么内存与延迟成本？写入频繁时为何可能不合适？**

集合很大时，即使写入少，一次复制也可能造成明显分配和停顿；长寿命迭代器还会延长旧数组存活。

写入频繁时复制成本和 GC 压力会迅速放大，应考虑锁保护的普通列表或适合业务的其他并发结构。

### 22. 不可修改的集合视图、独立副本与不可变对象有什么区别？

不可修改视图只是限制通过该视图调用修改方法，不代表底层数据不变；独立副本隔离容器结构变化，但可能共享元素；真正不可变对象还需要确保内部状态不被任何持有者修改。

跨线程共享时，既要控制可变性，也要正确发布对象。

**追问 1：比较 `Collections.unmodifiableList`、`List.copyOf` 与 `new ArrayList<>(source)`：原集合变化后，各自会发生什么？**

`Collections.unmodifiableList(source)` 通常包装原列表，原列表变化可被视图看到；

- `new ArrayList<>(source)` 复制引用，允许独立增删；
- JDK 10 起的 `List.copyOf(source)` 返回不可修改列表，不反映原列表后续结构变化，且不接受 `null` 元素。
- 它可复用合适的已有不可修改实例，不承诺每次新分配。

**追问 2：集合不允许增删时，集合中的可变元素是否也不能修改？**

并不是，集合中的可变元素仍然可以被修改。三种方式都不自动深拷贝元素，元素还可能被其他引用持有。

- 例如列表不允许添加订单，但订单金额字段仍可能变化。
- 需要稳定快照时，应复制可变元素或改用真正不可变的元素类型；仅对外层列表禁止增删还不够。

**追问 3：作为跨线程共享配置或对外返回的数据时，怎样避免调用方修改内部状态？请说明使用的 JDK 版本。**

配置可使用不可变值对象加不可修改容器，并通过构造器、`volatile` 或其他同步方式安全发布；对外返回内部数据时使用适当的防御性复制。

JDK 8 可用复制后再包装的方式隔离结构；不同版本 API 应明确，不要在 Java 8 示例里直接使用 `List.copyOf`。

### 1. `Runnable`、`Callable`、`Future` 与线程池分别负责什么？

`Runnable` 表示没有直接返回值的任务，`Callable<V>` 表示可返回结果并抛出受检异常的任务；`Future<V>` 表示异步结果与取消状态；线程池负责调度、并发数量和资源管理。

任务描述、执行资源和结果句柄是三个不同层次，不能把实现 `Callable` 本身说成已经创建并启动了线程。

**追问 1：如何选择并发任务的提交方式？**

无需结果且已有统一异常处理时可 `execute(Runnable)`；需要结果时可 `submit(Callable)` 并持有 `Future`；有依赖编排时可选择 `CompletableFuture`。

无论哪种方式，都需要明确使用哪个执行器、是否有界以及任务被拒绝时如何反馈。

**追问 2：任务需要返回值或传播异常时，接口应该怎样设计？**

使用显式结果类型表达成功数据，异常通过 `Future.get()` 的 `ExecutionException` 等路径返回并检查 cause。

需要部分成功时可设计批量结果对象，而不是把所有异常吞掉返回空值。取消和超时也应有独立语义，不能混同于业务失败。

### 2. 调用 `Thread.start` 与直接调用 `run` 有什么区别？

`start()` 请求 JVM 启动一个新线程，由该线程执行 `run()`；直接调用 `run()` 只是当前线程的一次普通方法调用，不会自动并行。

判断线程数量要看是否真正调用了线程启动机制，而不是方法名是否叫 `run`。

**追问 1：同一个线程能否多次 `start`？**

不能。一个 `Thread` 对象的生命周期只能启动一次，即使它已经执行结束，再次 `start()` 也会抛出 `IllegalThreadStateException`。

需要再次执行任务，应创建新线程或重新向执行器提交任务，而不是复用已终止的 `Thread`。

### 3. 用户线程与守护线程在 JVM 退出条件上有什么区别？

JVM 正常退出条件主要取决于是否还有存活的非守护线程。

- 守护线程适合后台辅助工作，但不会因为自己仍在运行就阻止 JVM 退出。
- 它不是“优先级低的线程”，也不是自动获得安全终止能力的线程。

**追问 1：只剩守护线程仍在运行时，JVM 是否必须等待它们完成？**

JVM 不必等待只剩下的守护线程完成工作，因此其 `finally` 或尚未完成的写入不能作为退出时的可靠保证。

设置守护属性通常应在线程启动前完成，不能等运行后再任意切换。

**追问 2：把日志落盘或事务收尾只交给守护线程有哪些风险？怎样设计明确的关闭流程？**

关键日志、消息和事务收尾不能仅依赖守护线程继续运行。

- 关闭时应先停止接收新工作，再等待有限时间完成已有任务，刷写必要数据并关闭资源；超时后记录未完成状态。
- 关闭钩子也不覆盖强杀、进程崩溃或机器断电，真正可靠的数据需要持久化协议。

### 4. Java 线程有哪些状态？`BLOCKED`、`WAITING` 和 `TIMED_WAITING` 应如何区分？

Java 的线程状态为 `NEW`、`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING`、`TERMINATED`。

`BLOCKED` 专指等待进入对象监视器；`WAITING` 是没有超时的等待；`TIMED_WAITING` 是带时间边界的等待。Java 状态与操作系统调度状态不完全一一对应。

**追问 1：获取 `synchronized` 锁与调用 `wait`、`sleep`、`join` 时，分别可能进入什么状态？**

竞争 `synchronized` 监视器可能为 `BLOCKED`；无超时 `wait/join` 或 `park` 通常进入 `WAITING`；`sleep`、限时等待通常为 `TIMED_WAITING`。

- 等待 `ReentrantLock` 常通过 `park` 表现为等待，而不是 `BLOCKED`。
- 原生 I/O 等情况也可能在 Java 层显示为 `RUNNABLE`，不能只看名称判断 CPU 使用。

**追问 2：线程处于 `WAITING` 是否足以判断故障？还需要结合等待对象和调用栈确认什么？**

不足。空闲线程池线程正常等任务就可能为 `WAITING`。

- 要看等待对象、持锁者、持续时间、队列积压、请求延迟和多次线程快照。
- 状态本身只描述当前停在哪里，不直接说明等待是否合理或是否形成死锁。

### 5. `wait`、`sleep` 与 `join` 的用途以及对锁的影响有什么区别？

| 机制 | 特点与边界 |
|---|---|
| wait | `wait` 用于等待对象监视器保护的条件，会释放该监视器并在返回前重新获取 |
| sleep | `sleep` 让当前线程等待一段时间，不释放已经持有的监视器 |
| join | `join` 用于等待目标线程结束 |

它们解决的是不同等待需求，不能相互替换来建立任意业务同步。

**追问 1：调用某个对象的 `wait` 时会释放哪一个监视器？线程同时持有其他对象的锁时，那些锁也会释放吗？**

只释放调用 `wait` 的那个对象的监视器，并在返回前恢复相应持有状态；其他业务锁不会一并释放。

持有多个锁再等待时，仍可能阻塞其他线程或形成循环依赖。

**追问 2：`sleep` 和等待另一线程结束的 `join` 是否会自动释放调用方已经持有的其他业务锁？**

不会。`sleep` 不释放业务锁；`join` 的内部实现可能使用目标线程对象上的等待，但并不自动释放调用方持有的其他锁。

若被等待线程恰好也需要这些锁，调用方持锁 `join` 就可能阻止它完成。

**追问 3：等待业务条件时，为什么必须在持锁状态下检查，并在唤醒后重新检查条件？**

条件检查和进入等待必须与修改条件使用同一同步协议，避免检查后、等待前错过通知。

唤醒可能是虚假唤醒，或条件已被其他竞争者改变，因此必须用 `while (!condition) wait()`，不能只用一次 `if`。

### 6. `notify` 与 `notifyAll` 的行为有什么区别？

| 机制 | 特点与边界 |
|---|---|
| notify | `notify` 从对应监视器等待集中选择一个线程唤醒，选择不保证公平或随机分布 |
| notifyAll | `notifyAll` 唤醒所有等待者，让它们重新竞争监视器 |

唤醒不是把锁直接交给等待者，当前线程完全释放锁后，等待者才有机会继续。

**追问 1：`Condition` 的 `await`、`signal` 与 `signalAll` 如何使用？**

`Condition` 与 `Lock` 绑定，持锁时调用 `await` 释放锁等待，返回前重新获取；`signal`、`signalAll` 通知相应条件队列。

无论监视器还是条件变量，都应使用循环检查业务条件，并在 `finally` 中正确释放显式锁。

**追问 2：多个业务条件共用同一把锁时，怎样避免唤醒不满足条件的等待者？**

可以为不同条件建立不同 `Condition`，如队列的 `notEmpty` 与 `notFull`，只通知可能继续的等待者。

只有一个等待集且存在多种条件时，`notify` 可能唤醒错误角色，必要时使用 `notifyAll` 并让各方重新检查条件，同时评估无效唤醒开销。

### 7. 什么样的代码存在线程安全问题？

- **发生条件：** 多个线程访问共享可变状态，如果其中的读写缺少正确同步，就可能出现数据竞争或业务不变量被破坏。
- **正确性要求：** 线程安全不仅是“单条赋值不撕裂”，还包括复合操作完整性和线程间可见性；没有共享可变状态通常能大幅简化并发设计。

**追问 1：原子性、可见性和有序性各自指什么？**

原子性指操作作为不可被观察到中间状态的整体完成；可见性指一个线程的修改按规则能被另一个线程观察；有序性指执行或观察顺序满足规定约束。

它们不是同义词，`volatile` 可建立可见性和顺序约束，但不让 `count++` 成为一个原子事务。

**追问 2：用共享计数器说明：多线程只读取数据与同时执行更新时，风险有何不同？**

计数器被安全初始化和发布后，多个线程只读取且没有后续写入，通常无更新竞争；同时递增就需要原子读改写或锁。

即便变量是 `int`，读、加一、写仍是多个步骤，两个线程可能都基于同一个旧值计算。

### 8. `LockSupport` 的 `park`、`unpark` 与 `wait`、`notify` 有什么区别？

`LockSupport` 按线程维护一个最多为 1 的许可，`park` 消耗许可或等待，`unpark(thread)` 给指定线程许可。

它不要求先持有对象监视器，也不自动释放已持有的业务锁；是 AQS 等同步器的底层构件，而非完整的业务条件协议。

**追问 1：`unpark` 先于 `park` 调用时，许可如何影响后续等待？许可是否可以无限累加？**

对已经启动的线程，先 `unpark` 通常使下一次 `park` 直接返回；多次许可不会累计成多个额度。在线程尚未启动前调用的效果不能作为保证。

若中间其他代码消耗了许可，也不能把某次 `unpark` 简单绑定到某一次业务等待。

**追问 2：线程中断或 `park` 无原因返回时，为什么仍需重新检查业务条件？**

`park` 可能因许可、中断或无原因返回，不会替调用者判断业务条件。

必须结合 `volatile`、原子变量或锁维护的状态循环检查；同时处理取消，避免中断标记一直存在导致反复立即返回形成忙循环。

**追问 3：与依赖对象监视器的 `wait`、`notify` 相比，LockSupport 对调用位置和唤醒目标有哪些不同要求？**

`wait/notify` 依赖同一对象监视器和等待集，调用前要持有监视器；`LockSupport` 指定线程进行唤醒，调用位置更灵活。

但“更底层”意味着调用者需要自己维护等待登记、条件可见性和生命周期，不能漏掉这些约束。

### 9. 如何利用 `interrupt` 协作式地结束线程，而不是直接强制终止？

中断是一种协作式取消请求，不是强行把线程从任意指令位置杀死。

- 任务应定期检查中断或调用支持中断的阻塞 API，收到请求后停止新工作、清理资源并退出。
- 关闭调用链还要把取消传递给数据库、网络客户端等实际执行者。

**追问 1：计算任务应在什么位置检查中断？可中断阻塞调用收到中断后会怎样？**

计算循环可在批次边界检查 `isInterrupted()`；`sleep/wait/join` 等可中断等待通常抛出 `InterruptedException`，并清除中断标记。

`Thread.interrupted()` 会读取并清除当前线程标记，而 `isInterrupted()` 不清除，应避免误用。

**追问 2：捕获 InterruptedException 后，怎样决定继续退出、向上传递还是恢复中断标记？**

能向上传播就声明并抛出；已处于任务边界时清理后退出；不能向上传播但上层仍需知道取消时，调用 `Thread.currentThread().interrupt()` 恢复标记。

不要只打印异常后无条件继续无限任务，也不要恢复标记后又进入不检查条件的忙循环。

**追问 3：任务正在执行不响应中断的调用时，如何限制其资源占用而不是假设它已经停止？**

配置相应客户端的连接、读取和整体超时，必要时关闭资源或使用隔离执行器限制并发。

调用不响应取消时，只能把影响限制在明确范围，不能因为 `Future` 已标取消就认定底层调用结束。强行停止线程还可能破坏共享状态，通常不采用。

### 10. JMM 如何约束线程间的内存可见性与指令重排？

JMM 定义线程读写共享变量时允许观察到哪些结果，以及同步操作建立怎样的顺序约束。

- 它允许不改变合法可观察行为的优化，而不是要求所有指令都按源码逐条执行。
- 正确使用锁、`volatile`、线程启动结束等同步关系，可以建立可靠的发布和读取顺序。

**追问 1：如何用 `happens-before` 判断一段并发代码中的读写是否有顺序保证？**

同线程程序顺序、同一监视器解锁到后续加锁、同一 `volatile` 写到后续读、`start` 到被启动线程的动作，以及线程结束到成功 `join` 返回，都可建立关系，并具有传递性。

这里的“先于”是语义上的可见性与顺序，不是仅比较两条日志时间戳。

**追问 2：Java 内存模型（JMM）与 JVM 的堆、栈等运行时数据区分别描述什么，为什么不能混为一谈？**

JMM 回答“并发读写是否合法、何时可见”；运行时数据区回答“执行状态、对象和元数据在虚拟机模型中如何组织”。

堆、栈不是 JMM 的几种一致性级别，也不能通过“两个线程访问同一块物理内存”就推导一定可见。

### 11. 下面共享计数器使用了 `volatile`，两个线程结束后结果是否一定为 20000？

```java
public class CounterCase {
    private static volatile int count;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 10_000; i++) {
                count++;
            }
        };
        Thread first = new Thread(task);
        Thread second = new Thread(task);
        first.start();
        second.start();
        first.join();
        second.join();
        System.out.println(count);
    }
}
```

- **结果判断：** 不一定等于 20000。
- **丢失更新的原因：** `volatile` 保证相应读写的可见性和顺序，但 `count++` 是读、加一、写三个步骤，多个线程可以基于同一旧值各写一次，从而丢失更新。
- **join 的边界：** `join` 保证主线程等待两者结束，不会把之前丢掉的递增补回来。

**追问 1：把一次 count++ 拆成读、计算、写三个步骤，构造一个更新丢失的交错顺序。**

初始为 0：线程 A 读 0，线程 B 也读 0，A 写 1，B 再写 1。发生了两次递增，计数却只增加一次。真正竞争的是整段读改写，而不仅是最后一次赋值。

**追问 2：`volatile` 在这里提供了什么保证，又缺少什么保证？**

`volatile` 让单次访问满足相应同步语义，限制不合法的缓存和重排行为；它不提供互斥，也不保证读到旧值后到写回之间无人更新。

最终结果不能靠重复运行某次恰好为 20000 来证明正确。

**追问 3：分别使用 `synchronized` 与原子类改写时，需要保护的操作范围是什么？**

锁方案应让所有递增使用同一把锁，将完整 `count++` 放进同步块；原子方案使用 `AtomicInteger.incrementAndGet()`，而不是 `set(get() + 1)`。

原代码已保留 `join`，替换共享变量与更新后可保证这两万个成功递增全部计入：

```java
private static final java.util.concurrent.atomic.AtomicInteger count =
    new java.util.concurrent.atomic.AtomicInteger();
// 每次递增：
count.incrementAndGet();
// 两个线程 join 后读取：
System.out.println(count.get());
```

### 12. `synchronized` 修饰实例方法、静态方法和代码块时，分别竞争哪一把锁？

实例同步方法锁住调用接收者 `this`；静态同步方法锁住声明类对应的 `Class` 对象；同步块锁住括号表达式实际求值得到的对象。

同一把锁才产生互斥，不能只看方法在同一个类里或变量名相同。

**追问 1：两个线程调用同一对象的同步方法，与调用不同对象的同步方法，互斥关系有何不同？**

同一对象上的同步实例方法竞争同一监视器，因此互斥；不同实例通常使用不同监视器，不会因为类型相同而互斥。

若方法内部另外使用共享静态锁，则要按那个实际锁对象重新判断。

**追问 2：静态同步方法与实例同步方法会不会互相阻塞？怎样判断 `synchronized` 代码块锁住的实际对象？**

静态同步方法的类对象锁与实例方法的 `this` 锁不同，通常不互斥。

同步块可使用私有固定锁对象；不宜随意锁可更换引用、装箱缓存对象或字符串常量，因为锁身份变化或意外共享都可能破坏预期。

### 13. `synchronized` 如何基于对象监视器实现互斥与可重入？

Java 语义上每个对象关联一个监视器，一次只允许一个线程拥有；同一线程可以重入，完全退出所有重入层次后才释放给其他线程。

虚拟机可以用不同优化路径实现这一语义，不是每个对象创建时都必须立刻分配一个重量级 `ObjectMonitor`。

**追问 1：同步方法与同步代码块在字节码中如何表示？**

同步代码块通常通过 `monitorenter/monitorexit` 表达，并处理异常退出路径；同步方法通过方法访问标志 `ACC_SYNCHRONIZED` 表达，由调用机制完成监视器操作。

不能要求同步方法字节码正文也必须出现同样的一对指令。

**追问 2：可重入的计数如何随调用变化？**

同一持有者再次进入时增加重入层次，退出一次减少一次；减到完全释放时其他线程才有机会进入。

方法正常返回或异常退出均应解除本次同步，不会因为抛异常就永久保留这一层锁。

### 14. 以 JDK 8 为例，偏向锁、轻量级锁与重量级锁如何适应不同竞争程度？

在典型 JDK 8 HotSpot 的历史实现中，偏向锁优化长期由同一线程使用的情况；轻量级路径通过锁记录和 CAS 等减少无竞争成本；竞争加剧时可能膨胀为监视器并阻塞等待。

它们是实现策略，不是业务必须手工切换的三种锁 API，也不适用于所有后续 JDK 版本。

**追问 1：锁升级、自旋、锁消除和锁粗化分别试图减少什么开销？**

升级适应竞争状态；自旋用短时间 CPU 等待换取少量阻塞切换；锁消除在证明对象不需要跨线程同步时移除不必要加锁；锁粗化合并连续同步区，减少频繁加解锁。

自旋过长会浪费 CPU，粗化也可能扩大临界区，应结合负载而非一概认为更快。

### 15. 原子类如何利用 CAS 完成并发更新？

CAS 原子地比较内存中的当前值与期望值，相同则写入新值，不同则失败。

- 原子类据此把读改写做成可重试操作，并提供相应内存语义。
- 它不是“完全没有协调成本”：失败重试、缓存一致性流量和热点竞争都可能明显消耗资源。

**追问 1：一次 CAS 失败后，怎样取得新的期望值并重试？**

失败后重新读取最新值，按最新状态计算新值，再尝试比较交换。不能用第一次读取的过期期望值无限重试。

更新函数可能执行多次，所以不要在可能重试的计算回调中直接发送消息或执行不可重复扣款。

**追问 2：数值从 A 变为 B 又变回 A 时，为什么可能需要版本信息？**

值回到 A 并不代表期间没有变化，某些结构的节点状态或生命周期可能已经不同。

可使用版本号或 `AtomicStampedReference` 等把变化历史的一部分纳入比较；版本本身也应考虑回绕和对象生命周期，不能只“加个数”就忽略所有 ABA 风险。

**追问 3：竞争持续增大时，反复自旋会消耗什么资源？何时应改用锁或减少热点竞争？**

高竞争下线程不断读取和争抢同一缓存行，产生自旋及一致性流量。

- 可通过分片计数、批量汇总、减少共享写入来降低竞争，或改用阻塞锁。
- 需要一次性维护多个关联字段时，锁或不可变状态整体替换也通常更清楚。

### 16. `AtomicInteger`、`AtomicLong` 与 `LongAdder` 在高竞争计数中应如何选择？

需要单个可线性化数值更新或读取时，用 `AtomicInteger/AtomicLong`；高竞争统计且允许汇总读不是严格瞬时快照时，可选 `LongAdder`。

例如指标计数适合分散更新，余额和严格序号通常不适合用一个非原子汇总结果作判断。

**追问 1：`LongAdder` 为什么可能提高吞吐？**

`LongAdder` 在竞争时把写入分散到多个 Cell，减少所有线程争用同一个位置，最终读取再把 base 和各 Cell 相加。

它以额外空间和汇总开销换取更新吞吐，低竞争或频繁精确读取时未必优于原子单值。

**追问 2：读取 sum 时能否把它当成与并发更新严格原子的快照？**

不能。并发更新期间 `sum()` 逐个读取各分片，结果不保证对应同一个原子时刻；没有并发更新时可得到当前总和。

不要用 `sum() < limit` 再 `increment()` 实现严格限额，这既有汇总语义问题，也有检查与更新分离的竞争。

### 17. `AQS` 如何管理同步状态，并组织获取失败的线程排队、阻塞和唤醒？

AQS 把同步器常见的状态管理、等待排队和阻塞唤醒封装起来，子类定义“如何尝试获取或释放状态”。

- 例如锁把 state 用作持有计数，信号量把它用作可用额度。
- AQS 本身不是某一把锁，也不会自动为任意业务代码确定正确状态含义。

**追问 1：同步状态、持有者与等待队列各自记录什么？**

`state` 表达同步资源状态；独占同步器还可记录持有线程；同步队列记录获取失败、等待重新竞争的节点。

队列顺序与具体获取策略共同影响公平性，存在 FIFO 队列不意味着所有同步器都严格公平。

**追问 2：竞争失败的线程何时入队、阻塞与重新竞争？被唤醒是否等于已经获得同步状态？**

快速尝试失败后进入队列，在合适前驱与状态下再尝试，否则通过 `park` 等等待；释放方按协议唤醒后继。

被唤醒只是重新竞争的资格，不等于已经拥有资源，因此还要检查条件并成功更新 state。

### 18. `AQS` 的独占模式、共享模式和 `Condition` 等待队列各适合什么同步需求？

独占模式适合互斥锁，共享模式适合信号量、闭锁等允许多个线程满足条件的同步。

Condition 的等待队列则保存“已经释放锁，等待某个业务条件”的线程；它与争取同步状态的主队列职责不同。

**追问 1：独占模式与共享模式分别如何表达一个线程独占资源和多个线程共享额度？**

独占模式通常只允许一个线程获取，重入由持有者和计数判断；共享模式可在额度或状态允许时放行多个线程，且释放可能向后传播唤醒。

state 的编码由具体同步器定义，不能把所有 AQS 都解释成 0 和 1 的锁。

**追问 2：同步队列与 Condition 条件队列中的线程分别在等待什么？`signal` 后线程能否立即继续执行业务代码？**

同步队列等待获取锁或额度，条件队列等待生产出数据等业务条件。

`await` 会保存并释放持有状态，`signal` 把相应等待者转入重新获取锁的流程；通知方仍持锁时，等待者不能立即执行受保护业务。

**追问 3：线程超时、中断或取消等待时，队列如何保持后续线程仍有机会获得资源？请结合所用 JDK 版本说明。**

以 JDK 8 为例，取消节点会被标记，并通过清理或跳过取消前驱、修复链接及必要唤醒，让有效后继继续推进。

较新 JDK 的节点和清理实现有所调整，回答应固定源码版本。共同要求是取消不能留下永久挡住后继的无效节点。

### 19. `ReentrantLock` 如何实现可重入、公平锁与非公平锁？

`ReentrantLock` 以 AQS 同步状态记录重入次数，并记录独占持有者。

- 公平模式在首次竞争时检查队列前驱，非公平模式允许新到线程先尝试抢占。
- 公平性降低插队机会，但不等同于操作系统绝对按时间顺序调度，也通常需要付出吞吐代价。

**追问 1：可重入如何记录当前持有者与重入次数？**

未持有时通过原子状态转换获取锁并设置持有者；持有者再次调用则增加计数；每次 `unlock` 减少计数，完全释放时清除持有者并唤醒等待方。非持有线程不能合法解锁。

**追问 2：公平与非公平获取分别在什么位置检查排队情况，会怎样影响吞吐与等待时间？**

公平获取通常在 CAS 之前检查是否有更早排队者；非公平获取可以直接竞争，因此刚释放的锁可能被新线程获得。

还应注意无参 `tryLock()` 即使在公平锁上也允许插队，不能把所有获取方法都笼统归为公平。

**追问 3：需要可中断获取、限时等待或多个条件队列时，相较 `synchronized` 应如何选择？**

需要 `lockInterruptibly`、带超时的 `tryLock`、公平选项或多个 `Condition` 时，`ReentrantLock` 更合适；简单互斥可优先 `synchronized` 的自动释放。

显式锁应采用 `lock(); try { ... } finally { unlock(); }`，且只在成功获得锁后释放。

### 20. 读写锁如何协调读操作和写操作？

读写锁允许多个读者同时进入，但写者需要与其他读写者互斥，适合读操作本身较重且读多写少的共享状态。

它不会让任意查询都自动安全：读路径必须真的不修改受保护状态，缓存懒加载等隐藏写入也应计入。

**追问 1：在不同读写比例与锁竞争程度下，使用读写锁需要权衡什么？**

收益取决于读临界区长度、读写比例、CPU 核数和竞争程度。

- 短小读取时维护读计数的原子操作可能比互斥锁更贵；写入频繁时读写者互相等待，也可能出现尾延迟或饥饿。
- 可比较不可变快照、分片锁和普通锁，而不是只按读比例套规则。

### 21. `ReentrantReadWriteLock` 的锁降级与锁升级有什么区别？

锁降级是持有写锁时先获取读锁，再释放写锁，使更新后的读取在不中断保护的情况下继续；升级是持有读锁再尝试获取写锁。

`ReentrantReadWriteLock` 支持符合规则的降级，不支持把现有读锁直接升级为写锁。

**追问 1：持有读锁时再请求写锁有什么风险？**

写锁需要其他读者退出，当前线程自己又持有读锁，直接请求写锁可能永久等待。

应先释放读锁、获取写锁，再次检查业务条件，因为间隙中状态可能已变；这不是保持原子性的无缝升级。

**追问 2：读写比例很高是否足以说明读写锁一定更快？**

不足。还要看每次读工作量、读计数竞争、写者等待和额外同步成本。

若只读一个字段，`volatile` 或不可变快照可能更适合；必须在同样负载下测吞吐与分位延迟。

### 22. `StampedLock` 的乐观读与普通读锁有什么区别？

`StampedLock` 的乐观读先取得 stamp，不阻止写者，再读取到局部变量并验证期间是否发生写入；验证成功才使用结果，否则退回真正的读锁。普通读锁会参与互斥协议。

乐观读适合可安全重读的短小读取，不适合读取中执行不可回退副作用。

**追问 1：为什么读取后还需要校验 stamp？**

读取期间可能与写入交错，多个字段可能暂时不一致，stamp 校验用于确认这一读取区间内没有相关写锁介入。

应先把字段读入局部变量再验证，而不是验证通过后又直接读取共享字段。

**追问 2：发生并发写入时应怎样退回安全的读取方式？**

验证失败则获取读锁，在保护下重新读取所有必要字段，最后按对应 stamp 解锁。

`StampedLock` 不可重入，乐观路径也不能随意调用需要稳定复杂对象图的操作，否则可能在尚未验证前就抛异常或执行错误副作用。

### 23. `ThreadLocal` 适合保存哪些线程内上下文？

`ThreadLocal` 用于把数据与当前线程关联，例如线程内请求上下文或框架维护的事务资源引用。

它让同一个 `ThreadLocal` 对象在不同线程中取到各自的值，但并不把值对象自动复制，也不保护值对象被其他路径共享后的并发访问。

**追问 1：它与给共享变量加锁有什么区别？**

锁协调多个线程对同一状态的访问；`ThreadLocal` 则把状态按线程隔离，解决的是不同问题。

若所有线程都需要共同更新同一个库存，把它放进 `ThreadLocal` 只会变成多份不一致状态，并不能代替同步。

**追问 2：为什么不能用 `ThreadLocal` 自动实现跨线程传递或跨服务传递？**

普通 `ThreadLocal` 的存储位于当前线程关联的 Map，不会自动进入另一个线程或进程。

异步任务需显式捕获和恢复上下文，跨服务还需通过协议字段传递，并按可信边界验证；任务结束后清理，避免线程池复用造成串用。

### 24. `ThreadLocal` 如何通过 `ThreadLocalMap` 实现线程间的数据隔离？

以典型 OpenJDK 实现为例，每个 `Thread` 持有自己的 `ThreadLocalMap`，以 `ThreadLocal` 实例为键保存线程内值。

`get/set` 先找到当前线程，再访问该线程自己的 Map，因此隔离边界是线程，不是把数据存放在一个全局 `ThreadLocal` 对象的普通字段里。

**追问 1：`Thread`、`ThreadLocal` 和 `ThreadLocalMap` 之间如何关联，key 与 value 分别保存什么？**

`Thread` 持有 Map，Entry 的 key 是指向 `ThreadLocal` 的弱引用，value 是强引用。

一个线程中多个 `ThreadLocal` 对应不同条目；同一个 `ThreadLocal` 在不同线程则对应不同 Map 中的条目。

**追问 2：多个 `ThreadLocal` 实例定位到冲突位置时，怎样查找和保存对应值？**

典型 `ThreadLocalMap` 使用开放寻址和线性探测处理冲突，不是 `HashMap` 那种链表或树桶。

查找和插入会沿数组寻找对应键或可用位置，并在部分访问路径中处理过期的弱引用条目。

**追问 3：一个 `ThreadLocal` 被多个线程使用时，为什么每个线程仍能维护各自的数据？**

键对象可以相同，但访问入口总是当前线程的 Map，因此不会直接读到别的线程条目。

如果向多个线程条目写入同一个可变对象引用，对象本身仍然共享，业务仍可能需要同步；隔离键值槽不等于深拷贝对象。

### 25. `ThreadLocal` 的 key 使用弱引用，为什么仍可能导致内存泄漏？

弱引用只影响 key 的可达性，value 仍由 Entry 强引用。

- 若 `ThreadLocal` 被回收，长期存活线程中的 Map 可能留下 key 已空但 value 尚未清理的条目；线程池又让线程长期不退出，从而延长 value 生命周期。
- 即便 key 仍被静态字段持有，未清理的大 value 也会被一直保留。

**追问 1：`Thread`、`ThreadLocalMap`、弱引用 key 与 value 之间，哪些引用可能长期存在？**

典型引用链为活线程 → `ThreadLocalMap` → Entry → value。

- key 是弱引用，并不会使这条 value 强引用链同步消失。
- Map 会在一些访问过程中清理失效条目，但不能把机会式清理当成及时释放保证。

**追问 2：在线程池复用线程时，为什么任务结束不等于 value 已经释放？**

线程池复用工作线程，任务结束只是执行栈返回，线程和 Map 仍在。

- 下一个任务可能读取到上一个请求的用户信息，还会让大对象长期存活。
- 业务上下文必须以任务为生命周期管理，而不能以线程结束为清理时机。

**追问 3：正常返回和抛出异常两条路径中，怎样保证 `remove` 执行，并避免下一个用户读到残留数据？**

采用 `try { local.set(context); ... } finally { local.remove(); }`，确保正常和异常路径都清理；嵌套上下文需要先保存旧值，再在 finally 中恢复旧值或删除。

不能在另一个线程调用 `remove` 来清理原工作线程，也不能只在成功路径末尾清理。

### 26. `InheritableThreadLocal` 与 `TransmittableThreadLocal` 分别在什么时机传递上下文？

`InheritableThreadLocal` 主要在线程创建时，从创建者复制继承上下文；线程池线程通常早已创建，因此不能准确代表每次提交任务的上下文。

`TransmittableThreadLocal` 是第三方方案，通过任务或执行器包装，在提交时捕获、执行时恢复、结束后还原线程原有上下文。

**追问 1：在线程池里提交多个不同用户的任务时，如何避免上下文没有传递、串用或未恢复？**

按任务提交时捕获，而不是复用某次旧快照；执行前安装，`finally` 中恢复工作线程原来的值。

- 必须按框架约定包装任务或执行器，并检查是否使用了代理增强。
- 传递的可变对象通常仍需考虑引用共享，不要认为上下文传递天然完成了深拷贝。

### 27. `ThreadPoolExecutor` 的核心参数如何共同决定任务的处理顺序？

题设：线程池初始没有线程，`corePoolSize=2`、`maximumPoolSize=4`，使用容量为 2 的 `ArrayBlockingQueue` 和 `AbortPolicy`，其余参数合法。

单个提交线程依次提交 7 个任务；在所有提交动作完成前，已启动的任务都持续阻塞，不会结束，也不会发生线程创建失败。

分别说明每次提交后的工作线程数、队列长度与任务去向。

规则是：

1. 线程数不足核心数时创建线程；
2. 否则尝试入队；
3. 队列满时再在最大线程数范围内创建线程；
4. 仍不能接收则拒绝。

题设中任务都不结束，因此结果可确定：

| 提交任务 | 工作线程数 | 队列长度 | 去向 |
|---|---:|---:|---|
| 1 | 1 | 0 | 新核心线程执行 |
| 2 | 2 | 0 | 新核心线程执行 |
| 3 | 2 | 1 | 入队 |
| 4 | 2 | 2 | 入队 |
| 5 | 3 | 2 | 新工作线程执行 |
| 6 | 4 | 2 | 新工作线程执行 |
| 7 | 4 | 2 | `AbortPolicy` 抛出拒绝异常 |

七个常见构造参数还包括线程空闲存活时间、时间单位、线程工厂，以及题设中的核心数、最大数、工作队列和拒绝策略。

**追问 1：依次提交题设中的 7 个任务时，哪些创建工作线程，哪些入队，哪一个触发拒绝？**

任务 1、2、5、6 直接交给新增工作线程，3、4 排队，7 被拒绝。

- 新增非核心线程可以先执行后提交的任务，因此线程池不自动保证所有任务严格按提交顺序完成。
- 题设排除了任务完成和创建失败，才能得到这张确定表。

**追问 2：队列改为无界队列后，`maximumPoolSize` 是否仍按原方式发挥作用？**

无界队列通常一直能接收核心线程之外的任务，因此通常不会走“队列满后扩到最大线程数”的路径。

最大线程数设置得很大也不能主动提升这类配置的并发；积压会转化为排队延迟和内存压力。

**追问 3：改变队列容量会怎样影响排队时间、线程创建与内存占用？**

较大队列缓冲更多峰值，但延长等待并占内存，也推迟非核心线程创建；较小队列更早扩线程或拒绝，但不能超过下游容量。

容量应按任务大小、最大可接受排队时间和处理速率共同确定，而不只是为了让监控上“不拒绝”。

### 28. 有界队列、无界队列与拒绝策略如何影响线程池在过载时的表现？

- **队列容量：** 有界队列把过载显式暴露为扩线程或拒绝，无界队列则容易把过载隐藏成不断增长的内存和延迟。
- **拒绝策略：** 拒绝策略决定系统如何向调用者反馈无法承载的新工作。
- **设计原则：** 过载设计本质上是资源和时限约束，不能靠无限排队保证业务可靠。

**追问 1：如何在任务可靠性、响应时间和资源占用之间取舍？**

关键任务可先可靠持久化再异步执行，并提供状态查询和幂等重试；实时请求超过预算应明确失败或降级，不宜无限等待。

监控队列长度、等待时间、拒绝数和执行耗时，设置与下游能力匹配的并发上限。任务进了内存队列并不等于机器故障后仍不会丢。

### 29. 线程池的四种常见拒绝策略分别如何处理新任务？

四种常见策略是 `AbortPolicy`、`DiscardPolicy`、`DiscardOldestPolicy` 和 `CallerRunsPolicy`。

- 它们分别偏向显式拒绝、静默丢弃、移走队头后重试提交、由提交线程同步执行。
- 策略应按任务是否允许丢失选择，而不是一律追求“不要报错”。

**追问 1：四种策略分别抛出异常、丢弃哪个任务，或者交给哪个线程执行？**

`AbortPolicy` 抛出 `RejectedExecutionException`；

- `DiscardPolicy` 丢弃新任务；`DiscardOldestPolicy` 在未关闭时移走队头并再次尝试提交，队头未必是业务优先级最低的任务；
- `CallerRunsPolicy` 在未关闭时由调用者执行。
- 静默丢弃还可能让等待对应 `Future` 的调用者长期得不到完成信号。

**追问 2：`CallerRunsPolicy` 把任务交回调用线程时，会怎样影响入口请求和背压？**

调用线程执行任务会减慢继续提交速度，形成某种背压；但若调用线程是 Web 请求线程或事件循环，也可能直接拉高接口延迟、阻塞其他连接。

必须明确这种影响能否接受，不能把它当无成本的可靠兜底。

**追问 3：线程池已经关闭时，还能否依靠这项策略保证任务执行？需要可靠交付的业务应怎样感知拒绝？**

线程池关闭后，`CallerRunsPolicy` 不保证执行，标准实现会直接不再运行任务。

需要可靠反馈的业务应采用显式拒绝、任务持久化或自定义失败完成机制，并让调用者获知未接收状态；不能把“没有抛异常”当作一定执行。

### 30. 通过 `Executors` 创建固定线程池和缓存线程池时，分别可能隐藏什么资源风险？

固定线程池通常使用无界队列，风险是任务积压和内存耗尽；缓存线程池常使用直接交接队列及非常大的最大线程数，风险是慢任务导致线程急剧增长。

工厂方法不是天然不能用，但其隐含资源边界必须与业务匹配。

**追问 1：与显式配置 `ThreadPoolExecutor` 相比，队列容量、最大线程数和任务类型应如何检查？**

检查核心与最大线程数、队列是否有界、线程工厂命名、异常处理和拒绝策略。

- 显式构造 `ThreadPoolExecutor` 更容易表达容量约束和监控需求。
- 多个业务共用池时还要隔离慢依赖，不能让非核心任务占满所有执行资源。

### 31. CPU 密集型与 I/O 密集型业务应如何估算线程池大小？

CPU 密集任务的并发通常从可用 CPU 核数附近开始估算；I/O 密集任务可根据等待与计算时间适度增加线程，以覆盖等待期。

这个估算只是压测起点，真正上限还受连接池、内存、下游配额及延迟目标限制。

**追问 1：CPU 核数、计算时间、等待时间和可用资源如何参与估算？**

可用近似式 `线程数 ≈ CPU数 × 目标利用率 × (1 + 等待时间/计算时间)` 形成初值，但等待比、资源争用和容器配额都可能动态变化。

计算密集任务过多只会增加调度与竞争，不能凭线程数量创造 CPU 能力。

**追问 2：下游连接池只能同时处理有限请求时，单独增加线程数会发生什么？**

线程会在连接池前继续排队，吞吐不一定提高，却增加栈内存、上下文切换和尾延迟。

应把关键资源并发作为限额，必要时在更早入口拒绝或排队，避免每一层都维护一个看不见的等待队列。

**追问 3：怎样通过吞吐、排队时间、响应时间与资源使用情况验证，而不是只套一个公式？**

逐步增加负载，观察吞吐何时不再增长、排队和 P95/P99 何时上升，同时看 CPU、GC、连接等待和错误率。

调参后在相同条件重复验证，留出峰值余量；不能只用平均响应时间或一次短测试判断最佳值。

### 32. 线程池如何回收空闲线程，并在服务退出时停止接收和处理任务？

线程池从队列取任务时，根据是否允许超时选择限时等待或持续等待；达到空闲条件的工作线程可退出。

关闭时应区分“不再接收新任务”和“已有任务全部结束”，并给收尾设置明确期限。线程池 API 不能强行终止不合作的业务代码。

**追问 1：非核心线程与核心线程分别在什么条件下允许超时退出？**

超过核心规模的空闲线程通常在 `keepAliveTime` 后允许退出；启用 `allowCoreThreadTimeOut(true)` 且满足有效超时要求后，核心线程也可以超时退出。

核心线程不是永远固定的那几个具体线程对象，而是维持规模的策略。

**追问 2：`shutdown` 和 `shutdownNow` 对新任务、排队任务与运行中任务分别有什么影响？**

`shutdown` 拒绝新任务，继续处理已提交任务；`shutdownNow` 尝试中断运行线程并返回尚未执行的队列任务，但不保证运行中任务立即停止。

返回的待执行任务需要业务决定取消、重新投递或持久化，不能默认它们已经成功执行。

**追问 3：怎样等待任务收尾并设定退出边界？发出中断后为什么还不能直接认定任务已经停止？**

停止入口后调用 `shutdown`，用 `awaitTermination` 等待有限时间，再按策略中断或记录未完成任务；同时设置下游超时和取消。

业务代码必须响应中断并释放资源，不能只看到中断已发送就宣布线程已退出。

### 33. `execute` 与 `submit` 在结果获取和异常传播方面有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| execute | `execute` 直接提交 `Runnable`，没有结果句柄；任务未处理的异常通常沿工作线程异常处理路径暴露，并可能使该工作线程退出 |
| submit | `submit` 把任务包装成结果对象，异常保存到 `Future`，调用 `get` 时通常以 `ExecutionException` 暴露，不能只盯着未捕获异常处理器 |

**追问 1：任务抛出的异常分别可能通过什么路径被调用方观察到？**

`execute` 的异常可由任务包装、`afterExecute` 或线程未捕获异常处理器观察；`submit` 的异常通常通过 `Future.get` 的 cause 获取。

两者在提交阶段的拒绝异常又是另一条路径，应区分“没提交成功”和“执行失败”。

**追问 2：`submit` 后不读取 `Future`，会产生什么异常感知问题？怎样设置统一的失败处理？**

不检查 `Future` 可能让执行失败长期不可见。

- 可以在任务包装层统一上报，使用完成回调，或在 `afterExecute` 对已完成 `Future` 读取结果并处理异常。
- 不要对尚未完成任务盲目阻塞读取，也要保留取消和中断的独立语义。

### 34. 父任务向同一个线程池提交子任务后同步等待，为什么可能发生线程饥饿？

父任务占住池中的工作线程，再等待只能由同一个池执行的子任务，就可能形成线程饥饿死锁。

- 队列里有可执行任务，但所有执行资源都被等待者占满，系统无法推进。
- 它不是普通“任务慢”，而是执行资源与依赖关系形成了闭环。

**追问 1：线程池只有两个工作线程，两个父任务都占用工作线程并等待尚在队列中的子任务，此时还有谁能推进任务？**

两个工作线程都在父任务的 `get/join` 中等待，两个子任务还在队列，没有空闲工作线程执行它们，因此父任务也无法结束释放线程。

无界队列还会使增大最大线程数的配置不按预想生效。

**追问 2：为什么这种等待不一定表现为对象监视器死锁？增大线程数是否能从根本上解决问题？**

等待发生在 `Future` 或同步器上，未必构成两个对象监视器互相持有，所以 JVM 的监视器死锁检测不一定直接报告。

加线程只是提高触发门槛，嵌套层数或负载增长后仍可能重现。

**追问 3：如何通过异步编排、分离执行器或改变任务依赖关系消除循环等待？**

优先把依赖改为异步完成阶段，父任务在提交后释放执行线程；或将父任务编排与子任务执行分离到资源边界明确的执行器。

分池也要分析下游依赖，避免形成新的跨池循环；取消和超时是止损手段，不代替修复依赖结构。

### 35. `CountDownLatch`、`CyclicBarrier` 和 `Semaphore` 分别适合哪些协作场景？

| 比较项 | 特点与用途 |
|---|---|
| CountDownLatch | `CountDownLatch` 是一次性倒计数，适合等待一组独立任务完成 |
| CyclicBarrier | `CyclicBarrier` 让固定数量参与者在阶段终点汇合，可重复使用 |
| Semaphore | `Semaphore` 管理并发许可，适合限制同时访问某项资源的数量 |

选择首先看需要的是完成通知、阶段协作还是资源配额。

**追问 1：等待全部任务完成、分阶段汇合、限制并发访问时应如何选择？**

主线程等多个初始化任务完成用闭锁，任务在 `finally` 中倒数；多个计算线程每一轮都汇合可用屏障，并处理破损与中断；最多 20 个外部请求并行可用信号量，并且只在成功获取许可后释放。许可不天然绑定持有线程，误释放会使限额失效。

### 36. 如何让三个线程依次输出 A、B、C，并在完成指定轮次后全部退出？

用同一个监视器保护 `turn` 和取消状态，只有轮到自己的线程才能输出，输出后推进状态并通知等待者。

- 循环检查条件，任何取消或异常都设置统一结束标记并唤醒其他线程。
- 以下 Java 8 代码输出指定轮次，并处理参与线程取消：

```java
public final class OrderedABC {
    private final Object monitor = new Object();
    private final int rounds;
    private int turn;
    private boolean cancelled;

    public OrderedABC(int rounds) {
        if (rounds < 0) throw new IllegalArgumentException("rounds < 0");
        this.rounds = rounds;
    }

    public void cancel() {
        synchronized (monitor) {
            cancelled = true;
            monitor.notifyAll();
        }
    }

    private void work(int id) {
        try {
            for (int i = 0; i < rounds; i++) {
                synchronized (monitor) {
                    while (!cancelled && turn != id) monitor.wait();
                    if (cancelled) return;
                    if (Thread.currentThread().isInterrupted()) {
                        cancel();
                        return;
                    }
                    System.out.print((char) ('A' + id));
                    turn = (turn + 1) % 3;
                    monitor.notifyAll();
                }
            }
        } catch (InterruptedException e) {
            cancel();
            Thread.currentThread().interrupt();
        } catch (RuntimeException | Error e) {
            cancel();
            throw e;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        OrderedABC task = new OrderedABC(5);
        Thread[] threads = new Thread[3];
        for (int i = 0; i < 3; i++) {
            final int id = i;
            threads[i] = new Thread(() -> task.work(id));
            threads[i].start();
        }
        try {
            for (Thread thread : threads) thread.join();
        } catch (InterruptedException e) {
            task.cancel();
            for (Thread thread : threads) thread.interrupt();
            throw e;
        }
        System.out.println();
    }
}
```

- 正常结果为 `ABCABCABCABCABC`。
- 真实业务不要把可能无限阻塞的外部调用放在这段临界区内。

**追问 1：应由哪些共享状态表示当前轮到谁，每个线程在什么条件下等待或继续？**

`turn` 的 0、1、2 对应 A、B、C，初始为 0；每个线程各执行 `rounds` 次，只有 `turn == id` 才输出。

条件检查、输出和 turn 更新使用同一监视器，避免检查后被别的线程抢先改变状态。

**追问 2：唤醒发生后，为什么仍应重新检查条件，而不是直接输出？**

通知可能同时唤醒多个角色，也允许虚假唤醒；重新获取锁时，状态还可能已被其他线程改变。

`while` 保证每次真正输出前重新验证轮次，`if` 则可能在错误角色被唤醒后输出乱序。

**追问 3：其中一个线程异常退出或被取消时，怎样让其他线程也能结束，避免永久等待？**

统一 `cancelled` 标记，并在任何退出路径中通知全部等待者。

- 等待条件同时检查轮次和取消，避免某一角色退出后其他角色永远等不到它。
- 外部取消也应调用同一取消入口，并在需要时中断等待线程。

### 37. 阻塞队列如何协调生产者和消费者，避免空队列读取或满队列写入？

阻塞队列用锁、条件队列或其他并发协议，把“检查空满状态”和“入队出队”组织成安全操作。

- 队列为空时消费者等待不空条件，队列满时生产者等待不满条件，状态变化后通知相应一方。
- `put/take`、限时 `offer/poll` 和立即返回方法应按延迟与背压要求选择。

**追问 1：常用阻塞队列的实现与容量选择会如何影响并发性能？**

数组有界队列存储紧凑，链表队列有节点分配成本且某些实现分离入队出队锁；直接交接队列不存储待处理元素。

- 容量过大会增加排队和内存，过小会频繁拒绝或阻塞。
- 阻塞操作还需处理中断，避免服务关闭时生产者消费者无法退出。

### 38. `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue` 与 `DelayQueue` 的使用场景有什么区别？

`ArrayBlockingQueue` 是有界数组队列；

- `LinkedBlockingQueue` 是链式阻塞队列，可指定容量，默认容量很大；
- `SynchronousQueue` 不存储元素，生产者与消费者直接交接；
- `DelayQueue` 依据元素到期时间让到期项可被取走，通常不提供固定容量限制。

**追问 1：容量、是否实际保存元素、锁竞争和到期顺序会怎样影响生产者消费者模型？**

数组队列通常用一个锁协调，链式实现常分离入队出队锁但仍有共享计数；直接交接适合立即配对，不是零容量缓存；延迟队列按到期顺序取出，不等于可靠分布式调度。

需要任务持久化或重启恢复时，还应使用数据库或消息系统记录状态。

### 39. `CompletableFuture` 如何组织多个异步任务的依赖、并行执行和结果汇总？

`CompletableFuture` 把异步结果与后续处理连接成完成阶段图。

- 依赖一个结果可用 `thenApply/thenCompose`，独立任务合并可用 `thenCombine`，等待多项完成可用 `allOf`。
- 关键是通过依赖关系触发后续工作，而不是占住工作线程等待每个子任务。

**追问 1：后一个任务依赖前一个结果，与两个独立任务并行执行后合并，分别如何组织？**

同步转换结果用 `thenApply`；下一步本身返回 `CompletionStage` 用 `thenCompose`，避免嵌套 Future。

独立任务分别启动后用 `thenCombine` 合并；`allOf` 只表示全部完成的信号，不自动替你收集所有类型化结果。

**追问 2：其中一项失败时，怎样决定整组失败、保留部分结果或提供降级结果？**

业务必须全部成功时让异常继续传播；允许部分结果时，对各任务分别转换为包含成功或失败的结果对象，再汇总；降级必须返回符合业务约束的替代结果。

不能把库存或支付失败一律降级成“成功”，也不能假设一个任务失败会自动取消全部兄弟任务。

**追问 3：相比逐个调用 `Future.get`，这种编排改变了哪些阻塞与组合方式？**

逐个 `get` 容易让编排线程同步等待，且异常和依赖结构分散；完成阶段可以在结果就绪时触发工作。

它并不让所有内部调用自动变成非阻塞，最终若在入口同步 `join` 仍可能等待，只是等待发生的位置和资源应更明确。

### 40. `CompletableFuture` 的异步阶段使用哪个线程池，异常如何传播到后续阶段？

异步阶段带显式执行器时使用该执行器；未指定时通常使用公共 `ForkJoinPool`，但低并行度等环境存在文档规定的备用行为。

非 Async 后续阶段可能由完成前一步的线程或发起关联操作的线程执行。异常会沿依赖传播，除非某个阶段明确处理或转换。

**追问 1：未显式指定执行器时，异步阶段会使用什么执行资源？同步后续阶段又可能在哪个线程执行？**

以 JDK 8 的标准 `CompletableFuture` 为例，未指定执行器的 Async 方法通常使用 `ForkJoinPool.commonPool()`；

- 若公共池不能提供至少为 2 的并行度，则为异步任务创建新的线程。
- 非 Async 阶段可由完成前一阶段的线程执行；注册时前一阶段已完成，也可能在注册该阶段的调用线程中执行。不要假定整条链始终在同一线程或同一个池里。
- 阻塞业务宜显式传入受控执行器；还需独立管理上下文、超时和资源并发限制。

**追问 2：`handle`、`exceptionally` 与 `whenComplete` 如何影响结果转换和异常传播？**

`handle` 同时处理正常值与异常，并可产生新结果；

- `exceptionally` 主要在异常时提供替代结果；
- `whenComplete` 用于观察结果或异常，通常保留原结果，但回调自身抛异常仍会影响后续完成状态。记录日志与业务降级应区分，避免无意吞掉故障。

**追问 3：调用方超时返回或取消 `Future` 后，怎样确认底层任务是否停止，并释放外部资源？**

`CompletableFuture.cancel` 或超时完成主要改变结果状态，不保证中断正在运行的任务。

- 应把取消传递到实际 HTTP、数据库或任务代码，配置底层超时并在 finally 中关闭资源。
- 需要确认结束时，还要检查实际执行状态，不能只看 Future 已完成。

### 41. `ForkJoinPool` 如何通过任务拆分与工作窃取提高并行处理能力？

`ForkJoinPool` 适合把较大计算拆成独立子任务，再合并结果；工作线程通常有本地双端队列，空闲线程从其他线程窃取工作，改善负载不均。

它的优势来自任务拆分和调度协作，不是给任意任务套上它就自动更快。

**追问 1：它与普通线程池的使用边界是什么？**

普通线程池适合较独立、粒度明确的任务；Fork/Join 更适合可递归拆分的计算，拆得太碎会被调度成本抵消。

合并步骤应有明确依赖，避免在其中无限等待不属于池管理范围的外部资源。

**追问 2：在共享池中执行大量阻塞任务需要关注什么？**

普通阻塞 I/O 可能长期占住工作线程，公共池还会影响并行流等其他使用者。

可改用专门受控执行器；确有需要时理解 `ManagedBlocker` 的补偿机制，但不能把它当成下游无限容量。仍要限流、超时并测资源开销。

### 42. `ScheduledThreadPoolExecutor`、`Timer` 与 `DelayQueue` 分别如何实现定时或延迟任务？

`Timer` 主要用单个线程安排任务；`ScheduledThreadPoolExecutor` 用线程池和延迟任务队列执行定时工作；`DelayQueue` 只是可按到期时间取出的队列，需要调用方负责消费执行。

它们都主要是进程内机制，进程退出后不自动恢复可靠任务状态。

**追问 1：固定频率与固定延迟有什么区别？**

对 `ScheduledThreadPoolExecutor`，`scheduleAtFixedRate` 的计划时间基于初次计划时刻加整数个周期；执行延误后可能连续补赶，但同一个周期任务不会并发重叠。

`scheduleWithFixedDelay` 则从上一次执行结束后，再等待指定延迟。

- `Timer` 也有固定频率和固定延迟的命名，但 `Timer.schedule(task, delay, period)` 的下一次时间主要以本次实际开始执行的时刻为基准，并不等同于“本次结束后再等待 period”。
- 任务耗时超过 period 时可能紧接着执行。比较不同 API 时必须给出方法名，不能仅靠“固定延迟”四个字判断行为。

**追问 2：单次任务执行过慢或抛出异常时，后续任务会怎样受影响？**

`Timer` 一个任务过慢会拖住后续任务，未处理的运行时异常可能终止定时线程；调度线程池能隔离部分并发，但池耗尽仍会延迟。

周期任务抛出异常时，后续周期执行通常被抑制，因此应记录失败并根据业务显式决定是否继续，而不是无限吞异常。

### 43. 动态线程池如何在运行中调整参数，而不是依赖重启应用？

动态线程池通过运行时配置与管理接口修改核心数、最大数、空闲时间等参数，同时用监控驱动调整。

它不是修改任意字段：例如已有 `ArrayBlockingQueue` 的容量不能靠标准 setter 原地改变，需要专门支持或替换方案。

**追问 1：需要监控哪些指标，如何判断参数调整是否有效？**

观察活跃线程数、队列长度和等待时间、执行耗时、拒绝数及下游容量。

- 提高核心数超过现有最大数时要先调整最大数，降低最大数时先保持约束合法；缩小上限也不意味着强杀正在执行的线程。
- 配置应支持校验、灰度、审计和回滚，调后验证尾延迟与错误率。

### 44. 平台线程与虚拟线程在任务执行和资源占用上有什么区别？

平台线程通常对应操作系统线程，创建和栈资源相对较重；虚拟线程由 JVM 调度到较少的平台承载线程，适合大量等待型任务保留顺序代码写法。

虚拟线程提高的是等待密集场景的并发承载能力，不会让 CPU 计算本身加速，也不会增加数据库处理能力。

**追问 1：以 JDK 21 为例，虚拟线程如何与承载它的操作系统线程协作？为什么阻塞 I/O 与 CPU 密集计算不能采用相同的扩容思路？**

JDK 21 中，许多受支持的阻塞操作可使虚拟线程卸载，释放承载线程处理其他任务；某些持有监视器或 native 场景会固定承载线程，需要结合版本排查。

- CPU 密集计算仍要占用处理器，因此不能靠创建更多虚拟线程获得线性加速。
- 后续 JDK 对固定问题有改进，不能永久套用 JDK 21 的细节。

**追问 2：每个任务创建一个虚拟线程，与用固定数量的平台线程组成线程池，有什么资源管理差异？是否还需要把虚拟线程放入固定大小的池中复用？**

典型方式是每个任务一个虚拟线程，而不是建立固定虚拟线程池去复用线程身份。

- 虚拟线程成本较低，真正需要限制的是数据库连接、内存和任务总量。
- 若把许可限制直接等同于“池中只能有几个虚拟线程”，可能抵消它在等待场景的收益。

**追问 3：数据库连接、外部服务配额等限制仍然存在时，应在哪一层限制并发？如何通过吞吐量、延迟与资源占用验证收益？**

在资源访问边界使用连接池、信号量、配额和有界入口控制，防止大量便宜线程变成昂贵的外部请求。

比较真实负载下吞吐、P95/P99、堆内存、连接等待和承载线程情况，确认不存在固定、排队转移或取消遗漏。

### 1. 字节流与字符流分别适合处理哪些文件？

字节流处理原始字节，适合图片、压缩包、网络报文等二进制内容；字符流在字节和字符之间进行编码转换，适合按文本处理。

选择依据是数据语义，不是文件扩展名或内容是否“看起来可读”。把图片按字符解码再写回，可能破坏原始数据。

**追问 1：字符编码在哪个环节生效？**

编码或解码发生在字节与字符的转换边界，例如 `InputStreamReader`、`OutputStreamWriter`。

缓冲流主要减少调用开销，并不自动决定正确字符集；发送方与接收方必须使用兼容的编码约定。

**追问 2：读取中文文本与传输图片时应如何选择？**

中文文本按明确字符集解码为字符后处理；图片保持字节内容直接传输。

即使都是文本，按字节截断也可能切开 UTF-8 多字节序列，所以文本长度、字符数和字节数应分开理解。

**追问 3：怎样避免依赖平台默认字符集造成乱码？**

显式指定 `StandardCharsets.UTF_8` 等协议约定的字符集，并处理非法编码输入；不要依赖操作系统或 JDK 默认值。

文件、HTTP 头和数据库连接处的编码要保持一致，避免在链路中多次错误解码。

### 2. 缓冲流为什么能减少 I/O 开销？

缓冲流先在内存中聚合少量读写，再以较大块与底层交互，减少频繁调用和系统调用开销。

它不会让磁盘速度无限提高，也不保证每个场景都受益；大块操作、已存在缓冲的层次以及刷新频率都会影响结果。

**追问 1：流对象的包装体现了什么设计模式？**

这是装饰器模式的典型应用：保持流接口，外层附加缓冲、编码、压缩等职责。

组合顺序会影响数据处理顺序，因此应理解每层职责，而不是随意套多层包装。

**追问 2：使用多层流包装时，如何安排关闭与刷新？**

通常关闭最外层包装流，由其按契约关闭下层；使用 `try-with-resources` 保证异常路径清理。

需要及时发送缓存内容时调用 `flush`，但过于频繁会削弱缓冲收益；`flush` 主要把这一层缓冲推给下层，不等于完成断电安全的磁盘持久化。

### 3. Java 文件写入返回成功、`flush` 返回成功与数据已经持久化到磁盘，是同一件事吗？

不是。写入方法返回可能只说明数据进入应用或操作系统缓冲；`flush` 通常把应用缓冲推给下一层；只有按文件系统和设备支持的同步机制完成持久化，才能讨论相应故障下的数据保证。返回成功的边界必须与业务可靠性需求匹配。

**追问 1：应用缓冲、操作系统页缓存与持久化存储分别在哪个阶段接收数据？**

数据可能依次经过 Java 缓冲区、操作系统页缓存、设备缓存和持久介质。

- 不同 API 跳过的层次不同，但不应把一次普通 `write` 直接解释为“物理盘已保存”。
- 文件内容和目录项等元数据的持久化也可能需要分别考虑。

**追问 2：进程异常退出与机器断电时，尚未持久化的数据可能处于什么位置？**

仅在进程内缓冲的数据会随进程消失；已进入内核页缓存的数据通常不会因该进程退出立即丢失，但机器断电仍可能丢失未落盘内容。

设备故障又超出单机刷盘的保护范围，需要副本与备份。

**追问 3：什么业务需要考虑 `force` 或同步写入，又应怎样权衡延迟和可靠性？**

日志、检查点、支付状态等需要明确耐久性时，可考虑 `FileChannel.force` 或相应同步写入方式，并固定本地存储等适用条件。

逐条同步延迟较高，常采用组提交或批量刷写，在明确的丢失窗口与延迟目标之间选择；不能用“调用过 flush”替代可靠性设计。

### 4. `try-with-resources` 如何关闭资源并保留异常信息？

`try-with-resources` 为实现 `AutoCloseable` 的资源生成关闭逻辑，退出 try 时按相反顺序关闭已经成功创建的资源，并保留主异常和关闭异常之间的关系。

它减少清理遗漏，但不会替业务决定事务提交或是否重试。

**追问 1：多个资源按照什么顺序关闭？业务执行失败时，关闭动作还会不会发生？**

资源按声明顺序创建，按逆序关闭；业务抛异常仍会关闭已创建资源。

- 后一个资源初始化失败时，前面已经成功创建的资源也会进入关闭流程。
- 资源引用在外部被提前关闭是否安全，则取决于具体资源的幂等关闭约定。

**追问 2：业务异常与 `close` 异常同时出现时，哪个成为主要异常，被抑制异常怎样查看？**

业务异常通常作为主要异常继续抛出，关闭异常加入 `getSuppressed()`；没有业务异常时，关闭阶段的异常可成为主要异常，其余关闭异常再被抑制。

日志应记录完整异常对象，而不是只记录 `getMessage()` 丢掉原因链和抑制异常。

### 5. BIO、NIO 与 AIO 的处理模型有何不同，如何据此选择网络 I/O 方案？

传统 BIO 通常在调用线程中等待读写完成；NIO 提供 Buffer、Channel 和 Selector，可用非阻塞网络通道加就绪通知管理多连接；AIO 以完成通知或 Future 表达异步操作。

NIO 这个包名不意味着其中所有通道都非阻塞，例如文件通道与网络 Selector 的支持范围不同。

**追问 1：同步、异步与阻塞、非阻塞的分类为什么不能混为一谈？**

阻塞与非阻塞描述调用在暂时无法推进时是否等待；同步与异步描述结果由调用者推进获取还是通过完成机制通知。

非阻塞 `read` 返回 0 后仍需调用者再次读取，所以不等同于异步完成。实际服务还要考虑线程、连接规模和业务是否阻塞。

### 6. NIO 的 `Buffer`、`Channel` 和 `Selector` 如何协作处理多个网络连接？

Buffer 保存数据与读写位置，Channel 在端点与 Buffer 之间传输，Selector 监听已注册非阻塞通道的就绪事件。

事件循环先等待就绪，再执行有限量读写并更新连接状态，避免为每个等待连接长期占用一个阻塞线程。

**追问 1：`Buffer` 的 position、limit、capacity 怎样约束读写区间？flip 与 clear 分别改变什么？**

满足 `0 ≤ position ≤ limit ≤ capacity`；position 是下一操作位置，limit 是本次可操作上界，capacity 是总容量。

`flip` 把已写数据切为可读区间；`clear` 重置读写边界但不清零内容；部分数据未消费完需要 `compact` 等方式保留剩余字节。

**追问 2：`Channel` 一次读写是否保证处理完全部数据？剩余内容和 `Selector` 就绪事件应该怎样配合？**

不保证，非阻塞读写可能只处理一部分甚至暂时返回 0；读到 −1 表示流结束。

连接状态需保存半包和待发送内容，写不完时再关注写就绪；写完后通常取消不必要的写事件订阅，避免持续就绪引发忙循环。

### 7. 堆内 `ByteBuffer` 与直接 `ByteBuffer` 在分配、复制和释放上有什么区别？

堆内 `ByteBuffer` 通常由 Java 数组承载，分配与 GC 管理较直接；直接缓冲区使用堆外内存，参与某些本地 I/O 时可以减少中间复制，但分配与回收成本较高。

它不等于绝对零拷贝，也不适合为了“更快”给所有小对象都使用堆外内存。

**追问 1：堆内与直接缓冲区在分配位置和参与 I/O 的复制路径上有何不同？**

堆缓冲在 Java 堆上，本地 I/O 路径可能需要临时直接缓冲以避免 GC 移动等影响；直接缓冲可直接提供稳定的本地地址。

具体拷贝次数仍受 JDK、操作系统、驱动和调用方式影响，应以所用路径分析。

**追问 2：直接内存的申请与释放怎样管理，为什么减少一次拷贝不等于没有内存管理成本？**

直接缓冲区对象本身仍在堆上，背后内存通常由清理机制或库的池化与显式生命周期协议管理。

频繁申请会有本地分配成本，释放时机也可能晚于业务使用结束；需要监控直接内存上限、池占用和引用泄漏，不能只看 Java 堆使用率。

### 8. `RandomAccessFile` 和文件映射如何支持随机读写或分片文件合并？

`RandomAccessFile` 通过文件位置定位读写，文件映射则把文件区间映射到进程地址空间按内存方式访问。

分片合并可给每片确定偏移并写入对应范围，避免一次把整个文件读入内存。映射也仍有缺页、刷盘和生命周期成本。

**追问 1：多个线程写入同一文件时，如何划分偏移量、控制文件长度并避免覆盖？**

共享 `RandomAccessFile` 的 `seek` 与 `write` 是复合操作，需要同步；

- 更适合并发分片的方式是使用带显式位置的 `FileChannel.write(buffer, offset)`，并循环处理部分写入。
- 提前校验偏移、长度、分片校验和与总文件大小，不允许重叠越界；完成所有写入并验证后再原子地发布最终文件。

### 9. Netty 的 Reactor 与线程模型如何组织连接接入和读写事件？

典型 Netty 服务端把接入事件交给 boss 事件循环组，把已建立连接的读写注册到 worker 事件循环组。

一个 Channel 通常固定关联一个 EventLoop，以串行处理该通道的相关事件，减少同步复杂度；一个 EventLoop 又可以管理多个连接。

**追问 1：连接接入与已建立连接的读写，分别由哪些事件循环处理？**

boss 负责接受新连接，再注册到 worker；worker 处理读取、写入就绪和定时任务等。

线程数量与角色不是必须各只有一个，具体由引导配置和通道实现决定；异步 API 不意味着每个请求新建线程。

**追问 2：业务处理怎样进入 Pipeline？为什么一个 `EventLoop` 上的阻塞可能影响多个连接？**

读取数据后沿 `ChannelPipeline` 调用入站处理器，业务处理也可能默认运行在同一 EventLoop 上。

若其中执行慢数据库调用，该循环无法及时处理其他连接，所以应把阻塞业务转给受控执行器，保留必要的事件顺序和生命周期。

### 10. Netty 的 `ChannelPipeline` 与 `ChannelHandler` 如何组织入站、出站事件？

Pipeline 是一个处理器链。入站事件通常从前向后传播，出站事件通常从后向前传播；处理器可以解码、编码、处理业务和异常，并决定是否继续传播。

调用 `channel.write` 与从某个 `ChannelHandlerContext` 发起写入，起始位置可能不同。

**追问 1：处理器顺序、事件继续传播和异常处理会怎样影响一次请求？**

解码器应在依赖解码结果的处理器之前，出站编码器要位于实际写路径上。

- 入站处理后若需要下一个处理器继续，就调用相应 `fire...`；出站拦截后通常需要继续 `ctx.write` 并维护 Promise。
- 异常由专门路径处理，不能简单吞掉，否则调用者可能一直等待完成。

### 11. Netty `ByteBuf` 如何进行池化、切片与引用计数管理？

ByteBuf 用 reader/writer index 区分已读与已写数据；池化复用内存，切片共享底层存储，引用计数控制何时释放。

- 效率来自避免重复分配和复制，但调用者必须明确所有权。
- 对象不可用了却仍持有引用，可能出现内存泄漏或释放后访问。

**追问 1：池化、切片和引用计数各减少什么开销，又引入什么生命周期约束？**

池化减少分配开销，切片避免复制区间内容；普通派生切片通常与原对象共享引用计数关系，不会自动多出一份独立生命周期。

需要独立持有可使用适当的 retained 变体或显式 `retain`，并与对应释放次数匹配。

**追问 2：`ByteBuf` 跨线程传递或被长期保存时，谁负责 `retain` 与 `release`？**

接收者需要在原持有者释放后继续使用时，应在交接前保留引用，接收者完成后释放。

- 规则必须约定由谁最终消费，不是每层盲目 retain。
- 使用会自动释放入站对象的处理器时尤其要注意，不能把原对象直接交给异步线程后假定仍有效。

**追问 3：遗漏释放和重复释放分别可能产生什么现象，应怎样检查完整交接路径？**

漏释放可能导致直接内存或池占用持续增长；重复释放或释放后使用可能抛引用计数异常并造成请求失败。

沿创建、派生、转交、异常和取消路径逐一检查，并结合 Netty 泄漏检测；引用计数正确也不意味着 ByteBuf 的并发读写天然安全。

### 12. 为什么不应在 Netty `EventLoop` 上执行耗时数据库访问或阻塞调用？

EventLoop 要及时处理一组连接的事件，耗时阻塞调用占住它会让其他连接的读写、超时和任务回调一并延迟。

Netty 的高并发并不允许在事件循环里无限等待下游；业务并发和 I/O 事件处理应有明确隔离。

**追问 1：同一 `EventLoop` 管理的其他连接会怎样受影响？**

同一循环上的其他连接可能出现响应慢、发送缓冲积压、心跳超时，哪怕它们的业务逻辑本身很轻。

症状还可能误导为网络问题，因此应查看事件循环线程栈和任务耗时。

**追问 2：如何把业务任务转交独立执行器并返回结果？**

把必要的不可变请求数据或已明确保留引用的缓冲交给有界执行器，完成后通过 Channel 或事件循环提交结果。

- 处理拒绝、连接已关闭、超时与取消，并保持业务要求的同连接顺序。
- 不能用无界线程池把阻塞从一个位置转移成无限内存增长。

### 1. JVM 的运行时数据区如何划分，线程共享与独享区域的边界是什么？

JVM 规范的主要运行时数据区包括堆、方法区、Java 虚拟机栈、本地方法栈和每线程程序计数器。堆与方法区为线程共享，栈和程序计数器属于线程。

规范描述抽象职责，具体内存布局由实现决定，不能把 HotSpot 的所有细节当成所有 JVM 的统一规则。

**追问 1：对象、局部变量和类元数据分别存放在哪里？**

普通对象与数组通常在堆上；栈帧保存局部变量、操作数栈和方法执行信息，局部引用值在栈帧中不意味着其对象也在栈上。

HotSpot 类元数据通常位于元空间；静态字段关联的 Java 对象和字符串等仍可位于堆，JIT 机器码还有独立代码缓存。

**追问 2：方法区与元空间是什么关系？**

方法区是规范概念，元空间是 HotSpot 自 JDK 8 起用于相关类元数据的实现方案，使用本地内存。

不能将方法区简单等同为“全部数据都放在元空间”；讨论内存问题还需区分 Java 堆、元空间、代码缓存、线程栈与直接内存。

### 2. `StackOverflowError` 与 `OutOfMemoryError` 分别可能在哪些资源不足时出现？

`StackOverflowError` 通常表示线程调用栈所需空间超出允许范围；`OutOfMemoryError` 表示某类内存或相关资源分配无法满足，可能是 Java 堆、元空间、直接内存或本地线程资源。

不能只看到 OOM 就立即增大 `-Xmx`，先看异常信息和实际耗尽位置。

**追问 1：深递归、堆中存活对象过多、元空间增长和创建过多线程，分别应检查哪类资源？**

深递归检查调用深度与 `-Xss`；存活对象过多检查堆转储和引用链；动态生成类检查元空间及类加载器泄漏；创建过多线程检查线程数、进程限制与本地栈空间。

容器被系统 OOM Kill 又可能没有 Java 异常堆栈，要查容器和内核证据。

**追问 2：增大线程栈与增大堆内存为什么可能相互挤占进程可用空间？**

进程或容器总内存有限，增加每线程栈乘以大量线程会挤占堆外余量，增大堆也会减少留给栈和本地库的空间。

虚拟地址保留与实际物理驻留还不完全相同，容量评估应同时看限制与实际使用。

**追问 3：如何用最小示例区分错误类型，再通过运行参数和诊断数据验证原因？**

仅在隔离测试进程中，用受控深递归观察栈溢出，用小堆持续保存对象观察堆 OOM，并记录参数和异常文本。

生产环境不主动制造耗尽；通过线程数、GC 日志、堆转储或 NMT 验证，避免最小示例的单一结论替代线上取证。

### 3. 类加载的加载、链接与初始化阶段分别完成什么工作？

加载读取类的二进制表示并建立运行时类型；链接包含验证、准备和解析；初始化执行类的静态初始化逻辑。

解析可以按实现策略延迟进行，因此不必假设所有符号引用在第一次执行前已经全部解析。不同阶段失败会产生不同类型的加载或链接错误。

**追问 1：验证、准备与解析分别处理什么，哪些工作不能与初始化混为一谈？**

验证检查格式和字节码等约束，准备建立静态存储等基础状态，解析把符号引用转换为可用的运行时关联；普通静态赋值和静态代码块的执行属于初始化。

不能把“类已经被加载”理解为所有静态业务逻辑已经执行。

**追问 2：第一次主动使用某个类时，怎样判断它是否已经完成加载、链接和初始化？**

`new`、调用静态方法、访问非编译期常量的静态字段及某些反射操作会触发初始化。

- `Class.forName` 的常用重载默认初始化，`ClassLoader.loadClass` 通常不主动初始化。
- JVM 协调同一类的初始化，重复主动使用不会反复执行成功的静态初始化块。

### 4. 双亲委派模型解决了什么问题，哪些场景需要改变默认的类加载路径？

双亲委派是常见类加载器的查找策略：先委托父加载器，父加载器找不到再由当前加载器尝试。它帮助统一核心类身份并避免重复定义。

类加载隔离和插件发现有时需要调整查找方向，但仍必须遵守 JVM 类型约束和核心类保护规则。

**追问 1：以 JDK 17 为例，启动类加载器、平台类加载器和应用类加载器分别负责什么？加载请求如何按默认规则委派？**

JDK 17 的启动类加载器负责核心运行时类，平台类加载器负责平台相关类，应用类加载器通常负责应用 classpath 等。

- 实际模块归属有细节，不能再机械套用旧扩展目录模型。
- 默认请求沿父链委托，查找失败后再回到子级尝试定义。

**追问 2：Tomcat 的应用隔离或 SPI 的实现发现，为什么可能需要调整默认查找方式？**

Tomcat 为不同 Web 应用提供隔离，部分应用类采用本地优先查找，同时对核心类等保留委派；SPI 的接口可能由父加载器定义，实现却在应用路径，需要线程上下文类加载器等让发现机制访问实现。

SPI 不意味着所有场合直接修改了 `loadClass` 的委派算法。

**追问 3：全限定名相同的类由不同类加载器定义后，能否直接当成同一种类型？如何分析转换失败？**

类身份由二进制名称与定义它的类加载器共同决定。

- 同名类由两个不同定义加载器产生时，通常不是同一类型，互相转换可能失败。
- 应检查类与接口各自由谁定义，而不是只看到全限定名相同就认为依赖一定兼容。

### 5. 类的静态变量、静态代码块、实例成员和构造方法按什么顺序初始化？

以普通 JDK 17/21 类构造为例，类初始化通常先父类、后子类，各类静态字段初始化表达式与静态块按规定顺序执行；创建实例时先有默认值，再沿构造器链完成父类初始化和构造，之后执行子类实例初始化与构造器剩余部分。

静态初始化与每次实例初始化不是同一次动作。

**追问 1：父类与子类同时存在这些初始化逻辑时，顺序如何变化？**

首次创建子类对象时，通常先执行尚未完成的父、子类静态初始化；对象构造再先父类后子类，每一层的实例字段初始化和实例块按文本顺序执行。

构造器中的虚方法调用可能分派到子类，而子类字段还未初始化，实际设计中应避免这种风险。

**追问 2：访问编译期常量是否一定触发声明类初始化？**

不一定。对编译期常量的引用可能被编译进调用方，不触发声明类初始化；普通 `static final` 引用或运行期计算值不一定是编译期常量。

判断要看常量表达式和访问方式，而不是只看字段有 `final`。

### 6. 解释执行与 JIT 编译如何共同执行 Java 程序？

HotSpot 通常先解释执行或使用较低成本编译，收集调用和分支等运行信息，再对热点方法或循环进行更深入 JIT 优化。

编译后的机器码可反复执行，运行假设失效时也可能去优化。这样在启动成本与稳定运行吞吐之间折中。

**追问 1：为什么不是所有方法从启动起就采用同一种执行方式？热点检测怎样参与选择？**

如果启动就高成本编译所有方法，很多从未执行的方法也会付出时间和内存；一直解释则热点路径成本高。

调用计数和循环热点帮助分配优化预算，分层编译使常见负载逐步进入适合的执行状态。

**追问 2：方法内联与逃逸分析可能带来什么优化，哪些代码特征会影响效果？**

内联消除部分调用开销并暴露更多优化机会；逃逸分析可帮助锁消除和标量替换。

- 复杂多态调用、反射、逃逸到共享结构等可能影响优化。
- 不能把某一次 JIT 行为写成语言保证，必须区分语义和实现优化。

**追问 3：程序预热会怎样影响压测结果？如何避免用一次短测试判断稳定性能？**

预热阶段涉及类加载、编译和缓存建立，短测试可能主要测到启动成本。

稳定压测应包含足够预热、持续负载和多次重复，并使用合适基准工具；微基准还要避免常量折叠、死代码消除等让测量对象消失。

### 7. 一个对象从 `new` 到初始化完成会经历哪些步骤？

概念上先确认类型可用并在需要时完成类初始化，再为对象分配空间、设置默认值及对象元信息，最后执行实例初始化和构造器。

实际实现可优化部分步骤，只要保持语言可观察语义。引用赋值与对象构造安全发布也应分开讨论。

**追问 1：对象布局包含哪些信息？**

常见 HotSpot 对象包括对象头、实例字段和对齐填充；数组还包含长度等信息。

对象头用于类型和运行时管理信息，具体大小受 JVM 版本、位数和压缩设置影响，不能只按业务字段相加。

**追问 2：逃逸分析与标量替换可能如何优化分配？**

若 JIT 证明对象不逃逸，并能把其字段拆成独立标量，可能消除对象分配，直接用寄存器或其他执行存储保存值；也可消除不必要的锁。

这是有条件优化，不是源码中写了 `new` 就必定出现一个可观测的堆对象。

**追问 3：为什么不能把“不逃逸”一律理解为“整个对象必定分配在栈上”？**

不逃逸是优化分析结果之一，不等于实现必然把完整对象搬到栈。

可能仍在堆分配，也可能被标量替换完全消除；是否实施还取决于 JIT 能力和具体代码。面试中说“逃逸分析决定一定栈上分配”过于绝对。

### 8. HotSpot 对象头、对齐填充与压缩指针会怎样影响对象大小？

以常见 64 位 HotSpot JDK 17 配置为例，对象头包含 Mark Word 和类指针，启用压缩类指针时普通对象头常为 12 字节，再按对象对齐要求补齐；数组还需要长度字段。

引用压缩减少对象内引用字段占用，但范围与编码依赖配置。其他版本可能采用不同对象头布局。

**追问 1：为什么估算一个对象的内存不能只相加业务字段的字节数？请说明 JVM 位数与相关配置。**

要加上对象头、字段排列、引用宽度和对齐填充，还要区分对象自身浅大小与它引用的整个对象图大小。

可用 JOL 等工具在目标 JVM 上验证，并记录 `UseCompressedOops`、`UseCompressedClassPointers` 与对象对齐配置；不要给出脱离环境的固定字节结论。

### 9. TLAB 如何降低多个线程同时创建对象时的分配竞争？

TLAB 是从堆中为线程分配的一小段本地分配缓冲，线程在其中创建小对象时通常只需推进自己的分配指针，减少每次都竞争全局分配位置的成本。

它位于堆内，不是线程栈，也不改变对象之后能否被其他线程引用。

**追问 1：TLAB 分配与对象是否线程共享有什么关系？**

线程私有的是分配区域管理权，不是其中对象永远私有。

对象随后仍可通过共享结构发布给其他线程；发布与并发访问需要正常的同步规则，不能因为对象来自 TLAB 就跳过。

**追问 2：空间不足或对象过大时如何处理？**

空间不足时可申请新的 TLAB，或走共享分配等慢路径；较大对象可能绕开 TLAB。具体行为受收集器和尺寸策略影响。

TLAB 末尾未用空间会形成浪费，因此实现会调整大小，在竞争减少与空间利用之间折中。

### 10. 在分代回收的语境下，对象如何在 Eden、Survivor 与老年代之间流转？

在典型分代回收中，多数新对象先进入年轻代；回收时存活对象在 Survivor 区之间复制或晋升老年代。

分代利用了很多对象短命的经验规律，但 Eden/Survivor 的物理组织因收集器而异，不能把 G1 的 Region 与固定连续分区完全混同。

**追问 1：晋升年龄、大对象和存活对象比例如何影响分配与回收？**

晋升受年龄阈值、Survivor 容量和动态年龄判定等影响，不是所有对象必定经历固定次数才进入老年代；大对象路径也依收集器而异，例如 G1 对 Humongous 对象有专门 Region 管理。

高存活比例会增加复制和晋升压力，应看实际 GC 日志。

### 11. JVM 如何从 GC Roots 判断对象可达性，为什么循环引用不一定阻止回收？

GC 从根集合出发遍历引用，能到达的对象视为存活；没有可达路径的循环引用仍可整体回收。

因此 Java 常用的追踪式 GC 与简单引用计数不同，不会仅因两个对象互相引用就永远无法回收。

**追问 1：GC Roots 可以来自哪些运行时状态？如何沿引用链判断一个对象是否可达？**

根可以来自线程栈和寄存器中的活跃引用、JNI 句柄、由存活类关联的静态引用以及虚拟机内部根等。具体扫描形式由实现决定。

分析泄漏时沿从根到对象的保留链定位“谁仍在持有”，而不是只统计对象数量。

**追问 2：两个对象相互引用，但没有从 GC Roots 到达的路径，应该怎样判断？**

若这两个对象之间只有内部互相引用，且没有任何根可到达它们，就可以成为回收对象。

真正的泄漏通常是集合、线程上下文、监听器等仍从根路径持有本应结束生命周期的对象。

**追问 3：强、软、弱、虚引用对存活与回收有哪些不同约束，资源关闭能否交给它们自动保证？**

强引用维持通常可达性；软引用在内存压力等条件下可被清理，不适合精确容量缓存；弱引用不阻止相应回收；虚引用配合引用队列观察回收相关阶段，不能直接取得对象。

文件、连接和锁必须显式关闭或释放，不能把及时资源清理交给 GC 时机保证。

### 12. 不同垃圾回收算法如何在复制成本、内存碎片与空间利用率之间取舍？

标记清除避免整体搬移但可能产生碎片；复制把存活对象集中搬到新空间，适合存活率较低区域，但需要预留空间；标记整理减少碎片，代价是移动对象和更新引用。

实际收集器会组合这些思想，并协调并行、并发与停顿阶段。

**追问 1：结合具体收集器，说明 Minor GC、Full GC 与 Mixed GC 的触发和回收范围。**

以 JDK 8 Parallel 收集器为例，年轻代分配无法满足时通常触发 Young/Minor GC，只回收年轻代；老年代分配或晋升无法满足、某些元数据回收请求或未被禁用的显式 GC 请求，可能触发 Full GC。

不能把“年轻代一满”直接等同于 Full GC。

- 在 G1 中，Young GC 回收年轻代；并发标记为老年代回收提供存活信息；Mixed GC 在回收年轻代的同时选择部分老年代 Region。
- 正常疏散和并发回收无法满足分配时，可能退化为 Full GC。
- 具体原因必须结合 GC cause、收集器和配置，不能把 G1 的 Mixed GC 套到所有收集器。

### 13. 进行新生代回收时，JVM 如何发现老年代对新生代对象的引用？

新生代回收不希望扫描整个老年代，因此用记忆集等结构记录可能存在跨代引用的位置。

应用写入对象引用时，写屏障按协议更新相关信息，回收时只扫描这些候选范围，再准确检查其中的引用。

**追问 1：卡表、记忆集和写屏障分别承担什么职责？**

卡表把堆划成较粗粒度的卡片，记录发生相关写入的区域；记忆集记录进入某代或某 Region 的外部引用信息；写屏障是在引用写入周围执行的维护逻辑。

卡片脏不等于其中每个对象都是垃圾，它只是需要进一步扫描的线索。

**追问 2：为什么不希望每次都扫描整个老年代？**

老年代可能远大于年轻代，每次完整扫描会使频繁年轻代回收失去低成本优势。

记忆集把部分成本转移到应用写入与后台维护；跨代引用很多时这部分开销也会变大，不能认为只要分代就没有额外成本。

### 14. 并发标记期间对象引用发生变化，会造成哪些漏标或保留过久的问题？

并发标记时，应用仍在改变对象图。如果算法只按一次静态遍历理解，可能漏掉仍存活对象，也可能保留本轮已无用的浮动垃圾。

收集器通过写屏障、读屏障或快照策略维护相应不变量，保证安全性，允许某些垃圾延后回收。

**追问 1：结合三色标记说明如何维护正确性，并区分垃圾回收屏障与 JMM 内存屏障。**

三色模型中，白色未访问、灰色待扫描、黑色已扫描；危险情况是引用改变让仍存活的白对象失去可被后续扫描发现的路径。

- G1 的 SATB 通过记录被覆盖的旧引用维护标记开始时的逻辑快照，是具体解决方案之一。
- GC 屏障维护对象图与引用访问，JMM 内存屏障维护并发可见性和顺序，两者名字相似但职责不同。

### 15. 为什么垃圾回收的部分阶段需要 STW，安全点在其中起什么作用？

某些根扫描、状态切换或对象移动阶段需要得到协调一致的线程状态，因此会暂停应用线程。

- 安全点是 JVM 能可靠识别执行状态和引用等信息的位置或机制。
- 并发收集器只是把大量工作移到并发阶段，并不意味着完全没有停顿。

**追问 1：应如何区分并发回收阶段与需要暂停应用线程的阶段？**

应按收集器日志区分并发标记等后台阶段、应用线程暂停阶段，以及到达安全点的等待时间。

短 GC 工作不代表总暂停一定短，线程迟迟到达可安全停顿状态也可能影响延迟；不能把所有 STW 都归因于老年代空间不足。

### 16. 如何根据吞吐量、停顿目标和资源限制选择垃圾收集器？

先固定 JDK 与硬件，再按延迟目标、吞吐、堆大小和资源预算选择。

以 JDK 21 为例，Serial 适合较小堆或受限资源，Parallel 偏重吞吐，G1 平衡吞吐与停顿，ZGC 偏重低停顿并发回收。没有对所有负载都最优的收集器。

**追问 1：Serial、Parallel、G1 与 ZGC 的目标和适用负载有什么不同？请固定 JDK 版本后比较。**

以 JDK 21 HotSpot 为例，Serial 用单个 GC 线程完成主要回收，适合小堆或受限资源；

- Parallel 用多线程执行暂停式回收，偏向吞吐；
- G1 用 Region、并发标记和疏散回收平衡吞吐与停顿；
- ZGC 把更多标记和重定位工作并发化，偏向低停顿。
- JDK 21 使用 `-XX:+UseZGC` 时默认是非分代 ZGC；加上 `-XX:+ZGenerational` 才启用该版本的分代 ZGC。
- 后续版本的默认值和可选模式有所变化，不能直接套用。比较应记录 JDK 版本、所选模式和同一套负载。

**追问 2：堆大小、存活对象比例、分配速率和可用 CPU 数量会如何改变选择？**

高分配速率需要足够回收能力和空间余量；高存活比例增加扫描或移动成本；小 CPU 配额下并发 GC 可能与业务争抢处理器；大堆且严格延迟场景更值得评估低停顿方案。

选择后仍需解决真实泄漏或无界缓存，换 GC 不会使无限增长变成有界。

**追问 3：为什么不能只比较单次 GC 停顿，还应同时观察吞吐量、分位延迟与总资源开销？**

降低单次暂停可能增加并发 CPU 或内存成本，甚至降低总吞吐。

用同一负载比较请求 P95/P99、完成吞吐、GC 总 CPU、分配速率和峰值内存，并检查是否发生分配停顿或退化回收，不能只挑最好的一次暂停截图。

### 17. G1 如何利用 Region 和回收集合安排回收工作？

G1 把堆划分为多个 Region，在年轻代回收和混合回收时形成回收集合，通过复制存活对象回收选中区域。

它根据历史成本和可回收收益估算工作量，并使用并发标记为老年代选择提供依据，目标是可预测地控制停顿而不是绝对保证。

**追问 1：Region 与回收集合怎样参与工作量选择和内存管理？**

Region 承担 Eden、Survivor、Old 等角色，角色可随使用变化；回收集合决定本次暂停要处理哪些区域。

跨 Region 引用由记忆集等辅助维护，避免每次都全堆扫描。普通回收需要足够目标空间供存活对象转移。

**追问 2：暂停目标为什么不能当成任何负载下的硬性停顿上限？**

暂停预测依赖历史行为，突然的高存活率、巨大对象、CPU 受限或转移空间不足都可能使实际耗时超出目标。

`MaxGCPauseMillis` 是目标参数，不是硬实时保证，调得极低还可能牺牲吞吐。

**追问 3：与历史环境中的 CMS 相比，碎片处理、并发阶段与资源开销有哪些取舍？**

CMS 主要对老年代并发标记清除，容易面对碎片和并发失败；G1 通过区域化复制整理改善碎片管理，但要付出记忆集、屏障和对象转移成本。

CMS 属历史收集器，比较时应明确旧环境，不能把它当作 JDK 21 的可选内置收集器。

### 18. G1 的 Young GC、并发标记、Mixed GC 与 Full GC 分别在什么条件下出现？

G1 Young GC 回收年轻代；并发标记统计老年代等区域的存活状态；随后 Mixed GC 将年轻代与部分收益较高的老年代 Region 一起回收。

正常增量路径无法满足分配需求时可能退化到 Full GC。具体触发应结合日志与占用变化分析。

**追问 1：Young GC、并发标记与 Mixed GC 分别处理什么范围和阶段？**

年轻代空间或相关分配压力触发 Young GC；并发标记通常在老年代占用达到自适应阈值附近启动；标记结束后按策略选择 Mixed 集合。

并发标记不是把全部老年代立即清空，后续回收仍需要空间与时间预算。

**追问 2：大对象分配或可回收空间不足时，可能怎样影响后续回收与停顿？**

Humongous 对象需要专门的连续 Region 布局，可能增加碎片与回收压力；存活对象转移所需空间不足可能出现 evacuation failure，并促使退化回收或更长停顿。不能只通过增大年轻代解决所有 G1 分配问题。

**追问 3：如何结合 GC 日志确认触发原因，而不是只看暂停时间目标是否配置？**

检查 GC cause、各代与 Region 变化、并发周期启动、Humongous 数量、转移失败和堆余量，再关联分配速率及应用延迟。

配置暂停目标只是输入条件，日志中的实际阶段与失败原因才是验证依据。

### 19. G1 与 ZGC 的设计目标和适用场景有什么不同？

G1 更偏向吞吐、资源和可控停顿的综合平衡；ZGC 用更多并发工作和相应屏障设计降低停顿对堆规模的敏感度。

它们都需要足够 CPU 与内存余量，也都不能修复业务保留对象无限增长的问题。

**追问 1：结合所用 JDK 版本，如何在吞吐量、延迟和资源开销之间选型？**

固定 JDK 21 时，分别测试 G1 与所选 ZGC 模式，明确是否启用分代 ZGC；后续版本默认模式变化需单独核对。

- 严格尾延迟且能接受资源成本时优先评估 ZGC，通用服务可先评估 G1。
- 比较实际吞吐、P99、GC CPU 与峰值内存，不只比较宣传的停顿数字。

### 20. 配置 JVM 堆、线程栈和垃圾收集器参数时，如何结合应用负载与机器资源确定边界？

先从进程或容器总资源中预留线程栈、直接内存、元空间、代码缓存和本地库空间，再确定堆上限；根据线程规模与调用深度设置栈，按负载选择收集器。

`-Xms`、`-Xmx` 和 `-Xss` 不是互不相关的独立旋钮，不能把全部容器内存都分给堆。

**追问 1：参数调整如何兼顾内存占用、GC 停顿与服务吞吐？**

用稳定负载下的存活集、分配速率、GC 周期和分位延迟形成基线，再一次调整少量参数并比较。

堆增大会减少部分回收频率，但可能增加扫描成本和挤占其他内存；栈增大可以容纳更深调用，却降低可承载线程数量。先修复泄漏和无界队列，再谈参数优化。

## 要点回顾

- 区分语言语义与具体实现：类型、相等性和可见性先按语义理解，集合内部结构、锁实现和收集器行为再结合 JDK 版本讨论。
- 选型要回到访问方式与共享状态：集合的方法线程安全，不代表一组复合操作天然安全；线程数量也不能脱离下游容量配置。
- 把分配、执行和回收连起来理解：对象可回收、进程内存下降以及 GC 停顿是不同问题，性能结论需要在可比负载下验证。
