### 1. IP、端口与域名在一次请求中分别用于定位什么？

IP 地址用于网络层寻址和路由，端口用于在目标主机上区分传输层通信端点，域名提供稳定、可管理的名称，并通常经 DNS 解析为地址。

域名不是某台机器的永久身份；一个域名可以对应多个地址，一个地址也可以承载多个域名和服务。

**追问 1：同一 IP 上部署多个服务时，反向代理如何继续区分目标服务？**

反向代理可根据监听端口、TLS 握手中的 SNI、HTTP/1.1 的 Host 或 HTTP/2、HTTP/3 的 `:authority`，再结合路径和路由规则选择后端。

SNI 主要帮助选择 TLS 虚拟主机和证书；TLS 解密后才能读取普通 HTTP 路径等内容。不能仅凭目标 IP 区分同 IP 下所有业务。

### 2. 网络分层中的封装与解封装如何进行？

发送端把应用数据交给传输层，添加 TCP 或 UDP 头，再添加 IP 头和链路层头尾，通过物理介质发送。

- 接收端逐层校验、识别并去掉相应封装，把数据交给目标协议和应用。
- 各层处理自己的语义，路由器通常转发 IP 包，不需要理解完整业务请求。

**追问 1：MAC 地址、IP 地址和端口分别用于定位什么？**

MAC 地址用于当前链路上的帧交付，IP 地址用于跨网络路由，端口用于标识主机内传输层端点。

跨路由器转发时，链路层源和目的 MAC 通常改变，IP 源和目的通常保持，NAT 等情况除外。不能把 MAC 当成互联网全路径的最终路由地址。

**追问 2：同网段通信与跨网段通信中，ARP、交换机和路由器各承担什么角色？**

以 IPv4 以太网为例，同网段通过 ARP 找到目标 IP 对应的 MAC，再由交换机按 MAC 转发；跨网段先通过路由表选择网关，ARP 获得网关 MAC，路由器再逐跳转发到目标网络。

交换机主要处理链路转发，路由器处理网络间寻路；IPv6 使用邻居发现而非 ARP。

### 3. 访问一个使用 HTTPS 的网站时，从输入 URL 到收到响应会经历哪些网络阶段？

通常先解析 URL，检查相关缓存与代理策略，通过 DNS 获取地址；再建立所需传输连接，完成 TLS 身份验证和密钥协商，发送 HTTP 请求。

- 服务端经过代理和业务处理返回响应，客户端读取报文并处理缓存与后续资源。
- 具体阶段会因连接复用、协议版本和缓存命中而省略或变化。

**追问 1：先以 HTTP/1.1 或 HTTP/2 为前提，说明 DNS、TCP、TLS 和 HTTP 如何衔接。**

HTTP/1.1 或 HTTP/2 的 HTTPS 链路通常是 DNS → TCP 三次握手 → TLS 握手及 ALPN 协商 → HTTP 请求响应。

- TLS 校验证书，ALPN 确定应用协议；之后 HTTP 数据由 TLS 保护，再由 TCP 提供有序字节流。
- DNS 不负责建立业务连接，TCP 也不负责验证网站证书。

**追问 2：DNS 缓存、TLS 会话恢复和连接复用分别能省去或缩短哪些环节？**

DNS 缓存可避免部分或全部解析往返；TLS 会话恢复减少重复认证和密钥协商成本；已有连接复用可以跳过新的 TCP 与完整 TLS 建连。

- HTTP 缓存若直接满足请求，甚至无需发送源站业务请求。
- TLS 恢复不是沿用所有旧连接状态，仍要满足安全和有效期条件。

**追问 3：如果协商使用 HTTP/3，传输层及连接建立过程应如何调整，为什么不能继续完整套用 TCP 链路？**

HTTP/3 使用 QUIC，QUIC 建立在 UDP 上，并把 TLS 1.3 的握手与传输状态协商结合起来，没有独立的 TCP 三次握手。仍需要地址发现、对端认证、流量和拥塞控制。

支持 0-RTT 的恢复连接可以更早发送部分请求，但早期数据存在重放风险，不能对有副作用的业务无条件启用。

### 4. 服务端的 socket、bind、listen、accept 与客户端的 connect 如何对应 TCP 建连过程？

服务端先 `socket` 创建端点，`bind` 绑定本地地址和端口，`listen` 进入监听状态；客户端 `connect` 发起 TCP 建连。

- 内核处理握手并把完成的连接交给监听队列，服务端 `accept` 取出一个已连接套接字供应用读写。
- 握手主要由内核完成，不是应用调用一次 accept 才发送一次握手报文。

**追问 1：监听套接字与每个已连接套接字分别记录什么状态？**

监听套接字记录监听地址、端口和连接队列等信息，用于接收新连接；已连接套接字记录具体双方地址、端口、序列号、缓冲和连接状态，承载一条连接的数据。关闭某个已连接套接字不会自动关闭监听套接字。

**追问 2：同一个服务端端口处理多个客户端时，连接如何区分？**

TCP 通常用源 IP、源端口、目的 IP、目的端口这一四元组区分连接，并结合协议和网络命名空间等上下文管理。

多个客户端连接同一服务端端口时，客户端地址或端口不同，因此连接仍可唯一识别。服务端不需要为每个连接开放一个新的监听端口。

**追问 3：连接建立但应用未及时 accept 或读取时，为什么请求仍可能等待？**

握手完成只说明内核建立了连接。应用迟迟不 accept，完成队列可能积压；accept 后不读取，接收缓冲可能填满、接收窗口缩小。

业务线程池或数据库也可能排队，因此“connect 成功”不等于“HTTP 请求已开始处理”，更不等于业务已完成。

### 1. TCP 与 UDP 在连接、可靠性、传输方式和开销上有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| TCP | TCP 提供面向连接、有序、可靠的字节流，并具有流量与拥塞控制 |
| UDP | UDP 提供无连接的数据报发送，保留报文边界，但自身不保证交付、顺序或去重 |

TCP 维护更多状态和协议交互，UDP 头部及机制较简单；但不能脱离网络和上层协议一概断言 UDP 一定更快。

**追问 1：连接状态、可靠交付、字节流与报文边界分别有哪些不同？**

TCP 建连后维护序列号、窗口和重传状态，不保留每次应用写入边界；UDP 的每次数据报是独立报文，接收缓冲不足可能截断或丢弃报文。

TCP 的可靠性是“成功交付有序字节或报告失败”的传输语义，不是网络永久故障下仍保证业务完成。

**追问 2：实时语音、文件传输与业务请求，对丢包、时延和顺序的要求为何不完全相同？**

文件传输通常要求内容完整、顺序正确，适合可靠传输；实时语音更在意及时播放，迟到重传的数据可能已失去价值，可以容忍少量丢包；交易请求需要可靠通信，还需处理业务超时和幂等。

实时业务也可能使用 TCP 或 QUIC，应根据网络可达性和实际协议选择。

**追问 3：选用 UDP 后仍需要可靠或有序交付时，应用还要额外承担什么？**

应用需要自行或通过成熟协议补充序号、确认、重传、去重、排序、拥塞控制和安全机制，还要处理 MTU、分片及 NAT 等问题。

- QUIC 是完整协议的例子，不是“UDP 自然具有 TCP 的所有能力”。
- 不宜为普通业务随意手写一套未经验证的可靠 UDP。

### 2. TCP 为什么需要三次握手，减少交互会留下什么问题？

三次握手用于同步双方初始序列号，并让服务端确认客户端确实收到了自己的建连响应。

- 典型过程是客户端发 SYN，服务端发 SYN+ACK，客户端再发 ACK。
- 它还帮助处理历史重复连接请求，避免仅凭一个迟到 SYN 就把旧请求当成有效新连接。

**追问 1：三次交互怎样交换并确认双方的序列号与连接状态？**

设客户端初始序列号 x，服务端为 y：SYN 携带 x；SYN+ACK 携带 y 并确认 x+1；最终 ACK 确认 y+1。

客户端收到第二个报文后知道对方收到了自己的 SYN，并获得服务端序列号；服务端收到第三个报文后才确认对方也接收了自己的 SYN。

**追问 2：省略最后一次确认时，服务端可能无法区分哪些历史或不完整请求？**

若只有两次，服务端对一个延迟到达的历史 SYN 回复后就宣布连接成立，无法确认客户端是否仍发起该连接、是否接受本次序列号。

第三次确认要求对方对当前服务端序列号作出响应，减少历史请求和不完整交互造成的错误状态。

**追问 3：三次握手中某个报文丢失时，应依据哪一方的状态分析重试，而不是统一回答“重新连接”？**

先看谁处于 SYN-SENT、SYN-RECEIVED 或 ESTABLISHED，以及哪一方有未确认的 SYN。

- SYN 和 SYN+ACK 由相关定时器重传；纯 ACK 本身不按普通数据一样独立重传，但对方重发 SYN+ACK 或后续交互可促使确认再次发送。
- 具体重试次数依实现和配置，不是统一“从头重连”。

### 3. TCP 三次握手中的某个报文丢失后，各方会如何重试或等待？

首次 SYN 丢失时，客户端等待后重传 SYN；SYN+ACK 丢失时，服务端可重传 SYN+ACK，客户端也可能因未收到响应而重传 SYN；

最后 ACK 丢失时，客户端可能已经认为建立成功，而服务端仍等待确认并重发 SYN+ACK，客户端再确认。达到超时上限才失败。

**追问 1：半连接队列与全连接队列分别保存什么？**

以常见 Linux 实现为例，半连接队列主要保存尚未完成握手的请求状态，完成队列保存已完成握手但尚未被应用 accept 的连接。

SYN cookies 等机制可能改变半连接状态保存方式；不要把两个队列都解释成“已经建立、等业务线程处理的请求”。

**追问 2：队列容量不足时，客户端与服务端可能观察到什么现象？**

队列满可能导致握手报文被忽略、重试增多，或在特定配置下重置连接。

- 客户端可能出现 connect 超时、建连成功后读写等待等不同现象；服务端可见监听溢出指标上升。
- 应结合 backlog、内核上限、accept 速度和抓包判断，不能只把 backlog 调大而忽略应用不接收连接的根因。

### 4. TCP 关闭连接为什么通常需要四次挥手，`TIME_WAIT` 与 `CLOSE_WAIT` 如何形成？

TCP 是全双工连接，双方的发送方向需要分别结束。

一方发送 FIN 表示自己不再发送，对方先确认，再在自己的数据发送完成后发 FIN，最后由最初关闭方确认，因此通常有四个报文。连接半关闭期间，另一个方向仍可传数据。

**追问 1：两个方向的数据发送为何需要分别结束，主动关闭和被动关闭分别经过什么状态？**

典型主动关闭方依次经过 FIN-WAIT-1、FIN-WAIT-2，收到对方 FIN 并确认后进入 TIME-WAIT；

- 被动关闭方收到 FIN 后进入 CLOSE-WAIT，应用关闭发送方向后进入 LAST-ACK，收到确认后关闭。
- 同时关闭等情况还有不同路径，不能只记一张不带前提的状态图。

**追问 2：为什么有时确认与关闭可以合并，而“通常四次”不能当成绝对次数？**

如果被动方收到 FIN 时已经没有数据需要继续发送，可把确认与自己的 FIN 合并；TCP 报文也可以携带数据。

四次描述的是通常的逻辑动作，不要求每次都恰好四个独立网络包。判断应依据双方发送方向和序列号是否被确认。

**追问 3：`TIME_WAIT` 与 `CLOSE_WAIT` 分别意味着哪一方还有什么后续工作？**

TIME_WAIT 通常表示最后确认方保留状态，以处理重传 FIN 和旧报文；CLOSE_WAIT 表示已收到对方 FIN，但本地应用还未关闭自己的发送方向。

大量长期 CLOSE_WAIT 往往应检查应用资源关闭，而 TIME_WAIT 较多可能只是短连接量大，不能一律当成泄漏。

### 5. TCP 的 `FIN` 与 `RST` 分别表示怎样的连接结束方式？

FIN 是有序结束发送方向，排在此前数据之后并占用序列号；RST 表示立即中止或拒绝连接，不走完整的有序关闭流程。

FIN 适合正常收尾，RST 常见于无效连接、应用中止或特定关闭配置。两者对未读或未确认数据的处理不同。

**追问 1：半关闭后还能否在另一个方向传输数据？**

可以。收到对方 FIN 意味着对方不会再发送，但本方仍可能发送剩余响应；`shutdown(SHUT_WR)` 只关闭自己的发送方向，也可以继续读取。

完整 close 还涉及描述符引用和应用使用方式，不能把半关闭等同于双方立即不能通信。

**追问 2：连接被重置与正常读到 `EOF` 应如何区分？**

正常流式读取在已读完对方此前数据且收到 FIN 后返回 EOF；RST 通常通过连接重置等错误暴露，具体时机取决于操作和缓冲状态。

业务协议还要检查消息是否完整，EOF 不能让一个只收到半个长度帧的请求被误判为成功；连接正常关闭也不证明业务事务已提交。

### 6. `TIME_WAIT` 为什么需要保留一段时间，而不是关闭后立即回收连接状态？

TIME_WAIT 主要使最后一个 ACK 丢失时仍能对重传 FIN 再次确认，并给旧连接中的延迟报文留出失效时间，减少相同四元组被复用后旧数据混入新连接的风险。

协议通常以 2MSL 描述这一等待，具体系统的实际定时实现不能简单套成所有环境同一个秒数。

**追问 1：减少 `TIME_WAIT` 与复用连接各解决什么问题？**

连接复用减少新建和关闭次数，从源头降低 TIME_WAIT 数量、握手和端口开销。

- 缩短或重用 TIME_WAIT 则是在连接关闭后改变状态回收策略，涉及正确性条件。
- 应优先修正无必要的短连接、客户端复用和连接池问题，再评估系统参数。

**追问 2：调整系统参数前需要考虑哪些正确性风险？**

要检查旧报文隔离、时间戳条件、NAT 后多客户端、四元组复用和对端行为。

- 历史参数可能已被移除或语义改变，不能复制过时的“优化脚本”。
- 先确定是端口耗尽、连接 churn 还是正常状态量，再在目标内核版本上验证吞吐和错误率。

### 7. TCP 如何结合序列号、确认与重传应对丢包和重复数据？

TCP 按字节编号，用确认号表示期望的下一字节；发送端保留未确认数据，并在超时或丢包信号出现时重传。接收端根据序号重排、去重，向应用交付连续字节。

校验和帮助发现传输损坏，但 TCP 本身不提供抗恶意篡改的密码学保护。

**追问 1：序列号、确认号和重传怎样发现并处理缺失或重复数据？**

例如接收端已收到字节 1～100、201～300，却缺少 101～200，累计确认仍指向 101；补齐缺口后才能推进连续确认。

发送端重传缺失范围，重复到达的数据依据序列位置被识别，而不是再次交给应用作为新数据。

**追问 2：仅依靠超时重传有什么延迟代价，快速重传试图利用什么额外信号？**

仅等重传超时可能要停顿一个较长 RTO，影响延迟和吞吐。

- 经典快速重传利用多个重复 ACK 推测中间报文丢失，提前重发；现代实现还可能采用更精细的丢包检测。
- 重复 ACK 是信号，不等于每次都精确证明同一种丢包原因。

**追问 3：TCP 层已经确认数据，是否等于应用已经完成业务处理？两层保证怎样区分？**

TCP ACK 通常表示对端协议栈已经接收相应字节，不表示应用已读取、校验、写数据库或完成支付。业务需要应用级响应、请求 ID、幂等和结果查询。

网络成功与事务成功是不同层次；业务响应丢失时仍会出现结果未知。

### 8. TCP 的累计确认与选择确认 SACK 有什么区别？

TCP 的累计 ACK 确认号表示“接收方下一步期望收到的字节序号”：小于该序号且位于当前接收序列中的数据已连续收到，它不是最后一个已收到字节的编号。

- 若中间有缺口，后续乱序数据不能靠单个累计确认号充分表达。
- SACK 选项额外报告已经收到的离散字节区间，帮助发送端避免不必要的重传；累计 ACK 仍负责推进连续确认边界。

**追问 1：一批数据中间丢失但后续报文已到达时，发送端怎样避免重传本来已经收到的全部数据？**

发送端根据 SACK 区间维护已到达数据的记录，只优先重传缺口，而不是从第一个缺口开始把后续全部数据再发一次。

SACK 是可协商能力，发送端仍需保留必要数据并遵守重传、窗口和拥塞控制规则；不能把 SACK 当成绕过可靠性状态机的独立协议。

### 9. TCP 的流量控制与拥塞控制分别约束什么，二者如何共同影响发送速度？

流量控制保护接收端，接收窗口 rwnd 反映还能接收多少数据；拥塞控制保护网络，拥塞窗口 cwnd 限制允许在途的数据量。

发送端同时受两者约束，典型上限由 `min(rwnd,cwnd)` 决定，再扣除已在途而未确认的数据。

**追问 1：接收方处理不及时与网络链路拥塞，分别应该约束什么窗口？**

接收应用读得慢、缓冲快满时，应缩小通告的 rwnd；链路丢包、拥塞或显式拥塞信号出现时，发送端按算法调整 cwnd。

一个针对接收主机承载能力，一个针对网络路径承载能力，不能把它们当成同一窗口的两个名称。

**追问 2：发送端的实际可发送范围怎样同时受到接收窗口与拥塞窗口限制？**

若 rwnd=64KiB、cwnd=32KiB，且已有 24KiB 在途，忽略其他限制时还可发约 8KiB。窗口随 ACK 和接收通告变化。

实际发送还受 pacing、应用可用数据、发送缓冲和协议实现限制，不能只依据链路带宽推算瞬时可发送量。

**追问 3：接收程序长期不读数据时，只扩大缓冲区能解决根因吗？**

不能。更大缓冲能吸收短暂波动，但接收程序持续处理不及会积累更多数据和更长排队延迟，最终仍填满。

应检查应用读取、线程调度和下游瓶颈，并建立背压或限流，不能用无限缓冲隐藏持续过载。

**追问 4：以经典 TCP Reno 为例，慢启动、拥塞避免、快速重传和快速恢复如何影响拥塞窗口？超时与收到重复 ACK 时的处理为什么不同？**

经典 Reno 在慢启动阶段使 cwnd 大致每 RTT 倍增，达到阈值后转为拥塞避免，约每 RTT 增长一个 MSS。

- 收到三次重复 ACK 时快速重传，并以约减半的阈值进入快速恢复；超时通常被视为更严重信号，窗口降到一个 MSS 后重新慢启动。
- 实际初始窗口、阈值和现代 CUBIC、BBR 行为不同，回答必须固定 Reno 前提。

### 10. 接收窗口变为零后，TCP 如何避免双方永久等待？

接收端通告零窗口后，发送端暂停普通新数据发送，但通过持续定时器和零窗口探测确认窗口是否重新打开，防止窗口更新报文丢失后双方永久等待。

零窗口探测与检测空闲连接存活的 keepalive 不是同一机制。

**追问 1：发送窗口与接收窗口、拥塞窗口是什么关系？**

接收窗口来自对端，拥塞窗口由本端拥塞算法维护；可发送的数据量受二者较小值限制，还要扣除未确认在途数据。

零窗口说明接收能力暂时不足，不直接证明链路拥塞，也不一定说明连接已经断开。

**追问 2：应用读取过慢时，扩大缓冲区是否总能解决问题？**

不总能。缓冲增加只能延后填满时间，不能提高持续低于发送速率的消费能力。

应定位应用是否被锁、磁盘或数据库阻塞，限制发送与排队，必要时超时或拒绝部分任务。否则会把吞吐问题变成更大的内存和尾延迟问题。

### 11. 给定连续两条应用消息，怎样在 TCP 字节流中可靠地识别消息边界？

题设：客户端依次发送两条消息，正文分别为 `hello` 与 `world`。每条消息的协议是“4 字节无符号正文长度（网络字节序）+ 正文”。

服务器的一次读取可能只得到长度字段的前 2 字节；也可能一次得到第一条完整消息和第二条消息的一部分。请描述解析器需要保存的状态，不要求实现具体 Socket 代码。

解析器需要一个可累积的接收缓冲，以及“正在读 4 字节头部”或“正在读长度为 L 的正文”的状态。

头部不足 4 字节就保留等待；够 4 字节后按大端解析无符号长度并校验上限；正文不足 L 字节继续累积，完整后交付一条消息，再循环解析剩余字节。题设两帧的长度字段都应是 `00 00 00 05`。

**追问 1：一次 `read` 只获得部分头部、部分正文或多个完整消息时，解析状态应怎样保留？**

读到前 2 字节时只记录已收头部长度；读到完整头部但正文不足时保存目标长度和已收正文；一次包含多帧时，循环消耗每个完整帧，最后保留半帧。读取结束不能清空未完成消息。

可以采用读写指针避免每次搬移整个缓冲，并定期压缩已消费空间。

**追问 2：定长、分隔符与长度字段协议各有什么边界条件，正文含分隔符时如何处理？**

定长协议简单但浪费空间或限制内容；分隔符协议需定义转义或编码，否则正文中的分隔符会被误拆；长度字段协议需规定字节序、长度是否含头部、无符号解析和最大值。

TCP 的一次 send 或 read 不能替代任何一种应用分帧规则。

**追问 3：长度字段异常或连接中途关闭时，怎样避免无限分配、丢失剩余数据或继续解析错误消息？**

先校验长度上限、整数溢出和连接总缓冲上限，再分配资源；设置读超时和最小进度约束，防止声明巨长正文后慢速发送。

- 连接中途 EOF 且仍有半帧，应按协议报告截断，不能交付部分成功消息。
- 长度非法时通常关闭连接或按明确同步规则恢复，不能随意猜测下一个头部位置。

### 12. MTU 与 MSS 分别限制什么？

MTU 限制某条链路可承载的网络层包大小；TCP MSS 表示单个 TCP 段可承载的最大数据部分，不包含 IP 和 TCP 头。

发送方通常结合对端通告的 MSS、路径 MTU 和实际头部开销决定分段大小，避免不必要的 IP 分片。

**追问 1：TCP 分段和 IP 分片有什么区别？**

TCP 分段把字节流分成可独立确认和重传的数据段；IP 分片把一个 IP 包拆为多个片，接收端需重组后交给上层。

- IPv4 路径中可能分片，IPv6 路由器不会执行同样的中途分片。
- 丢一个 IP 分片可能使整个原包无法交付，通常应通过路径 MTU 发现减少分片。

**追问 2：应用一次写入较大数据时，为什么不能据此推断一次网络发送或一次接收的大小？**

一次应用写入可能被拆成多个 TCP 段，多次写入也可能被合并；接收端读取量取决于缓冲和应用调用。

- 网卡的分段、聚合卸载还会改变本机抓包看到的大小。
- 因此不能从一次 write 的长度推断真实线上包数，更不能据此确定应用消息边界。

### 1. HTTP/1.1 请求报文与响应报文分别由哪些部分组成？

HTTP/1.1 请求由请求行、首部、空行和可选报文体组成，请求行包含方法、请求目标和版本；响应由状态行、首部、空行和可选报文体组成。

- 首部描述路由、内容、缓存和认证等信息，报文体承载业务数据。
- HTTP/2、HTTP/3 使用二进制分帧，不能直接套用相同的文本报文格式。

**追问 1：`Content-Type`、`Content-Length` 与请求体有什么关系？**

`Content-Type` 描述正文的媒体类型，必要时包括字符集或 multipart 边界；`Content-Length` 表示相关正文的字节长度，不是字符数。正文即实际传输的内容，两者不能替代正文校验。

中文 UTF-8 文本的字符数量与字节长度可能不同，必须按编码后的字节计算。

**追问 2：接收 JSON 与上传文件时该怎样理解报文？**

JSON 通常使用 `application/json`，按约定的字符编码解析；表单文件上传通常使用 `multipart/form-data; boundary=...`，每个部分带自己的头部和内容。

不能把任意二进制文件当普通字符串拆行；服务端还要限制总大小、字段数和文件类型，不能仅信任客户端声明的 MIME 类型。

### 2. `GET`、POST、PUT、DELETE 的用途及幂等性有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| GET | GET 用于获取资源，按语义应安全且幂等 |
| POST | POST 用于提交处理或创建，通常不默认幂等 |
| PUT | PUT 用于按给定表示创建或替换目标资源，语义上幂等 |
| DELETE | DELETE 删除目标资源与当前功能之间的关联，语义上幂等 |

方法语义必须由实现遵守，不是服务器自动替业务实现。

**追问 1：安全方法、幂等方法与数据是否加密，分别描述什么不同属性？**

安全表示客户端没有请求改变资源状态，幂等表示相同请求执行多次与一次的预期最终效果相同；加密表示数据传输是否受到机密性保护。

GET 不是因为“安全方法”就加密，使用 HTTPS 才提供相应传输保护；安全方法仍可能产生日志等附带效果。

**追问 2：PUT 或 DELETE 重复调用，为什么应区分业务最终状态与每次响应内容？**

第一次 DELETE 可返回成功，第二次可返回不存在，响应不同但最终资源均处于已删除状态，仍符合幂等。

- PUT 重复提交相同目标表示也应得到相同预期状态。
- 幂等不要求日志条数、访问计数或每次响应字节都相同，也不代表与其他并发修改交错后永远没有差异。

**追问 3：POST 接口遇到超时需要重试时，服务端怎样显式设计业务幂等，而不只依赖方法名称？**

由客户端为同一业务操作提供稳定的幂等键，服务端以唯一约束或事务记录绑定请求参数、处理中状态和最终结果。重复请求返回已保存结果，参数不一致则拒绝。

去重记录与业务更新应原子协调；不能先写“已成功”标记再执行可能失败的业务，也不能把每次重试都生成新键。

### 3. `Content-Length`、分块传输与连接关闭分别如何表示 HTTP/1.1 报文体边界？

HTTP/1.1 可用 Content-Length 指定正文长度，用 chunked 传输编码按块标明长度并以零长度块结束，或在允许的响应场景中以连接关闭表示结束。

- HEAD 响应、某些状态码及协议升级等另有正文规则。
- 解析必须遵守协议优先级，不能同时随意相信冲突的长度字段。

**追问 1：响应按流式逐步输出时，服务端与客户端需要怎样处理读取、刷新和中途断开？**

长度未知的流式响应可采用合法的 chunked 传输，应用逐段输出并适当刷新；客户端增量读取而非等待完整大对象。

- 代理缓冲可能延迟用户看到的数据，需要按产品配置验证。
- 中途断开要区分正常结束标记与截断，及时取消上游任务；不能把“读到 EOF”统一当成业务成功。

### 4. 如何根据接口结果选择合适的 HTTP 状态码？

状态码应表达协议层处理结果，再用稳定的业务错误码补充具体原因。

- 成功、客户端条件不满足、服务端故障应分开，避免所有情况都返回 200，也避免仅凭业务错误文本判断是否可重试。
- 状态码与响应体、重试策略和日志记录必须保持一致。

**追问 1：为创建成功、成功但无响应体、需要使用缓存、未认证、无权限、资源不存在、请求冲突与限流，分别选择常用状态码。**

创建资源常用 201，并可返回 Location；成功且无响应体用 204；条件 GET 验证未变化用 304；缺少有效认证用 401；已识别但无权限用 403；资源不存在用 404；状态冲突用 409；请求频率超限用 429。

304 不是普通业务成功而随意返回的空响应，它要与缓存验证条件配合。

**追问 2：301、302、307、308 在重定向语义和请求方法保留方面有什么区别？**

301 和 308 表示永久重定向，302 和 307 表示临时重定向。

- 301、302 在历史兼容行为中允许将某些 POST 改成 GET；307、308 要求保留原请求方法和正文。
- 需要明确保留带正文请求时应选择对应语义，并评估客户端是否允许重发及目标地址是否可信。

**追问 3：500、502、503、504 分别表达什么故障范围？为什么不能只凭状态码确定根因？**

500 表示服务器内部无法完成请求；502 表示网关收到上游无效响应；503 表示服务暂时不可用，例如过载或维护；504 表示网关等待上游超时。

它们指出错误边界，不直接给出根因：504 可能来自慢 SQL、线程池排队或网络问题，仍需结合请求 ID、代理和上游日志定位。

### 5. HTTP 长连接与短连接有什么区别？

HTTP 长连接指在一条传输连接上完成多次请求响应，短连接通常在一次交互后关闭。

- 复用可以减少握手、TLS 和端口开销，但需要正确读取报文边界、释放连接并设置空闲超时。
- 长连接不意味着一条请求永远不结束，也不意味着服务端主动推送。

**追问 1：如何判断和配置连接复用？**

HTTP/1.1 默认支持持久连接，`Connection: close` 可表达关闭意图；客户端连接池、服务端和中间代理的 keepalive 配置共同决定实际复用。

- 通过连接建立次数、四元组和日志验证，不只看某个请求头。
- HTTP/2、HTTP/3 的连接管理不能套用所有 HTTP/1.1 的 Connection 首部规则。

### 6. Cookie 与 Session 有什么区别？

Cookie 是浏览器保存并按域、路径和安全属性随请求发送的数据机制；Session 通常是服务端保存的会话状态，通过一个不透明会话 ID 与客户端关联。

- Session ID 可以放在 Cookie 中，所以二者不是互斥方案。
- Cookie 也可保存其他小型偏好，但不应直接保存可信权限或明文秘密。

**追问 1：HTTP 无状态与登录状态保持之间是什么关系？**

HTTP 本身不把多次请求自动解释为同一登录会话，应用通过凭据识别用户，并在服务端查会话或验证令牌。

登录后应轮换会话 ID，设置过期、退出和强制失效规则；Cookie 的 Secure、HttpOnly、SameSite 等属性降低特定风险，但不能替代服务端鉴权和防越权。

### 7. HTTP/1.1、HTTP/2 与 HTTP/3 如何处理连接复用和队头阻塞问题？

| 比较项 | 特点与用途 |
|---|---|
| HTTP/1.1 | HTTP/1.1 可复用 TCP 连接，但同一连接上的响应顺序限制会带来应用层队头阻塞 |
| HTTP/2 | HTTP/2 用二进制帧和流 ID 在一条 TCP 连接上交错多个逻辑流，缓解该层阻塞 |
| HTTP/3 | HTTP/3 使用 QUIC 的独立流，进一步避免一个流的数据丢失阻塞其他流的有序交付 |

**追问 1：HTTP/1.1 的连接复用与 HTTP/2 的多路复用分别在哪一层组织请求？**

HTTP/1.1 的持久连接减少建连，流水线仍要求响应按顺序返回；HTTP/2 的多路复用允许不同流的帧交错传输并独立组织响应，但字节仍经同一 TCP 连接传送。多路复用不是为每个请求建立一条新的 TCP 连接。

**追问 2：HTTP/2 仍基于同一 TCP 连接时，丢包为什么可能影响多个逻辑流？**

TCP 只交付连续有序字节，若一个段丢失，后续字节即使已到达，也可能等待缺口补齐；这些字节可能属于多个 HTTP/2 流，因此多个流一起受影响。

HTTP/2 的流 ID 无法让底层 TCP 绕过自己的有序交付约束。

**追问 3：QUIC 与 HTTP/3 改变了什么传输与流管理方式，哪些拥塞和资源限制依然存在？**

QUIC 在 UDP 上实现可靠流、丢包恢复、TLS 和连接管理，各流的数据顺序独立维护，减少跨流传输层队头阻塞。

但连接级拥塞窗口、带宽、CPU 和流控仍共享；一个流自身仍需等缺失字节，应用依赖和头部压缩依赖也可能造成等待，不能概括为“HTTP/3 完全没有阻塞”。

### 8. HTTP 强缓存与协商缓存如何决定是否发起请求及是否传输响应体？

| 机制 | 特点与边界 |
|---|---|
| 强缓存 | 强缓存依据响应的新鲜度直接复用本地或共享缓存，不必每次向源站验证 |
| 协商缓存 | 协商缓存则携带验证器询问资源是否变化，未变化返回 304 并复用原正文，变化则返回新表示 |

二者分别减少请求往返和重复正文传输，可以同时用于同一资源。

**追问 1：资源仍处于强缓存有效期时，请求是否一定发往源站？**

不一定。缓存仍新鲜且请求没有要求重新验证时，可以直接返回，源站看不到该请求。

- 请求指令、浏览器刷新方式、权限和 Vary 等条件也会影响是否复用。
- `Cache-Control: no-cache` 表示使用前需验证，不等于禁止保存；`no-store` 才是禁止相应存储的要求。

**追问 2：需要协商缓存时，客户端和服务器通过哪些验证信息决定是否发送响应体？**

客户端可发送 `If-None-Match` 携带 ETag，或 `If-Modified-Since` 携带修改时间；服务器按条件判断后返回 304 或新正文。

ETag 可表达比秒级时间戳更准确的版本，但强弱验证器和条件优先级要遵守协议，不能把任意字符串都当成内容哈希。

**追问 3：资源发生变化或需要强制刷新时，怎样控制缓存策略而不简单停用所有缓存？**

静态资源可以采用内容指纹 URL 加较长 max-age，更新时换 URL；动态数据设置较短有效期或要求验证；含个人信息的响应限制共享缓存并正确设置 Vary。

需要即时撤销时结合 CDN 刷新和版本机制，而不是把所有资源一概禁用缓存。

## 4. HTTPS 与 TLS

**本节问题**

- [1. TLS 握手如何完成身份验证和密钥协商，并保护后续业务数据？](#1-tls-握手如何完成身份验证和密钥协商并保护后续业务数据)
- [2. TLS 1.2 与 TLS 1.3 的握手过程有什么主要差异？](#2-tls-12-与-tls-13-的握手过程有什么主要差异)
- [3. 客户端如何验证服务器证书的可信性，CA、证书链与密钥分别起什么作用？](#3-客户端如何验证服务器证书的可信性ca证书链与密钥分别起什么作用)
- [4. 摘要、对称加密、非对称加密、数字签名与 HMAC 分别提供什么能力？](#4-摘要对称加密非对称加密数字签名与-hmac-分别提供什么能力)

### 1. TLS 握手如何完成身份验证和密钥协商，并保护后续业务数据？

TLS 握手协商协议与密码套件，验证对端身份，并生成后续对称加密使用的会话密钥。

- 现代常见配置使用临时密钥交换和证书签名证明身份，之后用带认证的对称加密保护应用数据。
- 它同时关注机密性、完整性和对端认证，不只是“把 HTTP 内容加密一下”。

**追问 1：客户端怎样确认对端身份，双方又怎样协商后续使用的密钥？**

客户端检查证书链、目标主机名、有效期和允许的用途，并验证服务器在握手中确实持有对应私钥。

- 双方通过例如 ECDHE 的密钥交换得到共享秘密，再结合握手上下文派生流量密钥。
- 现代 TLS 不应被一概描述为“客户端生成密钥后用服务器公钥加密发送”。

**追问 2：证书、公私钥与会话密钥承担什么不同职责？**

证书把身份与公钥绑定，并由可信链提供验证依据；公私钥用于签名、身份验证或特定密钥交换方案；会话密钥是本次通信派生出的对称密钥，用于高效保护记录。

证书本身不是秘密，也不能直接替代服务器对私钥的持有证明。

**追问 3：为什么不直接使用非对称加密处理全部业务数据，加密通道又为何不能替代应用鉴权？**

非对称运算成本高，适合建立信任和协商秘密，不适合逐块加密大量业务数据。

- TLS 证明连接对端和传输安全，却不判断某个用户是否能修改某个订单；应用仍需登录认证、权限校验、输入验证和防重放。
- TLS 终止在代理时，也要明确后续内部链路的信任边界。

### 2. TLS 1.2 与 TLS 1.3 的握手过程有什么主要差异？

不计 TCP 建连，且不考虑恢复、TLS False Start 或额外重试时，典型 TLS 1.2 完整握手需要约 2 个 RTT 后客户端才发送普通应用数据；TLS 1.3 通常缩短为约 1 个 RTT。

- TLS 1.3 简化密码套件与密钥交换选择，并在 ServerHello 之后加密大部分握手消息，包括证书消息。
- 它并非把所有交互都删掉；例如 HelloRetryRequest 会增加一次往返。
- 这里比较的是协议握手往返，不是某次请求实际完成所需时间。

**追问 1：会话恢复与 0-RTT 分别能减少什么延迟？**

会话恢复利用先前建立的状态或票据，减少重新认证和协商成本。

TLS 1.3 的 0-RTT 允许持有恢复信息的客户端在收到本次服务器响应前发送早期数据；它不表示第一次访问也能零往返完成全部身份验证，更不表示业务处理耗时为零。

**追问 2：为什么带副作用的请求需要额外考虑重放风险？**

早期数据可能被攻击者重放，多次触发非幂等业务。

- 转账、下单等不能只依赖 TLS 0-RTT 的传输保护，应禁用早期数据、只允许适当的无副作用操作，或建立严格应用防重放。
- 普通连接中的业务重试也仍需幂等设计，不能把重放问题只归于 0-RTT。

### 3. 客户端如何验证服务器证书的可信性，CA、证书链与密钥分别起什么作用？

客户端从服务器证书沿中间 CA 构造到本地信任根的链，验证各级签名、有效期、用途和目标主机名等条件，并检查适用的撤销与安全策略。服务器还要在握手中证明自己持有证书对应的私钥。

任意自签名证书只有被明确纳入信任策略后才可被接受。

**追问 1：如何区分“建立了加密通道”与“确认了对端身份”？**

未验证证书就加密，可能只是与中间人建立了安全通道，无法确认真正服务器。

- 身份校验成功意味着所连对端符合目标身份和信任策略，而不意味着服务器业务没有漏洞。
- 生产中关闭主机名校验或使用“信任所有证书”会破坏这一关键保证。

### 4. 摘要、对称加密、非对称加密、数字签名与 HMAC 分别提供什么能力？

| 比较项 | 特点与用途 |
|---|---|
| 摘要 | 摘要把内容映射为固定长度指纹，不能保密 |
| 对称加密 | 对称加密用共享密钥保护机密性，通常应配合认证 |
| 非对称机制 | 非对称机制用公私钥完成加密或签名等任务 |
| 数字签名 | 数字签名让持有公钥者验证签名者和内容 |
| HMAC | HMAC 用共享秘密验证消息完整性及持密钥者身份 |

它们不能按名称互相替换。

**追问 1：保密性、完整性、身份验证与不可否认性是哪些不同目标？为什么 Base64url 编码不等于加密？**

保密性阻止未授权读取，完整性检测修改，身份验证确认参与者，不可否认性还依赖签名密钥归属、管理和法律制度。

- HMAC 的双方都能生成合法值，不能证明一定由某一方签发。
- Base64url 只是可逆编码，不需要秘密，不能提供保密性。

**追问 2：文件校验、接口签名和 TLS 会话数据保护，应分别选择怎样的机制？**

普通文件误码检查可用摘要；要抵抗恶意替换，摘要必须经可信通道提供，或使用数字签名。

- 共享密钥的接口认证可用 HMAC-SHA-256，并对方法、路径、正文摘要等作规范化签名。
- TLS 流量通常使用 AES-GCM、ChaCha20-Poly1305 等认证加密，由成熟协议负责密钥和 nonce 管理。

**追问 3：接口签名已验证通过时，为什么还需要时间戳、随机数或请求标识防止重放？**

合法签名只说明数据由持密钥者生成且未被修改，旧的合法请求仍可能再次提交。

- 应将时间戳、nonce 或请求 ID 纳入签名，检查时间窗口并保存必要去重状态。
- 时间戳本身不阻止窗口内重复，签名规范也必须覆盖实际执行的关键参数。

## 5. DNS

**本节问题**

- [1. DNS 的递归查询、迭代查询与多级缓存如何协作完成域名解析？](#1-dns-的递归查询迭代查询与多级缓存如何协作完成域名解析)
- [2. DNS 为什么既会使用 UDP，也会使用 TCP？](#2-dns-为什么既会使用-udp也会使用-tcp)
- [3. CDN 如何缩短静态资源访问链路，缓存未命中时如何回源？](#3-cdn-如何缩短静态资源访问链路缓存未命中时如何回源)

### 1. DNS 的递归查询、迭代查询与多级缓存如何协作完成域名解析？

应用通常先检查浏览器、系统或本地缓存，再向递归解析器查询。

递归解析器若无缓存，会按根、顶级域和权威服务器的委派关系逐步查询，得到 A、AAAA 或相关记录，再返回并按 TTL 缓存。CNAME 等记录可能使解析继续到另一个名称。

**追问 1：本地缓存、递归解析服务与各级权威服务器分别参与什么步骤？**

客户端缓存直接保存近期结果；递归解析器代替客户端完成完整查询；根服务器指出顶级域服务器，顶级域进一步指出域的权威服务器，最终权威服务器提供具体记录。根服务器一般不保存所有网站的最终 IP。

**追问 2：递归查询与迭代查询怎样分工，缓存命中会怎样缩短路径？**

客户端向递归服务提出“请给最终答案”的请求；递归服务器向各级服务器发起查询并根据转介继续查找，常见为迭代过程。

若递归器已缓存最终记录或某一级委派，就能跳过相应步骤，实际请求不会每次完整经过根服务器。

**追问 3：域名记录更新后，为什么不同用户可能在不同时间看到新地址？**

用户使用的递归器和本地缓存不同，缓存剩余 TTL、负缓存、应用自身地址缓存和既有长连接也不同。权威记录更新不主动清空全世界缓存。

迁移应提前降低 TTL、保留新旧服务重叠期，并验证各层解析与实际连接去向。

### 2. DNS 为什么既会使用 UDP，也会使用 TCP？

传统 DNS 常用 UDP 获得较低交互开销，但响应可能被截断、较大结果需要 TCP，区域传送等也常用 TCP。现代还有 DoT、DoH 等传输方式。

因此 DNS 不是“永远只用 UDP”，客户端和解析器应具备相应的回退与传输支持。

**追问 1：`TTL` 与多级缓存如何影响域名切换生效时间？**

TTL 约束记录可被缓存的时间，降低新 TTL 不会让已按旧 TTL 缓存的结果立即失效。

- 多级缓存、负缓存和服务端旧连接仍可能延长观察到的切换时间。
- 应在迁移前提前调整，并监控旧地址流量，而不是修改记录后马上下线旧服务。

**追问 2：DNS 已修改但部分用户仍访问旧地址时，应该检查哪些缓存层？**

检查权威记录、递归解析器缓存、操作系统缓存、浏览器或 JVM 等运行时 DNS 缓存、应用连接池及代理解析行为。

- 可用 `dig` 对比指定权威和递归服务器，再检查实际远端 IP。
- 解析已正确但连接仍复用旧地址时，继续清 DNS 缓存不是根因修复。

### 3. CDN 如何缩短静态资源访问链路，缓存未命中时如何回源？

CDN 把可缓存资源放到靠近用户的边缘节点，请求命中时由边缘返回，降低用户到源站的延迟和源站压力；未命中时从上级缓存或源站获取并保存。

调度通常结合 DNS、网络位置和负载，不是保证地理最近节点在所有时候都最快。

**追问 1：缓存键、刷新策略和源站容量怎样影响一致性与回源压力？**

缓存键应涵盖会改变内容的域名、路径、必要查询参数和协商维度，避免错误共享或无意义碎片化。

- 更新可使用版本化 URL、过期和刷新策略；大量同时失效需要回源合并、分散过期和源站限流。
- 缓存命中率高不代表源站可以完全不预留失效后的承载能力。

**追问 2：动态请求是否一定适合缓存？**

不一定。用户专属、权限敏感、强实时或有副作用的请求往往不能被普通共享缓存直接复用；部分公共动态结果可在明确 TTL、缓存键和隐私规则后缓存。

CDN 也可做连接和网络加速，但“可以通过 CDN”不等于“可以缓存响应内容”。

## 6. WebSocket 与长连接

**本节问题**

- [1. SSE、WebSocket、长轮询与普通轮询应如何按实时通信需求选型？](#1-ssewebsocket长轮询与普通轮询应如何按实时通信需求选型)
- [2. 在 HTTP/1.1 场景中，WebSocket 如何通过握手建立持续的双向通信？](#2-在-http11-场景中websocket-如何通过握手建立持续的双向通信)
- [3. 长连接如何通过心跳、断线检测和重连维持有效通信？](#3-长连接如何通过心跳断线检测和重连维持有效通信)

### 1. SSE、WebSocket、长轮询与普通轮询应如何按实时通信需求选型？

| 比较项 | 特点与用途 |
|---|---|
| SSE | 仅服务端向浏览器持续推送事件，可优先评估 SSE |
| WebSocket | 需要高频双向通信可用 WebSocket |
| 长轮询 | 长轮询通过服务端挂起请求减少无效轮询 |
| 普通轮询 | 普通轮询实现简单但空请求较多 |

应比较方向、消息频率、恢复语义和基础设施支持，不必所有实时功能都上 WebSocket。

**追问 1：单向推送与双向交互分别更需要什么通信能力？**

SSE 基于 HTTP 事件流，适合通知和逐步输出，客户端向服务端另发普通请求；WebSocket 在同一连接上双向发送消息，适合聊天或协作。

- 长轮询适合事件不频繁、希望复用普通 HTTP 的场景。
- 浏览器 EventSource 的鉴权和请求能力也应纳入选择。

**追问 2：连接数、心跳、断线重连和中间代理限制，怎样影响方案成本？**

持续连接需要占用连接状态、心跳和代理空闲超时资源；连接数、浏览器限制、负载均衡和部署排空会影响成本。

普通轮询可无状态扩容但增加 QPS，长轮询和推送要避免一个连接长期占用一个昂贵业务线程。应通过实际峰值连接和消息速率压测。

**追问 3：连接恢复后如何继续业务进度，为什么“重新连上”不自动等于消息没有遗漏或重复？**

协议重连只恢复传输，业务要用消息 ID、序号或游标确认已收到的位置，保留可补读历史并处理重复。

SSE 的 Last-Event-ID 可以帮助续接，但服务端必须实现事件保存与回放；WebSocket 也需要应用层补偿。消息已发到连接不等于用户已经处理。

### 2. 在 HTTP/1.1 场景中，WebSocket 如何通过握手建立持续的双向通信？

HTTP/1.1 客户端发送包含 Upgrade、Connection、Sec-WebSocket-Key 等字段的握手请求，服务端验证后以 101 Switching Protocols 和相应 Accept 值确认，之后在同一连接上按 WebSocket 帧格式通信。

`wss` 还需要先建立 TLS。握手中的 Key 校验不是用户身份认证机制。

**追问 1：应用消息分帧与 TCP 字节流的关系是什么？**

WebSocket 定义数据帧、控制帧、消息分片和掩码等规则，TCP 仍只提供字节流。

接收端先解析完整帧，再根据 FIN 等信息重组消息；一个 WebSocket 帧也可能跨多个 TCP 读取。客户端帧掩码不是加密，保密需使用 TLS。

**追问 2：代理超时或连接断开后，如何恢复业务会话？**

重连后重新验证身份，携带会话或最后确认消息序号，服务端恢复订阅并补发保留范围内的消息。

- 用心跳和空闲超时发现死连接，重连采用退避和抖动。
- 不能把原连接里的未确认发送直接全部当成丢失或成功，应以应用确认和幂等规则处理。

### 3. 长连接如何通过心跳、断线检测和重连维持有效通信？

通过心跳或实际业务交互确认对端仍能通信，超过允许的连续超时后断开并释放资源，再按退避策略重连。

需要同时设置连接、读取和业务处理超时，避免长期保存失效连接；大量客户端重连时加入随机抖动，防止恢复瞬间形成洪峰。

**追问 1：应用层心跳与 TCP 保活为什么不能简单互相替代？**

TCP keepalive 主要探测空闲传输连接是否仍可达，默认时间和启用方式依系统而异；应用心跳可更快检测业务层是否响应，并携带会话信息。

TCP 可达但业务线程卡住时，keepalive 可能正常；应用心跳若仍走同一个拥堵队列，也要解释超时含义。两者可以配合，不应互相完全替代。

## 7. 网络安全

### 1. XSS、CSRF 与 SQL 注入分别利用了什么信任边界问题？

XSS 让不可信内容作为页面脚本执行，越过内容与代码边界；CSRF 利用浏览器自动携带凭据，诱导用户向可信站点发起非本人意图的操作；SQL 注入让输入被解释为 SQL 语法。

三者攻击的位置和防护方式不同，不能只靠统一“过滤特殊字符”。

**追问 1：后端应如何在输入、身份凭据和请求处理链路上防范？**

XSS 使用按输出上下文编码、可靠模板和必要的内容清洗，配合 CSP；CSRF 使用反伪造 Token、合理 SameSite 和 Origin 检查，不用 GET 改变状态；SQL 使用参数化查询，动态表名和排序字段采用白名单。

输入校验、最小权限和凭据保护仍需配合，HttpOnly 不能阻止所有 XSS 副作用，CORS 也不是通用 CSRF 防护。

### 2. SYN Flood 与 DDoS 如何消耗连接或服务资源？

SYN Flood 通过大量未完成握手占用半连接状态或处理能力；DDoS 更广，可耗尽链路带宽、连接数、TLS 计算或昂贵业务接口。

先确认瓶颈层次，再在流量到达昂贵资源之前过滤和限额，单靠应用进程往往无法处理已占满上游链路的流量。

**追问 1：针对不同瓶颈，防护应放在什么位置？**

带宽攻击需要运营商、清洗或边缘防护；握手压力可结合 SYN cookies、连接速率限制和内核队列治理；HTTP 业务攻击需 WAF、身份和接口维度限流、缓存及高成本操作配额。

保留监控、误封回退和核心业务优先级，不能用无限扩大队列代替防护。

### 3. 浏览器为什么限制跨域访问？

浏览器同源策略限制一个来源的脚本随意读取另一个来源的敏感数据。来源通常由协议、主机和端口决定。

CORS 是服务端声明哪些跨源脚本访问可以被浏览器允许的机制，不是阻止任意客户端向服务器发请求的网络防火墙。

**追问 1：CORS 预检请求由什么触发？**

不满足简单请求条件的方法、请求头或 Content-Type 等，会使浏览器先发送 OPTIONS 预检，询问目标是否允许该方法和首部。例如 JSON POST 通常需要预检。

预检结果可以按规则缓存；具体应按浏览器 Fetch/CORS 规则判断，而不是“只要跨域就一定预检”。

**追问 2：跨域配置与接口鉴权为什么不能互相替代？**

攻击者可使用非浏览器客户端直接请求，CORS 不会替服务端认证身份或校验数据权限。

某些跨站请求可以发出但响应不能被脚本读取，因此也不能把 CORS 当成完整 CSRF 防护。服务端仍需认证、授权、反伪造和输入检查。

**追问 3：携带凭据时需要注意什么？**

携带凭据时需明确允许的 Origin 和 Access-Control-Allow-Credentials，不能使用任意反射 Origin 的宽松配置。通配符 Origin 不能直接配合这类凭据读取。

还要检查 Cookie 的 SameSite、Secure 及域路径，并为动态 Origin 响应设置合适的 Vary，避免缓存串用。

### 4. 用户密码应该如何保存和验证，为什么不能只保存明文或直接计算一次 MD5？

密码应通过成熟的专用密码哈希方案保存验证结果，而不是保存明文、可轻易恢复的密文或一次快速 MD5。

验证时用保存的算法、盐和成本参数处理用户输入并比较，通常不需要也不应该能还原原始密码。专用哈希增加离线批量猜测的成本。

**追问 1：加密、普通摘要与专用密码哈希的用途有什么区别？为什么登录校验通常不需要恢复原始密码？**

加密可用密钥还原，适合确需恢复的秘密；普通摘要如 SHA-256、MD5 通常太快，不适合直接保存低熵密码；Argon2id、bcrypt 等专门增加计算或内存成本。

MD5 还存在额外安全弱点，但即使用现代快速摘要一次计算，也不等于合格密码存储。

**追问 2：盐值、计算成本以及 Argon2id、bcrypt 等密码哈希方案分别需要考虑什么安全与性能约束？**

为每个密码生成随机独立盐并与哈希一起保存，避免相同密码直接暴露相同结果和预计算复用。

- Argon2id 配置内存、迭代和并行度；bcrypt 有成本参数和输入长度限制，不能静默截断用户密码。
- 使用可靠库，在目标机器上基准测试并结合登录限流，避免参数过低易破解或过高造成认证拒绝服务。

**追问 3：升级密码哈希参数时如何兼容老用户，并在登录验证、重置流程和日志中避免泄露凭据？**

哈希记录携带算法和参数版本，老用户登录验证成功后用新参数重新哈希；长期未登录可要求重置，不能凭旧哈希直接还原密码再升级。

- 重置 Token 需随机、短期、单次使用，验证路径采用统一失败提示和速率限制。
- 日志、追踪和异常不得记录明文密码、完整 Token 或认证请求体。

### 5. 后端允许用户提交图片地址或回调 URL 时，如何防范服务端请求伪造（SSRF）？

SSRF 的核心是阻止用户把后端的网络权限变成访问内部资源的代理。

优先限制到明确的目标域名或服务白名单，只允许必要协议；验证解析后的 IP 及实际连接目标，限制重定向，并在网络出口阻断内网、环回、链路本地和敏感元数据访问。

**追问 1：为什么只检查 URL 字符串看起来像公网域名并不充分？解析后的地址、重定向与允许的协议分别需要怎样校验？**

看似公网的域名可能解析到私有地址，DNS 结果可能变化，重定向也可能把请求转向内部地址。

- 应使用标准 URL 解析器，规范化主机名，检查 IPv4、IPv6 及多地址结果，并对每一跳重新验证。
- 校验后连接时再次任意解析会留下 DNS 重绑定窗口，应确保连接使用已验证的目标并保留正确 TLS 主机名验证。

**追问 2：如何在应用校验和网络出口控制两层限制对内部服务与敏感元数据的访问？**

应用层做协议、端口、主机和地址白名单，避免携带内部凭据；网络层通过出口代理、路由和访问控制限制能到达的网段和服务，默认禁止访问云元数据等敏感地址。

两层都要生效，避免某次 URL 解析差异或新协议处理器绕过所有保护。

**追问 3：合法外部请求也可能返回超大内容或长期不结束，怎样限制超时、响应大小和并发？**

限制 DNS、建连、TLS、读取和总请求时长，限制响应正文及解压后大小、重定向次数和同时下载数，流式读取到上限即终止。

不要让单个用户占满连接池或磁盘，下载内容还要校验实际类型，并将任务与核心业务资源隔离。

## 要点回顾

- 分清各层定位和交付职责：域名、IP、端口与应用路由共同参与请求到达，单独一个地址不足以描述完整调用。
- 传输成功不等于业务成功：TCP 确认、HTTP 响应与事务提交各有边界，超时和重试必须结合业务幂等分析。
- 安全机制不能相互替代：TLS 保护传输并验证对端，登录认证、授权、输入校验和防重放仍需要应用落实。
