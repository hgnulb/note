### 1. etcd 为什么常用于配置、服务元数据与协调状态，而不是大对象业务数据？

etcd 是基于 Raft 复制的键值存储，适合保存配置版本、服务元数据、选举和锁等协调状态。

- 它提供原子事务比较、全局修订号、Watch 和 Lease，便于构造可恢复的多节点协作。
- 它不是为大文件或海量高频业务记录设计的通用数据库。

**追问 1：数据规模、更新频率和一致性需求会怎样影响选择？**

每次写入都要付出日志持久化和副本协调成本，历史版本还会持续增长。

- 数据越大、写入越频繁，对磁盘延迟、网络和配额压力越大。
- 协调数据应小而关键，大内容保存到数据库或对象存储，etcd 中只记录索引地址和版本；严格一致性的收益要与写延迟和多数派可用性要求一起评估。

### 2. etcd 的 `revision`、key version 与租约分别表示什么？

`revision` 是键值存储全局修改历史的序号，一次修改事务中的多个 key 共享同一修订号；

- key 的 `version` 表示该 key 当前生命周期内被修改的次数；
- Lease 是带存活期限的租约，可绑定多个 key，过期或撤销时删除附属 key。
- 三个概念分别描述全局历史、单 key 历史和生命周期。

**追问 1：`revision` 与某个 key 的 version 分别记录什么范围的变化？**

每次改变键值状态的事务推进全局 revision；具体 key 还拥有 create_revision、mod_revision 和 version。

- 一个事务同时改两个 key，不会为每个 key 独立生成完全不同的事务 revision。
- key 删除再创建后，version 重新开始，create_revision 则能区分新生命周期。

**追问 2：读取旧值后准备更新时，怎样利用版本信息识别期间是否已经被别人修改？**

读取值时保存 mod_revision，更新时在 Txn 中比较该 key 的 mod_revision 仍等于原值，再执行 Put。

别人期间修改后，即使把内容又改回相同文本，修订号也不同，可以识别这种变化。只比较值无法识别所有 ABA 情况。

**追问 3：`Lease` 管理的是键值生存周期还是数据版本，为什么不能把两者混为一谈？**

Lease 决定绑定 key 在何时可被自动删除，续期不等于业务数据版本更新。

- version 或 revision 增加也不会替代租约续期。
- 锁设计通常同时用事务条件保证唯一获取，用 Lease 管理存活，再用创建修订号等令牌约束旧持有者的资源访问。

### 3. etcd 与 ZooKeeper 的数据模型、监听方式与租约机制有什么区别？

etcd 使用扁平的键空间，以前缀组织逻辑目录；ZooKeeper 使用树形 ZNode。

- etcd Watch 能按 revision 订阅和在保留历史内续读；ZooKeeper Watch 更偏状态变化通知。
- etcd Lease 可绑定多个 key，ZooKeeper 临时节点则主要依附客户端会话。
- 二者都适合协调，但 API 与读取保证不能相互套用。

**追问 1：配置中心、服务注册和分布式锁分别更关心哪些行为？**

配置中心关心原子发布、版本和断线后的状态恢复；服务注册关心租约或会话失效、健康检查和客户端缓存；锁关心原子竞争、持有者身份、过期及 fencing。

选型还要比较普通读是否允许旧值、历史保留方式和团队运维能力，而不是仅凭“都用多数派”认为行为一致。

## 2. Raft 协议

**本节问题**

- [1. Raft 如何完成 `Leader` 选举、日志复制与提交？](#1-raft-如何完成-leader-选举日志复制与提交)
- [2. Raft 的 term、选举超时和日志新旧比较如何限制候选者成为 `Leader`？](#2-raft-的-term选举超时和日志新旧比较如何限制候选者成为-leader)

### 1. Raft 如何完成 `Leader` 选举、日志复制与提交？

Raft 将复制状态机拆成选举、日志复制和安全性规则。

- Follower 超时后成为 Candidate，增加 term 并请求投票；获得多数票后成为 Leader。
- Leader 为命令追加日志，复制到副本，满足提交规则后推进 commitIndex，节点再按日志顺序应用到状态机。

**追问 1：候选者怎样发起选举，任期与日志新旧检查怎样约束选票？**

每个节点在同一 term 最多投一票，并持久保存 term 和投票信息。

- 候选日志必须至少与投票者一样新：先比较最后日志的 term，再比较 index；随机化选举超时减少同时竞选。
- 网络响应快但日志落后的候选者不能因此绕过安全检查。

**追问 2：`Leader` 复制日志后，什么条件下才能提交并应用？为什么只说“到了多数副本”仍不够完整？**

Leader 通过多数派复制直接推进提交时，需要目标日志属于自己的当前 term；旧 term 的日志可随着当前 term 日志的提交被间接提交。

- 已提交不等于每个副本都已经应用，落后副本仍会追赶。
- 法定人数相交、任期、日志匹配和选举限制共同提供安全性，不能只背“复制到多数就行”。

**追问 3：`Leader` 失效后，已提交与尚未提交的日志怎样影响后继节点恢复？**

已提交日志必须出现在后继 Leader 的有效历史中，不能被覆盖。

- 尚未提交的尾部可能被保留，也可能因与新 Leader 冲突而截断。
- 客户端超时不能确定命令是否提交，业务仍需幂等标识和结果查询；Raft 的一致性不是替应用自动消除重试副作用。

### 2. Raft 的 term、选举超时和日志新旧比较如何限制候选者成为 `Leader`？

term 将领导时期分开，收到更高 term 的节点退回 Follower；随机选举超时避免节点总在同一时刻竞争。

投票者检查候选者日志的新旧程度，优先比较最后日志 term，再比较 index，确保拥有足够新历史的节点才可能得到多数支持。

**追问 1：新 `Leader` 为什么不能只根据谁的网络响应最快来选择？**

只按速度选 Leader，可能让缺少已提交日志的节点当选并覆盖正确历史。

- Raft 还要求任期合法、每任期单票和日志新旧检查。
- 性能因素可以影响部署和超时配置，但不能取代选举的安全约束。

**追问 2：未提交日志如何与新的日志序列协调？**

Leader 发送 AppendEntries 时携带前一条日志的 index 和 term。

- Follower 发现前缀不匹配则拒绝，Leader 回退或使用优化方式寻找公共前缀，再覆盖冲突的未提交尾部。
- 有效的已提交历史必须保留；不能为了“快速同步”任意删除已经提交的记录。

## 3. 一致性与高可用

**本节问题**

- [4. etcd 写入延迟升高时，为什么需要同时检查磁盘与节点间网络？](#4-etcd-写入延迟升高时为什么需要同时检查磁盘与节点间网络)

### 1. etcd 遭遇节点失效或网络分区时，如何判断哪些请求仍可处理？

写入和默认线性一致读取都依赖集群能建立有效的多数派协调。

少数节点故障后，若剩余节点仍可形成多数派，选举和追赶完成后可继续服务；不能形成多数派时，集群宁愿拒绝或等待，也不让孤立节点独立确认冲突写入。

**追问 1：哪些节点还能形成所需多数派，哪些操作依赖这一条件？**

标准 3 节点集群需 2 个成员，5 节点需 3 个。写入依赖 Leader 和多数派，线性一致读也要确认领导权及读取位置。

显式 serializable 读可能由本地状态提供较旧结果，但这不代表写入或锁判断仍然可用。

**追问 2：客户端连接到了一个存活节点，为什么仍可能无法完成请求？**

该节点可能不是 Leader、无法联系 Leader、属于少数分区，或落后到无法满足读取要求。

TCP 连接正常仅证明客户端能到达这个进程，并不能证明它与其他投票成员之间的网络和磁盘都正常。

**追问 3：判断请求失败时，怎样区分未执行、已执行但结果丢失与暂时无法确认？**

明确的参数校验失败与已经发到 Leader 后的超时不同。

- 后一种可能在服务端已提交而响应丢失，也可能尚未执行。
- 用请求对应的业务 key、事务条件和 revision 查询结果，重试必须保持幂等；不能收到 deadline exceeded 就直接执行相反的补偿操作。

### 2. etcd 的线性一致读与串行化读（serializable read）有什么区别？

线性一致读要求结果符合全局实际先后关系：已经完成的写入应在之后的读取中可见；它需要确认有效领导权和已应用位置。

etcd 的 serializable read 允许直接读取成员的本地状态，可能更快、在某些网络问题下仍有返回，但允许读到旧值。

**追问 1：两种读模式在是否允许读取较旧状态、对集群协调的要求与延迟方面有什么取舍？**

默认线性一致读取需要集群协调，通常增加网络往返并依赖多数派；serializable read 可免去这次同步协调，读取本地已经应用的状态，因此时效性较弱。

旧值可能落后多久并无单凭该模式就能给出的严格上限。

**追问 2：这里的 serializable read 与关系数据库事务的 `SERIALIZABLE` 隔离级别是同一个概念吗？**

不是。etcd API 中这个名称表示一种允许本地旧读的选项，不等于数据库最高隔离级别的可串行化事务，更不是“比线性一致更强”。

讨论时应直接说明是否允许陈旧数据、是否需要实时顺序约束，避免被名称误导。

**追问 3：读取普通配置与判断锁状态，是否能够接受相同的旧数据风险？如何根据操作用途选择读模式？**

普通展示配置若容忍短期旧值，可以使用缓存或 serializable read；决定是否获取锁、分配唯一资源或确认新领导权时，不能仅凭旧读。

获取锁应使用原子比较事务，而不是先线性读不存在、再无条件写入；两步之间仍可能竞争。

### 3. etcd 的历史压缩与存储碎片整理分别回收什么？

历史压缩 compaction 删除较早 revision 的可查询历史，限制 MVCC 历史增长；碎片整理 defragmentation 重排后端数据库文件，把已释放但尚未返还文件系统的空间收回来。

前者改变历史保留范围，后者改变物理空间布局，目的不同。

**追问 1：历史版本增长和磁盘配额耗尽会怎样影响写入？**

历史积累会扩大后端数据库，达到配额后可触发 NOSPACE 告警并限制普通写入。

- 应先检查存活数据和历史比例，制定保留窗口、压缩和碎片整理，再按操作结果解除告警。
- Watch 消费者也要能应对历史被压缩，不能只降低存储用量而不顾恢复需求。

**追问 2：为什么压缩历史不等于数据库文件立即变小？**

压缩后的页可能只是数据库内部可复用空间，文件大小仍然较大。

碎片整理才可能缩小文件，但会对正在操作的成员造成阻塞或延迟，应逐个成员执行并维持多数派可用，提前备份、观察领导切换和客户端超时，不宜同时整理所有节点。

### 4. etcd 写入延迟升高时，为什么需要同时检查磁盘与节点间网络？

etcd 写入需要 WAL 持久化、Raft 复制和状态机应用，磁盘 fsync 变慢或成员间 RTT、丢包上升都会增加提交延迟。

应联合查看 WAL fsync、后端提交时长、peer RTT、提案积压和 Leader 变化，而不是只检查客户端到节点的 ping。

**追问 1：`Leader` 频繁变化和租约超时可能怎样放大业务影响？**

选举期间写入可能暂停，客户端重试和连接切换又会增加压力；租约续期延迟可能让临时注册或锁失效，引发更多业务重建和选举。

协调服务的抖动会被上层大量客户端放大，需要限制重试并保留恢复余量。

**追问 2：怎样区分慢节点与真正不可用？**

看时间序列而非单次探测：进程是否存活、日志是否持续推进、磁盘是否高延迟、peer 心跳是否超时、提案是否最终提交。慢节点仍可能偶尔响应，却不能稳定参与法定人数。

应先排除资源争抢和网络问题，再决定迁移或替换成员，避免同时移除多个节点。

## 4. 分布式协调

**本节问题**

- [1. etcd `Watch` 如何订阅某个 key 或前缀的变更？客户端断线后怎样恢复监听？](#1-etcd-watch-如何订阅某个-key-或前缀的变更客户端断线后怎样恢复监听)
- [2. 如何用 etcd `Lease` 与 `KeepAlive` 管理临时注册信息或锁的存活？](#2-如何用-etcd-lease-与-keepalive-管理临时注册信息或锁的存活)
- [3. 如何用 etcd 的事务比较、`revision` 与 `Lease` 设计分布式锁？](#3-如何用-etcd-的事务比较revision-与-lease-设计分布式锁)

### 1. etcd `Watch` 如何订阅某个 key 或前缀的变更？客户端断线后怎样恢复监听？

先执行 Range 读取目标 key 或前缀，记录响应的全局 revision=r，再从 r+1 开始 Watch，衔接快照之后的变更。

Watch 按 revision 传递事件，客户端据此更新本地视图；它是异步通知，不保证收到事件时就与服务器当前时刻完全同步。

**追问 1：首次读取和开始 `Watch` 应怎样衔接，`revision` 在其中有什么作用？**

直接先读再“从现在开始监听”会遗漏两者之间的更新。

- 使用读取结果的 revision 作为续接点，服务器在历史仍保留时可发送间隙中的事件。
- 同一 revision 的事务事件应按完整批次处理，不能处理一半就记录该 revision 已全部完成。

**追问 2：客户端断线后，可以从哪个位置恢复，怎样处理重复事件？**

从最后完整应用的 revision+1 恢复，持久保存必要位点；若为安全而重叠重放，应按 key 的 mod_revision 或事件身份去重。

处理客户端缓冲、断线和崩溃时，位点提交不能先于实际状态更新，否则重启后会跳过未处理事件。

**追问 3：所需历史已经压缩时，为什么需要重新同步，而不是无限重试旧位点？**

服务器已不保留旧 revision 时，继续请求该位置只会反复失败。

- 应重新 Range 获取一致的当前快照和新 revision，重建本地视图，再从新位置 Watch。
- 若业务必须逐条处理所有历史事件，需另建持久事件日志，而不是依赖有限的 etcd 历史窗口。

### 2. 如何用 etcd `Lease` 与 `KeepAlive` 管理临时注册信息或锁的存活？

先 Grant 一个租约，把服务注册 key 或锁节点的 Put 绑定到该 Lease，再通过 KeepAlive 维持租约。租约过期或撤销后，附属 key 会被删除。

TTL 是服务端管理的生存约束，不是客户端暂停时自动终止业务线程的能力。

**追问 1：租约续期怎样影响附属键的存活，客户端需要处理什么失败信号？**

成功续期延长租约生存期，绑定的多个 key 共用这一生命周期。

客户端要处理续期流结束、超时、租约不存在等情况，进入无法确认或已失去身份的状态，并停止产生新的受保护操作。不能仅凭本地定时器仍在发送就认为续期已成功。

**追问 2：客户端长时间暂停、租约已经失效，但业务线程恢复运行后，会留下什么风险？**

旧客户端可能长时间 GC、暂停或断网，期间租约已过期且新客户端取得锁；旧线程恢复后仍持有之前读到的数据和连接，可能继续写数据库。

Lease 删除 key 不会自动回滚这些外部副作用，因此仅靠租约不能保证资源端始终互斥。

**追问 3：怎样让旧持有者停止受保护的写入，并与资源侧校验共同维护安全？**

业务侧在失去租约后取消任务，并在关键步骤复查状态；更强的保护是资源侧保存已接受的最大 fencing token，原子拒绝更旧令牌的写入。令牌与实际更新必须在同一资源事务中校验。单纯“写之前再读锁”仍有检查后失效的竞争窗口。

### 3. 如何用 etcd 的事务比较、`revision` 与 `Lease` 设计分布式锁？

可以先创建 Lease，然后用 Txn 比较锁 key 的 `create_revision=0`，成功分支 Put 随机持有者标识并绑定租约，失败分支返回已有状态。

- 释放时用 Txn 比较值或创建修订号仍属于自己，再删除。
- 锁成功创建时的 revision 可作为候选 fencing token，资源端必须真正执行递增校验。

**追问 1：为什么“读到锁不存在，再普通写入”不能替代原子比较更新？**

两个客户端可以同时读到不存在，再先后普通 Put，双方都以为拿到锁；原子比较事务把“仍不存在”和“写入身份”放在一个不可分割的状态转换中，只允许一个成功。

随机身份用于防误删，递增令牌用于拒绝旧持有者，二者作用不同；Lease 则负责失联后的清理。

## 要点回顾

- 多数派是继续推进的条件之一，不是完整安全规则的替代：任期、日志与提交约束仍需一起理解。
- 快照与通知要有连续边界：Range 后记录 revision，再衔接 Watch，客户端还要处理断线与历史压缩。
- 租约管理键的生命周期，不会自动撤销外部副作用：续约失败、旧持有者恢复和资源端令牌校验应共同纳入锁设计。
