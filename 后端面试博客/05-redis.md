### 1. 什么数据适合放缓存，什么数据不适合？如何选择本地缓存与 Redis？

- **适合缓存：** 适合缓存的是访问重复、读取或计算代价较高、允许一定时效差的数据，如商品展示、配置和热点查询结果。
- **不宜缓存：** 不宜无差别缓存低复用的大对象，也不应把未经持久化保障的缓存当成资金流水等权威记录。
- **本地与共享缓存：** 本地缓存省网络往返，适合单实例热点；Redis 便于多实例共享和集中管理，但增加网络依赖与一致性维护成本。

**追问 1：从读写比例、实时性、数据大小与可重复计算成本判断，哪些数据值得缓存？**

比较命中概率乘以省下的查询成本，与序列化、传输、失效和内存成本。

频繁变化且每次只读一次的数据通常收益不大；昂贵聚合结果即使规模不大也可能很值得缓存。实时性要求必须转化为可接受的最大陈旧时间。

**追问 2：单实例局部热点与多实例共享状态，为什么可能需要不同缓存位置？**

本地缓存各实例独立，读取快但更新不能自然同步；Redis 可使实例访问同一份状态，但异步复制、网络故障仍有边界。

局部只读热点可先放本地，多实例共享会话或计数则通常需要集中存储及对应可靠性设计。

**追问 3：引入缓存后新增的一致性与故障风险，是否被性能收益抵消？**

通过命中率、端到端延迟、数据库回源 QPS、内存和故障演练验证。

只有在更新失效、容量限制、回源保护都明确之后，才能判断收益是否抵消新增复杂度，而不是仅比较一次 Redis GET 与数据库 SELECT 的速度。

### 2. Redis 与 Memcached 的能力和使用场景有什么区别？

两者都能做内存键值缓存。

| 比较项 | 特点与用途 |
|---|---|
| Memcached | Memcached 更聚焦简单缓存，具有过期和淘汰能力 |
| Redis | Redis 除字符串外还提供集合、排序、脚本、持久化与复制等能力 |

选择依据应是业务操作模型、可靠性要求和团队运维成本，不是笼统断言某一个在所有场景都更快。

**追问 1：只需要简单键值缓存、需要丰富数据结构或需要持久化时，选型理由应如何变化？**

只有可丢弃的简单对象缓存时，两者都可评估，重点压测网络、对象大小和命中率。

需要原子计数、排行榜、集合运算或可恢复的数据时，Redis 的原生能力更匹配；启用持久化仍要明确刷盘、复制和故障切换的风险。

### 3. 引入缓存后，如何评估性能收益与新增的一致性、可用性风险？

先测无缓存基线，再观察命中后的响应时间、回源量和总成本，同时统计失效延迟、重建失败率和降级效果。

- 收益不能只用命中率衡量：一次低效的大对象命中也可能占满网络。
- 风险主要是旧值、缓存故障引发数据库过载，以及额外存储和运维依赖。

**追问 1：什么情况下缓存方案反而会增加系统复杂度或故障影响？**

读写都低频、命中率很低、数据必须始终实时或失效关系极其复杂时，缓存可能得不偿失。

缓存与数据库共用受限资源、没有回源限流，或者所有 key 同时到期，也可能让缓存成为故障放大器。

### 4. 设计 Redis key 与 value 时，应怎样考虑命名、序列化、字段更新和容量？

key 应包含业务、租户和稳定标识，必要时包含数据结构版本；value 按读取与更新粒度设计，避免把不相关且生命周期不同的数据塞到同一个大对象。

- 序列化格式应可演进、可观测，不存不必要的敏感字段。
- 容量评估必须包含 key 字节、对象元数据、分配器开销及副本成本。

**追问 1：同一对象保存为 JSON 字符串或 Hash，读取全部与修改部分字段的成本有什么区别？**

JSON String 适合整体读写和跨语言交换，局部更新往往需要读出、解析、修改、重写，并处理并发覆盖。

Hash 能按字段读写、自增，但字段名和结构也有开销；小 Hash 的紧凑编码可能节省空间，不能脱离实际数据测算。

**追问 2：命名空间、租户和版本怎样进入 key，避免冲突并便于清理？**

例如 `order:v2:{tenant42:1001}:detail`。

- 版本隔离兼容性变化，租户防冲突，花括号还影响 Cluster 槽位。
- 不要把整个租户或全部业务放进同一个 Hash Tag。
- 批量清理用可控扫描或索引，不依赖在线执行大范围 KEYS。

**追问 3：数据增长后怎样估算 key、value 与结构开销，防止一个方便的设计变成大 key？**

采样代表性对象，用 `MEMORY USAGE` 配合对象数量、长度分布与增长速度估算，再看整体 `INFO memory`。

限制集合成员数和返回条数，按时间、业务实体拆分；不能只算业务字段的原始字节或只测平均大小。

### 5. 为什么不宜在大型线上实例直接用 `KEYS` 扫描全部 key？`SCAN` 应如何正确迭代？

KEYS 会在一次命令中遍历键空间，大实例上可能长时间占用命令执行线程。

- SCAN 把遍历分散到多次调用，以游标推进，更适合限速的在线维护，但仍需完整遍历，不能理解为零成本索引查询。
- 使用时从游标 0 开始，持续采用服务器返回的游标，直到再次返回 0。

**追问 1：`KEYS` 与 `SCAN` 的执行方式有什么不同，为什么返回少量结果也不代表扫描没有成本？**

KEYS 一次执行完；SCAN 分批扫描。MATCH 通常是扫描后过滤，因此某批返回很少甚至为空，并不代表只检查了这些 key。

应限制调用速率、批次提示值和后续读取操作，监控延迟。

**追问 2：怎样判断一轮 `SCAN` 结束，`COUNT` 是否保证每次固定返回数量？**

结束条件是返回游标为 0，不是结果为空。COUNT 是工作量提示，不保证固定返回数量；紧凑编码的小集合扫描甚至可能一次返回全部成员。游标不是可自行加一的数组下标。

**追问 3：扫描期间数据被增删时，怎样处理重复结果，并避免把一次扫描误认为一致快照？**

完整迭代期间一直存在的元素有返回保证，但可能重复；期间新增或删除的元素是否出现不确定。处理动作应幂等，必要时去重。

需要一致快照时采用快照或业务版本机制，Cluster 还需要覆盖各主节点，而非只扫一个节点。

### 6. Redis 的 RESP 协议如何表示命令、参数与响应？

RESP 使用类型前缀和长度信息编码数据。以 RESP2 的 GET 为例，请求可表示为 `*2\r\n$3\r\nGET\r\n$3\r\nkey\r\n`：数组包含两个批量字符串。

- 响应可为字符串、整数、数组、错误或空值；RESP3 增加更丰富类型。
- 协议解析依靠类型和长度，而非把 TCP 每次读到的数据当成一条命令。

**追问 1：为什么不能简单依赖一行字符串来拆分任意二进制数据？**

二进制内容可以包含换行和零字节。批量字符串先声明字节数，再读取指定长度及结束符，所以内嵌换行不会产生歧义。

按字符数而不是编码后的字节数计算长度，同样会破坏解析。

**追问 2：客户端如何识别一条完整响应？**

解析器维护缓冲区与状态，先读类型和长度，再判断完整负载是否到齐；不足则继续读取，多出则保留给下一条响应。

数组需要递归解析成员，同时设置最大长度和嵌套限制，防止异常响应耗尽内存。

### 7. Jedis、Lettuce 与 Redisson 的定位和使用方式有什么区别？

Jedis 以直观的同步命令接口为主，传统用法通过连接池借还连接；Lettuce 基于 Netty，提供同步、异步和响应式接口，支持连接复用；Redisson 在命令之上提供锁、信号量、分布式集合等对象。

它们不是三种 Redis 服务端，也不能仅凭客户端名称推断所有使用方式都线程安全。

**追问 1：同步调用、异步调用、连接共享与高层分布式对象各适合什么需求？**

简单同步业务可选择 Jedis 池化连接；异步或响应式链路可选 Lettuce；需要成熟分布式对象封装时可评估 Redisson。

阻塞命令、事务和订阅通常需要单独考虑连接占用，不能把异步 API 等同于服务端执行并行。

**追问 2：如何检查所用客户端的线程安全边界？**

检查具体版本及连接对象的文档。传统单个 Jedis 连接不应被多线程任意共享；Lettuce 普通命令连接可复用，但事务、阻塞命令、关闭自动刷新等有连接级状态。

连接池本身线程安全不代表借出的对象可随意跨线程使用。

### 1. Redis 的 `String`、Hash、`List`、`Set` 与 ZSet 分别适合哪些业务场景？

| 比较项 | 特点与用途 |
|---|---|
| String | String 适合整体对象、计数和简单状态 |
| Hash | Hash 适合对象字段 |
| List | List 适合有序队列 |
| Set | Set 适合成员去重和集合关系 |
| ZSet | ZSet 适合带分数的排序与范围查询 |

选型先看需要的操作、返回规模和生命周期，再看接口是否方便，不能只把所有数据统一序列化为大字符串。

**追问 1：用户资料、任务队列、标签去重与排行榜，分别需要哪些操作能力？**

资料部分字段更新可用 Hash；简单任务交接可用 List，但可靠投递还需确认机制；标签去重用 Set；排行榜用 ZSet。

队列可靠性和排名规则不是选了类型就自动实现的，需要补业务语义。

**追问 2：同一个业务能使用多种类型时，怎样比较部分更新、查询方式与内存开销？**

整体 GET/SET 简单但局部更新会重写对象；Hash 节省局部传输，但一次 HGETALL 仍可能很大。Set 和 ZSet 的索引能力有额外结构成本。

应以典型对象、操作比例和峰值数据量测量，而不是只比较空结构。

### 2. Redis 的 SDS 相比传统字符串表示，为什么更适合其读写与内存管理需求？

SDS 在字符数据前记录长度和已分配空间，既能以常数时间取得长度，又能保存含零字节的二进制数据。

- 扩展时统一检查容量，避免普通 C 字符串拼接容易出现的越界。
- 它通常保留结尾零字节以兼容部分 C 函数，但数据有效范围由长度决定。

**追问 1：长度管理和空间分配方式如何影响操作成本？**

记录长度避免每次扫描到终止符；预留空间能减少连续追加时的反复分配和复制。短字符串的不同头部形式降低元数据成本。

不过预分配会占用额外内存，超大追加仍需分配和复制，不能说所有操作都是 O(1)。

### 3. Redis `String` 的 `int`、`embstr` 与 `raw` 编码分别适合什么数据？

以 Redis 7.x 为例，能够按整数表示的字符串可用 int 编码；短字符串可用 embstr，把对象头与 SDS 放在一次连续分配中；较长或需要可变存储的字符串使用 raw。

它们对客户端仍表现为 String，编码是实现选择，不是三种业务数据类型。

**追问 1：`int`、`embstr` 与 raw 分别针对什么数据表示和分配需求？**

int 避免单独保存十进制字符；embstr 减少分配次数并改善局部性；raw 分离对象与字符串存储，便于重新分配。

Redis 7.x 常见 embstr 长度阈值为 44 字节，应以具体源码和构建为准。

**追问 2：修改短字符串或把整数内容改为普通文本时，为什么可能发生编码变化？**

追加文本后可能不再能用整数表示；修改 embstr 通常先转为 raw，再进行实际修改。SET 新值也可能重新选择编码。

不能假定编码转换一定可逆，或每次缩短后都会自动回到紧凑形式。

**追问 3：怎样在所用 Redis 版本中观察真实编码，而不把历史阈值当成永远不变的规则？**

使用 `OBJECT ENCODING key`，结合 `STRLEN`、`MEMORY USAGE` 和当前版本源码验证。

长度按字节计算，中文编码后可能占多个字节；不可把字符数与编码阈值直接比较。

### 4. Redis 字典如何处理哈希冲突与扩容，为什么采用渐进式 rehash？

以 Redis 7.x 字典为例，哈希冲突通过桶内链式结构处理。

- 扩容期间同时保留旧表与新表，使用迁移位置逐步搬迁桶，避免一次性搬完全部元素。
- 渐进式 rehash 将整体工作分摊，但不消除重新分配、长冲突链或单次大命令的成本。

**追问 1：哈希冲突怎样组织，新旧哈希表为什么在扩容阶段同时存在？**

不同 key 可能落在同一桶，需要比较实际 key。

新表先建立，旧表尚未迁移完，二者共同保存当前字典；迁移完成后才释放旧表并结束 rehash 状态。

**追问 2：查找、写入与删除怎样跨新旧表工作，迁移进度在何时推进？**

新写入进入新表，查找和删除按迁移状态检查相关表。

- 普通字典访问可顺带推进迁移，服务器后台定时工作也可在预算内推进部分字典迁移。
- 具体触发、暂停与复制子进程期间的策略依版本而定。

**追问 3：渐进迁移减少的是什么停顿，能否据此认为所有相关操作的延迟都恒定？**

主要减少全量搬迁造成的一次长停顿。数组分配、迁移某个长桶、页复制和大量返回结果仍可能造成延迟，因此必须结合负载和延迟分布评价，不能宣传恒定响应时间。

### 5. Redis Hash 在字段少与字段多时，为什么可能采用不同编码？

小 Hash 采用紧凑连续编码可减少指针和分配开销；成员较多或字段、值较大时转为哈希表，以换取更好的随机字段访问能力。

以 Redis 7.x 为例，常见是 listpack 与 hashtable，两者对外命令相同，内部查询和更新成本不同。

**追问 1：字段数量、元素大小与内容变化，怎样影响编码选择与读写成本？**

紧凑结构需要顺序查找，修改可能搬动连续数据；哈希表通常字段查找更快，但每个条目元数据更多。

字段数或元素长度越过配置门槛会触发转换，不能只按字段数量判断。

**追问 2：怎样观察所用 Redis 版本中的实际编码，再比较局部字段更新与整对象读写？**

结合 `OBJECT ENCODING`、`HLEN`、字段大小分布和 `MEMORY USAGE` 观察。

业务只修改余额或状态时，HSET/HINCRBY 可避免整对象重写；主要整体读写时也要比较 JSON String 的传输和维护成本。

### 6. Redis `List` 的 `quicklist` 与 `listpack` 如何在连续存储和节点连接之间折中？

quicklist 把多个紧凑块连接成双向链表，块内连续存储多个元素，兼顾两端增删与空间利用。

Redis 7.0 的 quicklist 节点使用 listpack，后续 7.x 还可能让小 List 直接使用 listpack，因此应区分版本和实际编码，不能说所有 List 都是单一链表或单一数组。

**追问 1：它们与历史 `ziplist` 有什么关系？**

历史 quicklist 使用 ziplist 作为节点内容，后来以 listpack 替换。

listpack 的反向定位长度设计避免 ziplist 中前项长度变化引起的连锁更新问题，但连续内存增删仍可能需要移动数据。

**追问 2：元素大小和节点设置会怎样影响内存与访问成本？**

块越大，指针开销相对越小，但局部修改和解压成本可能增大；块越小，节点数和元数据增加。

大元素可采用专门节点处理，中间随机访问仍需定位，不能套用数组 O(1) 下标访问的结论。

### 7. Redis `Set` 如何支持去重与集合运算，底层编码怎样适应不同元素类型？

Set 保证成员唯一，并提供成员判断、交集、并集和差集。

- 以 Redis 7.2 为例，可根据内容和规模使用 intset、listpack 或 hashtable：小整数集合适合紧凑整数存储，小字符串集合也可紧凑保存，较大集合转为哈希结构。外部语义相同，不能把编码与业务类型混同。

**追问 1：intset、哈希表等编码如何适应元素类型与规模？**

intset 按整数保存并可随数值范围扩宽；出现不适合整数编码的成员或超过阈值时，需要转换。

紧凑结构省空间但有线性操作成本，哈希表提高一般成员访问能力但元数据更多。

**追问 2：共同关注和大集合求交时，如何评估处理时间与服务阻塞风险？请说明 Redis 版本。**

共同关注可用 SINTER，但成本与最小集合大小、集合数量和命中判断有关。大集合返回与计算会占用线程和网络。

能只问数量就不返回全部成员，必要时离线计算、分批维护关系或使用专门索引。

### 8. ZSet 在采用跳表与哈希表的编码时，如何同时支持按成员查询和按分数排序？

在跳表编码的 ZSet 中，哈希表支持按 member 快速查 score；跳表按 score、member 的组合顺序组织节点，支持排序、排名和范围访问。两份结构在同一条命令中协调更新。

跳表是内存场景下实现较直接的有序索引，并不代表它在任何场景都优于平衡树。

**追问 1：两种结构分别保存什么信息，插入、删除或修改分数时如何保持一致？**

字典维护成员到分数的查找信息；跳表维护有序节点、层级指针及跨度等信息。

新增和删除同时调整两者；改变分数可能需要重新定位节点，确保成员查询和排序结果一致。

**追问 2：与平衡搜索树相比，跳表在范围查询和实现复杂度方面有哪些取舍？**

两者平均有序操作都可做到对数级。跳表沿底层链容易连续扫描，实现和局部更新较直观，但多层指针有空间成本；平衡树靠旋转保持结构。

性能还取决于分配器、缓存局部性和具体操作，不能只比较复杂度。

**追问 3：小规模 ZSet 采用紧凑编码时，能否直接套用同一套内部结构解释？如何核对所用 Redis 版本和当前编码？**

小 ZSet 可能只有 listpack，按成员和分数访问通过紧凑序列完成，不存在另一份完整跳表。

使用 `OBJECT ENCODING` 并说明版本、成员数和长度阈值，再解释对应路径。

### 9. ZSet 的成员唯一性、score 排序与同分成员排序分别是什么规则？

同一个 ZSet 中 member 唯一，重复 ZADD 默认更新其分数；score 可以重复，升序查询先按 score，再按 member 的字节字典序排列。

同分不等于并列名次，ZRANK 返回每个成员在总顺序中的位置，通常从 0 开始。

**追问 1：排行榜分数更新、查询名次和同分排名需要怎样设计？**

更新积分可用 ZINCRBY；倒序名次可用 ZREVRANK 或相应倒序查询。

业务需要同分同名次时，要自行定义竞赛排名或密集排名，不能直接拿位置冒充。把时间拼进分数还要检查浮点精度和时间次序规则。

### 10. ZSet 插入、按成员查分数、按排名或分数取区间的时间复杂度有什么区别？

在跳表加哈希表的实现下，单个 ZADD 通常 O(log N)，ZSCORE 平均 O(1)，ZRANK 通常 O(log N)，典型排名或分数范围查询为 O(log N+M)。这里 M 是返回元素数。

紧凑编码路径和带很大 offset 的范围请求需另行分析，不能只记一个复杂度。

**追问 1：单个成员查询与区间查询分别包含哪些定位或遍历步骤？**

ZSCORE 主要做字典查找；排名需要累计跳表跨度；范围查询先定位起点，再沿有序节点取结果。修改分数既有字典操作也有有序结构维护。

**追问 2：集合共 N 个元素、返回 M 个元素时，为什么结果输出成本不能忽略？**

即使定位起点只需对数时间，序列化并传回 M 个成员至少要处理这些输出数据。

大成员还会增加字节复制与网络成本，所以元素数量和总返回字节量都要限制。

**追问 3：返回区间很大时，怎样控制批次与请求频率，避免只优化定位而忽略服务阻塞？**

设置每次最大条数和响应大小，采用稳定的分页或按分数续查并处理同分成员。

对热点排行榜可预生成前若干名并短期缓存，避免每个请求返回完整大集合。

### 11. Redis 为什么会为同一数据类型选择不同内部编码？

不同编码是在空间与访问成本之间自适应取舍：小集合用紧凑连续存储，省指针、分配和缓存未命中；大集合改用哈希、跳表等结构，提高关键查询能力。

编码转换有阈值和成本，外部同一条命令不代表内部永远走相同算法。

**追问 1：紧凑编码与通用结构各有哪些成本，`ziplist` 与 `listpack` 的变化解决了什么问题？请说明版本。**

以 Redis 7.x 为例，Hash、ZSet 等逐步使用 listpack 替代历史 ziplist。

- ziplist 的前项长度字段可能引发级联调整；listpack 让每项记录自身反向长度，降低连锁更新问题。
- 它仍是连续结构，插入移动和线性查找的代价并未消失。

### 12. Bitmap 适合怎样的签到、状态或去重场景？

Bitmap 用一个位表示某个编号对应的状态，适合编号相对稠密的签到、布尔标记和精确去重。

- SETBIT/GETBIT 操作单个位，BITCOUNT 统计置位数量，BITOP 可合并状态。
- 它本质上利用字符串的位操作，不保存每个用户的详细信息。

**追问 1：用户 ID 很稀疏时，位图为什么可能浪费大量空间？**

空间取决于最大偏移而非置位数量。只有少量用户但 ID 极大时，直接按 ID 置位会申请很长的字符串。

可建立稠密编号映射、按时间和范围分桶，或改用 Set、压缩位图等更适合稀疏数据的结构。

### 13. HyperLogLog 如何用于大规模 UV 统计？

HyperLogLog 是基数估计结构，用固定数量的寄存器汇总哈希分布，估计不同元素的数量。

- Redis 通过 PFADD、PFCOUNT、PFMERGE 使用它，经典实现的标准误差约 0.81%，稠密寄存器约 12 KiB 加少量头部。
- 它适合允许误差的 UV，而不是精确账务或获取去重名单。

**追问 1：允许近似统计 UV 与必须返回完整去重用户集合，是不是同一种需求？**

不是。HLL 不保存可枚举的原始用户集合，也不能可靠判断某个特定用户是否访问过。

需要名单、精确成员判断或删除单个用户时，应选择其他结构。

**追问 2：HyperLogLog、`Set` 与 Bitmap 在空间、误差和可支持操作上怎样取舍？**

Set 精确且可枚举，但空间随成员增长；Bitmap 对稠密编号很省空间且精确；HLL 空间小、可合并，但有统计误差且功能更窄。

选型依据是业务能否接受误差，不是单看节省多少内存。

**追问 3：多个实例或时间段的结果需要合并时，怎样确认统计口径一致？**

合并应使用相同用户标识规范与统计范围，例如跨端是否归为同一用户、匿名用户怎样标识。

不能简单相加每日 UV 得到多日 UV，应合并结构后估计并集；Cluster 多 key 合并还要满足槽位约束。

### 14. Redis GEO 如何支持附近地点查询？

Redis GEO 把经纬度编码后存入 ZSet，利用空间编码筛选候选，再进行距离过滤；GEOSEARCH 可按圆形或矩形附近范围检索。

适合附近门店等轻量查询，但不等于完整 GIS 或道路路线规划系统。

**追问 1：它与 ZSet 有什么关系？**

member 表示地点标识，score 保存空间编码，因此可复用有序结构，并能用 ZREM 删除地点。

业务不能随意用普通 ZADD 改写 score，否则会破坏地理编码含义。

**追问 2：距离计算、坐标更新和大量候选点筛选需要注意什么？**

要统一坐标系统与单位，输入合法经纬度，明确使用的是近似地球距离而非行车距离。

位置更新会重写编码；范围过大或密集区域候选太多会增加开销，应限制半径、结果量并评估分区与专业空间索引。

### 15. 使用 `List` 实现工作队列时，如何处理阻塞等待、消费者异常和消息取出后的失败？

最简单的队列是生产者 LPUSH、消费者 BRPOP，但弹出后任务从原队列消失，消费者崩溃可能造成业务丢失。

可靠一些的方案用 BLMOVE 将任务原子移到处理中列表，处理完成再确认删除，并由恢复任务重新投递超时工作。仍需业务幂等和持久化保障。

**追问 1：生产者入队、消费者等待与取出任务分别怎样实现？**

确定 FIFO 的入队与出队方向，例如 LPUSH 对应右侧弹出。

阻塞等待减少空轮询；消费连接会被阻塞，不宜与普通请求共用同一条独占连接。

**追问 2：任务已被取出但消费者尚未处理就退出，会留下什么故障窗口？**

弹出成功只代表数据移交，不代表业务提交。若没有处理中记录，进程退出后无法判断任务是否尚未执行。

业务成功但确认未完成时，又会出现重投后的重复执行。

**追问 3：怎样保留待确认状态或重新投递，什么情况下应选择专用 MQ 而不是继续增加自建逻辑？**

保存任务 ID、领取者、租期、尝试次数和完成状态，超时重新投递，执行端按业务唯一键幂等。

需要多组订阅、成熟重试死信、长期回放或可靠积压管理时，优先选择 Stream 或专用 MQ，避免自行重造完整消息系统。

### 16. Redis Pub/Sub 与 `Stream` 消费组在消息保留、确认和断线恢复方面有什么区别？

Pub/Sub 是在线广播，不为离线订阅者保留可回放历史，也没有业务 ACK。

- Stream 把消息作为数据保存，消费组通过位点和待确认列表管理交付；消息是否最终保住仍取决于持久化、复制和裁剪策略。
- 消费组提供处理协作，不自动提供业务恰好执行一次。

**追问 1：消息发布时消费者不在线，Pub/Sub 和 `Stream` 分别能否补读？**

Pub/Sub 离线期间通常直接错过消息。Stream 只要消息尚未裁剪或删除，就能按 ID 补读；新建消费组起点也决定从历史还是新消息开始，不能忽略初始化配置。

**追问 2：`Stream` 消费组如何记录处理进度与 pending 消息，确认应在什么时机完成？**

XREADGROUP 分发消息并记录 pending，业务结果可靠提交后再 XACK。

- XACK 从待确认状态中移除，并不等于删除 Stream 原消息。
- 应监控 pending 数量、最老等待时间与重投次数。

**追问 3：消费者失联后重新分配消息，怎样避免重复执行产生多次业务效果？**

通过 XCLAIM/XAUTOCLAIM 等机制回收长期未确认消息，但原消费者可能只是慢而仍在运行。

用事件 ID、唯一约束和业务事务去重，必要时加入租期或版本校验，不能把重新分配理解为自动停止旧任务。

### 17. 如何基于 ZSet 设计延迟任务队列？

用 ZSet 的 score 保存到期时间，member 保存唯一任务 ID。

- 消费者通过短 Lua 脚本选取到期任务并原子地从待执行集合移到处理中集合；后者的 score 表示领取租期截止时间。
- 任务完成后以领取令牌校验并确认，超时任务由恢复流程重投，业务处理保证幂等。

**追问 1：任务标识和到期时间分别保存在哪里？多个消费者如何原子地领取已到期任务，避免同一任务被同时取走？**

领取时需要同时完成“选到期任务、建立处理中状态、记录本轮领取令牌、移出待执行集合”。

- 下面给出 Redis 7.x 的有界批量领取脚本；三个 key 使用相同 Hash Tag，例如 `jobs:{mail}:ready`、`jobs:{mail}:running`、`jobs:{mail}:tokens`。
- 约定任务 ID 唯一，正常状态下一个任务只能处于待执行或处理中之一，ARGV[3] 是调用方为本次领取生成的不可复用随机标识。
```lua
-- KEYS：待执行 ZSet、处理中 ZSet、领取令牌 Hash
-- ARGV：当前毫秒、租期毫秒、本次领取唯一标识
local now = tonumber(ARGV[1])
local lease = tonumber(ARGV[2])
local nonce = ARGV[3]
if not now or not lease or now < 0 or lease <= 0
   or now ~= now or lease ~= lease
   or now + lease >= 9007199254740992
   or now ~= math.floor(now) or lease ~= math.floor(lease)
   or not nonce or nonce == '' then
    return redis.error_reply('invalid arguments')
end
if KEYS[1] == KEYS[2] or KEYS[1] == KEYS[3] or KEYS[2] == KEYS[3] then
    return redis.error_reply('keys must be distinct')
end
local expected = {'zset', 'zset', 'hash'}
for i = 1, 3 do
    local kind = redis.call('TYPE', KEYS[i]).ok
    if kind ~= 'none' and kind ~= expected[i] then
        return redis.error_reply('wrong key type')
    end
end
local ids = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', now, 'LIMIT', 0, 20)
local result = {}
for _, id in ipairs(ids) do
    if not redis.call('ZSCORE', KEYS[2], id)
       and redis.call('HEXISTS', KEYS[3], id) == 0 then
        local token = nonce .. ':' .. id
        redis.call('HSET', KEYS[3], id, token)
        redis.call('ZADD', KEYS[2], now + lease, id)
        redis.call('ZREM', KEYS[1], id)
        result[#result + 1] = id
        result[#result + 1] = token
    end
end
return result
```
- 返回结果按“任务 ID、领取令牌”成对排列。ACK 也必须用短脚本：仅当 Hash 中的令牌等于本次领取令牌时，才删除处理中记录和令牌；续期采用相同的令牌比较。
- 超时重投则原子地撤销旧令牌并把任务移回待执行集合。
- 类型与参数校验放在写入之前，但 Lua 运行错误不会自动回滚，故还需要一致性巡检、容量保障与恢复流程。脚本不包含外部业务执行，业务副作用仍必须幂等。

**追问 2：任务领取后进程崩溃时，怎样区分尚未处理、处理中与处理成功，并安排重试？**

待执行集合表示尚未领取，处理中集合与领取记录表示未确认，最终业务状态表示已成功。成功后 ACK；失联超过租期则重新入队。

若业务成功而 ACK 丢失，依靠业务幂等返回已有结果，而不是再产生一次副作用。

**追问 3：时钟偏差、轮询间隔与大量任务同时到期会怎样影响触发延迟？何时应改用专用消息队列或调度系统？**

使用统一时钟基准并监控回拨，轮询决定额外触发延迟，突发到期需要限速和背压。

Redis 故障、租期失效和裁剪都要有恢复方案；精度、规模或可靠性要求超出自建能力时，选择成熟延迟消息或调度平台。

### 1. Redis 的“单线程”具体指哪个执行环节？

以 Redis 7.x 常见配置为例，普通命令对数据结构的执行主要串行发生在主线程；网络 I/O 可按配置交给 I/O 线程，刷盘、异步释放等还可能由后台线程或子进程完成。因此“单线程”不是整个进程只有一条线程。

高性能来自内存访问、合适结构、事件驱动和减少锁竞争的共同作用。

**追问 1：命令执行、网络读写、持久化刷盘和大对象释放，是否都由同一条线程完成？请说明所用版本。**

命令逻辑主要在主线程；可配置 I/O 线程参与网络读写；AOF 的某些刷盘工作、大对象释放可走后台线程，RDB 和 AOF 重写涉及子进程。

不同 Redis 版本的分工会变化，应明确版本，不把各类后台工作都归为命令并行执行。

**追问 2：内存存储、数据结构与 I/O 多路复用怎样共同支撑并发请求？**

I/O 多路复用让一条事件循环管理许多连接，无需为每个连接保留一个阻塞工作线程；内存和原生数据结构降低单次处理成本。

只有就绪连接才进入相应处理路径，但最终容量仍受 CPU、网络和操作规模限制。

**追问 3：引入 I/O 线程后，为什么长时间命令或热点写入仍可能形成瓶颈？**

I/O 线程主要减少网络处理的主线程压力，不会让同一热点数据的普通命令任意并发执行。

大范围遍历、长脚本和热点写仍占用串行执行时间；应优化命令、限制结果规模、拆分热点或做业务聚合。

### 2. Redis 单条命令的原子性，为什么不能直接推导出多条命令组合也具有原子性？

- **保证范围：** 原子性只覆盖单条命令的执行边界。
- **竞争时序：** 业务先 GET、再判断、最后 SET 时，其他客户端可以在这些命令之间改变数据，导致旧值覆盖或超额扣减。
- **正确的保护边界：** 需要保护的是完整的“读取条件并据此更新”过程，而不是让其中每一步单独原子。

**追问 1：把读取、判断和写入拆成多条命令时，其他请求可能在哪些位置插入？**

例如余额 100，A 与 B 都 GET 到 100，各自扣 10 并 SET 90，最终只减少 10。每条命令都正确执行了，但组合失去了一次更新。单纯使用 Pipeline 仍存在这一问题。

**追问 2：只给每一条命令分别加原子性，能否保证整个业务条件始终成立？**

不能。即使读和写都不可拆分，判断依据也可能在写入前失效。

可用 INCRBY 等原生命令直接表达原子更新；涉及多条件时再采用 Lua 或 WATCH 条件事务。

**追问 3：需要把这些操作整体处理时，应怎样比较 Lua、事务或其他协调方式？**

Lua 适合在服务端完成读取、校验和更新；WATCH 加事务适合客户端先计算、提交时检测冲突；外部分布式锁成本更高且有租期失效问题。

跨数据库或 RPC 的操作不在 Redis 原子性范围内，必须额外设计事务或补偿。

### 3. Pipeline 如何减少批量请求开销，与 `MGET`、`MSET` 等批处理命令有什么区别？

Pipeline 允许连续发送多条命令而不逐条等待响应，减少网络往返和系统调用开销；MGET/MSET 是单条原生命令，一次表达多个 key 的操作。

Pipeline 灵活但各命令仍独立执行和报错；原生命令有自身的原子执行语义，也受 Cluster 同槽约束等限制。

**追问 1：网络往返成本怎样随批处理改变，Pipeline 与原生多 key 命令各减少了什么？**

逐条发送 N 次请求可能反复支付 RTT；流水线把等待集中起来，原生批量命令还减少命令解析等开销。

并不是带宽和序列化成本消失，跨分片由客户端拆分的批量调用也不能冒充一个服务器原子操作。

**追问 2：一批命令里存在不同业务操作时，返回结果和失败应该怎样对应？**

按发送顺序对应每条响应，逐个检查错误，不能看到整批网络读取成功就认为每条成功。

网络中断后可能部分命令已执行，应按业务幂等性和状态查询决定重试范围。

**追问 3：降低往返次数是否等于提供事务隔离，多条命令仍需要怎样分析原子性？**

不等于。Pipeline 没有提供整个批次的事务隔离或条件更新保证；需要组合原子性时使用明确的原生命令、Lua 或 WATCH/MULTI/EXEC，并单独分析失败和持久化。

### 4. Pipeline 批次过大时，为什么可能让吞吐提高但延迟和内存占用恶化？

过大 Pipeline 会让服务端积累返回结果，也会让客户端等待更长、占用更多缓冲；单个客户端集中提交还可能拖慢其他请求。

吞吐与延迟目标不同，最佳批次不是越大越好，应同时观察整体吞吐、P99 和双方内存。

**追问 1：怎样按命令大小、返回结果体积与网络往返时间选择批次？**

按总请求字节、总响应字节与可接受等待时间限制，而不只按命令条数。

先用小批次压测，逐步增加，直到吞吐收益下降或尾延迟、内存显著上升，并为大对象另设更小批次。

**追问 2：Pipeline 本身是否提供事务隔离？**

不提供。网络传输的批量化没有改变每条命令的业务边界，其他客户端的命令可能穿插；也没有整批自动回滚。

不要用一个 Pipeline 实现依赖旧值的余额扣减。

### 5. `MULTI`/`EXEC`、`WATCH` 与 Lua 分别解决什么并发控制问题？

MULTI/EXEC 将命令排队后连续执行；WATCH 在提交前检测被观察 key 是否发生变化，变化则取消整组执行；Lua 在服务端把读取、分支判断和修改写成一段不可被普通客户端命令穿插的处理。

三者都不能等同于关系数据库事务的完整 ACID。

**追问 1：命令排队后统一执行，与读取条件后发现冲突并取消，有什么区别？**

MULTI 后命令通常先排队，EXEC 才执行；此时不能像普通客户端代码一样立即拿排队 GET 的结果做后续分支。

WATCH 则先读取并计算，在 EXEC 时确认计算依据未被改变，否则客户端重新开始。

**追问 2：需要“读取—判断—修改”不可被其他命令插入时，如何选择？**

简单计数优先用 INCR 等原生命令。多步骤条件更新用短 Lua 脚本较直接；计算不能放到脚本中时可用 WATCH，接受冲突重试。

Cluster 多 key 操作需同槽，外部系统不在这段隔离范围。

**追问 3：事务或脚本的一部分执行报错，执行隔离、自动回滚和持久化保证是否能画等号？**

不能。执行阶段某条事务命令报错，其他命令可能仍执行；脚本在写入后报错也不会自动撤销已有写入。

持久性另外由 AOF、RDB、刷盘与复制决定，因此要先校验参数和类型，再尽量开始修改。

### 6. 根据给定执行顺序，分析 `WATCH` 与 `MULTI`/`EXEC` 的结果。

Redis 中 `balance` 初始为 100。客户端 A 的业务是从当前余额中扣减 20，客户端 B 的业务是增加 10。两个客户端分别使用独立连接，按以下顺序执行：

```text
1. A：WATCH balance
2. A：GET balance，取得当前余额
3. B：INCRBY balance 10
4. A：MULTI
5. A：SET balance 80
6. A：EXEC
```

题设中没有其他写入，也没有连接中断；先分析以上顺序，再讨论失败后的重试。

B 将余额从 100 增加到 110，改变了 A 正在 WATCH 的 key。

- A 的 EXEC 返回空结果表示条件事务未执行，SET 80 不会生效，最终余额仍为 110。
- A 若继续扣减，应重新 WATCH、读取 110 并计算 90，再提交，而不是认为上次业务已经成功。

**追问 1：客户端 B 修改被观察的 key 后，客户端 A 的 `EXEC` 应如何处理？**

取消整个排队事务，不执行其中的 SET。这里是 WATCH 冲突导致的取消，不是先写入 80 再回滚；B 已完成的修改不受影响。

**追问 2：A 决定重试时，为什么不能只原样重发最后一次写入，而要重新读取并计算？**

80 是基于旧余额 100 算出的结果。重发 SET 80 会抹掉 B 的增加操作；应重新观察和计算，直到成功或达到重试上限。

资金类业务还要有请求幂等键，防止结果未知后重复扣减。

**追问 3：命令入队阶段错误与 `EXEC` 执行阶段错误分别怎样影响结果？**

现代 Redis 中，语法等入队错误会使 EXEC 拒绝执行整个队列；执行期类型错误则作为对应命令的错误结果返回，其他命令仍可能成功。

客户端必须区分冲突空返回、EXECABORT 和逐命令错误，不能统一当作全部回滚。

### 7. Lua 脚本为何能保护一组 Redis 操作不被其他客户端命令插入？

Lua 脚本在 Redis 内连续执行，普通客户端命令不会在其间插入，因此可以基于刚读到的状态完成条件更新。

- 这个保证只覆盖同一 Redis 执行范围内的操作，并不包含应用进程、数据库或外部服务。
- 原子执行不等于错误时自动回滚，更不等于所有写入已持久化。

**追问 1：脚本执行期间，其他客户端命令能否插入同一段处理？这种保证覆盖哪些操作？**

同一实例普通命令不会穿插脚本中的数据操作；Cluster 中脚本访问的 key 还应按接口声明并满足同槽要求。

脚本不能把分散在多个系统的业务合并成一个本地原子事务。

**追问 2：脚本已经完成部分写入后报错，之前的写入是否必然自动撤销？**

不会自动撤销。`redis.call` 报错会终止相应脚本执行，但之前已发生的写入可能保留；`redis.pcall` 只是让脚本取得错误并处理，也不是撤销机制。应在写入前完成类型、参数和业务条件检查。

**追问 3：脚本运行过长或进程突然退出时，延迟、回滚与持久性应分别怎样判断？**

长脚本阻塞正常命令，超过时间限制不代表安全自动回滚。

已经写过数据的脚本不能任意杀掉而假装什么都没发生；进程故障后恢复范围由持久化日志决定。应保持脚本短小、有界，业务重试另做幂等控制。

### 8. 如何用 Redis 和 Lua 实现“每个用户任意连续 60 秒最多成功通过 100 次请求”的限流规则？

固定窗口不满足“任意连续 60 秒”的约束，边界前后可能瞬间放行近 200 次。

- 可用每用户一个 ZSet 保存已放行请求，score 为 Redis 服务器毫秒时间，member 为每次准入尝试的唯一 ID；在 Lua 中清除窗口外记录、计数、未满才登记。
- 以下以窗口 `(now-60000, now]` 为约定，拒绝请求不计数，返回 1 表示放行：
```lua
-- Redis 7.x；KEYS[1] 为该用户限流 key；ARGV[1] 为本次尝试唯一 ID
local key = KEYS[1]
local id = ARGV[1]
if not id or id == '' then
    return redis.error_reply('attempt id is required')
end
local clock = redis.call('TIME')
local now = tonumber(clock[1]) * 1000 + math.floor(tonumber(clock[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', key, '-inf', now - 60000)
if redis.call('ZSCORE', key, id) then
    return {0, redis.call('ZCARD', key)} -- 不把重复 ID 当作新的准入
end
local count = redis.call('ZCARD', key)
if count >= 100 then
    return {0, count}
end
redis.call('ZADD', key, now, id)
redis.call('PEXPIRE', key, 60000)
return {1, count + 1}
```
这保证正常单主、统一且不倒退的时间基准下的准入次数，不自动保证后续业务成功次数或故障切换后的严格全局配额。

**追问 1：固定窗口计数是否满足题设？选择滑动窗口时，如何表示请求时间与唯一标识，并明确窗口端点是否包含？**

用请求 ID 区分同一毫秒内的多个请求。删除 `<=now-60000` 的记录，保留左开右闭窗口；应将“成功通过”解释为限流器准入成功，而不是业务最终事务成功。若只统计业务成功，需要额外的预占与确认模型。

**追问 2：清理过期记录、检查配额与登记新请求为何应作为一个整体执行？被拒绝请求是否计入配额？**

如果计数和登记分开，两个实例都可能看到 99 并各放行一次，突破 100。脚本让这段检查更新串行完成。

拒绝不登记，否则持续拒绝可能不断延长有效统计并改变规则。

**追问 3：如何处理高流量用户、key 过期、Redis 不可用与多实例时钟差异？允许放行还是拒绝，应由什么业务要求决定？**

每个 key 最多保留约 100 个有效准入项，拒绝不追加记录，避免状态随全部请求无界增长；每次放行续 TTL，空闲后自动清理。

使用服务器时间减少客户端时钟偏差，但回拨、故障切换丢写和服务时钟跳变仍需单独处理。

- 要求严格全局配额时，协调服务不可用应拒绝，或者仅消耗故障前已安全分配、总量受约束的本地额度；随意给每个实例配置一个“较小的本地上限”仍可能合计超发。
- 普通展示类业务可按预先定义的风险策略有限放行，但必须说明此时不再保持原来的严格全局保证。

### 1. RDB、AOF 及两者结合的持久化方案，如何在恢复速度和数据丢失风险之间取舍？

| 机制 | 特点与边界 |
|---|---|
| RDB | RDB 保存某个时点的数据快照，文件通常紧凑、恢复较快，但可能丢失两次快照之间的更新 |
| AOF | AOF 保存可重建写入状态的日志，通过刷盘策略缩小故障丢失窗口，代价是写入和存储开销 |

两者结合可以兼顾恢复与备份，但最终可靠性仍依赖文件完整性、磁盘和复制机制。

**追问 1：快照与命令日志分别怎样重建数据状态？**

RDB 直接装载序列化的数据集；AOF 按基线和增量日志恢复状态。

混合 AOF 可在基线部分使用 RDB 格式，因此“AOF 一定全是可读命令文本”不成立。

**追问 2：备份大小、恢复耗时与可接受的数据损失，怎样影响 RDB 和 AOF 的选择？**

按恢复时间目标和允许数据损失选择：仅缓存可重建时可弱化持久化；恢复成本高或不能轻易丢写时使用 AOF 加可靠备份。

要计算 fork、磁盘带宽、额外内存和重写空间，不只是文件大小。

**追问 3：同时启用两者时，怎样确定实际恢复路径，并验证备份真的可用？**

同时启用时通常优先按 AOF 恢复，因为它一般覆盖更多最新写入；Redis 7.x 多文件 AOF 还需完整 manifest 与对应文件。

定期在隔离实例验证恢复后的关键数据、过期时间和应用兼容性，而不是仅检查文件存在。

### 2. `SAVE` 与 `BGSAVE` 的执行方式有什么区别？

| 比较项 | 特点与用途 |
|---|---|
| SAVE | SAVE 在服务器主执行流程中同步生成快照，会阻塞请求 |
| BGSAVE | BGSAVE fork 子进程生成快照，父进程继续处理业务 |

后台化减少了整个快照期间的长阻塞，但 fork、写时复制及磁盘竞争仍可能影响延迟。

**追问 1：为什么后台生成快照仍可能影响服务延迟？**

fork 需要建立子进程地址空间和页表；父进程后续修改共享页触发复制，子进程写文件还争用 CPU、内存带宽和磁盘。

因此大实例的后台快照也要留资源余量，不能把“后台”理解为免费。

**追问 2：快照期间是否允许处理业务写入？**

BGSAVE 期间父进程可以继续写，快照主要对应 fork 时的逻辑内存视图，之后变更不自动进入这份快照。SAVE 执行期间正常命令处理则被阻塞。需要保存快照后写入，应依靠后续快照或 AOF。

### 3. RDB 快照生成过程中的 fork 与写时复制，会如何影响内存和请求延迟？

fork 后父子进程的虚拟地址空间分别独立，初始物理页可共享；父进程修改某页时通过写时复制获得自己的页，子进程继续观察快照视图。复制以页为单位，不是只复制被修改的一个字段。写入覆盖页越多，额外内存可能越接近数据集规模。

**追问 1：fork 之后父子进程如何共享内存页，持续写入为何可能增加额外内存？**

共享的是物理页映射，而不是父子对同一可变逻辑对象无隔离地读写。父进程写热页触发 COW，子进程仍写出原快照。

大量随机更新可能触碰很多页，即使业务增量字节不大也造成显著内存增长。

**追问 2：后台生成快照为什么仍可能影响主进程延迟？**

fork 本身可能暂停主流程，页表复制有成本；随后 COW 缺页、内存带宽和子进程磁盘 I/O 都会竞争资源。

透明大页等系统设置也可能影响 COW 开销，需要结合运行环境评估。

**追问 3：怎样根据写入量、内存余量和快照时间判断风险，而不只检查是否开启 `BGSAVE`？**

监控 `latest_fork_usec`、RDB 子进程状态、COW 指标、RSS、写入速率和磁盘延迟。

为最坏写入覆盖和副本缓冲预留内存，错开重写与高峰；不能只看 Redis 配置的 maxmemory 是否小于机器总内存。

### 4. AOF 的命令追加与刷盘策略如何影响写入延迟和故障后的数据风险？

命令执行成功、追加到 AOF 缓冲、写入操作系统缓存以及 fsync 到持久化存储是不同阶段。

- `appendfsync always` 更强调每次写入的持久化，`everysec` 通常约每秒刷盘，`no` 交给操作系统安排。
- 吞吐提高往往伴随更大的故障丢失窗口，周期也不是绝对实时保证。

**追问 1：如何区分命令执行完成、日志进入缓冲区与真正刷入持久化存储？**

应用缓冲随进程丢失；操作系统页缓存通常能承受 Redis 单进程退出，但机器断电仍可能丢；fsync 的意义是请求存储层落实持久化，实际还受设备与系统保证约束。客户端确认不能一概当作所有阶段完成。

**追问 2：不同刷盘策略分别适合哪些业务要求？**

可重建缓存可接受较宽窗口；重要状态可用 always 或明确评估 everysec 的风险，配合备份及业务恢复。

everysec 通常描述约一秒数据风险，但磁盘阻塞、特殊重写配置和调度可能扩大，不能许诺绝对只丢一秒。

### 5. AOF 重写为何不能简单理解为复制旧日志或逐行去重？

AOF 重写根据当前数据集生成恢复该状态所需的精简基线，例如多次修改同一值不必保留全部历史。

以 Redis 7.x 为例，采用多文件 AOF：重写生成新的 base 文件，父进程把后续写入记录到增量文件，并通过 manifest 管理有效文件集合。旧版本的重写缓冲流程不能直接套到新版本。

**追问 1：AOF 重写为什么依据当前数据状态生成恢复所需的内容，而不是简单复制旧日志？**

目的在于恢复当前状态，而不是保留审计历史；过期或被删除的数据无需继续重放旧操作。

字符串、集合等会转换成足以重建当前对象的表示，因此不是简单按文本去重。

**追问 2：重写期间仍有业务写入时，如何衔接重写基线与新增变更？请说明讨论的 Redis 版本。**

新基线由子进程生成，重写开始后的增量写入继续保留；完成后以受控的 manifest 切换使新基线和有效增量成为恢复集合。

旧的单文件版本会有不同的缓冲与追加安排，回答需区分。

**追问 3：重写失败、文件切换中断或磁盘不足时，如何判断哪些文件仍可用于恢复？**

失败时不能随意删旧基线或增量文件，应先检查 manifest、文件完成状态和错误日志。

保存全部现场，在隔离副本上做校验与修复，确定能恢复的最后一致边界；磁盘不足时还要先止住持续写入压力。

### 6. 同时开启 RDB 与 AOF 后，应如何设计重启恢复与备份验证流程？

先确认实际使用的 Redis 版本、AOF 配置和恢复文件集合，保留原文件副本，再在隔离实例加载并校验。

- Redis 7.x 备份多文件 AOF 要让 manifest 与 base、incremental 文件保持对应；单拷贝一个看起来最大的 AOF 可能不完整。
- 恢复验证包括关键数量、业务抽样、TTL 和服务读取。

**追问 1：AOF 尾部不完整、备份文件损坏或文件版本不兼容时，如何评估恢复范围而不直接覆盖现场？**

尾部不完整可能按配置截断到可解析边界，但这意味着放弃相应尾部写入；中间损坏和版本不兼容不能用同一办法草率处理。

先用匹配版本的检查工具在副本分析，必要时从已验证备份恢复并补业务增量，不直接覆盖唯一现场。

### 1. Redis 的过期删除与内存淘汰为什么是两套不同机制？

| 比较项 | 特点与用途 |
|---|---|
| 过期删除 | 过期删除针对 TTL 已到的数据，解决生命周期 |
| 内存淘汰 | 内存淘汰针对达到 maxmemory 后的容量压力，按策略选择可牺牲对象 |

Redis 用访问时检查与周期性主动过期相结合回收过期 key，而淘汰可能删除尚未到期甚至没有 TTL 的缓存，二者不能互相替代。

**追问 1：`TTL` 到期与达到 `maxmemory` 是哪两种不同触发条件？**

TTL 是每个 key 的截止时间；maxmemory 是实例管理内存的容量约束。

内存充足也会删除过期数据，未过期也可能因容量压力被淘汰，业务不能把缓存存在时间视为承诺。

**追问 2：惰性删除、定期删除与内存淘汰分别决定什么，能否相互替代？**

惰性删除在访问时判断过期；定期删除按预算主动抽查和清理；淘汰在需要控制内存时挑选候选。

只有 TTL 不足以保证峰值容量，只有淘汰也不能表达“验证码五分钟失效”。

**追问 3：一个 key 没有设置 `TTL`，是否仍可能被淘汰？这取决于什么策略？**

可能。allkeys 类策略可从所有 key 选择，volatile 类仅从带过期时间的 key 选择；noeviction 不靠删除普通 key 腾空间。

不能丢的协调状态不应与可任意淘汰的缓存无差别混放。

### 2. key 的 `TTL` 到期，是否意味着它已经立即从内存中删除？

TTL 到期意味着逻辑上应视为过期，不等于物理内存恰在那一毫秒立即释放。

- 访问可能触发删除，后台主动过期按预算推进，事件通知通常在实际删除时产生。
- 副本还受复制与本地读取规则影响，不能把几个观察时点当成同一个瞬间。

**追问 1：直接读取、后台扫描、过期通知与从节点观察到的状态，为什么可能不在同一时刻变化？**

客户端读取时可得到不存在，而后台还未扫描过所有其他过期 key；通知产生和网络送达也有延迟。

副本一般由主节点传播过期删除，并按版本规则避免暴露过期数据，但复制进度仍可能滞后。

**追问 2：能否把过期事件通知直接用作保证不丢失、准时触发的订单关闭机制？客户端离线或通知延迟时应怎样补偿？**

不能。键空间过期通知依赖 Pub/Sub，没有离线补发保障，也不保证准点触发。

订单关闭应把到期时间保存在可靠业务存储，用延迟任务配合周期性扫描补偿，并以状态条件更新保证重复执行安全。

### 3. 如何根据访问模式选择 Redis 内存淘汰策略？

先区分哪些数据允许淘汰，再按访问模式选策略。常见 Redis 7.x 策略包括 noeviction、allkeys/volatile 的 LRU、LFU、random，以及 volatile-ttl。

通用热点缓存可评估 LRU 或 LFU；协调状态必须另行保障，不应为了提高命中率而接受无差别丢失。

**追问 1：LRU 与 LFU 的判断依据有何不同，近似实现带来了哪些取舍？**

LRU 关注最近访问时间，LFU 关注带衰减的访问频率。

- Redis 采用采样和近似信息控制维护成本，不维护理论上完美的全局 LRU/LFU 排序。
- 近似会选错部分候选，但通常以较低 CPU、元数据成本获得可接受效果。

### 4. Redis 达到 `maxmemory` 后，不同淘汰策略下的新写入会怎样处理？

超过内存限制后，Redis 会按所选策略尝试淘汰；采用 `noeviction`，或其他策略没有足够候选可释放时，受 OOM 准入限制的命令会被拒绝。

- 这里按命令语义和标记判断，不是执行完才按实际净增内存逐条放行：即使某次 `SET` 打算写入更短的值，也不能据此保证会被允许。
- 读取和 `DEL`、`UNLINK` 等释放数据的操作通常仍可执行，所以不能说“内存满后全部命令失效”。

**追问 1：只从有 `TTL` 的 key 中选择，和从所有 key 中选择，会形成怎样的可淘汰集合？**

volatile 类候选仅包含有过期时间的 key，allkeys 包含全部 key。

前者可避免普通无 TTL key 被容量淘汰，但不能据此把 Redis 当作无上限持久存储，候选不足仍会写入失败。

**追问 2：所有 key 都没有 `TTL` 时，`volatile` 类策略能否完成预期淘汰？**

没有候选，无法靠这类策略腾出空间，会出现类似 noeviction 的写入失败。

应检查策略是否与数据的 TTL 设计一致，而不是只调高 maxmemory 掩盖问题。

**追问 3：`noeviction` 下写入失败后，应用怎样区分缓存容量故障和业务数据不存在？**

OOM 是缓存容量异常，不是 key 不存在，更不是业务库存为零。

应用应记录错误并按降级策略处理，对缓存写入失败与业务事务失败分别判断，避免误删权威数据或无限回源。

### 5. 更新一个已设置 `TTL` 的 key 后，过期时间是否一定保留？

不一定。以 Redis 7.x 为例，普通 SET 覆盖值通常会移除旧 TTL，除非显式使用 KEEPTTL 或新的过期参数；HSET、INCR、列表内部修改等通常保留 key 原来的过期时间。

必须按具体命令语义判断，不能把“更新”当成统一行为。

**追问 1：覆盖写入 `String` 与修改集合中的部分内容，为什么需要分别检查 `TTL` 语义？**

SET 创建或覆盖整个字符串对象，默认重置原有过期状态；集合字段更新是在既有 key 上修改内容，通常不改变生命周期。

需要刷新会话有效期时应显式表达，不要依赖偶然副作用。

**追问 2：计数自增后再单独设置过期时间，两步之间退出会留下什么状态？**

INCR 成功、EXPIRE 之前退出，会留下没有期限的计数器；反复 EXPIRE 又可能把固定窗口变成滚动续期。应明确只在首次创建时设置，还是每次更新都续期。

**追问 3：怎样把需要共同成功的操作组织起来，兼顾原子性与既有 `TTL` 的业务规则？**

用 Lua 统一执行自增和首次设置 TTL，或使用支持的单条原子命令。

脚本中先定义返回值、TTL 缺失时的补救与重试语义；跨服务的同一业务重试仍需幂等标识，不能只靠计数原子性。

### 6. Redis 中“大 key”和“热 key”分别描述什么问题？

大 key 指单个键对应的元素数量或数据体积过大；热 key 指访问频率过高。

大 key 主要增加操作耗时、网络和释放成本，热 key 主要集中吞吐压力，两者可以同时出现，也可以独立出现。诊断必须看大小和访问分布两个维度。

**追问 1：同一个 key 是否可能只热不大或只大不热？**

一个几十字节的库存计数可以极热；一个几乎不访问的历史大列表可以很大但不热。

只按内存扫描找不到所有热点，只按访问次数也不能发现全部大对象。

**追问 2：拆分结构、读副本与本地缓存分别适合处理哪类压力？**

按业务或时间拆结构适合减少大对象单次操作；读副本和本地缓存主要分担可接受旧值的读热点；写热点需分片计数、合并更新或重新设计串行边界。把读热点复制多份不能自动解决强一致写热点。

### 7. Redis `used_memory` 与进程实际驻留内存为何可能存在明显差距？

used_memory 主要反映 Redis 通过分配器统计的分配量，RSS 是操作系统看到的进程驻留物理内存，两者统计边界不同。

分配器保留空闲页、内部外部碎片、代码和栈等可使 RSS 高于逻辑使用量；交换或其他内存行为也可能使关系变化。不能直接把差值全部叫作业务泄漏。

**追问 1：`used_memory` 与操作系统观察到的 RSS 分别采用什么统计口径？哪些分配已计入 Redis 自身统计，哪些不应简单重复相加？**

数据、客户端和复制缓冲等 Redis 分配通常已经计入自身统计，不能在 used_memory 上再无条件全部相加。

RSS 还含其他驻留映射；持久化子进程应从进程树或容器总量另看，避免重复统计共享页。

**追问 2：内存分配器碎片、客户端或复制缓冲区，以及持久化期间的写时复制，分别可能造成什么增长？**

大量不同大小对象增删造成碎片；慢客户端和慢副本积累输出缓冲；fork 后更新共享页产生额外 COW。

分别观察 allocator、客户端缓冲、复制和 COW 指标，单一碎片比值不足以定位原因。

**追问 3：删除数据后 RSS 未下降时，应如何判断仍存活的数据、可复用内存与系统实际压力？**

比较 `used_memory`、RSS、`MEMORY STATS`、对象数量与大小趋势；若逻辑分配已降而 RSS 稳定，可能是分配器保留可复用页。

还要看 available、容器限制和交换压力，不能因为 RSS 未立即下降就重复清空数据。

### 8. `DEL` 与 `UNLINK` 在删除大对象时有什么区别？

DEL 移除 key 并可能在主线程同步释放复杂对象；UNLINK 先从键空间解除关联，再将适合异步处理的内存释放交给后台，降低大对象释放造成的阻塞。

UNLINK 不是瞬间释放全部内存，也不消除后台 CPU 和内存压力。

**追问 1：`DEL` 与 `UNLINK` 在移除 key 和释放底层对象时分别做什么？**

两者对后续 key 查询都表现为已删除，但底层回收时机不同。

简单或很小对象可能直接释放，复杂对象才体现异步回收优势；调用成功不意味着 RSS 立即减少。

**追问 2：集合很大时，逐批删除成员与异步释放整个对象各有哪些开销？**

批量删成员能限制每次主线程工作，但次数多、会产生额外命令与复制日志；UNLINK 整体逻辑删除简单，却可能积累后台释放任务。

需要保留部分数据时分批清理，否则优先评估异步整键删除。

**追问 3：清理过程中怎样观察延迟与资源，避免用一次危险清理制造新的故障？**

限速操作，观察 P99、主线程 CPU、lazyfree 待处理数量、复制延迟和可用内存。

不要同时发出大量全量读取、同步删除或大脚本；清理前先确认 key 范围和业务可恢复性。

### 1. Redis 主从复制如何完成初始同步，并在连接中断后恢复同步？

- **首次同步：** 首次同步通常是副本发起 PSYNC，主节点生成并发送快照，同时保留快照生成和传输期间的增量写入；副本加载基线后继续应用增量。
- **重连恢复：** 断线重连时，如果复制历史和偏移仍匹配且所需增量尚在积压缓冲区，可部分重同步，否则重新全量同步。
- **确认边界：** 复制默认异步，不等于客户端写入确认时所有副本都已更新。

**追问 1：新副本首次加入时，已有数据与同步期间的新写入怎样衔接？**

主节点可把 RDB 写到磁盘再发送，或按配置走无盘传输。

副本先取得一致基线，再接上同一复制流的后续变更，不能在快照过程中随意遗漏新写入。

**追问 2：短暂断连后，怎样判断能够增量补齐还是需要重新全量同步？**

核对复制 ID、请求 offset 和主节点仍保留的历史区间；主从切换后还涉及可接受的旧复制 ID 范围。

只看断线时间很短并不够，高写入速率也可能迅速覆盖缓冲区。

**追问 3：同步范围变化后，网络、磁盘和内存成本分别可能怎样上升？**

全量同步涉及快照、网络传输、加载与增量追赶，可能显著消耗 CPU、内存、带宽和磁盘。

反复全量同步会形成“越慢越掉线、越掉线越忙”的循环，应留资源余量并限制同时接入数量。

### 2. Redis 部分重同步如何利用复制 ID、`offset` 与复制积压缓冲区？

复制 ID 标识一段复制历史，offset 标识该历史中的字节进度；复制积压缓冲区保留近期复制流。

- 副本重连时带上已知 ID 和进度，主节点只有能接上同一历史且仍保有缺失区间，才能只补增量。
- offset 相同但历史 ID 不同，不能直接当作数据相同。

**追问 1：复制 ID 与 `offset` 分别用于确认什么，积压缓冲保存哪一段历史？**

ID 区分历史，offset 区分位置，环形积压缓冲区保存有限窗口。

主节点切换后可能保留第二复制 ID 及其有效偏移边界，用于支持合理的部分重同步，不能忽略任期或历史变化。

**追问 2：断连时间和写入速率怎样影响可补齐范围？**

所需容量大致与峰值复制字节速率乘可容忍断连时间相关，还需留波动余量。

应使用实际复制流大小估算，不能直接拿业务请求条数当字节数。

**追问 3：超出缓冲区后退回全量同步，为什么可能让本已紧张的主节点更忙？**

全量同步增加 fork、COW、RDB 传输和加载，主节点还要继续服务写入并保存追赶数据。

若资源不足导致再次断连，扩大缓冲只是一个方面，还要修复带宽、慢副本或过载根因。

### 3. 新增多个副本或从节点频繁重连，为什么可能放大主节点的内存、网络和磁盘压力？

多个副本同时加入或反复重连，可能触发全量数据分发、增量积压和快照相关工作，放大网络与内存压力。

应区分“正常增量传输慢”和“复制历史接不上反复重做全量”，再决定限速、分批接入、调整缓冲或改善机器资源。

**追问 1：如何区分复制链路带宽不足与反复全量同步造成的压力，并安排扩容顺序？**

观察 full/partial sync 次数、副本 offset 差距、复制连接状态、输出缓冲、网络吞吐及快照指标。

若全量次数不断增长，先找断连原因并扩大合理历史窗口；新增副本分批进行，在追平后再继续，避免同时占满主节点资源。

### 4. 普通主从、Sentinel 与 Redis Cluster 分别解决什么问题？

普通主从负责数据复制，默认不独立完成成熟的自动故障转移；Sentinel 监控一组主从并协调故障切换、通知客户端；Cluster 则通过哈希槽把数据分散到多个主节点，并结合副本实现分片级故障恢复。

高可用、读扩展与容量分片是三个不同目标。

**追问 1：复制数据、自动切换主节点与拆分数据容量，分别由哪种机制负责？**

复制由主从机制负责；自动换主可由 Sentinel 或 Cluster 管理；多个主节点分摊键空间由 Cluster 等分片方案负责。它们不能只按“有几台机器”区分。

**追问 2：只增加副本，是否就会自动得到主节点故障切换或写入分片？**

不会。副本通常保存同一份数据，没有把主节点写入分散到多个独立分片；增加副本也需要故障发现、授权、客户端重连等流程才能完成自动切换。

**追问 3：业务需要扩大容量、提升读吞吐或自动恢复故障时，应怎样确定部署方案？**

单数据集容量足够但要自动恢复，可选主从加 Sentinel；需要扩大写入与容量，可选 Cluster 并评估多 key 限制；副本读只适合能接受复制延迟的业务，写后读或锁操作不可盲目走副本。

### 5. 哨兵的主观下线、客观下线与故障转移授权有什么区别？

主观下线是某个 Sentinel 根据自己的连接与心跳观察认定主节点异常；

客观下线需要达到配置 quorum 的共同判断；真正执行故障转移，还需要某个 Sentinel 获得选举授权，通常要求已知 Sentinel 的多数派参与。发现故障与获得改写拓扑的权限不是同一步。

**追问 1：主观下线由哪个观察者作出，客观下线又需要什么共同判断？**

每个 Sentinel 独立作出主观判断，再向其他 Sentinel 查询对该主节点的看法。

主节点达到 quorum 后可被认定客观下线，但这只是进入后续故障转移流程的条件。

**追问 2：`quorum` 与授权执行故障转移所需的多数派，为什么不能当成同一个条件？**

quorum 用于故障判断，可以配置；多数派用于避免少数分区各自授权切主。

例如 5 个 Sentinel 配 quorum=2，两台能判故障，但仍不足以获得 3 票授权，因此不应直接切主。

**追问 3：只有一部分哨兵或节点相互连通时，怎样分析能否切换，而不是只看主节点 ping 是否失败？**

分别画出 Sentinel 之间和它们与 Redis 节点之间的连通关系，检查是否有 quorum、是否能取得多数票、是否存在合格副本。

仅某一个探测失败不能证明主节点对所有客户端都不可用，也不能保证切换安全。

### 6. 发生主节点故障后，由哪个哨兵执行切换，又如何从副本中选择新主节点？

先在 Sentinel 之间选出本次故障转移的执行者，再由执行者从合格副本中选择新主。

- 通常先排除长时间失联等不适合节点，再按副本优先级、复制 offset 和确定性标识等规则排序。
- 完成提升后修改其他副本的复制目标，并让客户端发现新地址。

**追问 1：决定由哪个哨兵执行切换，与决定哪个副本升主，是哪两个不同选择过程？**

前者选择“谁来组织切换”，涉及 Sentinel 投票；后者选择“哪份数据成为主数据”，涉及 Redis 副本健康和复制进度。不能把两类节点或两套优先级混在一起。

**追问 2：副本优先级、复制进度和断连情况怎样影响候选资格？**

优先级数值越小通常越优先，优先级为 0 表示不参与提升；在合格候选中再比较复制进度等。

长时间断开主节点的副本可能被排除，不能只挑响应最快或机器性能最高的节点。

**追问 3：新主选出后，其他副本、旧主和客户端怎样重新建立正确连接？**

新主接收写入，其他副本被指向它，旧主恢复后应降为新主的副本。

客户端通过 Sentinel 查询或监听变化并重建连接，仍需处理过期地址、执行结果未知和重试幂等，切换不是无感且零风险的瞬时操作。

### 7. Redis Cluster 如何通过哈希槽分配数据，并在扩容迁移期间处理请求？

Redis Cluster 将键空间划成 16384 个哈希槽，通常以 CRC16(key) 对槽数取模定位，再由槽表找到主节点。

- 扩容迁移的是槽内的 key；迁移过程中源节点和目标节点标记状态，客户端按 MOVED、ASK 等响应调整访问。
- 它不是一致性哈希环，也不是把一个大 key 自动拆到多台。

**追问 1：多 key 命令和 Lua 脚本受到哪些分片约束？**

需要整体执行的多 key 命令、事务和脚本通常要求相关 key 位于同一槽。

可用 Hash Tag 放置关联键，但过度共槽会形成热点；迁移期间跨节点分布的相关 key 还可能暂时无法整体执行，需要有限重试或调度窗口。

### 8. Redis Cluster 的 `MOVED` 与 `ASK` 重定向有什么区别？

MOVED 表示该槽应由另一个节点负责，客户端应更新槽路由并重发；ASK 通常表示槽迁移期间这一次请求应去目标节点，客户端先发 ASKING 再执行原命令，但不把整个槽永久改路由。二者表达的是稳定归属与临时处理位置的区别。

**追问 1：永久路由变化与槽迁移中的临时访问，分别为什么需要不同重定向？**

迁移尚未完成时，同一槽部分 key 可能已经移动、部分仍在源节点，不能因为一个 key 被转走就把所有请求永久指向目标；这正是 ASK 的用途。迁移完成后再以正式槽归属返回 MOVED。

**追问 2：客户端何时更新槽路由缓存，何时只把当前请求发往临时目标？**

收到 MOVED 可更新对应槽或刷新完整拓扑；收到 ASK 只对当前操作执行临时重定向，并在目标连接发送 ASKING。

客户端库应处理这一流程，业务不宜手写无上限跳转循环。

**追问 3：重定向伴随超时重试时，怎样避免非幂等写入被重复执行？**

明确的重定向通常意味着原节点要求改路由，但网络超时不同，原写入可能已经执行。

对 INCR、扣减等操作需幂等标识或查询最终状态，限制重试次数，不能把所有异常统一原样重放。

### 9. Redis Cluster 为什么要求某些多 key 操作落在同一哈希槽？

单节点可以串行执行一段涉及多个 key 的逻辑，跨槽则可能跨不同主节点，Redis Cluster 不会自动为其建立跨节点事务。

限制同槽使服务器能够维持本地执行语义，代价是应用需要提前设计关联键的分布。

**追问 1：一次事务或脚本涉及多个 key 时，为什么路由位置会影响执行？**

事务或 Lua 需要一个节点访问相关键并保证中间不被普通请求穿插；不同槽的数据在不同节点，涉及网络失败与协调问题，不能仅靠 MULTI 或脚本消除。

**追问 2：Hash Tag 怎样把关联 key 放到同一槽，需要检查什么命名规则？**

例如 `order:{1001}:info` 与 `order:{1001}:lock` 都只对 `1001` 计算槽。

- 精确规则是：找到第一个 `{`，再找到其右侧第一个 `}`；两者之间非空才使用其中的字节，否则对整个 key 计算槽，不继续寻找后面的括号对。
- 因此 `a{}{x}` 使用整个 key，`a{x}{y}` 使用 `x`，`a{{x}}` 使用 `{x`。
- 应按这个解析规则设计关联键，而不是只判断字符串中是否出现相同子串。

**追问 3：为方便操作把所有租户都放到同一槽，会怎样破坏数据分布与容量扩展？**

全部落在一个槽等于把写入和容量集中到一个分片，其他节点无法分担。

应该只让必须原子操作的最小业务实体共槽；跨实体关系改为分步协议或业务一致性机制。

### 10. Redis 主节点写入成功后、复制完成前宕机，会产生什么数据风险？

Redis 复制默认异步，主节点确认写入后，副本可能尚未接收或应用该变更。

- 此时故障切换到落后的副本，已经向客户端报告成功的数据仍可能丢失。
- 高可用描述能否继续服务，不直接等于已确认写入的强持久性。

**追问 1：写入完成、复制完成和副本升主的时间点有什么不同？**

命令在主节点完成、进入复制流、到达副本、被副本处理，以及副本获准升主是不同时间点。

RDB/AOF 本地持久化也与副本复制是另一条保证链。

**追问 2：主节点确认后立即故障，新主为什么可能缺少刚刚确认的数据？**

选举只能从存活节点已有的数据中选择，无法凭空恢复尚未复制的写入。

旧主可能仍保留这条写入，但重新作为副本接入后通常要服从新主历史，不能自行合并旧业务状态。

**追问 3：缓存、计数和分布式锁能否接受相同的数据风险，业务应怎样选择保证边界？**

展示缓存通常可回源重建；计数若用于统计可接受一定误差，但库存、资金和互斥锁不能默认接受。

对强约束业务用数据库条件更新、幂等记录、资源端 fencing 或更合适的一致性存储保障，不把 Redis 成功响应当作全部证明。

### 11. Redis Cluster 如何感知节点状态并传播集群信息？

Cluster 节点通过集群总线交换心跳、槽位归属、配置纪元和故障信息，Gossip 让节点逐步了解其他节点状态。数据复制则通过主从复制链路传递实际写入。

网络分区下，故障判断和多数主节点授权共同影响能否提升副本与继续服务。

**追问 1：Gossip 与业务数据复制承担什么不同职责？**

Gossip 传播拓扑和观察，不用来复制每一条业务命令；复制流传递数据状态。

配置纪元用于区分槽位归属更新，不能把它当成每条业务写入的共识提交序号。

**追问 2：网络分区时应如何分析可服务范围？**

检查多数主节点是否互通、故障分片是否有可用副本、槽位是否完整及 `cluster-require-full-coverage` 等配置。

少数分区通常在超时后停止服务，但此前仍可能存在写入丢失窗口；不能简单概括成任何故障都自动切到任意副本。

### 12. 读请求切到 Redis 副本后，业务可能看到什么一致性差异？

副本读可能读到旧状态，包括刚写入的数据尚不可见或刚失效的状态仍未同步。

- 它可以降低部分读压力，但必须接受复制延迟，不能自动保证写后读一致性。
- 需要明确哪些接口允许旧值，哪些必须访问权威主数据或附加版本约束。

**追问 1：登录状态、库存校验与普通展示缓存是否适合相同的读路由策略？**

普通展示可接受短暂陈旧；登录撤销、库存确认等可能影响权限或超卖，不能仅凭副本旧值作最终决策。

可将展示与确认分开，关键判定走主库或权威事务，副本用于非关键查询。

### 13. `WAIT` 返回的副本确认数，能够说明 Redis 写入达到什么状态？

WAIT 等待当前连接之前写命令对应的复制 offset 被指定数量副本确认，返回实际确认数。

它可以降低部分丢写风险，但不是把 Redis 变成强一致共识数据库，也不等于这些副本已经按要求 fsync。必须在同一连接上理解它所等待的写入范围。

**追问 1：同一连接上先写入再执行 `WAIT`，它等待的是哪些写入的复制进度？**

等待该连接先前写入所达到的复制进度，而不是全系统所有客户端写入的任意全局事务。

连接池中先借一条连接写、再换另一条连接 WAIT，不能自动认为等待的是前一条连接的写入。

**追问 2：等待超时或副本确认数不足时，之前的写入是否自动撤销？客户端应该怎样解释结果？**

不会撤销。超时只表示截止时满足条件的副本数不足，主节点上的写入可能已完成且稍后继续复制。

业务应把它视为可靠性条件未满足，不能直接再执行非幂等操作。

**追问 3：获得副本确认后，能否直接宣称系统已具备强一致性或故障切换绝不丢数据？还需检查哪些持久化和选主条件？**

不能。还要看副本持久化、故障范围、选主是否选择这些副本以及网络分区行为。

更明确的 AOF 确认命令也有其边界；真正强业务不变量仍需在权威存储中保障。

## 7. 缓存穿透、击穿与雪崩

**本节问题**

- [1. 缓存穿透、击穿与雪崩的触发条件有什么不同，如何分别控制回源压力？](#1-缓存穿透击穿与雪崩的触发条件有什么不同如何分别控制回源压力)
- [2. 热点缓存过期后，互斥重建与逻辑过期各适用于什么一致性和延迟要求？](#2-热点缓存过期后互斥重建与逻辑过期各适用于什么一致性和延迟要求)
- [3. 布隆过滤器如何在较小空间内判断元素可能存在，其误判从何而来？](#3-布隆过滤器如何在较小空间内判断元素可能存在其误判从何而来)
- [4. 为一亿个元素设计布隆过滤器时，如何根据可接受误判率估算空间与哈希函数数量？](#4-为一亿个元素设计布隆过滤器时如何根据可接受误判率估算空间与哈希函数数量)
- [5. 新服务上线或缓存重启时，如何决定预热哪些数据，并组织缓存预热？](#5-新服务上线或缓存重启时如何决定预热哪些数据并组织缓存预热)
- [6. 数据库有两千万条数据，但 Redis 只容纳二十万条时，如何让缓存主要保存真正的热点？](#6-数据库有两千万条数据但-redis-只容纳二十万条时如何让缓存主要保存真正的热点)

### 1. 缓存穿透、击穿与雪崩的触发条件有什么不同，如何分别控制回源压力？

| 机制 | 特点与边界 |
|---|---|
| 缓存穿透 | 穿透是查询本不存在的数据，反复未命中回源 |
| 缓存击穿 | 击穿是少量热点 key 失效后大量请求同时重建 |
| 缓存雪崩 | 雪崩是大量 key 集中失效或缓存整体故障，造成回源洪峰 |

三者共同目标是控制数据库压力，但不能使用同一种措施包办。

**追问 1：缓存空值、互斥重建与逻辑过期各自适用于什么情况？**

不存在数据可短期缓存空值并校验参数；热点失效用单飞或互斥重建，能接受旧值时用逻辑过期后台刷新；大量失效用 TTL 抖动、分批预热、限流和隔离。

布隆过滤器能减少不存在查询，但有更新和误判边界。

### 2. 热点缓存过期后，互斥重建与逻辑过期各适用于什么一致性和延迟要求？

互斥重建让少数请求生成新值，其他请求等待、重试或降级，适合不能直接返回旧数据的场景；逻辑过期保留旧值并异步刷新，适合对低延迟更敏感且允许短暂陈旧的展示。两者都要设置失败重试边界和最大可接受陈旧时间。

**追问 1：用户能接受短暂旧数据时，与必须等待新数据时，返回策略有什么不同？**

允许旧值则快速返回并触发一次刷新；必须新值则有界等待刷新结果，超时明确失败或降级。不能把“请求返回得快”当作满足了强实时要求。

**追问 2：重建失败或其他请求拿不到重建锁时，怎样防止请求全部挤向数据库？**

只让一个或有限数量重建者访问数据库，其他请求不直接绕过锁回源；等待设上限，重建失败使用退避、短期失败缓存或熔断。

锁持有者异常时要能释放或过期，但过期仍可能产生重复重建。

**追问 3：已经过时到不能使用的旧值，应怎样降级，而不是永远返回旧数据？**

设置软过期与硬过期两条界限：软过期可刷新并暂用旧值，超过硬界限则返回受限结果或失败。

权限、价格确认等关键操作要重新向权威数据校验，不能无限续用失真缓存。

### 3. 布隆过滤器如何在较小空间内判断元素可能存在，其误判从何而来？

布隆过滤器用 k 个哈希位置在位数组中置位，查询时任一位为 0 可判断未加入，全部为 1 只能说明可能存在，因为这些位可能由其他元素共同置位。

经典无删除布隆过滤器对已正确加入的元素不产生算法性漏判，但工程上的更新遗漏、重建切换会破坏这个前提。

**追问 1：多个哈希位置与位数组怎样表达“可能存在”，为什么会出现误判？**

哈希碰撞使多个元素共享位，产生误报。位数组越满，误判概率越高；不能用普通清零来删除元素，否则可能清掉其他元素依赖的位并产生漏判。

**追问 2：在缓存穿透防护中，误判与漏掉新增合法数据分别会影响什么？**

误判会多一次回源，通常影响性能；新增合法 ID 没及时写入过滤器会被错误拒绝，影响正确性。

因此过滤器不是权威存在性数据库，新数据和同步延迟必须有容错路径。

**追问 3：数据库新增、删除或过滤器重建时，怎样组织更新与兜底，保证合法请求不被长期拒绝？**

新增先规划同步次序或允许近期 ID 兜底，删除可保留无害的误判直到重建，或使用支持删除的结构。

重建基线后追增量，校验再切换，保留旧版本与失败回退，不能边清空边继续用作硬拒绝依据。

### 4. 为一亿个元素设计布隆过滤器时，如何根据可接受误判率估算空间与哈希函数数量？

经典估算为 `m ≈ -n ln(p)/(ln 2)^2` 位，最优哈希数 `k ≈ (m/n) ln 2`。

- 例如 n=1 亿、目标 p=1%，约需 9.585 亿位，即约 119.8 MB（114.3 MiB），k 约 7。
- 这里只是位数组理论量，还要加实现元数据、扩容和副本开销。

**追问 1：目标误判率与元素数量怎样共同影响所需位数组大小和哈希函数数量？**

p 越低需要的每元素位数越多；按公式取合理整数 k 后再验证实际误判。

比如 p=0.1% 时约 14.38 位/元素、k 约 10，不是误判率降低十倍就需要十倍内存。

**追问 2：实际元素数远大于设计容量时，误判率会怎样变化？**

位逐渐被填满，误判率按近似式 `(1-exp(-kn/m))^k` 上升。

实际 n 超出设计容量时，原本 1%的目标不再成立，需要扩容分层或重建，并明确扩容方案是否改变查询成本。

**追问 3：怎样把空间估算与实际回源量、重建成本一起比较，而不只追求更低误判率？**

把不存在请求量乘误判率估算残余回源，再与数据库余量比较。

过低误判率可能浪费内存和哈希计算，重建还会占资源；选择足以保护后端且可持续维护的目标，而不是只追求理论最小误差。

### 5. 新服务上线或缓存重启时，如何决定预热哪些数据，并组织缓存预热？

预热应按历史访问、业务活动和重建成本选择少量高价值数据，不是启动时全表灌缓存。

以可恢复任务分批读取并写入，控制数据库 QPS、缓存写入速率和并发，记录进度；预热完成与否不能成为所有实例无限重启的循环依赖。

**追问 1：多个实例同时启动时，如何控制回源并发、进度与失败重试，避免预热本身变成流量洪峰？**

由协调任务或分片责任避免实例各自全量预热，批次之间限速并设置退避。

- 观察回源量、命中率和服务延迟，失败可从检查点续跑。
- TTL 加抖动，防止同一批预热数据下一次又同时到期。

### 6. 数据库有两千万条数据，但 Redis 只容纳二十万条时，如何让缓存主要保存真正的热点？

采用按需加载为主、少量热点预热为辅，给缓存设置容量上限和适合访问模式的淘汰策略。

根据实际热度而不是数据库全量规模决定驻留集合；对一次性扫描或很大的低价值结果不缓存，避免挤掉重复访问的数据。

**追问 1：按需加载、淘汰与预热如何配合？**

预热近期高频和活动热点，普通 miss 经受控回源后填充；LRU/LFU 等淘汰维持容量，TTL 保证时效。

还要为每个对象设大小上限，不能假设二十万个 key 的总空间始终固定。

**追问 2：怎样识别短时扫描造成的缓存污染？**

观察 miss 来源、访问复用率、淘汰速度和热点命中率；若批量任务扫过大量独立 ID 后热点命中下降，说明污染。

可对扫描链路绕过缓存、单独命名空间或设置准入门槛，而不是继续扩大预热范围。

## 8. 缓存一致性

**本节问题**

- [4. 通过 `binlog` 或 Canal 驱动缓存更新时，如何处理延迟、重复与失败事件？](#4-通过-binlog-或-canal-驱动缓存更新时如何处理延迟重复与失败事件)
- [5. 多个更新事件乱序到达缓存时，怎样避免旧值覆盖新值？](#5-多个更新事件乱序到达缓存时怎样避免旧值覆盖新值)
- [6. 本地缓存与 Redis 组成多级缓存后，如何同步多个服务实例的更新与失效？](#6-本地缓存与-redis-组成多级缓存后如何同步多个服务实例的更新与失效)
- [7. 缓存不可用、缓存未命中与命中空值，为什么应被视为三种不同结果？](#7-缓存不可用缓存未命中与命中空值为什么应被视为三种不同结果)
- [8. Caffeine 本地缓存的按需加载、过期与刷新，如何和 Redis 多级缓存配合？](#8-caffeine-本地缓存的按需加载过期与刷新如何和-redis-多级缓存配合)

### 1. 更新数据库与删除缓存的先后顺序，会分别产生哪些并发不一致窗口？

- **常用顺序：** 两种顺序都存在窗口，但通常采用“数据库事务提交后删除缓存”，避免在权威数据尚未更新时让新查询回填旧值。
- **剩余风险：** 删除比直接覆盖更容易承受写事件乱序，却仍可能遇到删除失败或旧查询迟到回填，需要可靠重试、TTL 和必要的版本控制，不能声称严格实时一致。

**追问 1：分别构造“先删缓存再更新数据库”和“先更新数据库再删缓存”的并发时序。**

先删：A 删缓存，B miss 读到旧库并回填，A 更新库后旧缓存留下。

先更新后删：可避免这一典型顺序，但 B 先读旧库、A 提交并删除、B 最后回填旧值，仍可能留下陈旧数据。

**追问 2：删除缓存与直接更新缓存，在多个更新者乱序完成时有何不同风险？**

直接更新缓存时，较早数据库更新对应的请求可能晚到，覆盖较新的缓存值；删除的重复执行一般不会把旧值写回来。

删除仍会触发重建，因此需要控制旧查询回填与回源压力。

**追问 3：延迟双删依赖哪些时间假设，为什么不能把一个固定延迟当成严格一致性证明？**

延迟双删希望第二次删除落在潜在旧读回填之后，但查询延迟、进程停顿和复制延迟没有固定上界。

固定睡眠只能降低概率，不能证明严格一致；重要业务需要版本比较、可重放失效事件或直接权威读取。

### 2. 分析下面时序，判断最后一次缓存读取可能得到什么值。

初始数据库和缓存中的商品价格均为 100。采用旁路缓存；缓存未命中时，从数据库读取并写回缓存。按以下顺序执行：

```text
1. 请求 A 开启事务，把数据库价格更新为 120，但尚未提交。
2. A 删除价格缓存。
3. 请求 B 缓存未命中，读取数据库；按题设，此时只能读取已提交数据。
4. B 将读到的价格写回缓存。
5. A 提交数据库事务，此后没有其他缓存失效动作。
6. 请求 C 读取价格缓存。
```

按给定顺序推导，不假定数据库事务能够自动回滚或提交 Redis 的操作。

- **读取结果：** C 会读到缓存中的 100。
- **执行时序：** A 的数据库新值 120 尚未提交时就删缓存，B 按题设只能读取已提交的 100，并把它回填；A 之后提交不会自动再次删除 Redis，因此缓存仍旧。
- **事务边界：** 数据库事务只能控制本地数据库操作，不会自动管理 Redis 的可见性。

**追问 1：删除缓存与数据库事务提交之间，另一个请求可能读取什么版本？**

B 看不到 A 未提交的 120，读到旧的已提交版本 100。

这里不需要出现数据库脏读，也能产生缓存陈旧，问题来自两个系统的时序。

**追问 2：把缓存失效动作移到事务提交后，会缩小哪个窗口，是否能消除所有故障？**

提交后再失效可消除“先失效、后提交”的这一窗口，但不能消除删除失败、旧查询晚回填、从库延迟等其他窗口。

事务事件回调控制时机，不自动保证回调一定可靠交付。

**追问 3：删除失败、事件延迟或旧查询迟到回填时，还需要哪些补偿与版本约束？**

用本地消息表或 CDC 保留可重试失效事件；短 TTL 限制陈旧时间；带业务版本的缓存写入需原子比较。

删除后若不保留版本墓碑，旧回填仍可能通过“键不存在”的检查，版本方案必须覆盖这个缺口。

### 3. 数据库已更新但缓存删除失败时，如何恢复一致性？

数据库提交后删除缓存失败，应把失效意图可靠地保存并重试，而不是只打印日志。

- 可在同一本地事务写 outbox，再由后台投递删除；也可用 binlog/CDC 捕获已提交变更。
- 重复删除通常可幂等执行，TTL 作为兜底，关键读取必要时直接访问权威数据。

**追问 1：只依靠 `TTL`，能够限制哪一种不一致持续时间，又无法保证什么？**

TTL 只能限制已有旧值在没有再次续期或旧值重写等情况下的存活时间，不能保证及时失效，也不能修复永久 key。

需要明确最长可接受陈旧时间，而不是说“最终总会过期”就满足所有业务。

**追问 2：采用异步重试时，怎样保留待处理事件，避免删除失败信息也随进程退出而丢失？**

业务变更与 outbox 记录在同一事务提交，后台按事件状态重试并告警，成功后确认。

若只在内存队列保存失败任务，进程崩溃仍会丢；先提交数据库再临时写 MQ 也有双写窗口。

**追问 3：补偿事件重复到达或处理时已有新数据，怎样保证重试不会制造新的错误？**

重复删除安全，但可能额外增加 miss；使用事件版本时应避免旧事件删除或覆盖新版本造成过度重建。

不要在重试删除失败后改为写回事件携带的旧值，结果未知的业务操作也不能被随意重做。

### 4. 通过 `binlog` 或 Canal 驱动缓存更新时，如何处理延迟、重复与失败事件？

CDC 从已提交的 binlog 生成变更事件，按稳定业务键分发，消费者幂等失效或按版本更新缓存，记录消费位点并支持重放。延迟会形成一致性窗口，事件乱序和积压必须监控。

它降低业务代码侵入，但增加了采集、消息和消费者整条链路的运维复杂度。

**追问 1：与业务代码直接更新或删除缓存相比，有哪些取舍？**

业务内直接删缓存时延短，但每条写路径都要正确处理；CDC 能覆盖更多写入口，却不保证零延迟。

应监控最旧事件延迟、失败重试与数据抽样一致性，处理表结构变化、全量初始化和增量衔接，不能把 Canal 当成自动强一致工具。

### 5. 多个更新事件乱序到达缓存时，怎样避免旧值覆盖新值？

以版本 11、12 为例，新事件 12 先到，旧事件 11 后到，盲目 SET 会把缓存倒退。

- 解决方式是按 key 保序、只做失效，或将业务版本与数据一起保存并通过 Lua 原子比较后更新。
- 版本必须来自可比较的权威更新顺序，而不是各实例随意取本机时间。

**追问 1：为同一业务 key 构造新事件先到、旧事件后到的顺序，直接覆盖会产生什么状态？**

数据库已经是 12，缓存先写入 12 又被 11 覆盖，后续命中不再回源，陈旧可持续到下次失效。这与重复事件不同，是更新顺序与到达顺序不一致。

**追问 2：删除缓存、比较版本号与按 key 有序处理分别在哪些条件下有效？**

按 key 保序要求从生产到实际处理全链路不破坏顺序；版本比较拒绝小于当前版本的写入；删除不写旧值但仍需防迟到回填。

跨多个 key 的一致视图不能由一个 key 的版本自动保证。

**追问 3：多实例处理、事件重复或版本信息缺失时，怎样明确无法提供的保证并设计兜底？**

多实例必须共享相同版本判断或有序消费约束；重复版本应幂等处理，并定义同版本不同内容为异常。

缺失版本时不能许诺防乱序，只能采用删除、短 TTL、权威回源或补全版本后再升级保证。

### 6. 本地缓存与 Redis 组成多级缓存后，如何同步多个服务实例的更新与失效？

常见做法是数据库提交后失效 Redis，并发布带 key/版本的本地缓存失效事件，各实例删除对应本地项；本地项同时设置较短 TTL 或最大陈旧时间。

通知不是唯一保障，实例重连需要同步版本或清理旧缓存，防止长期保留错过的变更。

**追问 1：某实例更新了数据库和 Redis，其他实例的本地缓存怎样感知变化？**

可用可靠事件流、版本轮询或客户端跟踪失效等机制通知各实例。

普通 Redis Pub/Sub 便于广播但会丢离线消息，不能单靠它证明所有本地缓存及时一致。

**追问 2：失效通知延迟、丢失或实例离线后重连时，怎样限制旧数据的存活时间？**

短 TTL 提供上界，断线时清空或停止信任本地项，重连后重同步版本。

对不能接受旧权限等数据，读取应进行权威校验；通知延迟期间不能假装所有实例已同时更新。

**追问 3：本地热点缓解了远端读取后，新增的一致性维护成本是否符合业务要求？**

本地缓存适合读热点、值相对稳定且允许短暂陈旧的数据。

- 如果每次读取还必须同步校验 Redis 才能保证正确，节省网络的收益可能消失。
- 需比较命中收益与失效流量、内存副本和错误容忍度。

### 7. 缓存不可用、缓存未命中与命中空值，为什么应被视为三种不同结果？

缓存未命中只说明缓存没有数据，不能证明数据库没有；命中空值表示曾查询得到不存在，仍受其 TTL 和新增数据影响；缓存不可用表示网络或服务故障，连缓存内容是否存在都无法确认。

应用应以不同结果类型表达，不能全部返回 null 后统一处理。

**追问 1：三种结果分别能否证明业务数据存在或不存在，调用方应该怎样区分？**

命中正常值可用于其允许的时效范围；命中空值可短期减少不存在查询；miss 需要受控回源；故障需要降级、限流或直接报错。故障绝不能被解释成业务余额为零或用户不存在。

**追问 2：若全部直接回源数据库，会带来什么容量风险，限流与降级应怎样介入？**

全量把异常当 miss 会在 Redis 故障时把所有流量压到数据库。

应配置回源并发上限、熔断、隔离、陈旧值降级和关键业务优先级，必要时拒绝非核心请求保护权威存储。

### 8. Caffeine 本地缓存的按需加载、过期与刷新，如何和 Redis 多级缓存配合？

Caffeine 可作为进程内一级缓存，Redis 作为共享二级缓存，数据库作为权威来源；按需加载只填充被访问的数据。

- 过期表示旧项不能再正常命中，刷新则可在已有值继续服务时异步加载新值。
- 多级缓存提升读性能，但每层都需要容量、时效和失败策略。

**追问 1：请求命中本地缓存时，能够减少哪些开销，又引入什么跨实例一致性问题？**

本地命中减少网络、序列化与 Redis QPS，但同一 key 在多个进程各有副本，更新不会自动同步。

缓存对象最好不可变，避免某个线程修改本地对象造成进程内也出现意外共享状态。

**追问 2：过期后重新加载与刷新期间继续提供旧值，分别适用于什么实时性要求？**

刷新适合可以短期用旧值的热点展示，过期后等待加载适合更严格时效。

`refreshAfterWrite` 通常在符合条件的后续访问时触发刷新，不等于后台定时任务无条件刷新所有条目；可结合硬过期界限。

**追问 3：加载失败、批量失效与实例重启时，如何限制回源并发并保持可观测性？**

同进程可利用加载去重，多实例还需分布式限速或重建控制；失败保留旧值必须有最大期限。

监控各层命中率、加载耗时、异常和回源量，实例批量重启时分批预热，避免一级缓存同时变冷。

## 9. Redis 分布式锁

**本节问题**

- [4. Redis 主从切换时，分布式锁会面临哪些安全问题？](#4-redis-主从切换时分布式锁会面临哪些安全问题)
- [5. 如何选择分布式锁的 key 和粒度，避免串行化范围过大？](#5-如何选择分布式锁的-key-和粒度避免串行化范围过大)

### 1. 下面的 Redis 加锁与释放流程存在哪些并发和故障风险？

考虑独立 Redis 实例上的以下伪代码；`token` 是每次尝试生成的持有者标识：

```text
if SETNX(lock_key, token) == 1:
    EXPIRE(lock_key, 10)
    execute_business()
    DEL(lock_key)
```

分别讨论进程退出、执行时间超过 10 秒和其他客户端重新取得锁的情况。

- **流程缺陷：** 该流程有两个关键问题：SETNX 与 EXPIRE 分离，进程可能留下永久锁；无条件 DEL 可能删除已经由别人重新获得的锁。
- **加锁与解锁改法：** 加锁应改为单条 `SET lock_key token NX PX 10000`，释放通过 Lua 原子比较 token 后删除。
- **故障边界：** 业务异常路径也要尝试安全释放，但租期过期后的业务写入还需资源端保护。

**追问 1：加锁成功但设置过期时间前退出，会留下什么问题？怎样让加锁与租期设置成为一个操作？**

SETNX 成功后尚未 EXPIRE 就退出，锁没有期限，其他客户端可能永久拿不到。

将不存在条件和租期放在同一个 SET 命令中，只有返回 OK 才视为本次取得锁；超时则执行结果未知，不能直接假定失败。

**追问 2：原持有者停顿后锁已经过期，其他客户端重新加锁，原持有者再 `DEL` 会怎样？**

A 超时后 B 得到新锁，A 无条件 DEL 会把 B 的锁删掉，允许第三个客户端进入。

token 必须每次获取独立生成，不能只用可重复的线程号。

**追问 3：怎样原子校验持有者并释放，为什么“先 `GET` 比较、再 `DEL`”仍然不够？**

比较与删除必须在一个脚本中完成：
```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```
- 先 GET 再 DEL 的两条命令之间仍可能过期并被别人重建。
- 这个脚本只避免误删，并不能阻止失去锁的旧客户端继续写数据库，必要时还要 fencing token 或数据库版本条件。

### 2. 可重入的 Redis 分布式锁需要记录哪些持有者信息？

可重入锁需要保存能区分客户端实例和执行线程的持有者标识，以及重入计数。

- 首次获取建立记录和租期；同一持有者再次获取增加计数；释放时减少计数，降至零才删除。
- 所有判断与更新应原子执行，且需处理客户端重启和租期失效。

**追问 1：同一线程多次加锁与多次解锁如何对应？**

每次成功重入对应一次释放，计数尚大于零时不能把锁整体删掉。

其他线程即使同进程也不是同一持有者；解锁者不匹配应拒绝，而不是静默删除。

**追问 2：它与普通 `SET NX` 锁相比多了什么状态管理？**

SET NX 只能表达“存在或不存在”，没有同一持有者再次进入的状态。

- 可重入还涉及续期、等待者通知、错误解锁和计数一致性。
- 优先使用经过验证的实现，同时理解其固定租期与看门狗模式。

### 3. 业务执行超过 Redis 锁租期时，互斥保护可能怎样失效？

租期到期后 Redis 可以让新客户端获得锁，但旧进程不会因此自动停止。若旧进程继续写业务资源，就会与新持有者并发。

看门狗续期能减少正常长任务的误过期，但不能消除长时间暂停、网络分区或故障切换导致的失去所有权。

**追问 1：原持有者仍在运行，但新持有者已经取得锁，两者可能怎样同时修改业务数据？**

A 暂停超过租期，B 获得锁并写新值，A 恢复后仍按旧状态写入，就可能覆盖 B。

即使 A 最终安全解锁失败，也不能撤销已经发生的越权业务写入。

**追问 2：看门狗续期如何帮助长任务，租期与续期间隔应怎样考虑业务耗时、停顿和网络延迟？**

自动续期在持有者存活且通信正常时延长期限；租期需覆盖合理业务时间和抖动，续期间隔留足余量。

Redisson 常见默认 watchdog 超时为 30 秒，可配置，但不应把这个默认值当作业务安全证明。

**追问 3：固定租期与自动续期模式是否相同？续期失败或节点切换后，为什么仍需明确锁的安全边界？**

显式固定 leaseTime 通常到期自动释放，不等同于自动看门狗持续续期。

续期失败后必须按锁失效处理，关键资源应验证递增 fencing token、业务版本或数据库条件；单靠客户端认为仍持锁不够。

### 4. Redis 主从切换时，分布式锁会面临哪些安全问题？

异步复制下，主节点保存了锁却未复制就宕机，新主可能认为锁不存在，从而授予另一个客户端。

Redlock 通过多个独立 Redis 节点中的多数成功和有效租期计算降低特定故障风险，但其安全性依赖时间漂移、执行耗时和故障假设，不能当作无条件分布式互斥证明。

**追问 1：锁刚写入主节点但尚未复制时发生切换，其他客户端可能观察到什么？**

旧客户端可能还在执行，而新客户端从新主取得锁，两者都认为自己有权操作。

增加副本或启用 AOF 不自动消除这个跨故障切换窗口。

**追问 2：Redlock 试图增加什么故障条件下的保障，它又依赖哪些时间与运行假设？**

它要求在有限时间内从多数独立节点获得同一随机 token 的锁，并从有效租期扣除获取耗时和时钟误差。

长暂停、通信延迟与时钟假设会影响结论，因此必须从具体故障模型评估，而不是只记“多数节点加锁”。

**追问 3：业务不能接受两个持有者同时写入时，还需要怎样与被保护资源的校验机制配合？**

被保护资源应拒绝旧持有者的迟到写入，例如记录单调递增 fencing token，或用数据库版本和唯一约束维护最终不变量。

token 的生成与比较也要可靠；随机解锁 token 只能识别持有者，不天然具有递增隔离能力。

### 5. 如何选择分布式锁的 key 和粒度，避免串行化范围过大？

锁粒度应与需要维护的不变量一致，例如同一订单状态转换锁订单、同一库存额度锁 SKU，而不是锁整个系统。粒度太粗降低并发，太细可能保护不了跨资源约束。

锁 key 要包含租户、资源类型和稳定业务 ID，避免不同业务误用同一把锁。

**追问 1：细化锁粒度时，怎样同时维护业务互斥约束？**

先列出一次操作读取和修改的相关资源。跨两个账户等操作若需多把锁，应统一获取顺序并有超时退出；能用数据库事务或原子条件更新表达的约束，通常比叠加复杂分布式锁更清楚。

## 要点回顾

- 先明确 Redis 的角色：缓存、共享状态与权威业务记录有不同的可靠性要求，不能在故障时一概按普通缓存未命中处理。
- 分清原子执行与持久可靠：单条命令或 Lua 的执行边界，不会自动覆盖数据库更新、消息发送和主从切换。
- 缓存优化要包含失效与恢复路径：除了命中率，还要检查旧值窗口、回源上限、热 Key、大 Key 以及重建期间的数据库压力。
