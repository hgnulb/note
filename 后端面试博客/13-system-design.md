### 1. 业务流量增长十倍后，如何设计高并发接口的分层承载和扩容方案？

- **确认容量：** 先把“增长十倍”转成可测的峰值请求率、并发、数据量和持续时间，再画出接入、应用、缓存、数据库及外部依赖的容量链路。
- **先保护、再优化：** 先限流保护系统，再针对瓶颈优化或扩容：
  - **静态资源：** 静态资源走 CDN。
  - **应用层：** 应用无状态扩展。
  - **读取链路：** 热点读用缓存。
  - **任务处理：** 非实时任务异步化。
  - **数据库：** 数据库优化索引和事务。

不是每层同时增加十倍机器。

**追问 1：先需要确认峰值持续时间、读写比例、响应目标与哪些容量数据？**

确认峰值持续多久、读写比、热点集中度、单请求数据量、平均及 P99 延迟目标、错误率和一致性要求；收集各依赖最大稳定吞吐、连接数、CPU、内存、I/O 和队列长度。

稳定条件下可用并发约等于吞吐乘平均响应时间作初步估计，但突发和长尾必须额外留余量。

**追问 2：沿接入、应用、缓存和数据库逐层分析，怎样找到最先达到上限的环节？**

做逐层时间拆分和阶梯压测，观察哪一层先出现排队持续增长、错误上升或吞吐平台。

- CPU 饱和查热点代码，数据库锁等待查事务冲突，Redis 单 key 热点查分布，连接池耗尽查任务耗时。
- 上游线程忙于等待下游时，扩应用实例可能反而放大数据库压力。

**追问 3：来不及扩容时，怎样控制接入、保护关键请求并降级非核心功能？**

按业务优先级设置入口额度和有界队列，拒绝超预算请求，保留支付等关键流程，关闭推荐、统计等可降级功能；热点数据可按明确时效使用旧值。

重试必须限次、退避，避免用户和多层服务把故障放大。库存、金额等约束不能为了可用性直接绕过。

**追问 4：扩容或优化后，怎样用可比较的压测和监控验证，而不只看机器数量增加？**

保持数据分布、请求比例、硬件和下游条件可比，比较稳定吞吐、P95/P99、错误率和单位请求资源。

- 测试突发、持续负载及失去一个实例后的表现，再灰度放量。
- 验证优化减少了实际瓶颈，而不是只把队列挪到下一层或牺牲正确性。

### 2. 一个接口依赖多个第三方服务，如何缩短整体耗时并控制失败影响？

- **梳理依赖与时限：** 先建立调用依赖图，把互不依赖的请求并行，把必要前置调用串行，使用统一 deadline 限制整条链路。
- **限制资源与失败范围：** 每个下游设独立连接与并发额度，明确哪些结果必需、哪些可降级。
- **并行化的边界：** 并行化只能减少可重叠耗时，不能消除最慢依赖和资源上限。

**追问 1：哪些调用存在数据依赖，哪些能够并行，完整请求的时间预算怎样分配？**

例如 B 需要 A 的结果，则 A→B 不能并行；独立的 C 可与 A→B 并行，总耗时接近两条路径中较长者，而非简单所有耗时相加。

总预算分给连接、调用、重试和结果处理，子调用超时应小于剩余总预算，不能每一层各自再等完整的几秒。

**追问 2：一个依赖超时，其他依赖已完成时，应该整次失败还是保留部分结果？**

取决于业务合同：聚合展示可以返回已完成内容并标注缺失，支付校验等必要条件失败则不能伪造成功。

- 应在接口设计中规定部分成功结构、缓存回退和错误码，而不是运行时随意选择。
- 已经发生副作用的调用需要单独保存状态，整次响应失败不等于它们都没执行。

**追问 3：客户端取消后，如何取消无用任务并限制各下游并发，避免并行化反而放大故障？**

把取消信号沿线程、context 和客户端调用传播，释放响应体与连接，停止排队的无用任务；无法中断的 SDK 放入独立有限资源池。

- 为每个依赖限制并发与重试预算，防止一次用户请求扇出几十个请求。
- 取消 Future 或上游 HTTP 断开也不一定自动停止底层任务，必须验证具体实现。

### 3. 有一万个独立任务需要调用外部服务，如何在限制并发的前提下提高完成速度？

将一万个任务持久化为独立工作项，通过有界队列和固定 worker 池处理，而不是一次启动一万个无限并发调用。

- 每项有稳定任务 ID、状态、尝试次数和超时，整体任务记录进度和汇总结果。
- 并发度由外部服务额度和单任务耗时决定，并通过运行指标调整。

**追问 1：任务应怎样划分、排队并限制同时执行数量？**

按工作项或可重试的小批次划分，限制同时在途数量和每秒调用率，这两个限制分别控制资源与频率。

- 队列满时让生产方等待、延迟调度或拒绝新增，不把所有请求积存在内存。
- 存在租户差异时再分配公平额度，避免一个大任务占满全部 worker。

**追问 2：怎样记录每项任务的成功、失败、超时与取消状态，并判断整批真正结束？**

状态可设计为 PENDING、RUNNING、SUCCEEDED、FAILED、CANCELLED，并记录租约或执行代次用于回收失联任务。

- 只有所有子项进入已确认终态，或剩余项被可靠取消后，整批才能结束。
- 超时可先是结果未知，不能只因调用返回异常就把可能已成功的外部副作用当作失败。

**追问 3：部分结果已写入后重试，如何避免重复处理？外部服务变慢时怎样施加背压？**

将稳定子任务 ID 作为外部幂等键，内部用唯一约束和结果记录防重复；外部不支持幂等时需查询或补偿。

- 服务变慢后降低在途并发、限制重试并延长调度间隔，监控排队时间和超时率。
- 完成状态与结果写入要原子协调，防止结果已保存而任务被当成未处理重新执行。

### 4. 请求到达速度为每秒 200 笔，下游最多处理每秒 100 笔，如何设计有序且可扩展的处理链路？

持续每秒到达 200 笔、只能完成 100 笔，系统存在每秒 100 笔的长期容量缺口。队列只能延后失败，不能让系统长期稳定。

应先明确“有序”是全局有序还是同一业务 key 有序，再通过扩下游、优化单位成本或限制接入使长期到达率不超过可持续处理率。

**追问 1：若持续保持给定到达率和处理率，队列长度会怎样变化？**

忽略拒绝与过期，经过 t 秒大约新增 100t 笔积压；等待时间随积压增长。

- 即使磁盘队列暂时放得下，用户延迟、重试和恢复成本也会越来越高。
- 有限内存或存储最终会耗尽，不能把入队成功当成容量问题已经解决。

**追问 2：哪些措施只能缓冲短时峰值，哪些措施才能处理长期容量缺口？**

排队和临时借用资源只能承接有限的突发，不能单独消除持续的容量缺口。

- 长期稳定需要提高下游处理率、减少每个请求的实际工作量，或者降低准入率。
- 缓存和请求合并要单独分析：对允许复用结果的重复读，它们可以长期减少实际回源量，并非只能缓冲；对每笔都必须独立处理的扣款或写入，则不能靠缓存省掉必要工作。
- 若下游仍最多处理每秒 100 笔，单纯增加消费者通常只会增加争抢。

**追问 3：如何共同设计接入上限、排队期限、拒绝方式和背压，并保持业务需要的顺序？**

设置全局或租户准入率、最大队列长度和最长等待时间，超出返回明确限流或异步受理状态，并向上游施加背压。

同 key 路由到同一分区顺序处理，不同 key 并行；全局严格顺序会限制扩展，应先确认是否真的必要。超时丢弃和重试也要遵守业务顺序与幂等规则。

### 5. 如何设计支持并发读写、`TTL` 和容量上限的进程内缓存？

可以用哈希表保存值、过期时刻和版本，用按过期时间组织的堆或时间轮做后台清理，用 LRU 等结构控制容量。所有相关结构更新必须在明确同步边界内完成。

读取时先判过期，过期不返回；删除要确认仍是自己观察到的那一代记录，避免误删新值。

**追问 1：怎样分别维护键值、过期信息与淘汰顺序？读到过期记录时应在什么条件下删除？**

每个条目可保存(value,expireAt,generation)，过期索引保存(key,expireAt,generation)。

- 更新时生成新版本并更新容量结构；后台弹出过期记录后，只在当前条目版本匹配且确实过期时删除。
- 容量应按条数或估算字节明确口径，单个超大对象也要单独限制。

**追问 2：多个线程同时更新同一 key 时，如何避免清理线程删除刚写入的新值？**

例如清理线程看到旧版本 v1 过期，业务线程已经写入 v2，清理时必须在锁内再次比较 generation 或对象身份，只删除仍为 v1 的条目。不能先无锁检查、之后直接按 key 删除。

TTL 可用单调时间衡量进程内持续时长，避免墙上时钟回拨造成异常。

**追问 3：全局锁与分片锁各有什么取舍？如何验证容量、过期与并发正确性，而不是只测试命中路径？**

全局锁容易维护精确 LRU 和全局容量，但竞争集中；分片锁提高并发，却需要分配各分片额度，通常只能近似全局 LRU。

- 容量控制必须涵盖辅助结构：若每次更新都向过期堆追加记录，旧版本即使不会误删新值，也可能长期占用内存。
- 可用带索引的堆原地更新或删除旧节点，或在陈旧记录占比超过阈值时受控重建过期索引，保证它与有效条目数保持有界关系。
- 测试应覆盖过期与更新交错、同 key 高频续期、容量边界、时间推进、并发删除及清理滞后；同时观察条目表、淘汰链表、过期索引和清理队列的大小。
- 使用可控时钟验证边界，再做持续并发测试，不能只检查命中率或哈希表没有超限。

- [5. 优惠券或库存已经预扣，但订单最终未创建成功，如何可靠地释放占用？](#5-优惠券或库存已经预扣但订单最终未创建成功如何可靠地释放占用)

### 1. 只有数据库、暂不引入 Redis 或 MQ 时，如何实现库存扣减与防超卖？

用 InnoDB 事务和带条件的原子 UPDATE 扣库存，同时在同一事务中写订单。

核心不是先查库存再无条件减一，而是让数据库在更新时检查库存仍足够。再用请求幂等键和业务唯一约束防止重试重复下单。
```sql
START TRANSACTION;
UPDATE stock
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
-- 应用必须检查受影响行数为1；否则回滚并返回库存不足。
INSERT INTO orders(order_id, request_id, user_id, sku_id, status)
VALUES (?, ?, ?, ?, 'CREATED');
COMMIT;
```
`sku_id`需有合适索引，`request_id`需有唯一约束；任一步异常都由应用回滚，不能跳过行数检查继续提交。

**追问 1：库存字段、扣减条件和失败判定应怎样设计，怎样确保库存不变成负数？**

库存用足够范围的非空整数，业务数量先验证为正；扣减条件为 available>=quantity，并根据受影响行数判断成功。

库存非负约束可作为额外防线，但并发正确性主要依赖原子条件更新和事务，不是前端禁用按钮。

**追问 2：库存扣减与订单写入应处于什么事务边界，任一步失败时怎样回滚？**

扣库存和写订单使用同一数据库连接、同一事务。订单写入唯一冲突或其他失败时回滚库存更新；提交响应超时则先查询幂等记录确认结果，不能直接再次扣减。事务中避免远程调用，以减少锁持有和死锁风险。

**追问 3：同一请求并发重试时，怎样避免只防住超卖却重复创建订单？**

用稳定 request_id 唯一约束；若规则是一人一单，再加活动与用户的联合唯一约束。

- 重复插入失败后必须回滚本次扣减，再查询原订单返回。
- 只防库存负数仍可能让同一用户买到多单，因此库存约束和去重约束必须分别建立。

### 2. 如何设计高并发秒杀链路，同时避免超卖并控制数据库压力？

入口先做资格校验、限流和防刷，静态信息走缓存；库存和订单必须有最终权威约束。

- 中等流量可直接用数据库条件更新，极热点可用 Redis 原子预占筛掉大多数失败请求，再把已可靠受理的任务送入 MQ、按下游容量创建订单。
- Redis 筛选不是数据库与消息跨系统原子性的替代品。

**追问 1：怎样估算入口流量、热点商品竞争与数据库实际可承载写入量？**

区分浏览请求、真实抢购尝试和可能成功的订单数，重点看单商品热点，而非平均 QPS。

- 测数据库每秒稳定创建订单能力、锁等待和连接池容量，以此设消费者速率。
- 库存只有几千份时，不应让数百万失败请求都进入订单事务。

**追问 2：只用数据库与采用 Redis 预减库存、MQ 异步下单，各在哪一段减少压力？**

数据库方案简单、约束集中，瓶颈是热点行和事务写入；Redis 预占把失败竞争前移，降低数据库无效访问；MQ 将成功候选按稳定速率交付，削平短时峰值。

它们不增加真实库存，也不保证持续超载可以无限排队。

**追问 3：预减成功而消息发送或订单创建失败时，怎样维护库存与订单的一致性？**

为每次预占生成稳定 ID 并保存可恢复状态。不能把“Redis 减一”和“发 MQ”当成天然原子：可采用可靠任务记录、事务消息或明确的预占事件流，再由补偿扫描处理未完成预占。

- 数据库创建订单仍校验唯一性和最终库存，消费失败后以预占状态 CAS 释放；消息结果未知先查状态，避免误回补。
- 若 Redis 故障可能丢预占，数据库最终约束必须兜住超卖风险。

**追问 4：缓存或队列不可用时，怎样有界降级，而不把全部请求立即转给数据库？**

设有界降级：暂停抢购、返回排队或繁忙，保留结果查询；只有压测证明数据库可承受的一小部分请求才能直接进入数据库。

MQ 恢复后控制重放速率，Redis 重建基于权威记录和正在执行任务校准，不能全量回源或把库存简单重置成初始值。

### 3. 秒杀链路如何实现一人一单，并处理请求重试与重复消息？

将用户与活动组成唯一业务键，例如 UNIQUE(activity_id,user_id)，在权威订单存储层强制执行。

- 入口 Redis 去重可以减少流量，但只是前置优化。
- 消息携带稳定请求 ID 和业务键，消费者在同一事务中完成去重、库存变更和订单写入，重复交付只能返回已有结果。

**追问 1：用户与活动应怎样组成唯一业务约束，在哪一层拒绝重复？**

活动 ID 界定购买资格范围，用户 ID 界定参与者；必要时加入商品或业务规定的维度。

- 数据库唯一约束是最终防线，Redis 或网关可提前拒绝明显重复。
- 若业务允许取消后重购，需要明确唯一规则如何随状态变化，而不是未经设计就删除去重记录。

**追问 2：并发请求和重复消息分别可能在哪个环节绕过普通“先查再写”？**

两个请求可同时查到“没有订单”然后分别写入；同一消息也可被两个消费者重投处理。分布式环境中的普通查询不能锁住未来状态。

应使用唯一插入或原子状态迁移，把检查和生效放在同一事务约束中。

**追问 3：库存扣减、去重记录与订单创建怎样一起成功或得到可恢复结果？**

同库时将事件 ID 登记、条件扣减和订单插入放在本地事务，失败一起回滚，成功后再 ACK。

- 跨系统预占使用稳定预占 ID 与状态机，确保创建和释放不能都成功。
- 客户端收到超时通过原请求 ID 查询，而不是新建另一条业务操作。

### 4. 秒杀接口采用异步下单时，“请求已受理”与“订单已创建”应如何区分？

异步入口只能在任务已被可靠受理后返回“已受理”，不能提前承诺订单存在或库存最终归属。

- 返回稳定的 request_id 或 task_id，客户端通过查询或推送获知 PENDING、SUCCEEDED、FAILED 等状态。
- 只有权威订单事务提交并记录结果后，才可宣布创建成功。

**追问 1：入口什么时候只能返回已受理，什么时候才能返回订单创建成功？**

任务仅进入进程内队列还可能因重启丢失，不足以承诺可靠受理；至少要跨过约定的持久化或消息确认边界。

- 若入口同步完成了订单事务，才可以直接返回订单成功。
- HTTP202 可表达异步受理，但业务状态和查询地址仍要明确。

**追问 2：客户端怎样查询最终状态，超时后重试又怎样关联原任务？**

客户端用原 request_id 查询状态，重试提交时继续带同一幂等键；服务端把该键映射到同一任务和最终订单。

查询应区分“还在处理”“不存在”“处理失败”和“结果暂不可确认”，不能超时就展示下单失败诱导用户重复购买。

**追问 3：异步消费才发现库存不足或无法创建订单时，怎样通知用户并修复已占用资源？**

消费者记录明确失败原因和终态，可靠触发结果通知或让客户端轮询；存在预占则发起按预占 ID 的幂等释放。

- 通知失败不应丢掉最终状态，任务表或订单查询仍可恢复。
- 释放和创建之间使用状态条件，避免迟到成功后还把库存加回。

### 5. 优惠券或库存已经预扣，但订单最终未创建成功，如何可靠地释放占用？

预占必须是一条可追溯资源记录，至少包含 reservation_id、业务请求、资源、数量、状态和截止时间。

- 用 HELD→CONFIRMED 或 HELD→RELEASED 的互斥状态转换管理。
- 只有成功把 HELD 改成 RELEASED 的执行者，才能执行对应的一次回补，并将状态与数量变更原子协调。

**追问 1：怎样记录预占来源、状态与释放条件，避免无法确认该回补哪一次占用？**

用稳定预占 ID 关联订单或优惠券请求，保存原扣减数量和执行版本。

释放条件应是预占仍 HELD 且已明确失败或满足超时处理协议；远端结果未知时先查询，不能只因本地超时就释放一个可能已经被使用的资源。

**追问 2：补偿重复执行或延迟到达时，怎样保证只释放一次？**

同库时将状态条件更新和库存回补放在一事务；重复执行发现已 RELEASED 就返回既有结果，不再加库存。

- 跨系统时每个资源服务维护幂等释放流水，并通过可靠消息重试。
- 去重记录保留期必须覆盖可能的迟到事件，不能刚释放就删记录。

**追问 3：补偿与迟到的创建成功事件并发出现时，状态机应怎样防止库存被错误增加？**

确认与释放竞争同一预占状态，只有一个转换成功。

- 若释放先成功，迟到创建必须拒绝使用旧预占，并按业务规则重新申请或撤销订单；若确认先成功，释放应成为无操作。
- 补偿不是无条件反向加一，而是受当前状态和业务事实约束的操作。

### 1. 订单 30 分钟未支付自动取消，应如何设计状态与触发机制？

订单保存待支付状态和绝对截止时间，创建订单时可靠记录超时任务或事件。

- 到期触发后重新读取并用条件更新把仍待支付且确实过期的订单转为关闭，再可靠释放资源。
- 延迟消息只负责提醒检查，不是无需校验即可直接取消的命令。

**追问 1：订单状态与超时截止时间怎样保存，触发任务需要携带什么标识？**

任务携带 order_id、截止时间和必要的订单版本或任务代次。

- 订单延期、重新支付等变化会使旧触发失效，因此处理时核对数据库当前 deadline 和状态。
- 订单创建与超时任务记录应同事务或采用可靠事件方式，防止订单存在却永远没有取消触发。

**追问 2：定时扫描、延迟队列与 MQ 延迟消息在精度、可靠性和运维成本上怎样比较？**

定时扫描实现直接，可建立(status,deadline)索引分批扫描，精度受周期影响；延迟队列或延迟消息减少无效扫描但引入组件和投递语义。

- 常用延迟触发加低频补偿扫描，既满足时效又能发现漏触发。
- 不能依赖 Redis 过期通知提供严格准点、可靠的关单事件。

**追问 3：触发晚了或同一订单被多次触发时，怎样确认当前状态并安全执行？**

重复或晚到触发都执行同一条件更新，例如状态仍待支付且 deadline<=当前时间才关闭。已支付或已关闭则不再改变。

释放库存和通知采用幂等流水或事务消息；触发迟到的业务损失应由产品规则明确，不能通过伪造实际关闭时间掩盖。

### 2. 订单超时取消与用户支付并发发生时，如何避免错误关单、重复回补库存或状态冲突？

支付确认和关单必须围绕同一个订单状态机竞争，数据库条件更新确保同一状态只能被一种转换占用。

支付渠道与本地数据库不是一笔本地事务，关单还需处理渠道支付中的状态，通常先进入关单处理中并查询或关闭渠道支付，再确认最终结果。

**追问 1：支付和关单各允许从哪些状态推进，数据库更新条件怎样表达互斥结果？**

例如待支付可转 PAID 或 CLOSING，但不能同时完成两个条件更新；使用`WHERE status='PENDING' AND version=?`等表达前提。

收到支付成功时记录真实渠道流水；关单流程依据渠道最终状态决定支付成功或 CLOSED，不能只本地改成 CLOSED 就认定远端不会扣款。

**追问 2：一个事件先完成，另一个延迟到达时，怎样返回可解释的结果并处理资金或库存？**

支付已成功则关单不应回补已售库存；关单已确认且后来收到实际成功付款，则按预设规则恢复可履约订单或发起退款，不能忽略资金事实。

状态更新失败需读取现状并返回可解释结果，所有迟到事件保留审计记录。

**追问 3：重复通知和重复回补发生时，怎样保证状态与数量都不会被重复改变？**

回调使用渠道流水或事件 ID 去重，库存释放使用订单预占 ID 和唯一释放记录。

- 订单状态与同库库存调整可事务提交，跨服务则依靠可靠事件和资源端幂等。
- 每次回调都`stock+1`或每次支付成功都再次发货，都会破坏业务不变量。

### 3. 远程扣费调用超时，但实际结果可能成功时，本地业务应该怎样推进？

先将本地支付操作标记为处理中或结果未知，保存唯一支付流水号、请求参数摘要和渠道信息。

- 通过同一流水号查询渠道结果，或按渠道支持的幂等机制重试。
- 只有确认最终失败才能按失败推进；超时本身不是失败事实。

**追问 1：本地超时能否证明远端失败，应该保存什么“结果未知”状态？**

超时只说明本地未及时获得结果，远端可能已扣费、正在处理或根本未收到。

- 应记录 UNKNOWN 或 PROCESSING，并保留后续查询和回调入口，避免用户看到失败后重新创建第二笔支付。
- 业务要有可见的处理中状态，而不是只在日志里记异常。

**追问 2：怎样使用业务流水号查询结果或发起幂等重试？**

同一次扣费使用稳定 merchant_payment_id 或幂等键，查询、回调和重试都关联它。重试参数必须一致，不能更换 ID 绕过渠道去重。

若渠道不提供可靠查询或幂等能力，应降低自动重试范围并引入对账或人工处理，而不是假设网络重发无害。

**追问 3：远端最终成功但本地需要取消时，如何设计可追踪的补偿，而不是再次盲目扣费？**

确认远端成功但本地业务已无法履约时，创建独立退款或撤销流水，关联原支付并使用独立幂等键，记录申请、处理、成功和失败状态。

退款失败继续查询和重试或转人工，不删除原支付成功记录；补偿要形成可核对的资金链，而不是再扣一次或直接改本地余额。

### 4. 同一订单同时从两个支付渠道发起付款，如何避免订单被重复确认或产生无法追溯的多笔扣款？

把业务订单、支付尝试和渠道流水分开建模：订单只允许一次有效付款确认，但可记录多次支付尝试；每笔真实渠道成功都必须留账。

入口尽量限制同订单同时存在多个有效支付会话，仍要为用户已在两个渠道完成扣款的情况设计退款流程。

**追问 1：订单、支付单与渠道流水怎样关联，各自表达什么业务事实？**

订单表达应收和履约状态；支付单表达一次渠道支付尝试，保存金额、币种、渠道和幂等键；渠道流水表达真实资金结果，使用渠道交易号唯一约束。

一个订单可对应多个支付尝试，但只能有明确的一笔被认定为有效结算，其余成功资金必须另行处理。

**追问 2：两个渠道都返回成功时，怎样避免订单重复确认，并识别需要处理的第二笔资金？**

收到成功事件后，用订单状态或有效支付 ID 的条件更新竞争确认；第一个合法支付完成订单，第二个不再重复发货或扣库存，而被标记为重复付款待退款。

不能因订单已 PAID 就丢弃第二笔成功通知，否则账上会有无法解释的多收款。

**追问 3：退款或人工处置失败时，怎样保留可核对状态并继续推进，而不是只打印错误日志？**

退款任务持久化并有状态、尝试次数和唯一退款号，渠道结果未知则主动查询，明确失败按策略重试或升级人工。

保留金额、原因、原支付与退款关联、操作人和时间，持续对账发现滞留。日志只用于诊断，不是退款工作流的可靠存储。

### 5. 如何设计购物车的添加、合并、数量修改与下单校验？

购物车以用户或游客会话为边界，以 SKU 及选定规格作为行键，保存数量和展示快照；价格、促销和库存以结算时权威校验为准。

添加、合并和修改需明确幂等与并发规则，不把购物车当成已经锁定库存的订单。

**追问 1：游客和登录用户的购物车分别怎样标识和保存，合并时采用什么数量规则？**

游客用随机会话标识保存在本地或服务端，登录用户通常持久化或缓存到共享存储。

登录合并可选择相同 SKU 数量相加、取较大值或按业务规则覆盖，但必须规定上限和重复合并标识，避免重试登录把数量多次累加。

**追问 2：购物车中的价格和库存是否可以直接作为下单依据，应该在哪个时点重新校验？**

不能直接使用。下单前重新校验 SKU 有效性、实时价格、优惠资格、购买限额和库存，在订单中保存最终成交快照。

购物车可展示“价格已变化”或“库存不足”，不能悄悄按旧价成交，也不应因商品在购物车中就长期预占库存。

**追问 3：同一商品被多端同时修改时，怎样处理覆盖、数量变化与最终用户展示？**

绝对数量更新可使用版本号检测覆盖，增量更新使用原子操作并带请求 ID 去重；明确最后写入、冲突提示或合并语义。

服务端返回最新版本与数量，客户端按版本刷新，避免迟到响应覆盖更新后的展示。多端一致性要求应与用户体验一起定义。

### 6. 支付结果通知可能重复、延迟或缺失时，如何通过回调与主动对账确认最终状态？

- **总体方案：** 采用“可信回调推进状态，主动查询和对账补漏”的双通道。
- **回调处理：** 回调验证来源后，根据唯一渠道流水和本地支付单检查金额、币种和状态，在事务中记录事件并执行合法状态迁移；处理可靠落库后再确认回调。
- **补漏机制：** 缺失或结果未知的支付由定时查询及账单对账继续收敛。

**追问 1：如何验证通知来源，并核对订单号、金额、币种与交易状态？**

按渠道协议验证签名、证书或共享密钥，必要时使用原始报文验证，检查时间窗口和防重放信息。

再核对商户身份、支付单号、订单号、金额、币种及终态，不只相信“支付成功”字符串；关键异常可主动向渠道查询确认，并保留原始事件的安全审计信息。

**追问 2：回调处理成功但响应丢失时，重复回调怎样保证只生效一次？**

数据库为渠道事件或交易号建立唯一约束，把去重登记与支付状态更新放在同一事务。

- 响应丢失后重投发现已处理，返回相同确认，不重复发货或记账。
- 后续发货、通知通过 outbox 等可靠事件推进，不能在回调事务里完成无限外部调用。

**追问 3：长期处于处理中、回调缺失或本地状态与支付渠道不一致时，怎样查询、对账、补偿并保留审计信息？**

扫描超时处理中记录查询渠道，定期比较渠道账单与本地支付、退款流水，按差异类型补状态、补通知或退款。

每个补偿有唯一 ID 和状态，失败进入可追踪队列与人工工单；对账不能只比总金额，还要逐笔关联交易，防止两笔相反差异互相抵消。

### 1. 多应用、多实例系统如何共享登录状态，并实现退出、强制下线与 Token 失效？

可以把统一认证与业务会话分开：认证中心负责验证用户、签发登录凭据；业务服务校验凭据后建立请求身份。

- 需要即时撤销时，使用共享会话存储或可查询的撤销状态；使用自包含的短期访问 Token 时，配合受控的刷新凭据。
- 不能既要求业务服务完全离线验签，又不增加任何状态传播机制，还保证退出立即对所有实例生效。

**追问 1：认证中心与各业务系统分别保存哪些状态，多个实例怎样共享有效身份？**

认证中心保存账号、认证会话和刷新凭据等状态；业务系统保存自身授权信息，必要时维护业务会话。

- 多个实例通过共享会话存储或相同的验签、公钥轮换规则识别用户。
- 请求级身份放在当前请求上下文中，不能把线程本地变量当成跨实例会话存储。

**追问 2：退出、强制下线和 Token 自然到期，分别需要失效哪些凭据？**

退出应撤销相应会话和刷新凭据，清理客户端 Cookie 或 Token；强制下线还可以更新用户会话版本或撤销指定设备会话。

- 已签发的访问 Token 如果没有在线撤销检查，仍可能使用到过期。
- 自然到期由验证端检查有效期，不能只依赖客户端主动删除凭据。

**追问 3：Token 被复制或服务端撤销信息延迟时，怎样确定可接受的生效窗口？**

复制的 bearer Token 在失效前可能被持有者使用，所以同时需要 TLS、安全存储、短有效期及异常会话检测。

- 撤销缓存的 TTL、事件传播延迟和访问 Token 剩余寿命共同决定窗口。
- 敏感操作可以在线检查会话或要求重新认证；对普通请求则按业务允许的窗口权衡可用性和成本。

### 2. 扫码登录如何关联二维码、浏览器会话和手机端确认？

服务端为浏览器生成随机、短期、一次性的登录尝试 ID，并将它与浏览器会话绑定。

- 手机扫码只表示识别了这次尝试，不应立即给浏览器登录；手机端在已认证状态下确认后，服务端把尝试原子地转为已确认。
- 浏览器通过受保护的轮询、SSE 或 WebSocket 得到结果，再用一次性结果换取自己的会话。

**追问 1：二维码怎样关联一次浏览器登录尝试，扫码与确认是哪些不同状态？**

状态可以是待扫描、已扫描、已确认、已消费、已过期或已取消。

- 二维码包含不易猜测的尝试标识，而不是长期登录 Token。
- 浏览器另外持有用于证明发起者身份的会话或秘密；扫码者不能仅凭二维码中的公开内容，冒充浏览器领取登录结果。

**追问 2：手机端确认后，怎样只通知正确的浏览器，并防止二维码重复使用？**

手机确认接口校验手机端身份、尝试状态和有效期，使用条件更新只允许一次确认。

- 结果通知只能到绑定的浏览器连接；最终领取时再次校验浏览器身份并原子消费。
- 登录成功后轮换会话标识，防止会话固定，也不要把手机的长期凭据直接交给浏览器。

**追问 3：二维码过期、浏览器断线或用户重复确认时，怎样保持状态一致？**

以服务端状态和到期时间为准，重复确认返回已有结果或明确的状态冲突。

- 浏览器断线后可在有效期内重新查询，不依赖某次推送必达。
- 过期与确认竞争时通过条件更新确定唯一终态，已过期或已消费的尝试不能重新恢复为可登录状态。

### 3. 短信验证码登录如何控制有效期、尝试次数、发送频率与重复使用？

验证码应绑定手机号、用途和本次验证流程，并在服务端保存有效期、剩余尝试次数及消费状态。

- 发送端按手机号、账号、设备、IP 和服务总预算限流；验证端把“校验、减少次数或标记已使用”作为原子操作。
- 验证码是短期凭据，不能记录到普通日志，也不能仅靠前端倒计时控制有效性。

**追问 1：验证码、手机号、登录尝试与有效期应怎样绑定，怎样控制发送频率？**

同一手机号的注册、登录、改密验证码不能混用；重新发送时要明确旧码是否立即失效。

- 除单手机号冷却时间和每日限额，还要限制设备、IP、网段及总发送量，防止换手机号或代理绕过。
- 验证码由安全随机源产生，服务端保存受保护的校验值，不将短信内容直接暴露给查询接口。

**追问 2：多次尝试与多人竞争验证时，成功消费验证码如何保持原子性？**

用数据库条件更新或 Redis Lua 在一次原子操作中检查用途、有效期、错误次数和未消费状态，成功后立即消费。

- 错误输入也原子扣减剩余次数，防止并发请求绕过上限。
- 消费成功与创建会话之间还要有明确的幂等结果或失败恢复设计，不能把两步都假设为绝不失败。

**追问 3：恶意批量请求怎样同时控制费用与安全风险，而不是只限制一个 IP？**

单 IP 限流挡不住分布式请求，也可能误伤共享出口用户。

- 应叠加账号与设备风险、发送预算、供应商配额和异常比例监控，达到阈值触发更强验证或暂停发送。
- 接口响应避免直接泄露账号是否存在，并给合法用户保留可控的恢复通道。

### 4. 多租户系统如何同时落实接口权限、数据权限与租户隔离？

身份和租户必须来自服务端验证后的认证上下文，不能直接信任请求中的 `user_id` 或 `tenant_id`。

- 接口层检查用户能否执行该动作，数据访问层进一步约束目标资源属于哪个租户、用户拥有哪些数据权限。
- 隔离要贯穿数据库、缓存、搜索、消息和文件访问，而不是只在控制器里补一个条件。

**追问 1：身份来自哪里，接口权限和数据权限分别应在哪一层校验？**

认证凭据建立可信用户身份，服务端再检查该用户是否属于目标租户。

- 接口权限控制“能否导出、修改”，数据权限控制“能导出、修改哪些记录”。
- 跨租户管理操作必须显式授权和审计，不能因为调用来自内部服务就默认拥有全局权限。

**追问 2：客户端修改 `user_id` 或 `tenant_id` 后，怎样保证查询和更新仍只触达合法数据？**

查询和更新条件包含服务端确认的租户及资源归属，例如 `WHERE tenant_id=? AND id=?`，并校验受影响行数。唯一约束、联合索引也按租户语义设计。

仅先查询权限、再无条件按 ID 更新仍可能留下状态竞争或越权路径，关键限制应进入最终写入条件。

**追问 3：后台任务、缓存和批量导出是否也遵循同样的隔离规则，如何检查遗漏路径？**

任务和消息要携带可验证的租户上下文，消费者重新建立作用域；缓存键、对象存储路径、搜索过滤及导出结果也必须隔离。

- 测试应覆盖伪造租户、批量 ID 混入其他租户、管理员降权及异步线程复用。
- 使用拦截器统一加条件有帮助，但仍要检查原生 SQL、旁路查询和特殊管理接口。

## 5. 短链接系统设计

**本节问题**

- [1. 如何设计支持高访问量的短链接系统？](#1-如何设计支持高访问量的短链接系统)

### 1. 如何设计支持高访问量的短链接系统？

先明确短码唯一范围、链接是否可修改、有效期以及生成与跳转规模。

- 一个基本方案是生成唯一 ID 后做 Base62 编码，或使用安全随机短码并靠唯一约束处理冲突；数据库保存短码到目标地址及状态的映射。
- 跳转链路以缓存承接热点，未命中才查存储，配合防穿透、限流和失效传播。统计异步处理，不应成为每次跳转的同步瓶颈。

**追问 1：先要确认生成量、访问量、有效期、同一长链接是否复用等哪些需求？**

需要确认每天新增量、峰值跳转 QPS、长链接长度、租户隔离、过期与修改需求，以及相同长链接是否允许生成不同短码。

- 若需要去重，还要明确 URL 规范化规则；随意排序查询参数或删除参数可能改变目标语义。
- 根据生成量估算短码空间和存储增长，而不是直接规定固定长度。

**追问 2：短码生成、冲突处理与映射保存怎样组织，怎样避免并发创建冲突？**

ID 编码方案依赖可靠的唯一 ID 分配；随机方案依赖足够空间及数据库短码唯一索引，冲突后有限重试。创建接口另设幂等键，处理响应丢失后的重复提交。

只在 Redis 中先检查短码不存在再写库，不能代替数据库唯一约束；短码也不应被视为访问权限凭据。

**追问 3：热点短码查询、跳转与缓存失效怎样配合，缓存不可用时如何保护存储？**

热点映射可放本地缓存与 Redis，缓存中保存有效期和状态。

- 无效短码使用短期空值缓存并限制随机探测；回源合并和并发上限保护数据库。
- 链接可变时慎用可长期缓存的永久重定向，按业务选择重定向状态和缓存头，避免浏览器绕过服务端继续访问旧地址。

**追问 4：短码失效、目标地址变更或数据迁移时，怎样保持跳转结果与管理端状态一致？**

数据库事务更新映射与版本后，可靠触发缓存失效或版本更新，处理失败重试与乱序。

- 安全封禁类状态可增加在线校验，不能只等长 TTL。
- 迁移时保持短码不变，进行全量加增量同步、校验和灰度切读；还应限制危险协议及钓鱼滥用，不能把任意目标地址都视为可信。

### 1. 即时通信系统如何组织连接管理、消息确认、离线消息与历史记录？

将长连接接入、消息持久化和消息投递分开。接入层保存当前连接及路由，持久层保存会话消息、稳定消息 ID 和顺序标识，投递层按用户设备维护送达进度。

发送成功通常应在消息可靠保存后确认；离线消息通过游标补拉，而不是只依赖内存中的连接和一次推送。

**追问 1：连接状态、消息内容与投递状态分别放在哪里，实例切换会影响什么？**

连接对象只能保存在实际持有套接字的节点，用户到节点的路由可放共享目录；消息和必要的投递进度应持久化。

- 节点切换后客户端重连并恢复身份，再从已确认游标补拉。
- 连接路由不是消息存储，实例宕机不应导致已确认的消息消失。

**追问 2：收到服务端 `ACK`、对方设备收到与对方已读，应怎样区分？**

服务端 ACK 表示消息被系统接收或持久化，具体边界需协议明确；设备送达回执表示客户端已收到；已读回执表示用户达到产品定义的阅读状态。三者不能混为一谈，也不保证对方真实理解了内容。

回执本身要允许重传和去重，服务端不能凭 socket 写成功就宣称已读。

**追问 3：用户离线后再次上线，怎样补齐历史并避免重复展示或消息乱序？**

客户端携带每个会话的最后确认序号，分页补拉后按消息 ID 去重，按会话顺序组织展示。

- 实时推送与补拉并发时允许重复但不允许漏段；遇到序号缺口继续补齐。
- 多设备独立维护送达或阅读进度，并明确撤回、编辑和删除事件的版本规则。

### 2. 直播间高并发弹幕如何设计接入与分发，避免推送压力集中到单点？

将接入连接按节点分散，把弹幕先送到房间级路由或消息总线，再分发给实际承载该房间观众的多个网关。

- 广播节点发送到网关组，而不是自己维持所有用户连接。
- 热点房间单独扩展分发能力，并对入口、房间和单连接设置有界缓冲及降载策略。

**追问 1：连接接入、消息广播与房间分组应怎样拆分压力？**

接入层负责连接和鉴权，房间服务负责成员路由、消息校验与顺序，分发层负责广播到订阅网关。

- 一个房间可以跨多个网关，网关再在本地扇出，减少中心节点重复网络发送。
- 用户进出房间应更新订阅关系，避免向没有观众的节点持续广播。

**追问 2：热点直播间突然放大流量时，怎样避免单个广播节点成为瓶颈？**

按房间建立可扩展的分发树或分区，热点房间使用专门的分发组，限制单发布者和单房间速率。

扩容时要处理新旧订阅重叠、消息去重和短时缺口，不能只增加网关却仍让唯一房间分发节点承担全部带宽。

**追问 3：消息到达速度超过用户展示能力时，如何在延迟、丢弃与展示完整性之间选择？**

普通弹幕通常优先低延迟，可按规则采样、合并或丢弃过期消息，并明确告知业务其非完整交付语义。

- 礼物、付费行为和审计事件应走可靠记录链路，展示降采样不能丢账。
- 慢客户端使用有限队列，必要时丢弃可丢消息或断开，不能无限积压拖累整个网关。

### 3. 一个用户向大量关注者发布消息时，如何设计推送或拉取方案，避免热点账号压垮服务？

推模式在发布时把内容索引写入关注者收件箱，读快但写扩散大；拉模式在用户访问时读取关注账号的发布流并合并，写轻但读成本高。

通常按账号规模、活跃关注者比例和时效要求混合：普通账号推给活跃用户，大 V 内容在读时合并或只推部分活跃人群。

**追问 1：推模式与拉模式分别把工作量放在写入还是读取阶段？**

推模式把扇出成本放在写入，收件箱通常保存内容 ID 而不是完整内容；拉模式保存作者发布流，读取时按时间或排序规则合并。

两者都要处理权限、删除和取消关注，收件箱已有索引不能绕过最终可见性校验。

**追问 2：普通账号与大 V 的关注者规模不同，为什么可能采用混合策略？**

大 V 一次发布可能触发数百万次写入，推送给长期不活跃用户收益很低；全部采用拉模式又会放大普通用户的读请求。

混合策略让不同账号承担适合的成本，并在切换时使用消息 ID 去重和补齐边界，避免一段内容既没推送也没被拉取。

**追问 3：突然增加海量关注者时，怎样限制单个账号扩散任务，保护其他用户请求？**

扇出任务按账号、分片和批次设置配额，放在有界异步队列，采用公平调度，避免一个账号独占工作线程。

- 关注者突增时动态降级为拉模式或只推活跃用户，限制批次与下游写入速率。
- 监控的是扇出延迟、积压和读端补拉成本，不仅是发布接口响应时间。

### 4. 海量关注关系需要支持“我关注的人”“关注我的人”和关注状态判断时，如何设计表结构与索引？

可以使用关系表 `follow(follower_id, followee_id, created_at, ...)`，以 `(follower_id, followee_id)` 保证关注关系唯一，并建立反向索引支持查询关注者。

列表使用稳定的复合排序键分页。数据量需要分片时，通常选择一方向作为权威写入视图，另一方向通过可靠事件维护，明确最终一致窗口。

**追问 1：出关注与入关注两类查询，各需要怎样的主键和索引访问路径？**

“我关注的人”以 `follower_id` 为首列定位；“关注我的人”以 `followee_id` 为首列定位。

- 若按关注时间倒序展示，可分别设计包含时间和对端 ID 的复合索引，同时保留关系唯一约束。
- 主键和索引组合应匹配实际查询，不必为了两个方向复制整份用户资料。

**追问 2：判断是否关注、分页列出关注者以及取消关注，怎样避免全表扫描或重复关系？**

是否关注使用两个 ID 的等值查询，新增依赖唯一约束，取消使用条件删除或状态转换。

- 分页以 `(created_at, 对端ID)` 等稳定键续查，而不是大偏移扫描。
- 同一关系重新关注时，需定义时间与版本是否重置，避免旧的取消事件覆盖新关注。

**追问 3：热点账号与数据分片后，双向查询和一致性维护分别会增加什么成本？**

按关注者分片后，“某账号的所有粉丝”可能跨分片，因此需要反向视图或额外路由。

- 大 V 的粉丝表和计数会形成热点，可按目标账号加子分桶分散存储，再合并分页。
- 双向视图通过版本化事件、幂等应用和对账修复维护，不应宣称两个独立库自动原子更新。

## 7. 计数与排行榜设计

**本节问题**

- [1. 一个接口每被调用一次就增加计数，单机与多实例部署下如何保证计数正确？](#1-一个接口每被调用一次就增加计数单机与多实例部署下如何保证计数正确)
- [2. 高并发点赞系统如何同时维护用户状态、点赞计数与持久化数据？](#2-高并发点赞系统如何同时维护用户状态点赞计数与持久化数据)
- [3. 排行榜或热榜如何设计更新与查询链路，在高并发下控制热点与存储成本？](#3-排行榜或热榜如何设计更新与查询链路在高并发下控制热点与存储成本)
- [4. 如何设计高并发抢红包系统，使总金额与总领取人数始终满足约束？](#4-如何设计高并发抢红包系统使总金额与总领取人数始终满足约束)

### 1. 一个接口每被调用一次就增加计数，单机与多实例部署下如何保证计数正确？

先明确统计的是每次请求尝试，还是每个独立业务事件。

- 单机内存计数可用原子变量；多实例需要集中原子计数、数据库原子更新，或按分片记录后汇总。
- 若每次返回值都要求是全局实时精确序号，就必须承担相应的协调成本，不能使用最终一致的本地累加冒充精确结果。

**追问 1：单机共享计数怎样实现原子更新，多实例后需要改变哪一层？**

单机可用 `AtomicLong.incrementAndGet()`，它同时完成原子加一并返回本次值；`LongAdder` 适合高并发统计，但 `sum()` 不是与所有并发更新线性一致的快照。

多实例时 JVM 内的原子变量彼此独立，应把操作移到共享存储或明确采用分片计数。

**追问 2：必须实时精确返回与允许异步汇总时，存储和同步方案为何不同？**

Redis `INCR` 可以在单实例上原子计数，但异步复制切换和持久化策略会影响故障后的结果；需要更强持久性时可用数据库事务计数或可靠事件账本。

允许延迟时，各实例批量上报、分片汇总更易扩展，但必须给出延迟与丢失风险，不能每次返回一个假装精确的全局值。

**追问 3：请求重试也会调用接口时，业务要求统计尝试次数还是独立业务事件，如何先明确口径？**

统计请求尝试次数时，网络重试也算一次；统计订单等独立事件时，需要业务 ID 去重，并让去重登记与计数更新共同生效。

若计数接口返回后响应丢失，客户端携同一幂等键重试应返回原结果，而不是再次计数。还需定义失败请求、取消请求是否计入。

### 2. 高并发点赞系统如何同时维护用户状态、点赞计数与持久化数据？

将“某用户是否点赞”作为可验证的业务状态，计数是该状态集合的聚合结果。

- 点赞只允许从未点赞转为已点赞并加一，取消只允许从已点赞转为未点赞并减一；这两步必须在同一原子边界内执行。
- 高并发下可把状态变更事件持久化并异步构建计数，利用版本号和周期对账修复偏差。

**追问 1：用户点赞状态与总计数应怎样关联，取消点赞需要满足什么前置状态？**

关系键通常是 `(内容ID, 用户ID)`。重复点赞不再加一，未点赞时取消不再减一。

数据库方案用唯一约束和事务保证关系与计数一致；Redis 方案用 Lua 统一检查状态、修改关系和计数，但还必须设计持久化与故障恢复，不能认为原子脚本自动解决跨库一致性。

**追问 2：重复、乱序和并发操作发生时，怎样防止计数与用户状态分离？**

不要把任意重试都解释成新的 `+1/-1`。事件携带唯一 ID、目标状态和可比较的版本或顺序，消费者按实体去重并拒绝旧版本覆盖新状态。

同一用户的并发操作须定义服务端接受顺序；客户端时间戳不能未经校验就充当可靠全局顺序。

**追问 3：Redis 与数据库短暂不一致时，读取以哪个状态为准，怎样完成持久化与修复？**

若数据库是权威状态，用户自己的点赞结果可优先由刚完成写入的权威链路确认，聚合计数允许短暂延迟并明确展示语义。

- Redis 作为展示视图可通过可靠事件重建；若先写 Redis 受理，则必须有可靠事件记录和后续落库结果。
- 通过关系明细重算计数，不能仅比较两个可能同时错误的计数器。

### 3. 排行榜或热榜如何设计更新与查询链路，在高并发下控制热点与存储成本？

实时单榜可以用 ZSet 保存成员和分数，批量更新并读取前若干名；周期热榜则可异步聚合成快照，降低每次请求的计算成本。

- 先定义分数公式、统计窗口、同分规则和更新时间，再选择结构。
- 大规模全局精确排名比查询少量热门项更昂贵，不应把两类需求按同一方案处理。

**追问 1：需要实时排名、周期刷新还是仅查询前若干名，分别会怎样影响数据结构？**

实时查询个人名次需要维护可排序的全量状态；只看前 K 名可维护候选集合，但成员掉出与回补仍需可靠数据来源。

- 周期榜单可以从事件流或数据库汇总后发布版本化快照。
- 时间窗口变化时要处理过期贡献，不能只累加永不减去的历史分数。

**追问 2：同分排序、热点更新和大榜单分页怎样处理？**

ZSet 同分默认按成员字节序排序，不等于业务要求的时间先后。

- 复合分数受浮点精确整数范围限制，不能任意拼接超大整数；可增加明确的排序方案或离线快照。
- 大偏移分页和热点成员高频更新都应评估成本，通过批量合并、限频及稳定快照控制压力。

**追问 3：数据量和更新频率持续增长时，怎样控制单点压力与存储成本，并验证榜单正确性？**

可以按地域、业务或用户分桶维护局部榜再汇总候选，但成员分数若分散在多个分片，简单合并各分片前 K 名不一定得到全局正确榜单。应明确分片规则和聚合保证。

通过权威事件重放、抽样计算与全量周期校验验证计数和排序，并控制历史榜单保留周期。

### 4. 如何设计高并发抢红包系统，使总金额与总领取人数始终满足约束？

金额使用整数最小货币单位，保存红包总额、剩余金额、总份数、剩余份数以及领取明细。

- 每次领取在同一原子边界内完成资格校验、金额分配、剩余量扣减和用户领取登记，保证不超金额、不超人数、同一用户不重复领取。
- 真正的入账还需要可靠账务流水，不能只靠 Redis 中的剩余数代表资金已经结算。

**追问 1：总金额、份数和用户领取记录，应怎样保存并建立不超发的约束？**

基本不变量是“已领取金额＋剩余金额＝总金额”，份数也满足对应关系；每份金额必须满足最小单位和剩余份数约束。

- 随机分配时，要为剩余领取者保留最低金额，最后一份领取剩余金额。
- 领取唯一键可用 `(红包ID, 用户ID)`，红包状态限制开放、关闭和退款之间的合法转换。

**追问 2：重复领取与并发竞争时，金额扣减和领取登记怎样共同生效？**

数据库事务可同时插入唯一领取明细并条件扣减余额；Redis Lua 可完成单槽内的高速资格和额度预占，但要配合可靠事件、幂等账务处理及故障恢复。

不能先扣余额、再单独记录用户而没有补偿或原子保证，也不能把两个用户同时读到的余额当成独占额度。

**追问 3：请求结果未知、领取失败或剩余金额到期退回时，怎样保证金额守恒与可核对？**

响应未知时按领取请求 ID 查询已记录结果，不重新随机分配。

- 到期关闭须与领取互斥地转换状态，确认已领取与未结算占用后，再对可退金额生成唯一退款流水。
- 迟到入账与退款不能同时消费同一份余额，定期按明细、余额和资金流水对账，差异进入可追踪的修复流程。

## 8. 文件上传设计

**本节问题**

- [1. 大文件分片上传如何支持并发、断点续传与可靠合并？](#1-大文件分片上传如何支持并发断点续传与可靠合并)
- [2. 文件上传如何防止同名覆盖、路径穿越、伪造类型与未授权下载？](#2-文件上传如何防止同名覆盖路径穿越伪造类型与未授权下载)

### 1. 大文件分片上传如何支持并发、断点续传与可靠合并？

先创建持久化上传任务，服务端生成上传 ID，约定总大小、分片大小、分片数量和校验方式。

- 分片按上传 ID 与编号独立保存，成功记录保存在共享存储；客户端可查询已完成分片并补传。
- 所有分片完整、校验通过且合并或对象存储完成操作成功后，任务才转为完成，并发布最终文件标识。

**追问 1：上传 ID、分片编号、完整性校验与合并条件分别怎样设计？**

分片编号必须处于合法范围，并校验实际长度和内容校验值；上传 ID 绑定用户和目标文件，不能由任意用户复用。

- 合并前确认分片齐全、顺序正确和总大小一致，合并后再验证约定的全文件校验。
- 对象存储的 ETag 不一定是文件 MD5，尤其是分片上传，不能未经协议确认就用于完整性结论。

**追问 2：断点状态保存在单机内存时，重启或路由到其他实例会发生什么？**

单机内存丢失后无法可靠区分已上传、未上传和正在合并，其他实例也看不到这些状态。

- 任务元数据应持久化，分片保存在共享文件或对象存储中；本地内存只作加速缓存。
- 实例重启后根据任务状态、分片对象和校验信息恢复，而不是要求客户端从零上传。

**追问 3：重复上传、缺失分片与并发合并应怎样处理，什么时候才能宣布上传成功？**

同一分片重复上传应按编号和校验值幂等处理，内容冲突则拒绝或显式替换。

- 合并通过版本号或条件状态转换只允许一个有效执行者，失败后可重试并清理临时产物。
- 对外成功的边界是最终对象可访问、元数据提交且权限建立；仅收到最后一个分片不等于文件已完成。

### 2. 文件上传如何防止同名覆盖、路径穿越、伪造类型与未授权下载？

客户端文件名和 Content-Type 都是不可信输入。

- 服务端生成独立对象标识，按允许的类型、大小和实际内容检查文件，禁止把用户路径直接拼接到本地目录。
- 上传与下载均校验资源归属，私有文件通过授权接口或短期签名访问；图片等需要进一步处理时，应在隔离、有资源限制的环境中完成。

**追问 1：客户端文件名、内容类型和存储路径是否都可信，服务端应验证哪些信息？**

文件名只作为展示信息，存储键由服务端生成；拒绝路径跳转、绝对路径和危险扩展名组合。

- 检查文件头、实际解码结果及解压后的体积，不能仅依赖后缀或 MIME 声明。
- 对会执行脚本或主动内容的文件，应隔离域名、使用合适的下载响应头，并避免在应用执行目录内保存。

**追问 2：上传与下载权限怎样关联，如何避免同名覆盖和未授权访问？**

上传 ID、对象键与用户或租户建立明确绑定，写入采用唯一标识和条件创建，避免同名覆盖。

下载时再次校验权限，签名 URL 设置短有效期和最小权限，并明确转发后可被持有者使用的风险。无法猜测的文件名不是完整授权机制。

**追问 3：长期未完成分片、大文件并发和校验失败时，怎样有界清理并限制资源？**

按用户和全局限制文件大小、分片数量、并发数与临时空间；超限尽早拒绝，不先读入全部内存。

- 未完成任务设到期时间，后台分批中止对象存储上传并清理分片，避免一次全量扫描阻塞服务。
- 校验失败的文件不得进入完成状态，清理失败应重试并监控存储增长。

## 9. 数据迁移与扩容

**本节问题**

- [1. 十亿级数据需要不停服迁移时，如何衔接全量、增量同步和流量切换？](#1-十亿级数据需要不停服迁移时如何衔接全量增量同步和流量切换)
- [2. 全量迁移完成后，如何证明新旧数据一致并安全切换读写流量？](#2-全量迁移完成后如何证明新旧数据一致并安全切换读写流量)
- [3. 数百万条数据的导入或导出任务如何避免内存耗尽和长事务？](#3-数百万条数据的导入或导出任务如何避免内存耗尽和长事务)
- [4. 数据库持续有新增和删除时，用 `LIMIT ... OFFSET ...` 分批同步为什么可能漏掉或重复数据？](#4-数据库持续有新增和删除时用-limit--offset--分批同步为什么可能漏掉或重复数据)

### 1. 十亿级数据需要不停服迁移时，如何衔接全量、增量同步和流量切换？

核心是建立一个连续且可恢复的数据边界：从一致性快照读取全量，同时从对应日志位点持续捕获增量；目标端按主键与版本幂等应用。

- 全量完成后追平增量、核对数据和性能，再灰度切读，最后在受控写入边界切换权威写库。
- 普通“双写两个库”并不自动保证不丢、不乱序或可回滚。

**追问 1：怎样划分迁移批次，确定全量读取与增量捕获的衔接位置？**

按稳定主键范围或分片划分全量批次，限制扫描速率和事务时长；使用能够关联一致性快照与 binlog 位点的工具或协议。

必须保证快照之后的变更都在增量链路中，不可先随意扫描再从“当前最新位点”开始，否则扫描过程中发生的变更可能遗漏。

**追问 2：源库持续新增、更新或删除时，怎样避免增量与全量互相覆盖或漏掉变更？**

全量与增量可能重复覆盖同一记录，目标端应按快照阶段和增量顺序应用，或使用可比较版本拒绝旧写入。

- 删除事件也要保留，必要时使用删除标记，防止迟到的全量记录把已删除数据复活。
- 跨表事务若影响业务不变量，应保留事务边界或在切换前验证一致性。

**追问 3：迁移中断后怎样续跑，怎样记录进度和幂等处理？**

为每个全量分片保存最后完成范围，为增量保存已成功应用的日志位点。

- 目标写入和进度提交尽可能处于同一事务；做不到时采用可重复应用方案，宁可重放已完成记录，也不能先推进进度再丢失数据。
- 故障恢复从已确认进度重试，记录坏数据而不是静默跳过。

**追问 4：什么时候具备切换条件，如何灰度切流并保留回滚路径？**

切换前需满足增量延迟达到目标、关键数据校验通过、新库容量与索引验证完成。

- 先影子读或灰度读，再短暂收敛写入、追平位点并切换权威写库，隔离旧写入口。
- 切写后回滚需要反向同步或明确的写入回迁策略，仅把读流量切回旧库可能读到过期数据。

### 2. 全量迁移完成后，如何证明新旧数据一致并安全切换读写流量？

记录数相同只能说明数量一致，不能证明记录内容、删除状态或业务关系一致。

- 应在可比较的快照或增量水位下，按主键范围比较数量与规范化校验和，再定位差异记录，检查金额、状态、外键逻辑等关键约束。
- 切换还必须验证查询结果、索引计划、容量和故障恢复，不只是“复制已经跑完”。

**追问 1：记录数相同是否足以证明内容一致，还需要比较哪些业务字段和约束？**

两库可能一条多、一条少却总数相同，也可能主键相同但金额或状态不同。

- 至少比较主键集合、关键字段、删除标记和业务聚合，确认字符集、时区、小数精度与 NULL 语义一致。
- 持续写入时要按共同位点比较，否则合法的新旧时差会被误报为数据错误。

**追问 2：抽样、校验和与逐条差异修复，各适合什么数据规模与正确性要求？**

抽样适合快速发现问题，但不能证明全量没有差异；分块校验和可缩小范围，需统一排序和字段序列化，避免格式差异或哈希碰撞被误解。资金等关键数据应进行更严格的逐条或约束校验。

修复从权威源按版本重放，不能把过期快照再次覆盖到更新后的目标记录。

**追问 3：灰度切读期间发现差异或新链路变慢，怎样停止放量并回滚？**

立即停止放量，保留请求与差异证据，读流量可先退回仍保持同步的旧路径。

- 若写入尚未切换，回退较简单；若已经切换写库，必须确认旧库追平新写入或暂停相关写入后回迁，防止形成两边独立写入。
- 重新验证数据与性能后再启动灰度，而不是在差异未明时继续扩大范围。

### 3. 数百万条数据的导入或导出任务如何避免内存耗尽和长事务？

将导入导出设计为持久化异步任务，按有限批次处理并记录进度，避免把数百万行一次加载到应用内存。

- 读取使用流式游标或稳定键分页，写入使用有界批次事务和幂等键。
- 任务状态需要区分已受理、处理中、部分失败和完成，并提供结果清单，而不是用一次长 HTTP 请求承担整个过程。

**追问 1：流式读取与分批读取怎样控制内存，批量写入怎样控制事务和下游压力？**

流式读取降低客户端缓冲，但仍可能长期占用连接和事务；稳定键分页则便于释放资源和断点恢复。

每批写入控制行数、字节数、持锁时间与重试成本，根据数据库压力自适应限速。导出也应流式写文件，不在内存中拼接完整结果。

**追问 2：进度、已处理范围与错误记录怎样保存，重启后怎样继续？**

保存任务 ID、输入版本、已处理主键或分片范围、成功失败计数以及错误位置。

- 进度只在批次结果确定后推进；对失败批次允许重放，避免跳过未提交数据。
- 任务领取使用租约或条件更新，失联后可以接管，但新旧执行者仍须通过版本或幂等控制避免重复生效。

**追问 3：一批数据部分成功后重试，怎样避免重复导入并让用户确认最终结果？**

目标记录采用业务唯一键或导入任务加行号的唯一键；每行结果要能追溯，重试只重做未完成或允许幂等覆盖的部分。

- 外部副作用不能只靠数据库 UPSERT 去重，应有独立事件标识。
- 最终向用户返回成功、失败及冲突记录，完成标记只有在全部记录获得明确结果后才能设置。

### 4. 数据库持续有新增和删除时，用 `LIMIT ... OFFSET ...` 分批同步为什么可能漏掉或重复数据？

OFFSET 表示当前结果集跳过多少行，不是一个稳定的数据位置。

- 上一页处理后，如果前面的行被删除，下一页偏移会越过尚未处理的记录；如果前面插入记录，下一页可能再次读到上一页的末尾。
- 稳定主键游标能避免这类位置漂移，但不能单独解决历史记录更新和删除的捕获问题。

**追问 1：在两次 `OFFSET` 查询之间插入或删除前面的记录，会怎样改变后续偏移位置？**

例如按 ID 排序，已处理前 100 行后删除其中一行，再 `OFFSET 100` 会把原第 101 行一起跳过；在前面插入一行则可能把已处理记录重新推到下一页。

没有 ORDER BY 的分页连基本顺序都不保证，更不能用于可靠同步。

**追问 2：使用稳定排序键和游标后，同一时间戳与相同排序值怎样处理？**

使用唯一且稳定的复合排序，例如 `(created_at,id)`，下一页条件为 `created_at > :t OR (created_at = :t AND id > :id)`，方向与排序保持一致。

只用可能重复的时间戳会漏掉同一时刻的其他行；作为游标的排序字段被修改时，也要重新分析重复和遗漏。

**追问 3：同步中断或历史记录更新时，仅靠单调游标是否足够，还需要怎样的增量位点？**

单调 ID 游标只可靠地推进相应有序扫描，旧 ID 的字段更新或删除不会自动出现在后续页中。

- 完整同步需要 CDC 日志位点、变更表或具有明确边界的增量机制，并记录已应用位置。
- 重启后从已确认位点继续，目标端幂等处理重复事件；不能仅保存“最后一次任务运行时间”就宣称无遗漏。

## 要点回顾

- 先定义业务不变量和容量目标：防超卖、金额守恒、身份归属与允许的延迟决定方案边界。
- 处理中、结果未知与最终成功要分别记录：异步受理、调用超时和重复通知不能直接转换成错误的业务终态。
- 恢复链路也是设计的一部分：幂等记录、补偿状态、同步位点和对账验证，决定故障后能否继续推进而不重复生效。
