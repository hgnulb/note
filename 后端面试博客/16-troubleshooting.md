## 1. CPU 与负载排查

**本节问题**

- [4. 容器内服务吞吐下降，但宿主机仍有空闲 CPU，应如何检查资源限制？](#4-容器内服务吞吐下降但宿主机仍有空闲-cpu应如何检查资源限制)

### 1. Java 服务 CPU 飙高时，如何从进程、线程定位到热点代码？

先确定异常时间窗与受影响实例，用 `top`、`pidstat` 确认 CPU 消耗来自目标 Java 进程，再用线程级统计定位热点。

对平台线程，可把操作系统 TID 转为十六进制，与线程转储中的 `nid` 关联；持续 CPU 热点更适合用 JFR、Arthas profiler 或其他采样工具确认。不能仅凭一次线程栈就认定某方法是根因。

**追问 1：先确认进程与热点线程，再怎样把线程标识关联到调用栈或采样结果？**

例如先执行 `top -H -p "$PID"` 或 `pidstat -t -p "$PID" 1`，记录高占用 TID，再用 `printf '%x\n' "$TID"` 转换并查 `jcmd "$PID" Thread.print -l`。

- 容器内外 PID 命名空间可能不同，必须在同一视角关联。
- 虚拟线程不宜简单按一个 OS TID 对应一个业务任务，应结合支持该版本的 JFR 或线程转储。

**追问 2：流量上涨、异常循环和锁竞争分别可能呈现什么证据，单次快照能否定性？**

流量上涨通常伴随完成请求数和业务 CPU 同步增加；异常循环表现为相近热点持续占用且有效吞吐低；锁竞争可能消耗在自旋、同步框架或频繁切换，也可能主要表现为等待而非高 CPU。

比较多个快照和一段时间的采样、QPS、GC 与上下文切换，才能区分。

**追问 3：确定热点后，怎样止损并验证改动有效，而不是只重启进程？**

先按风险限流、降级热点功能、回滚近期变更或隔离异常实例，尽量保留诊断数据。

- 修复后在相同数据与流量下比较 CPU 每请求成本、吞吐、P99 和错误率，并观察是否把瓶颈转移到数据库。
- 重启只能释放现场资源，不能证明异常保留或循环已经消失。

### 2. CPU 热点来自日志格式化、锁竞争还是业务计算，应如何用采样结果区分？

持续采样能估计 CPU 时间主要消耗在哪些调用栈。

- 日志热点常见于格式化、对象序列化或编码，业务计算热点集中在具体算法与数据处理，锁相关消耗则可能出现在自旋和同步路径。
- 但等待锁的时间不一定体现在 CPU profile 中，需要结合锁事件、wall-clock 或线程状态分析。

**追问 1：单次线程快照与持续采样能提供什么不同证据？**

线程快照回答“此刻线程在哪里”，多次采样回答“一段时间内哪些栈反复占用 CPU”。

- CPU profile 不等于请求总耗时，阻塞 I/O 或等待连接可能几乎不消耗 CPU。
- 应按问题选择 CPU、锁、分配或墙钟时间采样，并记录采样窗口和负载。

**追问 2：为什么不应只看某个线程恰好停在哪里？**

线程可能恰好在极短的日志调用或正常等待处被捕获，单次出现不代表累计成本高。

- 需要重复出现频率、样本占比、业务流量及优化前后对照。
- 还要区分包含子调用的总成本与方法自身成本，避免把入口方法的高占比误认为它本身执行昂贵。

### 3. 系统负载高但 CPU 使用率不高时，应如何继续定位？

Linux 平均负载不仅包含可运行任务，也包含某些不可中断睡眠任务，因此磁盘或其他内核资源等待可能使负载升高而 CPU 不忙。

先看任务状态、运行队列、I/O 延迟、内存压力和容器限制，再关联业务；直接加 CPU 可能完全没有帮助。

**追问 1：系统负载统计与 CPU 使用率分别描述什么，为什么可能不同时升高？**

CPU 使用率表示处理器时间花在哪里，load average 表示一段时间内可运行及不可中断任务的平均数量。两者统计口径不同，也可能跨容器和宿主机视角。

高负载低 CPU 常见于 I/O 等待、资源限额或大量 D 状态任务，但不能只凭这组指标直接确定磁盘故障。

**追问 2：应该检查哪些任务状态、磁盘 I/O 与等待信息来区分执行压力和资源等待？**

用 `vmstat 1` 看运行与阻塞队列，`iostat -xz 1` 看设备延迟和队列，`pidstat -d -p "$PID" 1` 找 I/O 进程，结合 `ps -eo pid,tid,stat,wchan:32,comm` 查看等待位置。

再检查内存交换、文件系统或网络存储异常。单个 `%util` 指标对不同设备不能机械解释为容量已经用满。

**追问 3：怎样把系统层证据关联到具体业务或后台任务，而不是直接增加 CPU？**

把异常时间与备份、批量导出、日志刷盘、数据库操作对齐，定位具体进程和调用栈。

- 暂停或限速可疑后台任务后观察负载和延迟是否同步下降，再进一步复现验证。
- 若是存储延迟或配额限制，优化访问方式、资源分配或任务调度比增加计算线程更有效。

### 4. 容器内服务吞吐下降，但宿主机仍有空闲 CPU，应如何检查资源限制？

宿主机有空闲 CPU 不代表容器可以使用它。容器可能受到 cgroup CPU 配额、cpuset 或调度权重约束，应用线程在配额耗尽后被节流。

应从容器实际限制和节流统计出发，结合线程数、运行队列与吞吐分析，而不是按宿主机总核数直接扩线程池。

**追问 1：容器的 CPU 配额、调度权重与实际可用核数分别表示什么？**

CPU 配额限制一个周期内可使用的 CPU 时间，cpuset 限制可运行的处理器集合，权重影响争用时的相对分配，并不等于硬性核数保证。

应用感知的可用处理器数还受运行时版本和容器识别能力影响，应核对实际配置而非仅看机器硬件规格。

**追问 2：怎样结合 CPU throttling、运行队列和应用线程数判断是否受到配额限制？**

在 cgroup v2 中检查 `cpu.max`、`cpu.stat` 和 `cpuset.cpus.effective`，观察 `nr_throttled`、`throttled_usec` 的增量；v1 路径和字段不同。

- 节流增长、可运行线程多而实际 CPU 受限，说明可能触及配额。
- 还需排除锁等待和下游阻塞，不能把所有低吞吐都归因于 throttling。

**追问 3：按照宿主机核数直接配置线程池为什么可能不合适？如何在相同限制下验证调整？**

按宿主机核数设置的 CPU 密集线程池可能远超容器预算，增加上下文切换和配额耗尽后的长尾。

- 用实际 CPU 预算估算，再在相同 limit、相同请求与数据下比较吞吐、节流时间、P99 和错误率。
- 确需更多 CPU 时调整配额或副本，同时确认下游容量允许。

## 2. 内存与 GC 排查

**本节问题**

- [1. Java 进程内存持续增长或发生 `OOM` 时，如何确定内存消耗来自哪里？](#1-java-进程内存持续增长或发生-oom-时如何确定内存消耗来自哪里)
- [2. 频繁 Full GC 应如何排查，而不是直接增大堆内存？](#2-频繁-full-gc-应如何排查而不是直接增大堆内存)
- [3. Young GC 明显变频繁但 Full GC 不多时，应检查哪些分配与晋升指标？](#3-young-gc-明显变频繁但-full-gc-不多时应检查哪些分配与晋升指标)
- [4. 容器中的进程因内存超限被终止，但 Java 堆尚未达到上限，应如何排查？](#4-容器中的进程因内存超限被终止但-java-堆尚未达到上限应如何排查)

### 1. Java 进程内存持续增长或发生 `OOM` 时，如何确定内存消耗来自哪里？

先区分 Java 堆占用、进程 RSS 和容器总内存，确认究竟哪一部分持续增长。

- 结合 GC 日志、对象分配与存活趋势、线程数量及本地内存统计，再选择 heap dump 或采样。
- 堆使用量上涨可能只是缓存预热；多次完整回收后存活集合仍持续无界增长，才更值得怀疑异常保留。

**追问 1：首先怎样区分 Java 堆、堆外、线程栈或其他进程资源的增长？**

用 JVM 堆指标与 GC 日志观察堆，用进程或 cgroup 指标观察总内存，检查直接缓冲区、元空间、线程栈及 native 分配。

支持且已启用 NMT 的 HotSpot 可通过 `jcmd "$PID" VM.native_memory summary` 查看分类，但 NMT 不是所有第三方 native 分配的完整账本。RSS 也可能包含映射页和共享页。

**追问 2：采集堆转储、GC 日志或本地内存信息前，应评估什么运行开销？**

heap dump 可能暂停应用、占用接近堆规模的磁盘并包含敏感业务数据；对象直方图和显式 GC 也可能带来开销。

- 先选有余量的实例、准备安全目录和容量，必要时摘除流量，再采集。
- NMT 通常需要启动时启用，不能临时命令就补出此前所有分配历史。

**追问 3：怎样结合对象数量、引用链和增长趋势区分正常积累与内存泄漏？**

比较多个时间点的对象数量、保留大小和到 GC Roots 的引用链，检查无界 Map、监听器、ThreadLocal、队列和缓存是否超过业务上限。区分短时分配多但可回收与长期被错误引用。

单个对象很大不等于泄漏，关键是生命周期是否合理、增长是否有界。

**追问 4：修复后怎样在相近负载下观察，确认只是延缓 `OOM` 还是消除了保留原因？**

在可比流量下覆盖足够长的运行周期，观察回收后存活量、队列长度和缓存规模能否稳定，并检查 RSS 与堆外趋势。只把堆加大后 OOM 晚发生，不能证明修复。

需验证原错误引用被解除或资源有界，同时确认吞吐、延迟与失败率没有恶化。

### 2. 频繁 Full GC 应如何排查，而不是直接增大堆内存？

- **先收集证据：** 先固定 JDK 和收集器，读取 GC 日志中的实际事件与触发原因，比较回收前后占用、分配速率、晋升和停顿。
- **按触发原因处理：** 若 Full GC 后释放很少，重点看存活集合和泄漏；若短期大量分配导致压力，则关注分配与批次；也可能是显式 GC、元空间或堆外相关触发，不能统一归因为堆太小。

**追问 1：从 GC 日志中先核对触发原因、回收前后使用量和停顿，分别能排除什么？**

触发原因帮助区分空间不足、显式请求或元数据压力；回收收益反映是否存在大量可回收对象；停顿和频率决定用户影响。

- G1 的 Mixed GC 与 Full GC 不能混为一谈。
- 日志应结合应用流量和容器内存，避免根据一个 GC 次数指标判断。

**追问 2：分配过快、存活对象积累、内存泄漏与配置不匹配应怎样区分？**

高分配率但回收后基线稳定通常是短命对象压力；存活基线随业务规模有界增长可能是正常缓存；基线持续无界增长则检查异常引用。

- 堆、年轻代或暂停目标配置不匹配也可能使回收效率差。
- 必须看对象和负载证据，不能只用“频繁”二字判断泄漏。

**追问 3：增大堆、减少分配或调整缓存，分别针对哪一种证据，如何验证？**

堆确实小于合理工作集且机器有余量时可以增大；临时对象多时减少重复转换、缓冲和批次；缓存保留过多时设置容量与过期规则。

分别比较回收后占用、分配率、总 GC 时间、P99 和吞吐，避免只减少次数却让单次停顿或容器 OOM 风险增加。

### 3. Young GC 明显变频繁但 Full GC 不多时，应检查哪些分配与晋升指标？

重点检查每秒分配字节数、Eden 消耗速度、Young GC 间隔和停顿、存活比例、晋升量及老年代增长。

Young GC 多并不必然异常，短命对象多的应用本来就会频繁回收；真正需要优化的是过高 CPU 成本、长尾或晋升压力。还要排查近期序列化、日志和批处理变更。

**追问 1：减少临时对象、调整缓存或批次，与简单扩大年轻代有什么不同收益和风险？**

减少临时对象降低根本分配量；调整批次可限制瞬时峰值；缓存可能减少重复创建，却增加存活集合和老年代压力。

- 扩大年轻代可能减少频率，但增加一次回收工作量，并挤压其他区域。
- G1 等收集器有自适应策略，不宜未经证据强行固定年轻代比例。

### 4. 容器中的进程因内存超限被终止，但 Java 堆尚未达到上限，应如何排查？

容器 OOM Kill 与 JVM 抛出 `OutOfMemoryError` 是不同路径。

- JVM 堆只是容器内存的一部分，直接内存、元空间、线程栈、JIT、native 库和计入 cgroup 的缓存都可能触及总限制。
- 进程被内核终止时，未必有 Java 异常或 heap dump。

**追问 1：如何区分 JVM 抛出 `OOM` 与 cgroup 内存限制触发的进程终止，并核对堆外、线程栈和容器总内存？**

检查 Pod 的终止原因、容器事件及 cgroup `memory.events`、`memory.current`、`memory.max` 等信息，并结合节点内核日志；

- 退出码 137 单独不足以证明 OOM，因为也可能是其他 SIGKILL。
- 比较 `-Xmx` 与总预算，给非堆内存留余量，检查线程数和直接内存增长，不要看到堆未满就排除内存问题。

### 1. 线程大量阻塞或等待时，如何区分正常等待、死锁和慢依赖？

线程 WAITING 或 BLOCKED 只是状态，不直接等于故障。

- 先按调用栈分组，识别空闲线程池等待、业务条件等待、锁竞争及外部依赖等待；再找持锁者或被等待任务，检查它们是否在推进。
- 使用多次线程转储与请求进度联合分析，才能区分正常等待和永久停滞。

**追问 1：哪些线程是业务正常等待，哪些构成锁竞争、循环等待或等待慢依赖？**

空闲工作线程等待任务通常正常；大量业务线程卡在同一个监视器可能是锁竞争；形成相互依赖闭环是死锁；停在连接池或 socket 读取则需要进一步检查资源与下游。

线程池父任务等子任务的饥饿，也可能没有传统监视器死锁报告。

**追问 2：怎样把线程栈中的等待对象与持有者、接口和外部调用关联？**

用带锁信息的 `jcmd "$PID" Thread.print -l` 查等待对象和持有线程，再关联线程名、请求 ID 与业务栈。

- 对数据库或 HTTP 等待，查看连接池借出记录、慢调用和下游会话。
- 当前线程栈不一定保存最初取得锁或连接的位置，需要日志、JFR 或泄漏检测补充。

**追问 3：多次快照与持续监控怎样帮助判断是否真的没有进展？**

间隔采集几次快照，结合完成任务数、锁等待时间和队列变化。

- 相同栈持续存在且完成计数不增长，更支持无进展判断；线程长期停在同一等待函数，也可能只是正常空闲。
- 修复后检查等待链是否消失、吞吐是否恢复，不能只看线程数量变少。

### 2. 根据给定线程池现象，提出排查顺序，并说明每一步要验证什么。

给定同一服务的两组监控观察：

```text
异常前：入口流量稳定；任务队列接近空；任务平均耗时稳定。
异常后：入口流量基本不变；活跃线程数达到池上限；队列持续增长。
同时：应用 CPU 不高；数据库连接获取耗时明显上升。
```

这些现象只用于确定排查方向，不能单独证明是连接泄漏或数据库容量不足。

题设更支持“任务因等待数据库连接而变慢”的方向，尚不能确定连接泄漏。

- 先核对任务提交与完成速率，再采集工作线程栈和连接池 active、idle、pending、借出时长；同时查看数据库正在运行的 SQL、事务与锁等待。
- 确认瓶颈后先限流或减少非核心任务，避免盲目扩线程把等待扩大。

**追问 1：怎样区分接入流量增加、任务变慢与工作线程未得到有效执行？**

入口流量稳定还不代表任务提交量稳定，需检查一次请求是否提交更多任务或发生重试。

若提交量相近、任务耗时增大且栈集中在获取连接，则重点查下游等待；若线程可运行却得不到 CPU，则检查配额与调度。按任务执行、排队和连接等待分别计时。

**追问 2：线程栈与下游连接池同时表现为等待时，直接增大工作线程数可能怎样？**

更多工作线程通常会变成更多连接等待者，增加内存和排队，未必提高完成速率。

- 连接池若已经受数据库容量约束，扩池还可能放大数据库并发。
- 先区分连接未归还、慢 SQL、长事务或池配置过小，再调整相应资源。

**追问 3：临时限流、调整队列与扩容下游，应按什么证据选择，并怎样验证积压开始消退？**

连接泄漏先修关闭路径或隔离实例；数据库慢则优化 SQL、锁或资源；确有余量且池过小时才逐步扩池。临时限制入口与队列长度并拒绝过期任务。

验证应看到完成速率超过进入速率、最老任务等待时间下降及数据库延迟恢复，而不是仅看队列被丢弃后清空。

### 3. 数据库连接池耗尽时，如何区分连接泄漏、慢事务和容量不足？

把应用连接池视图和数据库会话视图对应起来。连接长期借出却没有合理归还路径，怀疑泄漏；连接正在执行慢 SQL 或持有长事务，则是使用时间过长；查询本身正常但并发需求长期超过合理池容量，才考虑容量。三者可能同时存在，扩池不是通用修复。

**追问 1：等待连接、已借出连接和数据库正在执行的事务，应怎样相互对应？**

检查池 active、idle、pending、借用等待和连接占用时长，再用数据库进程、事务及锁等待信息关联连接 ID。

已借出的连接可能在应用中等待 RPC，数据库端显示空闲或事务空闲，因此不能只统计“正在执行 SQL”的会话数。

**追问 2：连接长期不归还、慢 SQL 和长事务，分别可能留下什么证据？**

泄漏常表现为借出数持续不回落、请求结束后连接仍被占用，可用池的泄漏检测和调用栈定位；慢 SQL 对应较长执行时间；长事务可能语句已结束却未提交，仍占连接或锁。

检查异常、超时和提前返回路径是否执行 close 或框架清理。

**追问 3：连接池扩大后数据库可能出现什么反应，怎样避免把上游等待转成下游过载？**

扩池会提高数据库并发，可能增加锁竞争、CPU、I/O 和上下文切换，使单条查询更慢。

- 应先缩短持有时间、修复泄漏并优化 SQL，再按数据库承载能力调整。
- 总连接预算要乘以实例数，滚动发布时额外副本也要计入。

### 4. Go 服务 goroutine 数或内存持续增长时，如何定位未退出任务与被保留对象？

先把 goroutine 数量与并发请求数、请求完成量和内存趋势对齐。

- 采集 goroutine profile 按相同栈聚合，找请求结束后仍留存的 channel、锁或网络等待；用 heap profile 检查这些 goroutine 是否保留大对象。
- 增长与流量同步且结束后回落可能正常，持续累积才需要追查生命周期。

**追问 1：怎样先确认增长来自未退出 goroutine、被引用对象还是正常并发增加？**

比较空闲基线、负载高峰和请求结束后的数量；heap profile 区分累计分配与当前存活。

- 大量等待 goroutine 可能各自保留请求体、缓冲区和闭包，从而造成内存增长。
- 也应检查连接池、缓存与 cgo 内存，不能把所有 RSS 增长都归因于 goroutine 泄漏。

**追问 2：goroutine 快照中的 channel、锁与网络等待，怎样关联到缺失的取消或退出路径？**

检查发送到无人接收的 channel、永不关闭的等待、持锁慢调用、遗漏 context 取消和没有超时的网络操作。

- 确认每个 goroutine 由谁创建、谁负责停止，以及所有阻塞点是否能收到退出信号。
- 调用 `cancel()` 不会自动停止不检查 context 的代码。

**追问 3：修复后应怎样在同样的请求结束、超时和取消条件下验证资源能够回落？**

设计正常完成、客户端取消、下游超时、worker panic 和提前返回等测试，等待合理清理时间后比较 goroutine 与存活内存。重复多轮而不是只运行一次，确保基线不持续上移。

配合 race detector 检查修复是否引入竞态，但无竞态报告不等于无泄漏。

### 5. Go 服务延迟上升但 CPU 不高时，如何区分锁竞争、channel 阻塞与调度等待？

CPU 不高而延迟增加，常见原因是线程或 goroutine 在等待资源。

- **goroutine profile：** goroutine profile 显示当前停在哪里。
- **block profile：** block profile 帮助观察同步阻塞。
- **mutex profile：** mutex profile 反映锁竞争。
- **trace：** 执行 trace 能展示调度、网络等待和 GC 等时间关系。

应按同一时间窗组合证据，不能用 CPU profile 代替所有延迟分析。

**追问 1：mutex、block profile 和 trace 分别适合观察什么，采集开销应怎样控制？**

mutex profile 适合找造成锁等待的持锁路径，block profile 观察 channel、锁等同步阻塞，trace 用于分析 runnable 等待与实际执行。

- 相关采样需按运行时接口启用并控制比例和时长，避免全量高频采集。
- 诊断端点要限制访问，文件可能包含业务路径和敏感上下文。

### 6. Go 服务出现数据竞争时，如何使用 race detector 缩小范围并验证修复？

用 `go test -race ./...` 在支持的平台运行覆盖相关并发路径的测试，必要时对服务使用 `go run -race` 或带 race 的测试构建复现。

报告会指出冲突读写及 goroutine 创建栈，先明确共享变量和同步关系，再通过锁、原子操作、所有权转移或不可变数据修复，而不是只压制报告。

**追问 1：为什么一次运行未报告竞态，不能证明所有执行路径都没有竞态？**

race detector 是动态检测，只能检查实际执行且形成冲突的路径。

- 一次测试没有覆盖特定时序、取消或错误分支，就可能没有报告。
- 应增加并发次数、不同负载和失败场景，并从内存模型证明同步正确；带 race 构建有明显性能和内存开销，不能把其压测数值当成正常性能。

## 4. 接口与网络排查

**本节问题**

- [1. 接口响应变慢但 CPU、内存正常时，应如何逐层拆分耗时？](#1-接口响应变慢但-cpu内存正常时应如何逐层拆分耗时)
- [2. 接口平均耗时变化不大，但 P99 明显恶化时，应该怎样定位长尾请求？](#2-接口平均耗时变化不大但-p99-明显恶化时应该怎样定位长尾请求)
- [3. 用户出现 502 或 504 时，如何定位到代理、连接还是后端服务？](#3-用户出现-502-或-504-时如何定位到代理连接还是后端服务)
- [4. 服务出现大量 `TIME_WAIT` 或 `CLOSE_WAIT` 时，排查方向为什么不同？](#4-服务出现大量-time_wait-或-close_wait-时排查方向为什么不同)
- [5. 流式请求或 WebSocket 已在客户端取消，服务端任务却仍持续执行，应如何排查？](#5-流式请求或-websocket-已在客户端取消服务端任务却仍持续执行应如何排查)

### 1. 接口响应变慢但 CPU、内存正常时，应如何逐层拆分耗时？

先从端到端耗时拆成入口排队、连接获取与建连、应用处理、数据库或 RPC、响应编码与传输。

CPU 和内存正常只能排除部分计算资源问题，不能排除连接池等待、锁等待、网络重传或慢下游。逐段计时后找到主要增量，再继续分解该段。

**追问 1：怎样把总耗时拆成排队、连接、应用处理与下游调用？**

入口代理日志可提供请求及上游耗时，应用埋点记录线程池排队、连接获取、SQL 和 RPC 时间，客户端记录 DNS、连接和首字节时间。

注意指标是否累计、是否包含重试和并行调用，不能直接把相互重叠的子调用耗时相加当成总耗时。

**追问 2：没有完整链路追踪时，怎样补充带请求标识的分段日志和小范围验证？**

给请求生成稳定关联 ID，在关键边界记录开始、结束和结果，使用单调时钟计算本进程耗时。

小范围采样避免大量同步日志拖慢线上，跨机器先校准时间并避免用墙钟差硬算精确网络耗时。通过相同参数的受控请求与日志关联定位。

**追问 3：发现某段慢后，如何继续区分等待资源与实际执行，而不只停在一个“慢接口”名称？**

例如 SQL 调用慢，应再拆连接等待、数据库执行、锁等待和结果读取；RPC 慢要拆连接建立、请求排队、服务端执行和网络返回。

确认资源等待原因后再做池配置或并发调整，不能只把某方法命名为“慢点”就结束分析。

### 2. 接口平均耗时变化不大，但 P99 明显恶化时，应该怎样定位长尾请求？

平均值可能被大量正常请求稀释，而 P99 反映较慢尾部的分布位置。

- 先按接口、参数、实例、时间段和依赖筛选长尾样本，比较它们与正常请求的差异。
- 重点检查短时排队、重试、冷连接、GC、热点锁和下游抖动，而不是只优化平均路径。

**追问 1：为什么平均值可能掩盖少量异常慢请求，应先取哪些长尾样本？**

记录直方图和足够样本数，选择超过目标分位的代表性 Trace 或日志，避免只看一条最慢请求。

- 按实例和请求类别拆分，防止流量构成变化导致聚合指标误导。
- 不能对多个实例的 P99 直接取平均来得到整体 P99。

**追问 2：排队、建连、重试、GC 与下游抖动分别怎样影响时间分布？**

排队接近容量时会非线性增长；新建连接或 TLS 握手使少量请求更慢；重试把多个尝试叠加；GC 或调度暂停会同时影响一批请求；下游抖动可能被扇出调用中的最慢分支放大。

通过同一时间窗的队列、连接、GC 与调用记录验证。

**追问 3：怎样在优化后同时检查吞吐、错误率与尾延迟，防止只改善平均值？**

保持负载、请求分布与成功判定一致，比较完成吞吐、P95/P99、超时率和资源。

- 若通过提前拒绝慢请求降低延迟，应把拒绝计入结果，不能宣布性能无代价改善。
- 还要观察长时间运行和流量突发，避免只在稳定低负载下有效。

### 3. 用户出现 502 或 504 时，如何定位到代理、连接还是后端服务？

- **定位报错层：** 先确认 502 或 504 是哪一层生成，再用请求 ID 和时间关联代理错误日志、访问日志与后端日志。
- **区分故障方向：** 502 常与上游连接失败、异常关闭或无效响应有关，504 常表示网关等待上游超时，但具体行为取决于代理和配置。
- **确认根因：** 状态码只给方向，不能代替证据。

**追问 1：先确认状态码由代理还是应用产生，分别查看哪些对应日志？**

检查入口的 upstream 地址、状态、建连时间、首字节和响应耗时，并确认后端是否收到请求。

- 若应用自己返回同样状态码，代理可能只是转发，应查看真实生成位置。
- 多层代理还需逐层关联，避免把外层超时误归因于最内层服务。

**追问 2：连接失败、上游异常关闭与读取超时，会留下什么不同证据？**

连接拒绝通常说明目标未监听或被主动拒绝；连接超时可能涉及网络、队列或防火墙；上游提前关闭会有对应连接重置或 premature close 记录；读取超时需要检查后端执行和响应进度。

结合套接字状态、服务发布事件与调用栈进一步判断。

**追问 3：调整超时或重试前，怎样评估是否只是延长等待、放大请求或掩盖根因？**

延长超时可能只增加排队和连接占用，重试则可能重复执行已成功的业务。

- 先看后端是否有进展、正常耗时范围和幂等保证，再调整预算。
- 对过载应限流或隔离，对异常发布应回滚；不能用无限超时把错误率暂时藏起来。

### 4. 服务出现大量 `TIME_WAIT` 或 `CLOSE_WAIT` 时，排查方向为什么不同？

TIME_WAIT 通常在主动关闭连接的一方出现，是正常 TCP 生命周期的一部分；CLOSE_WAIT 表示已收到对端关闭，而本地应用尚未完成关闭。

大量 TIME_WAIT 要看短连接频率、连接复用和端口压力；持续增长的 CLOSE_WAIT 更应检查应用关闭资源的路径，不能使用同一套参数调整处理。

**追问 1：如何结合连接建立、关闭和应用资源释放记录定位？**

用 `ss -tanp` 按状态、进程和对端聚合，结合连接创建速率、HTTP 客户端复用、响应体关闭和发布事件。

- TIME_WAIT 多但资源充足可能无需处理；CLOSE_WAIT 长期保留时查连接持有栈和异常清理。
- 修改 TCP 回收参数前需评估协议安全，优先修复不必要建连或资源泄漏。

### 5. 流式请求或 WebSocket 已在客户端取消，服务端任务却仍持续执行，应如何排查？

沿取消链逐层核对：客户端关闭连接是否被网关感知，网关是否向应用传播，应用是否取消工作任务，任务是否把信号传给下游 SDK。

任何一层只停止返回响应而未停止计算，都可能留下后台工作。已提交的业务效果不能靠断开连接自动撤销。

**追问 1：取消信号、线程中断、下游 SDK 与连接关闭各自在哪一层生效？**

连接关闭属于传输层事件，context 取消和线程中断属于应用协作信号，SDK 超时又是独立边界。

- 阻塞代码可能不响应中断，流式读取可能直到下次读写才发现断开。
- 记录各层取消与结束时间，设置下游 deadline、有限并发和 finally/defer 清理，并对无法取消的任务保留状态与恢复机制。

**本节问题**

- [2. 同一 SQL 在测试环境很快、在线上却很慢，应如何比较两边的差异？](#2-同一-sql-在测试环境很快在线上却很慢应如何比较两边的差异)
- [3. 线上出现锁等待或死锁时，如何找到冲突事务与具体 SQL？](#3-线上出现锁等待或死锁时如何找到冲突事务与具体-sql)
- [4. 一次 `ALTER TABLE` 长时间等待，并导致后续请求排队时，应如何寻找阻塞源？](#4-一次-alter-table-长时间等待并导致后续请求排队时应如何寻找阻塞源)
- [5. MySQL 主从复制延迟持续扩大时，如何区分写入压力、传输和从库执行问题？](#5-mysql-主从复制延迟持续扩大时如何区分写入压力传输和从库执行问题)

### 1. SQL 已经使用索引却依然很慢时，如何确认真正瓶颈？

“使用索引”不代表扫描量小，也不代表没有回表、排序和等待。

- 先取得实际 SQL、参数、表结构和索引，再看 EXPLAIN 的访问方式、估算行数、过滤比例和 Extra，结合慢日志与运行等待。
- 安全条件下使用 EXPLAIN ANALYZE 对比实际行数和耗时，但它会真正执行查询，不能在高风险线上语句上随意运行。

**追问 1：索引存在、计划使用了索引与实际扫描很少，为什么是不同的判断？**

索引存在只说明有候选路径；计划使用索引可能是扫描整个索引；真正高效还要看能否按选择性条件定位少量记录。

低区分度过滤、大范围扫描或非覆盖查询的大量回表，都可能让“key 不为空”的查询依然很慢。

**追问 2：扫描量、回表、排序、锁等待和网络传输应怎样分别验证？**

慢日志中的扫描与返回行数、执行计划中的 rows、loops 和排序信息帮助判断工作量；

- 锁等待查 Performance Schema 的 data_lock_waits 等视图；
- 网络与结果集读取看返回字节数、应用读取时间及连接状态。
- Using filesort 不一定落磁盘，覆盖索引也有 MVCC 可见性边界，不能只看一个标签。

**追问 3：优化后的计划对不同参数与数据分布是否仍然有效，怎样进行对照？**

选择典型、极端和高频参数，在接近真实数据分布与并发下比较计划、扫描量、P99 和写入成本。

- 新索引可能改善某条查询，却增加所有写入维护开销。
- 监控统计信息变化和计划回退，不能用一个测试参数证明所有查询都更快。

### 2. 同一 SQL 在测试环境很快、在线上却很慢，应如何比较两边的差异？

- **对齐查询与环境：** 先比较真实 SQL 和绑定参数，再比较表结构、索引、数据库版本、数据量与分布，取得两边的执行计划。
- **核对运行负载：** 随后检查缓存冷热、并发、锁等待、硬件和资源限制。
- **避免错误归因：** 测试表只有几百行时，线上千万行的代价差异不能简单归因于“线上机器慢”。

**追问 1：数据分布、统计信息、参数取值、缓存命中、并发与执行计划，哪些证据最值得先收集？**

优先收集查询条件的实际选择性、估算与实际扫描行数、索引是否相同、排序与临时表情况，以及异常时是否等待锁。

- 再检查 Buffer Pool 命中、磁盘延迟和连接获取时间。
- 保持参数与统计口径一致，避免一个环境查热点缓存、另一个环境做冷数据大范围扫描而直接比较。

### 3. 线上出现锁等待或死锁时，如何找到冲突事务与具体 SQL？

在 MySQL 8.x 中可结合 `performance_schema.data_locks`、`data_lock_waits`、事务视图及 `SHOW ENGINE INNODB STATUS` 找等待关系。

- 死锁日志给出参与事务和冲突锁，锁等待则需要沿等待链找到持有者。
- 当前最慢 SQL 可能只是受害者，真正阻塞源可能是一个已经空闲但尚未提交的事务。

**追问 1：怎样找到等待事务、持锁事务和对应 SQL，而不只看当前最慢的语句？**

先记录等待线程与事务 ID、锁对象和索引，再关联持锁事务、会话及已执行 SQL。

- InnoDB 状态中的最近死锁只覆盖有限现场，应结合错误日志或启用的死锁记录策略保存证据。
- 不要在采集前先杀掉所有会话，否则可能丢失关键时序。

**追问 2：索引选择、更新顺序和事务持续时间怎样共同形成冲突？**

同样业务访问顺序不同可能形成闭环；索引不合适会扩大扫描与锁范围；长事务延长持锁时间。

- 检查唯一键冲突、范围锁、插入意向及元数据锁，区分不同层次。
- 修复可统一顺序、缩短事务、改善索引和条件更新，不是简单降低隔离级别就解决所有问题。

**追问 3：终止会话或重试事务前，要确认什么回滚与幂等边界？**

确认终止的是查询还是连接、整个事务还是单条语句会回滚，评估回滚时间及外部副作用。

- InnoDB 死锁回滚与普通锁等待超时的范围可能不同，需检查配置。
- 业务重试使用原幂等键并重新执行完整必要事务，不能只重发最后一条 SQL 而忽略先前状态。

### 4. 一次 `ALTER TABLE` 长时间等待，并导致后续请求排队时，应如何寻找阻塞源？

- **排查重点：** 重点检查元数据锁等待链。
- **等待链如何形成：** 一个事务访问表后未结束，可能继续持有元数据锁；ALTER TABLE 等待排他性元数据锁时，后续访问也可能排队。
- **定位实际阻塞者：** 通过 `performance_schema.metadata_locks`、会话及事务信息找到最早阻塞者，而不是只看到 ALTER 很慢就增加 DDL 超时。

**追问 1：元数据锁、未结束事务与新请求之间是什么关系？**

元数据锁保护表结构与使用者之间的兼容，和记录上的行锁不同。

- 即使最早事务当前没有执行 SQL，只要事务尚未结束，仍可能阻止 DDL。
- 排队中的 DDL 又可能影响后续请求，所以需要沿“谁等谁”定位，而不是按当前 SQL 耗时简单排序。

**追问 2：终止会话前应评估什么风险？**

终止老事务可能引发较长回滚或业务失败，取消 DDL 则可能更快解除后续排队，但需确认操作阶段和清理成本。

- 先记录事务范围、日志与连接归属，再选择止损动作。
- 在线 DDL 也不意味着完全不需要元数据锁，后续应缩短事务并在受控窗口执行结构变更。

### 5. MySQL 主从复制延迟持续扩大时，如何区分写入压力、传输和从库执行问题？

- **分段观察：** 把复制拆成主库产生 binlog、副本接收日志、副本应用事务三段，分别比较日志位点、GTID 集合和接收、应用线程状态。
- **定位边界：** 延迟持续扩大说明某段长期处理能力不足或受阻，但单个 Seconds_Behind_Source 不能完整描述所有复制状态。
- **异常检查：** 还要确认复制是否报错或暂停。

**追问 1：主库产生变更、日志传输与副本应用分别怎样观察进度？**

通过 `SHOW REPLICA STATUS` 及相关 Performance Schema 复制视图检查接收与应用进度，再结合主库提交速率和网络流量。

接收已追平而应用落后，重点查副本执行；接收也落后则查网络、主库日志发送或副本接收压力。不同版本字段名和并行复制指标有差异。

**追问 2：大事务、资源不足或复制应用受限分别可能表现在哪一段？**

大事务可能长时间占用一个应用工作单元，并在提交前造成延迟突增；副本 CPU、I/O 不足会降低应用速率；锁等待或并行依赖限制会让有多个 worker 也不能有效并行。

检查慢事务、工作线程状态和设备延迟，不能只增加复制线程数。

**追问 3：延迟未消退前，读写分离怎样保护关键写后读请求，并避免扩大故障？**

关键写后读请求可临时读主库，或在明确位点等待副本追上后再读，等待必须有界。

- 普通展示可接受带延迟的读取，但不能用于最新库存或余额判断。
- 切流需考虑主库余量，避免把全部读请求一次性压回主库；先限流、降级并修复复制瓶颈。

## 6. Redis 问题排查

**本节问题**

- [1. Redis 延迟突然升高时，如何区分慢命令、持久化和机器资源问题？](#1-redis-延迟突然升高时如何区分慢命令持久化和机器资源问题)
- [2. Redis 大 key、热 key 或内存增长异常应如何发现和处理？](#2-redis-大-key热-key-或内存增长异常应如何发现和处理)
- [3. Redis 已删除大量 key，为什么进程内存仍可能没有明显下降？](#3-redis-已删除大量-key为什么进程内存仍可能没有明显下降)
- [4. Redis 集群整体不可用时，如何止损并保护数据库？](#4-redis-集群整体不可用时如何止损并保护数据库)
- [5. 缓存命中率突然下降但 Redis 本身没有宕机时，应从哪些方向检查？](#5-缓存命中率突然下降但-redis-本身没有宕机时应从哪些方向检查)

### 1. Redis 延迟突然升高时，如何区分慢命令、持久化和机器资源问题？

- **拆分端到端耗时：** 先比较客户端整体耗时与 Redis 侧命令执行耗时，区分连接池排队、网络传输、服务端排队和命令执行。
- **关联服务端与系统指标：** 结合 SLOWLOG、LATENCY、INFO、客户端缓冲及主机指标，在相同时间窗查慢命令、fork、AOF 刷盘、内存压力和大结果返回。
- **慢日志的观察边界：** SLOWLOG 未出现记录不代表端到端没有延迟。

**追问 1：先判断延迟来自客户端排队、网络还是 Redis 执行，分别需要什么证据？**

客户端记录借连接、发送、等待和读取结果时间；Redis 侧慢日志主要反映命令执行，不包含全部网络和排队。

- 检查连接数、超时重试、网络 RTT 与丢包，再看 Redis 主线程是否被阻塞。
- 大响应的传输与解码也可能让客户端慢而服务端执行很快。

**追问 2：慢命令、持久化和内存或磁盘压力，怎样通过同一时间窗口的指标互相验证？**

慢命令对应执行耗时和命令统计，持久化关注 fork 时间、AOF 延迟及磁盘 I/O，内存关注碎片、淘汰、swap 和写时复制。

将这些峰值与延迟尖峰对齐，再通过限速或受控调整验证因果。不要把所有尖峰都简单归为“Redis 单线程”。

**追问 3：扫描、采样或清理操作会不会进一步加重负载，应怎样控制诊断范围？**

避免在线执行 KEYS、MONITOR 长时间全量观察或一次性读取超大集合。

- 使用限速 SCAN、抽样及只读指标，控制批次和采集时长，必要时在副本或低峰诊断，并理解副本视图可能滞后。
- 清理大对象优先评估 UNLINK 或渐进清理，诊断动作本身也要监控。

### 2. Redis 大 key、热 key 或内存增长异常应如何发现和处理？

大 key 是单对象体积或元素数大，热 key 是访问频率高，整体内存增长则可能来自数量增长、无 TTL、缓冲区或碎片。

- 先按业务和数据类型分别量化，再决定拆分、缓存或清理。
- 不能用一个“热 key”标签解释所有 Redis 性能问题。

**追问 1：如何区分 key 很大、访问很热与整体内存持续增长，而不是只用一个标签概括？**

通过命令与业务访问统计识别热点，使用 `MEMORY USAGE`、集合长度和抽样内容估计对象大小，观察 key 数、过期与淘汰速度解释整体增长。热点可能很小，大集合也可能很少访问。

LFU 相关热度工具依赖相应配置，不能当成任何实例都具备的精确请求计数。

**追问 2：怎样选择不会长时间阻塞线上实例的采样与扫描方式？**

使用有界 SCAN 和每批有限样本，避免对大集合直接全量读取。

内存采样成本也与对象结构有关，应控制频率；访问热度优先来自客户端埋点、代理统计或可用的服务端指标，而不是长期运行高开销全量监控。

**追问 3：拆分、缓存、异步清理与过期策略分别适用于什么证据，处理后怎样验证？**

大对象可按业务边界拆分并避免一次全量读取，读热点可用本地缓存和副本，写热点需要业务分片或合并更新；无界数据增长则修容量和 TTL，历史对象清理可用异步释放。

处理后比较单命令延迟、回源、内存和正确性，避免拆 key 后产生更大批量请求与一致性问题。

### 3. Redis 已删除大量 key，为什么进程内存仍可能没有明显下降？

删除 key 释放的是 Redis 对象的逻辑占用，进程 RSS 不一定立即下降。

内存分配器可能保留空闲页以便复用，存在碎片；UNLINK 的异步释放可能尚未完成；复制、客户端缓冲和持久化子进程也可能占用内存。应区分数据集大小、分配器使用与操作系统驻留量。

**追问 1：如何区分仍存活数据、内存碎片、复制缓冲与持久化子进程开销？**

比较 INFO memory、MEMORY STATS、数据集和分配器指标、lazyfree 待处理数量、客户端及复制缓冲，再检查是否正在 fork 持久化。

- 写时复制可能使父子进程在系统层增加实际占用，但不能把共享页简单重复相加当成真实总内存。
- 确认碎片后再评估主动碎片整理或受控重启，而不是继续盲目删数据。

### 4. Redis 集群整体不可用时，如何止损并保护数据库？

先把缓存不可用与普通未命中分开，限制回源总并发和 QPS，保护数据库及关键业务。

允许旧数据的查询可使用本地快照或明确降级，非核心请求可拒绝；依赖 Redis 作为业务权威状态的操作则需要按一致性要求暂停或走经验证的恢复方案，不能直接当缓存丢了继续写。

**追问 1：怎样先限制回源并保护关键业务，哪些请求可以降级或拒绝？**

入口限流、熔断缓存调用、限制数据库连接等待，并优先保障核心查询。

- 库存、分布式锁等不能随意绕过 Redis 后继续操作，否则可能破坏约束。
- 返回降级或失败时使用明确业务语义，不能把无缓存结果伪装为零库存、零余额或登录成功。

**追问 2：缓存恢复后，怎样避免重试与集中预热同时形成第二次流量洪峰？**

恢复后逐步解除熔断和流量限制，预热只覆盖重要热点并设置速率，合并同 key 回源，给 TTL 增加合理分散。

客户端重试也受预算控制，避免积压请求与预热同时打数据库。不要一次全量清缓存再让所有实例同时回填。

**追问 3：如何验证恢复后的数据、命中率和数据库负载，而不只看连接重新成功？**

确认主从和 Cluster 状态、持久化恢复范围、关键数据版本，再观察命中率、回源量、数据库延迟和错误率。

- 连接成功只说明服务可达，可能仍缺数据或存在旧值。
- 涉及业务状态的 key 需要对账恢复，不能仅用 Redis PING 正常宣布业务完全恢复。

### 5. 缓存命中率突然下降但 Redis 本身没有宕机时，应从哪些方向检查？

先看 keyspace 命中与业务缓存命中是否使用同一口径，再按 key 前缀、接口和实例定位下降范围。

检查近期版本是否改变 key 命名、序列化或查询参数，是否批量过期、淘汰增加、切换到空实例，或者新流量访问了不同数据。Redis 在线不等于缓存内容和路由正确。

**追问 1：`TTL`、淘汰、key 规则变化、批量失效与预热不足，会怎样影响回源流量？**

TTL 集中过期会触发回源峰值，内存淘汰增大会减少热点保留，key 规则变化会让新版本全部访问新键，批量失效或新节点未预热也会降低命中。

- 对应地修正命名与路由、合理预热和容量，限制回源。
- 不能为了提高命中率盲目延长所有 TTL，牺牲数据一致性与内存边界。

## 7. 消息队列问题排查

**本节问题**

- [1. MQ 消息积压时，如何判断瓶颈位于生产、消费逻辑还是下游？](#1-mq-消息积压时如何判断瓶颈位于生产消费逻辑还是下游)
- [2. 业务反馈消息丢失时，如何沿生产、存储和消费记录还原消息链路？](#2-业务反馈消息丢失时如何沿生产存储和消费记录还原消息链路)
- [3. 出现重复消费或消息顺序异常时，如何还原故障发生的时序？](#3-出现重复消费或消息顺序异常时如何还原故障发生的时序)
- [4. MQ 故障后业务准备临时绕过队列，直接调用下游，需要评估哪些风险？](#4-mq-故障后业务准备临时绕过队列直接调用下游需要评估哪些风险)

### 1. MQ 消息积压时，如何判断瓶颈位于生产、消费逻辑还是下游？

先比较生产速率、真正完成业务的消费速率和积压年龄，确认是突发峰值还是持续供大于求。

- 再拆消费阶段的解码、处理、数据库、外部调用和确认时间，检查失败重试与坏消息阻塞。
- 扩消费者只有在分区、队列和下游容量允许时才有效。

**追问 1：先比较生产速率与实际消费速率，再怎样定位慢消费逻辑或慢下游？**

按 Topic、分区和消费组查看 lag 及最老消息年龄，结合消费处理耗时、重试率和下游指标。

- 消费方法调用次数不等于成功完成量，反复处理同一坏消息可能看起来很忙却没有进度。
- 积压若只集中在少数分区，还应检查 key 倾斜和顺序限制。

**追问 2：分区或队列数量、顺序要求与消费者内部并发，分别限制哪一种扩容？**

Kafka 一个消费组内单分区通常同一时刻由一个有效消费者负责，消费者多于分区无法继续提高分区并行；RocketMQ 需区分版本和消费模型；严格同 key 顺序限制内部并发。

消费者转线程池还必须正确提交连续完成位点，不能因后面的消息先完成就跳过前面的失败记录。

**追问 3：清理积压时怎样保护下游并保持重复处理安全，避免只追求队列快速清空？**

清积压使用受控并发与速率，保护数据库和外部配额，优先处理业务有效消息；过期任务按业务规则处理而不是无条件执行。

- 重放必须幂等，不能通过提前 ACK 或跳 offset 假装消除积压。
- 验证完成速率、积压年龄和业务对账，而不只看队列长度。

### 2. 业务反馈消息丢失时，如何沿生产、存储和消费记录还原消息链路？

沿唯一事件 ID 建立证据链：业务是否生成事件、发送是否被确认、Broker 是否存储或已按保留规则清理、消费者是否收到及提交业务、确认是否成功。

用户查不到结果也可能是消费失败、查询副本延迟或视图未更新，不一定是消息真正丢失。先定位断点，再决定补发。

**追问 1：生产记录、`Broker` 存储与消费确认，分别能证明哪一段已经发生？**

本地消息表证明业务事务生成了待发事件，生产者确认说明达到对应 Broker 确认边界，消费日志说明曾收到，业务流水与事务记录证明业务效果已提交。

ACK 或 offset 提交本身不能证明业务正确执行，如果应用先确认后处理，就可能出现真正业务遗漏。

**追问 2：怎样用事件 ID 区分真正未投递、已投递但未处理和已处理但业务查询未看到？**

使用事件 ID、业务 ID、消息 offset 或队列位置关联，而不是只按时间猜测。

- Broker 查不到可能因为保留到期或压缩，不能立即认定未发送；业务已落库但展示未更新，应查缓存和副本。
- 去重表与业务数据也要一起核对，防止只有消费标记没有真实效果。

**追问 3：确认缺失范围后，怎样补发并校验业务幂等，防止二次补偿扩大问题？**

从权威事件记录确定缺失范围，补发仍使用原事件 ID，并在隔离或受控流量下验证幂等。补发后核对业务不变量和未决清单。

不要把整段历史换新 ID 全量重发，也不能对已执行的资金或库存操作重复补偿。

### 3. 出现重复消费或消息顺序异常时，如何还原故障发生的时序？

将同一业务 key 的生产请求、发送重试、Broker 顺序、消费尝试、业务提交和确认时间排成时间线。

- 重复可能来自发送结果未知、消费后确认失败或 Rebalance；乱序可能来自不同分区、重试路径、消费者内部并发或回放。
- 消息系统读出顺序与业务最终提交顺序需要分开分析。

**追问 1：业务标识、确认记录与消费位点分别能提供什么证据？**

事件 ID 识别同一事件，业务 key 和版本识别实体顺序，offset 或队列位置说明消息所在顺序，确认记录说明哪些范围已被认为完成。

- 比较数据库实际提交与状态版本，检查是否先提交较后位点或并行覆盖旧值。
- 修复后验证重启、确认丢失、重平衡和重复投递场景。

### 4. MQ 故障后业务准备临时绕过队列，直接调用下游，需要评估哪些风险？

- **绕过队列的风险：** 绕过 MQ 会移除削峰、缓冲和重试边界，把入口压力直接传给下游；原队列恢复后还可能再次投递同一事件。
- **临时直连的前提：** 因此只有在业务契约、限流和幂等机制明确时才采用临时直连，并记录每个事件实际走过的路径和结果。
- **业务约束：** 不能把“恢复可用”建立在暂时丢消息或重复扣款上。

**追问 1：如何防止请求洪峰、恢复后的消息重放与重复业务效果，并确定可安全补发的范围？**

给直连路径独立的并发与速率上限，共用稳定事件 ID 和业务幂等约束，保存已处理及结果未知记录。

- 恢复时对队列重放进行限速，并依真实业务结果去重，不按“曾调用过”就跳过。
- 需要补发的范围来自权威事件与业务流水对账，而不是凭大致故障时间整段重发。

### 1. 线上故障处理时，如何安排止损、证据保留、定位、修复与验证的顺序？

先确认影响范围和风险，采取可回退的止损动作，同时保留足够证据；再定位根因、实施最小修复并验证。

严重故障不必等全部证据收齐才恢复服务，但也不能无记录地反复重启、清库和改参数。每个动作应有时间、执行人、预期效果和回退条件。

**追问 1：哪些止损动作能够先减少用户影响，哪些操作可能破坏现场或引入新风险？**

限流、关闭非核心功能、回滚近期版本或隔离故障实例通常可先减少影响。

- 清缓存可能把压力转向数据库，杀进程可能丢失未持久任务，切主可能带来数据风险。
- 先判断动作的业务后果，优先选择影响可控、可验证和可回退的措施。

**追问 2：重启、清缓存和改参数之前，应优先保留什么日志、快照与时间线？**

保留异常时间窗、版本与配置、日志、关键指标、调用链和必要线程或内存证据。

- 快照采集要评估停顿、磁盘和敏感信息，不能为了保留现场进一步压垮系统。
- 涉及消息和数据库时记录位点、事务与业务流水，方便恢复后核对。

**追问 3：修复后怎样验证恢复、确认根因并防止相同故障再次出现？**

验证用户成功率、延迟、吞吐、资源和数据不变量恢复，并观察一个足够长的业务周期。

- 根因应能解释时间线、受影响范围和修复效果，不能只写“重启后好了”。
- 补充回归测试、监控、容量边界和操作预案，避免同类问题再次发生。

### 2. QPS、TPS、并发数、响应时间和 P95、P99 分别衡量什么？

| 指标 | 统计口径 |
|---|---|
| QPS 与 TPS | QPS 是每秒请求或查询数，TPS 是每秒完成的事务或业务单元数，两者依统计定义不同 |
| 并发数 | 并发数是在某时刻同时在途的工作量 |
| 响应时间 | 响应时间是一次请求从选定起点到终点的耗时 |
| P95 与 P99 | P95、P99 分别是延迟分布的相应分位点 |

必须先统一口径，才能做容量推算。

**追问 1：它们各自衡量请求量、事务量、在途工作还是延迟分布？**

一次业务事务可能调用多个接口和多条 SQL，因此业务 TPS、接口 QPS 与数据库查询量不能互换。并发是数量，速率是每时间单位数量，延迟是时间。

P99 表示约 99% 的样本不超过该值，不是最慢 1% 请求的平均耗时。

**追问 2：估算并发需求时，应怎样保证流量与耗时采用相同口径？**

稳定系统中可用 Little 定律估算平均在途量 `L = λ × W`，例如每秒 1000 个完成请求、平均耗时 0.2 秒，对应平均约 200 个在途请求。

- 速率和耗时必须覆盖同一系统边界，单位一致，并满足稳定统计条件。
- 不能直接把平均定律中的 W 换成 P99 后宣称得到精确峰值并发。

**追问 3：平均耗时没有明显变化但 P99 恶化时，为什么容量与用户体验仍可能出问题？**

少量很慢请求可能占住连接和线程，放大队列并触发超时重试，平均值仍因大量正常请求而变化不大。高扇出业务尤其受最慢分支影响。

应同时观察分位延迟、积压、超时和拒绝，不能只用平均响应时间判断容量或体验。

### 3. `jstack`、`jmap`、`jstat`、`jcmd` 与 Arthas 分别适合收集哪些 Java 运行证据？

`jstack` 查看线程栈与锁，`jmap` 提供堆相关诊断和转储，`jstat` 观察 JVM 统计，`jcmd` 是支持多种诊断命令的入口，Arthas 可进行在线方法、线程和采样分析。

具体命令能力随 JDK 和工具版本变化，应先用帮助确认，并使用具备权限且与目标环境兼容的工具。

**追问 1：线程快照、堆转储、GC 指标与采样分析分别适合回答什么问题？**

线程转储找等待链与当前执行位置，heap dump 找对象保留及 GC Roots，GC 指标找分配和回收趋势，CPU 或 wall-clock 采样找累计热点和等待。

示例包括 `jcmd "$PID" Thread.print -l`、`jcmd "$PID" GC.heap_info` 和受控的 JFR 记录。工具结果要回答具体假设，而不是收集越多越好。

**追问 2：哪些采集动作可能产生停顿、额外 CPU 或磁盘压力，应怎样选择窗口？**

heap dump、某些直方图命令或显式 GC 可能暂停应用，采样和字节码增强也会增加 CPU 与内存，输出文件占磁盘。

先在低风险实例和有限窗口执行，准备容量及权限，限制 Arthas watch/trace 的匹配范围和次数，避免打印大量敏感参数。

**追问 3：单次快照与持续采样怎样相互补充，怎样用多个证据验证而不是凭一个工具输出定结论？**

单次栈用于定位当下状态，连续快照判断是否推进，采样估计时间占比，指标提供长期趋势。

- 把同一时间窗的 CPU、GC、线程和业务请求关联，再通过受控改动验证。
- 一个线程在数据库驱动里出现，不足以单独证明数据库就是根因。

### 4. Go 的 CPU、heap、goroutine profile 与 trace 分别适合排查什么问题？

CPU profile 反映执行消耗，heap profile 观察分配和存活对象，goroutine profile 显示各协程当前栈，trace 展示调度、阻塞、网络和 GC 的时间关系。

可以通过受保护的 pprof 端点或离线文件采集，采集必须限时、限权，不能把诊断接口公开暴露。

**追问 1：如何用 `pprof` 比较优化前后热点，并区分累计分配与当前存活内存？**

用 `go tool pprof` 的 `top`、`list` 和图形视图查看热点，前后对比需使用相同负载、时长和采样设置。

- `alloc_space` 主要看累计分配，`inuse_space` 看当前保留的堆对象，两者不能混用。
- CPU profile 不包含全部阻塞时间；Go 堆 profile 也不能完整解释 cgo 或所有进程 RSS。

### 5. 如何设计压测并验证一次性能优化或 GC 调整确实有效？

先设定业务成功标准、请求比例、数据规模和流量模型，再控制环境、版本、配置与缓存状态，完成预热后重复测试。

比较的是达到相同成功率和延迟目标时的有效吞吐与资源成本，不是只看压测工具发送了多少请求。优化前后一次短测不足以排除噪声和预热影响。

**追问 1：怎样设定请求比例、数据规模、并发模型、预热与成功判定，保持前后条件可比？**

固定读写比例、热点分布、参数与数据量，说明使用开环到达率还是闭环固定并发，控制数据库和外部依赖条件。

- 代码、JIT、连接池和缓存预热后再采样，保留失败和超时。
- 用多轮及持续运行验证稳定性，避免只挑最好的一轮报告。

**追问 2：吞吐、延迟分位数、错误率和资源开销应怎样同时观察？**

同时记录成功吞吐、错误率、P50/P95/P99、排队、CPU、内存、GC 和下游资源。优化若增加成本或降低一致性，应如实说明。

压测机本身也可能受 CPU、端口或带宽限制，必须确认没有先成为瓶颈。

**追问 3：接近瓶颈时，排队和超时会怎样改变结果，为什么仅比较平均响应时间不够？**

接近饱和时队列增长和超时重试会使系统失稳，平均值可能掩盖长尾或忽略失败请求。

- 闭环压测还可能因请求变慢而自动降低发送速率，隐藏真实过载；需要理解 coordinated omission 等测量偏差。
- 最终应找到满足服务目标的稳定容量，而不是只记录瞬时最高 QPS。

### 6. 系统每天在固定时段变慢或不可用，应如何验证周期性因素？

把多天异常的开始、结束时间与任务调度、备份、报表、日志轮转、流量和资源指标叠加，找共同变化。

再对可疑任务做受控错峰、限速或暂停试验，观察故障是否随之移动或消失。规律相同只是线索，不是因果证明。

**追问 1：定时任务、备份、日志轮转、流量规律与资源争抢如何逐个排查，而不是只增加机器？**

检查 cron、调度平台、数据库备份、大批量过期、批量同步与节点维护记录，结合磁盘、网络、锁等待和 GC。日志轮转还可能涉及文件句柄、压缩和磁盘占用。

先收集证据再逐项改变一个变量，避免同时扩容和改多个参数后无法判断究竟什么有效。

### 7. Elasticsearch 集群变为 yellow 或 red 时，怎样确定受影响的分片与业务请求？

Elasticsearch green 表示主分片和副本都已分配，yellow 表示主分片可用但部分副本未分配，red 表示至少有主分片未分配。

- 先定位受影响索引、分片和请求，而不是只看集群颜色。
- 单节点配置副本也可能长期 yellow，但这仍意味着对应冗余没有实现。

**追问 1：集群颜色分别与哪些主分片或副本分片状态有关，应先定位哪些受影响索引？**

用集群健康、分片列表及索引级状态找到未分配的主副本，确认哪些查询可能返回部分结果或失败、哪些写入受影响。

- red 不一定代表所有索引都不可用，yellow 也不代表可以忽略风险。
- 检查搜索响应的分片失败信息，避免把部分数据当完整结果。

**追问 2：节点丢失、磁盘水位和分配限制分别需要查看什么信息？**

使用 `GET /_cluster/allocation/explain` 查看具体分配拒绝原因，结合节点状态、磁盘水位、分配过滤、机架感知和副本限制。

节点丢失后需确认数据路径和可恢复副本，不能随意强制分配空主分片。磁盘写保护等伴随状态也应按版本和实际原因处理。

**追问 3：怎样在恢复分片时控制资源和查询影响，而不是只追求尽快变绿？**

恢复分片会消耗磁盘、网络和 CPU，应控制恢复并发，保留查询及写入余量，必要时降级非关键负载。先恢复关键主分片和数据正确性，再补齐副本。

强制接受陈旧副本可能造成数据损失，必须有明确证据与授权，不能为了变绿直接覆盖有效历史。

## 要点回顾

- 先建立同一时间窗的证据链：请求量、完成率、调用栈与资源指标要能够相互对应。
- 区分症状和根因：高负载不一定是 CPU 不足，等待连接不一定是泄漏，消息查不到也不一定是 Broker 丢失。
- 修复后同时检查性能与正确性：比较成功吞吐、分位延迟、错误率及业务结果，不能只把队列清空或报警消失当成恢复证明。
