# 十五、微服务：服务通信、治理、安全与发布

### 1. 单体系统应如何决定是否拆分为微服务，并确定服务边界？

是否拆分要看业务边界、团队独立交付、扩展和故障隔离需求，而不是单纯看代码量。

- 先把单体内部模块和数据归属理清，再拆出边界稳定、调用较少、收益明确的能力。
- 微服务增加网络故障、部署治理、观测和跨库一致性成本，规模较小且协作简单的系统可能继续采用模块化单体更合适。

**追问 1：业务耦合、数据归属与团队交付边界分别怎样影响服务边界？**

围绕业务能力和变化频率划分，把需要共同维护强约束的数据放在适当边界内。团队是否能独立负责接口、数据和发布也很重要。

一个服务不应任意读写其他服务的内部表，否则表面拆成多个进程，实际仍紧密耦合。

**追问 2：拆分后新增的远程调用和跨库一致性问题，是否值得当前业务承担？**

拆分后原本一次内存调用变成远程请求，原本一个本地事务可能变成分布式流程。

- 若只是为了技术形式而增加大量细碎 RPC，会放大延迟和故障概率。
- 应对比独立扩容、发布频率和隔离收益，确认收益足以覆盖运维与一致性成本。

**追问 3：怎样先拆一个边界清晰的能力并验证，而不一次性按表数量拆出大量服务？**

先选择通知、独立查询或其他边界清晰模块，定义接口、数据所有权和回滚路径，采用渐进替换。

- 观察发布效率、延迟、错误率与团队协作变化，再决定后续拆分。
- 不要按一张表一个服务或 Controller、Service、DAO 各一个服务进行机械划分。

### 2. DDD 中的限界上下文、聚合和领域服务如何帮助确定服务边界？

限界上下文规定一组业务术语和模型的适用边界，例如订单中的“客户”与风控中的“客户”可以有不同模型；聚合是一组需要共同维护不变量的对象，通常由聚合根控制修改；领域服务表达不自然属于单个实体的业务行为。

它们帮助识别业务边界，但不要求每个聚合都独立部署成微服务。

**追问 1：为什么不能简单按照数据库表或技术分层逐个拆成微服务？**

表是存储结构，技术分层是代码职责，两者都不一定对应独立业务能力。

- 按表拆分可能把同一业务不变量切开，按技术层拆分则会让每次请求跨多个服务。
- 应先识别模型、规则和事务边界，再选择服务部署粒度，避免把 DDD 简化成命名规范。

### 3. 同步 RPC 与异步事件在业务解耦、延迟和故障处理上有什么区别？

同步 RPC 让调用方立即得到结果，流程直观，但受下游延迟和可用性直接影响；异步事件允许生产与消费在时间上解耦，适合削峰和多订阅者，但引入延迟、重复、乱序及状态追踪。

异步不是天然更可靠，仍需可靠投递、幂等消费与失败恢复。

**追问 1：一次业务操作需要立即返回确定结果，与允许异步完成时，应怎样选择？**

必须立即判断库存是否预留、权限是否通过等，可以同步完成关键决策；通知、统计等允许稍后完成的动作适合事件。

- 长流程可返回已受理及任务 ID，通过查询或推送报告最终状态。
- 不能把发送成功的异步事件当成业务已经完成，也不能为了异步化而隐藏确定失败。

### 1. 一次 RPC 如何从客户端接口调用转换为服务端执行，再关联回正确的结果？

RPC 框架用代理把接口调用转换成包含服务、方法、参数和请求 ID 的消息，经服务发现与负载均衡选择实例，再通过连接发送。

服务端解码后路由到对应实现和方法，执行业务并编码结果；客户端根据请求 ID 找到等待的 Future 或回调，完成这次调用。远程调用的失败语义与本地调用不同。

**追问 1：代理怎样把本地方法调用转成请求，服务端怎样找到实际方法？**

客户端代理拦截方法调用，生成协议请求；服务端维护服务与方法的注册表，校验参数后调用实现。

实现可以通过反射、生成代码或其他分派方式完成，不是所有 RPC 都必须使用运行时反射。序列化之前还要明确接口版本与参数类型。

**追问 2：序列化、服务发现、连接管理与响应关联分别放在什么环节？**

服务发现提供候选地址，路由和负载均衡选实例，连接管理负责建立与复用连接，编解码负责消息边界和数据格式。

- 请求 ID 在客户端关联未完成调用，响应携同一 ID 返回。
- 线程模型应把网络事件处理与可能阻塞的业务执行合理隔离。

**追问 3：发生超时或重试时，怎样区分传输结果与业务执行结果？**

超时可能发生在连接、排队、执行或响应返回阶段；客户端失败不等于服务端未执行。

- 重试前检查方法的幂等语义，使用稳定业务请求 ID 和结果查询。
- 传输层请求 ID 只用于一次通信关联，不一定可以代替跨重试的业务幂等键。

### 2. RPC 请求 ID、序列化协议与连接复用如何支持多个并发调用？

连接复用需要协议能划分完整消息，并为并发请求建立关联标识。

客户端维护 `requestId → pending call` 的映射，发送时登记，收到响应后按 ID 完成对应 Future；超时或取消时清理映射，迟到响应按规则忽略或记录。服务端响应顺序不必等于请求顺序。

**追问 1：同一连接上存在多个未完成请求时，客户端如何把响应对应回正确的调用？**

同一连接上多个请求使用不同 ID，响应包含原 ID，不能用“第一个响应对应第一个请求”推断。

- 编码中还应包含长度、类型、状态等必要信息，防止字节流拆包后错位。
- ID 复用必须避免与尚未完成或迟到响应冲突，连接断开时应统一终止相关未完成调用并限制重试。

### 3. Dubbo 的服务调用与扩展机制如何工作？

Dubbo 通过服务引用代理、服务目录、路由、负载均衡、集群容错和协议传输组织调用，服务端再交给导出的服务实现。

- 其扩展机制允许协议、序列化、路由和过滤器等按配置替换。
- 讨论时应固定版本与协议，例如传统 Dubbo 协议与 Triple 不应混成同一条实现路径。

**追问 1：从服务发现、调用路由到返回结果，Dubbo 的主要处理链路是什么？**

注册发现更新服务目录，调用时按路由筛选实例，再由负载均衡选择目标，集群策略决定失败处理，协议层完成编解码与传输，结果沿过滤链返回。

一次重试可能重新选实例，但不能因此假设业务副作用不会重复。

**追问 2：扩展机制如何让协议、路由或其他实现可替换？**

Dubbo SPI 在扩展点接口与命名实现之间建立映射，按配置和调用上下文选择实现，部分扩展还支持自适应选择和包装。

它不只是 JDK ServiceLoader 的另一个名称，框架在扩展选择、依赖注入等方面有自己的机制。扩展代码也要遵守线程安全和生命周期规则。

**追问 3：与 Spring Cloud 比较时，为什么需要先明确是在比较 RPC 能力还是整套服务治理？**

Dubbo 重点提供 RPC 与相关治理能力，Spring Cloud 是多个服务治理项目的组合生态，两者并非完全同层互斥产品。

应按调用协议、跨语言支持、注册发现、限流容错、团队现有设施和运维成本比较，而不是简单回答哪个“性能更好”或“功能更多”。

### 4. Dubbo 的 Failover、Failfast 等容错策略应如何按业务语义选择？

Failover 在失败后重试其他或可用实例，适合允许重试的读操作或已经具备幂等保障的写操作；Failfast 失败立即返回，适合不宜自动重复执行或希望快速暴露错误的操作。

选择还应区分连接失败、执行超时和业务拒绝，不能把所有异常都交给同一重试规则。

**追问 1：失败重试、重试其他实例与同步返回失败，分别适合什么条件？**

确定请求未执行的连接阶段失败相对容易安全重试；执行超时可能已经产生业务效果，应依赖幂等键或查结果。

- 参数错误、权限不足、库存不足等业务失败通常不应换节点继续尝试。
- 重试次数包含关系、总超时和下游容量也要配置，避免多层重试放大故障。

### 5. gRPC 的协议与序列化方式如何影响服务调用？

gRPC 通常以 HTTP/2 承载 RPC，用 Protobuf 定义服务和消息并生成客户端、服务端代码，支持一元调用及流式调用。

HTTP/2 的多路复用和流控有助于并发通信，但业务序列化、线程调度和下游访问仍会形成瓶颈。接口模式与 deadline 应按业务语义设计。

**追问 1：超时设置与服务端任务停止之间，应如何分析实际生效边界？**

deadline 到期会使调用结束并触发取消语义，但框架无法强制停止任意业务代码。

- 服务端应检查取消上下文，向数据库和 HTTP 调用传递剩余预算，并在清理路径释放资源。
- 已经提交的数据库事务不会因为客户端超时自动撤销；不响应取消的调用需设置独立超时和并发隔离。

### 6. 网关、上游服务与下游服务的超时时间应该如何分配？

从用户可接受的总耗时倒推预算，而不是每层都独立设置相同的长超时。

- 入口创建整体 deadline，下游只使用剩余时间，并预留返回、序列化和降级处理空间。
- 建连、读取和任务排队都可能消耗预算，重试也必须包含在总预算内。

**追问 1：建连超时、读取超时与整体 deadline 分别限制哪一段？**

建连超时限制 DNS 之后或包含特定解析阶段的连接建立，具体依客户端实现；读取超时通常约束等待数据的阶段，不一定是整个响应的总时长；整体 deadline 限制整次调用。

持续有少量数据返回的流式请求可能不断满足读取超时，却超出业务整体时限，因此应区分两者。

**追问 2：一个请求还有多个串行或并行下游时，怎样分配剩余预算？**

串行调用的预算总和不能超过剩余总时间；并行调用可以共享同一截止点，但要控制并发和汇总等待。

- 为关键依赖和可降级依赖设置不同策略，剩余预算不足时直接降级或失败。
- 不要在下一层重新从零开始计时，导致请求离开用户视野后仍长时间运行。

**追问 3：上游已经放弃后，下游怎样感知取消并释放资源，不能响应取消的操作又应怎样隔离？**

通过 context、线程中断或框架取消信号通知下游，业务循环和阻塞调用需主动响应。

- 清理连接、关闭响应体、取消未启动任务，并记录未能停止的操作。
- 无法中断的 SDK 用有限线程池、连接池和超时隔离，不能把 Future 已取消等同于真实工作已终止。

### 7. Feign 如何把声明式接口方法转换成远程 HTTP 请求？

Feign 根据接口上的方法和参数元数据建立动态代理，调用时生成 HTTP 请求模板，由编码器序列化参数，再交给 HTTP 客户端发送，响应由解码器转换为返回值或异常。

在 Spring Cloud OpenFeign 中，还可接入服务发现与 LoadBalancer；Feign 本身不是自动具备所有治理能力的远程事务框架。

**追问 1：请求参数、目标实例和返回结果如何衔接？**

路径变量、查询参数、请求头和请求体按接口契约映射。

- 目标可以是固定 URL，也可以是经服务发现选择的实例；具体由集成配置决定。
- 应检查超时、连接复用、错误解码和重试策略，业务幂等仍由服务保证，声明式接口不会消除网络失败的不确定性。

### 8. RESTful API 如何利用资源路径、HTTP 方法、状态码与幂等语义表达业务操作？

RESTful 接口围绕资源表达操作，资源路径描述对象，HTTP 方法表达语义，状态码表示处理结果，响应体提供资源或错误详情。

- 例如创建订单可 POST 到订单集合，查询某订单使用 GET，更新和删除按相应资源语义设计。
- 业务动作复杂时可以显式建模，不必为了形式把一切都硬套成简单 CRUD。

**追问 1：创建、更新、删除和异步受理应如何返回结果？**

创建成功通常返回 201 并提供新资源位置；同步查询或更新可返回 200，成功但无响应体可用 204；异步受理返回 202 并提供状态查询位置。

- 输入错误、权限、冲突和限流使用相应 4xx，系统失败使用合适 5xx。
- 幂等不要求每次响应码完全相同，而是重复操作不增加额外业务效果。

**追问 2：为什么不能仅凭 `GET` 或 POST 名称推断代码安全性？**

GET 的安全语义要求不以修改业务状态为目的，但实现写错仍可能产生副作用；POST 也可能通过幂等键实现业务幂等。方法名称不会自动带来加密、鉴权或防重。

接口应正确实现语义，并配合 TLS、权限校验和业务约束，而不是只换一个 HTTP 方法。

### 9. Protobuf 接口增加、删除或修改字段时，怎样保持新旧服务兼容？

Protobuf 的二进制字段身份主要由字段编号及 wire type 决定，演进时优先新增字段、保留旧字段语义，删除字段后保留其编号和名称，避免复用。

兼容不只看“能否解码”，还要看默认值、存在性、枚举和业务含义是否一致；转成 JSON 后还会有另一套兼容边界。

**追问 1：字段编号与字段名称在编码中的作用有什么区别？为什么不应随意复用已经删除的字段编号？**

字段名称主要用于生成代码和 JSON/Text 格式，编号写入二进制协议。

- 复用删除字段的编号可能把历史数据解释成新字段，甚至造成静默数据错误。
- 应使用 `reserved` 保留编号和必要名称，改变字段类型也不能仅因为编码长度相似就认定安全。

**追问 2：字段缺失、未知字段、默认值与可选字段的存在性，会怎样影响业务判断？**

proto3 隐式存在性的标量字段通常无法区分未设置和显式默认值；需要区分时使用 `optional`、消息包装或明确的更新掩码。

- 未知字段在二进制往返中通常可保留，但逐字段重建或转 JSON 可能丢失。
- 新增枚举值和默认值也应有兼容策略，不能把未知状态误当成成功。

**追问 3：滚动发布时客户端与服务端版本并不一致，如何设计兼容测试与回滚条件？**

测试新客户端对旧服务、旧客户端对新服务，以及消息经中间服务转发后的行为。

- 采用先兼容读取、再逐步写入新字段的发布顺序，保留旧字段直到全部消费者完成迁移。
- 回滚前检查是否已产生旧版本无法理解或会误处理的新状态，必要时停止新写法而非只回退程序包。

## 3. 服务注册与发现

**本节问题**

- [1. 服务名称如何转换为实际可调用的实例地址？](#1-服务名称如何转换为实际可调用的实例地址)
- [2. 注册中心暂时不可用时，已有服务调用是否一定中断？](#2-注册中心暂时不可用时已有服务调用是否一定中断)
- [3. Nacos、Eureka 与 ZooKeeper 作为注册中心，应如何根据业务需求选型？](#3-nacoseureka-与-zookeeper-作为注册中心应如何根据业务需求选型)
- [4. Nacos 的临时实例、持久实例与命名空间各解决什么问题？](#4-nacos-的临时实例持久实例与命名空间各解决什么问题)
- [5. Eureka 的自我保护机制为什么可能暂时保留不可达实例？](#5-eureka-的自我保护机制为什么可能暂时保留不可达实例)

### 1. 服务名称如何转换为实际可调用的实例地址？

服务提供者把服务名、实例地址和元数据注册到注册中心，消费者订阅或拉取地址列表，在调用时按路由和负载均衡选择实例。

健康检查与租约用于判断实例是否仍可接收请求，但列表会有传播延迟，因此客户端还需要处理失效地址和请求超时。

**追问 1：注册、发现与健康检查分别完成什么工作？**

注册建立服务到实例的映射，发现把映射提供给调用方，健康检查更新实例可用状态。

健康既可能由客户端心跳上报，也可能由服务端主动探测或连接状态判断，具体依组件及版本。进程在线与业务就绪也应区分。

**追问 2：实例上线、主动下线和意外退出时，地址列表应如何变化？**

上线应在初始化完成并就绪后加入可选列表；主动下线先标记不再接收新流量，再排空存量请求；意外退出由心跳或检查超时剔除。

客户端缓存和长连接可能仍保留旧实例，不能假设注册中心一更新所有请求立即停止。

### 2. 注册中心暂时不可用时，已有服务调用是否一定中断？

不一定。消费者已经缓存了仍可用的实例地址，而且数据面不依赖每次实时查询注册中心时，可以继续调用。受影响的是地址更新、故障剔除和新实例发现。

缓存只能维持已知拓扑，不能长期代替注册中心的健康状态与版本变化。

**追问 1：客户端已经缓存的地址列表能否继续使用，需要哪些前提？**

前提是地址仍有效、网络可达、服务兼容且客户端没有在注册中心不可用时主动清空列表。

- 连接池和本地缓存可降低控制面故障对数据面的即时影响。
- 实例大规模重建、地址改变或安全策略要求实时校验时，这种维持能力会明显下降。

**追问 2：新实例加入和旧实例失效时，缓存无法更新会分别产生什么风险？**

新实例无法被发现会降低扩容效果；旧实例无法及时剔除会增加失败和超时。若所有缓存地址都失效，调用仍会中断。

长时间使用旧列表还可能忽略版本、权重和地域调整，因此需要缓存年龄、失败率和服务容量监控。

**追问 3：怎样通过健康检查、限时重试和降级降低影响，而不是简单认定所有请求都会中断？**

客户端对连续失败实例暂时摘除，有限且符合幂等语义地选择其他实例，设置合理超时，并对非核心调用降级。注册恢复后重新同步完整列表。

不要无限重试所有旧地址，也不要因为注册中心短时不可达就主动让所有健康服务停机。

### 3. Nacos、Eureka 与 ZooKeeper 作为注册中心，应如何根据业务需求选型？

应比较服务模型、读写与通知语义、故障时行为、客户端成熟度及运维成本。

- ZooKeeper 基于会话和一致性协调，适合较强协调需求；Eureka 偏服务发现和可用性取向；Nacos 结合服务发现与配置管理，并对不同实例类型采用不同机制。
- 不能用一句“某产品永远 CP 或 AP”代替具体部署分析。

**追问 1：一致性、故障行为和服务发现机制需要比较哪些方面？**

确认注册写入如何确认、地址变化怎样传播、断线后缓存能否继续用、失效实例何时剔除，以及分区时哪些操作停止。

- 还要比较环境隔离、健康检查、扩容规模、权限和现有框架集成。
- 配置中心与服务发现虽然可能由同一产品提供，但两种业务对一致性的需求并不完全相同。

### 4. Nacos 的临时实例、持久实例与命名空间各解决什么问题？

临时实例适合随进程或客户端连接生命周期变化的服务注册，失去有效存活条件后会被清理；持久实例的注册信息需要更显式管理，健康状态与是否保留记录是不同概念。

命名空间用于隔离环境或逻辑范围，但是否形成安全边界还依赖鉴权和权限配置。

**追问 1：不同环境和租户怎样隔离服务，健康检查失效时怎样理解实例是否应该被剔除？**

生产、测试和不同租户应使用明确的命名空间、分组及访问权限，不能只依赖相同服务名下的标签。

- Nacos 不同版本对心跳、连接存活和主动健康检查的实现存在差异，应以实际版本确认。
- 临时实例失活后的删除与持久实例被标记不健康，不应被当成同一行为；保留记录也不等于仍可被正常选用。

### 5. Eureka 的自我保护机制为什么可能暂时保留不可达实例？

Eureka 自我保护是在续约比例异常下降时，避免把大范围网络故障误判为所有实例同时死亡，从而暂缓自动剔除。

- 代价是列表可能保留实际已经不可用的实例，因此调用方仍需要超时、容错和健康反馈。
- 自我保护是在错误剔除和过期地址之间取舍，不是保证所有实例始终健康。

**追问 1：网络抖动与实例真正退出怎样区分？**

仅凭心跳丢失无法完美区分网络分区和进程退出，需要结合实例主动注销、节点监控、网络状况和持续失败证据。

- 主动下线应走明确注销流程，异常退出依赖租约与检测。
- 不要为了列表看起来“干净”而在网络抖动时批量删除所有实例。

**追问 2：客户端负载均衡如何降低过期地址对调用的影响？**

客户端设置有限超时，对失败实例暂时降低权重或摘除，再按幂等条件选择其他实例，并周期性恢复探测。

- 重试仍受总 deadline 和预算限制，不能一次请求遍历所有失效节点直到资源耗尽。
- 注册中心恢复后及时刷新缓存并观察失败比例是否回落。

## 4. 配置中心

**本节问题**

- [1. 配置中心如何将变更传递到运行中的服务，并在自身不可用时维持业务运行？](#1-配置中心如何将变更传递到运行中的服务并在自身不可用时维持业务运行)
- [2. 配置变更如何支持版本管理、灰度生效、回滚和审计？](#2-配置变更如何支持版本管理灰度生效回滚和审计)

### 1. 配置中心如何将变更传递到运行中的服务，并在自身不可用时维持业务运行？

配置中心负责保存版本化配置并通知客户端变更；客户端拉取完整版本、校验后再原子切换到新配置。

- 配置中心暂时不可用时，已运行实例可继续使用最近一次有效配置，新实例能否启动取决于是否有可信本地快照及业务安全要求。
- 配置更新不应直接逐字段修改共享对象，导致请求观察到半新半旧状态。

**追问 1：配置变化怎样通知实例，实例怎样得到一个完整可用的新版本？**

通知可以采用推送、长轮询或 Watch，但通知只表示有变化，实例仍需获得完整配置及版本。

先在临时对象中解析、校验依赖关系，必要时准备新连接池或资源，再通过原子引用或受控切换发布。失败则继续使用旧的有效版本，并报告未生效原因。

**追问 2：配置中心不可用时，本地缓存与已有对象能维持什么能力？**

本地内存与磁盘快照可维持原有行为，但不能获得最新撤销、路由或安全策略。

- 对于必须读取最新配置才能安全运行的操作，应选择拒绝或受限模式。
- 新实例使用快照启动时要检查版本、完整性和有效期，不能把任意过期配置当成可长期接受。

**追问 3：动态更新失败或只更新了一部分时，怎样回滚并保持相关配置的一致性？**

把相关配置作为同一版本快照发布，实例只在整体校验成功后切换；资源创建失败则保留旧资源。

- 回滚发布一个明确的新版本或恢复已知有效快照，并确认每个实例实际加载版本。
- 动态配置无法自动保证跨所有实例瞬时一致，强关联变更还需协议兼容或分阶段发布。

### 2. 配置变更如何支持版本管理、灰度生效、回滚和审计？

- **版本与审计：** 每次配置变更应有不可变版本、内容摘要、变更人、原因和审批记录。
- **灰度验证：** 灰度按实例、用户或环境逐步生效，观察错误率、延迟和资源指标，再扩大范围。
- **回滚确认：** 回滚应恢复一个已验证版本，并核对实际生效结果；修改控制台内容不等于全部进程已经加载。

**追问 1：多个相关配置项必须一致生效时，怎样避免实例只加载了一半配置？**

将相关字段封装成一个版本化配置对象，完整下载与校验后一次切换，避免分别更新 URL、凭据和超时等字段。

- 跨实例切换仍会存在版本混用，应让新旧配置在过渡期间兼容，或使用明确的激活版本和协调协议。
- 涉及不可逆数据写入时，回滚配置还要考虑已经产生的业务状态。

## 5. 网关与负载均衡

**本节问题**

- [1. 反向代理与 API 网关如何划分流量入口的职责？](#1-反向代理与-api-网关如何划分流量入口的职责)
- [2. Nginx 的 master、worker 与事件驱动模型如何协作处理请求？](#2-nginx-的-masterworker-与事件驱动模型如何协作处理请求)
- [3. 客户端与服务端负载均衡分别如何选择目标实例？](#3-客户端与服务端负载均衡分别如何选择目标实例)
- [4. Spring Cloud Gateway 的路由、断言与过滤器如何组成请求链路？](#4-spring-cloud-gateway-的路由断言与过滤器如何组成请求链路)

### 1. 反向代理与 API 网关如何划分流量入口的职责？

反向代理主要负责连接转发、TLS 终止、负载均衡和基础流量处理；API 网关还常承担统一认证、路由、限流、协议适配和请求策略。两者能力可能重叠，重点是明确职责和失败边界。

网关应保持轻量，不能把所有业务规则集中到一个新的单点。

**追问 1：哪些通用能力适合放在入口，哪些业务逻辑不应集中到网关？**

通用鉴权、流量限制、追踪上下文、路径改写和请求大小限制适合入口统一处理；订单状态、库存扣减和资源级数据权限仍应由业务服务落实。

不能因为网关验证过用户就省略内部授权，也不应在网关中执行大量跨服务聚合和数据库事务，扩大故障影响面。

### 2. Nginx 的 master、worker 与事件驱动模型如何协作处理请求？

Nginx master 负责读取配置、管理 worker 和处理重载，worker 使用事件驱动方式处理客户端与上游连接。

- 一个 worker 可以管理大量连接，不是每个请求创建一个线程。
- 实际容量受文件描述符、连接限制、内存、网络和上游处理能力共同约束，反向代理的一次请求可能同时占用客户端与上游连接。

**追问 1：master、worker 与事件循环分别负责哪类工作？**

master 通常不直接处理正常业务请求，worker 负责 accept、网络读写、协议解析和转发。

- 事件循环根据就绪事件推进连接，慢连接不必独占一个线程，但大响应、复杂处理和阻塞模块仍会消耗资源。
- 平滑重载通常启动新 worker 并让旧 worker 完成存量工作。

**追问 2：下游连接复用、超时、worker 数量和连接上限怎样共同影响容量？**

worker 数量应结合 CPU 和工作负载，`worker_connections` 与进程文件描述符上限共同约束连接容量；上游 keepalive 减少重复建连，但也占用连接资源。连接、读写和空闲超时限制无效等待。

不能简单把 worker 数乘连接数当成可承受的业务 QPS。

**追问 3：后端持续变慢时，为什么仅提高代理连接上限可能扩大排队与资源占用？**

后端变慢后，代理中的在途请求和连接会累积，提高上限只会延后拒绝并增加内存、排队和超时。

- 应限制入口与上游并发、合理超时、隔离故障服务，并从下游瓶颈入手修复。
- 容量规划应观察排队时间与尾延迟，而不是只看连接是否还能建立。

### 3. 客户端与服务端负载均衡分别如何选择目标实例？

客户端负载均衡由调用方根据本地实例列表选择目标；服务端负载均衡由代理或负载均衡器接收请求后转发。

前者减少集中代理路径但需要每个客户端具备发现和治理能力，后者集中管理流量但增加中间层容量和故障点。两者也可以分层组合使用。

**追问 1：轮询、随机与哈希策略在均衡性和业务约束上有什么取舍？**

轮询简单，适合实例能力接近的情况；随机实现成本低，大量请求下可较均匀分散，但短窗口可能偏斜；哈希可把同一 key 路由到固定实例，便于会话或缓存局部性，却容易受到热点影响。

实际可结合权重、最少活跃请求或延迟反馈，避免仅按请求数量判断负载。

### 4. Spring Cloud Gateway 的路由、断言与过滤器如何组成请求链路？

以 Spring Cloud Gateway 的响应式 Server WebFlux 形态为例，路由定义目标 URI，断言判断请求是否匹配，过滤器链在调用下游前后执行逻辑。

- 请求先匹配路由，再经过按顺序组织的全局与路由过滤器，完成鉴权、改写、限流及转发。
- Gateway 也存在其他运行形态，不能把所有版本都概括为同一线程模型。

**追问 1：鉴权、路径改写、限流和调用下游分别在什么位置执行？**

鉴权和限流通常在发送下游前完成，路径、请求头改写影响实际转发请求；响应过滤用于补充头部、记录耗时或转换结果。

- 过滤器顺序决定前后执行关系，重试过滤器还会改变调用次数。
- 复杂业务授权仍应在目标服务验证，不能只依赖入口过滤。

**追问 2：网关使用阻塞代码时有什么风险？**

在响应式事件循环中执行阻塞数据库或外部 SDK 调用，会占住处理多个连接的线程，放大延迟。

- 应优先使用非阻塞客户端，确需阻塞时转交有界执行器并限制并发，而不是无限增加线程。
- 即使接口返回 Mono，也不代表内部代码自动变成非阻塞。

## 6. 限流、熔断与降级

**本节问题**

- [1. 限流、熔断和降级分别解决什么问题？](#1-限流熔断和降级分别解决什么问题)
- [2. 固定窗口、滑动窗口、漏桶与令牌桶应如何按流量特征选择？](#2-固定窗口滑动窗口漏桶与令牌桶应如何按流量特征选择)
- [3. 限流、熔断、降级和线程池隔离如何配合，避免慢下游拖垮调用链？](#3-限流熔断降级和线程池隔离如何配合避免慢下游拖垮调用链)
- [4. 如何通过舱壁隔离让某个慢依赖或非核心接口不拖垮所有请求？](#4-如何通过舱壁隔离让某个慢依赖或非核心接口不拖垮所有请求)
- [5. 熔断器的关闭、打开与半开状态如何切换？](#5-熔断器的关闭打开与半开状态如何切换)
- [6. Sentinel 的资源、规则与调用统计如何参与限流和熔断判断？](#6-sentinel-的资源规则与调用统计如何参与限流和熔断判断)

### 1. 限流、熔断和降级分别解决什么问题？

限流控制进入系统的请求数量或速率，避免超过容量；熔断依据下游失败或慢调用状态暂时停止调用，防止故障扩散；降级用较低成本或较少功能的结果替代原能力。

三者可以协作，但不能把返回任意默认值都当成正确的业务降级。

**追问 1：流量突增、下游持续超时与非核心功能出错时，各该优先使用什么手段？**

流量突增先限流并保护关键资源；下游持续超时可熔断，减少无效等待；非核心推荐或统计失败可降级。

库存、支付等关键判断不能随意返回成功或虚构数据，应明确拒绝、稍后重试或处理中状态。降级结果应有监控，避免长期掩盖故障。

### 2. 固定窗口、滑动窗口、漏桶与令牌桶应如何按流量特征选择？

固定窗口按离散周期计数，简单但边界可能出现集中突发；滑动窗口按最近一段时间控制数量，约束更平滑但状态和计算成本更高；漏桶以稳定速度排出，适合整形但会排队或丢弃；令牌桶按速率补充令牌，允许容量范围内的短时突发。

先明确业务约束是速率、并发还是周期配额。

**追问 1：固定窗口、滑动窗口、漏桶和令牌桶怎样处理突发流量与持续速率？**

固定窗口在前后两个窗口交界可能连续放行接近两倍限额；滑动窗口覆盖当前时间之前的连续区间，减少边界问题。

漏桶的输出速率稳定，积压超过桶容量需要拒绝；令牌桶积累的令牌允许一批请求立即通过，但长期平均受补充速率限制。

**追问 2：允许短时突发、要求均匀输出与限制固定周期总量，分别怎样选型？**

允许短时突发可用令牌桶，要求匀速调用脆弱下游可用漏桶或有界排队，严格“最近 60 秒不超过 N 次”可用滑动日志或近似滑动计数。按自然日的业务额度可用固定周期计数。

每种方案都要另外考虑请求耗时和在途并发，速率限制不是连接池容量控制。

**追问 3：单机扩为多实例后，局部额度如何变成全局约束，协调服务故障时怎样取舍？**

每实例都给全局额度会随实例数放大，需要集中原子计数、全局令牌服务或分配可回收的局部配额。

- 协调服务不可用时，严格额度可选择拒绝，普通防护可退为保守本地限流；必须明确可能超发的上界。
- 按 key 分片还要处理热点、时钟和重试的计数语义。

### 3. 限流、熔断、降级和线程池隔离如何配合，避免慢下游拖垮调用链？

先给调用设置合理超时和并发上限，再按依赖隔离线程或连接资源；错误率或慢调用持续超过阈值时熔断，非核心功能返回明确的降级结果，入口限流防止恢复期间流量再次压垮下游。

保护机制不能只依赖一个总线程池，慢依赖应尽量不占满核心业务资源。

**追问 1：熔断恢复、超时和重试之间应如何协调？**

超时要覆盖实际执行与排队，重试只能在剩余预算和幂等条件内进行。

- 熔断打开时不要让重试绕过保护；半开探测只放少量请求，成功后渐进恢复。
- 降级路径本身也需限流与隔离，避免故障时所有请求同时访问另一个没有容量的后备系统。

### 4. 如何通过舱壁隔离让某个慢依赖或非核心接口不拖垮所有请求？

舱壁隔离把不同依赖或业务等级使用的有限资源分开，一个慢依赖只能耗尽自己的额度，而不能占满整个服务的线程、连接和队列。

隔离可以是线程池、信号量、连接池或进程级，粒度应与故障域和业务优先级匹配，不是每个接口都必须创建独立大线程池。

**追问 1：不同依赖或接口共享执行资源时，一个慢依赖怎样耗尽整个服务？**

共享线程池里大量任务等待慢下游时，其他本来很快的任务也无法取得线程；共享连接池或无界队列同样可能耗尽内存。请求超时后任务仍运行会进一步放大占用。

应观察每个依赖的在途数量、等待时长和拒绝率，找到真正的共享瓶颈。

**追问 2：线程池、信号量与连接池隔离分别限制什么资源和等待？**

线程池隔离限制执行线程和排队，但增加调度开销；信号量限制同时进入的调用数，不另建线程，阻塞任务仍占用原调用线程；连接池限制实际连接资源，但入口仍需控制等待。三者可配合使用，并设置有界等待和取消路径。

**追问 3：隔离池划分过细会带来什么闲置或管理成本，怎样结合负载调整？**

过细隔离会造成某些池闲置、另一些池拥塞，并增加线程数、配置和监控复杂度。

- 可按关键依赖、业务等级或成本分组，使用共享总预算加分组额度，在负载变化时受控调整。
- 调整不能突破下游总容量，也不能因局部资源空闲就取消关键隔离边界。

### 5. 熔断器的关闭、打开与半开状态如何切换？

关闭状态正常放行并统计调用；达到失败率、慢调用比例等条件后进入打开状态，快速拒绝或降级；经过冷却期后进入半开，允许有限探测；探测满足恢复条件再关闭，失败则重新打开。

熔断器观察的是一段窗口内的行为，不应由一次偶发错误随意永久切断服务。

**追问 1：什么信号使熔断器从关闭转为打开，为什么不能永久拒绝所有请求？**

触发条件通常包含最小请求样本数及失败或慢调用比例，避免低流量下单个异常造成误判。

- 永久拒绝无法发现下游已恢复，所以需要冷却和受控探测。
- 哪些错误计入失败应按语义定义，用户参数错误一般不应作为下游故障统计。

**追问 2：半开阶段怎样限制恢复探测，成功或失败后如何进入下一状态？**

半开只允许少量并发或固定次数的探测，其余请求继续快速失败或降级。

- 探测成功后逐步恢复正常流量，失败则延长或重新开始打开期。
- 探测本身需要超时，不能因为几个探测永久挂起让熔断器卡住。

**追问 3：超时、重试与探测流量怎样协调，避免下游刚恢复就再次过载？**

重试应计入实际下游流量和失败统计，不能对每次拒绝立即再次重试。

- 探测流量与正常请求共享受控资源，恢复时逐步提高额度并观察延迟和错误率。
- 入口瞬时洪峰仍需限流，熔断恢复不等于下游突然具备所有积压请求的处理能力。

### 6. Sentinel 的资源、规则与调用统计如何参与限流和熔断判断？

Sentinel 把需要保护的方法或调用定义为资源，进入和退出资源时记录通过量、并发、响应时间及异常等指标，再按流控、熔断等规则决定放行或阻断。

保护是否有效取决于资源边界、统计口径、规则持久化及异常上报，不能只引入依赖就认为所有调用受到保护。

**追问 1：单机限流与集群限流怎样区别？**

单机规则通常约束当前实例，扩容后总通过量可能增加；集群流控需要全局额度协调或相应的集群模式。

应明确规则类型、统计维度和 token 服务故障时的回退行为。单机阈值相同并不等于全局阈值固定。

**追问 2：配置阈值时应如何结合下游容量，而不是只看本机流量？**

根据下游连接数、吞吐、尾延迟和可接受排队制定阈值，再结合调用放大倍数换算上游额度。多个上游共享同一下游时，不能各自分配全部容量。

规则变更通过压测、灰度和监控验证，区分阻断异常与业务异常，避免降级掩盖真实故障。

## 7. 认证与授权

**本节问题**

- [1. 微服务如何统一校验身份和访问权限，JWT 与服务端 Session 方案如何取舍？](#1-微服务如何统一校验身份和访问权限jwt-与服务端-session-方案如何取舍)
- [2. OAuth 2.0 解决的是哪类授权问题？它与用户登录认证有什么区别？](#2-oauth-20-解决的是哪类授权问题它与用户登录认证有什么区别)
- [3. JWT 的签名、加密与 Base64url 编码分别提供什么能力？](#3-jwt-的签名加密与-base64url-编码分别提供什么能力)

### 1. 微服务如何统一校验身份和访问权限，JWT 与服务端 Session 方案如何取舍？

Session 方案在服务端保存会话状态，客户端持有会话标识；JWT 方案可以让服务根据签名和声明离线验证身份，但撤销和权限变化可能需要额外状态查询。两者都需要 TLS、安全凭据存储和服务端授权。

选择取决于撤销时效、跨服务验证成本和运维复杂度，不是 JWT 天然比 Session 安全。

**追问 1：JWT 与服务端 Session 分别把身份状态放在哪里，验证时需要哪些信息？**

Session 校验通常查询共享存储中的有效会话，JWT 校验需要可信密钥、允许的算法及签发者、受众、有效期等声明。

- JWT 可包含身份声明但不宜保存敏感明文；其自包含也不意味着权限永久有效。
- 访问 Token、刷新 Token 和会话状态应分别管理。

**追问 2：网关通过认证后，服务内是否还需要校验操作与数据权限？**

需要。网关验证身份不能替代服务内的动作权限与数据归属校验，内部调用也可能绕过网关。

- 下游应验证可信身份传递来源，检查用户或服务是否有权操作目标资源。
- 不能直接信任来自客户端的用户 ID、角色头或租户头。

**追问 3：退出、撤销或凭据被盗时，两种方案怎样控制失效范围与生效时间？**

Session 删除或版本更新后可较快失效，但缓存仍带来传播窗口；离线 JWT 一般会持续有效到过期，除非检查撤销表或会话版本。

- 退出应处理刷新凭据和客户端存储，被盗时还需撤销相关设备会话、轮换受影响凭据并调查使用记录。
- 签名验证无法识别正常密钥签发后被盗的 Token。

### 2. OAuth 2.0 解决的是哪类授权问题？它与用户登录认证有什么区别？

OAuth 2.0 主要解决客户端在用户授权下访问资源的问题，不是单独的用户身份认证协议。

- 授权码流程中，用户在授权服务器完成认证与授权，客户端得到短期授权码，再向令牌端点换取访问令牌，资源服务器验证令牌后按 scope 和策略提供访问。
- 需要标准化登录身份时，通常使用 OpenID Connect 等明确的身份协议。

**追问 1：授权码流程中，用户、客户端、授权服务与资源服务分别交换什么？**

浏览器把用户导向授权服务器，授权服务器把授权码重定向到已登记的客户端地址；客户端在后端或适当的安全环境中用授权码及 PKCE verifier 等换取 Token，之后向资源服务器请求资源。

授权码不是访问令牌，不能直接拿它调用资源接口；刷新凭据也不应当成普通 API 的访问凭据。

**追问 2：授权与用户登录认证为什么不是同一个概念，身份信息应由什么约定确认？**

授权回答“客户端能访问什么”，认证回答“当前用户是谁”。

- 不能随意解析一个访问令牌就把其中任意字段当成标准登录身份。
- OIDC 的 ID Token 有专门的受众、签发者、nonce 和验证规则，客户端应按协议验证，而不是把来自任何资源服务的 Token 都接受为登录成功。

**追问 3：PKCE、redirect_uri 校验与 Token 生命周期管理分别防范哪一段风险？**

PKCE 把授权码兑换绑定到发起流程的客户端，降低授权码被截获后的滥用风险；严格校验 redirect_uri 防止码泄露到攻击者地址。

还要校验 state 或使用协议允许的等价防护，管理 Token 有效期、作用域、受众和刷新令牌轮换，避免长期凭据被重放。不要采用已不推荐的简化流程来省略这些保护。

### 3. JWT 的签名、加密与 Base64url 编码分别提供什么能力？

Base64url 是编码，不提供保密；签名保护消息完整性并验证由受信任密钥持有者签发，不能阻止持有 Token 的人读取载荷；加密才用于隐藏内容。

常见 JWT 是 JWS 签名形式，任何拿到它的人通常都能解码声明，因此不应直接放入密码等敏感数据。

**追问 1：如何检查签发者、受众、有效期与密钥轮换？**

验证端使用预配置的允许算法和可信密钥来源，不能完全服从 Token 自报算法或任意密钥 URL。

- 检查 `iss`、`aud`、`exp`，按需求检查 `nbf` 等，并限制时钟容差。
- 密钥轮换保留合理重叠期，按可信 `kid` 查找密钥，未知标识不能触发无约束外部访问。

**追问 2：Token 被盗后的风险为何不能只靠“签名正确”消除？**

bearer Token 被盗后，攻击者可以在权限和有效期范围内使用它，签名仍然完全正确。

- 需要短有效期、刷新凭据保护、撤销机制、安全 Cookie 或存储、异常检测及敏感操作再认证。
- 签名只能证明凭据未被篡改，不能证明当前持有人就是最初的用户。

## 8. 链路追踪

**本节问题**

- [1. 分布式链路追踪如何通过 Trace ID 关联多个服务中的调用？](#1-分布式链路追踪如何通过-trace-id-关联多个服务中的调用)
- [2. Trace 与 Span 的父子关系如何跨 HTTP、RPC、MQ 和线程池传播？](#2-trace-与-span-的父子关系如何跨-httprpcmq-和线程池传播)

### 1. 分布式链路追踪如何通过 Trace ID 关联多个服务中的调用？

一次请求用 Trace ID 关联整条调用链，每个具体操作用 Span 记录开始结束、父子关系、状态和属性。

- 跨服务通过标准传播头或消息元数据传递上下文，再把 Trace ID 写入结构化日志。
- 链路追踪提供调用结构与耗时证据，但采样和埋点缺失意味着它不是完整业务账本。

**追问 1：日志、指标与调用链各自提供什么证据，如何联合定位失败或慢请求？**

指标显示总体趋势和异常范围，日志记录具体事件与错误细节，Trace 展示一次请求经过哪些服务以及时间花在哪里。

先从错误率或 P99 识别时间窗，再查代表性 Trace，关联 SQL、重试和日志；若缺少 Span，还需补充系统指标和分段计时，不能把链路空白当成没有耗时。

### 2. Trace 与 Span 的父子关系如何跨 HTTP、RPC、MQ 和线程池传播？

同步调用通常把当前 Span 上下文注入请求，下游提取后建立服务端 Span，再为其内部操作建立子 Span。

线程池和 MQ 改变了执行线程与生命周期，必须显式传递上下文；异步批量或多来源场景也可能适合 Span Link，而不是强行建立一个唯一父节点。

**追问 1：同步 HTTP 或 RPC 的父子 Span 关系怎样传递到下游？**

使用 W3C Trace Context 等约定传递 trace ID、parent span ID 和采样标志，服务端创建自己的 Span ID，不能把整条链路的 Span ID 都设成同一个值。

跨信任边界对传播头进行验证和必要限制，避免任意用户注入无限属性或造成错误关联。

**追问 2：改成 MQ 或线程池后，执行线程与生命周期变化，上下文应怎样显式交接？**

提交线程池任务时捕获上下文，执行时建立作用域，结束后恢复或清理，防止复用线程串用。

- MQ 在发送属性中注入上下文，消费时提取并建立消费 Span；批量消费涉及多个生产上下文时可记录多个 Link。
- 业务关联 ID 仍需单独保存，不能只靠有采样的 Trace 追账。

**追问 3：采样、重试和上下文清理分别可能造成什么缺失或串用，怎样与日志一起核对？**

采样可能让部分调用不可见，重试应产生可识别的多次尝试，不能用一个成功 Span 掩盖之前失败。

- 上下文未传递会断链，未清理会把其他用户请求接到旧链上。
- 结合请求 ID、事件 ID、时间戳和日志验证传播路径，并对异步边界做专门测试。

### 1. 灰度发布如何控制新旧版本流量，并处理接口或数据库结构变化？

灰度发布让少量明确的用户或流量先使用新版本，观察正确性和性能后逐步扩大。

- 路由维度应稳定，避免同一业务流程在不兼容的新旧版本间随机切换。
- 接口与数据库采用向前兼容的分阶段演进，发布程序和迁移数据必须共同设计回滚边界。

**追问 1：哪些用户或请求进入新版本，怎样保证一次业务链路中的版本组合可接受？**

可按用户、租户、地区或固定流量比例分组，必要时将灰度标识沿调用链传播。

即使上下游版本不同也应保持协议兼容；不能只把入口流量分开，却让下游随机混用不兼容模型。核心用户和高风险操作可采用单独策略。

**追问 2：数据库结构与接口同时演进时，旧版本和新版本需要怎样兼容？**

采用扩展—迁移—收缩：先增加兼容字段或接口，新旧版本都能运行；再迁移读写并校验；最后停止旧写法并删除旧结构。

新增非空字段、枚举状态或改变字段含义都可能破坏旧版本。不要把删列与应用升级绑定成一次不可回退操作。

**追问 3：观察到哪些指标或错误时停止放量并回滚，回滚前还要检查哪些已经写入的数据？**

观察错误率、业务成功率、尾延迟、资源和关键数据不变量，达到停止条件立即暂停放量。

- 回滚前检查新版本是否写入旧代码不认识的数据，是否已执行不可逆迁移。
- 回退镜像不等于回退数据库，必要时先关闭新功能、修复数据或执行兼容回迁。

### 2. 滚动发布、蓝绿发布与金丝雀发布有什么区别？

滚动发布逐批替换实例，新旧版本共存；蓝绿发布准备两套环境，通过入口切换流量；金丝雀发布先让少量流量验证新版本，再逐步扩展。

三者关注的维度不同，可以组合使用，例如滚动替换实例的同时按用户金丝雀放量。

**追问 1：容量冗余、流量切换、回滚速度和新旧数据兼容各需要怎样评估？**

滚动发布冗余较少，但要控制不可用副本和兼容窗口；蓝绿需要额外容量，流量回切快但共享数据库仍可能阻止真正回滚；金丝雀利于控制风险，但需要稳定路由和可比较指标。

无论采用哪种，长连接、异步消息、新旧数据格式与迁移操作都需要单独处理。

### 3. 服务上线和下线时，注册状态、存量请求与长连接应按什么顺序处理？

上线先完成配置、依赖和必要初始化，再标记就绪并加入流量。

- 下线时先进入排空状态，撤销就绪或注册，使负载均衡不再把它选为新请求目标；在地址传播和长连接过渡窗口内，按协议继续处理可接受请求或返回明确的可重试拒绝，而不是立即切断监听。
- 随后停止接收新工作、等待在途请求和任务收尾，最后按依赖顺序关闭连接池、线程池等资源并退出。
- 步骤需与框架和编排平台协调，不能假设控制面摘除会立即清空数据面流量。

**追问 1：实例准备就绪前，什么时候才能注册为可接收流量？**

进程启动不等于可以服务，数据库连接、关键配置和服务端口准备完成后才应对外就绪。

- 非必要依赖失败可以降级，但必须明确哪些关键能力不可缺。
- 注册时若先暴露地址再初始化，用户请求会落到半初始化实例。

**追问 2：下线时停止新请求、摘除注册、处理存量请求与关闭资源，应怎样排序？**

先标记排空并更新注册、就绪和负载均衡状态，给地址传播及协议级排空留出有界窗口；停止领取新的后台任务，并逐步停止新业务准入。

- 继续保留在途请求所依赖的数据库、MQ 和线程资源，待它们完成或达到宽限期后再按依赖顺序关闭。尚未完成的可恢复任务需要持久进度。
- 不能先关闭数据库连接池，再让尚未结束的业务请求使用它，也不能等待无限时间阻止服务退出。

**追问 3：客户端仍缓存旧地址或长连接未结束时，怎样避免立即退出造成大量失败？**

旧地址缓存和现存长连接可能继续带来请求，应在传播窗口内保留可控的接收或明确拒绝能力，并配合客户端重连与幂等重试。

- HTTP/2、WebSocket 等长连接需要协议级排空或通知。
- 宽限期结束后的未完成任务需持久化恢复，不能依靠无限等待阻止发布。

### 4. 容器处于运行状态，但外部访问应用失败，应如何核对部署配置？

先判断容器内应用是否真正监听，再逐层检查 Pod 或容器地址、端口映射、Service 端点和入口路由。

- 运行状态只代表容器主进程未退出，不证明监听地址、健康检查和业务依赖正确。
- 用实际 HTTP 请求验证每一层，比只看容器状态更有意义。

**追问 1：应用只监听 `127.0.0.1`、容器端口与 Service 目标端口不一致，分别会造成什么现象？**

应用只监听容器内 `127.0.0.1` 时，通常只有同网络命名空间内的回环访问能到达，外部转发到 Pod IP 会失败；应按部署要求监听 `0.0.0.0` 或正确接口。

Service `targetPort` 指错端口会把请求发到未监听位置，Service `port` 与应用端口不同本身并不是错误，映射关系正确即可。

**追问 2：如何在应用、容器和服务入口逐层发起测试，区分监听、端口映射、网络策略和业务错误？**

先在容器内检查 `ss -lntp` 并请求本地端口，再从允许的相邻 Pod 请求 Pod IP，随后请求 Service，最后请求 Ingress 或外部地址。

比较每一步的连接错误、HTTP 状态和日志，检查 Service 选择器、EndpointSlice、网络策略及入口配置。不能在外部失败时直接认定应用代码错误。

**追问 3：配置修复后，应怎样验证外部流量和健康检查都已恢复，而不是只确认进程没有退出？**

通过真实外部入口执行关键接口，确认响应内容、状态码和日志中的实例符合预期，同时检查就绪探针成功、端点已加入和错误率下降。

还要测试多副本、重启及发布过程，避免修复只对单个实例有效。健康接口成功不能替代业务链路验证。

### 5. Docker 镜像与运行中的容器有什么区别，应用状态应该保存在哪里？

镜像是包含应用及依赖的分层制品，容器是基于镜像运行的进程及其隔离环境。

- 容器可写层适合临时数据，需跨重建保留的数据应存到数据卷、数据库或对象存储，并明确备份和生命周期。
- 镜像应尽量不可变，配置和密钥在部署时注入，不能把运行中的手工修改当成可重复交付。

**追问 1：镜像层、容器可写层与数据卷各承担什么职责？删除并重建容器后哪些数据可能丢失？**

镜像层可被多个容器复用，容器可写层记录该实例的修改；删除并重建容器通常会丢失可写层内容。

- 数据卷可独立于容器存在，但是否持久和是否跨节点取决于具体存储类型。
- 把数据库目录放进卷不等于自动有备份、高可用或正确的跨节点访问。

**追问 2：容器与虚拟机在内核共享和隔离方式上有什么区别？命名空间与 cgroup 分别约束什么？**

常见 Linux 容器共享宿主机内核，命名空间隔离进程、网络、挂载等视图，cgroup 对 CPU、内存等资源进行限制和统计；虚拟机通常运行独立客体内核。

隔离不是绝对安全，应控制权限、宿主挂载和特权模式，并维护内核与镜像补丁。

**追问 3：怎样让应用制品可重复构建，并把环境配置、密钥与持久化数据同镜像分离？**

通过版本化构建文件、锁定依赖与基础镜像标识、自动测试和制品校验保证可重现。

- 环境配置使用外部配置机制，密钥采用受控注入和轮换，持久数据放外部存储。
- 日志输出到可采集通道，不能只保存在容器内部一个会随重建消失的文件里。

### 6. Kubernetes 的 Pod、Deployment 与 Service 如何协作运行多实例后端服务？

Pod 是共同调度并共享部分资源的运行单元；Deployment 通过 ReplicaSet 维护无状态应用的期望副本及滚动更新；Service 为一组符合选择条件的端点提供稳定访问入口。

Pod 的生命周期是可替换的，因此服务不应依赖某个 Pod 永久拥有同一地址或本地状态。

**追问 1：Pod 被替换后地址可能变化，Service 如何让调用方继续访问一组实例？**

Pod 替换后由控制面更新相应端点信息，Service 名称和虚拟地址通常保持稳定，数据面将新连接路由到可用端点。

- 具体转发由集群网络实现，不能假设总是同一种 iptables 路径。
- 已有连接不会自动搬到新 Pod，客户端仍需要处理断开与重连。

**追问 2：Deployment 的期望副本数与滚动更新策略如何影响发布期间的可用容量？**

副本数决定目标容量，`maxSurge` 允许额外副本，`maxUnavailable` 限制更新期间不可用副本。

- 新副本需要通过就绪条件后才能承担流量，慢启动和资源不足会影响更新进度。
- 单纯把副本数设大也可能因数据库连接总量或节点资源不足导致整体性能下降。

**追问 3：应用有本地会话或写入本地磁盘时，水平扩容和 Pod 重建会暴露什么状态管理问题？**

本地会话会让请求路由到其他 Pod 后丢失登录或流程状态；本地写入文件可能在重建或迁移后丢失。

- 应将共享会话和持久数据移到适当外部存储，或选用具有明确状态管理的工作负载方案。
- 粘性会话只能暂时减少跨实例访问，不能解决节点失效后的状态恢复。

### 7. 启动探针、存活探针与就绪探针分别判断什么，失败后的处理是否相同？

| 机制 | 特点与边界 |
|---|---|
| 启动探针 | 启动探针判断应用是否完成初始启动，成功前可抑制存活和就绪探针的常规执行 |
| 存活探针 | 存活探针判断容器是否需要重启 |
| 就绪探针 | 就绪探针判断当前是否适合接收流量 |

就绪失败通常使端点不再作为普通就绪后端选择，不会仅因此重启容器；存活或启动探针持续失败则按规则触发重启。

**追问 1：应用仍在预热、线程彻底卡死和暂时无法接收流量，应分别如何表达？**

预热慢用启动探针提供足够启动窗口；无法自行恢复的卡死可通过存活检查暴露；短暂过载或依赖不足以服务请求时可表达为未就绪。

探针应有合理超时、周期和失败阈值，不能让一次偶发抖动就触发破坏性重启。

**追问 2：为什么把所有下游短时故障都配置成存活失败，可能造成重启连锁反应？**

数据库短暂故障可能同时影响所有实例，若全部被判存活失败就会一起重启，增加建连和预热洪峰，反而拖延恢复。

- 存活检查应尽量反映本进程是否需要重启，依赖可用性更多影响就绪或业务降级。
- 就绪依赖也要慎重，避免非核心下游失败导致整个服务无后端。

**追问 3：怎样与优雅下线、终止宽限期和负载均衡配合，避免切走新请求后仍丢失正在处理的任务？**

终止时端点状态传播、应用收到信号与存量连接排空不是严格瞬时串行过程，应协同 readiness、preStop、应用优雅关闭及终止宽限期。

- preStop 的时间也计入宽限期，不能无限睡眠。
- 应用停止新任务后等待在途请求并持久化可恢复进度，超时后安全结束；负载均衡摘除不保证现有长连接立刻断开。

## 要点回顾

- 服务拆分围绕业务与数据边界：独立部署带来治理与一致性成本，不能仅按数据库表或技术分层机械拆分。
- 超时、重试、限流与隔离应共同受预算约束：不能让每一层独立重试，也不能让一个慢依赖占满全部执行资源。
- 可观测性和发布流程都要落到实际状态：注册在线不等于就绪，回退镜像不等于回退数据，日志与 Trace 也不能替代业务账本。
