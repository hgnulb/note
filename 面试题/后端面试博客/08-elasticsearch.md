### 1. Elasticsearch 适合解决哪些搜索问题？

Elasticsearch 适合全文搜索、多条件检索、相关性排序、日志分析和一定规模的实时聚合。

它以文档为单位建立倒排索引，并将索引分片分布到多个节点，适合从大量文档中找出匹配内容，而不是逐行扫描文本。

**追问 1：与 MySQL 查询相比有哪些优势和限制？**

相较 MySQL，它在分词、相关性评分和分布式搜索方面更直接；MySQL 则更适合关系约束、多表事务、精确更新和作为交易数据事实来源。

- ES 的搜索可见性通常是近实时的，跨文档事务能力也不同。
- 常见方案是 MySQL 保存权威业务数据，ES 维护可重建的搜索视图，并明确同步延迟。

### 2. Elasticsearch 的 Mapping 为什么需要结合查询需求设计？

Mapping 决定字段如何索引、分析和读取，应从实际查询反推。

商品名称可能需要 `text`，商品编码需要 `keyword`，价格需要数值类型，时间需要 `date`；对象数组若要求同一元素内联合匹配，还要考虑 `nested`。类型选错不仅影响结果，也会增加存储与查询成本。

**追问 1：字段用于全文搜索、精确过滤、排序还是聚合，分别怎样影响类型选择？**

全文检索依赖分词和词项匹配；精确过滤通常使用 `keyword`、数值或日期；排序和聚合通常依赖适合的字段及 doc values。

同一字段有不同需求时可建多字段，例如 `title` 用于搜索、`title.raw` 用于排序，不应强行让一个处理方式满足全部需求。

**追问 2：动态映射推断错误或字段持续膨胀时，会给查询和后续变更带来什么成本？**

动态映射可能把数字样式的业务编码、日期或对象推断成不合适的类型。

- 任意用户键持续成为新字段，会导致 mapping 膨胀、集群元数据和内存开销增加。
- 应限制动态字段，使用显式模板，必要时采用固定键值结构或 `flattened`，而不是无限添加字段。

**追问 3：数据已经写入后再改变字段类型，为什么需要先考虑迁移方案？**

已建立的索引结构依赖字段类型，许多类型变化不能直接原地修改。

- 通常要建新索引、重新导入并同步增量，再切换别名。
- 增加一个新子字段也不会自动为历史文档补齐索引数据，仍需重建相关文档并验证查询结果。

### 3. `text` 与 `keyword` 有什么区别？

`text` 面向全文搜索，内容经分析器变成多个词项；`keyword` 将整个值作为一个词项，适合编码、标签、精确过滤、排序和聚合。

`keyword` 可配置 normalizer，但这与把句子分成多个词不是同一过程。

**追问 1：两个字段类型是否进行同样的分词，分别怎样影响全文匹配与精确过滤？**

例如标题“分布式数据库设计”在 `text` 中可能分为多个词，搜索其中一个词也能匹配；`keyword` 通常按完整值匹配。

对分词后的 `text` 使用 `term` 不会自动分词输入，容易因大小写或词项不一致而查不到。必须根据实际分析结果判断。

**追问 2：同一个标题既要搜索又要排序或聚合时，如何组织字段而不混用处理方式？**

可将标题定义为 `text`，同时增加 `keyword` 子字段：
```json
{"title":{"type":"text","fields":{"raw":{"type":"keyword"}}}}
```
- 搜索使用 `match` 查询 `title`；精确筛选、排序或聚合使用 `title.raw`。
- 应给过长标题等边界设置合理规则，并评估额外索引开销。

### 4. `object` 与 `nested` 字段在保存对象数组时有什么区别？

某条文档包含数组字段 `members`：

```json
{
  "members": [
    {"name": "张三", "role": "普通用户"},
    {"name": "李四", "role": "管理员"}
  ]
}
```

业务要求查询“存在同一个成员，其姓名为张三且角色为管理员”的文档。

业务要求两个条件属于同一个成员，应使用 `nested`。

普通 `object` 数组会把各字段展开成多值字段，丢失同一数组元素内部的关联；于是“张三”和“管理员”可能分别来自两个成员仍被匹配。题设文档不应该命中该业务查询。

**追问 1：对给定数组同时查询 `name=张三` 和 `role=管理员`，为什么必须明确两个条件是否要求命中同一元素？**

“文档中有张三，并且文档中有管理员”与“张三这个成员是管理员”是两个不同谓词。题设仅满足前者，不满足后者。

先明确这个语义，再选映射，不能用查询写了两个 AND 条件就认定关联自动保留。

**追问 2：分别采用 `object` 和 `nested` 映射时，应怎样构造查询并验证是否发生跨元素匹配？**

可建立如下字段映射：
```json
{
  "mappings": {
    "properties": {
      "members": {
        "type": "nested",
        "properties": {
          "name": {"type": "keyword"},
          "role": {"type": "keyword"}
        }
      }
    }
  }
}
```
搜索请求体为：
```json
{
  "query": {
    "nested": {
      "path": "members",
      "query": {
        "bool": {
          "filter": [
            {"term": {"members.name": "张三"}},
            {"term": {"members.role": "管理员"}}
          ]
        }
      }
    }
  }
}
```
- 这条查询不匹配题设文档。若将映射改为普通 `object`，并在外层 `bool.filter` 中直接放同样两个 `term`，则会跨成员匹配。
- 两个条件必须置于同一个 nested 查询中；拆成两个独立 nested 查询也可能分别匹配不同成员。

**追问 3：使用 nested 后，文档数量、更新和查询成本会怎样变化？**

每个 nested 元素在底层对应独立的隐藏 Lucene 文档，再与根文档关联；N 个成员通常意味着 N+1 个底层文档。

- 查询需要块连接处理，更新某个成员也常导致整个根文档块重建。
- 因此不能无节制地塞入超大数组，必要时拆成独立业务文档或重新设计查询关系。

### 1. 倒排索引如何由词项定位文档，与 MySQL 常见索引的访问路径有什么区别？

倒排索引保存“词项 → 含该词项的文档及相关信息”。

- 查询先找到词项的倒排列表，再求交、求并、计算分数和排序。
- MySQL 常见 B+ 树则按字段值有序组织记录或主键位置，更适合等值与范围访问；两者优化的访问方向不同。

**追问 1：分词结果如何影响文档匹配，哪些查询适合倒排检索？**

索引中只有实际生成的词项才能直接参与匹配。分词粒度、大小写归一化和同义词会改变召回结果。

关键词搜索、短语搜索和多词布尔组合适合倒排检索；精确金额范围、强事务更新等不能仅因存在倒排索引就认为比关系数据库更合适。

### 2. 索引时分词与搜索时分词如何共同影响匹配结果？

索引时分析器决定文档写入哪些词项及位置信息，搜索时分析器决定查询被转换成哪些词项。

- 两者应兼容，但不必配置完全相同，例如搜索时扩展同义词。
- 搜索分析错误时，查询再复杂也可能匹配不到预期词项。

**追问 1：如何使用分析器调试分词、大小写处理、停用词与同义词，而不是只更换查询语句？**

使用 `_analyze` 输入典型文本，分别指定索引分析器和搜索分析器，观察 token、位置、偏移及归一化结果。

- 准备包含中文、大小写、标点、停用词和同义词的测试集，先确认实际词项，再检查查询。
- 修改索引时分词规则通常需要重建历史数据；仅修改搜索时分析器则要验证召回与精度变化。

### 3. term、`match`、`match_phrase` 与 `bool` 查询分别适用于什么条件？

`term` 直接匹配索引中的词项，不分析输入；`match` 分析输入后执行全文匹配；

- `match_phrase` 进一步考虑词项顺序和位置，可配置 slop；
- `bool` 用 must、filter、should、must_not 组合条件。
- 选择依据是业务语义，不是“哪一种名称看起来更高级”。

**追问 1：`filter` 与 `must` 的职责、相关性评分和缓存行为有什么区别？**

`must` 在查询上下文中参与匹配及评分；`filter` 只判断是否满足条件，不为该条件计算相关性分数，适合租户、状态和时间范围等约束。

过滤条件可能被查询缓存复用，但是否缓存由策略和实际复用情况决定，不能理解成每一个 filter 都立即缓存。

### 4. 倒排索引、`_source` 与 doc values 分别支撑什么读取需求？

倒排索引从值或词项找到文档；`_source` 用于返回原始文档内容，并支持重新索引等操作；doc values 是按字段组织的列式存储，方便排序、聚合和脚本读取。

它们不是三份完全相同用途的数据，关闭其中一项要先明确损失哪些能力。

**追问 1：对 `text` 字段进行排序或聚合时，为什么需要理解 `keyword` 与 `fielddata` 的成本？**

`text` 的词项经过分词，通常不直接用于整段原文排序或聚合。

- 开启 fielddata 可以从索引构造内存中的字段数据，但可能占用大量堆内存。
- 通常为整值增加 `keyword` 子字段并使用 doc values；不要为解决一次聚合报错就给大文本字段盲目打开 fielddata。

- [5. 多个客户端并发修改同一 Elasticsearch 文档时，如何避免旧数据覆盖新数据？](#5-多个客户端并发修改同一-elasticsearch-文档时如何避免旧数据覆盖新数据)

### 1. Elasticsearch 文档从写入成功到可以被搜索，中间经历了什么？

以 Elasticsearch 8.x 的常规索引为例，写入先由主分片处理并复制，更新 Lucene 内存索引和 translog；refresh 打开新的搜索视图，使写入能被 search 看到。

写入确认与 refresh 是不同事件，因此收到成功响应后立刻 search 仍可能暂时查不到。

**追问 1：`refresh`、`flush`、`translog` 与 Lucene segment 分别参与哪一步？**

translog 记录尚未进入 Lucene 提交点的操作，帮助崩溃恢复；refresh 使新 segment 对搜索器可见，不等于完成持久化提交；flush 完成 Lucene commit 并推进 translog 生命周期。

segment 是 Lucene 索引的组成单位，后续还会通过 merge 合并。

**追问 2：已经可搜索、已经收到写入确认和已经跨过某种持久化边界，为何不是同一个概念？**

可搜索是读取视图问题；写入确认取决于主副本执行和相应配置；持久性取决于 translog 刷盘和存储保证。

默认 `index.translog.durability=request` 会在相关 translog 持久化后确认，但这不表示所有配置的副本始终存在，也不自动触发搜索刷新。副本数、活动分片要求和实际响应仍要核对。

**追问 3：提高搜索可见性的及时程度时，需要怎样权衡写入吞吐与额外处理成本？**

频繁强制 refresh 会产生更多小 segment、搜索器开销和后续合并工作。

- 写后必须立即搜索的局部流程，可评估 `refresh=wait_for` 等等待可见性方案；批量导入可适当延长刷新周期，并在完成后刷新。
- 应按业务可接受延迟选择，而不是全局每条写入都强制刷新。

**追问 4：按 ID 执行实时 GET 与通过 search 检索，是否具有相同的可见性时机？验证写入结果时应如何选择？**

按 ID 的 GET 默认是实时读取，不受 search 的近实时刷新时机同样约束，适合确认已知文档是否写入及内容是否正确。

- search 用于验证分词、过滤和排序等索引查询行为，需要等待刷新。
- 实时 GET 也不能替代复杂查询的正确性测试，二者验证目标不同。

### 2. 一次 Elasticsearch 分布式搜索如何在多个分片执行，并汇总为最终结果？

典型的 query-then-fetch 搜索先由协调节点向相关分片副本发送查询，各分片返回本地候选的文档标识、分数或排序值；协调节点合并出全局需要的结果，再向对应分片获取完整字段并组装响应。不是把所有匹配文档全文都先拉到协调节点。

**追问 1：协调节点怎样把查询发到相关分片，每个分片先返回什么？**

协调节点根据索引、routing 和分片状态选择每个分片的一份可用副本。

- 查询阶段各分片执行过滤、评分或排序，返回满足当前窗口所需的局部候选。
- 查询可能同时涉及主分片和副本分片，但同一分片的数据不会因为有多个副本就都重复计算一次。

**追问 2：局部候选怎样合并成全局结果，随后获取完整文档又需要什么工作？**

协调节点对各分片候选做全局归并，确定最终文档及顺序；fetch 阶段只取这些文档需要的 `_source` 或字段。

跨分片分数统计可能影响相关性，要求更统一的词频统计时可评估相应搜索类型，但要承担额外往返开销。

**追问 3：查询分片越多、排序窗口越大时，协调节点与网络开销可能怎样增长？**

分片越多，RPC、局部搜索器和候选归并开销越大；`from+size` 越大，每个分片需要保留的候选通常越多。协调节点会消耗更多堆、CPU 和网络资源。

多分片并行能降低单分片负担，但过度分片会增加固定成本，不能无限扩展。

### 3. Elasticsearch 更新或删除文档时，底层为什么不能简单地原地改写倒排索引？

Lucene segment 主要采用不可变结构。

- 文档更新通常表现为标记旧文档删除并索引新文档；删除先改变可见性标记，物理空间通常在后续 segment merge 时回收。
- 这样有利于顺序构建索引和并发读取，但会产生写放大和暂时的空间占用。

**追问 1：删除标记和 segment merge 会怎样影响磁盘空间、查询与写入延迟？**

查询会排除已删除文档，但旧 segment 的文件仍可能存在。

- merge 需要读取旧 segment、生成新 segment 并回收不再使用的旧文件，会消耗 CPU、I/O 和额外磁盘空间；频繁更新和长期保留的 PIT 可能延迟回收。
- 不能把删除请求成功等同于磁盘立即缩小，也不宜在持续写入的索引上频繁强制合并。

### 4. Bulk API 返回成功的 HTTP 响应，是否表示每一条文档都写入成功？

不是。Bulk 的 HTTP 成功表示请求已被正常处理，批次内仍可能出现映射错误、版本冲突、限流或分片失败。

必须检查顶层 `errors` 和每个 item 的状态、错误类型及对应文档 ID，再决定后续处理。

**追问 1：HTTP 请求成功与批次内各项成功应在哪一层分别检查？**

先检查传输和 HTTP 层是否成功，再遍历 items。

- 某个 item 返回 400 的映射错误，与返回 429 的暂时资源拒绝，处理方式不同。
- 不能只看 HTTP 200 或顶层是否有响应就提交整批任务的成功状态。

**追问 2：只有部分文档失败时，怎样定位并仅重试失败项？**

保持输入项与响应项的对应关系，把可重试失败项单独收集，按退避和并发上限重试；不可重试数据进入错误记录或人工修复通道。

整个请求响应丢失时，各项结果可能未知，应依靠稳定文档 ID、业务版本和幂等语义安全重放，而不是生成新 ID 全量再写。

**追问 3：重试可能与后续更新交错时，如何避免重复创建或旧内容覆盖新内容？**

固定文档 ID 可以避免重复创建，却不能防止旧内容覆盖新内容。

- 要为事件携带单调业务版本，或使用 ES 条件更新；更新发生冲突时重新读取并重算。
- 对不可幂等的脚本加一操作尤其要去重，不能把“重发相同请求”默认视为无副作用。

### 5. 多个客户端并发修改同一 Elasticsearch 文档时，如何避免旧数据覆盖新数据？

先读后整文档写回可能丢失并发更新。应读取文档的 `_seq_no` 与 `_primary_term`，提交更新或删除时使用 `if_seq_no` 和 `if_primary_term` 作为前提；只有文档仍处于读取时的修改版本，操作才成功。

条件不满足返回冲突，由业务决定重算、合并或拒绝。

**追问 1：先读取再整文档写回会产生什么丢失更新问题？**

A、B 都读取库存 10，A 修改价格后写回，B 使用原文档修改库存后整份写回，可能把 A 的新价格覆盖成旧价格。

- 两次写入本身都可以成功，但组合业务发生丢失更新。
- 版本检查用于发现这种“我读取后别人已经修改”的窗口。

**追问 2：`if_seq_no` 与 `if_primary_term` 如何限制更新或删除的前提？冲突响应后应如何重新读取、合并或放弃？**

这对参数标识所读取的文档修改版本。例：读取到 seq_no=15、primary_term=3，提交时带同样条件；期间文档被修改则返回 409。

收到冲突后应重新 GET、检查业务约束、合并必要字段并重新计算，再有限重试；用户编辑冲突也可以直接提示，不必所有情况自动覆盖。

**追问 3：盲目重试原来的完整文档为什么可能继续覆盖他人的修改？如何区分重试请求与重算业务操作？**

盲目重试旧完整文档仍表达“恢复旧快照”，并没有吸收他人的更新。

- 安全重试应重新执行业务意图，例如“在最新库存仍足够时扣减 1”，而不是无条件写回某个旧数值。
- 脚本更新也要明确是否幂等和是否允许自动重试，防止重复扣减。

## 4. 分片与副本

**本节问题**

- [1. 如何选择 Elasticsearch 的分片数和副本数？](#1-如何选择-elasticsearch-的分片数和副本数)
- [2. Elasticsearch 的主节点、数据节点与协调节点如何分工？](#2-elasticsearch-的主节点数据节点与协调节点如何分工)
- [3. 主分片数、副本数与 `routing` 分别如何影响扩容和数据分布？](#3-主分片数副本数与-routing-分别如何影响扩容和数据分布)

### 1. 如何选择 Elasticsearch 的分片数和副本数？

分片数量应由数据量、索引膨胀、单分片搜索与恢复时间、写入吞吐和节点资源共同决定；副本数量主要服务于容错和读取分担。

先用代表性数据和查询压测，再选择能满足故障恢复目标的布局，而不是按用户数套固定分片公式。

**追问 1：数据规模、单分片大小、查询并行度与写入方式应怎样共同参与估算？**

估算实际索引体积，而不仅是原始 JSON 大小；测试目标分片大小下的查询延迟、写入和恢复速度，计算每节点可承载的分片与并发。

大量小分片增加元数据和搜索开销，过大分片则可能使恢复过慢。具体容量阈值依版本、硬件和数据结构确定。

**追问 2：增加副本与增加主分片，分别改变什么容量或容错特征？**

增加副本复制相同数据，可提高读分担和节点故障后的可用性，但也增加磁盘、网络和写入复制成本，不增加唯一业务数据的分片容量。

增加主分片把数据划成更多独立处理单元，可能提高写入和查询并行度，也增加固定开销；它与副本不是互相替代的扩容方式。

**追问 3：节点故障恢复期间，还需要预留哪些资源，而不是按正常状态占满容量？**

要为副本重建、segment merge、分片迁移、网络传输及剩余节点接管查询预留容量。

- 正常时磁盘或 CPU 接近满载，故障后就可能同时出现恢复缓慢和业务雪崩。
- 容量规划应至少模拟损失一个故障域后的负载，而不仅测试全部节点正常的峰值。

### 2. Elasticsearch 的主节点、数据节点与协调节点如何分工？

集群主节点负责元数据、索引创建、分片分配等集群管理，不是所有搜索和写入的数据中转站。

数据节点保存分片并执行查询和索引操作；协调节点负责拆分请求、路由和归并，任何接收请求的节点都可能承担协调工作。

**追问 1：主分片和副本分片在查询、写入及节点故障时分别承担什么职责？**

主分片接收并组织文档写入，再将操作复制到副本；查询可由主分片或相应副本处理。

- 主分片所在节点故障时，合格的副本可被提升为新主分片。
- 集群 master 与文档数据的 primary shard 是两种不同概念，不能因中文都叫“主”就混为一个角色。

### 3. 主分片数、副本数与 `routing` 分别如何影响扩容和数据分布？

主分片决定数据的初始分布单元，副本提供相同分片的额外拷贝；routing 决定文档进入哪个分片。

默认通常依据文档 ID 路由，自定义 routing 可以缩小某类查询的分片范围，但也可能把热点业务集中到一个分片。

**追问 1：索引创建后修改副本数，与改变主分片布局有什么不同？**

副本数可在线调整，系统按配置创建或删除副本。主分片布局不能直接通过任意修改数字完成重分布，需要符合条件的 split、shrink，或建立新索引并 Reindex。

不同操作有只读、因子和容量等前提，执行前要固定版本并验证。

**追问 2：单个租户流量过大时怎样避免热点分片？**

大租户可采用独立索引、带分桶的 routing 或分区路由，把一个租户的数据分散到多个单元，同时保留可控的查询扇出。小租户继续共享索引。

单纯增加副本可能缓解读取，但对集中在一个主分片的写热点帮助有限；拆分规则必须同时覆盖写入、查询和迁移。

## 5. 查询优化

**本节问题**

- [1. Elasticsearch 深分页为什么会产生较大开销？](#1-elasticsearch-深分页为什么会产生较大开销)
- [2. 大数据量搜索性能不足时，如何从索引、查询与分片三个层面定位优化方向？](#2-大数据量搜索性能不足时如何从索引查询与分片三个层面定位优化方向)
- [3. 相关性评分与显式字段排序有什么区别？](#3-相关性评分与显式字段排序有什么区别)
- [4. Elasticsearch 的桶聚合与指标聚合分别适合什么统计需求？](#4-elasticsearch-的桶聚合与指标聚合分别适合什么统计需求)

### 1. Elasticsearch 深分页为什么会产生较大开销？

`from/size` 深分页需要各分片找到前 `from+size` 个候选，协调节点再合并并丢弃前面的结果。

偏移量越大，中间候选和排序成本越高；用户只拿到一页，并不意味着系统只处理这一页。

**追问 1：from/size 的偏移量增大时，各分片和协调节点需要额外处理多少候选结果？**

若有 S 个分片、偏移 F、页长 K，典型情况下各分片需维护最多约 F+K 个候选，协调节点合并最多约 S×(F+K) 个候选，具体优化取决于执行计划。

它不是只扫描 K 条的常量成本，因此不宜通过无限调大窗口支持任意深页。

**追问 2：search_after 对排序字段和访问方式有什么要求，为什么需要稳定的次序？**

`search_after` 使用上一页最后一条结果的排序值继续向后查，查询和排序必须保持一致。

- 排序要有稳定的唯一判定，例如时间加唯一业务 ID；不能只用可能重复的时间戳。
- 它适合顺序翻页，不直接支持无上下文跳到任意第 N 页。

**追问 3：翻页期间数据持续变化时，PIT 能帮助维护什么视图，又要付出什么资源成本？**

PIT 保留搜索时点的索引视图，配合 search_after 避免刷新导致翻页时重复或遗漏。

- 应使用最新返回的 PIT ID 和完整排序值，设置短而足够的 keep_alive，结束后关闭。
- PIT 会保留旧 segment、文件句柄和相关状态，长时间大量开启会增加资源压力。

### 2. 大数据量搜索性能不足时，如何从索引、查询与分片三个层面定位优化方向？

先确定慢的是查询阶段、取文档阶段还是排队与协调，再检查 Mapping、分析器、查询条件、聚合和分片布局。

- 用慢日志、节点指标、查询 profile 和代表性数据验证。
- 常见优化包括减少无效字段与返回内容、使用合理过滤、避免深分页和高开销脚本、控制分片扇出。

**追问 1：如何判断瓶颈来自数据组织还是查询执行？**

若词项数、nested 数组或字段基数异常，可能是建模问题；若同一数据上某种通配符、脚本或聚合特别慢，主要检查查询执行。再比较单分片与多分片耗时、缓存冷热和节点热点。

profile 有额外开销，也不涵盖全部网络及排队时间，应与端到端指标一起分析，而不是只优化其中最大的一个函数。

### 3. 相关性评分与显式字段排序有什么区别？

相关性评分回答“文档与查询有多相关”，显式字段排序回答“按价格、销量或时间等字段排在什么位置”。

字段排序可以完全盖过相关性排序，也可以把 `_score` 作为其中一项；应先明确用户期望，而不是默认分数越高就越符合业务目标。

**追问 1：在商品搜索中，关键词相关性、销量和时间新鲜度应怎样组合，并验证结果质量？**

先用文本相关性得到合理候选，再以归一化的销量、时间衰减等信号做加权或重排，避免销量量级直接淹没文本相关性。

通过人工标注查询集、NDCG 等离线指标，以及点击、转化和不良结果率进行验证；不能只看某几个示例排名更好就全量发布。

**追问 2：BM25 中词频、逆文档频率与字段长度分别可能怎样影响评分？如何使用解释信息核对某条结果为何排名靠前？**

BM25 中，词频增加通常提升得分但收益逐渐饱和；越少文档包含的词通常提供更高区分度；字段长度归一化用于避免长文本仅因词多获得不合理优势。

可用 `_explain` 检查某文档的词项贡献、长度影响和查询组合；具体参数与统计范围依字段配置及搜索方式而定。

### 4. Elasticsearch 的桶聚合与指标聚合分别适合什么统计需求？

桶聚合把文档分组，例如按品牌、日期区间或价格范围形成桶；指标聚合在文档集合或桶内计算 sum、avg、min、max 等数值。可先按日期分桶，再对每个桶计算销售额和客单价。必须区分“分组方式”与“组内统计值”。

**追问 1：terms 聚合返回全局热门项时，分片局部候选截断可能怎样影响结果？**

terms 聚合通常先从每个分片收集有限的局部热门候选，再在协调节点合并。

- 某项在多个分片都不够热门、却在全局很热门时可能被漏选，计数也可能低估。
- 可调 shard_size 并检查误差信息；需要遍历全部分组时考虑 composite 聚合，而不是无限增大一次返回的 terms 数量。

**追问 2：高基数字段聚合需要评估什么资源开销？**

高基数意味着更多桶、ordinal 或哈希结构、内存和网络开销，子聚合还会放大成本。

- 应限制时间范围、桶数和返回字段，评估全局序号构建、熔断器和查询并发。
- 精确去重与近似 cardinality 聚合的精度、空间也不同，选择前要明确业务是否允许误差。

## 6. 数据同步

**本节问题**

- [1. MySQL 数据同步到 Elasticsearch 时，如何衔接全量初始化与增量更新？](#1-mysql-数据同步到-elasticsearch-时如何衔接全量初始化与增量更新)
- [2. 字段类型或分词规则变化后，如何通过新索引、`Reindex` 和别名切换完成迁移？](#2-字段类型或分词规则变化后如何通过新索引reindex-和别名切换完成迁移)

### 1. MySQL 数据同步到 Elasticsearch 时，如何衔接全量初始化与增量更新？

一种可靠流程是先建立可恢复的增量消费位置，再取得与该位置协调的一致性快照做全量导入，最后重放快照期间的增量并追平。

MySQL 是事实来源，ES 按稳定主键写入，增量包含插入、更新和删除；同步进度必须持久化。

**追问 1：全量导入期间数据库仍在更新，增量读取从什么位置开始才不易漏掉变化？**

不能等全量结束才开始监听，否则导入期间的修改会丢失。

- 应使用具备快照与 binlog 位点衔接能力的 CDC 工具，或设计并验证等价协议，保留起始位点之后的日志。
- 全量写入和增量覆盖要有版本控制，防止慢到的旧快照覆盖已应用的新事件。

**追问 2：同一文档的更新重复、乱序或暂时失败时，怎样维护最终结果？**

以数据库主键作为文档 ID，实现重复写的稳定定位；同一实体按顺序消费，或附带单调业务版本拒绝旧事件。

- 删除也需携带足够的版本或删除标记，避免迟到更新复活已删除数据。
- 失败项进入可重试队列，只有对应结果可靠处理后再推进消费位点。

**追问 3：怎样验证同步一致性和延迟，而不只比较文档总数？**

比较主键集合、关键字段校验和、删除状态和抽样内容，不只比较数量；监控源变更时间、消费位点、积压和 ES 搜索可见性延迟。

持续运行差异修复任务，故障演练覆盖重复、乱序、断点恢复和全量重建，才有依据说明最终一致性可恢复。

### 2. 字段类型或分词规则变化后，如何通过新索引、`Reindex` 和别名切换完成迁移？

先创建带新 Mapping 和分析器的索引，导入旧数据并持续同步增量；校验结果和性能后，通过一次别名更新切换查询入口。旧索引暂时保留用于回滚。

Reindex 负责搬运当时可读取的数据，并不会自动替代持续增量同步。

**追问 1：为什么不宜直接假设原索引的已有字段类型或分词语义能够原地变更？**

已有字段的索引结构和词项由写入时配置决定，许多类型与分析语义不能直接改变历史内容。

即使允许修改某些搜索配置，也要检查它是否只影响后续查询或后续写入。采用新索引重建能够显式隔离新旧语义并验证效果。

**追问 2：新索引重建期间的增量写入怎样衔接，怎样核对结果？**

从明确位点保留并重放增量，或者让可靠事件流同时投递新旧索引，并对相同文档使用版本条件。

验证总量、关键字段、查询结果、排序、聚合和写入延迟；迁移期间尤其检查旧全量数据与新增量的覆盖顺序。

**追问 3：切换别名前后，怎样控制回滚与新旧写入，避免只切换查询入口就认为迁移结束？**

切换查询别名时还要明确写别名或写入口指向哪里，新旧索引是否继续同步，以及回滚的数据追平方法。

- 只把读取切回旧索引，但旧索引已停止接收变更，会造成新的数据缺失。
- 停止旧同步和删除旧索引应安排在观察期之后，并保留可恢复的源日志。

## 要点回顾

- 数据建模决定检索方式：字段类型、分词与查询条件要匹配，倒排索引与数据库 B+ 树优化的访问方向不同。
- 写入确认、搜索可见与持久恢复需要分别分析：收到写入成功响应，不能直接推出后续 search 已能读到该文档。
- 查询与同步都要考虑规模：深分页、分片数量和聚合影响资源成本，全量与增量同步则必须衔接位点、版本和删除事件。
